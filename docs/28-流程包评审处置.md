## 三 · 分歧与裁决

> 三份评审在**四个地方**给出了不同答案。下面逐条裁，并写明**为什么这么裁**与**裁错的代价**。

### 3.1 「缺四个概念」——26 说是 2 真 2 夸大，25/27 说 4 个都真

**裁决：26 对，但结论要改写。**

- 「跨目标直传」：不是**概念**缺口（接口形状缺、能力不缺——样板就是一条 `exec scp`）→ **R7** 把它从概念清单里撤下，首版走两跳。
- 「角色」：不是新原语，是「带用途名的 profile 引用」→ 但**绑定解析 + 多连接事务**是真缺口 → 保留在清单里，改名为「绑定」。
- 「任务（Job）」：**概念不缺，实现缺**。`exec(cmd, {timeoutMs})` 的超时**无上限**（`ssh.ts:180`），30 分钟是能跑的；`buildrun.py` 自己也是 `o.read()` 读到 EOF 才返回（**不要流、不要取消**）。→ 真正缺的是**流式输出与取消**，而那两样是**用户需求驱动**的（「观察过程中的中间结果」），不是样板驱动的。→ **R10**。
- 「非标量结果通道」：真缺，但载体不是 Source → **R9**。

**代价**：如果我按 24 的四个概念去设计，会为「直传」造一个接口（`Connection.copyBetween()`），
而它的凭据模型（目标 A→目标 B）**根本不存在**——**造了一个用不了的接口**。

### 3.2 「窗口在关，现在做 = 扩 M6」——25 说不成立，26/27 说顺序反了

**裁决：26/27 对**（即：**窗口不成立，顺序要反**）。

三份其实**结论一致**：先实验/尖兵 → M6 → 格式 → 真板跑通 → 才进契约。
分歧只在**「先 M6 还是先尖兵」**：

- 25：先 M6（把执行器接口开到「事务」粒度），流程层后进。
- 27：**先尖兵**（宿主内建一条流程，TS 代码，不是 pack），M6 边界后定。
- 26：W0.5 手搓一次 → M6 → 契约。

**裁决：按 27 的顺序**——**尖兵先，M6 边界后**。理由：
尖兵要跑的正是 buildrun.py 的净支路，而它的第一步是**在客机上跑 `make`**——
**那不是板型包的动作**（客机 `board_pack: null`），
所以尖兵**必然**逼出「非板目标上跑命令」怎么授权的答案——**这正是 C1**。
先写 M6 再做尖兵，等于**先把 C1 的答案猜出来写进契约**，再拿尖兵去验证——顺序倒了。

**代价**：尖兵会晚几天出结果，且它不产出「可用的产品功能」（它是一次性代码）。
这是**故意**的：它买的是「契约不再对着想象冻结」。

### 3.3 最小一版的形状——26 给一套，27 给另一套

**裁决：以 27 的分期为准，以 26 的「最小执行器」为内容。**

| | 26 的最小版 | 27 的最小版 | 裁决 |
|---|---|---|---|
| 流程怎么表达 | 流程包（YAML） | **宿主内建流程（TS 代码）** | **27**：格式从代码里长出来（板型包格式就是这么长出来的） |
| Job | 不做 | 做（开始/状态/流/取消） | **27**：但只做**实现层**，不进契约词汇 |
| 直传 | 不做（两跳） | 不做（两跳） | 一致 ✓ |
| 参数化 | 首版写死一个项目 | 尖兵里做（`inputs`） | **27**（用户原话的核心） |
| 时间线 | 复用现有动作审计的行式格式 | 独立的时间线 + 审计行带 `runId` 外键 | **R8**：并存、关系定死 |
| 契约增量 | W1（挪到 W0.5 之后） | W3（**砍掉原 W1，合并进 W3**） | **R1**：格式先落 `docs/` + `fixtures/`，真板跑通两条后再晋升 `spec/` |

### 3.4 「流程包是不是契约层」——26/27 都问，无人回答

**裁决：首版不是。**（**R1**）

理由链：
1. `AGENTS.md:21` 说「契约层 = `docs/spec/` 五份文档」→ **进了 `spec/` 就是契约层**，
   就有版本承诺、评审义务、对拍测试；
2. 三个前置此刻都没定：**M6 没有实现**（`src/main/` 无 `actions/`）、
   **Stream 契约没定死**（`spec/00:190`）、**多板语义 O11 没结论**（`docs/05:1102`）；
3. 24 自己 §八 Insight 八 说「不必先设计完整流程包……**避免为不存在的问题设计一整套机制**」——
   **它在自己的 Insight 与自己的分期之间选了后者**，这是全文最贵的矛盾。

**连带**：24 §九 的改动清单**作废**；卡片 API（`spec/03`）与 MCP 工具（`spec/04`）**首版不动**。
→ 卡片侧首版**只读**：订阅已有的 tag，不驱动流程。
→ **这意味着用户那张卡的「点击编译」在首版不成立**——见 §五·R1 的代价说明。

| **R2** | **流程包继承 `spec/02` §5.6 的信任模型**：①写步骤要么引用**已声明的动作**（走 M6 全链），要么是自由命令（**必须过同一张危险地板**）；②**启用流程包要人点头**（确认界面展示「会在哪些目标上跑哪些命令」）；③`run_workflow` 与 `execute_action` 同构（`dry_run` → 人确认 → 带 `confirm_id` 重试）；④**角色不许绑到 `local` 当执行目标**（本机只当文件源） | 三份一致指出的 C1；`spec/02:412`「控制面只有『发一条命令』，那它就是遥控器」；`spec/02:786-800` 已有先例 | 不做 → 流程包给 agent 开了一条**在用户机器上执行任意命令**的通道，比 `spec/04:38-47` 禁止的还宽 |
| **R3** | **成功判据统一复用 M6 回读五形式**（tag / `file_equals` / `command_ok` / `verify` / `none`）；`await`/`assert` 是用法不是新判据。**`system.load` 那个 tag 作废** | 「编译成功」不是板上的量测；词表 21 条无 `system.*` | 照用 `system.load` → 私造词表 + 违反「词表只有一个源头」 |
| **R4** | **流程包要有 `inputs`**（封闭类型表照 `spec/02` §4.3：integer/number/string+maxLength/boolean/enum），步骤里 `{input}` 占位，**替换后的最终命令过地板与编码**（§4.6） | `buildrun.py:258` 的 `project = sys.argv[1]` 是它全部的价值；没有参数化则「一件事」= 一个硬编码实例 | 不做 → 每换一个项目就要一份新流程包 → 流程层没有存在意义 |
| **R5** | **placement 是默认，不是唯一**：目的地支持 `path` \| `placement` \| `ask`；placement 词表进**封闭清单**（引用清单外的名字 → 校验报错） | 用户原话是「上传到板子上的**选定位置**」；`buildrun.py:277/279` 的 `--ko-dir/--bin-dir` 就是用户覆盖。24 把「默认值」升级成了「红线」，**把用户的一个明确需求删掉了** | 照 24 → 用户的「选定位置」需求**在契约层消失** |
| **R6** | **旗舰样例改三处**：`insmod` → `depmod -a` + **`modprobe <名字>`**；`system.load` → 真判据；硬编码路径 → `inputs`。另补 `chmod +x` 与「推完再 depmod、勿并发推模块」 | 放置规范 §4 硬规矩 2/6/7；`buildrun.py:435-439` 的实际做法 | 照抄 → **第一份流程包第一天就破坏板子的规矩** |
| **R7** | **跨目标直传要做**（用户 2026-11-15 拍板，**推翻本裁决的初稿**）：发现产物后**不经宿主取回**，由**客机直接 SSH 送到板子**。形态 = **「在源目标上跑一条传输命令」**（普通 action：命令 + 参数编码 + 过地板）＋ **「凭据准备」作为显式的独立一步**（装公钥 = **destructive**，走 R2③ 的确认通道）。**不需要** `Connection.copyBetween()`，**不需要**新的凭据模型 | 2026-11-15 实测：客机 → 板子 `scp` **成功**；板子 `sshd` 在 22 端口 LISTEN；客机 ping 板子 `192.168.5.100` → **网络与凭据都不是障碍**（初稿的判断被实测推翻） | 照初稿 → 产物仍绕宿主中转（一两分钟，见尖兵 §三·F1），宿主磁盘成瓶颈 |
| **R8** | **审计与时间线并存、关系定死**：动作审计（行式、每行 flush）是**追责单位**；时间线是**一次运行的记录**，每阶段引用 `audit_id`；**非动作步骤（客机 exec、两跳传输）也必须产审计行** | `spec/02` §5.4 的行式审计已经在契约里；「扩还是换」没写会让实现各选各的 | 不定 → 出现**三个「发生了什么」的源头**，且「对宿主机的写」完全无审计 |
| **R9** | **时间线是一条新通道**（不是 Source；`SPEC-D20` 是取数侧）；首版传输形状 **poll**（卡片轮询），不订阅 | `spec/00:140` SPEC-D20 是取数侧；`spec/00:190` 连续流的契约**没定死** | 照 24「照 Source 形状做即可」→ 假装已有一条契约，实际没有 |
| **R10** | **判据改三问**：「跨目标 ∨ 长时可取消 ∨ 要给 agent」——有一才进流程层；并加否决项「只有一个步骤 → 就是一次 action」 | 24 的四问是 OR 且④「被审计」几乎恒真，与 §5.4 自相矛盾；三份都指出漏了「长时且需取消」 | 照 24 → 「只有一个步骤、但要被审计」也满足 → 流程层被过度使用 |
| **R11** | **step kind 收成 5–6 个**：`exec`（含 `stream` 参数）/ `file.fetch`+`transfer`（合并，差别只在「谁搬」）/ `action`（引用已声明动作）/ `await`（判据=五形式）/ `assert`（=await+on_mismatch）/ `discover`（产物发现）。**`exec_script` 从清单里删掉**（连「留位置」都不留——逃生门一旦写了表项，agent 就会去用） | 三份一致指出的冗余；`exec_script` 是 24 自己的自相矛盾（kind 表里有、待拍板说首版不要） | 照 24 → 逃生门提前打开，注入面提前打开 |
| **R12** | **现状表按四档重写**：**已实现** / **契约有、实现无** / **设计有、未建** / **真缺**。每格给 `file:line` | 27·C5：24 把「设计中的」当「现有的」，同一份文档前后矛盾（M6 未开工 vs「卡片能调已声明动作」） | 照 24 → 计划按不存在的地基排期 |
