## 决策 ① · capability 词汇表：契约与实现是**两套同名不同义的词表**

### 前因（谁被它卡住）

M3 要写**板型包校验器**（契约 §七 的 24 条规则）。校验器必然要读板型包里的
`requires.capabilities`——但**它拿什么词汇去比对，没有定义**。

而 UI 侧（`connections:list` 的返回值）与运行时侧（`TerminalManager` 决定 pty 还是 pipe）
**已经在读另一套词表**了。三处读三个名字，改一个词就可能只改一处。

### 现状（逐条有出处）

| 位置 | 词表 | 谁在读 |
|---|---|---|
| `docs/spec/02-board-pack.md:25`（板型包 `requires:`） | `shell` / `exec` / `stream` / `files` | **契约层**（包声明「这块板能做什么」） |
| `src/shared/ipc-contract.ts`（`Capabilities`） | `exec` / `pty` / `files` / `exitCode` | **实现层**：UI 的降级判断（`FileBrowser` 禁不禁上传）、运行时选 pty 还是 pipe |

**两套词既不同名也不同义**，而且**根本不是同一个轴**：

- 契约那套是**板子级**的——「这块板支持串口/ADB/SSH，能跑命令、能开 shell、有文件通道」。
- 实现那套是**传输级**的——「**这条连接**能不能跑命令、能不能开 pty、能不能传文件、能不能拿到退出码」。

举个能立刻看出不对的例子：**串口传不了文件**（事实 S7），但**板子**当然有文件通道。
所以「files」在契约里是板子的属性，在实现里是连接的属性——**同一��词，两个意思**。

还有两个更硬的问题：

1. **契约里有 `stream`，实现里根本没有**——Stream 是已知的契约缺口
   （`docs/09` §三「① Stream 契约缺失」）。板型包却**声明了它**。
2. **实现里有 `exitCode`，契约里没有**——而它是串口的关键差异
   （事实 S5：串口拿不到退出码，命令超时要归一成 124）。

### 选项

**A. 两套词各归各位，明确它们不是一回事**（推荐）
- 契约那套**改名**成「板子能力」，加一句定义：`shell` = 能开交互式 shell、
  `exec` = 能跑一条命令拿结果、`stream` = 能推连续流、`files` = 有文件通道。
- 实现那套**保留**（它本来就是传输级），但**改名**成 `TransportCapabilities`
  或加注释说清它是连接级的，避免同名。
- 板型包里**去掉 `stream`**（没实现就别声明——否则校验器按契约判「有 stream 能力」，
  而运行时给不出来）。
- **映射表**（板子能力 → 连接能力）写在契约里，运行时按连接算，UI 按连接算，
  **板型包的 `requires.capabilities` 只用于「这块板至少要有这些能力」的门禁**。

**B. 统一成契约那套**，实现层也用 `shell` / `exec` / `stream` / `files`
- 要改 `src/shared/ipc-contract.ts` 的 `Capabilities`（`pty` → `shell`，加 `stream`），
  以及 `capabilities.ts` / `registry.ts` / `App.tsx` / `FileBrowser.tsx` 一路。
- **`exitCode` 没地方放**——它是实现必需的（串口 false），契约里没有对应词。
- 要动契约 → **升 `apiVersion`**（现在还是 `devboard/v1`，但 v1 尚未发布，可以当定稿前修正）。

**C. 契约那套先冻结，实现层另起一套但**改名**
- 与 A 几乎一样，只是契约层不动（省一次评审）。
- 代价：**同名不同义**继续存在，将来一定有人踩。

### 我的建议：**A**

理由：**它们本来就是两个轴**，硬合成一个词表会逼着实现层长出「板子级」的字段
（`stream` 现在根本没实现，合过去只能给个恒 false，等于把契约缺口藏进类型里）。
A 让两边各自诚实，**代价小**（主要是改名与补定义），而且**不用升 apiVersion**
（契约层只是加澄清，不是改语义）。

**不选会怎样**：M3 的校验器只能「跳过 capabilities 这一项」——
于是 `requires.capabilities` 变成**没人校验的字段**，而它正是「这块板能做什么」的声明。
UI 的降级规则（「串口不能传文件 → 禁上传」）依赖的是**连接级**能力，与包声明无关——
**两套词继续并存，且没人说得清哪个管哪个。**

## 决策 ② · 确实没有回读的动作，怎么声明（O13）

### 前因（谁被它卡住）

契约 §7 规则 15 强制：**`danger: destructive` 的动作必须有 `readback`（形式 1/2）
或 `verify`（形式 4），不得用 `command_ok`**。这是对的——不可逆动作不能盲发。

但有一类动作**真的没有可回读的状态**：点亮一颗 LED、往某个 UART 写一串字节、
触发一次蜂鸣。**契约里没有能表达它们的形状** → 按现在的规则，这类动作
**根本无法声明**。

而 M4 要拿板型包过校验器 —— 如果将来补这类动作，规则 15 会把它拦下来。

### 现状

| 位置 | 内容 |
|---|---|
| `docs/spec/02-board-pack.md` §4.5 | 四种回读形式：tag / file_equals / command_ok / verify |
| 同上，规则 15 | destructive 必须有 form 1/2/4 |
| `docs/05` O13 | **待拍板**：允许 `verify: none`，但必须显式声明且结果标 `unverified` |
| `docs/10` deepseek 版 D4 | 补了这条建议（契约漏了它） |

现在的板型包里**没有这类动作**，所以 M4 暂时不受影响；但**规则 15 没有出口**是真实的。

### 选项

**A. 加 `verify: none` 形式**（推荐）
- 形状：`readback: { kind: none }` 或 `verify: { kind: none }`，
  **必须显式写**（不写就是漏 → 规则 15 拦下）。
- 执行结果标 **`unverified`**（不是 `ok` 也不是 `failed`）——
  契约 §2.1.1 的 `reason` 封闭枚举要加一个码。
- 额外闸门：**只允许 `danger: reversible` 且**声明了用户可见后果的动作用它；
  `destructive` **仍然禁止** `none`（不可逆动作不许「不验证」）。

**B. 不支持这类动作**——没有可回读状态的动作**不声明**
- 契约零改动。
- 代价：AI 想做「点亮 LED」就没有合法路径，只能绕开契约层（更坏）。

**C. 用 `verify` 跑一条恒真的命令**（如 `true`）
- 形状不用改。
- 代价：**形式上过了验证，实质上没验**——比 A 更危险：
  `verify` 的语义是「验证板子进入了目标状态」，而 `true` 什么都没验证，
  却让调用方以为验过了。**明确不推荐。**

### 我的建议：**A**

理由：这类动作**确实存在**，而「显式声明 + 结果标 unverified」把这件事说清楚了。
C 看着最省事，实际是**把「没验证」伪装成「验证过了」**——
正是这个契约一路在防的事（`unavailable ≠ 0` 是同一个道理）。

**不选会怎样**：将来补这类动作时，要么违反规则 15（于是规则形同虚设），
要么走契约外（于是 agent 与卡片都没有合法路径）。

## 决策 ③ · 板型包缺的两个动作，与 `npu.governor` 的归属（O9 剩余 + O15）

### 前因（谁被它卡住）

M4 的判据是「`probe:board` 对 `rk3588-atk` 全绿」——
**板型包必须先过得了自己的校验器**。
而 `docs/06` C4 列的三个动作里，`system.reboot` 已补，
**另两个还悬着**，且其中 `npu.governor.set` **按现在的规格根本实现不了**。

### 现状

| 动作 | 规格 | 能不能做 |
|---|---|---|
| `npu.governor.set` | `echo {governor} > /sys/class/devfreq/fdab0000.npu/governor`，回读 `npu.governor` | ❌ **做不了**：<br>① 板型包**没有** `npu.governor` 这个 tag（`npu.governor` 按 O7 拍板走 `custom`，但包里也没提供）<br>② 规则 12 要求 `readback.tag` **必须**是本包提供的 tag<br>③ 那个节点的 `available_governors` 是 **rkdevfreq 全局列表**（含 dmc/vop2/venc）——写进去大概率是**给别的模块改频率**（O15 的核心） |
| `debugfs.mount` | `mount -t debugfs debugfs /sys/kernel/debug`，回读 `npu.usage` | ⚠️ **规则 15 拦下**：它是 `destructive` 吗？<br>挂 debugfs 是**挂载点**，算系统级改动 → 若判 destructive，则**必须有回读**；而 `npu.usage` 挂上之前读不到（要挂了才有值）→ **自指** |

**还有一个已实测的事实**（今天在真板上量的）：
**这块板的 debugfs 已经是挂着的**（`debugfs on /sys/kernel/debug type debugfs (rw,relatime)`），
`/sys/kernel/debug/rknpu/load` 直接读得到。
→ 所以 `debugfs.mount` 在**这块板上是多余的**——它是为「debugfs 没挂」的板准备的。

### 选项

**A. 两个都不补，把缺口记清楚**（推荐）
- `npu.governor.set` **不做**：那个 `governor` 节点是 rkdevfreq **全局**的，
  写它会影响 dmc/vop2/venc 等其他模块——**语义不清、副作用不明**，
  按契约 §6 的参数注入与危险地板的思路，这种动作**不该由 agent 触发**。
- `debugfs.mount` **不做**：这块板已经挂着；真要做，也应该是**人类在板子上做**，
  而不是 agent 通过一个「回读要靠它自己」的动作来挂。
- 代价：板型包里**只有两个 reversible 动作**（背光、调频策略）+ 一个 destructive（重启），
  `destructive` 的样本**只有一个**（够用）。

**B. 补 `npu.governor.set`，并把 `npu.governor` 作为 `custom.rk3588-atk.npu.governor` 提供**
- 要：新增一个 reader（读 `/sys/class/devfreq/fdab0000.npu/governor`）+ 一个 custom tag +
  枚举值收敛（O15）+ 动作定义。
- 枚举值收敛（O15）：**实测可用值**要现读一次
  `/sys/class/devfreq/fdab0000.npu/available_governors`——
  但那个列表是**全局的**（含 dmc/vop2/venc 的），收敛成「NPU 能用的那些」需要人工判断。

**C. 补 `debugfs.mount`**
- 要：先解决「回读自指」——挂上之后才有 `npu.usage`。
  可能的形状：`readback` 用 `file_equals` 读 `/proc/mounts` 里的 debugfs 行
  （挂载成功 `/proc/mounts` 就会有）——**这条是通的**。
- 代价：挂载是**系统级改动**，危险地板表里**没有**这一档 → 要动契约的地板表
  （改地板表 = 改契约，要升 apiVersion）。

### 我的建议：**A**，并把 O15 的实测补上

理由：

1. `npu.governor.set` 的**语义不明**（写的是全局列表）——契约的参数注入防线
   （§4.6）防的是「参数注入命令」，但这里的问题是「**这个节点到底控制谁**」。
   **在没搞清楚之前把它交给 agent，是不负责任的。**
2. `debugfs.mount` 要动**危险地板表**（改契约、升 apiVersion），
   换来的是一个**这块板上已经不需要**的动作。
3. 代价可接受：`destructive` 已有 `system.reboot` 这个真实样本 ✓。

**顺带两件：已在 2026-11-13 的真机实测里做掉了**（结论记进 `docs/02` §3.1）：

- **O15 的枚举内容**（实测）：
  ```
  /sys/class/devfreq/fdab0000.npu/available_governors
  → rknpu_ondemand dmc_ondemand vop2_ondemand venc_ondemand
    userspace powersave performance simple_ondemand
  ```
  **只有 `rknpu_ondemand` 是 NPU 自己的**，其余 8 个是 rkdevfreq **全局列表**
  （含 dmc/vop2/venc 与 cpufreq 通用档）。
  → **写 `userspace` 到这个节点，是去改一个通用档，不是去改 NPU 的策略。**
  这就把「`npu.governor.set` 的语义不明」从推测变成了**有数据支撑的判断**。

- **C1 的取舍**（实测）：`/sys/class/devfreq/fdab0000.npu/cur_freq` **存在**，
  读出 `1000000000`；`/sys/kernel/debug/rknpu/freq` 同样是 `1000000000`
  但**依赖 debugfs**。
  → **建议选 `cur_freq`**（依赖更少、sysfs 下 always available），
  而前身工程写的 `…/rknpu/devfreq/cur_freq` **不存在**（C1 已按此回滚 ✓）。
  这一条可以直接定，不必再等。

**不选会怎样**：`npu.governor.set` 继续挂着一个**实现不了**的规格
（规则 12 必然拦下它）——M4 一跑就红。

## 附一 · 不用你定、我已经定了或记下的

| 项 | 结论 | 在哪 |
|---|---|---|
| capability 词汇表的**实现层**（连接级） | 保留 `{exec, pty, files, exitCode}`，但**要改名或加注释**说清是连接级 | 决策 ① |
