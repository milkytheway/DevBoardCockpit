## 〇、一页结论

这个工程的**契约层质量很高**。它不是在描述一个理想系统，它是在描述一台真板子上
已经踩过的坑——`spec/02 §七` 那 19 条校验规则，每一条背后都是一次真实故障。
`spec/01` 的五态模型、`spec/02` 的 poll group 模型、`spec/04` 的危险地板，
三者合起来构成了一个能落地的「驾驶舱」语义。

问题**不在契约的核心思想**，而在**四个边界上的词汇与流程**：

| 边界 | 症状 | 影响 |
|---|---|---|
| 契约 ↔ 设计 | MCP 传输、动作分档、卡片存储，三处正面冲突 | 实现者按哪份写都能写错 |
| 契约 ↔ 事实清单 | 状态词三分裂、单位换算责任沉默 | 实现者不知道该认哪份 |
| 契约 ↔ 数据 | 绑定字段名与包 id 三方不一致，连接 profile 断链 | **主力板绑不上板型包** |
| 契约 ↔ 流程 | Q1 被单方面执行、三套 Q 编号、三套 D 编号 | 「拍板」这件事本身失去意义 |

外加两类具体欠账：**黄金向量不完整**（`cpu.usage` 的差值样本根本不存在），
以及**前身的零代码加板路径与管道模式行编辑被静默丢弃**。

按严重度排序，本报告共 **5 条 P0 / 29 条 P1 / 24 条 P2 / 20 条 P3**，
外加 **5 条待决清单**（T-1 ~ T-5）。

**建议的收口顺序**：先修 2 条「不需要任何决策就能修」的硬伤（P0-1 的数据部分、
P0-2），再补 3 条契约空洞（P1-9 `verify`、P1-3 单位换算、P1-6 状态迁移缺边），
再让用户裁 T-1/T-2 两项冲突，最后补 fixtures 与事实标注。
**P0-1 的字段名部分与 T-3 绑定**——改字段名要改契约，需用户拍板。

### P0-1 · 连接 profile 指向已删除的板型包（现役硬伤）

**证据**

| 位置 | 内容 |
|---|---|
| `profiles/targets/board-adb.json:5` | `"board": "atklrk3588"` |
| `profiles/targets/board-serial.json:5` | `"board": "atklrk3588"` |
| `profiles/boards/rk3588-atk/board.yaml:19` | `id: rk3588-atk`（仓库里唯一的包） |
| `docs/03-迁移对照表.md:100` | `profiles/boards/atklrk3588.yaml`（Codex 起草）**作废并删除** |

**影响**

两块板的连接都绑不到任何板型包。按 `spec/02 §10.1`，终端与文件互传照常可用，
但**监控与控制全部不可用**。而这条承诺的设计意图恰恰是「用户拿一块新板来，
先能连上、能敲命令，再补一个包」——现在这条路在自家主力板上就断了。

目前实际能工作，靠的是 `spec/02 §十` 的**兜底路径**（读 `board.model` → 按
`match` 匹配），因为 `board.yaml` 的 `match.models` 含 `ATK-DLRK3588`，
而实测型号是 `ATK-DLRK3588 Board`（substring 命中）。
**这是巧合，不是设计**：那个 `board` 字段静默失效，没人报错。

**附带问题：同一个字段三种说法**

| 出处 | 字段名 | 值 |
|---|---|---|
| `docs/spec/02-board-pack.md:598`（契约） | `board_pack` | `rk3588-atk` |
| `docs/05-决策记录.md:82`（ADR D5） | `board` | — |
| `docs/spec/04-mcp-tools.md:57`（契约） | `board_pack` | — |
| 实际数据 | `board` | `atklrk3588`（错） |

**建议**

1. 字段名以契约为准统一为 `board_pack`（`spec/04` 已经用它，改一处少改一处）；
   若坚持用 `board`，必须写进 `spec/02 §十` 并在 `spec/04` 对齐。
2. 数据的值改成 `rk3588-atk`。
3. **字段名部分要动契约 → 归入待决清单 T-3 的绑定键小项**；
   **数据的值部分不需要任何决策 → 可直接修**。

### P0-3 · MCP 传输形态：契约与设计正面冲突（**用户本轮不决定 → 记入 T-1**）

**证据**

| 出处 | 原文 |
|---|---|
| `docs/spec/04-mcp-tools.md:448-449` | 「**倾向 HTTP + 本地端口**，理由：GUI 本来就是一个用户会打开并一直开着的东西，agent 是**连到已经在跑的 GUI**」 |
| `docs/spec/04-mcp-tools.md:445`（stdio 的问题） | 「一个正在被用户使用的桌面应用，让 agent 去启动它，很别扭」 |
| `docs/spec/04-mcp-tools.md:459-470` | 发现文件 `%LOCALAPPDATA%/DevBoardCockpit/mcp.json`，含 `transport/host/port/pid/cards_dir`，「这个文件是**唯一**的耦合点」 |
| `docs/04-架构设计.md:320` | 「**传输**：stdio。两种启动方式——」 |
| `docs/04-架构设计.md:107` | 「\| MCP \| `@modelcontextprotocol/sdk` \| **stdio** \|」 |

**两个叠加问题**

1. **发现机制整体丢失**：`docs/04` 全文没有出现 `mcp.json`、端口、发现文件中的任何一项。
   契约 §7.1 把「具体形态由 `docs/04` 决定」与「本契约只要求『agent 能发现并连上』」
   同时写下；`docs/04` 选了 stdio，等于默认了「agent 自己拉起 GUI」——
   于是发现机制需要有人补，但没有人补。**结果是 agent 无从知道这个 MCP server 在哪。**

2. **独立进程路径违反 ADR D2**：`docs/04-架构设计.md:322` 给了第二种启动方式
   「独立进程 `devboard-cockpit --mcp-stdio`」。若它真是独立进程，它**读不到**
   main 进程里的卡片清单与卡片运行时日志——ADR D2 的全部论证
   （`docs/05:30-35`：「用普通函数调用互操作，不跨进程」）当场失效。

**建议**：见 T-1。两个选项的代价已经算清楚，留在那里由用户选。

### P0-4 · 动作分档：ADR、契约、设计三方互不相同（**用户无偏好 → 记入 T-2**）

**证据**

| 出处 | 基数 | 字段名 | 声明位置 |
|---|---|---|---|
| `docs/05-决策记录.md:109-110`（ADR D7） | **三档** `read`/`reversible`/`destructive` | `tier` | **卡片 manifest** |
| `docs/spec/02-board-pack.md:383-388`（契约） | **两档** `reversible`/`destructive` | `danger` | **板型包** |
| `docs/spec/02-board-pack.md:451-453`（契约） | — | — | 明写「板型包里也**没有** `danger: readonly` 的动作——**动作一律是写**」 |
| `docs/spec/03-card-manifest.md:228-231`（契约） | — | — | 明写「**卡片不声明 `danger`**……会被校验器拒绝（schema 封闭）」 |
| `docs/spec/03-card-manifest.md:408`（契约 §九 规则 11） | — | — | 「卡片**不声明** `danger` / `readback`」 |
| `docs/04-架构设计.md:179-180`（设计） | 三档 | — | 声称「契约的档位叫 `readonly` / `reversible` / `destructive`」 |

ADR D7 那句「每个 action 在 manifest 里声明 tier」就变成了误导。

**建议**：见 T-2。

### P0-5 · 卡片沙箱存储：契约承诺了一件设计层封死的事

**证据**

| 出处 | 内容 |
|---|---|
| `docs/spec/03-card-manifest.md:298` | 沙箱表：「**存储** \| 只能写卡片自己的命名空间（布局、偏好）」 |
| `docs/spec/03-card-manifest.md:299` | 「**文件** \| 不可读写宿主机文件系统（**除布局存储的受控接口**）」 |
| `docs/04-架构设计.md:249` | 「**不给 `allow-same-origin`** → 卡片在独立不透明源里，碰不到宿主 DOM / **存储**。」 |

**技术事实**：`<iframe sandbox="allow-scripts">` 不带 `allow-same-origin` 时，
文档处于**不透明源（opaque origin）**，`localStorage` 访问抛 `SecurityError`。
契约承诺的「写卡片自己的命名空间」在设计选定的沙箱模型下**无法兑现**。

**而且那个「受控接口」从来没被定义过**：`spec/03 §七` 的卡片 API 全集是
`tags.get` / `tags.subscribe` / `tags.subscribePattern` / `tags.list` /
`cockpit.degradation()` / `cockpit.actions.invoke()` —— **没有 `cockpit.storage.*`**。
「布局存储的受控接口」这个短语在全套文档里只出现这一次，既无 API、无参数、
无权限模型、无执行点。

**影响**：卡片开发者按 `spec/03` 写代码时会去用存储能力，然后在运行时撞上异常，
而契约上并没有任何东西告诉他「别用」。

**建议**（三选一，需用户定）：
1. 契约降级——把存储行改成「v1 无存储能力；布局与偏好由宿主管理」，
   并删掉「受控接口」这个未定义短语；
2. 设计放开——给 `allow-same-origin` 并提供 `cockpit.storage.*` API（但这要重新评估
   「卡片碰不到宿主存储」这条安全承诺）；
3. 契约补契约——定义一个受控的 `cockpit.storage.get/set(key, value)`，
   由宿主代为落盘到每卡独立命名空间。

## 二、P1 —— 契约 / 设计 / 数据之间的不自洽

> 这一批不会立刻炸，但会让实现者做出**错误的选择**，且错了很难自查出来。

### 2.1 词汇表：同一个语义多个名字

**P1-1 · 状态词三分裂**

| 出处 | 用的词 |
|---|---|
| `docs/spec/01-tag-contract.md:111`（契约权威） | `unavailable` |
| `docs/02-设备事实清单.md:153`（G2）与 `:170`（§5 第 5 条「`unknown` 语义（G2）—— 继承」） | `unknown` |
| `docs/spec/01-tag-contract.md:309`（名词对照「现有代码对应」） | `None` |
| `docs/04-架构设计.md:207` | `unavailable` |

`docs/02` 自称「**唯一事实源**」「全库最不能丢的一篇」，却把契约的状态词换了一个。
「继承」两个字尤其误导——继承的是**语义**（缺失 ≠ 0），不是**词**。
**建议**：统一到 `unavailable`；`docs/02` G2 保留「缺失 ≠ 0」的结论，词改过来。

**P1-2 · ADR D6 的白名单方法名在契约里一个都不存在**

| ADR D6（`docs/05:96`） | 契约 `spec/03 §七` |
|---|---|
| `getTag` | `tags.get(name)` |
| `subscribeTag` | `tags.subscribe(name, cb)` |
| `listTags` | `tags.list()` |
| `setAction` | `cockpit.actions.invoke(...)` |
| `log` | **不存在** |
| `notify` | **不存在** |
| — | `tags.subscribePattern(pattern, cb)`（D6 漏了） |
| — | `cockpit.degradation()`（D6 漏了） |

`log` 与 `notify` 在契约里没有定义，因此**没有参数、没有返回、没有权限模型、
没有执行点**——而卡片运行时日志恰恰是 agent 的「自测眼睛」（`spec/04 §1.2`）。
`docs/04 §6.4` 描述了卡片错误如何进日志，但没有说是经由 `log` 这个 API。

**建议**：把 D6 的方法名列表替换成 `spec/03 §七` 的全集；
`log` / `notify` 要么在契约里补定义（谁写、写在哪、卡片能不能读回），
要么从 D6 删掉。

**P1-3 · 能力层词汇：三层三套名字**

| 出处 | 观测侧 | 控制侧 |
|---|---|---|
| `docs/00-项目愿景.md:32-33`（上位约束） | Metric / Video / File / Shell | Action / **Command** |

`Command` 在契约里根本不存在——`spec/02 §4.1` 恰恰明写
「如果控制面只有『发一条命令』，那它就是遥控器」。而 `Stream` 在契约里只有
`spec/00 §七` 一句「目前只有一个占位定义，没定死」，板型包却已经把它写进

`docs/spec/01-tag-contract.md:29` 的示例块写 `mem.total`，

### 2.2 契约里的空洞

**P1-5 · `verify` 被校验规则引用，但从未定义**

`spec/02 §七` 规则 15：「`danger: destructive` 的动作必须有 `readback` 或 **`verify`**」；
但 `spec/02 §4.4` 只定义三种回读形式（`tag` / `file_equals` / `command_ok`），
`docs/04 §7` 的执行流程同样只列三种。
而 `docs/06` C4 的 `system.reboot`——**唯一一个 destructive 候选**——恰好需要它。

**建议**：要么定义 `verify`（结构、判定方式、执行点），
要么把规则 15 改成「必须有 `readback`」，并让 `system.reboot` 走 `command_ok`。

**P1-6 · 单位换算的责任，契约完全沉默**

`spec/02 §2.4` 的 `meminfo` kind 只列参数 `path` 与产出 `total_bytes/used_bytes/usage`，
全文**没有一句说「谁负责 ×1024」**。但：

- `docs/02-设备事实清单.md:69`：「源单位是 kB，**reader 必须 ×1024**」
- `docs/06` C6 明确要求写死这条。

温度同理：`docs/02 §3` 写「毫摄氏度，如 `32384`」、`31461 → 31.461 °C`，
而 `spec/01` 的单位列直接是 `celsius`——**÷1000 的责任在契约里没有任何位置**，
C6 也只覆盖了内存，没覆盖温度。

**建议**：在 `spec/02 §2.4` 的 kind 表加一列「单位换算」，
或加一条通用条款：「**契约只认 SI 单位；reader 负责换算**」。
温度必须一并写进去。

**P1-7 · 状态迁移表缺边**

`spec/01 §2.1` 的迁移表有 16 行，但缺：

| 缺哪条边 | 为什么必须有 |
|---|---|
| `ok → error` | `spec/01 §二` 定义 `error` = 「**应该能读**，但读取或**解析失败**」——读成功了再解析失败，必须能从 ok 过去 |
| `pending → stale` | 首读 pending 后第二次采样失败 |
| `unavailable → stale` / `unavailable → error` | 资源回来但第一次读失败 |
| `error → stale` | 资源回来但拿到的是旧值 |
| `stale → pending` | 资源回来需要重建基线 |
| `(无) → unavailable` | `docs/04 §11.2` 要求「板子不在 device 状态 → 位号转 `unavailable`」，但**从未被读过的** tag 没有这条边 |

另外，表的首行「（无）→ `pending`」只覆盖「需要两次采样做差」的 tag。
**非差值 tag（如 `mem.total_bytes`）的首次读在契约里无状态可归**——
这是五态模型里一个真实存在的空白。

**P1-8 · `npu.usage` 的语义描述与数据源性质不符**

`spec/01` 核心词表写 `npu.usage` 语义 = 「**过去 1 秒内** NPU 各计算核利用率的**最大值**」，
`gpu.usage` = 「**过去 1 秒内** GPU 执行非空闲指令的时间占比」。
但实际来源是 `/sys/kernel/debug/rknpu/load` 与 `/sys/class/devfreq/*/load`——
**都是瞬时快照，不做差**。只有 `proc_stat` 类才做差。

而 `spec/04 §2.1` 明写 `describe_tag` 返回的 `semantics` 是「**防误用的关键**」。
一句不准确的语义会直接误导 agent——它会以为 `npu.usage` 是窗口平均值。

**建议**：把这类 tag 的语义改成「**当前**读数」（并说明各核取 max），
只有 `proc_stat` 系才写「过去 1 秒内」。

**P1-9 · 连接 profile（target）没有契约**（**用户已定：本轮不补，记为待办 T-3**）

契约五份没有一份定义 target 的字段、必填性、未知字段策略。
`docs/03-迁移对照表.md:20` 承诺「新增 schema 校验（旧版没有）」——**但校验什么，没有写**。
`docs/04 §3` 只规划了 `src/main/profiles/schema.ts` 这个文件名。

前身那张 options 表（`docs/legacy/旧工程-如何加一块板.md`）只存在于 legacy 文档里，
而它恰好是「零代码加板」这条产品体验的全部内容：

| transport | option | 含义 |
|---|---|---|
| adb | `adb_path` / `serial` | adb 路径 / 板子序列号 |
| serial | `port` / `baudrate` | 端口 / 波特率 |
| ssh | `host` / `port` / `username` / `key_filename` / `password` | 主机 / 端口 / 用户 / 私钥 / 密码 |
| 通用 | `pty` / `prompt` / `commands` | 是否真终端 / 提示符 / 快捷命令集 |

**P1-10 · `pty` 语义没定义，而管道模式行编辑被误判为「xterm.js 自带」**

`docs/03-迁移对照表.md:32` 把 `ui/keymap.py` / `line_editor.py` / `console_input.py`
判为「丢弃」，理由「xterm.js 自带」。

**但 xterm.js 只带 PTY 流。** 管道模式（`adb shell` 无 PTY）下远端没有 readline，
行编辑**必须由本地做**——这正是前身 `LineEditor` 存在的唯一理由，
也是事实 A1 明写的对策：「用 `adb shell`（无 PTY），**自己画提示符、自己做行编辑**」。

前身为此专门写了 `console_input.py` + `keymap.py`（还带单测），现在连同单测一起
被判为「xterm.js 自带」而丢弃了。而 `pty` 这个字段在契约层从未被定义——
`spec/02 §十` 的示例里出现过一次（在一份讲板型包的文档里），`docs/04` 全文没提。

**这条与 P1-13 一起看**：前身那条「呈现形态属于 profile 而不是代码」的重要教训，
在新契约里没有落点。

**P1-11 · capability 词汇表没有定义，UI 降级规则断链**

前身 `capabilities()` 返回 `{shell, exec, stream, files}`，
UI 读它决定禁用哪些控件（事实 S7：串口传不了文件 → 禁用文件浏览器）。
`docs/02 §5` 第 2 条明确写「**能力协商驱动 UI 降级**」是要继承的结论。

新工程里：`spec/02` 的 `requires.capabilities` 是**板型包的要求**，
`spec/04` 的 `list_capabilities()` 返回 `{transports, features}`——
**连接自身声明什么能力、取值域是什么、谁来填，全部未定义。**

附带：板型包 `requires.capabilities` 含 `files`，但事实 S7 明写串口传不了文件，
而 `profiles/targets/board-serial.json` 正绑这个包。虽然 `requires` 按 `spec/02 §10.2`
是「信息，不是限制」，但它在**唯一那份串口绑定**上宣称了一个串口给不出的能力。

**P1-12 · `docs/02` 里 `capabilities()` 的继承结论与新契约的 `requires` 语义不同源**

见 P1-11。补充：`spec/00 §五` 说旧 `core/targets.py`「留用」，并注明
「加 capability 面（`pty`、`files` 已经是雏形）」——`pty` 与 `files` 正是
P1-10 和 P1-11 缺定义的东西。

**P1-13 · 用户级 profiles 目录：前身最顺手的加板路径被丢了**

前身：把 JSON 丢进 `%LOCALAPPDATA%\DevBoardConsole\profiles\`，**重启，板子出现**。
零代码、零 git、零发版。

新工程：`docs/03 §4` 只说旧用户数据目录改名保留，
**没说新应用会读 `%LOCALAPPDATA%\DevBoardCockpit\profiles\`**。
`profiles/` 躺在仓库里，`profiles/boards/README.md` 还把「新增一块板」指向 `docs/spec/02`。

对比之下，**卡片那条路做对了**：`docs/04 §6.1` 明确「卡片根目录（**用户目录 + 内置目录
合并，同 id 用户优先**）」。**同一个工程里，两个扩展点待遇不一致。**

**P1-14 · `QUICK_COMMANDS` 丢弃了，但数据里还留着残骸**

`docs/03 §4` 把 `QUICK_COMMANDS` 列为「明确不迁移」，理由「换『卡片 + tag + 动作』体系」。

但四个 target profile **全都还带着 `"commands": "adb" | "serial" | "ssh"`**，
而这个 option 在新契约里没有任何承接者（spec 四份里没有 `commands` 概念，
`docs/04` 的 renderer 目录里也没有）。更尴尬的是 `profiles/targets/local.json` 的
`"commands": "ssh"` —— 从 `ubuntu-ssh.json` 复制来的笔误，
**而且没人会注意到，因为没有 schema 会拒绝它**（P1-9）。

同时，替代物「卡片 + 动作」目前**一张卡都没有**（`cards/` 目录不存在），
所以「新人上手即有 8 个常用命令」这块体验在新工程里目前是零。

**P1-15 · Stream 契约完全缺失**

`spec/00` 三处提到它（`§二` 能力层、`D4`「流走另一条 API」、`§七` 待办），
但**没有任何一份 spec 定义 Stream 的字段、API 或权限**。
而 `docs/00 §二` 把 Video / File / Shell 列为能力层，
板型包也已声明 `requires.capabilities: [..., stream, ...]`。
`spec/04` 的工具清单里也没有任何与流相关的工具。

**HDMI 采集卡（M8）整条线没有契约。**

**P1-16 · `spec/03` 的 manifest 无连接绑定字段，多板语义在两层不一致**

`spec/03` 的字段全集：`apiVersion/kind/id/name/version/description/entry/
requires{tags,actions,min_board_pack}/layout{...}/permissions{read,write}/actions[]`
——**没有任何字段指明这张卡连的是哪块板**。

而 `spec/03 §九` 规则 5 写「`permissions.write` 里每个动作 id 在**当前连接的**板型包里存在」，
`docs/04 §5.3` 又说「订阅关系按 `(connectionId, tag)` 维护」，
但 `docs/04 §10` 的 `tag:snapshot { tagIds }` **没有 connectionId**。

契约层隐含全局单连接，设计层按连接隔离。`docs/04 §8` 把「目标切换器」列为内置卡、
`§13` 把「多板管理」推到 M8，所以「一次一块板」可能是刻意的——
但**契约层没把这个取舍写下来**，将来加多板就得改 `spec/03`（升 apiVersion）。

**P1-17 · `docs/04 §5.2` 的 TS 类型漏了 `enum`**

`spec/01 §一` 的类型列是「number / string / boolean / **enum**」，
`docs/04 §5.2` 写的是 `value: number | string | boolean | null;` —— **没有 `enum`**。
而 `docs/06` C3 恰恰建议新增 `cpu.governor`（enum）/ `npu.governor`（enum）：
若 T-2/T-4 拍板为「进核心词表」，TS 侧类型立刻不够用。

### 2.3 设计与契约的措辞冲突

**P1-18 · `docs/04 §5.2` 已经单方面替契约拍板了 `reason` 字段**

`docs/04 §5.2`：
```ts
reason?: string;   // unavailable/error 的原因（见 06 核对 C5）
```
而 `docs/06 §三` Q5 写的是：「字段名待定（`reason` / `detail`）；**契约里目前还没位置**」。

设计层把一个明确标注「待定、契约里还没位置」的开项，写成了已定的 TS 字段。

**P1-19 · `docs/04 §11.2` 引用了一个不存在的动作，还引错了核对项**

`docs/04 §11.2`：
「debugfs 没挂载 → `unavailable` + reason `debugfs_not_mounted`；界面给出
**`debugfs.mount` 动作按钮**（见 06 核对 **C5**）」

`debugfs.mount` 是 **C4** 的候选动作，**板型包里没有这个动作**；
而 C5 讲的是 reason 码。引用链两处都错。

**P1-20 · `destructive`「默认 dry-run」与确认流互斥**

`spec/02 §4.2`：`destructive` 的行为 = 「**必须二次确认**，且**默认 dry-run**」。
`spec/04 §2.4.1` + `docs/04 §7`：`destructive` → 返回 `needs_confirmation` →
**人点确认** → agent 带 `confirm_id` 重试 → **这次才真的执行**。

若 `destructive` 默认 `dry_run=true`，确认通过后的重试仍只会回显、不会执行。
两者不能同时为真。

**P1-21 · 装卡授权在「板子没连上」时无从定档**

`spec/03 §3.2` 步骤 1：「取它在新板型包里的 `danger` 等级」；
`spec/03 §九` 规则 5 却允许「连不上板时跳过此检查，标注『未验证』」。

**没有板型包 → 不知道是 reversible 还是 destructive → 授权弹窗问什么？**
（`spec/04 §2.4.1` 说 agent 授权与卡片授权「是另一回事」，
但 agent 侧的授权**同样没有记录/存储定义**。）

**P1-22 · 两套确认凭据，生命周期未统一**

`spec/04` 的 `consent_id`（装卡）与 `confirm_id`（执行）命名不同、
有效期与作用域都没定义；`execute_action` 返回 `needs_confirmation` 时
**没有 `expires_at`**（只有 `confirm_action` 工具返回）。

**P1-23 · 参数校验在设计层没有落点**

`spec/04 §2.4` 的执行流程第 3 步是「校验参数（范围、枚举）→ 否则 `invalid_params`」；
`docs/04 §7` 的 7 步流程**没有这一步**，也没有 `invalid_params` 这个失败原因。
而 `spec/02 §4.3` 特意写了「危险动作的参数范围是安全边界的一部分」。

**P1-24 · 布局状态归属：renderer 还是 main**

| 出处 | 说法 |
|---|---|
| `docs/03-迁移对照表.md:66` | 布局编辑器 → `src/renderer/layout/` |
| `docs/04 §3` 目录树 | `src/renderer/ layout/ cards/ terminal/ panes/ theme/` |
| `docs/04 §9.2` | 「布局 \| `layout/` \|」——列在 main 一侧 |
| `docs/04 §9.3` | 「卡片清单、卡片运行时日志、**布局**、位号表**都住在 main 进程**」 |
| `docs/04 §10` | `layout:get/:set/:export/:import` 方向 **R→M**——暗示状态在 main |

MCP 的 `set_layout`/`get_layout` 在 main，读的是 renderer 的状态——
**跨进程双向依赖，没有定义。**

**P1-25 · 词表模块落点：同一份设计文档两个答案**

`docs/04 §3` 目录树：`src/main/tags/ … vocabulary.ts …`
`docs/04 §4.1` 映射表：「`spec/01` tag 契约 \| `src/shared/tag-vocabulary.ts`」

`docs/04 §4.3` 强调「实现层的词表必须**从契约生成**」——
那它到底属于 `shared`（main+renderer 共用）还是 `main/tags`（运行时私有）？
这直接决定「生成器」放哪。

**P1-26 · `list_data_sources` 的映射在设计层降了粒度**

`spec/04 §2.1` 明确返回 **reader 粒度**
（`{ id, board, poll_group, reader, kind, interval_ms, provides, status }`，
并解释「哪些 tag 可读」这个问题的答案天然按 reader 组织）；
`docs/04 §9.2` 却把它映射成「`tags/` 的当前位号表」——**tag 粒度**。
且 §3 的目录树里 `src/main/tags/` 没有 `describe.ts`，而 §9.2 引用了它。

**P1-27 · `spec/04` 内部引错章节号，设计层抄了同一个错**

`spec/04 §2.3` 的 `validate_card`：「静态校验，**不安装**。校验规则见
`03-card-manifest.md` **§八**」——§八是「目录布局」，校验清单在 **§九**。
`docs/04 §9.2` 抄了同一个错（「校验规则 = spec/03 §八」），
而 `docs/04 §4.1` 又写对了（「契约 **§九** 的校验规则（含负例）」）——
**同一份设计文档里两处指向不同章节。**

**P1-28 · 卡片根目录：单根 vs 双根；内置卡无契约**

`spec/04 §2.3` 的 `install_card`：「把卡片目录放进**卡片根目录**」（单数）。
`docs/04 §6.1`：「卡片根目录（**用户目录 + 内置目录合并，同 id 用户优先**）」。

契约里**没有「内置卡」概念**：`docs/04 §8` 说内置卡「与用户卡片同一套布局，**不可删除**」，
但 `spec/03` 的 manifest 规范只面向用户卡目录——没有内置卡 id 白名单、
没有「不可删除」的表达方式、没有内置卡 manifest 样例。

**P1-29 · 危险地板表没有版本与演进规则**

`spec/02 §5.2` 说「可执行的版本由实现层提供」，但地板表本身属于**契约**。
契约升版时地板表怎么演进、由谁裁决，没有规则。
而 `spec/00 D14` 说「危险等级有地板」是让 D12 与 D13 同时成立的机制——
机制本身没有版本策略，等于留了个后门。

### 4.2 黄金向量：`fixtures/`

**P3-8 · 样本的分段格式 ≠ 契约规定的围栏协议**

| 出处 | 格式 |
|---|---|
| `docs/spec/02-board-pack.md:175`（契约） | `echo '###R cpu STAT'; ...; echo '###E cpu' ; echo '###R gpu LOAD'; ...; echo '###E gpu'` |
| `fixtures/metrics/snapshot-sample.txt`（实际） | `###STAT` / `###INFO` / `###GPU` / `###NPU` / `###MEM` / `###TEMP` / `###END` |

三个具体差异：围栏形状（per-reader vs 扁平段落）；命名依据
（**reader id** vs **内容种类**）；`###INFO` 是独立段——
但新设计里 `/proc/cpuinfo` 是**同一个 `cpu` reader 的第二个参数**
（`proc_stat` kind 要 `stat_path` + `cpuinfo_path`），两段应合并成一个 `cpu` 段。

**后果**：`spec/02 §2.4` 的 kind 表只规定参数与产出 sample，
「怎么从板子上取」明确**委托给实现层**——于是 fixture 反倒成了事实上的格式规范，
但它是**旧工程的格式**。而 `fixtures/README.md` 的规矩是「**样本只增不改**」。
**按契约实现的解析器喂不了现有样本。**

**P3-9 · `cpu.usage` 的差值黄金向量根本不存在**

`cpu.usage` 必须两次采样做差（`spec/01 §3.3`、`spec/02 §2.4`「**需要两次采样**，
首次为 pending」）。但仓库里只有**一份** `/proc/stat`——
`proc-stat.txt` 与 `snapshot-sample.txt` 的 STAT 段**逐字节相同**。
「样本只增不改」意味着**不能改这两个文件**，只能**加**一份新样本。

**P3-10 · 无样本的 reader / 动作 / 分组**

| 缺什么 | 为什么重要 |
|---|---|
| `board` reader（`file_read`，`/proc/device-tree/model`，带 NUL） | `strip_trailing_null` 无从验证；且 `board.model` 驱动**自动识别**（P0-1 的兜底路径） |
| `npu_devfreq`（`measure: duty_cycle`） | duty_cycle 路径无向量；`100@1000000000Hz` 只在散文里出现过 |
| `rare` 轮询组（30000 ms） | 整组无向量 |
| `backlight.set` 的 readback | 实测 `200`/max 255 只在散文里 |
| `cpu.governor.set` 的 readback | 实测 `schedutil` 只在散文里 |

**P3-11 · `snapshot-degraded.txt` 是全库最有价值的一个文件，应保留并扩充**

它是**构造**的，每个 section 用不同的方式坏掉：

| Section | 畸形 | 要求的行为 |
|---|---|---|
| `###STAT` | 只有聚合 `cpu` 行，**无 `cpu0`–`cpu7`** | `cpu.core.*.usage` 必须 `unavailable`，**不是 0** |
| `###INFO` | `CPU part : 0xZZZ` | 解析不出 hex → cluster 不可用，**不能编一个簇名** |
| `###GPU` | **空段** | `unavailable`，**不是 0** |
| `###NPU` | **空段** | 同上 |
| `###MEM` | 有 `MemTotal`，**无 `MemAvailable`** | **部分可用**：`mem.total_bytes` ok，`mem.used_bytes`/`mem.usage` 不可用 |
| `###TEMP` | `broken-line` / `x=` / `name=notanumber` | 三个 `temp.*` 全 `unavailable` |

关键区分：**空段 ≠ `0@300000000Hz`**。
`snapshot-sample.txt` 里 GPU 真的读 0%，`snapshot-degraded.txt` 里是空段。
把空段当「duty = 0」的解析器，会把 `unavailable` 塌缩成 `0`——正是契约禁止的那件事。

**P3-12 · `cpuinfo-excerpt.txt` 藏着三个边界**

1. **processor 块的字段集不同**：block 0 有 `BogoMIPS`/`Features`，block 4 没有。
   按固定字段序解析的解析器会在第二块上崩。
2. **分隔符风格不同**：`CPU part\t: 0xd05`（冒号前是 tab）vs `CPU architecture: 8`（无空格）。
   不能假设 `\t: `。
3. **只有 2/8 个处理器在样本里**：核 1,2,3,5,6,7 没有 cluster 映射，
   必须报 unknown，且绑定不得为没见过的核发出名字。

**P3-13 · `serial-session.log` 藏着三个边界**

1. 末行 `=== session closed 2026-11-12 02:20:10 ===` **无时间戳前缀**，其余行都有。
2. 一行长输出**被时间戳边界截断**：`drwx------ ... lost+fou` / `nd/`——
   不做续行拼接就会把 `lost+found` 弄坏。
3. 逐键回显行：`l` / `s` 各占不同时间戳——「一条日志行 = 一条终端行」的假设会崩。

**P3-14 · `MemAvailable` 数字冲突（一个必须查证的矛盾）**

| 出处 | 值 | 推出的 `mem.usage` |
|---|---|---|
| `fixtures/metrics/snapshot-sample.txt` | `MemAvailable: 6104320 kB` | ≈ **24.71 %** |
| `docs/02-设备事实清单.md:70`（🟢「实测」） | `MemAvailable 7655664 kB` | ≈ **5.58 %** |

两个都像实测值，都没注明是否同一时刻。
fixture 是黄金向量，实现会照抄它——
于是**卡片显示的内存占用会与 `docs/02` 对不上**。其中一个是陈的。

**P3-15 · 契约的示例包自身违反契约的校验规则**

`spec/02 §一` 的标准示例包：`poll_groups.rare.readers: [board, npu_devfreq]`
引用了 `board` reader，但示例的 `readers:` 列表里**没有定义 `board`**。
而 `spec/02 §七` 规则 17 要求「每个 reader 必须属于恰好一个 poll group」，
规则 10 要求未知顶层字段报错——**契约自己的示例包不满足契约自己的规则**。

**P3-16 · 契约示例包与真实包已漂移**

| | `spec/02 §一` 示例 | `profiles/boards/rk3588-atk/board.yaml` |
|---|---|---|
| `board` reader | **不存在**（但被 poll group 引用） | 存在（`file_read`，`/proc/device-tree/model`） |

| `match.models` | `[ATK-DLRK3588]` | `[ATK-DLRK3588, ATK-DLRK3XXX]` |

**P3-17 · `match.models` 里的 `ATK-DLRK3XXX` 是死字面量**

`mode: substring`（`spec/02 §11` 只允许 `exact`/`substring`，**不支持通配**）下，
`ATK-DLRK3XXX` 是字面的 X 字符，永远匹配不到 `ATK-DLRK3588 Board`。
看起来本意是 `ATK-DLRK3*` 家族。**这正是 substring 模式的校验器不该静默当通配的东西。**
且它未进入 `docs/06` 的任何一条。

**P3-18 · `spec/02 §4.4` 的死参数措辞与自己的示例冲突**

`spec/02 §4.4`：「**校验器两处都扫**：只在一处出现过的参数算『死参数』，
两处都没出现过的 `{param}` 算『未声明』」。
按字面读，`backlight.set` 的 `value`（出现在 `command` 与 `readback.expect`）、
`cpu.governor.set` 的 `governor`（同上）都会被判成死参数——
**而 `spec/02 §一` 的示例包正是这个形状**。

即 command 必须用上每个声明的参数；真实包满足那一版。）

**建议**：把规则 14 的措辞改成「**在 `command` 里必须用到每个声明的参数**」，

**P3-19 · 版本字段三种拼写 + `version` 一词二义**

| 场景 | 字段 |
|---|---|

| MCP 响应 / SDK 文档 | `api_version`（`spec/04 §四`） |
| MCP 发现文件 | `"version": "devboard/v1"` |

另外 `spec/02 §一` 同时存在 `apiVersion: devboard/v1` 与 `requires.min_contract: devboard/v1`，
**没有任何规则要求两者相等**。

### T-1 · MCP 传输形态（P0-3）

| 选项 | 代价 | 收益 |
|---|---|---|
| **A. 契约为准：HTTP + `mcp.json` 发现文件** | 要改 `docs/04 §9` 与 §3 技术栈表；Windows 首次可能弹防火墙；需处理端口占用与多开 | agent 连到**已经在跑的 GUI**，与产品定位一致；契约 §7.1 已把论证写好；发现文件是「唯一耦合点」，换传输不影响 agent |
