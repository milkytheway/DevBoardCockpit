## 二、计划 3 的代码，我读后的判断

六个 Task 我都读了源码。**质量比我预期的更好**，有三处判断值得点名：

### 2.1 往返队列 —— 一个关键取舍，比我写的计划更好

我在计划里让它实现超时清理；**它拒绝了**，理由写在注释里：

> 队列若自己判超时，就会在**传输层还在等 marker** 的时候放行下一次往返——
> 下一次往返就会**认领上一次残留的回包**。
> 那比「队列堵住」糟得多：**堵住是看得见的，串台是看不见的。**

**这个判断是对的，而且比我原来的设计更对。** 超时是传输层的事（传输层知道 marker 有没有收齐），
队列只管排队与优先级。**一个「更完整的」实现反而是错的**——这值得记一笔。

### 2.2 调度器 —— 「跳过不补发」的判据选得对

契约没说怎么判「错过了」。它用 **「在队列里等了多久」**（不含这次采样自己的执行时间），
而不是「总耗时」。注释里说清了为什么：

> 一次采样自己的往返可能就比周期长（串口尤其慢），那**不是**让路造成的，
> 不该因此跳过——**板子慢 ≠ 错过了周期**。

**准确。** 而且还有第二道防堆积：`group.queued` 为真时直接跳过，不再往队列里加。

### 2.3 绑包 —— 「不猜」落到了实处

契约 §10 写的是「认不出来怎么办？**不猜**」。
实现里：**零个匹配**和**多个匹配**都返回 `no-pack`，并给出不同的 reason。
——「多个也认不出来」这一条我在计划里只写了「不猜」，实现比我写的更明确。

### 2.4 读数面板 —— 显示规则照抄契约，没有自己简化

`stale` 与 `error` **显示旧值**（不是隐藏），`unavailable` **不显示数值**，
`error` 无旧值时显示「读取失败」—— 逐条对应契约 §2.1.1。
还处理了「preload 没加载」的情况：面板自己降级报错，**不把整个应用带崩**。

### 2.5 变异守卫 —— 补齐了

M27–M32 覆盖 M3 的规则/floor/store/sampler，M33–M35 覆盖计划 3 的新代码。
**35 项全守住。** 我上轮说的「M3 零守卫」已关闭。

## 三、我发现的三个问题（**不阻塞 M5，但该记**）

### P1 · 运行时**只试一次，不重试** —— 板子晚插上，面板永远空着

`src/main/index.ts` 的 `startTagRuntime()` 在 `app.whenReady()` 时**挨个试**候选 profile，
**都不行就放弃**。没有重试、没有定时再试。

**后果**：用户先开应用、**后插板子**（或 adb 后授权）→ 面板永远是空的，
**必须重启应用**才有数。

对一个「**看板子的读数是主线**」的产品，这是硬伤。
串口场景尤其容易踩：应用启动时 COM3 被 SecureCRT 或 `serial-server.py` 占着 → 启动失败 → 永远失败。

> **建议**：失败的候选**按退避重试**（2s / 5s / 10s / 30s 封顶），
> 或者至少在「用户新建/启用一条连接」时重试一次。
> **这条改动很小，但它决定了这个产品在没有板子时是不是活的。**

### P2 · `p.board_pack !== undefined` 的过滤是错的

```ts
const candidates = listProfiles().filter((p) => p.board_pack !== undefined);
```

`local.json` 与 `ubuntu-ssh.json` 的 `board_pack` 是 **`null`**，
而 `null !== undefined` 为 **true** → 它们**会被当成候选**。

**后果**：运行时会去连**本机**和 **Ubuntu 客机**，读它们的 `/proc/device-tree/model` 做自动识别
（必然认不出来）—— 白开两条连接。

更值得警惕的是**串口独占**：`runtime.ts` 的注释明说「运行时与终端标签各要一条连接，
同一个 COM3 上只能有一个」。候选顺序若把串口排前面，一次失败的尝试可能**占着端口不放**，
把本来能用的 adb 连接挤掉。

**修法**：`p.board_pack != null`（一行）。

### P3 · 串口独占的产品口径没定

运行时**自建一条连接**，与终端标签的连接**分开**。这个取舍在注释里**明说了**（不藏），很好。

但**产品上没解决**：
**用户开了「串口」终端标签的时候，面板还能不能起串口连接？**
现在答案是「不能，而且失败是看得见的」—— 但「看得见」不等于「好用」。

至少要定一条口径：**串口被终端标签占用时，面板应该显示什么**，
以及**要不要自动退到 adb**（如果板子同时挂着 adb）。

### 4.3 🔴 红灯：**卡片 API 怎么进 iframe**（必须先定）

卡片要拿到 `cockpit.*`。卡片跑在 `sandbox="allow-scripts"`（**不给** `allow-same-origin`）的 iframe 里
→ **不透明源** → Electron 的 preload **只挂在 BrowserWindow 上，挂不到 iframe**。

契约 §六 明写「本轮规格**不锁**这一点」—— 所以这是 M5 必须自己做的技术决策。

| 路 | 做法 | 代价 |
|---|---|---|
| **A** | `<webview>` + `webviewTag: true` + webview 自带 preload | API 最干净，但 **`<webview>` 与 `sandbox: true` 不兼容** —— 要把主渲染进程的 sandbox 放开，**那是倒退**（`main/index.ts:208` 特意为「装不可信卡片」开着 sandbox） |
| **B** ✅ | **`cockpit://` 自定义协议** + `<iframe sandbox="allow-scripts">` + 宿主在响应里**注入 CSP 头** + 注入一个**同源** bridge 脚本（`cockpit://card/__host/bridge.js`，在 iframe 里实现 `window.cockpit`，底下走 `postMessage`） | 契约 §6.1 **已经把注入点写死了**（「CSP 由宿主在响应 `cockpit://card/...` 时注入」）→ **B 与契约完全对齐** |
| **C** | `<BrowserView>` / `<WebContentsView>` | 重量级、独立 session，拖拽布局也难做 |

**我建议 B**，理由：

1. **契约已经指定了注入点**（`cockpit://card/...`）—— 这是强证据，说明契约作者心里就是 B。
2. **不动主渲染进程的 `sandbox: true`**（装不可信卡片的第一道防线不能为了 API 方便而拆掉）。
3. **`<iframe>` 与 `react-grid-layout` 直接兼容**；`<webview>` 是独立组件，拖拽排序别扭。
4. CSP 指令逐条对得上：`connect-src 'none'` 断网络 ✓；**`postMessage` 不受 CSP 限制** ✓；
   `script-src 'self'` 要求 bridge 同源 → 就由同一个协议提供 ✓；
   `default-src 'none'` + `frame-src 'none'` 断掉嵌套 ✓。

**但 B 有两个坑，必须在 M5 的设计里写死**：

- **不透明源无法指定 `targetOrigin`** → 宿主→iframe 的 `postMessage` 只能用 `'*'`，
  iframe→宿主也一样。**必须有每张卡一个 nonce**（宿主生成、随 HTML 注入、bridge 校验），
  否则同窗口里的别的页面可以冒名发消息。**这是 B 的必要条件，不是可选项。**
- **宿主必须校验「这条消息来自哪张卡」** → 通道按卡实例分开（每卡一个 `MessageChannel` 或一个 nonce 命名空间）。

## 五、我的建议：M5 怎么切

### 5.1 先做两件小事（约半小时，**在写 M5 之前**）

| # | 事 | 为什么 |
|---|---|---|
| **0.1** | **修 P1 + P2**：`board_pack != null` 的过滤（1 行）+ 失败候选的**退避重试** | P1 决定「产品在没有板子时是不是活的」；P2 会误抢串口 |
| **0.2** | **定串口独占的产品口径**（P3） | 这是**产品决策**，不是实现细节。该由拍板人定 |

### 5.2 M5 的建议范围：**只做读侧**

| 做 | 不做 |
|---|---|
| 卡片 manifest 校验器（§九 13 条） | `cockpit.actions.invoke`（**写侧 → M6**，依赖动作执行器 U5） |
| `cockpit://` 协议 + CSP 注入 + bridge 脚本（§4.3 的 B） | ECharts 注入（**第一张卡用纯 HTML/CSS 就够**，ECharts 推到 M6 或 M7） |
| `<iframe sandbox>` + `postMessage` + **每卡 nonce** | MCP（M7） |
| 安装 / 卸载 / 热插拔 | `react-grid-layout` 之外的布局高级玩法（Q6/Q7 简化） |
| 拖拽布局（`react-grid-layout`） | |
| 第一张**只读**监控卡（用 `cockpit.tags.get` / `subscribe`） | |

**为什么只做读侧**：写侧要动作执行器（参数编码 §4.6 / guard §5.5 / 地板 R3 / 审计 §5.4 / dry-run §5.3），
那是 **M6** 的全部工作量。**M5 一旦碰写侧，就会顺手把 M6 的安全面（注入防线）提前写掉**——
那是最不该赶的部分。

### 5.3 M5 的**风险集中点**

按工程总纲的顺序原则（「先终端（最可能做不出来），再移植契约，最后卡片与 AI」）：

> **M5 最可能做不出来的是「卡片沙箱 + CSP 断网 + API 注入」这一块**，
> **不是布局、不是热插拔。**

**理由**：`sandbox="allow-scripts"` 的 iframe 是**不透明源** ——
`localStorage` / `sessionStorage` / `IndexedDB` **全部抛 `SecurityError`**（契约 §6.2 已经写明，
所以存储必须宿主代管）。加上 CSP 要靠**协议层注入响应头**，`postMessage` 又因为不透明源
**不能校验 origin**。**这三条叠在一起，M5 的第一版很容易做成「能显示，但没真的隔离」。**

**建议**：M5 的**第一个 Task 就是「证明隔离真的成立」**，而不是「先做出一个能显示的卡」。
具体判据（**机械可判**）：

1. 卡片里 `fetch('https://example.com')` → **被 CSP 拦掉**，且**卡片运行时日志里能看见这条违规**
   （契约 §6.1 明写「agent 因此能看到『这张卡试图联网』」）；
2. 卡片里 `localStorage.setItem` → 抛 `SecurityError`；
3. 卡片里 `parent.postMessage` 伪造**别的卡的 nonce** → 宿主**丢弃**（并记一条日志）；
4. 宿主→卡片的推送**只发往正确的那张卡**。

**这四条过了，隔离才叫成立。** 先做「一张能显示的卡」再回头补隔离，等于把最危险的部分留到最后。
