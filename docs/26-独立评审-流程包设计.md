## 〇 · 结论

**有条件通过。**

**问题选对了，方案还不能用。** "编译 → 上传 → 运行"这件事当前卡片 API 确实表达不了（🟢 `src/main/cards/api-registry.ts` 全文只有 12 个方法，无文件 API、无命令、无目标枚举），
但这份设计**绕开了契约里已经解决过两次的同一个洞**（§三 C1），
**旗舰示例踩了板子自己的硬规矩**（C2），
**把用户原话里的一个需求悄悄删掉了**（C3），
并且**自相矛盾**：一边说"契约层一行不改"，一边要改四份契约再加一份（I5）。

**能不能往下走：能，但不能按本文的分期往下走。**
W0（评审 + 拍板）该做；**W1（契约增量）必须往后挪**——文档自己在 §八 Insight 八 说"不必先设计完整流程包"，
而 §7.2 把契约增量排在最前面，顺序反了（I10）。
更重要的是：**流程包是否进 `docs/spec/` 这件事没拍板，而它决定了这份设计是不是契约层**（I5、可疑点 3）。

## 二 · 做得好的（逐条带证据）

**G1 · 问题选得对，而且证据链是实的。**
"复杂卡片当前做不出来"不是空话：🟢 `src/main/cards/api-registry.ts` 的全集只有 12 个方法
（`capabilities` / `tags.get` / `tags.subscribe` / `tags.subscribePattern` / `tags.list` / `degradation` / `storage.get,set,remove,keys,clear` / `log`），
**没有文件 API、没有目标枚举、没有起任务、没有拿流**。
卡片 API 的封闭清单在 `spec/03` §7.7（`docs/spec/03-card-manifest.md:540-551`）也确认了这 13 个名字。
§2.2 的清单与它大体重合。**这一条站得住。**

**G2 · "不另造第三套执行/授权/审计路径"的立场正确，且有仓库先例。**
§3.8 把流程执行器挂在 M6 那条服务路径上（"与 M6 的 executor / 授权 / 回读 / 审计是同一条服务路径"），
这与 `docs/21:160-170`（§4.4 权限过滤点定在 main、**过滤与授权一处做、MCP 与卡片共用同一条服务路径**）完全一致。
**方向对**——本文最大的问题不是方向错，是实现细节把这个方向漏了（C1）。

**G3 · 反目标清单（§3.9）质量高。**
"不引入通用声明式渲染管线""不做通用工作流引擎（DAG、循环、条件分支、变量、模板引擎）""不把流程塞进板型包"

## 三 · 问题

### 3.0 Critical

---

#### C1 · 流程包给 agent 开了一条不过危险地板的裸命令通道 —— 契约里对同款洞已有处置，文档没照抄

**位置**：`docs/24-流程包设计.md:215-225`（step kind 表）、`:227-234`（两条红线）、`:350-357`（§3.7 权限与审计）、`:513`（§六 item 7）、`:599-609`（§九）

**现象**：
`exec` step 的参数是 `role, cmd, cwd, timeout, env` —— **一条裸命令**；`exec_script` 是更宽的逃生门。
角色可以绑到 `local`（宿主 Windows，`profiles/targets/local.json`）、`ubuntu-ssh`（客机）、`board-adb`（板子）。
文档 §3.7 写"**流程里的写动作仍走 M6 的动作授权（按动作 id）**" —— 但**流程里的步骤没有 action id**：
`exec` 步骤不是板型包声明的动作，`artifact.transfer` 也不是。

**为什么错**：

1. 🟢 **危险地板不覆盖它**。`spec/02` §5.2（`docs/spec/02-board-pack.md:658-660`）原文：
   "运行时在执行一个**动作**前，把命令和地板表对一遍。命中任何一条，这个动作按 `destructive` 处理。"
   地基只管**动作**。同理 §4.6 的参数编码、§5.5 的 `guard` 参数域、规则 27 的"每个 action 必须声明 readback"，
   **一条都不适用于流程包的 `exec` 步骤**。于是 `exec` 一步可以在板子上跑 `rm -rf /` 而**不需要任何人确认**。
2. 🟢 **契约里对"能执行任意命令的包"已有明确处置，流程包是同一类包且更强**。
   `spec/02` §5.6（`docs/spec/02-board-pack.md:786-800`）原文：
   > "**§5.2 的危险地板只管动作。但 `exec_regex` / `script` 是 reader —— 它们在板子上执行任意命令，却不过地板、不需要用户授权。**"
   > "**处置：板型包 = 设备权限，不是卡片。** …… **agent 可以写文件，但装包这一步要人点头。** 区别在「文件存在」与「文件生效」。"

   同一件事在 `spec/04` §2.4.2（`docs/spec/04-mcp-tools.md:365-380`）又写了一遍：
   > "板型包里的 reader 可以执行任意命令……**「包一律生效 + agent 可以写包」合起来就是一条绕过确认的通道——这与 §1.3「不准有裸 send_command」是同一个东西换了入口。**"

   流程包比板型包**更强**：它能跑任意命令、能在**宿主本机**上跑、还能跨目标搬文件。
   按契约自己的逻辑，它**更**应该走"装包要人点头"。而本文**从头到尾没有这一条**——
   §3.7 只说"流程不自带权限，实际授权在宿主、用户手上"，§六/§七/§九 也没有"启用流程包要人确认"。
3. 🟢 **MCP 侧会把这扇门彻底打开**。§六 item 7 要新增 `run_workflow`。
   于是驾驶舱的 MCP agent 第一次获得了**在用户机器上执行任意命令**的能力。
   今天 agent 的能力上限是"写卡片文件 + 调已声明动作"，而卡片跑在 CSP 沙箱里、
   只能调 `spec/03` §7.7 那 13 个白名单方法。`spec/04` §1.3（`docs/spec/04-mcp-tools.md:38-48`）
   "**不准有裸 send_command**"会被正面冲破。
4. 🟢 **卡片侧也没有闸**。`cockpit.workflows.start` 会成为一张卡能调的方法，
   而卡片授权模型只覆盖"tag 读 + action id 写"（`spec/03` §2.2/§2.3、§九 规则 3/7）——
   **流程里的 `exec` 不在任何一个 action id 里**，所以一张卡可以启动一个会跑任意命令的流程，
   而它的 `permissions.write` 里**不需要写任何东西**。

**怎么改**（照抄契约已有的处置，不要另发明）：

- 把"**流程包 = 设备权限面，不是卡片创作面**"写成红线（与 `spec/02` §5.6 同句式）：
  **启用一个流程包要人点头**，确认界面必须展示**这个流程会在哪些目标上跑哪些命令**（`exec` 的 cmd 原文 + `exec_script` 的 ref + 目标 profile）。
- `exec` 的 cmd 必须过**同一张危险地板表**，按 `spec/02` §5.2.1 的 argv 规范匹配，命中即按 `destructive` 处理。
- 更彻底的一条：**流程的写步骤应当引用"已声明的动作"或"流程自己声明的一份带 danger + readback 的命令清单"**，
  而不是自由文本 `cmd`。否则流程包就是 spec/02 §4.1 明令禁止的"只有发一条命令的控制面"。
- 角色绑到 `local`（宿主本机）时，`exec` 要**单独再确认一次**——这一条比板子更该要。
- 卡片侧：`cockpit.workflows.start` 必须受**卡片授权**约束（至少"这张卡可以启动哪个流程"要落在 `permissions.write` 或一个新的字段里）。
- §3.7 那句"流程里的写动作仍走 M6 的动作授权"要么改成"流程的每个写步骤必须落在 M6 的授权域内（逐步骤）"，
  要么删掉——现状是它给了读者一个**不存在的安全感**。

**怎么验证**（机械判据）：
写一条契约级检查：流程包里任一 `exec` 步骤的 cmd 经 §5.2.1 规范化后命中地板表，
**流程包校验器必须报错**（或在启用流程包时强制人工确认）。今天没有这条通道 → 一定会红。

#### C2 · 旗舰 YAML 用 `insmod`，正是板子放置规范明令禁止的常规流程；而且它自己打脸了"换落位规范不改流程"

**位置**：`docs/24-流程包设计.md:275-279`（`load` 步骤）、`:229-231`（红线 1）、`:463-471`（§5.2 隔离矩阵）、`:287-291`（§3.4 permissions）

**现象**：
旗舰 YAML 的第五个步骤是：

```yaml
  - id: load
    kind: exec
    params:
      role: target
      cmd: "depmod -a && insmod $(ls /usr/lib/modules/$(uname -r)/extra/hello.ko)"
```

**为什么错**（两条，各有独立出处）：

1. 🟢 **它违反了板子的硬规矩**。`04-环境/板子放置规范.md:139`（§4 硬规矩第 2 条）原文：
   > "❌ **不要用 `insmod /path/x.ko` 当常规流程** → 装进 `extra/` + `depmod -a` + `modprobe <名字>`"
   > （`insmod` 只在临时验证"模块本身能不能加载"时用）

   而 `buildrun.py:437-439` 正是用 `modprobe <名字>`，并且脚本自己的注释（`:435-436`）说明了原因：
   > "按【名字】加载，不需要写路径 —— **这就是装进 extra/ 的好处**"

   旗舰 YAML 用 `insmod` + `$(ls ...)`，**恰好把装进 `extra/` 的全部好处丢掉了**，
   还多了一次 `ls` 和一层 shell 展开。**第一份流程包如果照抄，板子的规矩第一天就被破坏。**
2. 🟢 **"换落位规范 → 只改板型包，流程包不改"是假的**。
   §5.2 矩阵第 3 行（`:467`）写"换落位规范 | 板型包 | 卡片 ❌ | **流程包 ❌**"。
   但落位路径 `extra/` **已经被写死进流程的 `cmd` 里**（`:279`）。
   板型包把 `kernel-module` 解析到别处时，流程包的 `load` 步骤**必须同步改**。
   **流程与落位知识没有解耦**——这正是 §5.2 声称"整个重构的收益所在"的那一格。

**怎么改**：

- `load` 步骤改成 **`modprobe <名字>`**（名字由 `produces` 的产物名派生，不含路径）；路径只出现在 `placement` 里。
- `run` 步骤不要再用 `dmesg | tail -20` 充当"观察"——它只是 tail 一下 dmesg，不是"跑起来看输出"。
- 把 §5.2 隔离矩阵**逐行对着旗舰 YAML 复核一遍**；凡是矩阵里写"流程包 ❌ 不改"的行，
  旗舰 YAML 里都不许出现对应的具体路径或命令。

**怎么验证**：
把 §5.2 矩阵的每一行当断言写进评审检查表（人工即可）：
「矩阵说流程包不改 ⇒ 旗舰 YAML 里 grep 不到硬编码的落位路径」。今天 `extra/` 就在 `cmd` 里 → 必红。

#### C3 · 用户原话「上传到板子上的**选定位置**」被换成了"语义化 placement"，而两个 step kind 都没覆盖"用户选定"

**位置**：`docs/24-流程包设计.md:31-38`（§1.1 引用用户需求）、`:229-231`（红线 1）、`:215-220`（kind 表）、`:268-273`（`deliver` 步骤）、`:615-623`（§十 七条待拍板——**没有这一条**）

**现象**：
§1.1 引用用户需求原文："上传到板子上的**选定位置**"。
§3.3 紧接着立红线："**`placement` 是语义，不是路径。**"
§十 的七条待拍板里**没有一条**问"语义 placement 与用户选定路径怎么共存"。

**为什么错**：

1. 🟢 **真实样板两个都支持**。`buildrun.py` 里：
   - 规范默认：`KO_SUBDIR = "extra"`（`:80`）、`BIN_DIR = "/usr/local/bin"`（`:81`）；
   - 用户选定：`--ko-dir` / `--bin-dir` 两个命令行参数（`:275-280`）——**用户现场指定落位路径是样板的功能**。
   所以**语义 placement 是默认值，不是唯一值**。文档把"默认值"升级成了"红线"，把用户的一个明确需求删掉了。
2. 🟢 **两个 step kind 恰好把交集漏掉了**：
   - `file.fetch`（`:217`）的目的地是**显式 path**（`to: {role, path}`）；
   - `artifact.transfer`（`:219`）的目的地是**语义 placement**（`to: {role, placement}`）。
   **"用户现场选一个路径"两边都表达不了** —— `artifact.transfer` 的 `to` 只接受 `placement`。
   这正是可疑点 1 的确切机制：**不是缺一类需求，是缺的是"两种目的地形态的并集"，而设计把它拆成了两个互斥的 kind。**

**怎么改**：

- 把 `placement` 降级为**目的地的一种形态**，另一种是**运行期由人给**：
  `to: {role, path}` | `to: {role, placement}` | `to: {role, ask: user}`。
  语义 placement 的地位改成"**未指定路径时的默认**"。
- `file.fetch` 与 `artifact.transfer` 合并成一个 kind（见 §六 建议 3），
  目的地支持上述三种形态；差别只留在"搬运由谁执行"（宿主中转 / 直传），那属于**绑定**而不是 kind。
- §十 补一条待拍板（编号见 M3）。

#### C4 · "一次闭环一条时间线"是**第三套审计形态**，而改动清单没提它

**位置**：`docs/24-流程包设计.md:325-349`（§3.6）、`:514`（§六 item 8）、`:599-609`（§九 改动清单）、`:361-370`（§3.8）

**现象**：
- `spec/02` §5.4（`docs/spec/02-board-pack.md:730-737`）是**契约**：
  "每次动作执行记一行：时间、卡片 id、动作 id、参数、结果、回读值。……沿用旧工程 `core/session_log.py` 的形态（追加写、每行 flush、时间戳前缀）"
- 🟢 现有实现就是这个形态：`src/main/logging/session-log.ts`（行式文本、ANSI 剥离、每行 flush、写进 `%LOCALAPPDATA%/<App>/logs/<date>/<label>-<HHMMSS>.log`）。
- 文档 §六 item 8 写"审计形态：从「每次 action 一行」**扩**到「一次闭环一条时间线」"——**扩**（并存）还是**换**（替换）？§3.6 又是"对比现状"（并存）。**没说。**

**为什么错**：

1. 🔵 **流程的步骤不是 action**（C1），所以**现有的动作级审计根本不会记这些步骤**——
   一次 `run_workflow` 在动作审计里可能**一行都没有**。
   于是流程跑过的事实只存在于新时间线里，而板子上真正发生过的写操作（`depmod`、`modprobe`）在旧审计里也没有。
2. 于是并存的结果是**三个"发生了什么"的来源**：
   ① 动作审计（行式，`spec/02` §5.4）② 流程时间线（结构化，§3.6）③ 卡片运行时日志（`cockpit.log` → `get_card_runtime_log`，`spec/03` §7.5）。
   仓库的规矩是"**词表只有一个源头**"（`AGENTS.md:74`）——这里会变成"**审计有三个源头**"，而它们的口径、内容、保留期各不相同。
3. 形状差异不是"风格"：旧的是**行式文本**（可 grep、可 tail），新的是**JSON 时间线**（可查询、无自然分段）。
   §3.6 的示例 JSON 里 `"tail": "…CC [M]  Building modules"` 还把**输出内容塞进了时间线记录**——
   输出流与审计记录混在一起，等于审计日志里存大段 stdout。

**怎么改**（二选一，必须拍板）：

- **(a) 嵌进去**：一次闭环 = 动作审计里的一段（同一套行式格式，缩进或加 run id 前缀），**不另立存储**。
  优点：不新增第三套；缺点：跨目标的时间线不好查。
- **(b) 分开但定死关系**：保留动作审计，另立时间线存储，但必须写明**一条时间线的每个 stage 对应哪些审计行**、
  缺一行算什么状态、时间线放哪、留多久、怎么查（`workflow_timeline` 工具的形状）。
  并把 §3.6 示例里的 `tail` 字段挪走（输出流归输出流，审计归审计）。

**怎么验证**：
写一句机械判据——"**任何一次 `run_workflow` 的每一个写步骤，都能在审计里查到一条可追责的记录**"。
按现状（C1 + 现状的审计只记动作），这条判据**今天就是红的**。

#### I1 · 「缺概念 1：任务（Job）」是从旗舰样板推不出来的 —— 样板只要 `exec` + 长超时

**位置**：`docs/24-流程包设计.md:143`（§2.4 编译行）、`:154`（§2.5 概念 1）、`:397-398`（§4.1 末段）

**现象**：
§4.1 末段："**注意 `ssh_run` 的超时是 1800 秒**：这就是'命令'和'任务'必须分家的实证——
现有 `exec(cmd, {timeoutMs})` 的形状，**天然表达不了**'跑 30 分钟，中途要看、要能停'。"

**为什么错**：

1. 🟢 **`exec(cmd, {timeoutMs})` 就是表达"跑 30 分钟"的形状**。
   `src/main/hal/ssh.ts:180`：`const timeoutMs = opts?.timeoutMs ?? 30_000;`——**默认值 30 秒，传 1800000 就是 30 分钟，无上限**；
   超时统一归一到 124（`src/main/hal/session.ts:16` `TIMEOUT_EXIT_CODE = 124`）。
2. 🟢 **样板自己就不要流式与取消**。`buildrun.py:114-132` 的 `ssh_run` 是 paramiko 的
   `exec_command(cmd, timeout=1800)` + `o.read()` —— **收完再返回 `(rc, out, err)`**。
   它**没有**流式输出，**没有**取消。`board_run`（`:200-211`）同理。
   **所以旗舰样板对"流式 + 可取消"零需求**，而文档把"长超时"当成了"需要 Job"的证据。
3. 🟢 **真正缺的是流式与取消**，而且**样板没演示它**——但**用户的需求演示了**：
   §1.1 引用的用户原话是"能**观察过程中的中间结果**"。这句话指向的是流式，
   不是长超时。文档把论据用错了地方。

**怎么改**：

- 把结论改成"**缺的是流式输出与取消**，不是长时执行"；`Job` 抽象相应缩到"可取消 + 流式"，超时交给 `exec`。
- 若首版不做流式，就在 §四 明说"首版流程的中间结果只在步骤结束后可见"——
  这是与用户"观察中间结果"之间的**明确差距**，需要用户拍板（而不是默认它已经满足）。

#### I2 · 跨目标直传是整套设计的收益中心，却没有凭据模型 —— 样板默认的那条路根本表达不出来

**位置**：`docs/24-流程包设计.md:156`（§2.5 概念 3）、`:294-311`（§3.5 绑定）、`:393`（§4.1 表）、`:400-412`（§4.2）

**现象**：
`buildrun.py` 的**默认**传输是 `net`（`:264` `transport = "net"`），即"**客机自己 scp 直达板子，宿主全程不碰这个文件**"；
为此脚本有 `ensure_guest_to_board_key()`（`:213-237`）——**往板子的 `/root/.ssh/authorized_keys` 写客机的公钥**。
文档 §3.5 的绑定只有 `role: {profile: ...}`。

**为什么错**：

1. 🟢 **宿主现有 profile 里没有"目标 A → 目标 B"的凭据**。
   `src/main/profiles/schema.ts:47-66` 的 ssh 选项只有 `host/port/username/key_filename/password`——全是**宿主→目标**的凭据。
   `profiles/targets/ubuntu-ssh.json` 是宿主→客机；`board-adb.json` 是宿主→板子（ADB）。
   **没有任何字段表达"客机拿什么去连板子"。**
2. 🟢 **§4.2 把这一格称为"整个重构的收益所在"**（`:412`），但**这一格在提出的绑定模型里不存在**：
   `artifact.transfer` 的"直连不经宿主"需要目标间凭据，绑定里没有；
   而"给目标装公钥"这种**写 `/root/.ssh/authorized_keys` 的动作**，
   9 种 step kind 里**一个都不是**（它既不是 `exec`（会经过地板与授权），也不是 `file.fetch`）。
3. 而且这是**安全动作**：往板子的 root 授权文件里写公钥，等于把板子的 root 登录权交给客机。
   按 C1 的逻辑，它**必须**走人工确认——文档里连它的位置都没有。

**怎么改**：

- **(a)** 绑定里增加一段"传输策略"：`transfer: {from: build, to: target, method: guest-scp, credential: <ref>}`，
  并把"安装/校验凭据"作为一个**显式步骤**（人工确认）。
- **(b)** 首版**放弃直传**，只做"经宿主两跳"，并诚实写明代价（宿主要落一份产物、占磁盘、可能几百 MB）。
  🔵 按 `buildrun.py` 的实际体量（一个 `.ko` 几 MB、一个用户态程序几 MB），
  两跳在 v1 **完全够用**；直传的价值要等产物变大或宿主落盘成为瓶颈时才兑现。
- **无论选哪条，都不要把"直传"当成已得的收益写进 §4.2 的对比表**——今天它是**未兑现的承诺**。

#### I3 · 「`await` 的判据是 tag」这条红线与真实样板对不上，而且旗舰时间线引用了一个不存在的 tag

**位置**：`docs/24-流程包设计.md:232-234`（红线 2）、`:341`（时间线里的 `readback`）、`:147`（§2.4 观察行）

**现象**：
红线 2："**`await` 的判据是 tag，不是字符串**……闭环与 tag 契约缝在一起，**不另造成功判定**。"

**为什么错**：

1. 🟢 **旗舰时间线里的 tag 不存在**。`:341` 写 `"readback": { "tag": "system.load", "value": 1, "status": "ok" }`。
   核心词表（`docs/spec/data/tag-vocabulary.yaml`）共 **21 个** tag：
   `cpu.usage / cpu.core.*.usage / cpu.core.*.cluster / cpu.governor / gpu.usage / gpu.freq_hz /
   npu.usage / npu.core.*.usage / mem.total_bytes / mem.available_bytes / mem.used_bytes / mem.usage /
   temp.soc / temp.gpu / temp.npu / board.model / board.kernel / net.rx_bytes / net.tx_bytes /
   disk.*.free_bytes / disk.*.total_bytes`。
   **没有 `system.load`**，也没有"编译成功"、"模块已加载"。
2. 🟢 **样板的真实判据是命令，不是 tag**：
   - 编译成功 = `make` 退出码 0 **且产物列表非空**（`buildrun.py:308-325`）；
   - 落位成功 = `modinfo -F filename <name>` 查得到（`:366-371`）；
   - 这正是契约 `spec/02` §4.4 的**回读形式 2 / 3 / 4**（`file_equals` / `command_ok` / `verify`），
     **不是 tag**。而 `verify` 形式的语义（"执行后跑二次命令，轮询到成功或超时"，`docs/21:571-576`）
     **与 `await` 高度重叠**——`await` 是 `verify` 的流程层版本。
3. 🟢 **`await` 在 build 角色上根本用不了**：`ubuntu-ssh.json` 的 `board_pack` 是 `null`，
   而采样候选只留 `board_pack != null` 的 profile（`src/main/tags/runtime.ts:212`）→ **客机没有 tag**，
   客机上**没有可 await 的量**。`await` 只能用于 target 角色。
4. 🔵 把"任务结果"塞进 tag 语义，正是 `SPEC-D4` 担心的那种污染（`spec/00:124`：
   "视频流、日志流、文件内容塞进 tag 词汇表会污染它"）。

**怎么改**：

- 把红线 2 改成**两类判据**：
  **板上量 → tag（`await`）；非板上的量 → 步骤自己的产出契约**（退出码 + 产物清单 + 可选的命令回读）。
  "成功"是**每步各自的判据**，不是统一的 tag 判据。
- 顺便把 `await` 与 M6 的 `verify` 形式的**关系写死**（`await` 复用 `verify` 的回读引擎，不要实现第二套）。
- `system.load` 要么换成词表里真实存在的 tag，要么改成 `custom.*` 并写明**谁提供那个 reader**（板型包）——
  否则时间线示例本身不合法。
- `await` 的适用面在文档里写清：**只对 target 角色成立**。

#### I4 · 流程包没有参数化机制 —— 旗舰 YAML 表达不了用户要的那张卡

**位置**：`docs/24-流程包设计.md:200`（§3.2 "里面 | 步骤、**参数**、阶段、权限诉求、产物声明"）、`:238-292`（§3.4 YAML，**没有 params/inputs 段**）、`:426`（§4.3 `run_workflow("hello-kernel.build-run", {source: "local"}, {dry_run: false})`）

**现象**：
§3.2 说流程包里有"参数"，但 §3.4 的 YAML 格式里**没有任何参数声明**：
路径写死（`~/work/build/01-hello`）、命令写死（`make -C ~/work/build/01-hello modules`）、
产物写死（`produces: [hello.ko]`）。而 §4.3 的 MCP 调用却传了一个 `{source: "local"}` 参数对象——
**§3.4 的格式里没有地方接它**。

**为什么错**：

1. 🟢 **用户要的核心需求是"选代码"**。§1.1 引用的原话："用户可以选择**本机**或者**客机**上的代码，选完点**编译**"。
   没有参数化，流程包就是**一份写死的脚本**：用户挑代码这件事要么被写进绑定（每换一次代码改一次绑定），
   要么退回卡片里拼（**那就回到了设计要解决的老问题**）。
2. 🟢 **样板本身就是带参数的**：`buildrun.py:258` `project = sys.argv[1]`——项目目录是命令行参数。
   旗舰 YAML 把"脚本的一个参数"写死成了流程的常量，**丢掉了样板最重要的一个性质**。
3. 🔵 **参数化会立刻引出三个本文没考虑的问题**：
   参数的封闭类型表（照 `spec/02` §4.3）、参数值怎么进命令（照 §4.6 的编码，**不是原样拼接**）、
   以及**参数是流程级还是绑定级**（`source: "local"` 是"换绑定"还是"换参数"？§3.5 与 §4.3 都没说）。

**怎么改**：

- YAML 加一段**封闭的参数声明**（名字、类型、必填/默认、取值域），
  步骤里用**占位符**并走 §4.6 的编码规则。
- 产物不要写死文件名：按"编译产物目录 + 过滤规则"声明（样板是
  `find -maxdepth 1 -type f` + 扩展名/SKIP 过滤，`buildrun.py:312-328`）。
- §4.3 的 `{source: "local"}` 要有地方落：要么它覆盖绑定、要么它是参数——**二选一并写进格式**。

#### I5 · 文档说"契约层一行不改"，§九 却要改四份契约并新增第六份

**位置**：`docs/24-流程包设计.md:85`（§1.4）、`:530`（§7.1）、`:510`（§六 item 4）、`:599-609`（§九）

**现象**：
§1.4 与 §7.1 都写着 ✅ "契约层已冻结且语言中立……流程包可以是**宿主层的产物**，契约层一行不改"。

1. 🟢 **一份进了 `docs/spec/` 的文档就是契约层**。`AGENTS.md:21`：

2. 这正是可疑点 3 的确切答案：**进 `spec/` 就算契约层**；不进 `spec/` 就没有校验规则、没有版本承诺，
   `spec/04` 的 `run_workflow` 也就没有契约依据 —— **两条路不能都要**。
3. 🔵 若它是契约层，那么按 `AGENTS.md:31`（"改 `docs/spec/` 要升 `apiVersion` 并走评审（ADR-D15）"），
   §九 那行"`apiVersion` 是否还够？| **待定** | **要拍板**"就是**必须先拍板才能动契约**的前置项，

**怎么改**：

先拍板"流程包是不是契约层"，然后二选一：

- **是**：§1.4 / §7.1 改成"契约要改四处 + 新增一份"，并按 `spec/00` 的编号给出契约层决策
  （下一个 `SPEC-D*` 是 **D23**，见 M2）；把 apiVersion 讨论摆到 W1 之前。
- **否**（纯宿主层的数据格式）：那它**没有**校验规则与版本承诺，

#### I7 · 流程在板子上跑长命令会把这块板的采样全堵死 —— 与 `SPEC-D22` / ADR-D23 正面冲突，文档没提

**位置**：`docs/24-流程包设计.md:339`（时间线 `"run": { "ms": 30000 }`）、`:221`（`launch` kind）

**现象**：
旗舰时间线里 `run` 阶段耗时 **30 秒**；§3.3 的 `launch` 定义为"在某角色启动一个进程并观察"。

**为什么错**：

1. 🟢 **同一条连接上同时只能有一次往返**。`spec/02` §1.2.1（`docs/spec/02-board-pack.md:213`）、`SPEC-D22`（`spec/00:142`）：
   "**一次往返在链路上独占；动作与回读不可拆分**"。
   🟢 实现侧：`src/main/hal/round-trip-queue.ts:49` 的 `inFlight` **恒为 0 或 1**。
2. 因此：流程在板子连接上跑一条 30 秒的命令，**这 30 秒里这块板的 tag 采样全部停摆**——
   监控卡上的 CPU / 温度是**死的**。串口更糟（与终端共用一根线，事实 S1）。
3. 🔵 这是"驾驶舱 vs 遥控器"（`docs/09:124-132` §2.4）在流程层的直接冲突。
   文档 §八 Insight 二只谈"渲染与策略分离"，**没谈通道占用**；而它自己的时间线就写着 30 秒。

**怎么改**（三选一，必须挑一个并写进设计）：

- 把"观察"改成**不占长往返**的方式（读 tag / 读文件 / `modinfo` 式的一次性查询），而不是长跑一条命令；
- 或者明确写"**流程运行期间该板采样暂停**"，并在 UI 上把这件事说出来（别让用户以为板子死了）；
- 或者给流程单独一条不受 `RoundTripQueue` 约束的通道 —— **这一条要单独评估**，
  它会打破 `SPEC-D22` 的"动作与回读不可拆分"，而那条是 `spec/00` 级别的契约。

#### I11 · §八 Insight 三「reader kind 成功了，所以 step kind 也会成功」是跨语境推断，不成立

**位置**：`docs/24-流程包设计.md:565-569`

**现象**："reader kind 成功了（**加板型不用改代码**），所以 step kind 也会成功。"

**为什么错**：
🔵 两者被验证的命题**不是同一个**：

| | reader kind | step kind |
|---|---|---|
| 封闭的是什么 | 一次**板上往返**的取数形状（`proc_stat` / `meminfo` / …） | 一串**跨目标**的步骤 |
| 加一个的代价 | 一份 kind 的说明书 + 一份实现 | 可能牵动绑定、授权、判据、审计 |
| 失败形态 | 解析失败 / 状态错 | **超时、部分完成、凭据缺失、回滚** |
| 契约的理由 | `spec/02` §2.3：保住 pack 的**自解释性** | 文档给的理由是"不做表达式语言"——**换了一个理由** |

`spec/02` §2.3 选混合式的核心理由是"**AI 读完 pack 的 YAML 和 kind 的说明书，就知道这块板的一切**"（自解释性）。
§3.3 引用这一节时（`:209-212`）**只借了"不做表达式语言"这一半**，
没有继承"**AI 必须能只读文档就写出一个流程包**"这一半——
而这恰恰是"AI 可造卡"这条产品主线对流程包的要求。

**怎么改**：

- Insight 三改成"**同一种套路可以复用，但判据要另立**"，并补上 reader kind 真正被验证的那条：
  **流程包也必须"AI 读完文档就能写出来"**——§3.4 那个 YAML 格式现在还做不到（无参数化、无产物发现）。
- §3.3 的引用补上 §2.3 的**自解释性**那一条，并据此写出流程包对应的要求：
  **每个 step kind 必须有"接受什么参数 / 产出什么 / 失败长什么样"的说明书**。

### B · 设计本身

| # | 结论 |
|---|---|
| **B1** | **有一处层数错配、两处该合并。** ①**①语义层与②定义层该合并**：step kind 是流程包用的**词**，不是与它并列的一层——对照 reader kind 的先例，kind 的清单与说明书是**契约里的一张表**，pack 引用它，不是"pack 下面还有一层"。②**③绑定层不是"层"**，它是"流程 + 绑定 = 一次运行配置"的**实例参数**（§十 item 2 自己说绑定是独立文件）。③**Job 被当成"缺的概念"，其实它是执行层的实现**——§3.1 的 ④执行层里已经写了"Job 调度"。缺的概念只有三个（角色 / 直传 / 非标量结果）。④**⑤呈现层与④执行层之间缺一层契约**：状态流的形状没定（M8）。 |

| **B4** | **不够，而且缺的不是"语义 vs 具体"这一个维度，是三层。** ①**语义 placement vs 用户选定路径**（C3）：两者应该是并集（`path` / `placement` / `ask: user`），不是二选一。②**跨目标凭据**（I2）：绑定里完全没有。③**"谁执行搬运"**（I6）：`profile` 换不了"客机 scp"与"宿主 adb push"的差别。

| **B5** | **不够，而且这条红线本身要改。** tag 是**板级量测**，而"编译成功"**根本不在任何板上**——🟢 词表 21 个 tag 里没有"编译成功""模块已加载"，
🟢 旗舰时间线里的 `system.load` **不存在**。真实判据是命令：`make` 退出码 + 产物存在（`buildrun.py:308-325`）、
`modinfo -F filename` 查得到（`:366-371`）——这正是 `spec/02` §4.4 的**回读形式 2/3/4**。

| **B6** | **有富余也有缺，缺的不是状态是多态。** 富余：`idle` 与 `armed` 的区别没定义（"已绑定待启动"与"空闲"对用户是同一件事）；

**部分成功**（前两步已生效，第三步失败，板子处于半状态）。另：**stage 的状态词借用了 tag 的 `ok`**

| **B7** | **并存，但文档没说并存的是哪两样，也没有说它们的事务关系。** 现状是**动作级**审计（`spec/02` §5.4，🟢 行式文本、每行 flush、写进 `logs/<date>/<label>-<HHMMSS>.log`）；
文档要加**闭环级**时间线（结构化 JSON）。🔵 真正的麻烦：流程的步骤**不是 action**，
所以**现有动作审计一条都不会记它们**——一次 `run_workflow` 在旧审计里是空的。
加上卡片运行时日志（`cockpit.log`）就是三套。→ 见 C4（必须二选一，并写进 `spec/02` §5.4 的改动清单）。 |
