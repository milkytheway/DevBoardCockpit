## 一 · v2 两条 Critical 的复核

> **复核口径**：
> **已解决** = 契约文本写到位 **且** 实现里有对应的执行器与单测。
> **部分解决** = 方向对了，但落点还差一截（或差在契约那一侧）。

### 一.1 · V2-C1 —— 确认链在契约与实现里都没有落点

**v2 怎么说**（`docs/35:172-219`）：

> 契约写了「destructive 每次都要人确认」，也写了凭据**绑什么**，
> 却**从头到尾没有一个字说**：**谁签发这张凭据？人在哪个界面上点？点完之后那次运行怎么继续？**
> 实现里 `WorkflowService` **根本没有 confirm / resume 方法**，`scripts/run-workflow.ts` 不传 `confirmations`
> → destructive 步**永远卡住**。

**v3 怎么说**（`docs/36:107-126`）：§二·2.5 给出确认链的五步图：
签发（待确认）→ 流程停在 `awaiting_confirmation`（**不是 failed**）→ 人点头 → 凭据变可用 →
**从停住的那一步继续（前面的步不重跑）** → 同一个 `run_id`、同一份时间线。
另补 §二·2.4 的凭据绑定四项、§六·3/5 的状态机与续跑、§五 的 `confirm_workflow`。

**实现的证据**（🟢 逐条核对过）：

| 环节 | 证据 | 判定 |
|---|---|---|
| 凭据两段式（签发 ≠ 有效） | `src/main/actions/authorization.ts:158-201`（`issue()` 挂成 `pending`；`approve()` 才置 `approved`；`:228-229`「没被人点过 → 不能用」） | ✅ |
| TTL 5 分钟 + 一次性 | `authorization.ts:119`（`CONFIRM_TTL_MS = 5 * 60_000`）· `:224-227`（过期即删）· `:233`（用掉即删） | ✅ |
| 凭据绑「这一步的输入」 | `src/main/workflows/runner.ts:812-830`（`bind()` 把 `input:<名>` 并进摘要） | ✅ |
| 状态是「等确认」不是「失败」 | `src/main/workflows/service.ts:216-221`（`state = 'awaiting_confirmation'`） | ✅ |
| 点完之后从停住的那一步继续 | `service.ts:172-180`（取 `pausedAtStep` → `execute(..., pausedAt)`）· `runner.ts:168-173`（`if (index < startAt) continue`） | ✅ |

**复核结论：部分解决。**

**方向完全对**，实现这一侧确实补齐了（比 v2 强得多）。但**还差三处**，其中第一处是 Critical：

**① 「批准」这个动作**由谁执行**——契约里没有**（→ **V3-C1**）

- `docs/36:298`：`confirm_workflow(run_id, confirm_id)` 出现在 **§五 · `docs/spec/04-mcp-tools.md` 的增量**里 ——
  **MCP 工具表 = agent 可调的面**。
- 实现里唯一的批准入口是 `src/main/actions/authorization.ts:184-201` 的 `approve()`，
  它的注释写得很死：「**这是「人点头」那一下的唯一入口** ✓（宿主侧由 GUI 调用；
  命令行侧由 `npm run workflow:confirm` 调用 ✓）」。
- 而 `WorkflowService.confirm`（`service.ts:156-181`）**调的正是 `approve()`**（`service.ts:166`）。
- → **按提案字面实现**：`run_workflow` 跑到 destructive 步 → 返回 `confirm_id`（待确认）→
  agent 调 `confirm_workflow(run_id, confirm_id)` → `approve()` → 凭据生效 → **agent 自己批了自己**。
  `authorization.ts:154-157` 的原话（「没有这一档 = 谁要谁批 ✗ → 确认通道形同虚设 ✗」）**原样成立**。
- §二·2.5 只写了「没人点，`confirm_id` 永远无效」，**没写「『点』这个动作谁能做」**——
  这正是 `spec/04` §2.4.1 的两段式里最要紧的一格。
- 另外 `docs/36:117` 引用的 `workflow:confirm` **这个命令不存在**：
  `package.json:20-23` 只有 `workflow:run` / `workflow:list` / `workflow:approve` / `workflow:revoke`。

**② 唯一的生产入口没接线**（类实现了，但没有人能用）

- `scripts/run-workflow.ts:145-155` 直接调 `runWorkflow(pack, args.input, {...}, { approved: true })` ——
  **不传 `confirmations`** → `runner.ts:814-816` 落到桩 `{ issue: () => '', consume: () => false }`
  → destructive 步拿到的 `confirmId` 是**空串**（`runner.ts:191` `String(... ?? '')`）→ **命令行这条路永远走不完**。
- `WorkflowService` 在全仓**零调用者**（`grep -rn "WorkflowService" src/ scripts/` 只命中它自己的定义）。
- → 「已实现并真机跑通」这句话在**确认链**这一项上是**不成立的**。

**③ §六·6「要续跑就用同一个 `run_id`」没有 API 落点**（→ **V3-I2**）

- `docs/36:320` 写「重试 = 从头再跑（首版语义）—— 不是续跑 ✓ → **要续跑就用同一个 `run_id`** ✓」。
- 实现：`service.start()`（`service.ts:122-146`）**每次都新建 run**（`service.ts:130`），
  `run_workflow(id, inputs, dry_run)`（`docs/36:296`）**不接受 `run_id`**。
  唯一能续跑的是 `confirm(runId, confirmId)` —— 而它要求**人已经批过**。
- → 「人没点头、agent 重试一次」这条路径**只能从头再跑**（前面的写步骤重复执行）。
  这正是 31-C3 点名的要害（「编译两遍、传输两遍、`depmod -a` 两遍」），v3 把结论写了，**但没给路**。

## 二 · v3 新引入 / 仍开着的洞

> **说明**：凡是「实现已做但提案没写」的，标成「实现层 ✓、契约层 ✗」——
> **契约层才是权威**，实现做了不等于契约写了。

### 2.1 · Critical

---

#### **V3-C1 · 「批准」这一步的接口没写：照 §五 实现，agent 能给自己批 destructive 步**

**结论**：v3 把「确认链」画出来了（`docs/36:107-116`），但**链条上最要紧的一格 —— 「人点头」由谁执行 —— 是空的**。
两种可能的读法**都坏**。

**证据**

| 环节 | 提案 | 实现 | 坏在哪 |
|---|---|---|---|
| 工具清单 | §五（`docs/36:298`）把 `confirm_workflow(run_id, confirm_id)` 列进 **MCP 工具表** → **agent 可调** | `src/main/workflows/service.ts:166`：`this.opts.confirmations?.approve(confirmId, this.now())` | 若这个工具映射到 `service.confirm` → **agent 批准了自己的 destructive 步** |
| 「签发 ≠ 有效」 | §二·2.4 规则 5（`docs/36:105`）✓ | `src/main/actions/authorization.ts:184-201`（`approve()` = 「人点头那一下的**唯一入口**」）· `:228-229`（没点过不能用） | 两段式的**全部价值**就在这一格；把它暴露给 agent = 两段式白做 |
| 人的落点 | §二·2.5（`docs/36:117`）：「人点头（GUI 或 `workflow:confirm` ✓）」 | `package.json:20-23` **没有 `workflow:confirm`**；`grep -rn "workflow" src/main/cards/` = 0 → **GUI 侧也没有** | 契约引用了一个**不存在的命令**和一个**不存在的界面** |
| §五 的形状 | 「**递一次确认请求**（人点了才有效）… 返回 `{ confirm_id, expires_at }`」 | run 暂停时**已经签发过**一张待确认凭据（`runner.ts:225-231` → `executor.ts:225-231` → `service.ts:216-221`） | 若语义是「递请求」→ **重复**：一次运行会出现**两张凭据、两个真相**；若语义是「批准」→ 回到上一行 |

**为什么是问题**

1. **这是 V2-C1 原话的重演**。v2 的原话是「**从头到尾没有一个字说**：谁签发这张凭据？人在哪个界面上点？点完之后那次运行怎么继续？」
   v3 答了「谁签发」「点完怎么继续」，**「谁点」这一格仍然没答**。
2. **契约层在这里不能靠「实现自己会做对」兜底**。
   `spec/04` §2.4.1 的现成先例是 `confirm_action`：**它只是把请求递到 GUI 的确认队列**，
   「批准」这个动作**根本不是一个 MCP 工具** —— 它在 GUI 那一侧。
   → 流程层必须照这个先例走：**MCP 面上只有「递请求」，没有「批准」**。
3. v3 §二·2.5 自己写着「『签发 ≠ 有效』：没人点，`confirm_id` 永远无效 ✓」——
   **它知道这条原则，却没把「点」这个动作的权限边界写出来**。

**建议**（三处一起改，否则契约会自相矛盾）

1. **§二·2.5 的链条图加一格**：
   `→ 人点头（**GUI 确认界面** / **宿主命令行**）→ 凭据变成可用 ✓`，
   并加一句：「**『批准』不是 MCP 工具** —— agent 只能递请求，不能批准 ✓」。
2. **§五 的 `confirm_workflow` 改成请求语义**，签名与返回对齐 `spec/04` §2.4.1 的 `confirm_action`：
   `confirm_workflow(run_id) → { confirm_id, expires_at }`（**待确认**），
   并写明「**它不使凭据生效**；生效只由人点过之后的那条路径发生 ✓」。
3. **§八 item 3**（`spec/04` 的改动清单）补上：「`§2.4.1` 的 `confirm_id` 生命周期表**扩到流程层** ✓
   （谁能批 / 批什么 / 批完怎么续）」—— 这是 `spec/04` §2.4.1 那张表的原文要求，不是新增机制。

#### **V3-I1 · §二·2.5 的「确认链」少了两格：凭据从哪来、续跑后审计行怎么算**

- **证据**：`docs/36:107-116` 的链条从「执行器签发 confirm_id」开始，
  **没写**：① 凭据**绑的摘要**里那三项（输入摘要 / 最终命令摘要 / 包 id）在流程层**分别是谁**
  （§二·2.4 规则 3 写了，§二·2.5 的图里没体现，读者会以为是一条链）；
  ② **续跑产生的是新审计行还是同一行** —— 实现是**新行**（`executor.ts:161-175` 每次执行都 `deps.audit(...)`），
  而 §三·3.7·3 说「时间线：一次运行的记录，每阶段引用那一行的 `audit_id`」——
  **续跑后同一个阶段会出现两个 `audit_id`**（时间线上会出现重复的阶段项）。

  时间线上同一阶段可能有两个 `audit_id`（前一行是『被拦下的那一次』）✓」——
  或者规定「续跑**不重写**那一行、另起一行并用 `resumed_from` 指回」，两种都行，但**必须写**。

#### **V3-I2 · §六·6「要续跑就用同一个 `run_id`」没有 API 落点**

- **证据**：`docs/36:320`；`service.start()`（`service.ts:122-146`）**每次新建 run**（`:130`）；
  §五/§四 的 `run_workflow(id, inputs, dry_run)` 与 `cockpit.workflows.run(id, inputs)`（`docs/36:273/296`）
  **都不接受 `run_id`**；唯一能续跑的是 `confirm(runId, confirmId)` —— 而它要求**人已经批过**。
- **为什么是问题**：§六·6 的结论（「重试 = 从头再跑」）本身**是对的**，
  但它给出的替代方案（「用同一个 `run_id`」）**在契约的 API 上不存在** →
  下游照着实现，会写出一个「支持 resume 的接口」，或者**默默按从头再跑实现**。
  更糟的是：§二·2.5 说「**前面的步不重跑** ✓」——**这两句在同一份文档里指向相反的行为**，
  读者按 §二 理解、按 §六 实现，就矛盾了。
- **建议**：§六·6 改成两条互斥的、有 API 落点的规定：
  - 「**重新触发**（`run_workflow` 再调一次）= **从头再跑** ✓；前面已完成的**写步骤会重复执行** ✓
    → 因此 `destructive` 的步骤**不得**放在有副作用的写步骤之后，或者**首版要求一次运行最多一次确认** ✓」。
  - 「**续跑**（人点头后）= `confirm(run_id, confirm_id)` ✓ → **从停住的那一步继续** ✓（§二·2.5）」。

#### **V3-I3 · §六·7 的并发规则没有执行者，而且粒度写错了**

  两条 `scp` 同时打同一块板 → 串台。
- **粒度也不对**：v2 评审 V2-I5 建议的是「同一个 `(流程 id, role 集合)` 同时只允许一个运行」——
  因为**冲突的根源是目标（串口 / 板子），不是流程包**：
  两个**不同的**流程包跑**同一块板**同样会串台，而 v3 的规则**管不到**。
- **还缺**：超出的那一次是**排队**还是**拒绝**？拒绝时的 reason 码是什么？
- **建议**：§六·7 改成「**同一个 `role` 集合**（即同一批目标）同时只允许一个运行 ✓；
  超出的**排队**（按 §六 的顺序执行）✓；**排队的运行**的状态是 `running` 还是新的一档 `queued`（**要写死**）✓」。

#### **V3-I5 · §三·3.8 规则 3/4（主机身份）在流程层无处落地**

- **证据**
  - 规则 3（`docs/36:242`）：「不许关掉主机身份校验（`StrictHostKeyChecking=no` **禁止** ✓）」——
    `grep -rn "StrictHostKeyChecking\|hostVerifier\|known_hosts" src/` = **0 命中**（这一半字面为真）。
    **但正面要求没有**：宿主的 ssh2 连接（`src/main/hal/ssh.ts`）**没有配 `hostVerifier`** →
    **ssh2 默认不校验主机密钥**。
  - 规则 4（`docs/36:243`）：「主机身份校验失败 → **判据不成立**」——
    **无处判定**：判据命令（`test -f {to.path}`）**跑在源目标（客机）上**（`runner.ts:621-659`），
    宿主管不到客机的 ssh 客户端配置，也看不到客机的校验结果。
- **为什么是问题**：规则 3/4 看起来是流程层的规矩，**实际上它们约束的是「客机自己的 ssh 客户端」**——
  那是**流程包碰不到的地方**。规则 4 更直接：一个**在流程层之外**发生的失败，
  流程层**怎么知道**它发生了？→ 这两条在当前形状下**不可执行**。
- **建议**（二选一）
  - **甲（推荐）**：把传输改成**宿主生成 + 宿主直连**——宿主用 ssh2 直接连目标机传文件
    （`hal/ssh.ts` 已经有 `pull`/`push`），主机身份校验就在宿主手里，
    规则 3/4 变成可执行的条款；同时「传输命令跑在源目标上」这条**直传语义要重新设计**
    （v3 §三·3.4 明写它是「直传的全部语义」）——**这条要连带拍**。
  - **乙**：保留源侧传输，但契约改成「流程包**必须**声明目标主机的 `known_hosts` 指纹，
    宿主在**装包期**比对；指纹不符 → 装包期就报错」——
    至少把校验点搬到**宿主能管的地方**（装包期），而不是运行期的一句无法判定的话。

#### **V3-I6 · §二·2.5 押的防线（「装包时人看过」）实际上看不到判据命令**

- **证据**：`docs/36:125`：「一个判据命令理论上能写（`verify` 的命令是包给的 ✓）→
  **首版的防线是「装包时人看过」** ✓（§二·2.3 ✓）+ 地板 ✓」。
  而批准界面的内容来自 `registry.ts:78-97` 的 `planOf`：
  它打印 `id / kind / role / **command（= step.cmd）** / dangerous / readbackRole` ——
  **`readback.command` 不在其中**（`registry.ts:87-95`）。
  批准命令的打印在 `scripts/workflow-registry.ts:85-93`，同样只打 `step.command`。
- **为什么是问题**：**人批准的时候根本没看到判据命令** →
  §二·2.5 说的「防线」在判据这一侧**是空的**。
  再加上：判据命令**在别的机器上跑**（跨目标，`runner.ts:621-659`）、
  **只过地板**（`runner.ts:645-655`）、**不进确认通道**（§二·2.5 明写）→
  → **一个包可以让流程在客机上跑一条任意命令（只要不命中地板），零确认、人没看见**。
- **建议**（两条，写进 §二·2.5 或 §三·3.5）
  1. **批准界面必须显示判据命令**（`planOf` 加 `readbackCommand` 字段 + 打印）——
     否则「装包时人看过」这句话要删掉。
  2. 给判据命令加一条**封闭允许集**（`test` / `ls` / `cat` / `readlink` / `md5sum` 之类），
     或至少规定「判据命令**必须声明为只读形态**」——
     **「只过地板」不等于「只读」**（地板表管的是 reboot/mkfs/dd 这几类，不管 `> file`、`tee`、`curl`）。

#### **V3-I9 · 卡级授权这一维仍然没有；「装卡点头」与「包级批准」被说成一件事**

- **证据**
  - `src/main/cards/grants.ts:26-38`：`CardGrant` **只有 `actionId`** —— **没有流程这一类**。
  - `src/main/workflows/runner.ts:843-849`：`granted()` 返回 `{ actions: { [actionId]: undefined } }` —— **无条件放行**。
  - `service.start()`（`service.ts:122-146`）的入参是 `(id, inputs)` —— **不知道是「哪张卡」在调**。
  - `docs/36:273`：权限判据只有「`permissions.workflows` 里有这个 id ✓ **且**它已批准 ✓」——

    而 `registry.ts:224-235` 的 `approve(id)` 记的是**包**（id + 内容摘要），**不是卡**。

  1. `spec/03` §2.4 的模型是「**有效写权限 = `permissions.write` ∩ 已授权**」——
     **两本账**：manifest 说的 vs 人授过的。流程侧现在**只有一本**（manifest 说的），
     → **「用户只批准了其中一部分流程」这条语义对流程不成立**（v2 评审 V2-C2 原话）。
  2. 装一张卡顺带**批准了整个包** → 那张卡之后删了，**别的卡也能跑这个包**。
     这一步把「**这张卡**被用户授过没有」这一维**整个删掉**了。
- **建议**（二选一，写进 ADR-D34）
  - **甲**：加**卡级授权**（`grants.json` 增一类 `(卡片 id, 流程 id, 流程包内容摘要)`），
    有效流程权限 = `permissions.workflows` ∩ **本卡被授过的流程** ∩ **已批准的包** ✓；
    §二·2.3 改成「**两本账**：包级批准（`workflows-approved.json`，绑内容摘要 ✓）
    ＋ 卡级授权（卡片授权账，绑 `(卡片 id, 流程 id, 摘要)`）✓」。
  - **乙**：明写「**首版没有卡级授权** → 任何声明了 `permissions.workflows` 的卡都能跑已批准的包 ✓」，
    并把这条**作为已知欠账**写进 §七 的「不做的事」——
    **不能既说「声明 ≠ 授权」（`docs/36:264`）、又说没有第二本账**。

## 四 · 逐条答复提案 §九「请评审重点看的这六条」

> **1. §二·2.5 确认链的落点（谁签发 → 人怎么点头 → 点完之后怎么继续；前面的步不重跑）——够不够？**

**不够，比 v2 强很多，但最后一格还空着。**

- **够的部分**：链路的**实现**是完整的、有单测、有守卫：
  `ConfirmationStore.approve` 两段式（`authorization.ts:184-201`）·
  `WorkflowService.confirm`（`service.ts:156-181`）·
  `pausedAtStep` 续跑（`service.ts:219-221` + `runner.ts:168-173`）·
  「前面的步不重跑」有专门的单测（`runner.test.ts:401-423`）与守卫（M111）。
  **「前面的步不重跑」这条硬要求**（`docs/36:118-119`）**落实了** ✓ —— 这条要给 v3 记功。
- **不够的部分**：**「人怎么点头」这一格在契约里是空的**（→ **V3-C1**）：
  §五 把批准操作放进了 **MCP 工具表**（agent 可调），
  而实现里那个接口调的正是「人点头的唯一入口」；
  `workflow:confirm` 不存在，GUI 侧的流程确认界面不存在。
  另外「续跑」在 API 上无路可走（→ **V3-I2**），
  唯一能用它的路径（`confirm`）要求**人已经批过** → 「人没点头时重试怎么办」这个问题**仍然没有答案**。
- **一句话**：**v3 把 V2-C1 从「类里没有」搬到了「契约里没有」**。类里那一份是真做了（值得记功）；
  契约那一份还差「批准权」这一格。

> **2. §四·4.1 的 `permissions.workflows`（规则 3 的另一半）——是不是该另开一个字段？**

**该另开，而且已经另开了 —— 这一条 v3 做对了。**

- **理由写清楚了**（`docs/36:266`）：`permissions.write` 装的是**板型包里的动作 id**，
  规则 5/6 会对它做「在板型包里存在吗」「不许通配符」的检查 —— **流程 id 不是动作 id**，
  混进去会让那两条规则误判 ✓。这个理由是成立的。
- **实现四处都到位**：字段表 ✓、解析 ✓、规则 3 的流程那一半（逐项报）✓、单测 ✓、守卫 M114 ✓。
- **但还差两条**：
  ① 「`permissions.workflows` **精确 id、不支持通配**」这条**根本没写进契约** ——
     §四·4.1 规则 5 的「为什么」里顺带提了 `write` 的规则 6，但**流程侧自己的通配禁令没有条款**；
     §八 item 2 也**没把 `spec/03` §2.3 列入改动清单**（v2 评审原话：「必须补上那五节」）。
  ② **「有效流程权限 = 声明 ∩ 已授权」的交集模型**没写进契约 ——
     `spec/03` §2.4 的现成模型是「**有效写权限 = `permissions.write` ∩ 已授权**」，
     流程侧要有一个对称的 §2.4 条款，而 §八 item 2 **没列 §2.4**；
     并且**「已授权」这一维在实现里不存在**（`grants.ts:26-38` 只有 `actionId`）→ 见 **V3-I9**。

> **3. §三·3.5 的八条判据规矩（含「形式 1 不支持」「判据只过地板」）——有没有漏？**

**漏了三条，其中两条是执行者层面的。**

- **八条里，六条有执行者** ✓：
  规则 2/3/8（角色必须在流程里声明过）→ `format.ts:563-568` ✓；
  规则 4（`await`/`assert` 必须说得出在哪个角色上读）→ `format.ts:486-488` ✓；
  规则 5（形式 1 直接报错）→ `format.ts:531-537` ✓；
  规则 7（判据命令过地板）→ 运行期 `runner.ts:645-655`（跨目标）+ `executor.ts:266-276`（同角色）✓。
- **漏的三条**：
  ① **规则 6（`none` 只在 `reversible` 上）没有执行者** ——
     板型包侧有（`tags/validator.ts:340-342`），**流程层没有**（`format.ts:525-582` 不看 `danger`）→ **V3-I7**。
  ② **规则 7 只有运行期，没有装包期** ——
     `src/main/workflows/format.ts` 全文**无 `checkFloor`** → 包里写 `readback.command: "rm -rf /"` **能过装包期** → **V3-I7**。
  ③ **规则 1 与规则 5 仍然打架**（→ **V3-M2**）；
     且 ADR-D32 §二要求的「判据词汇分『目标内』/『跨目标』两类」**没做**。
- **另外**：§三·3.5 规则 7 只说判据命令「要过地板」，
  **没说它必须只读** —— 而 §二·2.5 把「只读」当成了**前提**（「判据命令是**只读的**验证」）
  却把它当**事实**用在了「代价」那一段的推理里（→ **V3-I6**）。

> **4. §六 的九条运行语义（含并发与「重试 = 从头再跑」）——够不够？**

**不够。九条里两条（并发、超时）只有半句，另有一条（续跑）没有路。**

- **够的**：
  ① `run` 立刻返回 `run_id` ✓（实测耗时引对了：58.9s / 98.5s）；
  ② `status` 轮询 ✓（ADR-D31 R9）；
  ③ 状态机（`running`/`awaiting_confirmation`/`done`/`failed`）✓ —— **「等人点头不是失败」**这条写得很对，
  实现也照做了（`service.ts:216-221`）；
  ④ 幂等（status 层面）✓；
  ⑤ 续跑「前面的步不重跑」✓；
  ⑥ **取消明写不支持** ✓ —— 而且**把 `cancelled` 从状态机里删掉了** ✓（v2 的 V2-I1 一半解决）；
  ⑦ **「重试 = 从头再跑」写下来了** ✓（v2 的 V2-M5 补上了）——
  **但它给出的替代方案「用同一个 `run_id`」在 API 上不存在** → **V3-I2**。
- **不够的**：
  ① **并发（§六·7）没有执行者**，粒度也写错（按包 vs 按目标）→ **V3-I3**；
  ② **超时（§六·8）只写了「单步超时由 `timeout_ms` 定」** ——
     **默认值没说**（HAL 是 30 秒）、超时后的 reason 没说、该步算不算完成没说、清理没说；
  ③ **取消不可中断的后果没写**：ADR-D32 D32-4 与尖兵 S3 实测「75 秒的传输步收到取消后**照跑完**」——
     契约里「首版不支持取消」是对的，但**用户点了取消之后命令还在跑**这件事，
     流程**没有任何对外表达**（没有 `cancelling` 那一档）→ §六·3 的状态机要补一句。

> **5. §三·3.8 的四条跨机写规矩（含「不许关掉主机身份校验」）——够不够？**

**不够。两条是空转，两条不可执行。**

- **规则 1**（四项进确认摘要）：**没有执行者**，而且**没说传输步为什么会需要确认** → **V3-I4**。
- **规则 2**（装包批准时要显示跨机写）：**部分可达** ——
  批准界面确实逐条打印（`scripts/workflow-registry.ts:85-93`），
  `file.transfer` 步的 `cmd`（含 `scp {from.path} {role:target.user}@{role:target.host}:{to.path}`）
  **会显示** ✓；但**判据命令不显示**（→ **V3-I6**），且规则 2 说的「客机 → 板子 传 x」这句话
  在界面上**看不出来**（打印的是模板，不是解析后的源/目的地）。
- **规则 3/4**（主机身份）：**不可执行** ——
  宿主侧 ssh2 **根本没配 `hostVerifier`**（默认不校验），
  而传输命令的 ssh 策略**在源机器上**，宿主管不着；规则 4「校验失败 → 判据不成立」
  在流程层**无法判定** → **V3-I5**。
- **还缺一条最要紧的**：§二·T4 说「自由命令是第二条命令通道 ✗ —— 它必须与动作**同一条防线** ✓」，
  但**地板对 `ssh` 包装的命令是空的**（`floor.ts:188-189`）→
  `ssh host 'rm -rf /'` **过地板**。→ 这句话在自己的例子里失效 → **V3-I4**。

> **6. §七 的「不做的事」——有没有该做的？**

**有，六条。**

| # | 该补的「不做」 | 依据 |
|---|---|---|
| 1 | **卡级授权首版不做**（或反过来：补上） | §四·4.1 规则 3 说「声明 ≠ 授权 ✓」，但**没有第二本账** → **V3-I9** |
| 2 | **`ask` 形态的落位首版不做** | O19 已拍板三形态（`docs/05:1274`），实现只做两种（`format.ts:519-521`）→ **V3-M3** |
| 3 | **`verify` 判据命令会每 100ms 重跑**（首版不只跑一次） | 实现 `readback.ts:223-237` 一直轮询到超时 |
| 4 | **判据命令没有只读保证**（首版只过地板） | §二·2.5 把它当前提用了 → **V3-I6** |
| 5 | **失败/取消后不清理半截产物** | v3 §七 已有「失败后的产物清理」✓（这条补上了）—— 但**尖兵 §七·2 的「半截产物清理还没做」**要在契约里点名 |
| 6 | **流程层没有自己的版本协商**（`min_contract` 首版不做） | → §三 缺口 13 |

另外 §七 里**已经补上的**要记功：失败后的产物清理 ✓、分支与循环 ✓、
判据命令走确认通道（下一期）✓、续跑的任意步跳转 ✓ —— 这三条是 v2 评审 M5/M6 点名的，v3 补齐了。

**这四句的共同形状是：断言的对象存在，但断言的内容不是它的样子。**
下一版若只是把措辞再修一修，**这四条还会再开一次** ——
