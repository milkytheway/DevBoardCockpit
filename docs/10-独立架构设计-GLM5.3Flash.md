## 一、总架构：一个核心域，一条单向数据流

```
┌────────────────────────────────────────────────────────────────────┐
│ Electron main（核心域，唯一拥有设备 I/O 的进程）                      │
│                                                                    │
│  ┌──────────┐   事件    ┌──────────┐  sample  ┌──────────┐          │
│  │ Connection│ ───────▶ │ Roundtrip│ ───────▶ │  Reader  │          │
│  │    HAL    │          │  Queue   │          │ Registry │          │
│  └────┬─────┘          └────┬─────┘          └────┬─────┘          │
│       │                     │ ← poll scheduler 驱动 │                │
│       │                     ▼                     ▼                │
│       │                ┌─────────────────────────────┐             │
│       │                │          TagStore           │             │
│       │                │  值 + 五态 + 时间戳 + 环形历史  │             │
│       │                └──────┬──────────────────────┘             │
│       │                       │ 订阅推送（唯一出口）                 │
│       │        ┌──────────────┼───────────────┐                    │
│       │        ▼              ▼               ▼                    │
│       │  ┌──────────┐  ┌─────────────┐  ┌──────────────┐           │
│       │  │ Card     │  │ MCP Server  │  │ Renderer 桥   │           │
│       │  │ Runtime  │  │ (HTTP 回环)  │  │ (IPC 只读视图) │           │
│       │  └────┬─────┘  └──────┬──────┘  └──────────────┘           │
│       │       │ cockpit.actions.invoke                            │
│       │       ▼                                                 │
│       │  ┌────────────────────────────────────┐                 │
│       └─▶│        Action Pipeline（单入口）      │                 │
│          │ 编码→guard→地板→授权→执行→回读→审计     │◀── MCP execute_action
│          └────────────────────────────────────┘                 │
└────────────────────────────────────────────────────────────────────┘
          ▲
          │ postMessage 白名单 / ipcRenderer
┌─────────┴──────────┐
│ renderer（只画）      │  布局（react-grid-layout）、终端卡（xterm.js）、卡片 iframe 宿主
└────────────────────┘
```

**三条结构律**（本文其余部分都是它们的展开）：

| # | 律 | 出处 |
|---|---|---|
| S1 | **设备 I/O 只在 main。** renderer 不知道 adb/serialport 的存在；卡片 iframe 更不知道。 | ADR-D2 |
| S2 | **TagStore 是数据的唯一汇点、订阅的唯一源。** 不管数据是轮询来的还是推送来的，进 TagStore 之后再分发。卡片订阅的是 TagStore，永远不是某个连接。 | 本文 GLM-D1 |
| S3 | **动作只有一个准入入口。** GUI 按钮、MCP `execute_action`、卡片 `actions.invoke`，最终走同一条 `ActionPipeline.execute()`，不允许旁路。 | ADR-D7、`spec/04` §1.3 |

S2 是本文相对契约**新增**的一条结构承诺，理由见 §四：契约里 Stream 是占位，但 poll/push 两种取数形态必须在**接口层**留好，否则 M3 会把 poll 原型焊死成唯一形态。

## 二、进程模型与模块清单

Electron 三段（electron-vite）：`src/main`、`src/preload`、`src/renderer`。核心域全部在 main。

| 模块 | 职责 | 不负责 |
|---|---|---|
| `connections/` | Connection HAL：serial / adb / ssh / local 四实现 + capability 协商 | 解析、业务语义 |
| `roundtrip/` | 往返队列：互斥、marker 协议、串口单行变体、超时清理 | 决定「该不该发」（调度归 poller） |
| `tags/` | poll group 调度器 + reader kind 注册表 + 五态状态机 + TagStore | 触发动作 |
| `actions/` | ActionPipeline：参数校验/编码、guard、危险地板、授权、回读、审计 | 直接发命令（一切经 roundtrip 队列） |
| `cards/` | 卡片注册表、manifest 校验器、热重载、授权存储、卡片 iframe 生命周期 | 读板子 |
| `mcp/` | HTTP 回环 server + 发现文件 + 工具薄壳 | 业务逻辑（全部委托上面各模块） |
| `store/` | 配置、授权记录、审计日志、卡片 storage 的落盘 | — |

**每连接一个实例组**：`connections` / `roundtrip` / `tags` 按 connectionId 各持一份实例（一条连接一个队列、一个调度器、一个 TagStore 分区）；`actions` 是跨连接的单例，内部按 connectionId 分发。这是 §七 连接上下文的地基。

## 三、数据面

### 3.1 Connection HAL

接口（能力协商驱动降级，事实清单 §5.2 的继承）：

```ts
interface Connection {
  readonly id: ConnectionId;          // 来自 targets/*.json
  readonly transport: 'serial' | 'adb' | 'ssh' | 'local';
  capabilities(): { exec: boolean; files: boolean; pty: boolean; exitCode: boolean };
  open(): Promise<void>;
  close(): Promise<void>;
}
```

- `exitCode` 是新增的显式能力位：串口上为 `false`（事实 S5），运行时据此拒绝 `command_ok` / `verify` 类回读（契约 R2），而不是执行后假装成功。
- adb 路径来自 `profiles/settings.json`，不进代码（事实清单 §2 的规矩）。
- 子进程一律 `windowsHide: true`（事实 G3）。
- 连接断开 → 本连接 TagStore 分区**所有 tag 转 `unavailable`**（`spec/01` §2.3），不允许恢复旧值为 `ok`。

### 3.2 往返队列（互斥）

契约 `spec/02` §1.2.1 的执行点。每个连接一个队列，**采样与动作进同一个队列**：

```
出队 → 组装命令（poll group 合成 / action 模板编码）→ 发送
     → 按 marker 收集回包（串口上 marker 出现两次：回显一次、输出后一次，取其间内容）
     → 收齐或明确放弃该 marker → 允许下一次出队
```

| 项 | 规则 | 出处 |
|---|---|---|
| 优先级 | 动作请求插队到采样往返之前 | `spec/02` §1.2.1 |
| 错过周期 | 采样因让路错过本周期 → **跳过，不补发** | 同上 |
| 超时 | 超时后本周期跳过；marker 未收齐前队列不得放行下一次 | 同上 + 事实 S2 |
| 串口单行 | serial 传输上所有取数命令压成单行 | 事实 S6 |
| 超时码 | 各传输统一映射为 124 | 事实 G1 |

**marker 协议**沿用 fixtures 已固化的 per-reader 围栏（`###R <reader>` / `###E <reader>`，`fixtures/README.md`）：解析器遇到 reader 侧段缺失/畸形 → 该 reader 的 tag 报 `unavailable`，**不影响同组其他 reader**。旧扁平格式样本（`snapshot-sample.txt`）作为「未知分段降级行为」的回归输入保留。

### 3.3 Poll group 调度器

- 每个 poll group 一个定时器（`interval_ms` 来自包），到点把「组采样请求」入队（不是直接发送——队列可能正被动作占用）。
- 组内 reader 按包声明合成一条命令；每个 reader 的输出段独立成态。
- 自动识别时序照契约 `spec/02` §10：连接建立后、reader 启动前，用 `board.model` 一次性探测选包；认不出 → 终端/文件照常，监控/控制明确「这块板没有板型包」（§10.1 的「不猜」）。

### 3.4 Reader kind 注册表：从 YAML 生成，不许手写

**v1 的 8 个 kind**（`proc_stat` / `meminfo` / `devfreq_load` / `rknpu_load` / `thermal_zone` / `file_read` / `exec_regex` / `script`）的参数 schema、产出 sample、是否需两次采样，**机器可读形态从契约生成**：

```
docs/spec/02 §2.4 表 + data/tag-vocabulary.yaml
        │ build 时生成（脚本，不是手抄）
        ▼
src/tags/kinds.gen.ts   ← 头注标注「生成物，源头在 docs/spec」
```

对拍测试三源逐条比对：YAML ↔ `spec/01` 的渲染表 ↔ 生成物（`spec/00` §三、ADR-D18）。任何一源改动而另两源未动 → 测试红。生成脚本跑在 CI/提交前检查里。

### 3.5 五态状态机：唯一实现点

`spec/01` §2.1 那张迁移表**在一个纯函数里实现**，全工程只有这一处：

```ts
// src/tags/state-machine.ts —— 表驱动，与 spec/01 §2.1 逐行对应
transition(from: TagStatus, event: RuntimeEvent, hasPrevValue: boolean): TagStatus
```

- **纯函数**，输入 `(from, event)`，无时钟、无 I/O —— 黄金向量直接喂它。
- reader 只产 `ok/pending/unavailable/error`（判「读没成」）；`stale` 由运行时按「3 × poll group 周期」判（判「值新不新」）——分工照契约 §2.2。
- 取值越界 = `error`，不夹取、不当 0（§2.1 末段的强制）。
- 超时与失败同时发生 → `stale` 优先（§2.3）。
- `pending` 是**有状态 tag**（需两次采样做差）的专属态；基线建立前任何读失败不产生伪值。

**测试策略**：迁移表每行至少一条黄金向量（`fixtures/` 补 `state-machine/` 一组，真机事件序列抓取优先，构造样本须在文件头声明）。

### 3.6 TagStore

```
key = (connectionId, tag)
value = { value, status, at, reason?, detail? }    // reason/detail 见 §九 C5
```

- 每个 tag 保留**环形缓冲**（容量按 poll group 周期换算，默认保 300 点），MCP `sample_tag(name, n)` 直接从这里出。
- 推送按 poll group 节拍：到点、写库、然后统一广播订阅者——**订阅回调里不做任何取数**。
- 权限过滤发生在分发层：卡片订阅键先过 `permissions.read` 的模式匹配，再决定推不推（`spec/03` §7.1）。

## 四、push 预留：Source 双态接口（GLM-D1）

**问题**：契约里 Stream 是占位（`spec/00` §七自己承认）。但 Stream（HDMI 采集、摄像头→NPU、日志尾随）天然是 **push**：高频、不由宿主发起往返、不服从「采样给动作让路」的互斥模型。如果 M1/M2 按纯 poll 把「取数 → 分发」的路径焊死，将来补 Stream 等于破坏所有卡片 API。

**决策（提案 GLM-D1）**：v1 **不实现** Stream，但从第一行代码起，取数侧统一为 **Source** 接口，且 Source 有两个 kind：

```ts
interface SourceDriver {
  readonly kind: 'poll' | 'push';
  start(ctx: SourceContext): void;   // poll: 向调度器登记；push: 在连接上开监听
  stop(): void;
}
```

| | poll source（v1 实现） | push source（v1 只留形状） |
|---|---|---|
| 驱动者 | poll group 调度器 | 连接层事件 / 板端推送 |
| 互斥 | 进往返队列，给动作让路 | **不进队列**，独立通道 |
| 新鲜度 | 3 × group 周期 → stale | 心跳/到达间隔超阈 → stale（同倍数语义） |
| 汇点 | TagStore | **同一个 TagStore / 未来 StreamHub** |

**不变量的价值**：无论 kind 是什么，S2 成立——**卡片订阅 TagStore，不感知 Source 的 kind**。将来 Stream 落地时，卡片 API（`spec/03` §7.7）一行不改；改的只是「谁往 TagStore/StreamHub 写」。

**本条与契约的关系**：不违反 `SPEC-D4`（「连续流不是标签」）——push source 的新鲜度语义只是把五态的 `stale` 判据从「轮询间隔」泛化为「数据到达间隔」，tag 层不变。M1 实现时**只要求** poll 路径走 Source 接口、push 分支留空壳 + 一条注释指向本节；不写任何 Stream 业务代码。

**被否掉的选项**：
- 「现在就定完整 Stream 契约」——契约占位自有理由（没有第二块板的样本），提前定会重演「规格空转」。
- 「M3 再考虑」——接口多态是**一行签名**的决定，拖到 M3 的代价是返工所有卡片订阅路径。

## 五、控制面：Action Pipeline

### 5.1 单一准入（S3）

三个调用方，一个入口：

```
GUI 按钮 ─────────┐
卡片 actions.invoke ─┼─▶ ActionPipeline.execute(actionId, params, {caller, confirmId?})
MCP execute_action ─┘
```

`caller` 只影响**审计里记谁**，不影响裁决结果——权限判定对三个 caller 完全一致（ADR-D7「不允许旁路」）。

### 5.2 流水线（九步，顺序即契约）

```
1 resolve        动作在当前连接的板型包里存在吗？        否 → not_found
2 authorize      caller 的授权集 ∩ manifest write？（MCP caller 按其授权档） 否 → denied
3 validate       参数类型/范围/枚举/maxLength 再校验（不信包自述）        否 → invalid_params
4 encode         按类型编码：int/number 数字字面量；enum 取 values；
                 string 单引号包裹 + '\'' 转义，≤ maxLength            否 → invalid_params
5 render         编码值注入模板 → 最终命令字符串
6 guard          参数落 guard 域内？                                    否 → needs_confirmation (guard_exceeded)
7 floor          最终命令 shell 切词 → argv → 地板表匹配                命中 → 强制 destructive
8 confirm        destructive（含 7 强制）且无有效 confirmId？            是 → needs_confirmation
9 execute        入 roundtrip 队列 → 发送 → 回读（4 形式之一，串口拒绝 3/4）
10 audit         一行落盘：时间、caller、动作、参数、结果、回读值
```

要点：

- **地板匹配发生在「最终命令」上，不是模板上**（`spec/02` §5.2.1，ADR-D17）——这是第 5 步先于第 7 步的原因。匹配器实现为纯函数 `matchFloor(argv: string[]): FloorHit | null`，与表一起做黄金向量测试。
- **存在性先于授权**（`spec/04` §2.4）：`not_found` 先于 `denied`，让 agent 可发现能力、不可发现实现。
- **回读值是唯一可信的状态**：第 9 步之后，回读结果写回 TagStore，按钮渲染只认 TagStore——「点了什么」不进 UI 状态。
- `confirm_id` 绑定 `(动作 id, 参数规范化摘要, 板型包 id, 契约版本)`、一次性、5 分钟——照 `spec/04` §2.4.1，不赘述。

### 5.3 地板表的治理

- 表内容 = 契约 §5.2 的六条 + `danger_floor_version`；匹配规则 = §5.2.1（词元相等、`*` 后缀前缀、路径规范化、`dd`/`rm` 组合判定、表外记 warning）。
- **warning 是表 v2 的输入**：运行时把「表外命令」记进审计日志的独立通道，里程碑 M6 时人工（或让 agent）回顾这批 warning，作为契约升版提案——这让地板表「永远不完整」这件事有了收敛机制，而不是烂尾。

## 六、卡片运行时

### 6.1 托管与断网

- 每卡一个 iframe，`sandbox="allow-scripts"`，无 same-origin（ADR-D6）。
- 自定义协议 `cockpit://card/<id>/…` 托管卡片目录；**CSP 响应头由协议 handler 注入**，头内容逐字采用 `spec/03` §6.1（`connect-src 'none'` 等八条）。卡片无法覆盖——meta 标签不算数。
- CSP 违规事件汇入卡片运行时日志（MCP `get_card_runtime_log` 可见）——agent 因此能看见「这张卡试图联网」（ADR-D16 的测试策略）。

### 6.2 postMessage 桥

- preload 里一个极薄的 RPC shim：卡片调 `cockpit.*` → `postMessage` → main 校验（方法在白名单内、参数符合 `spec/03` §7.7 签名、读权限模式匹配）→ 执行 → 回包。
- **全 API 不抛异常**：失败返回 `{ ok: false, reason }`；`tags.get` 例外，返回状态化值。
- reason 码表与 §九 C5 的 `reason` 枚举**共用一张表**——卡片 API 错误码与 tag 不可用原因码是一套词汇，不给 AI 两套需要翻译的方言（这是本文对契约的一个补充建议，见 §十三 P3）。

### 6.3 存储

`cockpit.storage.*` 五方法，宿主代管落盘 `cards/<card-id>/storage.json`；JSON 可序列化、单键 64 KB / 总量 1 MB、键不得 `__` 开头——照 `spec/03` §6.2，无增减。

### 6.4 热重载与授权

- 文件监听 + `install_card` 两条路**同一道校验**（13 条清单）+ 同一套授权重审（`permissions.write` 变了 → 重新征求）。
- consent 绑定 manifest 内容哈希 + 目录快照，一次性、5 分钟——照 `spec/04` §2.3。

## 七、连接上下文绑定（GLM-D2）

**问题**（评审意见第四条）：契约规定卡片只见 tag 名，但本工程是多连接的。`cpu.usage` 在 TagStore 里的键是 `(connectionId, cpu.usage)`——这个上下文由谁携带、在哪一层定死，决定 M5 卡片 API 的形状。契约没写，这就是「Q4 阻塞 M5」的实质。

**决策（提案 GLM-D2）**：

1. **manifest 不携带连接。** 卡片声明的是能力（tag 名、动作 id），不是去向。
2. **连接发生在布局。** 布局单元记录 `(cardId, connectionId)`——用户把一张卡拖到某个连接的画布上，绑定即发生。一张卡可以在两个连接上各有一个实例（实例 = `(cardId, connectionId)`，共享同一份代码目录与授权）。
3. **卡片 API 的隐式上下文 = 实例的 connectionId。** iframe 创建时，宿主把 connectionId 注入 shim；卡片调 `tags.get("cpu.usage")`，宿主在 `(实例的 connectionId, "cpu.usage")` 上取值。卡片代码里**没有** connectionId 这个词。
4. **订阅键 = `(connectionId, tag)`**，TagStore 的分区键天然就是它（§二「每连接一个实例组」）。

**对 agent 的含义**：agent 写卡不需要知道连了谁；MCP 的 `list_tags(board?)` 返回带 `board` 字段，供 agent 校验「这张卡在目标连接上是否降级」。

**需要契约跟上的一步**（用户拍板项，见 §十三 P1）：在 `spec/03` §七加一段「卡片以**宿主注入的连接上下文**为隐式作用域；tag 名在卡片 API 内始终是不带连接前缀的全局名」。写死这一句，Q4（多板位号前缀）才能安全延后——因为前缀问题被隔离在宿主的解析层，永远不进卡片与 manifest。

**被否掉的选项**：
- manifest 写死 `connection`——卡就绑死了某块板，「N+M」退化回「N×M」。
- 卡片 API 显式传 connectionId——把宿主的路由问题泄漏给卡片作者（AI），每张卡都要多写一个没意义的参数，且写错不易察觉。

## 九、C4 / C5 落地方案（提案，等用户拍板）

### 9.1 C4：补三个动作，`system.reboot` 放首位（GLM-D4）

按 `docs/06` §二 C4 的候选表补进 `profiles/boards/rk3588-atk/board.yaml`：

```yaml
  - id: system.reboot
    label: 重启板子
    danger: destructive
    params: {}
    command: "reboot"
    readback:
      kind: verify
      command: "uptime -s"          # 验证命令：重启后 uptime -s 变化即确认
      timeout_ms: 60000
```

要点：

1. **串口注意**：`verify` 依赖退出码，串口上不可用（R2）——本动作在 ADB/SSH 连接上可用，串口连接上 `execute` 返回 `unsupported_transport`。这正是「destructive + verify」链在三种传输上的差异化验收样本。
2. **地板压包负样本**（评审意见的核心建议，采纳为 M6 验收判据）：
   - 在 `fixtures/validator/` 放一个**故意非法**的板型包样本：把 `reboot` 声明成 `danger: reversible`；
   - 断言两件事：**校验规则 16 拒包**（静态）；**运行时地板兜底**——即使包被强行喂给运行时，ActionPipeline 第 7 步仍判 `destructive`，返回 `needs_confirmation`；
   - 样本文件头声明「本样本永远不应通过校验」（fixtures 只增不改的纪律对它同样成立）。
3. `npu.governor.set`（走 `custom` 命名空间对齐 C3 的拍板）与 `debugfs.mount`（reversible，回读 `npu.usage` 转为可读——它是 C5 reason 机制的**活体验证样本**，见下）随后补齐。

### 9.2 C5：`reason` 封闭枚举 + `detail` 自由文本（GLM-D3）

**采纳评审方向：字段名 `reason`（机器码，给 AI 与卡片逻辑），另加 `detail`（自由文本，给人看）。** 位置：`spec/01` §二 五态的 `unavailable`（以及 `error`）事件结构。

```json
{ "value": null, "status": "unavailable",
  "reason": "device_absent",
  "detail": "/sys/kernel/debug/rknpu/load 不存在：debugfs 未挂载。修复：mount -t debugfs debugfs /sys/kernel/debug" }
```

**码表是契约级封闭枚举，带版本**（`reason_code_version`，与 `danger_floor_version` 同一治理模式）。起始三码：

| 码 | 语义 | 典型来源 |
|---|---|---|
| `not_in_pack` | 当前板型包根本不提供这个 tag | 静态可判，装卡时就能算出 |
| `device_absent` | 资源此刻不在：路径不存在、设备被拔、挂载丢失 | reader 段缺失、文件不可读 |
| `service_down` | 依赖的服务/进程没在跑 | exec_regex 的命令失败、script 推送失败 |

**RK3588 的 debugfs 案例归入 `device_absent`**——文件字面不存在，语义精确命中，`detail` 里写修复命令。不需要第四个码：码表保持最小，`detail` 承担特异性。

**卡片侧的联动**（这是 reason 码的全部目的）：`cockpit.degradation()` 返回缺失清单时携带 reason；卡片可用包内动作 id 与 reason 的**静态映射**渲染修复按钮——`unavailable(device_absent on /sys/kernel/debug)` ↔ `debugfs.mount`。映射声明在卡片 manifest？**不在**——它声明在板型包动作的 `heals` 字段里（v2 提案，本文不展开），v1 先靠卡片作者（AI）在读完 `describe_tag` + `list_capabilities` 后自己接线，这本来就是 agent 的本职。

**被否掉的选项**：
- 「包声明 `requires: [debugfs]`，运行时自动检查」——引入第二套前置条件模型，与五态+reason 冗余；且 requires 清单永远追不上现场（能力动态出现）。留给 v2 若 reason 码表长到十个以上再议。
- 自由文本 `reason`（不给封闭枚举）——AI 读不懂「每个包一种写法」的原因串，降级提示无法被程序化消费，等于没做。

## 十、fixtures 纪律与黄金向量（GLM-D5）

**纪律（采纳评审意见，固化为验收判据）**：

1. **黄金向量必须真机抓取**，构造样本必须文件头声明 ⚠️ 且给出派生规则——现状 `fixtures/README.md` 已有此规矩，本文把它升格为**验收硬判据**：任何「契约声称的行为」若无对应向量，里程碑不得标记完成。
2. **只增不改**：修正一个向量 = 新增文件 + 旧文件保留为回归输入。
3. **静态对拍不越界**：fixtures 对拍覆盖「解析、状态机、校验器、地板匹配」四个纯函数域；运行时行为（队列时序、热重载、授权）以 `npm run probe:board` 对真板验证，**不被静态对拍伪装成已验证**。
4. 当前缺口（`fixtures/README.md` §已知缺口）排进里程碑：真机第二份 `/proc/stat`、真机 per-reader 往返样本 → M0/M1 的 spike 顺手抓取；`rare` 组向量、两个动作回读向量 → M3。

## 十一、里程碑：spike 与主线并行（GLM-D6）

评审意见第一条**全盘采纳**，理由再压缩成一句：AI 产设计物的速度远超人类验证的速度，唯一的解药是让冻结的契约尽早接触现实——黄金向量对拍再绿，也代替不了真板上冒出的第一个数字。

|---|---|---|
| **writing-plans** | 实施计划文档，**半天上限**。M0–M3 顺序已明确，计划不许比代码长得快 | 一页纸：任务序列 + 各任务引用的契约节号 |

| **M3 控制面** | ActionPipeline 全九步、地板匹配器、guard、授权存储、`backlight.set`/`cpu.governor.set` 控制卡 | 回读闭环实测：改背光 → UI 显示板子真实值；串口上 destructive 依赖退出码的动作返回 `unsupported_transport`；fixtures 补动作回读向量 |
