## ADR-D1 · 技术栈：Electron + React + TypeScript（整体推翻旧 UI）

**背景**：旧工程 = Python + PySide6(Qt Widgets)。愿景要求卡片是任意网页 + iframe 沙箱 +
白名单 API + 热插拔 + 拖拽布局，Qt Widgets 没有对应物（PySide6-Essentials 连 WebEngine 都不含）。

**决策**：新工程全量使用 **Electron + React + TypeScript**（electron-vite）。
旧的 Python 核心**不作为运行时保留**，其知识与样本迁移进文档与测试向量。

**被否掉的选项**：
- Tauri v2（终端要另起 Rust/Node 侧车，复杂度翻倍）
- Wails + Go（生态成熟度、MCP/前端库不如 TS）
- 浏览器 + 本地 daemon（没有桌面应用质感，与「Windows 桌面工作台」定位冲突）

**影响**：终端渲染从自研 pyte 网格换成 xterm.js；旧 `ui/` 全部重写。

## ADR-D2 · MCP server 必须与 GUI 同进程（放 Electron main）

**背景**：愿景写明「GUI 实现 MCP server」，agent 需要读卡片清单、卡片运行时日志、
数据源、连接状态。

**决策**：**MCP server 与卡片注册表、tag 层、action 层全部在 Electron main 进程内**，
用普通函数调用互操作，不跨进程。

**理由**：这是 D1 的**硬约束**，也是否掉「双层混合（Python 后端 + Electron 界面）」的直接原因：
若 MCP 在 Python 侧，它读不到 Electron 里的卡片清单与运行时日志，就得再架一条反向桥，
最终变成 Python ⇄ Electron ⇄ Python 两条桥——恰好是愿景最不该有的复杂度。

**被否掉的选项**：Python core + Electron UI 的双层混合（路线 B）。

**影响**：设备 I/O、tag、action、卡片注册表、MCP 全部落在 main；renderer 只负责画。

## ADR-D3 · 布局模型：网格单元（react-grid-layout）

**背景**：需求是「任意拖拽」。

**决策**：卡片占**网格单元**，可拖动换位、可在单元内缩放；布局存 JSON，可导入导出分享。

**理由**：组态软件的语义是「画面 + 元件」；自由浮动面板虽然灵活，但布局难以序列化与分享，
且与「组态」的心智模型不符。

**被否掉的选项**：自由浮动面板（dnd-kit）。

**影响**：需要定下网格列宽/断点策略；布局文档只描述「卡片 id → 单元矩形」。

## ADR-D4 · 卡片视图：免构建 ES Module

**背景**：愿景要求「agent 写完卡片即生效，热插拔」。

**决策**：卡片目录 = `manifest.json` + `view.js`（原生 ES Module，**不需要任何构建步骤**）。
应用用自定义协议 `cockpit://card/<id>/…` 托管，卡片内可用相对路径 `import`。

**理由**：AI 写原生 JS 比写 React 组件 + 构建链更少出错；改文件即生效，是「一轮对话做完一张卡」的技术前提。

**被否掉的选项**：预打包 bundle（更可控但引入构建步骤，热插拔有摩擦）；卡片写成 React 组件（要工具链）。

**影响**：卡片是「平台无关的原生 JS」，不引入框架；需要一份 `card-sdk.js` 提供白名单 API 客户端。

## ADR-D5 · profile 拆成两个正交概念

**背景**：旧工程只有「连接 profile」（怎么连上）；愿景的「板型 profile」讲的是「这块板的每个 tag 怎么产生」。
同一块板在旧工程里出现两次（ADB / 串口）→ **板 ≠ 连接**。

**决策**：
- **连接 profile（target）**：`profiles/targets/*.json`，描述**一个连接实例**（连谁、用什么传输、参数）。
- **板型 profile（board）**：`profiles/boards/*.yaml`，描述**一类板**（这台板有哪些 tag、每个 tag 怎么产生、
  有哪些 action）。
- 连接 profile 通过 **`board_pack`** 字段引用板型；一个连接实例可指向任一板型。

**理由**：兑现愿景里「N 张卡 × M 种板 = N+M 个文件」。不拆的话，N 会被 M 放大回 N×M。

**影响**：这是 tag 契约能成立的前提，必须在写实现之前冻结。

> **2026-11-12 评审修订**：绑定键的名字统一为 **`board_pack`**（契约口径）。
> 历史上 `board` 与 `board_pack` 两种写法并存，运行时按契约只认 `board_pack`，
> 见到 `board` 报「未知顶层字段」。见 ADR-D15。

## ADR-D6 · 卡片沙箱：sandbox iframe + postMessage 白名单

**背景**：愿景的「双层安全」第一层：坏卡搞不垮工作台。

**决策**：每张卡跑在 `<iframe sandbox="allow-scripts">`（**不给 same-origin**）里，
宿主能力一律通过 `postMessage` 白名单 API 暴露，方法名以契约
`spec/03` §7.7 的**全集**为准：
`tags.get / tags.subscribe / tags.subscribePattern / tags.list / degradation /
actions.invoke / storage.get / storage.set / storage.remove / storage.keys /
storage.clear / log / notify`。

**理由**：不给 same-origin，iframe 无法触碰宿主 DOM 与存储；白名单 API 让卡片能力显式可审。

**影响**：卡片不能直接访问 `window.parent`、不能取 cookie/localStorage；
所有数据都经宿主转发。卡片崩溃只影响自己那一帧。

> **2026-11-12 评审修订**：原 ADR 另列了一套方法名（`getTag / subscribeTag /
> setAction / log / notify / listTags`），与契约的 `tags.*` / `cockpit.*` 不一致，
> 且 `log` / `notify` 在契约里从未定义。现改为**只引用契约的全集**，不另立一套。
>
> 另：sandbox 属性**不限制网络**。断网由宿主注入的 CSP 执行（`spec/03` §6.1），
> 存储由宿主托管的 `cockpit.storage.*` 提供（`spec/03` §6.2）。
> 这两条是契约级承诺，实现细节见 `docs/04` §6.2。见 ADR-D16。

## ADR-D7 · 控制面：动作两档分级 + 参数域 + 回读闭环

**背景**：愿景的「技术命门」——点击 → 写命令 → **回读状态** → UI 以回读为准。

**决策**（**2026-11-12 评审后按契约口径改写**）：
- 动作只有**两档**：`reversible` / `destructive`。**只读不是动作**——只读走 tag。
- 危险等级声明在**板型包**里，字段名 **`danger`**；**卡片 manifest 不声明 `danger`**。
- 写入后**必须回读**，回读结果才是 UI 的显示依据（不显示「你上次点的意图」）。
- `destructive` 需二次确认 + 审计；`execute_action` 支持 `dry_run`。
- GUI 按钮与 MCP `execute_action` **走同一个准入入口**，不允许旁路。
- 动作可声明**参数域 `guard`**，超出域内的参数要另行确认（见 ADR-D18）。

**理由**：这是「驾驶舱」与「遥控器」的分界线，也是 agent 安全边界。

**影响**：action 层要在 main 进程集中裁决；审计日志落盘。

> **2026-11-12 评审修订**：原 ADR 写的是「三档 `read`/`reversible`/`destructive`，
> 字段名 `tier`，声明在**卡片 manifest** 里」——这与契约正面冲突：
> 契约明确「只读不是动作」，且卡片的 `danger` 字段会被校验器拒绝
> （`spec/03` §九 规则 11）。按「契约是权威」的口径，**以契约为准**，
> 本 ADR 改写成两档 / `danger` / 板型包声明。
> 被否掉的选项：三档制（`read` 作为动作档位）——只读走 tag 更简单，
> 少一个档位就少一处「只读动作到底算不算破坏」的争论。

## ADR-D8 · 板型 profile 用 YAML

**背景**：愿景写明「板型 profile（YAML 数据包，每板一份）」。

**决策**：板型 profile 用 YAML；连接 profile 保持 **JSON**（从旧工程迁移，兼容用户已有文件）。

连接 profile 是机器读写的小结构，JSON 足够。

## ADR-D12 · 契约层沿用迁入的 spec 草案，不另起炉灶

**背景**：新工程开工时，前身工程里躺着一份**未提交但完整**的契约层：
`docs/spec/` 五份文档（tag 契约、板型包、卡片 manifest、MCP 工具集、总览）、
一份真实板型包 `boards/rk3588-atk/`。
同一批产出里还有一套 Python 参考实现 `tools/boardkit/`（含单测与真机样本）——
那部分属于**实现**，处置见 ADR-D13。

**决策**：**契约层整体迁入新工程，作为权威**（`docs/spec/`、
`profiles/boards/rk3588-atk/`）。
新工程的设计文档**只写落地方式，不复述契约**。

**理由**：

1. 那份契约是**语言中立**的（它自己写着「外壳选 Electron、选薄壳还是纯 Web，
   规格一个字都不用改」），正好就是本工程要的东西。
2. 它在契约层比 Codex 的独立草稿**更严谨**：命名规范（设备域.实例.属性）、
   五态模型（`ok/stale/unavailable/error/pending`）、词表准入门槛、
   「占空比不得绑定 `*.usage`」这类可机器校验的规则——都是踩过坑才写得出来的。
3. 有**真机样本**（`fixtures/`）：契约的验证材料，越早固定越好。

**影响**：

- Codex 早先起草的 `profiles/boards/atklrk3588.yaml`（另一套命名）**作废并删除**，
  避免两套词汇表并存。
- 契约与实测的差异**不私自改**，统一记进 `docs/06-契约核对.md`，由用户拍板。

## ADR-D13 · 契约评审通过前不保留任何实现代码

**背景**：迁入的那批产出里混着一套 Python 参考实现（解析器、校验器、探针、词表，
加三份测试）。它当时「躺在旧工程里没提交」，看起来像参考资料，
实际是**在契约定稿之前就写出来的实现代码**——顺序反了。
其中确有几处实现 bug（如 `flash_uboot` 因 `\b` 不匹配下划线而漏过危险地板）。

**决策**：**移除那套 Python 实现**，本工程在契约评审通过前**不含任何实现代码**。

**理由**：

1. 评审的对象是**契约**，不是实现。留着一份未评审的实现，
   会让人误以为「它已经对了」——而它没被评审过。
2. 契约若在评审中改了（很可能），那份实现就得跟着改；改完还得再评审一遍，
   等于把评审工作量翻倍。
3. 它作为「契约的可执行解释」的价值，**可以通过「实现层从契约生成 + 逐条核对」得到**，
   不需要靠一份手写的第二份来保证（见 `docs/04-架构设计.md` §4.3）。

**保留**：契约文档、板型包数据、真机样本 `fixtures/`——都不是实现。

**影响**：

- `docs/spec/01` 的词表权威从「`vocabulary.py`」改为「本表即权威，实现层从它生成」；
  `docs/spec/02` 的校验规则表明确为「这 19 条就是契约本身」。
  **这是表述的更正，不是契约内容的变更。**
- 那份 Python 代码没丢：迁入时的版本在本工程 git 历史里（提交 `c24b084`）。
  评审通过后可以取回来对照，**但不作为实现直接使用**。

> **2026-11-12 评审修订**：上面那句「这不是契约内容的变更」**不准确**。
> `git diff c24b084 0244852 -- docs/spec` 是 **+956/−187 行**——
> 危险地板、agent 授权、传输与发现都是那一次加进来的。
> 契约层的**当前基线已由用户追认**（ADR-D15），
> 逐节来源见 `docs/spec/00-overview.md` §一之二。

## ADR-D16 · 卡片断网与存储：宿主注入 CSP + `cockpit.storage.*`（用户 2026-11-12 拍板）

**背景**：契约承诺「网络默认禁，且 v1 无法申请」「只能写卡片自己的命名空间」，
但实现只写了 `<iframe sandbox="allow-scripts">`。
**sandbox 属性不限制网络**——卡片照样能 `fetch` / `WebSocket` / `sendBeacon`；
而**不给 same-origin 的 iframe 里 `localStorage` 会抛 `SecurityError`**，
「可写自己的命名空间」根本兑现不了。

**决策**：
- **断网由宿主注入的 CSP 执行**（`spec/03` §6.1 给了完整头）：
  `connect-src 'none'` 断掉 `fetch`/`XHR`/`WebSocket`/`EventSource`，
  `img-src 'self' data:` 断掉 `<img>` 外传。卡片**不能**覆盖它。
- **存储由宿主代管**：卡片经 `cockpit.storage.get/set/remove/keys/clear` 访问，
  每卡一个命名空间，值必须 JSON 可序列化，单键 64 KB / 总量 1 MB。

**理由**：卡片的合法输入恰好是板子的遥测，而卡片的作者是 agent。
「一张坏卡能把板子数据发出去」必须由机制挡住，不能靠卡片自觉。

**影响**：`docs/04` §6.2 要写清 CSP 注入位置与 storage 的落盘位置；
卡片 API 清单（`spec/03` §7.7）要加上 `storage.*`；
测试策略要加一条：卡片 `fetch` 外部被 CSP 挡住、且违规进运行时日志。

## ADR-D17 · 动作安全链：参数编码 + 地板匹配解析后的命令 + 授权参数域（用户 2026-11-12 拍板）

**背景**：动作安全链有三处独立断裂，任何一处都足以让确认机制形同虚设：

1. `string` 参数原样拼进 root shell（`--model 'x; reboot'`）；
2. 地板匹配的是**命令模板**而不是渲染后的命令，注入进来的 `reboot` 不在模板里；
3. 授权只到动作 id，用户批准「可以改背光」实际拿到 `0..255` 全域。

**决策**（三条同时上）：
- **参数按类型编码后注入**（`spec/02` §4.6）：整数按数字字面量、
  枚举按 `values` 里的值、**字符串一律单引号包裹并转义 `'`**，长度受 `maxLength` 限制；
  模板里的占位不得自带引号。运行时执行前**再校验一次**。
- **危险地板匹配「解析后的 argv 序列」**，不是模板（`spec/02` §5.2.1）：
  词元相等而非子串（`upgrade_status.sh` 不命中 `upgrade`）、路径先规范化、
  地板表带 `danger_floor_version`、表外命令记 warning。
- **授权粒度 = 动作 id + 可选参数域 `guard`**（`spec/02` §5.5）：
  `guard` 只能**缩小**参数的声明域，不能扩大；超出域内的参数要走一次确认。

**理由**：「没有人能绕过人的确认」是契约里最重的一句承诺。
它需要三道机械闸门，而不只是文档里的一句话。

**影响**：板型包的动作要声明 `params` 的类型与 `maxLength`；
`danger` 档位不变（仍两档，见 ADR-D7），但 `destructive` 的回读形式增加 `verify`（`spec/02` §4.5）。

## ADR-D18 · 契约层的两个机械承诺：往返互斥 + 词表机器可读（用户 2026-11-12 拍板）

**背景**：两个问题在评审中被指出，都不需要产品取舍，但必须写进契约。

**决策**：
- **同一连接上的一次往返必须互斥**（`spec/02` §1.2.1）：
  poll group 的采样往返与动作往返共享同一条通道，进同一个队列；
  **动作优先**；采样因让路而错过本周期就**跳过，不补发**；
  超时后必须等 marker 收齐或明确放弃才能开始下一次。
  理由是串口只有一根线、一个读线程、一份 transcript（事实 S1/S2），
  并发往返会导致 marker 回包串台。
- **核心词表以 `docs/spec/data/tag-vocabulary.yaml` 为唯一权威**
  （`spec/01` §一），Markdown 表格是它的渲染结果，实现层也从它生成。
  理由：Markdown 表格不是可靠的机器可读载体（单元格含 `|`、列序靠人维护）。

**影响**：实现层要有一个「从 YAML 生成词表与表格」的步骤；
对拍测试要比对三份：YAML / 渲染结果 / 代码里的词表。

## ADR-D19 · MCP 传输：HTTP 回环 + 发现文件 + bearer token（用户 2026-11-12 拍板）

**背景**：契约倾向 HTTP + 发现文件，设计选了 stdio，还提出「独立进程 `--mcp-stdio`」——
三方各写一套。独立进程同时违反 ADR-D2（MCP 必须与 GUI 同进程）与契约（没有发现机制）。

**决策**：
- **MCP server 走 HTTP 回环**，listener 仍在 Electron main 进程内（ADR-D2 不变），
  agent 连的是**已经在跑的 GUI**。
- **本机安全基线写进契约**（`spec/04` §7.1）：只绑 `127.0.0.1`、
  校验 `Origin`（不合法回 403）、校验 `Host`、每个请求带 bearer token、
  token 每次启动重生成、发现文件仅当前用户可读、不发 CORS 头。
- **发现文件**（`spec/04` §7.2）加 `token` 字段；先写临时文件再原子改名；
  GUI 退出即删；agent 连不上时不重试其他端口。

**理由**：本地 HTTP MCP server 若不校验 `Origin`/`Host`，
任何用户访问过的恶意网页都能通过 DNS rebinding 直接驱动 `execute_action` 改用户的板子。
MCP 规范对此有明确要求（「servers MUST validate the `Origin` header」）。

**影响**：`docs/04` §9 从 stdio 改成 HTTP；stdio 的「独立进程」选项被否掉；
Windows 防火墙弹窗的问题要在实现阶段实测（loopback 通常不弹）。

## ADR-D20 · 板型包须人确认才生效；卡片不审批（用户 2026-11-12 拍板）

**背景**：`spec/04` §2.4.2 写着「包一律生效……agent 可以写板型包扩展，写完直接用」。
但板型包的 **reader**（`exec_regex` / `script`）能在板子上执行任意命令，
而**危险地板只管动作**（`spec/02` §5.2）。两条合起来就是一条绕过确认的通道：
agent 写一个包，reader 里跑一条任意命令，这条命令不过地板、不需要人确认。

两份独立设计（`docs/10`）都指出了这个问题，**两轮评审（`docs/07` / `docs/08`）都没发现**。

**决策**：
- **卡片的创作面是 agent 的**——装卡**不**审批（`spec/03` §3.3 不变）。
- **设备的权限面是人的**——agent 可以起草板型包，但**启用要人确认**。
  确认界面必须展示：这个包会执行哪些命令、声明哪些动作、每个动作多危险、涉及哪些 tag 与路径。
- **升级不静默扩权**：升级若新增 `destructive` 动作或扩大命令权限，必须重新确认。
- 装包失败不影响终端与文件互传（该连接相关 tag 报 `unavailable`）。

**理由**：「不准有裸 send_command」（`spec/04` §1.3）与「包一律生效」不能同时成立——
一个能执行任意命令的 reader **就是**裸命令通道，只是换了入口。

**被否掉的选项**：
- 现状（包一律生效，agent 写的也生效）——上文的旁路。
- 完全禁止 `exec_regex` / `script`——它们是契约的逃生门，砍掉就没有复杂板子的出路。
- 让 reader 也过危险地板——地板是**下限**不是**授权**；reader 的命令在采样期就要跑，
  逐次确认会让采样不可用。

**影响**：**收窄 `SPEC-D12`**（包一律生效 → 人确认过的包才生效）。
`spec/02` §5.6 与 `spec/04` §2.4.2 已同步。

## ADR-D21 · 取数侧接口为 Source（poll / push），v1 只实现 poll

**背景**：契约里 Stream（视频 / 日志 / 文件）是占位定义（`spec/00` §七）。
但 Stream 天然是 **push**：高频、不由宿主发起往返、不服从「采样给动作让路」的互斥模型。
若 M1/M2 把「取数 → 分发」按纯 poll 焊死，将来补 Stream 等于返工所有卡片 API。

**决策**：
- 取数侧统一为 **Source 接口**，`kind ∈ {poll, push}`。
- v1 **只实现** poll；push 分支留空壳 + 注释指向该节。**不写任何 Stream 业务代码。**
- 不违反 `SPEC-D4`（「连续流不是标签」）：push 只是把 `stale` 的判据
  从「轮询间隔」泛化为「数据到达间隔」，tag 层不变。

**理由**：接口多态是**一行签名**的决定，拖到 M3 的代价是返工所有订阅路径。

**影响**：`docs/04` §5.4 写明接口形状与 v1 的实现边界。

## ADR-D22 · TagStore 是读数的唯一汇点；读数带单调 `seq`

**背景**：没有一条规则说「UI、卡片、AI 看到的必须是同一份状态」。
于是每层都可能自建一份「我记得是……」，出现两块卡片显示不同数字、
而用户无法判断哪个是真的。

**决策**：
- **TagStore 是读数的唯一汇点**：不管数据来自轮询还是将来的推送，
  进 TagStore 之后再分发。卡片订阅 TagStore，不订阅「某个连接」。
- **质量只由 tag 引擎产生**，卡片 / UI / MCP 不得改写。
- 每个读数带 `seq`（同一 tag 内单调递增），渲染层按 `seq` 丢弃乱序的旧值。

**理由**：「驾驶舱」产品的底线是 UI 显示板子的真实状态。
一份状态有多个副本，就等于没有真相。

**影响**：`docs/04` §5.3 写明落点。`seq` 需要进 `spec/01` 的读数结构（见 O13）。

## ADR-D23 · 一次往返在链路上独占；动作与回读不可拆分

**背景**：`spec/02` §1.2.1 已定「采样与动作进同一个队列」。但没有定**优先级**，
也没说清「动作的执行 + 回读」是不是一个不可分的单元。

**决策**：
- 四级优先级：`action-verify` > `manual-refresh` > `card-sampling` > `diagnostics`。
- **动作的执行与回读是一个不可拆分的独占事务。**
- 每个事务带 deadline（连接级默认 3 秒）；排队超时报 `conn_busy`，队列有上限。
- 终端活跃时托管采样暂停，受影响 tag 转 `stale` + reason `link_busy_terminal`；
  空闲后恢复。**停采必须如实反映成质量，不能静默。**

**理由**：回读若被采样插队，读到的可能是别的命令的输出——
「回读不符」就成了假阴性，驾驶舱会显示错的真实状态。
而无界排队等于把「卡」变成「数据旧」，那是最难排查的一类故障。

**影响**：`docs/04` §5.1 写明落点。

## ADR-D24 · capability 词汇表：板级与连接级是**两个轴**（用户 2026-11-13 拍板）

**背景**：`docs/spec/02` 的 `requires.capabilities` 用 `shell` / `exec` / `stream` / `files`，
而实现层（`src/shared/ipc-contract.ts`）用 `exec` / `pty` / `files` / `exitCode`。
**两套词既不同名也不同义，根本不是同一个轴**：
契约那套是**板子级**的（「这块板能做什么」），
实现那套是**连接级**的（「**这条连接**能不能…」）。

能立刻看出不对的例子：**串口传不了文件**（事实 S7），但**板子**当然有文件通道——
所以 `files` 在契约里是板子的属性，在实现里是连接的属性。

**决策**：

1. **两套词各归各位**。契约那套叫**板级能力**，实现那套叫**连接级能力**。
   **不合成一套**——合成一套就等于让包感知传输，直接违反 `spec/02` §10.2
   （「包描述板子，HAL 描述通道，两者由运行时接起来」）。
2. **契约里放一张「词义对照表」**（`spec/02` §10.3.2），**不是函数**——
   同一块板走 adb 和走 serial 连接能力完全不同，**板子能力推不出连接能力**。
   表里 `exitCode` **没有板级对应物**：它是**通道的属性，不是板子的属性**。
3. **实现层改名 `Capabilities` → `ConnectionCapabilities`**。
   依据：`capabilitiesFor(profile)` 读的是 **profile**，`pty` **可被 profile 覆盖**
   → 是连接级；叫 transport 级会跟代码自己的注释打架。
4. **`requires.capabilities` 是信息，不是连接门禁**。
   串口的 `files=false`——拿板子级 `files` 做门禁，这个包在串口上就废了，
   **违反 §10.2**。它做两件事：被校验（规则 25/26）、被查询（包描述接口）。
5. **`stream` 留在词表，但 v1 的包不许声明它**。
   新增**规则 25**（封闭词表）与**规则 26**（必须是运行时已实现的能力），
   声明 `stream` 是**错误**不是警告。
   **规则 26 读的是一张数据表，不是硬编码的 `if (stream)`**——
   Stream 契约落地那天，改的是表，不是规则。

**被否掉的选项**：

| 选项 | 为什么否 |
|---|---|
| B · 统一成契约那套（`pty`→`shell`、加 `stream`） | `exitCode` 没地方放——它是实现必需的（串口 false），契约里没有对应词。要动契约 |
| C · 契约那套冻结，实现层另起一套但改名 | 「同名不同义」继续存在，将来一定有人踩 |
| Codex 的「把 `stream` 从契约词表删掉」 | 顾虑（不许恒假）成立，但**处置不必是删词**：删了将来要还，而还的时候才升 `apiVersion`。改用规则 26 硬报错，撞到的人拿到的是指路牌而不是悄悄的洞 |
| GLM 的「叫 `TransportCapabilities`」 | 与 `capabilitiesFor(profile)` 的实际语义不符（`pty` 可被 profile 覆盖） |

**理由**：它们本来就是两个轴。硬合成一个词表会逼着实现层长出「板子级」的字段
（`stream` 现在根本没实现，合过去只能给个恒 false，等于把契约缺口藏进类型里）。

**影响**：
- `spec/02` §10.3 新增能力词表与词义对照表；§一 的示例包与
  `profiles/boards/rk3588-atk/board.yaml` 去掉 `stream`；
- `spec/02` §七 规则数 24 → 27；
- `src/shared/ipc-contract.ts` 及其全部引用点改名；
- 实现层的 `ConnectionCapabilities` **不是契约词表**——它是运行时的协商结果。

**评审意见的采纳**：Codex 的「词义对照表不是函数」「改名 `ConnectionCapabilities`」
「`requires.capabilities` 要有消费者」「`exitCode` 本来就该是连接级的」全部采纳；
GLM 的「`stream` 留词表 + 硬报错」采纳，其「映射矩阵当校验数据派生 transports×capabilities
一致性规则」**方向采纳但不落成规则**（`ssh`/`local` 两行没有实测依据，写死会变成假规则）。
逐条处置见 `docs/16` §六。

## ADR-D25 · 没有回读的动作：`readback: {kind: none}` + `verified: false`（用户 2026-11-13 拍板）

**背景**：契约 §4.1 正文写的是「**每个**动作必须声明怎么回读」，
但 **24 条校验规则里只有第 15 条管 `destructive`**——
**一个 `reversible` 动作不写 `readback` 也能过校验**，闭环静默断掉。

同时，有一类动作**真的没有可回读的状态**（点亮 LED、往 UART 写字节、触发蜂鸣），
契约里没有能表达它们的形状 → 这类动作**根本无法声明**。

**决策**：

1. **新增回读形式 5：`readback: { kind: none }`**（`spec/02` §4.4.1）。
   **只用这一种拼法**——`verify` 块**不允许** `kind: none`
   （否则「没有回读」有两种写法，校验器要同时认两种表达同一件事的写法）。
2. **`none` 必须显式写**，不许用「不写」表达同一件事。
   **新增规则 27**：每个 action 必须有 `readback` 块；`kind` 为 `none` 时
   **必须带非空 `consequence`**（一句话说明副作用）。
   **把「声明用户可见后果」从自然语言变成机械可查的字段**。
3. **`none` 只允许 `danger: reversible`**；`destructive` 仍禁止
   （它若真没有可观测后态，唯一合法路径是加一条 `verify` 命令）。
4. **执行结果用 `ok: true` + 独立布尔字段 `verified: false`**（`spec/04` §2.4）。
   **`unverified` 不进 `spec/01` §2.1.1 的 tag reason 枚举**——
   那是 **tag 读数**的原因码；动作结果的原因码在 `spec/04` §2.4。**两张表，别混。**
   `unverified` 也不是 tag 状态——加进五态会污染所有 tag 消费者。
5. **UI 口径写死**：`verified: false` → 显示「**已执行，未验证**」，
   **不得**显示成「已生效」。
6. **逐动作 warning + 审计留痕**：校验器对每个用 `none` 的动作记一条 warning；
   审计日志要能一眼看出「未验证」（`spec/02` §5.4）。

**被否掉的选项**：

| 选项 | 为什么否 |
|---|---|
| C · 用 `verify` 跑一条恒真的命令（如 `true`） | **把「没验证」伪装成「验证过了」**——`verify` 的语义是「验证板子进入了目标状态」，`true` 什么都没验证，却让调用方以为验过了。**这正是这份契约一路在防的事**（同 `unavailable ≠ 0`） |
| `ok: false` + `reason: "unverified"` | 命令**确实执行了、效果也确实有**（点 LED 亮了）。报失败是**另一种撒谎** |
| `ok: true` 什么都不说 | 把「没验证」藏起来——**与被否掉的 C 是同一个毛病** |
| 两种拼法并存（`readback:{kind:none}` 与 `verify:{kind:none}`） | 校验器要同时认两种表达同一件事的写法 |

**理由**：`ok: true` + `verified: false` 是**唯一同时避开这两种撒谎的表达**。
驾驶舱的产品底线是「UI 显示板子的真实状态」——
**把没验证的东西显示成生效了，比不显示更危险。**

**影响**：`spec/02` §4.4 改「五选一」+ 新增 §4.4.1；§4.5 明写 `verify` 不许 `none`；
§七 规则 15 与 23 扩充、规则 27 新增；`spec/04` §2.4 加 `verified` 字段与 UI 口径；
`spec/01` §2.1.1 加一句交叉引用（防止后人指错表），**其枚举本身不动**。

**评审意见的采纳**：Codex 的「只用一种拼法」「`unverified` 不进 tag 的 reason 表」
「改用 `verified: false`」「顺手补『每个动作都必须有 readback』」全部采纳；
GLM 的「`consequence` 必填非空」「逐动作 warning」采纳，其
「`unverified` 加进 `spec/01` §2.1.1」**不采纳**（指错了表）。

## ADR-D26 · `npu.governor.set` 与 `debugfs.mount` 不补（用户 2026-11-13 拍板）

**背景**：`docs/06` C4 列的三个动作里 `system.reboot` 已补，
另两个还悬着。`npu.governor.set` 按原规格**根本实现不了**
（板型包没有 `npu.governor` 这个 tag，规则 12 必然拦下它）；
`debugfs.mount` 的回读**自指**（挂上之后才有 `npu.usage`）。

**决策**：**两个都不补**，理由分别如下。

### `npu.governor.set` —— 理由是**实测会锁死且不可恢复**

**实测 E4（2026-11-13，真板）**：向 NPU 节点写 `powersave`，
**写调用挂死在内核里**——`/proc/<pid>/wchan = devfreq_monitor_stop`，
进程进 **D 状态**，`kill -9` 无效；
此后该节点的**所有** governor 读写与 `trans_stat` 读取全部阻塞在 D 状态。
**只有重启能恢复。** 同顺序先跑过一次没挂 → **是竞态，不是必现**。
但**一次就够把板子锁死**。

> **对「agent 能触发的动作」这是不可接受的**：
> agent 写错一个值 → 板子失去 devfreq 控制 → 只能靠物理重启。
> **在找到并修掉这个内核侧死锁之前，`npu.governor.set` 绝对不能进板型包。**

**被实测证伪的原理由**：`docs/14` 说「那个节点是 rkdevfreq **全局**的，
写它会影响 dmc/vop2/venc」。**实测 E3：不对**——
写 NPU 节点期间 `dmc/governor` **始终是 `dmc_ondemand`**（两次独立观测）。
**当前值是每节点独立的**；全局的是**可选值列表**（E1：两个节点的
`available_governors` 完全相同），不是当前值。**两件事被混成了一个。**

**边界**（免得误伤）：这条风险覆盖 **devfreq 类节点**
（`fdab0000.npu`、`dmc`、`fb000000.gpu`…）。
**现有的 `cpu.governor.set` 走的是 cpufreq 的 `scaling_governor`**（不同驱动），
**实测干净**（E6：写 `ondemand` → `schedutil`，rc=0、无挂死、读回一致）→ 保留。

### `debugfs.mount` —— 四个理由

1. **这块板默认已经挂着**（E7：`/proc/mounts` 有 debugfs 行，`rknpu/load` 读得出 0%）
   → 动作在这块板上是**空转**。
2. **引导路径本来就通**：契约 §2.1 已经把「debugfs 没挂」建模成 `unavailable`，
   并在 `detail` 里给了修复提示。**契约早就假设它可能没挂。**
3. **挂载是系统级改动**，不是「这块板的能力」；真要做也该是**人类在板子上做**。
4. 真要加就得动**危险地板表** = 改契约 = 升 `apiVersion`——为一块不需要的板子不值。

**事后草图（账要留，事不做）**：若将来真要加，回读走 **`/proc/mounts` 的 debugfs 行**
（挂载成功后该行必在），**不是**「挂上之后才有值」的 `npu.usage`——后者是**自指**。
这条路线是通的，只是今天不值得做。记入 `docs/06` C4。

### 顺带定下的两件事

| 项 | 结论 | 依据 |
|---|---|---|
| **O15**（`npu.governor` 的枚举值） | **收敛为 `rknpu_ondemand` 一个值** | E1：列表是 rkdevfreq 类级全局并集；E2：节点**接受列表里的任意值**（rc=0、无报错、读回原值）→ **列表给不出正确的枚举**。要加别的档，得先有「这个节点真正实现了哪些 governor」的依据——**现在没有** |
| **C1**（NPU 当前频率取哪条路径） | **选 `/sys/class/devfreq/fdab0000.npu/cur_freq`** | 实测存在、读出 `1000000000`、与 `rknpu/freq` 一致；**依赖更少**（sysfs 下 always available，不依赖 debugfs）；且是**纯只读观测，不碰 governor 写路径**——**没有 E4 那种死锁风险** |

**影响**：板型包里只有**两个 reversible**（背光、调频策略）+ **一个 destructive**（重启）。
`destructive` 的样本只有一个——**够**：规则 15 的校验逻辑用 fixture 里的**合成包**测
（`fixtures/validator/illegal-floor-downgrade.yaml` 已是这个模式）。
**真实包保真，合成包保规则覆盖。**

## ADR-D27 · 地板的匹配规范、错误码表的合并、视觉体系（用户 2026-11-13 拍板）

> 这一条把**五条**待拍板的收在一起：它们都是「**实现比契约严**」或
> 「**两套词汇并存**」，性质一样，所以一起拍。
> 委托口径：用户 2026-11-13 明确「拍板点这几个，就按你觉得合适的来」。

**契约改动的口径**：本次改的是 `spec/01` 的一个 reason 码、`spec/02` 的
kind 表与地板表的**措辞**、`spec/03` 的一个错字、`docs/00` 的技术栈一行。
**`devboard/v1` 尚未随任何实现发布** → 走「**v1 定稿前的修正**」口径：
**不升 `apiVersion`**，但**一次成文、一次评审**（与 ADR-D24/25/26 同一条）。
地板表的版本仍是 **1**——它从未发布过，**v1 的表就是我们写的那张表**，
不存在「改了已发布的表要迁移」这回事。

### 一、地板的匹配规范（C13 / C11）

**背景**：探针在真机上跑通之后暴露了一个洞——**地板在真实写法上是空的**：

| 真实写法 | 只按「词元相等」匹配的结果 |
|---|---|
| `/sbin/reboot` | **不命中**（词元是 `/sbin/reboot`，不是 `reboot`） |
| `rm -rf /*` | **不命中**（路径规范化后是 `/*`，不是 `/`） |

而契约 §5.2 说得很清楚：「**某些操作永远是 destructive，不管包怎么声明**」，
§5.2 的表里那行也写着「`rm -rf /` **及其等价形式**」。
**只按字面实现 = 契约自己承诺的那条防线在最常见的写法上是空的。**

**决策**：

1. **词元的 basename 也算**（§5.2.1 新增一条）：
   `/sbin/reboot` 的 basename 是 `reboot` → 命中。
   理由：**真实的调用几乎都带绝对路径**。
2. **`rm -rf /*` 与 `rm -rf /` 等价**（表里那句「及其等价形式」说的就是它）。
3. **`mkfs` → `mkfs*`**：`mkfs.ext4` 与 `mkfs` 是**同一个操作**，
   而**地板是下限不是上限**。
4. **`flash` → `flash*`**：契约的**匹配规范**里本来就写着
   「如 `flash*` 命中 `flash_uboot`」——**匹配规范比表格优先**（表格是清单，规范是规则）。
5. **`erase` / `burn` 退回精确匹配**：契约**没有**给它们前缀例句，
   而 `erase_cache` / `burn_count` 是**无害**的常见名——
   前缀匹配在这里制造的是**假阳性**（把无害动作逼成 destructive），不是堵洞。
   **按契约的沉默不擅自加码**；将来有实测依据再议。

**理由与代价**：前四条让地板在真实写法上不再有洞（**安全侧**）；
第五条把假阳性收回来（**可用侧**）。
**代价**：`erase_all` / `burn_flash` 这类写法**仍然不命中**——
这是**已知且刻意**的缺口（记在 `docs/06` C11），要用它得**加一条规则**，
不能靠偷偷放宽前缀。

### 二、错误码表：`not_in_pack` 合并进 `not_found`（O14）

**背景**：读侧与写侧各有一套 reason 码，两边**都有**「你问的那个东西不存在」，
却叫**两个名字**：读侧 `not_in_pack`、写侧 `not_found`。
AI 写卡片时两个都要认，还要知道哪个用哪个——**两套要互相翻译的方言**。

**决策**：**合并成一个 `not_found`**，语义 =
「**你问的那个东西不存在**」（动作 id 不存在 / 这个 tag 不在板型包里 / 权限里没有）。
具体性由 `detail` 承担（契约 §2.1.1 的原话：「码表保持最小，
具体性由 detail 承担」）。

**理由**：契约**自己的**原则就是「码表保持最小」——
`not_in_pack` 与 `not_found` 是**一个意思的两个码**，违反的正是这条原则。
而且**不合并就要翻译**：卡片拿到 `status: 'unavailable', reason: 'not_in_pack'`
时，AI 没法直接判断「是我要错了」还是「板子没有」。

**代价**：丢掉了「不在包里」这层区分——但它**本来就该在 `detail` 里**
（`detail: '板型包 rk3588-atk 不提供这个 tag'`）。

### 三、视觉体系：主体 UI **不引 Ant Design**（O1）

**背景**：愿景 §五的技术栈里写着 Ant Design，而 ADR-D10 把它标成待拍板。
实施到 M4.5 才发现一个**既成事实**：**token 层已经存在**
（`src/renderer/theme/tokens.css`，30+ 个 token），读数面板就是用它写的。

**决策**：**主体 UI 不引 antd**，用**自有的 token 层**自写组件。
理由三条：

1. **卡片即网页，而卡片不受控**——卡片是 agent 写的任意 HTML。
   套一层 antd 的 chrome 只会让**两套视觉语言**并存（壳一套、卡片一套）。
2. 主体 UI 是**壳**（工具栏 / 标签页 / 终端 / 读数面板 / 文件树 / 卡片容器），
   antd 里真正用得上的是**文件树**与**动作确认弹窗**两个——
   代价是一整套 CSS-in-JS 与**第二套主题机制**。
3. **token 层本来就是换皮的接口**：将来想换视觉，改 token 就行，
   不必先拆掉 antd。

**`react-grid-layout` 仍要引**（M5 的硬需求：拖拽布局）。
**ECharts 是给卡片用的**：卡片的网络被 CSP 禁了，
所以图表库要**由宿主提供给卡片**（`cockpit://` 协议）——属于 M5 的范围。

**愿景同步**：`docs/00` §五 已回写（愿景的规矩：「冲突要先改本文」）。

**代价**：组件样式要自己写。**但这个产品本来就要自己写**——
卡片不受控，主体 UI 的组件也很少。

## ADR-D28 · 卡片沙箱与桥接机制（用户 2026-11-14 拍板）

> 这一条把 M5 的**三个技术空白**一次定死：卡片跑在什么源里、
> `cockpit.*` 怎么进到卡片里、卡片怎么知道宿主支持什么。
> 三者都是**实测出来的**，不是推理出来的。

**契约改动的口径**：本次改的是 `spec/03` 的 §六（两句 + 一份别名清单）与 §7.7（一行 + 一句），
`spec/02` 的 §5.5（**一个码**）。**`devboard/v1` 尚未随任何实现发布** →
走「**v1 定稿前的修正**」口径：**不升 `apiVersion`**，但**一次成文、一次评审**
（与 ADR-D24/25/26/27 同一条）。

### 一、卡片跑在**不透明源**里（沙箱**不给** `allow-same-origin`）

**背景**：契约 §六 写「独立 iframe，`sandbox="allow-scripts"`（**不给** `allow-same-origin`）」，
但**没有写它带来什么**——于是「卡片之间能不能互相看见」这件事在实现层是悬空的。

**实测**（Electron 34 尖兵，`docs/superpowers/spikes/2026-11-13-卡片沙箱与桥接实测.md`）：

| 变体 | `localStorage` | 卡片之间 |
|---|---|---|
| A `sandbox="allow-scripts"` | **抛 SecurityError** | **每个 iframe 一个独立的不透明源 → 互不可见** ✅ |
| B `sandbox="allow-scripts allow-same-origin"` | 可用 | **所有卡共享 `cockpit://card` 一个源 → A 卡能读 B 卡的存储** ✗ |

**决策**：**维持变体 A**（契约原文不改）。

**理由**：契约 §6.2 承诺「每卡一个命名空间、**互不可见**」——
**只有变体 A 能兑现**（B 下所有卡共享一个源，`localStorage` 直接互相可读）。
而变体 A 顺带把 §6.2 的前提也兑现了：卡片**连 `localStorage` 都碰不到**，
所以「存储必须经 `cockpit.storage.*`」不是将就，是**必然**。

**顺带作废了一个过度设计**：上一轮评审建议「每卡一个 nonce」——
**不需要**。见下一节。

**代价**：卡片**不能自己指定 `targetOrigin`**（不透明源下 `event.origin` 是 `null`），
宿主→卡片只能用 `'*'`；卡片→宿主也一样。**这靠「认人」而不是「验源」来补**（下一节）。

**影响**：契约 `spec/03` §六 补一句「**因此卡片之间互不可见**」；
实现层 `src/main/cards/protocol.ts` 的沙箱属性写死为 `allow-scripts`。

### 二、桥接走**宿主注入的 bridge + MessageChannel**（**不需要 nonce**）

**背景**：契约 §六 说卡片的能力只有 `cockpit.*` 白名单，但**从没说这些方法怎么到卡片手里**。
而**实测**：**Electron 的 preload 不进子 iframe**（主帧有 `window.cockpit`，卡里是 `undefined`）——
所以 `contextBridge` 这条路**不存在**，必须有**显式的注入机制**。

**实测**（同一份尖兵）：

| 探针 | 结果 |
|---|---|
| `MessagePort` 转进不透明源 iframe | ✅ **可用** |
| `event.source` 认人 | ✅ **准确**（不透明源下 `event.origin` 是 `null`，**只能靠 source**） |
| 卡片拿得到别的卡的 window 引用吗 | **拿不到** → **冒充不了** |

**决策**：

1. 协议 handler 在响应卡片入口 HTML 时**注入一个 bridge 脚本**（`cockpit://card/__host/bridge.js`），
   它在卡片里定义 `window.cockpit.*`，底下走一条**私有的 MessagePort**。
2. 握手：卡片发 `cockpit-hello` → 宿主**按 `event.source` 认人** →
   宿主建 `MessageChannel`，把一端转交卡片 → 之后所有请求-响应走那条私有端口。
3. **不需要 nonce**：卡片拿不到别的卡的 window 引用 → **冒充不了**（实测）。

**为什么「认人」比「验源」更稳**：不透明源下 `event.origin` 恒为 `null`——
**任何基于 origin 的校验在这里都是空的**（上一轮评审正是栽在这：它以为可以按 origin 校验，
于是提了「每卡一个 nonce」）。**能用的只有 `event.source`**，而它指向的是**具体的 window**。

**但认人要认两次**：`event.source` 只告诉你「是哪个 window」，
不告诉你「这个 window 现在装的是哪张卡」——**卡片可以把自己导航到别的卡的 URL**。
所以 **bridge 脚本里带着它所属的实例 id**，握手时一并回传，宿主**比对**：
对不上就**丢弃**（连会话都不开）。
**三道防线**：协议只放行已登记的实例 + bridge 带着实例 id + 宿主比对。

**影响**：契约 `spec/03` §六 补一句「**preload 进不了 iframe，API 必须经宿主注入的 bridge 提供**」；
实现层新增 `src/main/cards/bridge-script.ts`（从 API 注册表生成）与 `src/renderer/cards/broker.ts`。

### 三、卡片 API 加 `capabilities()`（卡片要能发现宿主支持什么）

**背景**：契约 §7.7 的方法表是**封闭全集**，卡片**无法问**「宿主支持哪些方法 / 当前连的是谁」。
而**卡片是 AI 写的**——它写卡时只能硬编码假设「`cockpit.tags.get` 一定在」。
宿主版本一换，卡片只能靠 try/catch 猜，**而卡片跑在沙箱里，猜错了没有任何提示**。

**决策**：

1. §7.7 新增 **`cockpit.capabilities()`**（只读、无权限面、无危险面）：
   `{ apiVersion, methods, connection: { label, transport }, tags }`。
   `methods` 列的是**本 build 实际有的方法**（不是契约全集）——
   否则它对「我能不能调这个」毫无指导意义。
2. §7.7 加一句失败语义：**本宿主没有实现的方法** → `{ ok: false, reason: 'unknown_method' }`。
   （`unknown_method` **不进** `spec/01` §2.1.1 的 tag reason 表——那张表是**读数**的原因码。）
3. **`spec/03` §六 追加「卡片可依赖的 CSS 变量」清单**（15 个 `--cockpit-*`）。

**第 3 条为什么要进契约**：契约 §六 要求「卡片不得硬编码颜色，只用宿主注入的 CSS 变量」——
但**宿主到底注入哪些变量，契约里一个字都没有**（实测：`spec/03` 搜不到 `CSS` / `变量` / `--cockpit`）。
**卡片需要一份「可以依赖什么」的清单**，否则换个宿主版本就得靠猜——
而卡片是 AI 写的，**它不会猜，它会硬编码**。
**只冻结名字与含义，不冻结色值**——色值是皮肤的事（`docs/UI设计/01` §7.3 给了实测值）。

**影响**：契约 `spec/03` §7.7 加一行 + §六 加一节别名清单；
实现层 `src/main/cards/api-registry.ts` 登记该方法。

### 顺带定下的一件事（`spec/02` §5.5 的码）

`spec/02` §5.5 说「参数超出 `guard` → 报 `needs_approval`」，
而 `spec/04` §2.4 说「→ `needs_confirmation`（另带 `guard_exceeded: true`）」——
**同一个意思两个码**，违反 ADR-D27 的「码表保持最小，不给 AI 两套方言」。
→ **统一为 `needs_confirmation`**（`spec/04` §2.4 是动作执行的原因码表，以它为准）。

## ADR-D29 · 整支评审的修复：接线层里那些「静默失效」的地方（2026-11-14）

> 计划 4（M5）的整支评审查出了 4 条 Critical + 6 条 Important。
> 它们有一个共同点：**症状是「什么都不显示」，而且不报任何错**——
> 没有一行日志、没有一次抛错。测试全绿、类型检查全绿、构建全过，
> 而产品**在真机上是不能用的**。

### 一、四条 Critical 的根因

| # | 现象 | 根因 |
|---|---|---|
| **C1** | 单元套件在 HEAD 上是**红的** | 变异测试跑到一半被 **SIGKILL**（`finally` 与信号钩子都拦不住）→ 三个「变异体」留在工作树 → 提交时 `git add -A` 一起带进去了。其中两个是**上一轮评审修好的 Critical**（串口端口不开、危险地板不命中） |
| **C2** | 生产环境**一张卡片都装不上**（卡片区一片空白） | 外壳的 CSP 写的是 `frame-src 'none'`——**照抄了卡片的 CSP**。外壳是唯一装 iframe 的地方，`frame-src` 管的就是「这个文档能装哪些 frame」 |
| **C3** | `window.cockpit` **恒 undefined** | 注入的 bridge 标签写的是 `/__host/bridge.js`（**相对根路径**）→ 在 `cockpit://card/<实例 id>/index.html` 下解析成 `cockpit://card/__host/bridge.js` → **实例 id 被吃掉** → 处理器把 `__host` 当实例 id → 404 |
| **C4** | CSP 违规**一条都抓不到**（agent 永远看不到「这张卡试图联网」） | Electron 34 的 `WebContents.console-message` 是**旧签名** `(event, level, message, line, sourceId)`；代码按 `(event, messageDetails)` 读 → `args[1]` 是**一个数字** → `source` 恒 `undefined` → 每条违规都在第一道门被丢掉。**`MessageDetails` 那个形只属于 `ServiceWorkers`** |
| **C6** | 契约写的那几个**顶层方法根本调不通**（`cockpit.capabilities()` / `cockpit.log(level, message)` / `cockpit.degradation()` / `cockpit.notify(...)`） | bridge 把**没有点号的顶层方法**放进了「同名命名空间」里 → 实际形状是 `cockpit.capabilities.capabilities()` → 卡片按契约写就 `TypeError: cockpit.capabilities is not a function` |

**C2/C3 的病根在设计层**：`docs/21` §4.7 给外壳开的那份 CSP 本身就是错的，
计划照抄，实现照抄——**所以必须连设计层一起改**，否则下一轮还会照抄。

### 二、修 C3 时发现的第五条（评审也没抓到）

| # | 现象 | 根因 |
|---|---|---|
| **C5** | `await cockpit.capabilities()` 拿不到能力表（`caps.methods` 是 undefined） | bridge 把**整个传输信封**（`{ id, ok, value }`）交给卡片，而契约 `spec/03` §7.7 写的是「`const caps = await cockpit.capabilities()` → 能力表本身」 |

→ **bridge 必须解包**：成功给 `value`，失败给 `{ ok:false, reason }`。
这条顺带把契约 §7.7 的「所有方法都不抛异常：失败时返回 `{ ok: false, reason }`」**兑现了**
（方法级的失败现在会提到传输信封上，卡片不用自己去翻 `value`）。

### 三、决策

| 项 | 决策 |
|---|---|
| **外壳的 CSP** | 单独成文件 `src/main/shell-csp.ts`（`main/index.ts` 引入 Electron，**单测进不去**，而这条错了不报错、只是什么都不显示）。`frame-src cockpit:`——卡片在 `cockpit://card`、外壳在 `cockpit://app`，**两个不同的源**（host 不同）→ `'self'` 盖不住；CSP 的 host-source 语法只认 http/https/ws/wss/ftp → 只能用 **scheme 源** |
| **bridge 的注入 URL** | **带实例 id 的绝对 URL**（`cockpit://card/<实例 id>/__host/bridge.js`）。代价：每个实例的标签不一样——这正是要的（**bridge 脚本里带着自己的实例 id**，RF-1 的凭据） |
| **CSP 违规的捕获** | **不再靠 `console-message`**（实测抓不全，见 §七）→ 改用**卡片文档里的 `securitypolicyviolation` 事件**：宿主注入**经典脚本** `__host/csp.js`（**不是** module——要赶在卡片自己的脚本之前装上监听）→ 卡片 `parent.postMessage` → 页面侧经纪人**认人两次**后转 main → 进那张卡的运行时日志 |
| **bridge 的顶层方法** | 顶层方法**自己就是一个函数**（`cockpit.log(level, message)`）；顶层也包一层 Proxy，不认识的名字回 `unknown_method`（不是 TypeError）；`then` / `catch` / `finally` **不能**是函数（thenable 会让 `await` 永远挂着） |
| **符号链接** | `resolveInsideCard` 在词法判据之外**对真实路径再判一次**（`realpath`）——软链是最常见的绕过，契约 §六 白纸黑字「卡片不可读写宿主机文件系统」 |
| **规则 2（id 全局唯一）** | 比的是 **manifest 的 id**，而且**排除自己**。原来比的是**目录名** → 卡片**改一次文件**（热更新必然触发一次 refresh）就在第二次 refresh 里把自己判成「重名」→ 卡片无缘无故变成 degraded |
| **订阅的退订** | 会话**存下** `deps.subscribe` 返回的退订函数，关会话时**真的调用**；外加**每实例 64 个订阅的上限**（超了回 `too_many_subscriptions`）。契约 §六：「单卡崩溃不影响其他卡，也不影响工作台」——「影响」在这里就是「把 main 打满」 |
| **存储目录** | 挪到**兄弟目录** `card-storage/`。原来它在卡片根目录里，而卡片根目录被 `fs.watch` 盯着 → 写一次 `storage.json` 就触发一次 `refresh` + `cardsChanged` → **回路** |
| **变异脚本** | 加**还原日志**（journal）：改坏文件**之前**把原文写进 `.mutation-restore.json`，下次运行先还原；**工作树脏就拒绝跑**；跑完**断言工作树还是干净的**。SIGKILL 拦不住信号钩子，但**下次跑能自己修回来** |

### 四、没有改契约

本次**没有动 `docs/spec/` 任何一处**：
- 没加新方法（`cockpit.tags.unsubscribe` **不加**——契约 §7.7 的 API 表是「唯一的 API 定义处」，
  加一个方法要走「v1 定稿前的修正」口径（一次成文 + 一次评审 + 记录 ADR）；
  而 §7.7 的下一轮修订本来就在 M6（`actions.invoke` 落位时）→ **留到那一轮一起改**）。
- 只加了**一个原因码**（`too_many_subscriptions`）与**一条上限**——契约 §7.7 说
  「所有方法都不抛异常：失败时返回 `{ ok: false, reason }`」，
  而方法级的原因码词汇表**本来就是开的**（`unknown_method` 也明确「不进 tag 的 reason 表」）。

### 五、代价

| 代价 | 说明 |
|---|---|
| **卡片不能自己退订** | 宿主侧（关会话 + 上限）把洞堵住了，但卡片想「不再听某个 tag」时**只能等会话结束**。M6 改 §7.7 时补 `tags.unsubscribe` |
| **断线重连卡片会重载一次** | 实例 = (卡, 连接)（契约 §7.8 明写「一张卡可以在多个连接上各有一个实例」）→ 连接变了就是新实例 → iframe 重建。**会话泄漏已经堵上了**（旧会话在实例换掉时就被关掉） |
| **软链被拒** | 卡片目录里指向外部的软链一律 404/403。指向**目录内**的软链仍允许（同一份代码的别名不算越界） |

### 六、判据（每一条都有测试守着）

| 判据 | 在哪 |
|---|---|
| 外壳的 CSP 允许 `cockpit:` 源 | `tests/unit/shell-csp.test.ts` |
| 注入出来的 URL **真的能被处理器路由到**（按浏览器的规则解析） | `tests/unit/cards/protocol.test.ts` |

### 七、真机实测（2026-11-14 · Linux Electron 34.5.8）

单测只能证明「逻辑对」。这次把**修好的代码**重新构建，**在沙箱里用 Linux 版 Electron 真的跑起来**，
装一张卡，用 CDP 驱动，逐条打日志——**测量**而不是推理。

| 测什么 | 结果 |
|---|---|
| 外壳 CSP 放不放行卡片（**C2**） | ✅ iframe 正常加载（`cockpit://card/<uuid>/index.html`）；修之前是 `ERR_BLOCKED_BY_CSP` |
| bridge 装没装上（**C3**） | ✅ 卡片里 `typeof window.cockpit === 'object'`，卡片自己的文字变成 `cockpit-ok` |
| CSP 违规抓不抓得到（**C4**） | ✅ `connect-src` / `img-src` / `script-src` **三类全部落进那张卡的运行时日志**（`captured=e2e-card`），消息是中文的 |
| 顶层方法调不调得通（**C6**） | ✅ `capabilities()` 拿到能力表；`log()` 回 `{ok:true}`；不认识的名字回 `unknown_method` |

1. **`console-message` 这条路是走不通的**（不是「签名读错了」，是**根本没有归属信息**）：
   Electron 34.5.8 的 `sourceId` **对 `connect-src` / `script-src` 违规是空串**，
   对 `img-src` 才有值 —— 而「试图联网」正是 `connect-src`。
   → 换成 DOM 的 `securitypolicyviolation` 事件（**实测三类违规全中**）。
2. **顶层方法的形状是错的**（评审没抓到，单测也没抓到）——
   真机一调 `cockpit.capabilities()` 就报 `TypeError`。

> **教训**：**「测试全绿」和「产品能用」之间隔着一次真机运行。**

## ADR-D30 · 假设备：一块**只吐原始文本**的假板子（2026-11-14）

> 用户诉求（2026-11-14）：「UI 这方面，如果为了方便显示调试，考虑可以先做一个假设备来调试？」
> —— 背景是外壳正在重写（DSH 接手），**没有板子就没法调界面**：
> 板子不插电、adb 没起、串口被占的时候，外壳只能对着空气调。

### 一、它放在哪一层（决定性的一条）

**假设备在 HAL 边界上，不在 TagStore 上游。**

它实现的是 `Connection`（`src/main/hal/fake/connection.ts`），
所以**真包 + 真 kind + 真 store + 真采样器**全都在跑，
只有「跟板子说话」那一层被换掉了。

**为什么不直接喂 TagStore**：五态（`pending` / `stale` / `unavailable` / `error` / `ok`）
是**契约**（`docs/spec/01` §2.1）。假设备自己造这些状态 =
**把契约抄了第二份**，迟早与真实现漂移，而漂移的正是最要紧的那部分。

| 假设备**吐**的 | 假设备**不碰**的 |
|---|---|
| `/proc/stat` 的 jiffies 计数 | 百分比（由 `proc_stat` 这个 kind 算） |
| `/proc/meminfo` 的 kB | 字节与占用率（由 `meminfo` kind 算） |
| devfreq 的 `<占空比>@<频率>Hz` | 频率与占空比（由 `devfreq_load` kind 算） |
| thermal 的毫度 | 摄氏度与归并（由 `thermal_zone` kind 算） |
| **「文件不存在」这件事本身** | `unavailable` 这个状态（由 kind 判「读出来是空的」） |

→ 契约里的行为（首读 pending、计数器倒退报 parse_error、读不到报 unavailable）
**是被真代码判出来的**，不是假设备假装出来的。

### 二、它怎么「执行」命令

`src/main/hal/fake/exec.ts` 是**一个极小的 shell**：`;` 分语句、引号包参数、
`$( )` 做命令替换、`for … do … done` 展开 glob。

**为什么不按 marker 切字符串**（这是踩过的坑）：
`proc_stat` 的取数片段里**自己带一个 echo**（分隔行 `--- cpuinfo ---`）。
按 marker 切的时候，**切到哪一步全靠运气**——分隔行被当成 marker 时，
kind 报的是 `parse_error`，而**原因在假设备里，看板子里看不出来**：
那是**假的板子教错了真的代码**。
→ 这条已写成回归测试（`tests/unit/fake-device.test.ts`）。

**认不出来的命令一律不输出**——假设备宁可说「我不知道」，也不要编一个数出来。

### 三、开关与产物（**合成数据不许进生产包**）

| 项 | 做法 |
|---|---|
| 开关 | 环境变量 `COCKPIT_FAKE=1`（假设备排第一）/ `=only`（只有假设备）/ 不给 = 关 |
| profile | **内存里造的，不落盘**（`profiles/targets/` 保持干净） |
| 假 profile 的 `board_pack` | 必须指 `rk3588-atk`——候选挑选只留带 `board_pack` 的 profile，不指就选不上 |
| 进包方式 | **动态 import** + 编译期常量 `__COCKPIT_FAKE_BUILD__`：生产构建把它编成 `false` → 那一段是死代码 → **那个 chunk 根本不产出** |
| 自检 | `scripts/check-build.ts` 扫 `out/main/**`，**标记串出现就判红**（已实测两个方向：假设备开着 → 变红并点名那个 chunk；正常构建 → 绿） |

**标记串 `cockpit-fake-device/1` 住在假设备自己的模块里**，
而且**被假终端的横幅引用**——两件事一起做：

1. 终端上**明说这是合成数据**（不然有人会把假数当真数看）；
2. 标记串因此**留在产物里**，构建自检才验得到它。
   （导出但没人用的常量会被 rollup 摇掉——**检查就成了摆设**，
   这条坑跟 M40 那次「变异守卫失效」是同一类。）

### 四、故障注入（**五态必须可达**）

| 注入 | 默认节奏 | 打出什么状态 |
|---|---|---|
| 往返超时 | 每 7 轮 | `stale`（保留上一个值）/ `error`（从没成功过 → 值是 null） |
| meminfo 截断（少了 `MemAvailable`） | 每 17 轮 | `error` + `parse_error`（**不许拿 0 顶上**——那会让占用率变成 100%） |
| NPU 的 debugfs 路径不存在 | 一直 | `unavailable`（真板上的 debugfs 挂载**也不是持久的**） |

**为什么必须能看见 unavailable 与 error**：一个从不显示「不可用」的界面，
说明**那个状态没被设计过**——等板子真掉线时，界面会第一次见到它。

### 五、判据（每一条都有测试守着）

| 判据 | 在哪 |
|---|---|
| 首读 `cpu.usage` 是 **pending**（不是 0） | `tests/unit/fake-device.test.ts` |
| 第二次采样是 **ok**，且是 0..100 的真数 | 同上 |
| NPU 读不到 → **unavailable**，值是 null | 同上 |
| 超时 → **stale** 且**保留上一个值** | 同上 |
| meminfo 坏掉 → **error** | 同上 |
| 取数片段里的 echo 也要输出（分隔行不能被吃掉） | 同上（回归测试） |
| 认不出来的命令 → **什么都不给** | 同上 |
| 变异守卫 **M64–M69** 守着上面这七条 | `scripts/mutation-check.mjs` |
| 生产产物里**没有**假设备 | `scripts/check-build.ts`（随 `npm run build` 跑） |

### 六、真机实测（2026-11-14 · Linux Electron 34.5.8 · 沙箱）

**在真的应用里跑一遍**（不是单测）：把假设备编进产物，
用 Linux Electron + Xvfb 起应用，**从渲染进程读宿主的读数**。

| 测什么 | 结果 |
|---|---|
| 运行时**认了假 profile** | ✅ `tagsStatus` = `{state: 'running', profileId: 'fake-board'}` |
| 读数**在动** | ✅ `cpu.usage` 26.5% → 54%；`gpu.usage` 21 → 11；三个温度各自在动 |
| **五态都出现过** | ✅ `ok` / `stale`（第 7 轮注入的超时，**旧值保留**）/ `unavailable`（NPU） |
| 核名与簇 | ✅ `cpu.core.0..3` = A55、`cpu.core.4..7` = A76 |

**实测抓出一条单测抓不出来的 bug**：

> 假设备的 `MemAvailable` 写成了 **「4 MiB ± 1.5 MiB」**（本意是 GiB），
> 而总量是 8 GiB → **占用率 99.93%**——
> **面板说满载，板子其实闲着**：那正是契约 N2 说的「最坏的那种假数」。
>
> 单测没抓住，是因为**没人断言那个数的量级**；
> 真机跑起来、盯着读数看，才看见「内存 99.9%」不对劲。
> → 已修（GiB），并补了一条断言量级的测试（**先红后绿**）。

> **又一次印证同一条教训**：**「测试全绿」和「产品能用」之间隔着一次真机运行。**
> 这次的收获是双向的：假设备**有用**（没有板子也能调），而且**它自己也需要被真机看**。

### 七、独立评审的发现与处置（2026-11-14 晚间）

三路独立评审（各自不同侧重）在这轮改动里查出的东西，**处置如下**：

| # | 评审发现 | 严重度 | 处置 |
|---|---|---|---|
| **F1** | **假设备没载入成功时，profile 还在列表里，但连接回落成了真本机连接**（Windows 上就是开发者自己的 cmd.exe）——列表写着「假板子 · 合成数据」，打开却是自己的机器 | **Critical** | ✅ 规则抽成纯函数（`hal/fake/wiring.ts`）：没载入成功就**不列它**，而且路由是 `refuse`（明确拒绝）而不是 `not-fake`（后者会掉进正常传输里） |
| **F2** | **横幅在构造期 emit，那时还没有监听者** → 那一刻发等于没发 → 终端上**从来没出现过「这是合成数据」** | Important | ✅ 改到第一个监听者来了之后再发 |
| **F3** | **profile 声明 `pty: true`** → 宿主只转发裸键，`uname` 永远匹配不上，也没有提示符与回显 | Important | ✅ 改成 pipe 模式；`capabilities()` 由 profile 推导（能力位只有一份实现） |
| **F4** | **故障注入按「这条连接上的第几次 exec」计数** → 三个轮询组共用一条连接，慢组（唯一读 meminfo 的）只占 1/3 → 「error 那一态几乎看不见」，而超时多半落在快组 → CPU/GPU 几乎一直 stale | Important | ✅ 按命令里的路径**分别计数**：超时算快组，meminfo 的坏只算真的读 meminfo 的那一轮 |
| **F5** | 假设备**报告文件传输成功但不真传** | Minor | ✅ 明确报错（「假设备不传文件」）——报告成功却不传 = 骗人 |
| **F6** | `/proc/stat` 与 `/proc/meminfo` **缺尾换行** → 分隔行会粘在最后一行上 | Minor | ✅ 补上（真文件有） |
| **F7** | 汇总 `cpu` 行**不是各核之和** → 卡片上「总占用率」与八个核的数互相矛盾 | Minor | ✅ 改成各核之和（真板上的 `/proc/stat` 就是这样） |
| **F8** | **构建自检的「不变量」只有一行代码守着**（标记串被谁引用）——那条横幅被删掉，标记串就会被 rollup 摇掉，检查永远绿 | Important | ✅ 标记串被**假终端的横幅**引用，而横幅有单测（M70 守着）+ 假设备整个不在生产包（两个方向都实测过） |

> **F1 与 F8 是同一类**：**「检查指向的东西」没了，检查还在**。
> 跟 M40 那次「变异守卫失效」同源——
> 所以新增的检查都要问一句「**它指向的东西还在吗**」。

### 八、代价

| 代价 | 说明 |
|---|---|
| 假设备的文件内容**不是真的 shell 输出** | 它只认三种命令形态（`cat` / `echo` / `printf` / `for`）。新的 kind 若用别的取数方式，假设备要跟着加——**这正是要付的代价**：加错了会在假设备这里先炸，而不是在真板上炸 |
| 假设备**不模拟串口/ADB 的故障模式** | 只模拟「超时」与「内容坏掉」。真板的「端口被占」那种故障仍要靠真机（`docs/02` 事实 G1） |
| 合成数据**可能与真板差很远** | 它是**界面设计的脚手架**，不是**真板的行为模型**。真机验收仍然必须做（`docs/06` C12） |

## ADR-D31 · 流程包（workflow pack）的处置：方向保留，**契约不冻结**，先做尖兵（2026-11-15）

## ADR-D32 · M6 控制面的实现层决定（计划 5 收尾，2026-11-15）

> **背景**：计划 5（`docs/superpowers/plans/2026-11-15-plan5-控制面.md`）把
> `spec/02` §4/§5 与 `spec/03` §5 的**已定契约**实现了出来，**一个字没改契约语义**。
> 本文记的是**实现层**的决定：模块落点、哪一步归流程层、哪一步推迟、哪一条是契约级的边界。
> **不升 `apiVersion`**（`devboard/v1` 未发布）。

### 一、四条决定

| # | 决定 | 理由（一句话） | 裁错的代价 |
|---|---|---|---|
| **D32-1** | **「凭据准备」这一步归流程层，不做成板子动作**（计划 5 的 4.1.6 由此改判） | **板型包的回读只能验「目标自己」的状态**：「板子上有这把公钥」能验（`file_equals`），但「**客机现在连得上板子了**」验不了——那是客机侧的事，板子的 action 碰不到 | 硬做成板子动作 → 回读只能退化成「文件非空」这类**弱判据** → 界面说「已就绪」，实际连不上；比没有更坏 |
| **D32-2** | **跨目标的验证词汇由流程层出**（不在板型包这一层解决） | 同上；流程层天生同时看得到两个目标 | 不出这条词汇 → 流程层只能「相信步骤返回了 0」→ **直传的成败不可信**（尖兵 §三·F1 的 20 倍耗时波动正说明传输会失败） |
| **D32-3** | **假设备的多角色（客机）推迟**（计划 5 的 8.1.1 / 8.1.1b 由此改判） | **流程层还没有**（ADR-D31 R1）→ 多角色假设备**现在没有消费者**；卡片侧首版也不能发指令 | 现在就做 → 一块**没人用的**脚手架，还会在流程层的形状定下来时返工 |
| **D32-4** | **执行原语的可中断性**：M6 只做到**「在动作层能说清楚『被取消』」**，**HAL 层的 abort 语义留给流程层** | 尖兵实测：取消只在**步骤边界**生效；真要杀掉在飞的传输，得进 HAL 的四种传输（ssh / adb / 串口 / local）各自实现 abort——而「要不要留 `.b64` 垃圾」都还没定（尖兵 S4） | 现在就做 HAL abort → 四种传输各写一遍，**形状还会再改一次** |

### 二、这一轮测到的一条**契约级边界**（不是实现问题，也不是契约的错）

**`spec/02` §4.4 的回读五形式，全都只在「目标自己」的上下文里成立**：

| 形式 | 它问的是谁的问题 |
|---|---|
| `tag` | **目标自己**的读数 |
| `file_equals` | **目标上**那个文件的内容 |
| `command_ok` / `verify` | **目标上**那条命令的退出码 |
| `none` | 什么都不问 |

→ **「跨目标的事实」（客机连得上板子吗？产物真的到板上了吗？）用板型包的回读验不了。**
这不是契约的错——**板型包本来就是「一个目标的包」**；
错的是**拿一个目标的回读去回答两个目标的问题**。
→ 处置 = D32-1 + D32-2（归流程层）。
→ **但这条要留给将来**：流程层晋升契约时，回读词汇要**分「目标内」与「跨目标」两类**
（进 `docs/06-契约核对.md` 的视野）。

## ADR-D33 · 流程层的实现层决定（计划 6，2026-11-15）

### 一、三条决定

| # | 决定 | 理由（一句话） | 裁错的代价 |
|---|---|---|---|
| **D33-1** | **「目标」这一维先不进契约**（待裁决的 **D7** 因此**不用现在拍**）：流程包把「角色 → profile id」的绑定**写在宿主侧**，卡片侧要选目标是**后续的契约增量** | 流程包首版是**宿主层格式**（ADR-D31 R1）→ 「目标在哪」由**宿主侧的文件**回答 ✓；契约层**一个字不用改** | 现在拍 D7 = 在**没有流程层**的时候先改契约 → 重蹈 `docs/21` §4.8 的覆辙 ✗ |

> **背景**：ADR-D31 R1 说「流程包首版不进 `docs/spec/`，真板跑通**两条**流程后才晋升契约」——
> **前置已满足** ✓（真板跑通两条 ✓，2026-11-15 实测 ✓，报告
> `docs/superpowers/spikes/2026-11-16-流程直传.md` ✓）。
> → 本次**把流程包正式写进契约** ✓。
>
> **过程**：提案 v1（`docs/30`）→ 两路独立评审判「需重做」（`docs/31` / `docs/32` ✓）→
> 提案 v2（`docs/34`）→ 评审判「有条件通过」，两条 Critical（`docs/35` ✓）→
> 提案 v3（`docs/36`）→ 评审判「有条件通过」，一条 Critical（`docs/37` ✓）。
> **每一版的评审意见都在实现层落地了** ✓（不是只改文档 ✓）。

### 一 · 决定

| # | 决定 | 理由 | 裁错的代价 |
|---|---|---|---|
| **D34-1** | **流程包格式进契约**（新增 `docs/spec/05-workflow-pack.md` ✓），版本词汇**统一成 `apiVersion: devboard/v1`** ✓ | ADR-D31 R1 的前置已满足 ✓；且格式**已实现并真机跑通** ✓（契约层只认已实现的东西 ✓） | 契约层再冻一个**没跑过**的格式 → 重蹈 `docs/21` §4.8 的覆辙 ✗ |
| **D34-2** | **「目标」不是契约的概念** | 「本机编译」与「客机编译」是**两个流程包** ✓ → 卡片只看到「流程 id + 输入声明」✓ | 用户那句「用户可以选择本机还是客机」在契约层没有位置 → **用户还要再等一期** ✗（**代价已知** ✓） |

| **D34-4** | **「批准」不是 MCP 工具** | 契约 `spec/04` §2.4.1 的现成先例：`confirm_action` **只是把请求递到 GUI 队列**，「批准」这个动作**在 GUI 那一侧** ✓ → 流程层照它走 ✓ | 把 `approve` 暴露给 agent → **两段式白做** ✓（拿到 `needs_confirmation` 的那一方自己就能重试成功 ✓） |
| **D34-5** | **流程的授权有**两层**：① 流程包**已批准**（宿主侧 ✓）② 这张卡**被授过**这个流程（卡级 ✓）→ **两层都要过** ✓ | 流程**不是动作**（不在板型包里 ✓），但它**一样能在用户机器上执行命令** ✗ → 它**必须**有自己的授权层 ✓（评审 37 的 V3-I9 ✓） | 少一层 = 「一张卡声明了就能跑」✗ |
| **D34-6** | **判据复用 M6 的五形式**，**首版支持形式 2–5**，**形式 1（tag）首版报错** | tag 属于**板型包的核心词表** ✓，流程层没有板型包 → **查不了** ✗ → 与其收下再悄悄丢掉 role，不如**直接报错** ✓ | 收下 tag 再忽略 `role` → 「判据在哪个角色上读」被悄悄改掉 ✗（评审 35 的 V2-I3 ✓） |
| **D34-7** | **跨目标的判据由流程层跑**（执行器在**执行的那条连接**上回读 ✓）→ **两个事实、两行账** ✓ | 「板子上真的有那个文件吗」是**另一台机器**的事实 ✗ → 本来就不该在同一个事务里 ✓（SPEC-D22 ✓） | 塞进执行器 → 要么破坏「执行与回读不可拆分」✓，要么跨目标的判据**没法追责** ✗ |
| **D34-8** | **长任务 = `run_id` + 轮询**；**重试（重新触发）= 从头再跑**；**续跑（人点头后）= 从停住的那一步继续** ✓ | 编译实测 58.9s / 98.5s ✓ → 同步返回不成立 ✓；而重跑 = 编译两遍 ✗ | 两句话指向相反行为 → 下游照着实现就矛盾 ✓（评审 37 的 V3-I2 ✓） |
| **D34-9** | **判据命令进确认通道**（首版**不做** ✓，理由写进契约 ✓） | 判据是**只读验证** ✓；首版的防线是「装包时人看过」✓ + 地板 ✓ | 静默不做 = 契约没说 = 下游以为有 ✗ |

## ADR-D35 · D7 的具体形状：**两个流程包 + 宿主路径选择器**（契约零改动，2026-11-15）

### 一 · 决定

| # | 事 | 决定 | 为什么 |

## ADR-D36 · 取消、在飞的那一步与残留清理（**实现层**，2026-11-15）

> **背景**：契约增量 **v4**（`docs/39` ✓）经独立评审（`docs/40` ✓，判定「⚠️ 有条件通过」✓）

> 独立评审 40 的 C-1 ✓）→ 先修 ✓，再改契约 ✓。

### 一 · 三批实现（**顺序有依赖** ✓）

| 批 | 事 | 依赖 | 状态 |

### 二 · 五条实现层决定

| # | 决定 | 理由 | 裁错的代价 |
|---|---|---|---|
| **D36-1** | **「取消」的状态写在运行级**，而**步骤级**用 `reason: 'cancelled'` ✓ | 「取消不是失败」要在**两层**都说清楚 ✓ —— 界面看运行状态 ✓，追责看步骤理由 ✓ | 只写运行级 → 时间线上那一步显示「回读不符」✓ → **撒谎** ✗（人叫停 ≠ 板子不听话 ✓） |
| **D36-2** | **执行器**在 `execResult.cancelled` 时**直接给 `cancelled`**，**不管回读是什么形式** ✓ | 回读形式是 `none` 时它会报 `ok: true` ✓（「命令执行了、效果也有」✓ —— 但它**被砍到一半**了 ✗） | 只在 `command_ok` 里判 → **`none` 那条路漏掉** ✓ → 取消的步骤报成功 ✗✗ |
| **D36-3** | **取消的入口**：GUI 的「停一下」（**外壳那条轨** ✓） + **宿主命令行按 Ctrl-C 停自己那条运行** ✓；**跨进程取消首版不做** ✓ | 运行记录在**进程内存**里 ✓（O26 已拍「运行记录临时」✓）→ 另一个进程**找不到**那次运行 ✗ → 要落盘就得推翻 O26 ✗（不值 ✓） | 落盘运行登记处 → 多一份要清、要过期、要防篡改的账 ✗（为了一个 CLI 取消 ✓） |
| **D36-4** | **判据用「目的地传输前不存在」**，**不**用「大小 + mtime 变了」 ✓ | 大小+mtime 分不出「这一步改的」与「别人改的」✓；同秒同大小**测不出** ✓；最常见的取消场景（板子正忙 ✓）里**取不到「传输后」那次快照** ✓ | 用大小+mtime → 传输期间**别人**动了那个文件 → **宿主把它删了** ✗✗（删掉的是别人的东西 ✓） |
| **D36-5** | **清理命令是宿主写的** → **不过危险地板** ✓，但**路径按 `02` §4.6 编码** ✓、**只许普通文件** ✓、**与 `to.path` 逐字符相等** ✓ | 地板是给**包给的命令**用的 ✓（表里只有 `rm -rf /` ✓ → `rm -f /opt/x` 根本不命中 ✓）；清理命令是**宿主自己**写的 ✓、路径是**宿主自己**算的 ✓ → 不过地板 ✓，但**必须编码** ✓（`to.path` 是**包给的** ✓） | 不过地板又不编码 → **一条注入面** ✓（包能把 `to.path` 写成 `/opt/x; reboot` ✓） |

## ADR-D37 · 卡片侧触发流程（**实现层**，2026-11-15）

> **背景**：计划 7（`docs/superpowers/plans/2026-11-15-plan7-卡片触发流程.md` ✓）——
> 契约**一个字没改** ✓（`spec/03` §7.7 的三行早就写好了 ✓），
> 这一轮是**把它实现出来** ✓。
> **契约层**：SPEC-D23/24/25（v4 ✓）· **这一轮的实现层**：本文 ✓。

### 一 · 五条实现层决定

| # | 决定 | 理由 | 裁错的代价 |
|---|---|---|---|
| **D37-1** | **流程的授权是独立的一维**（`CardApiPermission` 加 `'workflow'` ✓），**不混进 `permissions.write`** ✓ | 契约 §3.3 ✓ —— 流程**不是动作** ✓（不在板型包里 ✓）但它**一样能在用户机器上执行命令** ✗ → 它**必须**有自己的授权面 ✓；混进 write 就是**两套规则** ✓ | 混进 write → 一张卡声明了 `permissions.write: ['demo.run']` 就**能跑流程** ✗（而流程 id 不是动作 id ✗ → 授权账里那一维对不上 ✗） |

### 三 · 三条**不能含糊**的

| # | 决定 | 为什么 |
|---|---|---|
| 1 | **材质层叫 `--shell-mat-*`，不叫 `--cockpit-mat-*`** | `--cockpit-` 是**契约前缀**（卡片能依赖）✓。材质层是**外壳专有**的 ✓ —— 卡片一旦能自己造材质，「统一皮肤」当场就破 ✓ → **名字上就把边界写着** ✓（比写文档可靠 ✓） |

| 3 | **本轮**不改**任何观感** | 用户明确要求「保证不改动 GUI 设计」✓。→ 材质层是**登记**，不是**重画** ✓ |

### 四 · 「观感零变化」是**核验过**的，不是**声称**的

核验方法：把 `visual.css` 迁移前后的**每一条声明**解析成具体值
（`var()` 全展开、`--shell-mat-*` 展开成材质值），逐条比对：

```
[dark]  removed=1 added=0
   - box-shadow: -24px 0 48px rgba(30, 40, 55, 0.16)   ← 浅色专属规则，折叠进材质层
[light] removed=1 added=0
   - box-shadow: -24px 0 48px rgba(0, 0, 0, 0.42)      ← 暗色规则，被材质层的浅色值取代
```

每套皮肤里唯一「消失」的那条，**都是在该皮肤下本来就不生效的那条** ✓；
取代它的新值与它**逐字相同** ✓ → **两套皮肤的最终计算样式完全一致** ✓。
