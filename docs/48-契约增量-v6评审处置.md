## 二 · **R1 · 评审的 I-7 引出了一条更根本的发现**（**它让整个契约改动都不必要** ✓）

### 2.1 评审问的那句：「`target` 角色为什么不能改绑 `board-ssh`？」

我去查了 —— **发现一条比它更根本的东西** ✓：

```ts
// src/main/workflows/runner.ts · resolveEndpoints
const release = await ctx.deps.targets.runOn(profileId, async (conn) => {
  const result = await conn.exec('uname -r');
  ...
});
```

→ **它无条件去问目标机器的内核版本** ✗。
→ 但**只有 `kernel-module` 的落位需要内核版本** ✓：

```ts
// src/main/workflows/placement.ts
'kernel-module': { dir: '/usr/lib/modules/{kernel_release}/extra/' },  // ← 要版本
'user-program':  { dir: '/usr/local/bin/' },                        // ← **固定** ✓
```

### 2.2 于是「宿主连板子」这件事**根本不需要**

| 步 | 在哪跑 | 要什么 |
|---|---|---|
| `compile` | 客机（`build` 角色 ✓） | 客机的交叉工具链 ✓ |
| `artifacts` | 客机 ✓ | 客机的文件 ✓ |
| `deliver`（scp） | **客机** ✓（`runTransfer`：**命令在源目标上跑** ✓） | 客机自己的私钥 ✓（尖兵装过 ✓） |
| `make-executable`（chmod） | **板子**（`role: target` ✓） | **宿主要连板子** ✗ |
| `run` | **板子** ✓ | **宿主要连板子** ✗ |

→ **最后两步要宿主连板子** ✗ —— 而宿主**没有板子的私钥** ✗（实测 ✓）。

### 2.3 结论：**这一轮不需要动契约**（**前提** ✓）

**若把最后两步也放到客机上跑** ✓（命令写成 `ssh root@板子 '...'` ✓ —— **客机中转** ✓）：

| 步 | 在哪跑 | 宿主要连板子吗 |
|---|---|---|
| `compile` / `artifacts` / `deliver` | 客机 ✓ | **不需要** ✓ |
| `make-executable` / `run` | 客机上经 `ssh` 中转 ✓ | **不需要** ✓ |

→ **宿主全程不需要板子的私钥** ✓ —— 「走客机中转」✓（用户 2026-11-16 拍板 ✓）。

→ **但 `scp` / `ssh` 命令里的板子地址从哪来？** ✓ —— **`{role:target.host}`** ✓
→ 而 target 角色绑的是 `board-adb` → **`options` 里没有 `host`** ✗ → **空串** ✗。

### 2.4 **所以真正的缺口只有一个** ✓ —— 而且**不是「设备」概念** ✓

> **流程包怎么拿到「板子的 SSH 端点」** ✓。

**三个候选** ✓（评审没提这个对比 ✓ —— **这是本轮真正要拍的那一条** ✓）：

| # | 方案 | 契约改动 | 实现改动 | 代价 |
|---|---|---|---|---|
| **甲** | **profile 加 `ssh` 块（顶层）** | `spec/02` §10 加字段表 ✓ | `schema.ts` 封闭表 ✓ + **`factsOf` 改** ✓ | **SSH 事实要复制到每条相关 profile** ✓（漂移风险 ✓ → 用「不一致就报错」挡住 ✓） |
| **乙** | **profile 的 `options` 里带 `ssh`** | **契约顶层一个字不加** ✓ | `TRANSPORT_SPECS` 的 `optional` 表都加 `ssh` ✓ + **`factsOf` 改** ✓ | 「跨传输的事实混进传输参数」✓ —— **但契约里本来就没说 `options` 只放传输自己的参数** ✓ |
| **丙** | **流程包自己写板子的地址** | `spec/05` 加一个输入 ✓ | 几乎零 ✓ | **机器专属的值进包** ✗ —— **违反「机器专属的值走 `inputs`」的规矩** ✗（但 `inputs` **就是**给机器专属的值用的 ✓ —— 所以丙其实是**合规的** ✓） |

**我的倾向：乙** ✓ —— **契约顶层一个字不加** ✓（评审 I-2 的要害 ✓）→
**改动面最小** ✓ → 而且它**顺手解决了 I-3 的双写** ✓（`options.host` 与 `ssh.host` 冲突怎么办？——
**甲才有那个问题** ✓；乙里 `ssh` 就在 `options` 里 ✓，**只有一处** ✓）。

> **但乙有一个问题**：`transport: 'ssh'` 的 `host` 是**必填** ✓ → `board-ssh.json` 的 `options.host` 已经是那块板 ✓
→ **`options.ssh` 就不必加了** ✓ —— **板子的 SSH 端点就是 `board-ssh` 那条 profile 的 `options.host/port/username`** ✓
→ **流程包的 target 角色该绑哪条 profile？** —— 它**一条只能绑一条** ✗
→ 而「chmod/run 要在板子上跑」+「scp 要在客机上跑」→ **两个不同的目标** ✗
→ **所以流程包需要**「target 角色 = 板子（用于 chmod/run 的落位与判据）」**和**「SSH 端点 = 板子的 SSH 地址」**两件事** ✓。

→ **这就是「设备」概念真正该出现的地方** ✓ —— 但**范围比提案小得多** ✓。
