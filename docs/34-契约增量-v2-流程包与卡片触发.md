## 一 · D7 的处置：**目标不进契约，进数据**

> **待裁决的 D7**（「目标」这一维要不要进契约）—— **本文给出一个不需要它也能满足用户需求的答案**。

**用户原话**：「用户可以选择**本机**或者**客机**上的代码」。

**本文的形状**：

```
目标（哪台机器）  ← 由**流程包**声明（role → profile id，宿主侧的文件 ✓）
用户的选择        ← 由**用户选哪个流程**表达 ✓
```

→ **「本机编译」与「客机编译」是两个流程包** ✓ → 卡片**只看到流程**（id + 输入声明 ✓）→
**卡片不知道目标** ✓ → **契约层一个字都不用改「目标」这一维** ✓（ADR-D33 D33-1 ✓）。

**代价（诚实说）**：卡片**不能自己拼**「先在客机编译、再传到板子」这种多步组合
——它只能选一个**已经声明好的流程** ✓。
→ 用户要的新组合 = **写一个新的流程包**（宿主侧的文件 ✓，不是卡片代码 ✓）。

**两份评审都认可这个形状** ✓（`docs/31` §六、`docs/32` §六 ✓）；
它们指出的是**「谁批准」**这条线**没写清** ✓ → 见 §二 ✓。

## 二 · 信任模型（**两份评审的同一条 Critical** —— 这一节是本次增量的**核心**）

> 评审 32 的原话：**「agent 可自写包并触发任意命令」**。
> → 原因很直白：**一个流程包就是「一组要在用户机器上执行的命令」**。

### 2.1 三本账（**各管一件事** ✓）

| 账 | 记什么 | 在哪 | 谁能改 |
|---|---|---|---|
| **注册表** | 目录里有哪些包（id → 包 + **内容摘要**） | `workflows/`（内置 `profiles/workflows/` + 用户 `~/.local/share/DevBoardCockpit/workflows/`） | 放文件进目录 |
| **批准账** | 哪些包**被用户批准过**（id → 摘要 + 时刻） | `workflows-approved.json`（用户数据目录 ✓） | **只有人能改** ✓ |
| **审计** | 每次运行每一步做了什么 | `logs/actions.log`（行式 ✓） | 宿主 |

### 2.2 五条规矩（**契约里必须写死** ✓）

| # | 规矩 | 为什么 |
|---|---|---|
| **T1** | **放一个文件进目录 ≠ 批准它** | 否则「能写文件」=「能执行命令」✗ |
| **T2** | **批准绑内容摘要** | 改了内容 → 摘要变了 → **要重新批准** ✓（不然「批准 A 版、跑 B 版」✗） |
| **T3** | **卡片与 agent 只能按 id 取注册表里的包**，**给不了路径** | → agent 不能自写一个包就跑 ✗（评审 32-C1 ✓） |
| **T4** | **每个写步骤都过 `spec/02` §4.6 的编码 + §5.2.1 的危险地板**；命中地板 → **按 destructive 处理**（要人确认 ✓） | 自由命令是**第二条命令通道** ✗ —— 它必须与动作**同一条防线** ✓（评审 31-I4 / 32-I3 ✓） |
| **T5** | **角色不许绑到 `local` 传输** | `local` 是**宿主自己的 shell** ✓（Windows 上是 cmd.exe ✓）——流程在它上面跑命令 = 在宿主上跑命令 ✗（ADR-D31 R2 ✓） |

### 2.3 「点头」发生在哪（**两条路，落到同一本账** ✓）

| 路 | 谁点头 | 什么时候 |
|---|---|---|
| **装卡** | 装卡的界面（**卡片声明 `requires.workflows`** → 装它时逐条过目 ✓） | 装卡时 ✓ |
| **命令行** | 人自己敲 `npm run workflow:approve -- <id>` ✓ | 随时 ✓ |

→ 两条路都写进**同一本批准账** ✓ → 卡片与 agent 看到的是**同一份授权** ✓。

### 2.4 危险命令的**运行期**确认（与动作同构 ✓）

| # | 规矩 | 为什么 |
|---|---|---|
| 1 | 步骤可以声明 `danger: destructive` → **每次运行都要人确认** ✓ | 「凭据准备」那一步就是它（写目标机器的 `authorized_keys` ✓） |
| 2 | **命中危险地板 → 也按 destructive 处理**（取更严的 ✓） | 包可以写一条命令骗过 `danger` ✓ |
| 3 | **确认凭据绑** `(动作 id（含步骤 id）, 参数摘要 + **这一步的输入摘要**, 包 id, 契约版本)` | 自由命令没有动作参数 → 不绑输入的话，**换一组 inputs 就能复用同一张凭据** ✗（评审 32-C3 ✓） |
| 4 | **回读的 `verify` 命令也要过地板** | 它是**包给的命令** ✓ → 不查就能借「验证」之名跑危险命令 ✗（评审 32-C2 ✓） |
| 5 | **跨目标的判据由流程层跑**（执行器在**执行的那条连接**上回读 → 跨目标是**另一个事务** ✓）→ **两个事实、两行账** ✓ | SPEC-D22：执行与回读不可拆分 ✓（ADR-D33 D33-2 ✓） |

## 三 · `docs/spec/05-workflow-pack.md`（新增）

> **内容**：`docs/29-流程包格式.md` 的**契约版** ✓。
> **不新增**任何宿主层没有的东西 ✓。

### 3.1 顶层字段（封闭）

```yaml
apiVersion: devboard/v1      # ← **与板型包/卡片 manifest 同一套版本词汇** ✓（评审 31-I10 ✓）
kind: Workflow
id: hello-kernel.build-run
name: 编译内核模块 → 直传板子 → 装 → 跑
version: 1.0.0
description: …
inputs: { … }                # 封闭类型表（见 §3.2 ✓）
roles:  { … }                # role → 连接 profile id（**只许引用** ✓）
steps:  [ … ]                # 六种 kind（见 §3.4 ✓）
```

> **评审 31-I10**：v1 用了 `formatVersion`（另一套版本词汇 ✗）→ **统一成 `apiVersion`** ✓
> （契约层不能有两套版本号 ✓ ——「词表只有一个源头」是本工程的硬规矩 ✓）。

### 3.2 `inputs`：**照 `spec/02` §4.3 的类型表**（评审 31-I1）

| type | 额外必填 | 说明 |
|---|---|---|
| `string` | `maxLength` | 不许开口 ✓ |
| `integer` | — | 可选 `min` / `max` ✓ |
| `number` | — | 可选 `min` / `max` ✓ |
| `boolean` | — | |
| `enum` | `values`（封闭取值表 ✓） | 不在 `values` 里 → **报错** ✓ |
| `path` | `maxLength` | **等价于 `string`** ✓ —— 不另造类型 ✓ |

> **v1 的错**：多了一个 `path` 类型、少了一个 `default` → **第二套方言** ✗。
> → **`path` 只是 `string` 的别名** ✓（编码规则一样：单引号包裹 ✓）；
> → **补上 `default`** ✓（`spec/02` §4.3 有 ✓）。

### 3.3 `roles`：角色 → 连接 profile（**只许引用** ✓）

```yaml
roles:
  build:
    purpose: 编译所在（客机）
    profile: ubuntu-ssh        # **宿主里存在的连接 profile id** ✓
  target:
    purpose: 板子
    profile: board-adb
```

| # | 规矩 |
|---|---|
| 1 | **只许引用 profile id，不许覆写字段**（地址、用户、凭据**全是宿主的账** ✓） |
| 2 | **不许绑 `local` 传输**（T5 ✓） |
| 3 | **profile 不存在 → 报错**（不许悄悄连到别的 ✓） |

### 3.4 六种 step kind（**封闭**）

| kind | 干什么 | 必填 |
|---|---|---|
| `exec` | 在某个角色上跑一条命令 | `role` `cmd` |
| `discover` | 产物发现（**规则 + 排除表** ✓） | `role` `pattern` `out` |
| `file.transfer` | 搬运（源 → 目的地） | `from` `to` `cmd` |
| `action` | 引用**板型包里已声明的动作** | `role` `action` |
| `await` | 等一个判据成立 | `readback`（+ **在哪个角色上读** ✓） |
| `assert` | 判据 + 不符时怎么办 | `readback`（+ 同上 ✓） |

> **`exec_script` 连「留位置」都不留**（ADR-D31 R11 ✓）——
> 逃生门一旦写进表项，agent 就会去用 ✓。

### 3.5 判据：**复用 `spec/02` §4.4 的五形式**，只多一个 `role`

```yaml
readback:
  kind: verify
  role: target          # ← **在哪个角色上读**（不写 = 本步自己的角色 ✓）
  command: "test -f {to.path}"
```

| # | 规矩 |
|---|---|
| 1 | **五形式不变**（tag / file_equals / command_ok / verify / none ✓）——**不新增第六种** ✓（ADR-D31 R3 ✓） |
| 2 | **多一个 `role`**：「在哪个角色上读」 ✓ —— 跨目标的验证靠它 ✓ |
| 3 | **`role` 指到没声明过的角色 → 报错** ✓ |
| 4 | **`await`/`assert` 必须说得出在哪个角色上读**（自己的 `role` 或判据的 `role` ✓）——不然「默认读哪」就是猜的 ✗（评审 31-I7 ✓） |
| 5 | **形式 1（tag）暂不支持**（tag 属于**板型包的核心词表** ✓，流程层没有板型包 → **查不了** ✗）→ **直接报错**，不静默丢弃 ✓（评审 31-I3/I6 ✓） |
| 6 | **`none` 形式**：只在 `danger: reversible` 的步上用 ✓（照 `spec/02` §4.4.1 ✓） |

### 3.6 占位符（**封闭的五种** —— 它**就是注入防线** ✓）

> **评审 31-I2**：v1 把这一整段漏了 —— 而它恰恰是安全的关键 ✓。

| 写法 | 指什么 | 在哪种替换模式里 |
|---|---|---|
| `{input:名字}` | 一个参数的值 | 命令模式（**编码过的**）/ 值模式（原样 ✓） |
| `{role:角色.事实}` | 角色的连接事实（`host` / `port` / `user` / `key` / `profile_id` ✓） | 命令模式（**字符串包引号** ✓） |
| `{output:槽}` | **前面某一步**产出的槽 | 命令模式（**包引号** ✓）/ 值模式（原样 ✓） |
| `{output:槽.name}` | 文件名**去掉扩展名**（`hello.ko` → `hello` ✓） | 同上 |
| `{from.path}` / `{to.path}` | **这一步自己的**源 / 目的地（**只有 `file.transfer` 步里有** ✓） | 同上 |

**两种替换模式（**必须写进契约** ✓）**：

| 模式 | 用在哪 | 输入值 | 角色事实 | 槽里的路径 |
|---|---|---|---|---|
| **命令模式** | 步骤的命令、回读的二次验证命令 | **按类型编码过**（整数不带引号、字符串单引号 ✓） | **字符串包引号** ✓ | **包引号** ✓ |
| **值模式** | 回读的 `expect` / `path`、发现的 `dir` / `pattern` / `exclude` | 原样 ✓ | 原样 ✓ | 原样 ✓ |

→ **命令模式就是注入防线** ✓：`; reboot` 这种输入值**被当字面量** ✓。
→ **角色事实也要包引号** ✓：它来自**宿主的 profile**（半可信 ✓）——
「半可信」不等于「可信」✗（评审 32-I2 ✓）。

### 3.7 审计与时间线

| # | 规矩 |
|---|---|
| 1 | **每个写步骤一行审计**（照 `spec/02` §5.4 ✓），`actor` = `workflow:<pack id>` ✓ |
| 2 | **审计行必须带**：触发者 / **最终命令** / **输入值** / 结果 / 回读值（评审 32-I1 ✓ —— 追责链不能断 ✓） |
| 3 | **时间线**：一次运行的记录，每阶段引用那一行的 `audit_id` ✓ |
| 4 | **跨目标的判据单独一行**（`workflow:<pack>:<step>:readback` ✓）→ **两个事实、两行账** ✓ |
| 5 | **时间线里别的东西机器的信息要过滤**（别的目标的路径 ✓ —— 评审 32-I6 ✓） |

## 六 · 长任务的运行语义（**评审 31-C3 —— v1 整段缺失** ✓）

| # | 规定 |
|---|---|
| 1 | **`run` 立刻返回 `run_id`**，不返回时间线（编译实测 58.9s / 98.5s ✓ → 同步返回不成立 ✓） |
| 2 | **`status(run_id)` 轮询取时间线** ✓（ADR-D31 R9：首版 poll ✓） |
| 3 | **同一次运行的状态机**：`running` / `done` / `failed` / `cancelled` ✓ |
| 4 | **幂等**：同一个 `run_id` 重复查 → **同一份时间线** ✓（不是重跑 ✓） |
| 5 | **续跑**：失败后**从失败的步继续** —— **首版不做**（§八 ✓），但**必须说清** ✓ |
| 6 | **取消**：`cancel(run_id)` → **首版不支持**（执行原语不可中断，ADR-D32 D32-4 ✓）→ 契约里**明写不支持** ✓ |
