## 一 · 触发这件事的**一次实测**（2026-11-16 ✓）

宿主 → 板子 `192.168.5.100`（SSH）：

```
$ ssh root@192.168.5.100 'uname -r'
Permission denied (publickey,password,keyboard-interactive).
```

→ **网络通** ✓ · **认证失败** ✓ —— **那把私钥在客机上** ✓
（流程尖兵 2026-11-15 把它装进了板子的 `authorized_keys` ✓ —— **客机的公钥** ✓）。

### 1.1 三个事实

| # | 事实 | 含义 |
|---|---|---|
| 1 | **一块板有多条连接** ✓（ADB ✓ · 串口 ✓ · SSH ✓ —— 都指同一块板 ✓） | 「板子」与「连接」**不是一回事** ✓ |
| 2 | **跨机器的动作在客机上发起** ✓（`runTransfer`：**命令在源目标上跑** ✓） | **命令用到的 SSH 事实属于板子** ✓，**执行命令的机器是客机** ✓ |
| 3 | **同一块板的 SSH 端点只有一处该知道** ✓（`board-ssh` 那条 profile ✓） | **复制到每条 profile → 漂移** ✓ |

## 二 · **顺着评审的追问，查出一条更根本的**

评审问：「`target` 角色**能不能改绑 `board-ssh`**？」

我去查了 —— 发现：

```ts
// src/main/workflows/runner.ts · resolveEndpoints
const release = await ctx.deps.targets.runOn(profileId, async (conn) => {
  const result = await conn.exec('uname -r');
  ...
});
```

→ **它无条件去问目标机器的内核版本** ✗
→ 但**只有 `kernel-module` 的落位需要** ✓（`user-program` → `/usr/local/bin/` ✓ —— **固定路径** ✓）。

**这条的后果比「多一次往返」严重** ✓：

> **宿主必须能连上目标机器** ✓ —— 而「宿主只有 ADB、板子私钥在客机上」时 ✓ —— **那条路走不通** ✗
> → **本来不需要的依赖变成了硬依赖** ✗。

**已修** ✓（`ADR-D43` ✓ · 守卫 **M198** ✓ —— 判据：「`user-program` 不问 `uname -r`」✓ / 「`kernel-module` 问」✓）。

**修完之后，「宿主全程不需要板子的私钥」** ✓：

| 步 | 在哪跑 | 宿主要连板子吗 |
|---|---|---|
| `compile` / `artifacts` | 客机（`build` 角色 ✓） | **不需要** ✓ |
| `deliver`（scp） | **客机** ✓（命令在源目标上跑 ✓） | **不需要** ✓（客机用自己的钥匙 ✓） |
| `make-executable` / `run` | 客机上经 `ssh` 中转 ✓ | **不需要** ✓ |

→ **唯一剩下的缺口**：**流程包怎么拿到板子的 SSH 端点** ✓（`{role:target.host}` 现在是空串 ✓）。

## 三 · **重做后的方案**（**三处契约改动 + 一处实现** ✓）

### 3.1 `spec/02` §10：**补一节「连接 profile 的格式（封闭）」** ✓

> **为什么要补这一节** ✓（评审 I-2 ✓）：契约**从没定义过** profile 的字段表 ✓
> （只有一段示例 JSON ✓ + 绑定键的命名规矩 ✓）→ **要加字段 ✓ 就得先有表** ✓。

**新增 `device_key`（可选，缺省 = profile id）** ✓：

```jsonc
// profiles/targets/board-adb.json
{ "id": "board-adb", "transport": "adb", "board_pack": "rk3588-atk",
  "device_key": "atk-01",
  "options": { "serial": "f34dca7784396ab2", "pty": false } }
```

| 项 | 规则 |
|---|---|
| **形状** ✓ | 字符串 ✓ |
| **缺省** ✓ | `profile.id` ✓（**一板一连** ✓ 的连接就这么办 ✓） |
| **同一块板的多条连接** ✓ | **必须写同一个 `device_key`** ✓ |
| **取值域** ✓ | **profile id 空间里的一个 id** ✓ —— **不是主机名、不是 URL** ✓ |
| **谁校验「同一个 `device_key` 的多条 profile 声明一致」** ✓ | **实现层** ✓（**宿主启动时查一次** ✓） |

**新增 `options.ssh`（可选，跨传输的 SSH 端点）** ✓：

```jsonc
// profiles/targets/board-adb.json —— 这条连接背后那块板的 SSH 端点
{ "id": "board-adb", "transport": "adb", "board_pack": "rk3588-atk",
  "device_key": "atk-01",
  "options": { "serial": "f34dca7784396ab2", "pty": false,
               "ssh": { "host": "192.168.5.100", "port": 22, "username": "root" } } }
```

| 项 | 规则 |
|---|---|
| **为什么住在 `options` 里** ✓ | **顶层字段表一个字不加** ✓（评审 I-2 的要害 ✓）→ **改动面最小** ✓ |
| **为什么每条传输都允许它** ✓ | 它**跨传输** ✓ —— 「这条连接**背后那台机器**的 SSH 端点」✓ |
| **`transport: 'ssh'` 的 profile 呢** ✓ | **它自己就是那个端点** ✓ → **不用再写 `options.ssh`** ✓（**双写 = 漂移** ✓ —— 评审 I-3 ✓） |
| **冲突怎么办** ✓ | `transport: 'ssh'` 的 profile **不许**带 `options.ssh` ✓ → **报错** ✓（不是「谁赢」✓ —— **不猜** ✓） |
| **`local` 呢** ✓ | **不许带** ✓（它是宿主自己 ✓ —— 评审 M-1 ✓） |

> **为什么不用「顶层 `ssh` 块」** ✓（上一版的做法 ✓）：
> ① **改动面大** ✓ —— 要改 `factsOf` ✓（它读 `options` ✓）+ 改 `spec/05` §六 ✓ + 改 `schema.ts` 顶层封闭表 ✓；
> ② **要复制到每条 profile** ✓（**漂移** ✓ —— 评审 C-3 ✓）；
> ③ **契约里从没说过「`options` 只放传输自己的参数」** ✓ —— **那条只存在于实现** ✓
> → **把它当既成事实来推，依据不足** ✓（评审 I-2 ✓）。
> → **`options` 本来就是 `Record<string, unknown>`** ✓ —— **加个键** ✓。

### 3.2 `spec/05` §六：**角色事实的来源**（**评审 C-1 的要害** ✓）

| 事实 | 来源（**新**）✓ |
|---|---|
| `host` | 该角色所绑 profile 的 **`options.ssh.host`** ✓ → 没有则 **`options.host`** ✓ → 再没有则**空串** ✓ |
| `port` | 同上（`options.ssh.port` → `options.port` → **22** ✓） |
| `user` | 同上（`options.ssh.username` → `options.username` → **`root`** ✓） |
| `profile_id` | 该角色的 `profile.id` ✓ |

> **「角色事实的封闭表」不变** ✓（`host` / `port` / `user` / `profile_id` ✓ —— **只是来源多了一个** ✓）
> → **流程包文件一个字不用改** ✓。

### 3.3 `spec/04` §2.1：`list_connections` 加两个字段 ✓

```
→ [{ id, label, transport, board_pack, device_key, current, connected, capabilities }]
```

| 字段 | 含义 |
|---|---|
| **`device_key`** | **这块板的标识** ✓ —— **同一块板的多条连接给出同一个** ✓ |
| **`current`** | **它是当前运行时那条连接吗** ✓（**与 `connected` 的两条判据分开写** ✓ —— 评审 I-6 ✓） |

> **为什么要 `current`** ✓：agent 看到两条 `connected: true`（一条是运行时 ✓ · 一条只开了终端 ✓）
> → **不知道哪个是「当前那块」** ✓ → **`device_key` 无合法值可填** ✓。

### 3.4 `spec/04` §2.4：`execute_action` 加 **`device_key?`**（**必须真的实现** ✓）

| 项 | 规则 |
|---|---|
| **省略** | **当前运行时那块板** ✓（与今天一样 ✓） |
| **给了** | **它必须是当前运行时那条连接的 `device_key`** ✓ → 否则 **`not_found`** ✓（detail 写清「没有这个设备：X」✓） |
| **绝不允许** | **忽略 `device_key` 然后打当前那块** ✓（**那是「静默地做另一件事」** ✗ —— 评审 C-4 ✓） |

**§二 里「参数位置留着，行为不做」这句删掉** ✓ —— **要么实现这个检查 ✓，要么本轮不出现这个参数** ✓（评审 C-4 ✓）。

### 3.5 `spec/04` §2.4.1：**凭据绑定表加 `device_key`**（**第六项** ✓）

```
(动作 id, 参数的规范化摘要, 板型包 id, 契约版本, 最终命令的摘要, **device_key**)
```

> **为什么现在加** ✓（评审 I-4 ✓）：**将来多设备时** ✓，一张为 A 板签发的凭据能拿去动 B 板 ✗ →
> **那时再加绑定项同样是破坏性变更** ✓ → **现在加** ✓。
> → **`confirm_action` 也要带 `device_key?`** ✓。
