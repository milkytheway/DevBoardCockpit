## 一 · D7 的处置：**目标不进契约，进数据**

> **待裁决的 D7**（「目标」这一维要不要进契约）—— **本文给出一个不需要它也能满足用户需求的答案**。

**用户原话**：「用户可以选择**本机**或者**客机**上的代码」。

**本文的形状**：

```
目标（哪台机器）  ← 由**流程包**声明（role → profile id，宿主侧的文件 ✓）
用户的选择        ← 由**用户选哪个流程**表达 ✓
```

→ **「本机编译」与「客机编译」是两个流程包**（`hello-kernel.build-run.local` / `.guest` ✓）
→ 卡片**只看到流程**（id + 输入声明）✓ → **卡片不知道目标** ✓
→ **契约层一个字都不用改「目标」这一维** ✓（ADR-D33 D33-1 ✓）。

**代价（诚实说）**：卡片**不能自己拼**「先在客机编译、再传到板子」这种多步组合
——它只能选一个**已经声明好的流程** ✓。
→ 用户要的新组合 = **写一个新的流程包**（宿主侧的文件 ✓，不是卡片代码 ✓）。

**ADR-D34 的草案**：**「目标」是流程包的属性，不是契约的概念**；
卡片与 agent 触发的是**宿主已声明的流程**（与 ADR-D31 R2 的「角色不许绑到 `local`」一致 ✓）。

## 二 · `docs/spec/05-workflow-pack.md`（新增）

> **内容**：`docs/29-流程包格式.md` 的**契约版**（字段表 / 六种 step kind / 封闭词表 / 占位符 ✓）。
> **不新增**任何宿主层没有的东西 ✓。

### 2.1 顶层字段（封闭）

```yaml
formatVersion: 1        # 宿主层格式版本（**不是契约的 apiVersion** ✓）
kind: Workflow
id: hello-kernel.build-run
name: 编译内核模块 → 直传板子 → 装 → 跑
version: 1.0.0
description: …
inputs: { … }           # 封闭类型表（照 spec/02 §4.3 ✓）
roles:  { … }           # role → 连接 profile id（**只许引用** ✓）
steps:  [ … ]           # 六种 kind
```

### 2.2 六种 step kind（**封闭**）

| kind | 干什么 | 必填 |
|---|---|---|
| `exec` | 在某个角色上跑一条命令 | `role` `cmd` |
| `discover` | 产物发现（规则 + 排除表 ✓） | `role` `pattern` `out` |
| `file.transfer` | 搬运（源 → 目的地） | `from` `to` `cmd` |
| `action` | 引用**板型包里已声明的动作** | `role` `action` |
| `await` | 等一个判据成立 | `readback` |
| `assert` | 判据 + 不符时怎么办 | `readback` |

### 2.3 判据：**复用 `spec/02` §4.4 的五形式**，只多一个 `role`

```yaml
readback:
  kind: verify
  role: target          # ← **在哪个角色上读**（不写 = 本步自己的角色）
  command: "test -f {to.path}"
```

> **为什么不新增第六种形式**（ADR-D31 R3 ✓）：
> 「板子上真的有那个文件了吗」是**另一个目标**的事实 →
> **执行器在执行的那条连接上回读**（`spec/02` §5.2 / SPEC-D22：执行与回读不可拆分 ✓）→
> 跨目标的判据**由流程层跑**（ADR-D33 D33-2 ✓）→ **两个事实、两行账** ✓。

### 2.4 危险等级与确认

| # | 规定 |
|---|---|
| 1 | 每个写步骤**都过 `spec/02` §4.6 的编码 + §5.2.1 的危险地板** ✓ |
| 2 | 步可以声明 `danger: destructive` → **每次运行都要人确认** ✓ |
| 3 | **命中危险地板 → 也按 `destructive` 处理**（取更严的 ✓） |
| 4 | **凭据准备**（写目标机器的 `authorized_keys`）**必须**声明为 `destructive` ✓ |

### 2.5 审计与时间线

| # | 规定 |
|---|---|
| 1 | **每个写步骤一行审计**（照 `spec/02` §5.4 ✓），`actor` = `workflow:<pack id>` ✓ |
| 2 | **时间线**：一次运行的记录，每阶段引用那一行的 `audit_id` ✓ |
| 3 | **跨目标的判据单独一行**（`workflow:<pack>:<step>:readback` ✓） |

## 三 · `docs/spec/03-card-manifest.md` 的增量

### 3.1 manifest 新增一个字段

```yaml
requires:
  workflows: [hello-kernel.build-run]     # ← 新增（封闭字段表 ✓）
permissions:
  write: []                               # ← 流程的动作**不在这里声明** ✓
```

> **为什么动作不重复声明**：流程包**自己**声明它的步骤 ✓
> ——**卡片只声明「我要用哪些流程」** ✓（装卡时点头 ✓）。

### 3.2 §7.7 的 API 全集：加两行

| 方法 | 读/写 | 权限 |
|---|---|---|
| `cockpit.workflows.list()` | 读 | 无（只列**宿主已声明**的流程 ✓） |
| `cockpit.workflows.run(id, inputs)` | 写 | `requires.workflows` 里有这个 id ✓ |

```js
const r = await cockpit.workflows.run('hello-kernel.build-run', { project: '01-hello' });
// r = { ok: true, runId: 'wf-…', stages: [ { stepId, ok, verified, audit_id, … } ] }
```

> **返回的是时间线**（不是「成功/失败」一个布尔 ✓）——
> 「编译 → 上传 → 加载」每一步的结果**都要看得见** ✓（用户那张卡的「观察中间结果」✓）。

### 3.3 §5 的写侧闭环：加一段「一件事」

> §5 现在写的是「**一个动作**」的闭环（卡片 → 动作 → 回读 ✓）。
> §5.5 加：「**一件事**」= **流程**（卡片 → 流程 → 多个步骤 → 时间线 ✓）。

## 五 · 这条增量**不做**的事

| 不做 | 为什么 |
|---|---|
| **「目标」进契约** | 本文 §一 的形状已经满足用户需求 ✓；D7 因此**不必现在拍** ✓ |

| **角色的自由绑定**（包里写 host/user/key） | 同上 ✓；而且**角色不许绑到 `local`**（ADR-D31 R2 ✓） |

## 六 · 请评审重点看这五条

1. **§一的形状够不够**（卡片选流程 = 选目标 ✓）——**这是产品判断**；

5. **§五那些「不做」的**有没有该做的 ✓。
