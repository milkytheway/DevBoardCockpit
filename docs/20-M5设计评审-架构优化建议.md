# M5 设计评审 · 架构优化建议

> **日期**：2026-11-13
> **作者**：Codex（独立评审）
> **评审对象**：`docs/04-架构设计.md` §2.1 / §6 / §7 / §8 / §10 / §12、`docs/spec/03-card-manifest.md`、`docs/spec/04-mcp-tools.md`、ADR-D3/D4/D6/D14/D16/D27
> **问题**：**M5（卡片框架）的计划与设计，有没有需要优化的地方**，使它有更好的架构、更能承载预期功能、更有拓展性？
> **性质**：只评审、只提建议。不改契约、不改实现。

---

## 〇、结论

**设计文档写得比一般项目好**（进程模型画得清楚、扩展点待遇表、降级矩阵、测试策略都在）。
但它有三个**空洞**，都恰好在 M5 最硬的那块：

| # | 空洞 | 后果 |
|---|---|---|
| **A** | **卡片 API 怎么进 iframe，没有设计** | §6.2 只说「宿主只认白名单方法」——**没说方法怎么到卡片手里**。M5 的第一个 Task 会卡在这 |
| **B** | **卡片的权限过滤点没定** | 决定「renderer 只画」这条铁律能不能守住 |
| **C** | **IPC 通道模型与实现已经漂移** | M5 会照着一张**过时的**通道表做 |

**加上四条会挡住扩展的地方**：卡片 API 没有能力发现、卡片之间隔离靠什么、内置卡与用户卡两套渲染模型、宿主外壳自己没有 CSP。

**好消息**：我用一次 Electron 尖兵把 A 全部实测清楚了 —— **方案可行，而且比我原以为的更简单**（不需要 nonce）。
证据在 `docs/superpowers/spikes/2026-11-13-卡片沙箱与桥接实测.md`。

## 一、我怎么验的

**没有靠推理。** 契约 §六 明写「卡片跑在 iframe 里……**本轮规格不锁这一点**」——
那就意味着这是 M5 必须自己做的技术决策，而它是整个 M5 的成败所在。

所以我写了一个 **Electron 34 尖兵**（一次性，不进 `src/`）：
注册 `cockpit://` 协议 → 用契约 §6.1 的**逐条原文**作为 CSP 响应头 → 两个 sandbox iframe
（一个不透明源、一个 `allow-same-origin`）→ 卡片里跑 6 个隔离探针 + 一套完整的桥接。

**结果推翻了我的一个假设，也坐实了另一个**：

| 实测 | 结论 |
|---|---|
| `script-src 'self'` 在**不透明源**下 | **照样匹配** —— 卡片自己的 ES Module 与相对 import 都能跑 ✅（**我原以为是错的**） |
| 卡片读 `parent.document` / `window.top` | 两种变体都是 **SecurityError** ✅ |
| `fetch` / `WebSocket` / `<img>` 外传 | **全被 CSP 拦掉**，且违规**能被宿主 `console-message` 抓到** ✅ |
| `localStorage` | 不透明源下**抛 SecurityError** ✅（与契约 §6.2 的前提一致） |
| **Electron 的 preload** | **不进子 iframe**（主帧有 `window.cockpit`，卡里 `undefined`）→ **postMessage 桥是必须的** |
| **MessagePort 转进不透明源 iframe** | ✅ **可用** |
| **`event.source` 认人** | ✅ **准确** → **不需要 nonce** |

## 二、四个 🔴 级发现

### F1 · 卡片 API 怎么进 iframe —— **设计空白**，但方案已实测可行

**现状**：`docs/04` §6.2 写「宿主只认白名单方法（以契约 §7.7 的全集为准），
每条消息校验三件事：**来源 frame** → **方法在白名单** → **该卡片的权限**」。

**「校验」写清楚了，「投递」没写。** 卡片里的 `window.cockpit` 从哪来？
`docs/04` §2.1 的图里写了一行「postMessage（白名单，无同源）」，但那只是**方向**，不是机制。

**为什么这是空白而不是小事**：实测证明 **Electron 的 preload 挂不到 iframe 上**。
所以卡片**不可能**像宿主页面那样通过 `contextBridge` 拿到 API。
**必须**有一条显式的注入机制 —— 而设计文档里没有。

**我实测出来的机制（可以直接写进设计）**：

```
① 协议 handler 在响应 cockpit://card/<id>/index.html 时，
   注入 <script type="module" src="cockpit://card/__host/bridge.js">
   （同源，所以 script-src 'self' 允许；且卡片改不了 —— 它是宿主写的响应）
② bridge 脚本在卡片里定义 window.cockpit.*，底下是一个 MessagePort
③ 卡片发 {type:'cockpit-hello'} 给 parent
④ 宿主用 event.source 认人（★ 不看 origin —— 不透明源下 origin 是 null）
   → 找到是哪个 iframe → 建 MessageChannel
⑤ 宿主 iframe.contentWindow.postMessage({type:'cockpit-port'}, '*', [port2])
⑥ 之后全部请求-响应都在这条私有端口上
```

**关键：不需要 nonce、不需要 token。**
`event.source` 就是「哪个 window 发的」，卡片拿不到别的卡的 window 引用 → **冒充不了**。
（我上一轮评审说要「每卡一个 nonce」—— **那是过度设计，实测证明不需要**。）

**顺带必须补进设计的实现要求**：

| # | 要求 | 为什么 |
|---|---|---|
| 1 | **协议 handler 必须按扩展名给正确 MIME**（`.js` → `text/javascript`） | 我第一跑全按 `text/html` 发，module script **直接被拒**（"Strict MIME type checking is enforced"） |
| 2 | **CSP 响应头由协议 handler 注入**，不靠卡片 `meta` | 契约 §6.1 已写；实测 `connect-src 'none'` 真的拦住了 |
| 3 | **CSP 违规要从 renderer 的 `console-message` 收集** → 写进卡片运行时日志 | 实测可行；契约 §6.1 承诺了 agent 要能看到「这张卡试图联网」 |
| 4 | **路径穿越防护**要写清算法（`..`、绝对路径、符号链接、`%2e%2e`） | §6.1 只写了「路径穿越防护」四个字 |
| 5 | **宿主外壳自己也要有 CSP** | 实测 Electron 报了 Security Warning；现在 `index.html` **完全没有 CSP** |

### F2 · 卡片的**权限过滤点**没定 —— 这决定「renderer 只画」能不能守住

契约 §3.3 说卡片不能运行时提权；§七说「运行时保证：只返回 `permissions.read` 里列出的 tag」。
**但「运行时」是 main 还是 renderer？** 设计文档没写。

| 放哪 | 后果 |
|---|---|
| **renderer** | 违反 AGENTS.md §5「**卡片注册表在 main，renderer 只画**」；而且**安全过滤落在 renderer** —— 一张卡的 bug 就能泄漏另一张卡的数据；MCP 在 main 也拿不到同一套过滤 |
| **main** ✅ | main 知道每张卡的权限 → **过滤与授权一处做**；MCP 与卡片共用同一条服务路径；renderer 真的只画 |

**建议**：**每张卡的会话（权限、tag 服务、动作执行、审计）由 main 持有**；
renderer 只负责「建 iframe、转发一次性握手、把端口转交」。

> 这也正好对上 AGENTS.md §5 的铁律，和 ADR-D2「MCP 与 GUI 同进程，agent 读到的与用户看到的完全一致」。

### F3 · IPC 通道模型**已经漂移** —— M5 会照着错的做

`docs/04` §10 的表 vs 实现的 `IPC`：

| `docs/04` §10（设计） | 实现 | 差异 |
|---|---|---|
| `tag:snapshot` / `tag:update` / `tag:subscribe` / `:unsubscribe` | `tags:readings` / `tags:changed` | **不只是改名**：设计是「**按 tag 订阅**」，实现是「**广播全部读数给每个窗口**」 |
| `card:event` **M→R（推送）** | — | **方向自相矛盾**：载荷写的是「卡片请求宿主能力」，那是 **R→M** |
| `card:list` / `:validate` / `:reload` / `card:storage` / `card:consent` / `layout:*` / `log:*` / `settings:*` | 都不存在 | 设计先行，尚未实现（正常） |

**为什么这条重要**：卡片按 `permissions.read` 过滤 tag（§7.1）——
**过滤发生在哪一层，直接决定 F2**。
如果过滤在 renderer，renderer 就要维护「每张卡能看哪些 tag」的表；
如果过滤在 main（我建议的），main 在**向该卡推送时**就已经过滤掉了。

**建议**：**把 §10 的表改成实现的形状**，并补一句
「卡片订阅的粒度是**卡片实例**，不是 renderer —— 过滤在 main 做」。
（顺带修掉 `card:event` 的方向矛盾。）

### F4 · 卡片 API **没有能力发现** —— 扩展性的真正瓶颈

- **MCP 侧有** `list_capabilities()`（`spec/04` §2.1）。
- **卡片侧没有**：`spec/03` §7.7 的 9 个方法是**封闭全集**，卡片**无法问**「宿主支持哪些方法 / 当前连的是谁 / 哪些 tag 可读」。

**为什么这是扩展性瓶颈**：
「AI 可造卡」是这个产品的核心主张（AGENTS.md 主线二）。
agent 写卡片时**必须知道宿主现在支持什么**——
现在它只能**硬编码假设**「`cockpit.tags.get` 一定在、`cockpit.actions.invoke` 一定在」。
一旦宿主版本不同，**卡片只能靠 try/catch 猜**——而卡片跑在沙箱里，猜错了没有任何提示。

**建议**：给卡片 API 加一个 **`cockpit.capabilities()`**，
返回 `{ apiVersion, methods: [...], connection: {...}, tags: [...] }`。
它是**对称**的（MCP 侧已有），也是**让卡片 API 能演进的前提**：
加了新方法，老卡片先问一句就知道有没有，而不是报「未知方法」。

> 这一条要改契约（`spec/03` §7.7 + §7.8）。按 v1 定稿前修正口径，**不升 apiVersion**。

## 三、六个 🟡 级发现

### F5 · 卡片之间的隔离：**必须用不透明源**

实测：**变体 B（`allow-same-origin`）下所有卡共享 `cockpit://card` 一个源** →
**A 卡能读 B 卡的 localStorage**。
契约 §6.2 承诺「每卡一个命名空间、**互不可见**」——**只有变体 A 能兑现**。

**建议**：**维持 `sandbox="allow-scripts"`（不给 `allow-same-origin`）**。
代价是 `localStorage` 抛 SecurityError —— 但契约**本来就要求宿主代管存储**，
所以这条前提是**成立**的，不是将就。

**顺带**：`cockpit://` 的 host 部分建议**按卡片分**（`cockpit://<card-id>/…`）——
用不透明源时不需要，但为将来留门（万一要 `allow-same-origin`，每卡一个源才是隔离的）。

### F6 · 内置卡与用户卡是**两套渲染模型**，但要挤进同一个布局

`docs/04` §8：「内置卡：终端卡、文件浏览器卡、日志工作区、目标切换器——
**与用户卡片同一套布局**，不可删除」。

**问题**：内置卡是**宿主的 React 组件**（xterm、文件树），
用户卡是 **sandbox iframe**。两者：
- 焦点 / 键盘 / 滚动 / 缩放 / 右键菜单 **行为不一致**；
- 热插拔、崩溃隔离、CSP **只对 iframe 卡有意义**；
- react-grid-layout 的每个格子要能装两种东西 → **布局系统被卡片实现绑死**。

**建议**：**布局只认「槽位」，不认实现**。
```
Slot { id, kind: 'builtin' | 'user', cardId?, connectionId?, layout }
```
- `kind: 'builtin'` → 宿主 React 组件
- `kind: 'user'` → sandbox iframe
布局引擎只管 `Slot` 的位置与尺寸。**这样 M8 的 promote / 全屏 / 布局分享不必再动布局系统。**

### F7 · 宿主外壳**自己没有 CSP**

实测 Electron 直接报了 Security Warning（`index.html` 里一个 CSP 都没有）。

宿主外壳跑的是**不可信卡片的宿主**——它的 CSP 至少要有
`default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'none'`。
**设计文档只覆盖了卡片的 CSP，漏了外壳的。**

### F8 · 文档漂移三处（其中一处是**两份 ADR 直接矛盾**）

| # | 位置 | 状态 |
|---|---|---|
| 1 | **`ADR-D10`「视觉体系：沿用愿景的 Ant Design（🟡 待用户确认）」** vs **`ADR-D27`/O1 已定「主体 UI 不引 antd」** | 🔴 **两份 ADR 矛盾**。下一个 agent 照 ADR-D10 去装 antd 就跑偏了 |
| 2 | `docs/04` §3「组件库 Ant Design 5 `[待确认 D10]`」、§8「Ant Design 的主题变量与 `--cockpit-*` 一一映射」、§15 Q1「待拍板」 | 🔴 全部过时 |
| 3 | `docs/04` §12 的注释「探针的真机验收还没跑过——见 C12」 | 🟡 已经跑过了 |

**建议**：**ADR-D10 改写为「已被 ADR-D27 取代」**（保留历史，不删），
`docs/04` §3/§8/§15 同步。

### F9 · `docs/04` §3 的目标目录**已经和实现对不上**

设计写 `src/main/tags/` = `kinds.ts readers.ts binding.ts poll.ts validate.ts describe.ts`；
实际是 `src/main/tags/kinds/`（目录）+ `sampler.ts` `scheduler.ts` `runtime.ts` `probe.ts` `floor.ts` `vocabulary.ts` `pack.ts` `schema.ts` `validator.ts` `fetch.ts` `store.ts`。

**M5 的 `src/main/cards/` 目录要按**实际约定**来（一个职责一个文件、kind 放子目录），
而不是按设计文档那张过时的表。

### F10 · 卡片 manifest 校验器要支持**离线模式**

`spec/03` §九 规则 5：「`permissions.write` 里每个动作 id 在**当前连接的板型包**里存在
（**连不上板时跳过此检查，标注「未验证」**）」。

→ 校验器有**两种模式**：连上板（full）与连不上（degraded）。
设计文档 §6.1 的热插拔流程只写了「读 manifest → schema 校验 → 不通过就保留上一版」，
**没说离线时怎么办**。
→ 建议：`validate_card` 返回 `{ ok, issues[], unverified: [...] }`，
**「未验证」要与「不合法」在报告里分开**（MCP 的 `validate_card` 要能把这两类分开告诉 agent）。

## 四、我建议的 M5 架构

```
┌─ Electron main ─────────────────────────────────────────────┐
│  cards/                                                     │
│    registry.ts    卡片注册表：发现（双根合并）+ 权限 + 实例   │  ← 权限在这
│    manifest.ts    manifest 解析（封闭 schema）               │
│    validate.ts    spec/03 §九 的 13 条规则（含离线模式）      │
│    protocol.ts    cockpit:// 托管 + CSP 响应头注入 + MIME      │
│    session.ts     每卡一个会话：端口 + 权限 + tag 服务         │  ← 过滤在这
│    runtime-log.ts 卡片运行时日志（CSP 违规、window.onerror）   │
│    consent.ts     需要人工确认时的弹窗                        │
│  actions/    M6：executor + policy（参数编码/guard/地板/审计）│
│  mcp/        M7：与卡片共用 session 服务（同一套权限语义）    │
└──────────────┬──────────────────────────────────────────────┘
               │ IPC（invoke/handle + 事件推送）
┌──────────────▼──────────────────────────────────────────────┐
│ Electron renderer（只画）                                    │
│  layout/    react-grid-layout，**只认 Slot**（F6）            │
│  cards/     iframe 宿主：建 iframe、转发握手、转交端口        │  ← 不判权限
│  terminal/  panes/  theme/                                   │
└──────────────┬──────────────────────────────────────────────┘
               │ postMessage + MessagePort（每卡一条私有通道）
┌──────────────▼──────────────────────────────────────────────┐
│ 卡片 iframe：sandbox="allow-scripts"（**无 same-origin**）    │
│ cockpit://card/<id>/index.html                               │
│ 宿主注入的 bridge.js 提供 window.cockpit.*                    │
└─────────────────────────────────────────────────────────────┘
```

**五条关键决策**：

| # | 决策 | 依据 |
|---|---|---|
| 1 | 沙箱**不给** `allow-same-origin` | 卡片之间的隔离（F5，实测） |
| 2 | API 经**宿主注入的 bridge 脚本 + MessagePort** | preload 进不了 iframe（实测） |
| 3 | 认人用 **`event.source`**，不用 nonce | 实测足够，且更简单（实测） |
| 4 | **权限过滤与 tag 服务在 main** | AGENTS.md §5 + ADR-D2（F2） |
| 5 | **布局只认 Slot** | 内置卡与用户卡两套模型（F6） |

## 五、契约要不要改？（三处，都走「v1 定稿前修正」口径）

| # | 改哪 | 改成什么 | 为什么 |
|---|---|---|---|
| 1 | `spec/03` §7.7 | **加 `cockpit.capabilities()`** | 卡片无法发现宿主能力 → 卡片 API 无法演进（F4）。MCP 侧已有对称的 `list_capabilities()` |
| 2 | `spec/03` §六 | 沙箱已经写了「不给 `allow-same-origin`」✅，但**没写它带来什么** → **补一句「因此卡片之间互不可见」**，把 §6.2 的承诺与沙箱选择**绑在一起** | 现在 §六 与 §6.2 的关联是隐含的；实测证明改掉沙箱就会破坏 §6.2 的承诺（变体 B 下 A 卡能读 B 卡的 localStorage）。加一句就不容易被后来的实现悄悄改掉 |
| 3 | `spec/03` §六 | **写明 `preload` 进不了 iframe，API 必须经宿主注入的 bridge 提供** | 契约层明写「本轮规格不锁这一点」；现在**已经锁了**（实测），应该写进去 |

> **第 1 条是唯一「加能力」的改动**。它加的是**只读**方法、无权限面、无危险面，
> 而且让卡片 API **第一次有了版本协商的可能** —— 这是扩展性的地基。

## 七、给拍板人的三个问题

## 八、我建议的 M5 验收判据（**机械可判**，不是「看着像对」）

| # | 判据 | 怎么判 |
|---|---|---|
| 1 | 卡片**碰不到宿主 DOM** | 卡片里 `parent.document` 抛 SecurityError |
| 2 | 卡片**碰不到别的卡** | A 卡读不到 B 卡的存储 |
| 3 | 卡片**连不上网** | `fetch` 抛错，**且** CSP 违规出现在**卡片运行时日志**里（agent 可见） |
| 4 | 卡片**拿不到未授权的 tag** | 卡片请求 `permissions.read` 之外的 tag → 被拒，**且**主进程有审计记录 |
| 5 | 卡片**崩了不影响别人** | 一张卡抛异常，其他卡照常 |
| 6 | **改文件即热更新** | 改 `card.js` → iframe 重载 → 新行为生效，**布局位置不丢** |

> 第 6 条有个设计问题要先定：**重载 iframe = 卡片状态全丢**（订阅要重订阅）。
> 宿主代管的存储能保住（契约 §6.2 已经承诺卸载保留），
> 但**运行时的状态**（比如用户展开的面板）保不住 —— 这是可接受的，但要写进卡片开发规范。
