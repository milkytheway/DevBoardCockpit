## 一、决策 ① · capability 词汇表

### 1.1 结论

**两套词表是两个不同的轴，各归各位，谁也不改名成对方的词。**

契约层那套叫**板级能力**（board-level）：「这块板能做什么」。
实现层那套叫**连接级能力**（connection-level）：「**这条连接**能做什么」。

**这不是妥协，是契约刻意的分层。** `docs/spec/02` §10.2 写得很直白：

> **包描述板子，HAL 描述通道，两者由运行时接起来。**

同一个词在两个轴上含义不同，是**当前设计的固有事实**，不是历史遗留。
能立刻看出不对的例子：串口传不了文件（事实 S7），但**板子**当然有文件通道——
所以 `files` 在契约里是板子的属性，在实现里是连接的属性。

### 1.2 词义对照表（**这是契约的一部分**）

`docs/14` 原写「映射表（板子能力 → 连接能力）」。**这个措辞会被实现成一个函数，
而它不可能是函数**——同一块板走 adb 和走 serial，连接能力完全不同
（实测：`serial` 的 `files=false`、`exitCode=false`；`adb` 都是 true）。
**板子能力推不出连接能力。**

所以契约里那张表只能是**两种词之间的对照**，长这样：

| 板级能力（契约，包声明） | 连接级能力（实现，profile 协商） | 语义 | v1 实现状态 |
|---|---|---|---|
| `shell` | `pty` | 能开交互式 shell | ✅ 已实现 |
| `exec` | `exec` | 能跑一条命令拿结果 | ✅ 已实现 |
| `files` | `files` | 有文件通道 | ✅ 已实现（**但串口上没有**——见下） |
| `stream` | —— | 能推连续流 | ❌ **未实现**：Stream 契约缺失（`docs/09` §三①） |
| —— | `exitCode` | **通道能给退出码** | ✅ 已实现（**串口上没有**，事实 S5） |

**最后一行是关键**：`exitCode` **没有板子级对应物**——
它是**通道的属性，不是板子的属性**（串口拿不到退出码）。
这正好证明两套词不是同一个轴。

**这一行的另一个作用**：它说明 `exitCode` **本来就该是连接级的**，
不是「实现里多出来的一个」。`docs/14` 把它当后者，是漏看了。

> **注意 `files` 那行的双重性**：板级 `files` 与连接级 `files` 同名，
> 但**语义不同**——板级说的是「这块板有文件通道」，连接级说的是「**这条连接**能传文件」。
> 串口连接上后者是 false，前者仍然是 true。
> **这正是为什么 `requires.capabilities` 不能当连接门禁用**（见 1.4）。

### 1.3 实现层改名：`ConnectionCapabilities`

`docs/14` 在 `TransportCapabilities` / 「连接级」之间留了个口子。
**拍板取 `ConnectionCapabilities`**，理由是代码自己说的：

```ts
// src/main/hal/capabilities.ts
// 能力位由 **profile 决定**，不是由传输名决定。
export function capabilitiesFor(profile: ConnectionProfile): Capabilities {
  ...
  pty: typeof explicit === 'boolean' ? explicit : defaults.pty,
}
```

`pty` **可被 profile 的 `options.pty` 覆盖**（串口默认 true、adb 默认 false，
但 profile 可以改）→ 能力位是 **profile（连接）级**的。
叫 `TransportCapabilities` 会跟这段代码自己的注释打架。

**代价**：`src/shared/ipc-contract.ts` 一处定义 + `src/main/hal/` 五处引用 +
renderer 两处。改名是机械的，但**必须一次改干净**——留一个 `Capabilities` 别名
等于两套名字并存，正是本决策要消灭的东西。

### 1.4 `requires.capabilities` 是**信息**，不是门禁

`docs/spec/02` §10.2 已经写明 `requires.transports` 是「**信息，不是限制**」。
**`requires.capabilities` 同样如此**，而且理由更强：

> **串口的 `files=false`。** 若拿板子级 `files` 做连接门禁，
> 这个包在串口上就废了——**直接违反 §10.2「这个包在串口上也能用」**。

所以 v1 **不**把 `requires.capabilities` 当连接绑定条件。
它有两件事要做：

1. **被校验**（两条新规则，见 1.5）；
2. **被查询**——让 agent 知道「这块板声明支持什么」。

**「被查询」在 v1 的落点**：板型包描述接口（`describe_board_pack()` 一类）
与 `probe:board` 的输出里带上它。
**如果 v1 不想开这个工具，就得在 `docs/06` 记一条「该字段暂无消费者，待 v2」——
别装作它有意义。**（已按此记入 `docs/06`。）

### 1.5 新增校验规则 25 / 26

`docs/spec/02` §七 原有 24 条，**没有一条检查 `requires.capabilities`**
（实测确认：也没有一条检查 `requires.transports`）。
这不是「以后再说」能糊过去的——**M3 就是要写这个校验器**，
现在不定，M3 就会写出一个「跳过 capabilities」的校验器。

| # | 规则 | 为什么 |
|---|---|---|
| **25** | `requires.capabilities` 的每个值必须属于**封闭词表** `{shell, exec, stream, files}` | 拼错的值要有报错，不是静默忽略（与规则 24 同一条封闭性原则） |
| **26** | `requires.capabilities` 的每个值必须属于**运行时已实现的能力集**（v1 = `{shell, exec, files}`） | 声明一个**给不出来**的能力 = 承诺一个不存在的交付 |

**规则 26 是通用的，不是给 `stream` 开的特例。**
它读的是一张**数据表**（已实现能力集），不是一条硬编码的 `if (stream)`。
Stream 契约落地那天，**改的是那张表，不是规则**。

### 1.6 `stream` 的处置 —— 两份意见**唯一**的真分歧

| 意见 | 主张 |
|---|---|
| Codex | **从契约词表里删掉**。实现层根本没有 stream，词表里留一个**恒假**的能力，等于允许「声明了但永远给不出」——与 `unavailable ≠ 0` 是同一条原则的反面 |
| GLM5.3 | **词表保留**，但**校验器硬报错**。它是真实的板级能力，将来 Stream 契约落地后直接用，**不必现在删词**；而且「没实现就别声明」靠自觉守不住——下一个写包的人会照抄 `spec/02:25` 的示例 |

**拍板取 GLM 的路线：词表保留 `stream`，校验器硬报错（规则 26）。**

**理由**：

1. **Codex 的顾虑已经被满足**。他要防的是「声明了但永远给不出」——
   硬报错让声明**变成一个错误**，而不是一个静默的谎。
   顾虑成立，处置不必是他那一种。
2. **删词要还回去。** Stream 契约迟早落地（`docs/09` §三① 已登记为缺口），
   那一次**才**升 `apiVersion`。为一个还没写的功能先动契约词表，
   等于把「将来要改的东西」提前改掉了。
3. **`stream` 这个词本身是有意义的**：「这块板能推连续流」是**板级事实**
   （板子确实有视频管线）。缺的**不是词**，是**运行时交付**——
   而运行时交付的缺失有它自己的登记处（`docs/09` §三①）。
4. **硬报错比删词更能指路**。错误信息可以指向缺口登记处：
   「`stream` 尚未实现（Stream 契约缺失，见 `docs/09` §三①）」——
   下一个人撞到的是一块**指路牌**，不是一个**悄悄的洞**。

**代价（写清楚）**：词表里躺着一个**当前无人能交付**的词。
靠**规则 26**兜住——而规则 26 是有测试守着的（M3 的校验器单测）。
**如果哪一天规则 26 被放松了，这条决定就失效了**——所以规则 26 有单测。

### 1.7 板型包本身的改动

`profiles/boards/rk3588-atk/board.yaml` 的
`requires.capabilities` 从 `[shell, exec, stream, files]` 改为 `[shell, exec, files]`。

**这不是「这块板不能推流」**——是「**本产品 v1 还没有 Stream 契约**，
这个包不承诺它」。等 Stream 落地，声明再加回来。

## 二、决策 ② · 没有回读的动作怎么声明

### 2.1 结论

**加 `readback: { kind: none }` 一种写法**，配三条闸门。

**选项 C（用 `verify` 跑一条恒真的命令，如 `true`）明确否掉**：
它把「没验证」伪装成「验证过了」——
`verify` 的语义是「验证板子进入了目标状态」，而 `true` 什么都没验证，
却让调用方以为验过了。**这正是这份契约一路在防的事**，
和 `unavailable ≠ 0` 是同一个道理。

### 2.2 形状：**只用一种拼法**

`docs/14` 给了两种拼法（`readback: {kind: none}` **或** `verify: {kind: none}`）。
**必须只留一种**，否则校验器要同时认两种表达同一件事的写法。

**取 `readback: { kind: none }`**，理由：

- `readback` 的形式**已经是封闭枚举**（规则 23），加一个成员只改一处；
- `verify` 在 §4.5 是**另一个块**（有 `command` / `timeout_ms` / `expect`），
  给它加 `kind: none` 会让「没有回读」有**两种**写法；
- 语义上 `none` 是「**这个动作没有可观测状态**」——
  这是 **readback 形状**的事实。

**契约里要明写**：`verify` 块**不允许** `kind: none`；
没有回读就写 `readback: {kind: none}`。

### 2.3 结果怎么标：**`ok: true` + `verified: false`**

`docs/14` 说「契约 §2.1.1 的 reason 封闭枚举要加一个码」——**指错了表**。

`spec/01` §2.1.1 的 `reason` 是 **tag 的**原因码；
**动作**结果的原因码在 **`spec/04` §2.4**
（`readback_mismatch | denied | not_found | needs_confirmation | timeout |
invalid_params | failed | unsupported_transport | guard_exceeded`）。**两张表，别混。**

tag 的五态是 `ok / stale / unavailable / error / pending`——
**`unverified` 不是 tag 状态**，加进去会污染所有 tag 消费者（卡片 widget 的渲染分支）。

**取 `ok: true` + 一个独立的布尔字段 `verified`（默认 `true`）：**

| 表达 | 问题 |
|---|---|
| `ok: false, reason: "unverified"` | 命令**确实执行了、效果也确实有**（点 LED 亮了）。报失败是**另一种撒谎** |
| `ok: true` 什么都不说 | 把「没验证」藏起来——**这正是选项 C 被否掉的同一个毛病** |
| **`ok: true` + `verified: false`** | **唯一同时避开这两种撒谎的表达** |

**UI 口径写死**：`verified: false` → 卡片**必须**显示「**已执行，未验证**」，
**不得**显示成「已生效」。
这直接对应 `spec/02` §4.1 已有的那句「命令已发出，未确认生效」。

> **不预设 O14。** O14（卡片 API 错误码与 tag reason 是否共用一套）**还开着**。
> `verified` 作为独立布尔字段**不预设** O14 的答案——别提前统一。

### 2.4 三条闸门

1. **只允许 `danger: reversible`**——`destructive` 仍禁止 `none`。
   > 若某个 destructive 动作真的没有可观测后态，**唯一的合法路径是加一条 `verify` 命令**
   > （如 `test -e /tmp/marker`），这正是 §4.5 的 `verify` 存在的意义。
   > 连 `verify` 都做不到的动作，**v1 就不许声明**——这是刻意的、说得出口的限制。

2. **`consequence` 必填且非空。**
   `docs/14` 写「声明了用户可见后果」——那是自然语言，**校验器没法执行**。
   落成机械可查的字段：

   ```yaml
   readback:
     kind: none
     consequence: "点亮板载 LED 约 1 秒后熄灭"   # 必填，非空
   ```

   **不写 `consequence` 就过不了校验**——与「必须显式写 kind」同一力度。
   它是**给人看的**：授权界面把这句话原样显示出来，
   用户批准的是「我知道它会做这件事」。

3. **逐动作 warning + 审计可追。**
   校验器对**每个**用 `none` 的动作记一条 warning（不是静默通过）——
   想偷懒跳过回读的包作者会立刻看到一串警告。
   **这个可见性就是主要防线**（`unavailable ≠ 0` 防的是「把没读到当读到」，
   这条防的是「把没验证当不用验证」，同一个道理）。
   同时：审计日志要能一眼看出「未验证」（`spec/02` §5.4），否则事后无法追责。

### 2.5 顺手补一个洞：**每个动作都必须声明 readback**

`spec/02` §4.1 正文写的是「**每个**动作必须声明怎么回读」，
但**校验规则里只有第 15 条管 destructive**——
**一个 `reversible` 动作不写 `readback` 也能过校验**。
这是真洞：**闭环静默断掉**。

**新增规则 27**：

> 每个 action 必须有 `readback` 块，其 `kind` 属于
> `{file_equals, command_ok, verify, none}`（不写 `kind` 时按形式 1 读 tag）。
> **`none` 是唯一合法的「我没有可回读状态」的写法——不许用「不写」来表达同一件事。**

这一条同时把 2.1 的洞堵上：`none` **必须显式**，漏写就是校验错误。

## 三、决策 ③ · 剩下的两个动作

### 3.1 结论

**两个都不补。`npu.governor.set` 与 `debugfs.mount` 都不进板型包。**

**但 `docs/14` 给的两条理由里，有一条被实测证伪，必须换掉。**

### 3.2 我的理由①**错了**——实测 E3

`docs/14` 说：

> 那个 `governor` 节点是 rkdevfreq **全局**的，
> 写它会影响 dmc/vop2/venc 等其他模块。

**实测 E3：不对。** 写 `fdab0000.npu/governor` 期间，
`dmc/governor` **始终是 `dmc_ondemand`**（两次独立观测）。
**当前值是每节点独立的。**

Codex 说得很准：`available_governors` **是**全局的（E1：NPU 节点与 dmc 的列表完全相同），
但那是**可选值列表**共享，**不是当前值**共享。
`docs/14` 把这两件事混成了一个。

**结论不变**（不该做），但**理由的性质变了**：
副作用不是「波及其他模块」，而是「**把这个 NPU 节点切到一个可能不该切的档**」。

### 3.3 真正该用的理由（比原理由硬得多）——实测 E4

**E4：向 NPU 节点写 `powersave`，写调用挂死在内核里。**

```
/proc/<pid>/wchan = devfreq_monitor_stop
进程进 D 状态，kill -9 无效
此后该节点的所有 governor 读写与 trans_stat 读取全部阻塞在 D 状态
```

**只有重启能恢复。** 同顺序先跑过一次没挂 → **是竞态，不是必现**。
但**一次就够把板子锁死**。

> **所以 `npu.governor.set` 不能做的理由不是「我们不确定它的语义」，
> 而是「实测它会把板子锁死、且不可恢复」。**
>
> 这对「agent 能触发的动作」是**不可接受**的：
> agent 写错一个值 → 板子失去 devfreq 控制 → 只能靠物理重启。
> **在找到并修掉这个内核侧死锁之前，`npu.governor.set` 绝对不能进板型包。**

**边界要写清楚（免得误伤）**：

- 这条风险覆盖 **devfreq 类节点**（`fdab0000.npu`、`dmc`、`fb000000.gpu`…）。
- **现有的 `cpu.governor.set` 走的是 cpufreq 的 `scaling_governor`**（不同驱动），
  **实测干净**（E6：写 `ondemand` → `schedutil`，rc=0、无挂死、读回一致）。
  → 这条动作**此前从未被真机验过**，本轮验过了，**可以写进 `docs/02` §3.1**。

### 3.4 `available_governors` 给不出正确的枚举 —— E1 / E2 / E5

- **E1**：`fdab0000.npu` 与 `dmc` 的 `available_governors` **完全相同**（9 个值）——
  这是 rkdevfreq **类级的全局并集**，对单个节点**没有信息量**。
- **E2**：向 NPU 节点写 `dmc_ondemand`、`powersave`：**rc=0、无任何报错、读回原值**——
  节点**接受列表里的任意值**。列表不会告诉你哪个值对这个节点有意义。
- **E5**：`cur_freq` 权限位 **`-r--r--r--`**（root 也写不进去）——
  `userspace` governor 在这块板上**没有可用语义**：
  它的含义是「由用户态设频率」，而用户态没有写权限。

→ **O15 的答案只能是 `rknpu_ondemand`（v1 就这一个）。**
要加别的档，得先有一个「这个节点**真正实现了**哪些 governor」的依据——**现在没有**。

（`npu.governor` 按 O7 走 `custom`，所以这个枚举当前**没有消费者**——
但结论要记下来，免得将来有人去挑那 9 个值。）

### 3.5 `debugfs.mount` 不做，理由换四条

1. **这块板默认已经挂着**（E7：`/proc/mounts` 有 debugfs 行，`rknpu/load` 读得出 0%）
   → 动作在这块板上是**空转**。
2. **引导路径本来就通**：契约 §2.1 已经把「debugfs 没挂」建模成 `unavailable`，
   并在 `detail` 里给了修复提示（`mount -t debugfs debugfs /sys/kernel/debug`）。
   **契约早就假设它可能没挂。**
3. **挂载是系统级改动**，不是「这块板的能力」；真要做也该是**人类在板子上做**，
   不是 agent 触发。
4. 真要加就得动**危险地板表** = 改契约 = 升 `apiVersion`——为一块不需要的板子不值。

> **顺带留一个事后草图**（进 `docs/06` C4，**账要留，事不做**）：
> 若将来真要加 `debugfs.mount`，回读走 **`/proc/mounts` 的 debugfs 行**
> （挂载成功后该行必在），而不是「挂上之后才有值」的 `npu.usage`——
> 后者是**自指**。这条路线是通的，只是今天不值得做。

### 3.6 C1 的取舍：**选 `cur_freq`，现在定**

`/sys/class/devfreq/fdab0000.npu/cur_freq` 实测存在，读出 `1000000000`，
与 `/sys/kernel/debug/rknpu/freq` 一致。比 `rknpu/freq` 多一条理由：

**`cur_freq` 是纯只读观测，不碰 governor 写路径——也就是没有 E4 那种死锁风险。**

依赖更少（sysfs 下 always available）、语义更干净（就是当前频率）、
风险更低（只读）。**直接定，不必再等。**

### 3.7 代价

板型包里只有**两个 reversible**（背光、调频策略）+ **一个 destructive**（重启）。
`destructive` 的样本只有一个——**够**：规则 15 的校验逻辑用 fixture 里的**合成包**测
（`fixtures/validator/illegal-floor-downgrade.yaml` 已经是这个模式）。
**真实包保真，合成包保规则覆盖**，两不耽误。
