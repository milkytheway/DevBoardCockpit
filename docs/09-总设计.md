## 一、整体架构

### 1.1 一张图

```
┌─────────────────────────────────────────────────────────────────┐
│  宿主 AI Agent（Claude Code / Codex）                            │
│  感知 → 写卡 → 热插拔 → 自测 → 迭代                              │
└───────────────┬─────────────────────────────────────────────────┘
                │ MCP 契约（AI ↔ GUI）：读状态 / 写卡片 / 触发动作
                │ 传输：HTTP 回环 + 发现文件 + bearer token
┌───────────────▼─────────────────────────────────────────────────┐
│  Electron main（设备、契约执行、MCP、卡片注册表）                 │
│  hal/ 连接层 │ tags/ 位号层 │ actions/ 控制面 │ cards/ │ mcp/     │
└───────────────┬─────────────────────────────────────────────────┘
                │ IPC（invoke/handle + 事件推送）
┌───────────────▼─────────────────────────────────────────────────┐
│  Electron renderer（只画，不碰设备）                              │
│  layout/ │ cards/ 卡片宿主 │ terminal/ xterm.js │ panes/         │
└───────────────┬─────────────────────────────────────────────────┘
                │ postMessage 白名单（无同源、无网络）
┌───────────────▼─────────────────────────────────────────────────┐
│  卡片 iframe：sandbox="allow-scripts"                            │
│  一个目录 = manifest.json + 免构建 ESM 视图                       │
└─────────────────────────────────────────────────────────────────┘

磁盘：%LOCALAPPDATA%/DevBoardCockpit/（用户可写：cards / profiles）
      <app>/（内置只读：cards / profiles）· 合并时用户优先
      fixtures/（真机样本）
```

### 1.2 两条总线

整个产品只有两条契约，其余全是实现细节：

| 总线 | 连接谁和谁 | 契约 | 回答的问题 |
|---|---|---|---|
| **tag 契约** | 卡片 ↔ 板子 | `spec/01` + `spec/02` | 板子现在怎么样、怎么改它 |
| **MCP 契约** | AI ↔ GUI | `spec/04` | 这个软件现在有什么、你能替我做什么 |

**为什么是对称的**：宿主 AI 同时是这两条总线的读者。
它读 tag 契约去理解一块它没见过的板，读 MCP 契约去理解一个它没见过的软件。
所以两份契约都必须**由 AI 自己能读懂**——格式要自带解释力。
这正是它们和普通配置文件的区别。

### 1.3 依赖方向只有一条

上层依赖下层，下层不知道上层存在：

- 卡片不知道板子是谁，只认识 tag 名字
- 板型包不知道卡片是谁，只声明「我提供哪些 tag、怎么产生、能接受哪些动作」
- 连接层不知道上面有谁，只提供「能读文件、能执行命令、能推流」

**这条方向一旦被破坏，「支持新板 = 提交一个包」「N 张卡 × M 种板 = N+M 个文件」就不成立。**

## 二、核心机制（每一条都有出处）

这六条是整个设计的承重墙。它们不是设计偏好，是从真机踩坑里长出来的。

### 2.1 语义位号：名字不含板型

`cpu.usage` 在 RK3588 上、在 RK3568 上、在全志上，含义必须一致。

> **为什么**：这是「N+M」的前提。卡片只认名字，板子差异住在板型包里。
> 前身工程做不了这件事——板型路径硬编码在 `metrics.py` 里，换一块板就得改核心代码。

核心词表的**机器可读权威**是 `docs/spec/data/tag-vocabulary.yaml`（21 条）；
`spec/01` 里的表格是它的渲染结果；实现层也从它生成。三份由对拍测试保证一致。

### 2.2 五态：`unavailable ≠ 0`

一个 tag 的读数**永远是「值 + 状态」**，不是裸数字：

| 状态 | 含义 | 卡片怎么显示 |
|---|---|---|
| `ok` | 有值，且在刷新周期内 | 正常显示 |
| `stale` | 有值，但上次刷新失败，值可能过时 | 显示值 + 「已过时」标记 |
| `unavailable` | 这块板不提供这个 tag，或该资源此刻不在 | 显示「不可用」，**不显示数值** |
| `error` | 应该能读，但读取或解析失败 | 显示错误 |
| `pending` | 还没建立起基线（如需两次采样做差） | 显示「等待」 |

> **为什么**：继承前身工程做对的一件事——读不到的量是 `None` 而不是 `0.0`。
> 一块够不到的板和一块没事干的板，绝不能长得一样。
> 显示 0% 负载的按钮，可能其实没连上。

### 2.3 poll group：一次往返

一个 group = 一次往返 = 一个刷新周期。同组所有 reader 合成一条命令取回，每个 reader 用自己的 marker 隔开。

> **为什么**：两条实测事实打架——每文件一次 `adb shell` ≈ 30ms 且 fork 的 CPU 时间会污染 `/proc/stat`，
> 而 `/proc/stat` 必须每秒采（占用率是两次采样做差）。
> 快的东西和慢的东西分开取。

配套：**同一连接上的一次往返必须互斥**（采样与动作共用通道，串口只有一根线）。
动作优先；采样因让路而错过本周期就跳过，不补发。

### 2.4 回读闭环：驾驶舱 vs 遥控器

```
用户点击 → 发命令 → 回读真实状态 → UI 以回读为准
```

按钮显示的是板子的**真实状态**，不是你上次点的意图。
回读不符时显示「命令已发出，未确认生效」，**不允许乐观显示成已开启**。

> **为什么**：这是愿景里的「技术命门」。遥控器按你按了按钮来显示，驾驶舱按板子实际在做什么来显示。

### 2.5 危险地板：信任 agent 但不让它越权

板型包自己声明危险等级，但有一张**固定的操作模式表属于契约**：
重启 / 刷写 / 格式化 / 裸写块设备 / 删根 / 清防火墙——命中即按 `destructive` 处理，
**不管包怎么声明**。

三条机械闸门（都是本轮评审补上的，缺一条承诺就不成立）：

| 闸门 | 做什么 | 出处 |
|---|---|---|
| 参数编码 | 字符串参数单引号包裹 + 转义 `'`；整数按字面量；枚举取 `values` 里的值 | `spec/02` §4.6 |
| 地板匹配 | 匹配**解析后的 argv**，不是命令模板；词元相等而非子串；路径先规范化 | `spec/02` §5.2.1 |
| 参数域 | 授权 = 动作 id + 可选 `guard`；`guard` 只能缩小不能扩大；超域走单独确认 | `spec/02` §5.5 |

> **为什么**：这三处本来都是断的。
> 字符串参数原样拼进 root shell（`--model 'x; reboot'`）、
> 地板匹配模板导致注入的 `reboot` 不在模板里、授权只到动作 id 让「批准调到 30」变成「批准调到 0」。

### 2.6 扩展点：用户目录 + 内置目录，同名用户优先

三个扩展点——**卡片、板型包、连接 profile**——走**同一套**规则：

| 扩展点 | 用户目录（可写） | 内置目录（只读，随应用分发） | 同名时 |
|---|---|---|---|
| 卡片 | `%LOCALAPPDATA%/DevBoardCockpit/cards/` | `<app>/cards/` | **用户优先** |
| 板型包 | `%LOCALAPPDATA%/DevBoardCockpit/profiles/boards/` | `<app>/profiles/boards/` | **用户优先** |
| 连接 profile | `%LOCALAPPDATA%/DevBoardCockpit/profiles/targets/` | `<app>/profiles/targets/` | **用户优先** |

> **为什么这条要三个扩展点统一**：前身工程最顺手的加板路径是
> 「把 JSON 丢进用户目录，**重启，板子出现**」——零代码、零 git、零发版。
> 新工程如果只有卡片这一条路保留用户目录、板型包只读仓库，
> 用户丢个包进去发现没反应——**同一工程两个扩展点待遇不一致**，是最容易让人失望的地方。

### 2.7 卡片沙箱：两件独立的事

| 防护 | 防什么 | 手段 |
|---|---|---|
| 代码沙箱 | 坏卡搞垮工作台、偷读宿主文件 | iframe + 白名单 API + 无 Node 集成 + **宿主注入的 CSP**（`connect-src 'none'` 真断网） |
| 动作权限 | 卡片乱写板子 | `permissions.write` + 分级 + 装卡授权 + 参数域 + dry-run + 破坏性二次确认 + 审计 |

> **为什么必须分开**：沙箱只保证卡片**搞不垮工作台**，不保证卡片**不会乱动板子**。
> 混成一个「权限系统」的结果是既防不住崩溃的卡，也拦不住越权的卡。
>
> **CSP 不能省**：iframe 的 `sandbox` 属性**不限制网络**——不给 same-origin 只是拿不到宿主的源，
> 卡片在自己的不透明源里照样能 `fetch` / `WebSocket` / `sendBeacon`。
> 而不给 same-origin 的 iframe 里 `localStorage` 会抛 `SecurityError`，
> 所以「卡片可写自己的命名空间」必须由宿主的 `cockpit.storage.*` 兑现。

### 2.8 板型包与卡片：创作面 vs 权限面

**卡片是 agent 的创作面，装卡不审批。板型包是设备的权限面，装包要人确认。**

理由是一个具体的洞：**板型包的 reader（`exec_regex` / `script`）能在板子上
执行任意命令，而危险地板只管动作。**
「包一律生效 + agent 可以写包」合起来，就是一条绕过「破坏性动作要人确认」的通道——
一个能执行任意命令的 reader **就是**裸命令通道，只是换了入口。

所以：

| | 谁能写 | 生效条件 |
|---|---|---|
| 卡片 | agent | 直接生效（但受动作分级约束） |
| 板型包 | agent 可起草 | **人确认后生效**，确认界面展示「会执行哪些命令、声明哪些动作、多危险」 |

升级包若新增 `destructive` 动作或扩大命令权限，**必须重新确认**。

> **这条是两份独立设计共同指出的，两轮评审都没发现。**
> 它把 `SPEC-D12`（板型包一律生效）**收窄**了——
> 生效的是「人确认过的包」，不是任何包。

### 2.9 TagStore：读数的唯一汇点

**所有读数都写进 TagStore，再从 TagStore 分发。**
不管数据来自轮询还是将来的推送，进 TagStore 之后再出去。

| 是 | 不是 |
|---|---|
| TagStore 是板子状态的**唯一一份** | UI 自己缓存一份、卡片自己缓存一份 |
| 卡片订阅 TagStore | 卡片订阅「某个连接」 |
| 质量由 tag 引擎产生 | 卡片 / UI / MCP 改写质量 |

**为什么**：一块状态有多个副本，就等于没有真相——
两块卡片显示不同数字，用户无法判断哪个是真的。

**每个读数带 `seq`**（同一 tag 内单调递增）：异步推送必然乱序，
渲染层按 `seq` 丢弃过期的旧值。

### 2.10 链路仲裁：动作与回读不可拆分

半双工线（串口）上，一次往返是**独占**的。四级优先级：

| 级 | 事务 |
|---|---|
| 1 | `action-verify`（动作的**执行 + 回读**，不可拆分） |
| 2 | `manual-refresh` |
| 3 | `card-sampling` |
| 4 | `diagnostics` |

**回读若被采样插队，读到的可能是别的命令的输出**——
「回读不符」就成了假阴性，驾驶舱会显示错的真实状态。

终端活跃时托管采样暂停，受影响的 tag 转 `stale`（带 reason）——
**停采必须如实反映成质量，不能静默**。

## 三、这套设计撑得住你的想法吗

按你的三层产品设想逐条对照。

### 3.1 撑得住的部分

**第一层「统一工作台」**——架构上有明确位置。终端与文件互传走连接层（串口/ADB/SSH），
这层是稳定的，因为终端是成熟领域，有 VS Code 同款方案可抄。

**第二层「可插拔卡片系统」**——这是产品的差异点，架构给了它完整的支撑：
- 卡片即文件 → agent 写卡片用它最擅长的方式（编辑文件）
- 热插拔 → 改完立刻看到效果，agent 的「写 → 看 → 改」循环才成立
- 沙箱 → 坏卡不拖累宿主，agent 写卡才敢放手
- 位号 + 板型包 → 换板子不用改卡

**第三层「AI 协作」**——MCP 契约就是为它写的，且刻意做成**对称**的：
AI 既是 tag 契约的读者（理解板子），又是 MCP 契约的读者（理解软件）。
协作回路的关键是「agent 的眼睛」：`validate_card` + `get_card_runtime_log` 两条工具，
没有它们，agent 只能盲写。

**双层安全**——分成两件独立的事，各有机制，各有出处。

### 3.2 撑不住或未定的部分

诚实说四处。前两处是**架构缺口**（契约层缺东西），后两处是**语义未决**（两边说法不一致）。
第三处（多板）本轮已解开，不再算缺口。

**① Stream（连续流）契约缺失——最大的架构缺口，但接口已预留。**
你的愿景里有 HDMI 采集卡、有「摄像头 → NPU 推理 → 显示输出」的链路，
但 `spec/00` 里 Stream 只有一句「目前只有一个占位定义，没定死」。
板型包已经声明 `capabilities: [..., stream, ...]`，契约却没有对应的东西。

**接口层已经预留**（ADR-D21 / `SPEC-D20`）：取数侧统一为 Source 接口，
`kind ∈ {poll, push}`，v1 只实现 poll、push 留空壳。
所以将来补 Stream **不用返工所有卡片 API**——但业务契约仍然要定。

**② capability 词汇表缺失。**
`shell` / `exec` / `stream` / `files` 这四个词到处在用（板型包声明、
UI 降级规则依赖、旧工程也有），但**没有一份封闭的词汇表**说明每个词
什么意思、谁有权声明它。结果是「不支持 `files` 的目标禁用文件浏览器」
这条降级规则没有契约依据——它靠的是旧工程的继承结论，不是契约。

**③ 多板语义——已解开（不再算缺口）。**
契约层原本**隐含全局单连接**（manifest 没有字段指明这张卡连的是哪块板），
设计层按连接隔离（订阅键是 `(connectionId, tag)`）。现在补上了：
`spec/03` §7.8 规定「卡片 API 以宿主注入的连接上下文为隐式作用域，
tag 名在卡片 API 内始终不带前缀」，绑定发生在**布局层**（`(cardId, connectionId)`）。
**前缀问题被隔离在宿主的解析层**，将来加多板不必改卡片 API。

**④ 愿景的能力层图与契约冲突。**
愿景写「控制面（GUI→板）：Action / **Command**」，而契约里**根本没有 Command 这个概念**
——`spec/02` §4.1 明写「如果控制面只有『发一条命令』，那它就是遥控器，不是驾驶舱」，
即 `Command` 正是这个设计要**避免**的东西。契约收敛成只有 `Action` 是对的，
但愿景是上位约束，它自己写着「与本文冲突的设计必须先改本文」——
所以这张图需要按契约更新。这是**文档表述冲突，不是架构问题**。

**⑤ 连接 profile 没有 schema。**
你已决定本轮不补（O5），我同意——它不是架构级阻塞。
但 `options` 里那些字段（`pty`、`commands`、`serial`）目前全靠猜，
实现时会磨擦。

> ①② 已写进 `docs/spec/00` §七「待办与风险」，④⑤ 对应 `docs/05` 的 O10/O12/O5。
> ③ 已由 `spec/03` §7.8 解开。

### 3.3 一个不算缺口但要知道的事实

**契约层现在是 2800 行、6 个文件，比一周前厚了不少。** 骨架没变——
两条总线、三个层、四个关键决策，从第一天到现在没动过。
变的是边角，以及把两轮评审发现的空洞补上。

「越来越看不懂」这个感受是**信息密度一次性升高**造成的，不是结构性问题。
结构自始至终是简单的。

### 4.3 两轮评审的综合处置

两轮评审（`docs/07` **78 条**、`docs/08` **39 条**，**合计 117 条发现**）已逐条回源核查。
它们的性质差别很大，处置方式也不同——**不是所有发现都该变成设计改动**。

分类判据（可复核）：

| 类 | 判据 | 条数 |
|---|---|---|
| **A 结构缺口** | 需要改契约/架构的「形状」：新增字段、接口、目录、分层，或缺失一整块 | 14 |
| **B 语义与机制** | 需要定义「是什么 / 怎么算 / 怎么判」：状态、编码、匹配、粒度、生命周期 | 59 |
| **C 表述与卫生** | 只影响引用、计数、编号、措辞、样本、缓存残留 | 44 |

> 合计 117，与两份报告的编号总数一致（**可复跑**：
> `python3 scripts/audit-review-findings.py` 会统计两份报告里 `### Pn-n` /
> `**Pn-n**` / 表格行三种形态的编号，去重后 07 有 78、08 有 39，
> 并校验三类互斥且求和 = 117）。

| 类 | 处置方式 | 例子 |
|---|---|---|
| A | **按用户拍板落地**，写进契约或 ADR | 传输定 HTTP、两档分级、`cockpit.storage.*`、用户目录 + 内置目录合并 |
| B | **全部落地**，写进契约或 ADR | CSP 断网、参数编码、地板匹配 argv、`guard` 参数域、往返互斥、`verify` 回读形式 |
| C | **就地修正，不进设计** | 章节号引用错、计数错、编号撞车、`mem.total` 笔误、`.pytest_cache` 残留 |

**明确不取的**，三类：

| 不取 | 理由 |
|---|---|
| 07 P1-9「连接 profile 本轮补 schema」 | 用户已定**本轮不补**（O5）。评审认为该补是对的，但不推翻用户的决定——记为待办 |
| 07/08 中「把 X 也写成三档 / 加档位」类的建议 | 与「契约是权威」冲突。契约已定两档，评审的替代方案不取 |
| 08 §8.4 对 C1「改法本身有道理、只需追认」的判断 | **不认同**。`load` 里的 `@freq` 是「duty 在哪个频率上测的」，不是当前频率——语义被冒名了。所以按 T-6 **回滚**而非追认 |

**分歧的处理**：两份评审有 4 处实质分歧（`docs/08` §8.4），全部按用户拍板收敛——
传输定 HTTP、分级以契约为准、C1 回滚、卡片网络与存储一起解决。

**这一轮的补漏**：把 117 条逐条回源核查（脚本核对「是否已落地」），发现 7 条遗漏，
本轮补上：

| 遗漏 | 补在哪 |
|---|---|
| `ATK-DLRK3XXX` 死字面量（`substring` 匹配会命中同系列其它板） | 板型包 `match.models` 删除 |
| `MemAvailable` 两个数字冲突 | `docs/02` 标注「不同时刻，不是矛盾」 |
| probe 命令行两套 | 统一为 `--pack` + 传输参数，以 `docs/04` §12 为准 |
| `spec/04` 与 `docs/04` 把校验清单指向 §八（实为 §九） | 两处改正 |
| `list_data_sources` 在设计层降了粒度 | `docs/04` §9.2 补明 reader 粒度 vs tag 粒度 |
| capability 词汇表缺失 | 记入 `docs/spec/00` §七（O10） |
| 多板语义未写进契约 | 记入 `docs/spec/00` §七（O11） |

另有一项**结构性的补漏**：用户目录 + 内置目录合并，此前只有卡片这一条路有，
板型包与连接 profile 没有——前身「丢个 JSON 重启板子出现」的零代码路径断了。

### 4.4 三份独立设计的对照与取舍

除了两轮评审，另有**两份独立设计**（`docs/10-独立架构设计-GLM5.3Flash.md`、
`docs/10-独立设计-deepseek-v4.1-flash.md`）在 contract 层之上给出了各自的落地方式。
两份都**未读** `docs/04` 与两轮评审，独立得出——这正是对照的价值。

#### 三者的关系

| | `docs/04`（Codex） | `docs/10` GLM 版 | `docs/10` deepseek 版 |
|---|---|---|---|
| 定位 | 与契约绑定的实现层设计 | 契约的一种落地方式 | 契约的一种落地方式 |
| 与契约的关系 | 逐条对齐 | **逐条对齐**，冲突处让契约赢 | **多处冲突**（见下） |
| 体量 | 652 行 | 约 460 行 | 1477 行 |

**GLM 版与现行契约基本同构**——它的每个章节都能回答「契约的哪一行由它兑现」。
**deepseek 版与契约有 14 处实质冲突**，且多数冲突方向是**倒退**：

| 冲突 | 契约现状 | deepseek 版 | 裁决 |
|---|---|---|---|
| 危险地板 | 契约级地板表 + 按解析后 argv 匹配 | **完全没有地板机制**，只靠包自声明 | **不取**——地板是 D12+D13 成立的前提 |
| 参数编码 | 单引号包裹 + 转义 + 运行时二次校验 | 自造 `shell_escape`，示例命令把重定向/多命令塞进一个 shell 串 | **不取** |
| `guard` 参数域 | 契约有，且只能缩小 | 无此概念 | **不取** |
| 采样单位 | poll group（契约规则 17/18 强制） | 改为 Reader 各自带周期 | **不取**——动它要升契约版本 |
| sample/tag 两命名空间 | 契约的核心机制之一 | 塌成 `produces: [tag...]` | **不取** |
| 卡片 API 命名 | `cockpit.*` | 自造 `dbc.*`，且缺 `notify`/`subscribePattern`/`degradation` | **不取** |
| MCP 工具集 | spec/04 已定稿 17 个工具 | 自造一套，缺 `confirm_action` 等 6 个 | **不取** |

> **裁决原则**：契约是权威且已追认（ADR-D15）。
> 独立设计是**提案**，不是替代品——冲突时契约赢，
> 这两份文档自己在开头也都这么声明。

#### 实际取用的（7 条）

| 来源 | 取了什么 | 落在哪 | 为什么取 |
|---|---|---|---|
| 两份共同 | **板型包授权**（创作面 vs 权限面） | ADR-D20、`spec/02` §5.6、`spec/04` §2.4.2 | 一个两轮评审都没发现的真实漏洞 |
| GLM-D1 | **Source 双态接口**（poll / push），v1 只实现 poll | ADR-D21、`docs/04` §5.4 | 补 Stream 缺口而不必现在定 Stream 契约 |
| GLM-D2 | **连接上下文绑定**：manifest 不带连接，绑定在布局层 | ADR（§9.4）、`spec/03` §7.8 | 直接解掉 O11 的多板语义问题 |
| GLM-D3 | **reason 封闭枚举 + detail 自由文本** | `spec/01` §2.1.1 | C5 的具体答案；AI 要能程序化消费 |
| GLM-D4 | **地板压包负样本**进验收 | `fixtures/validator/illegal-floor-downgrade.yaml` | 「地板是下限、校验器是第一道闸」要两验 |
| 两份共同 | **TagStore 唯一汇点 + `seq`** | ADR-D22、`docs/04` §5.3 | 单一真源；异步推送必然乱序 |
| deepseek | **安全测试清单 + 失败注入矩阵** | `docs/04` §12.1/§12.2 | 安全承诺要有攻击性用例兜底 |

另有一条**否决项**要记下来：deepseek 建议「destructive 首次调用默认 dry-run」。
契约已在 ADR-D17 里把「默认 dry-run」改成「二次确认」——
因为 dry-run 的返回值不是执行结果，确认完还得再跑一次，流程自相矛盾。
**保留契约的写法。**

#### 一条必须说的：deepseek 有一处比契约更好

它的 `D4`「动作成功只由 verify 回读裁决，不由调用方声明」与契约一致，
但它加了一条契约没有的：**`verify: none` 必须显式，且结果标 `unverified`**。

契约现在只说「destructive 动作必须有 readback 或 verify」，
没说「确实无法验证的动作怎么办」。这个缺口是真的——
纯展示类动作（比如点亮一个 LED）可能真的没有可回读的状态。
**已记入待决（O13）**，不在本轮擅自改。

### 6.3b 后两轮复评（`docs/12`、`docs/13`）

前两轮（6.2、6.3）修完之后，又来了两轮复评：**一份专看 renderer**（`docs/12`），
一份看整体（`docs/13`，`S-01`~`S-10`）。**又查出了 10 条**，其中 3 条严重：

| # | 缺陷 | 后果 |
|---|---|---|
| **S-01** | 构建产物自检会被**陈旧产物**骗过 | 构建真的产出了 ESM preload，自检仍打印「✓ 通过」——**唯一的构建期守卫是摆设** |
| **S-02** | 变异测试把**环境故障**读成守卫失效 | 4/20 报「形同虚设」，其实是原生模块架构不对——**两个方向都会骗人** |
| **S-03** | profile 的 `pty` 覆盖**到不了运行时** | 用户改 `pty:false` → 终端完全不可用，而 UI 侧报 false、运行时按 true 走——**两个能力位来源互相矛盾** |

**S-03 尤其值得记**：上一轮把「两份能力位实现」合并了，**但运行时压根没走那一份**——
合并了不等于用上了。上一轮的变异 **M12 只守住 UI 那一半**。

另修：上传的远端目标恒为 `/`（本机 `copyFile` 到目录必挂）、远端树进不去目录、

关闭按钮键盘不可操作、隐藏标签把极小尺寸报给远端、下载同名文件静默覆盖。

**pipe 模式提示符的排错**（`docs/12` N-1 / `docs/13` S-04）：
提示符原来在**提交的那一刻**就画出来，而远端的输出**再走一次往返才回来**——
于是输出落在「下一个提示符」后面，读起来像是那个提示符的输出。
改成**用户开始打下一条命令时才画**，顺序就对了。

> **没做的**：旧工程把提示符放在**独立输入行**里（不混进输出流），
> 那是从根上避免输出与输入行互相干扰。
> 本工程仍是「回显进终端流」——**远端输出若与用户正在输入的一行撞上，仍会插进去**。
> 这是已知差距，要换架构留给计划 2 拍板。

### 6.4 教训：三条

1. **假实现会盖住协议 bug。** 原来的假串口是「按契约编好的答案」——
   它回显的内容形状恰好就是解析器期待的形状，于是 C2 这种「协议形状错了」的 bug
   在测试里永远绿。现在假串口按真实行为建模（回显每一行 + 执行），C2 立刻暴露。
2. **mock 同步、真实异步，同样会盖住 bug。** C3 就是这么漏过去的。
3. **「测试通过」和「测试能抓住这个 bug」是两件事。**
   变异测试查出 3 条 Critical **修了但没锁住**；现在 **23 个变异**，
   每个改坏后必须变红，**且红的原因必须对**（编译失败不算守住）。
   而**「守卫失效」与「环境跑不起来」也必须分开**——
   混在一起报，开发者会得出**完全相反**的结论。

> **前两条是「写得不够小心」，第三条是「验证器本身也要被验证」。**
> 一个只在 Linux 上跑得起来的验证器，在本工程的目标平台上等于没有。

### 7.3 一次教训

整支评审查出的 6 条 Critical，**没有一条是「沙箱里没硬件所以没法验证」那类**——
全是读代码就能发现的逻辑缺陷。它们漏过去的共同原因有两个：

1. **假实现建模了结论而不是行为。** 原来的假串口是「按契约编好的答案」：
   它回显的内容形状恰好就是解析器期待的形状，于是「协议形状错了」这种 bug 在测试里永远绿。
   现在假串口按真实行为建模（回显每一行 + 执行），C2 立刻暴露。
2. **mock 同步、真实异步。** C3（SSH 的 `shell()` 是异步的）就是这么漏过去的。

这两条不是「写得不够小心」，是**测试替身建模错了**。
本仓库的规矩是「纯函数必须有单测；真机样本做黄金向量」——
下一步要把这条扩展到：**替身要按行为建模，不按结论建模**。

### 7.3.1 验证本身也要被验证

修完 6 条 Critical 之后，我做了**变异测试**：把每个修复改回坏的样子，
对应的测试**必须变红**。结果：

| 修复 | 有测试守着吗 |
|---|---|
| C1 串口端口真的打开 | ❌ **没有**——真实工厂是模块内私有的，删掉 `await port.open()` 测试全绿 |
| C2 marker 单行协议 | ✅ 有 |
| C3 SSH shell 异步 | ✅ 有 |
| C4 终端输出不重放 | ❌ **没有**——jsdom 里 xterm 的 `write` 是空实现，测不到写了什么 |
| C5 文件互传按传输分派 | ✅ 有 |
| C6 renderer 呈现错误 | ❌ **没有**——压根没测过错误路径 |

**三条 Critical 修了但没锁住。** 「测试通过」和「测试能抓住这个 bug」是两件事，
只有变异能区分。

补完之后，`scripts/mutation-check.sh` 把这件事固化成可复跑的脚本：
**6 项，0 形同虚设**。以后每次改动都能跑一遍。

> **这一条应该进 AGENTS.md 的硬规矩**：修完 bug 之后，
> 把修复改回去，确认测试会红——这是「测试真的在守」的证明。
