### C-1 · `args_summary` 的白名单「按参数名筛」**实现不了它自己声称的边界**（安全底线）

- **位置**：`docs/44` §2.4「`args_summary` 的脱敏边界」（第 201–219 行），特别是第 215–217 行：
  > 「`args_summary` 是「**按参数名逐个筛**」的白名单 …… **不是**「按 kind 整块放行或整块拒绝」✓ → 白名单：`path` / `glob` / `pattern` / `format` / `measure` / `strip_trailing_null` / `type` ✓ → **其余一律不给** ✓（`command` / `interpreter` / **`path`（script 的）** ✓ 全挡在外面 ✓）」

- **问题**：这段话**自相矛盾**，而且矛盾的那一边是安全底线。
  - 白名单按「**参数名**」筛 → `path` 在名单里 → `script` 的 `path` 就**在**名单里 → **给出去**。
  - 但同一段又要求「`path`（script 的）不给」。
  - 两者不可兼得：**按参数名筛 ≠ 按 (kind, 参数名) 筛**。而 `script` 的 `path` 是**宿主文件系统上的路径**（`src/main/tags/kinds/script.ts:26-27` 注释明写「**宿主**上的路径（包声明的）」），`interpreter` 也是宿主路径 → 两者一起就是「宿主上有什么、在哪」的目录结构泄漏（契约 §1.3 禁止给 agent 裸命令，`interpreter + path` 拼起来就是一条命令）。
  - 按提案的字面规则实现 → **`script` reader 的宿主路径会漏给 agent**。
  - 反过来，如果实现方按提案的**意图**（按 kind 挡）→ 规则文字与实现不符 → **两个实现出来的行为不一样**，正是这份提案要消灭的那件事。
  - 附带：**白名单误伤了无害参数**。8 个 kind 的参数表实测如下（`src/main/tags/kinds/`）：

    | kind | 参数（实测） | 在提案白名单里？ |
    |---|---|---|
    | `proc_stat` | `stat_path`, `cpuinfo_path`（proc-stat.ts:103-106） | ❌ **两个都不在** |
    | `meminfo` | `path`（meminfo.ts:17-19） | ✅ |
    | `devfreq_load` | `path`, `measure`（devfreq-load.ts:19-21） | ✅ |
    | `rknpu_load` | `path`（rknpu-load.ts:20-22） | ✅ |
    | `thermal_zone` | `glob`, **`type_map`**（thermal-zone.ts:23-27） | `glob` ✅ / **`type_map` ❌** |
    | `file_read` | `path`, `glob`, `format`, `strip_trailing_null`（file-read.ts:16-26） | ✅ |
    | `exec_regex` | `command`, `pattern`, `format`（exec-regex.ts:18-26） | ✅（`command` 挡 ✓） |
    | `script` | `path`, `interpreter`, `format`（script.ts:25-30） | **`path` 挡不住** ❌ |

    → `proc_stat` 是**最常用的 reader**，按提案白名单它**一个参数都给不出去** → agent 拿到 `args_summary = {}`，「这个量是怎么来的」变成空 → **这正是契约 §2.1 想要的东西没了**（`spec/04:107`）。
    → `type_map`（`soc-thermal → soc` 这类归并表）也被误伤 → agent 看不出 `temp.soc` 是按 `type` 归并的。
    → 白名单里的 **`type` 没有任何 kind 用**（`thermal_zone` 的参数叫 `type_map`）→ 一条永远不生效的规则。

- **后果（具体）**：契约里会出现一条**实现者无法照做**的脱敏规则。要么宿主路径泄漏（安全），要么两个宿主行为不同（契约没兑现）。

- **建议怎么改**（把规则改成**按 (kind, 参数名) 的封闭放行表**，这是唯一能同时满足两头的形态）：

  ```
  args_summary 的放行表（封闭，逐 kind 写死）：
  | kind          | 给 agent 的参数                          | 挡掉的                  |
  |---------------|------------------------------------------|-------------------------|
  | proc_stat     | stat_path, cpuinfo_path                  | —                       |
  | meminfo       | path                                     | —                       |
  | devfreq_load  | path, measure                            | —                       |
  | rknpu_load    | path                                     | —                       |
  | thermal_zone  | glob, type_map                           | —                       |
  | file_read     | path, glob, format, strip_trailing_null   | —                       |
  | exec_regex    | pattern, format                          | command                 |
  | script        | （空）                                    | path, interpreter, format |
  ```
  并加一句总则：
  > **「白名单」按 (kind, 参数名) 判定，不按参数名单独判定** —— 因为 `path` 在 `file_read` 里是**板上路径**（可给），在 `script` 里是**宿主路径**（不可给）✓。
  > **不在表里的参数一律不给** ✓（封闭表，不是「先给再筛」）✓。
  > `script` 的 `args_summary` **恒为空对象** ✓ —— agent 只知道「这个量来自一个脚本」✓（`kind` 字段已经说了 ✓）。

### C-2 · `missing_tags` 的口径在宿主侧**算不出来**，而且会算错

- **位置**：`docs/44` §2.6「`missing_tags` 的判定口径」（第 287–300 行），特别是第 291 行：
  > 「`permissions.read` | 每一个读权限里的 **tag 名** ✓（**按模式展开** ✓ —— `cpu.core.*.usage` 匹配当前所有读不到的 `cpu.core.N.usage` ✓）」

  与第 294–296 行：
  > 「**判定「读不到」**：当前 `TagStore` 里**没有这个 tag** ✓，**或**它在那儿但**状态不是 `ok`** ✓」

- **问题（两处，都可验证）**：

  **(1)「模式 → 具体名」这个方向宿主侧不存在。**
  `src/main/tags/vocabulary.ts:56-71` 的 `matchTagPattern(pattern, name)` 只有**一个**方向：**具体名匹配模式**。
  唯一的另一个使用者 `src/main/cards/permissions.ts:31-33` 的 `permissionCovers(perms, tag)` 走的也是这个方向（`perms.read.some((pattern) => matchTagPattern(pattern, tag))` —— 拿**具体名**去问模式）。
  → **宿主侧没有「把一个模式展开成一串具体名」的函数**。要凑出 `cpu.core.0..7.usage`，只能**反过来扫 TagStore 里已有的具体名**，用 `matchTagPattern(pattern, name)` 筛。
  → 提案写「按模式展开」，读起来像有个现成的展开函数 —— **没有**。这不是吹毛求疵：两个实现者会一个去扫 store、一个去写一个展开器 → 结果不同。

  **(2)更要命的：store 里根本没有「读不到」的那批具体名，所以这条口径会给出错误答案。**
  `src/main/tags/sampler.ts`：
  - 采样成功时，**只有绑出来的具体名**才进 store（`sampler.ts:188-200`：`bindSampleToTag(p.tag, p.sample, sampleName)` → `store.put`）→ 板上只有 4 核时，store 里就**只有** `cpu.core.0..3.usage`。
  - 采样失败时，**带 `*` 的 tag 被整条跳过**（`sampler.ts:212`：「带通配符的 tag 现在还不知道具体名字——**不猜**」；`sampler.ts:235` 同理）→ **通配实例永远拿不到非 `ok` 的状态**。
  - 首读 pending 同样跳过 `*`（`sampler.ts:174-175`）。

  → 后果一：一张卡要 `cpu.core.*.usage`，板子只有 4 核 → store 里没有 `cpu.core.4.usage` → 按提案口径 → **报「缺失」**（其实板子就没有这个核，报「缺失」勉强说得过去，但**理由不是「读不到」而是「板上就没有」**——提案自己在第 288 行就把这两个口径混成一句了：「这张卡要的、当前板上读不到的 tag」）。
  → 后果二（**更严重**）：`cpu` reader 整个挂了 → 通配实例**不会被标 stale** → store 里 `cpu.core.0.usage` 还是 `ok` + 旧值 → 按提案口径 → **这张卡一点都不 degraded** → **agent 被骗了**。而契约 §2.3 的 stale 定义（`spec/01:271-285`）说「刷新停了 → stale」——**实现现在就没做到**（这是实现层的洞，但提案的 `missing_tags` 口径**建立在这个洞上**）。

  → 后果三：`missing_tags` 与 `degraded` 会**在离线时全错**：store 一条都没有（运行时没起） → 所有卡都「残」。

- **建议怎么改**（把「板上根本没有」与「现在读不到」**分成两个字段**，各自口径写死）：

  ```
  list_cards[]：
  | missing_tags      | 「这张卡要的、**当前板型包根本没有**的 tag」✓
  |                   | 判据（**模式级**，不依赖 store ✓）：
  |                   |   对 permissions.read 的每个模式 P，
  |                   |   当前包的所有 reader 的 provides 模式 Q 里，
  |                   |   **没有一个 Q 覆盖 P**（P 的每个段要么字面相等、要么 P 是具体而 Q 是通配）
  |                   |   → P 整条记进 missing_tags（**记模式本身**，不展开 ✓）
  | unreadable_tags   | 「声明了、包也提供了、但**现在读不出来**的 tag」✓
  |                   | 判据：TagStore 里**该具体名存在**且 status ≠ ok ✓
  |                   | **只列具体名**（store 里有的那些）✓ —— 通配实例读不到时**不列**
  |                   |   （store 里没有它 = 「板上就没有 / 还没采到」≠「读不到」✓）
  | degraded          | = (missing_tags 非空) || (unreadable_tags 非空) ✓
  ```
  并在契约里加一句**免责**（这是 `spec/01` §2.3 的实现现状逼出来的）：
  > **「读不到」与「不存在」是两件事** ✓（同 `spec/01` §2.1 的 `unavailable` vs `error` 之分 ✓）。
  > **通配 tag 的实例在 store 里缺席时，不得据此判定「缺失」** ✓ —— 采样器**按契约不猜具体实例名**（`sampler.ts:212`）✓。

  > **顺带一条实现层的欠账要记进 `docs/06`**：通配实例在刷新失败时**不会被标 stale**（`sampler.ts:212,235` 跳过 `*`）→ 与 `spec/01` §2.3 的「刷新停了 → stale」**对不上** ✓ → 归 `C27` ✓（下一个 C 编号是 C27，`docs/06` 现在到 C26 ✓）。

### C-3 · 「加字段不算破坏性变更 → 不升 `apiVersion`」的**理由不成立**，且 `resolved.tags/actions` 本来就是**语义变更**

- **位置**：`docs/44` §2.7（第 320–324 行）：

- **建议怎么改**：
  1. 把 §2.7 的结论改成三句：
