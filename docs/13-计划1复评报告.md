## 二、本轮新发现（按严重度）

### 🔴 S-01 · `npm run build` 的产物自检会被**陈旧产物**骗过 —— 唯一的构建期守卫是摆设 🟢 **实测**

**位置**：`scripts/check-build.ts:48-62`

```ts
  const preloadPath = join(preloadDir, PRELOAD_FILE);
  checks.push({
    what: `preload 产物是 ${PRELOAD_FILE}（main 要的就是它）`,
    ok: existsSync(preloadPath),
    ...
  });
```

**根因**：`electron-vite` 的 preload 构建**不清空 `out/preload/`**。
上一次正常构建留下的 `out/preload/index.cjs` 活了下来，
而自检读的**正是这个陈旧文件**——真正的 ESM 产物 `index.mjs` 根本没人看。

**🟢 实测（我亲手做的）**：

```
把 electron.vite.config.ts 的 format 改成 'es'、entryFileNames 改成 '[name].mjs'，然后：

out/preload/index.mjs  2.46 kB      ← 本次构建的产物（ESM）
✓ 构建产物自检通过（preload = index.cjs，沙箱 preload 必须是 CommonJS）
=== CHECK EXIT: 0 ===
```

**失败场景**：把 preload 构建格式改回 ESM（这正是 electron-vite 在
`package.json` 是 `"type":"module"` 时的**默认行为**，`electron.vite.config.ts:12-19`
的注释里就写着这个坑）→ **`npm run build` 打印「✓ 通过」、exit 0** →
提交的是一个**沙箱 preload 加载不了的**产物。
（Electron 官方：*Sandboxed preload scripts can't use ESM imports*；
ESM preload 需要 `sandbox: false`，而 `sandbox: false` 等于关掉渲染进程沙箱——
那是 ADR-D16 的最后一道防线。）

**更糟的日常形态**：`out/preload/` 里陈旧的 `index.cjs` 与新的 `index.mjs` 并存，
main 加载的是**上一次的 preload 代码** → `window.cockpit` 少一个 API 时，
界面表现为「某个功能莫名其妙不工作」，而构建自检说一切正常。

**为什么这条最该先修**：它守的**正是上一轮的 P0**（preload 路径错）。
而变异项 **M7 就是这道守卫**——它报「改坏之后测试**仍然全绿** —— 这个测试形同虚设」。

**修法方向**：(a) 构建前清 `out/`；
(b) `check-build.ts` 断言 `out/preload` 里**只有** `index.cjs`；
(c) 校验 `index.cjs` 的 mtime 新于 `out/main/index.js`；
(d) 变异 M7 的判据改成「产物里**不得出现** `.mjs`」。

**测试覆盖**：变异项 M7（**已失效**）；`tests/unit/build-layout.test.ts` 只测纯函数 `preloadEntryName()`，不碰构建产物。

### 🔴 S-02 · `npm run mutation:check` 在目标平台 exit 1，4/20 是**环境造成的假警报** 🟢 **实测**

**位置**：`scripts/mutation-check.mjs`（`run()` 起 `npx vitest run <file>` 子进程）

**🟢 实测（本机）**：

```
node scripts/mutation-check.mjs
  ✗ C2  marker 单行协议：红了，但红的原因不对
  ✗ M7  preload 必须是 CommonJS：改坏之后测试仍然全绿
  ✗ M11 串口的回包缓冲不许被裁剪：红了，但红的原因不对
  ✗ M12 能力位由 profile 决定：红了，但红的原因不对
=== 结果：守住 16 项，形同虚设 4 项 ===   ← exit 1
```

**那 3 项差额的真实原因**（已隔离验证）：它们的 check 都是
`npx vitest run tests/unit/{serial,registry}.test.ts`，这两个套件 `import serialport` →
**原生模块架构不匹配 → 套件直接加载失败**（`Tests no tests`）。
「红了」是因为**加载失败**，不是因为断言失败——`expect` 字符串当然找不到。

加上 `PREBUILDS_ONLY=1` 再跑：
```
✓ C2 / ✓ M11 / ✓ M12 全部守住
=== 结果：守住 19 项，形同虚设 1 项 ===
```

**结论**：**只有 M7 一个是真失效**（就是 S-01）。其余 3 项是宿主假象。

**失败场景**：`AGENTS.md` §3 把「跑 `npm run mutation:check` 看当前这批修复是否都还守着」
写成硬规矩、§7 把它列为 8 条可用命令之一。开发者照做 → **exit 1** →
合理但错误的结论：「4 个回归测试是摆设」。

**更危险的方向**：这个脚本**把环境故障读成守卫失效**，
将来若真的有一个守卫失效，它也可能被读成「环境问题」——**两个方向都会骗人**。

**修法方向**：`mutation-check.mjs` 的 `run()` 补 `env: { ...process.env, PREBUILDS_ONLY: '1' }`；
或在 `package.json` 加 `mutation:check:win`。
**并且**：加载失败必须报「**环境问题**」而不是「测试变红」——
判据要区分「套件没跑起来」与「断言失败」。

**测试覆盖**：无（脚本自己不设 `PREBUILDS_ONLY`）。

### 🔴 S-03 · profile 的 `pty` 覆盖**仍然到不了运行时** 🟢 **实测**

**位置**：`src/main/terminal/manager.ts:125`

```ts
    const pty = connection.capabilities().pty;
```

`connection.capabilities()` 是**传输名决定的常量**
（`serial.ts:34` / `adb.ts:35` / `ssh.ts:22` / `local.ts:20`），**不看 profile**。
而 profile 感知的那个实现 `capabilities.ts:41-46`：

```ts
    pty: typeof explicit === 'boolean' ? explicit : defaults.pty,
```

**只有 `main/index.ts:94` 的 `connections:list` 在用它**（UI 侧）。
**运行时终端模式不用它。**

**🟢 实测**：

```
profile.options.pty = false

UI 侧 (index.ts:94  connections:list) 用 capabilitiesFor(profile).pty = false
运行时 (manager.ts:125  connection.capabilities().pty)   = true

>>> 两个能力位来源互相矛盾
```

**失败场景**：用户把 `profiles/targets/ubuntu-ssh.json` 改成 `"pty": false`
（服务端不分配 PTY）。schema 允许（`schema.ts:33` `COMMON_OPTIONAL` 含 `'pty'`，
只对 `adb` 的 `pty:true` 报错），契约 `spec/02 §10` 的 profile 示例里也有。

运行结果：宿主**不做行编辑、不回显** → 用户打的字一个都看不见；
回车原样发成 `\r` → 远端永远等不到行尾 → **命令永远不执行**——
**与 R-01 修复前的症状一模一样**。而 UI 上 `connections:list` 却报 `pty:false`，
**两个能力位来源互相矛盾**。

**测试覆盖**：**无**。`tests/integration/registry.test.ts` 只测 `capabilitiesFor`（UI 侧），
**没有一条断言 `options.pty` 影响 `TerminalManager.open()` 的行为**。
变异 **M12 只守住 UI 那一半**——它改的是 `capabilities.ts`，改不动 `manager.ts:125`。

**修法方向**：`manager.open()` 改成 `capabilitiesFor(profile).pty`，
并让 `Connection.capabilities()` 与它同源（或直接删掉连接上的 `capabilities().pty`，统一由 profile 决定）。

> ⚠️ **注意**：下游复评报告（`docs/12`）把 R-13 判成「✅ 已修复」，
> 依据是「两份实现合一了」。**这个判定不成立**——实现合一了，但运行时压根没走那一份。

### 🔴 S-04 · pipe 模式的**提示符画在命令输出之前** 🟡 推断（可复现）

**位置**：`src/main/terminal/manager.ts:171-175` + `line-editor.ts:389`

```ts
    const edit = live.editor.input(data);
    if (edit.toRemote.length > 0) live.session.write(edit.toRemote);
    if (edit.echo.length > 0) {
      for (const cb of this.dataCbs) cb(sessionId, edit.echo);
    }
```

`line-editor.ts:389` 在提交一行时把**下一个提示符**加进 echo：
```ts
          echo += `\r\n${this.prompt}`;
```

而远端的输出要**再走一次往返**才回来。于是提示符**先到**，输出**后到**。

**失败场景**：用户敲 `ls` 回车 → 屏幕上是：

```
root@ATK-DLRK3588:/# ls
root@ATK-DLRK3588:/#        ← 下一个提示符先到了
file1
file2
```

**输出落在「下一个提示符」后面**，而不是落在「刚敲的那条命令」后面。
每条命令都是这样。**第二条命令起连提示符都不对**——因为提示符画在输出之前，
上一条的输出把上一条提示符冲掉了。

**修法方向**：提示符不应该由**提交时**画，而应该在**远端输出到达后**画，
或者根本别画（让远端自己画——但 pipe 模式远端不画 PS1，这是事实）。
旧工程的做法是把提示符放在**独立输入行**里，不混进输出流。

**测试覆盖**：**无**。`line-editor.test.ts` 测的是 `PipeInput` 的纯函数输出，
`terminal-manager.test.ts` 测的是「回车发给远端的是 LF」——
**没有任何测试断言「提示符与输出的相对顺序」**。

**我核查过、确认不是问题的三点**（省得下一轮重复查）：
- 提示符**不污染会话日志**——两条路径都绕开了 `log.write` ✓
- **不与板子提示符重复**——pty 模式根本不画；且实测这块板的 pipe 模式 shell
  **不回显、不打印 PS1**（3.5 秒内零输出）✓
- **不是每 chunk 画**——开一次 + 每提交一行一次 ✓

### 🟠 S-05 · 上传的远端目标恒为 `/`；本机传输 `copyFile` 到目录**必挂** 🟢 **实测**

**位置**：`src/renderer/files/FileBrowser.tsx:102` + `src/main/hal/local.ts:128-135`

```tsx
// FileBrowser.tsx:102
    onPush(selectedLocal, remotePath);        // remotePath 恒为默认的 '/'
```
```ts
// local.ts:128
  async push(localPath: string, remotePath: string): Promise<void> {
    try {
      await copyFile(localPath, remotePath);  // ← remotePath 是「远端目录」
```

**🟢 实测**：

```
copyFile(src, '/') => 失败: ENOENT | ENOENT: no such file or directory,
                             copyfile 'C:\...\up-src.txt' -> 'D:\'
```

**两条传输的语义不一样，而 UI 传的是同一个参数**：
- `adb push <local> <dir>` —— 目标是**目录** → 自动拼上 basename（实测 `adb push up.log /` 成功）
- `sftp.fastPut(local, '/')` —— 目标是**文件**完整路径 → 目录会报错
- `copyFile(local, '/')` —— 目标是**文件**完整路径 → ENOENT

**失败场景**：「本机」目标点「↑」→ 目标恒为 `/` → **必挂**。

### 🟠 S-06 · `stripAnsi` 漏掉 ST 结尾的 OSC → 日志里留下半截转义码 🟢 **实测**

**位置**：`src/main/logging/session-log.ts:67`

```ts
  const OSC = /\x1b\][^\x07]*\x07/g;   // 只认 BEL 结尾
```

**🟢 实测**：

```
OSC+BEL : "text"                     ✅
OSC+ST  : "0;titletext"              ❌ 残留
CSI ?25l: "hidden"                   ✅
OSC 8   : "8;;http://xlink"          ❌ 残留
```

OSC 序列有两个合法终止符：**BEL**（`\x07`）与 **ST**（`ESC \`）。
xterm 及多数现代 shell 在 OSC 0/2（窗口标题）、OSC 8（超链接）上用 ST。
日志里会留下 `0;titletext` 这种半截。

**级别**：P3（R-18 的原始诉求「OSC 也要剥」只完成了一半）
**测试覆盖**：有测试但**只测 BEL**（`session-log-format.test.ts:139`）。

## 七、给下一轮的三条硬约束

> 从上面 60 条里**提炼**，不是新规矩。

1. **验证器要先验证自己。**
   本轮两条 P1（S-01/S-02）都是**验证器自己的洞**：
   一个会被陈旧产物骗过，一个会把环境故障读成守卫失效。
   **每一个门禁脚本，在写完之后都要问一句：「我自己怎么骗过我自己？」**——
   尤其是那些「查文件是否存在」的检查（构建产物、陈旧缓存、跨平台差异）。

2. **同一件事只能有一个来源。**
   S-03 的根因是「能力位有两个来源」：UI 侧读 profile，运行时读传输常量。
   这与「核心词表只有一个源头」是同一条道理，
   而上一轮修 R-13 时**只合了实现、没统一调用点**——
   合并了一半等于没合。

3. **判据与复核必须一一对应。**
   `docs/09:563` 的 ✅ 只描述了**布局**，判据原文却是「双树浏览」；
   `docs/09:782/783` 的 ✓ 对应的是**不存在的校验器**。
   **复核时若发现判据里有一个词对不上，就该把 ✅ 降级**——
   而不是给布局起个名字就叫它完成了。

## 八、评审结论

**上一轮 5 条 P0 全部真修，且大多被变异测试守着。** 这是实打实的进步——
尤其 `line-editor.ts` 从旧工程取规格、`AppError extends Error` + `{ok,error}` 信封、
`{ok,error}` 让 renderer 能按 `code` 分支、
变异脚本从 bash/python 改写成 Node 跨平台跑。

**但本轮暴露了一个更值得记的问题**：**两条 P1 都在「验证链」上**——
构建自检会被陈旧产物骗过，变异测试会把环境故障读成守卫失效。
**这与仓库的第一原则直接冲突**：「验证本身也要被验证」——
而现在验证器自己有洞。
**这两条不修，后面所有的「全绿」都少了一分可信度。**

**M1/M2 的判定**：
- **M1**：三通道代码齐备，**ADB 通道经真机实测通了**（R-01），
  串口 exec 的永久超时修好；**但仍有 S-03（pty 覆盖不到运行时）、
  S-04（提示符时序）、S-07（本机 pty 退出不上报）三条影响正常使用**。
- **M2**：管道通（IPC、按传输分派、双栏 UI、宿主定落盘位置），
  **但「双树浏览」不成立**（S-08）、**「双向传输」在本机与 SSH 上必挂**（S-05）。
  → **M2 仍是 ⏳ 部分满足**，但比上一轮的「✅ 全满足」诚实得多。

**建议的处置**：按 §六 的四级优先级推进。
**第 0 级（修验证链）最优先**——它花的时间很少，
但决定了后面所有「全绿」这两个字有多少分量。
