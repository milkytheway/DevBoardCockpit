## 三 · 问题

### 三·一 Critical

#### C1 · 执行与授权模型断裂：`exec` 步骤是一条绕过整条防线的裸命令通道，而 §3.7 承诺的“按动作 id 授权”在 schema 里根本不存在

- **位置**：`docs/24:215-225`（kind 表）、`:248-288`（样例 YAML）、`:350-357`（§3.7）、`:414-434`（§4.3）、`:479-481`、`:521-523`；契约侧 `spec/04:38-47`、`spec/02:410-452`、`spec/02:784-809`、`docs/21:549-558`。
- **现象**：`exec`/`launch` 的参数是 `(role, cmd)`——**自由文本命令**；9 个 kind 里**没有任何一个能调用板型包已声明的动作**。但 §3.7 写“流程里的写动作仍走 M6 的动作授权（**按动作 id**）”，§4.3 写“和今天 agent 只能触发宿主已声明的动作是同一个安全模型”。
- **为什么错**：
  1. **类型对不上**：M6 执行链（`docs/21:549-558`，共 7 步）处理的是“板型包 action id + 参数编码 + 地板 + 回读”。`exec (role, cmd)` 没有 action id、没有 danger/guard、没有 readback、没有地板——“按动作 id 授权”落不了地。
  2. **正面撞契约**：`spec/04:38-47` 原文“不准有裸 send_command。`execute_action` 取代裸命令执行。agent 只能触发**已声明的动作**，不能发任意命令”；`spec/02:807-809` 已把“换个入口执行任意命令”堵死（“一个能执行任意命令的 reader **就是**裸命令通道”）。流程包给了 agent 更好的旁路：**写一个 workflow pack，就能在任意角色（含宿主机 Windows、含存 SSH 私钥的编译机）上跑任意命令**。`buildrun.py:117-118` 用的就是 `%USERPROFILE%\.ssh\id_ed25519_*`——宿主机凭据。
  3. **信任模型缺失**：板型包之所以允许 `exec_regex/script` 是因为“agent 起草、**人确认才生效**”（`spec/02:784-809`；`spec/04:365-399`）。流程包呢？§3.7 一句没写；而 §5.3/§8·七 把“**AI 还能造流程**”当卖点（`docs/24:479-481`）——这等于把 agent 的权限边界从“已声明动作”扩到“任意命令”，却没有对应的审批设计。
  4. **`spec/04:533-540` 的 MCP 边界**还写着“不做通用 shell”“不存 agent 状态”；`run_workflow` 若可执行任意命令，前一条直接失效。
- **怎么改**：
  1. **拆两类步骤**：`action`（`role + actionId + params`，只能引用该连接板型包的动作，走 M6 全链）与 `command`（仅允许非板角色，或**人签名的 allowlist**；参数按 `spec/02` §4.6 编码后过地板）。
  2. 流程包纳入 `spec/02` §5.6 的信任模型：agent 可起草、**启用要人确认**；确认界面逐条列出“在哪个角色、执行什么最终命令”。
  3. agent 侧 `run_workflow` 与 `execute_action` 同构：`dry_run` → 人确认 → 带 `confirm_id` 重试；`confirm_id` 绑定 `(workflow id, 版本哈希, 绑定摘要)`（照 `spec/04:401-433`）。
- **怎么验证**：写一个“恶意流程包”用例（`exec {role: source(local), cmd: "type %USERPROFILE%\.ssh\..."}`）——按现稿规则**没有任何东西拦它**；改完后校验器/运行时必须能拦（未确认不生效 + 命令过地板 + 本机角色默认禁写）。🟢 这是可从现稿直接推出的漏洞。

#### C2 · 契约层定位自相矛盾：说“契约一行不改”，却要改 5 份契约；`apiVersion` 用“待定”回避了格式变更，且多板前置（O11）全文未提

- **位置**：`docs/24:7`（“不改契约”）、`:85`（“契约层一行不改”）、`:540`（“现有契约一条不改”）vs `:380`（“契约文档要改，要走评审”）、`:597-609`（§九：改 `spec/00/02/03/04` + 新增 `spec/06` + manifest 加 `workflow` 字段）；`:240-241`（`apiVersion: devboard/v1` + `kind: Workflow`）；`:606`（apiVersion“待定”）。
- **为什么错**：
  1. **自相矛盾**：§1.4/§7.2 的不变前提与 §九的改动清单直接打架。哪怕全是“新增 API”，按本仓库规矩 `docs/spec/` 就是契约层，改它就要走契约评审（`AGENTS.md` §2/§3；`spec/02:840`：“这 27 条就是契约本身”）。这不是措辞问题——W1 的验收判据因此无法成立。
  2. **`apiVersion` 不是“待定”能绕开的**：`spec/02:830` 明写“格式本身变了这个才动”。新增一个 **`kind: Workflow` 的第五种文件格式**、给 manifest 加 `workflow` 字段，都是“格式变了”：`spec/03:106-127` 每层封闭、实现里 `src/main/cards/manifest.ts:52-74` 是封闭白名单（`TOP_ALLOWED/PERMISSIONS_ALLOWED/…`），旧 v1 校验器遇到新字段/新 kind 必然报错。把 `kind: Workflow` 挂在 `devboard/v1` 下，等于**私自把一个未注册格式声明成 v1**。
  3. **“v1 未发布所以不升版”这条先例不能照抄**：`docs/05:642-647`/`docs/21:620-622` 的口径是“v1 **尚未随任何实现发布** → v1 定稿前的**修正**，不升版、一次成文一次评审”。现在 v1 已随实现落盘：`package.json:16` 有 `validate:profiles`、`src/main/tags/validator.ts:13` 实现了 27 条规则、manifest 白名单已实现——一条**新增格式**不是“修正”。
  4. **多板前置被漏掉**：`docs/05:1102` O11 白纸黑字“契约隐含全局单连接…本轮明确**单连接**（契约不动）；多板进 M8 时升 `apiVersion`”，而流程包的 `source/build/target` 三角色天然是**多连接同时在场**。文档全文（628 行）没有出现 O11/多板。`spec/03:585-601` 只是把“卡片 API 的前缀问题”隔离在宿主解析层，不等于“宿主层多连接编排语义已定”。
  5. **MCP 边界也变**：`spec/04:533-540`“不存 agent 的状态”，而 `run_workflow → runId → workflow_timeline(runId)`（`docs/24:426-428`）要求宿主长期保存任务状态——必须改 §六 措辞，区分“会话态/任务态”。
- **怎么改**：W0 拍板三件事：①workflow pack 是否进 `spec/`（若进，就承认是契约层变更，按契约评审走，不写“一行不改”）；②版本策略——推荐给 workflow pack **独立版本号**（如 `workflowApiVersion`），不蹭 `devboard/v1`；③O11 多板语义的结论（v1 是否允许流程跨连接），因为它决定 `roles/bindings` 的整个形状。§九 升级为正式变更清单（版本、校验规则、兼容/迁移策略）；删掉 §1.4/§7.2 的“契约不变”表述。
- **怎么验证**：把 §九 的改动逐项喂给“是否改契约层”判定；把新增 YAML 喂给现有 `validate:profiles`/manifest 校验器——现在**必然红**（未知字段/未知 kind）。🟢

#### C3 · 非标量通道：`SPEC-D20` 被挪用，时间线/流没有任何契约形状

- **位置**：`docs/24:126-136`（§2.3）、`:147`、`:325-348`（时间线 JSON）、`:428`（“订阅/轮询”）、`:514`。
- **现象**：文档称 `SPEC-D20` 的 push 源“决定了结果的推送方式已经预留好了，流程执行器照那个形状做即可，**不必再造第三种事件流**”。
- **为什么错**：
  1. `SPEC-D20` 原文是“**取数侧**接口为 Source（poll/push），v1 只实现 poll”（`spec/00:140`）——Source 是**往 TagStore 供标量 tag 值**的接口；`SPEC-D4`（`spec/00:124`）又把日志/流排除在 tag 之外。**Source 不可能承载编译日志**：装进去就违反 D4，不装进去就与 Source 形状无关。
  2. 真正对应“日志/进度流”的是 **Stream**，而它只有占位：`spec/00:190`“连续流的契约 Stream…目前只有一个占位定义，没定死”；`docs/09:268-275` 直接说“Stream 契约缺失——**最大的架构缺口**”。所以“接口基础已经有了”是反的。
  3. 代码里**没有 Source 实现**（本次 `src/main` 全仓搜 `Source` 无接口/实现，只有 `push` 数组与 `poll_groups`）；但已有两条推送通道：卡片端口 push（`bridge-script.ts:109-116`）与 main→renderer IPC 事件（`index.ts:141`）——**新通道不是不能造，而是不能假装它有契约**。时间线的载荷、订阅/退订、`seq`、保留、背压、与 tag 五态的关系、与审计行的关系，全部没定义。
- **怎么改**：明确“时间线 = 新通道”，并二选一：复用现有 IPC/端口 push（定义载荷与订阅协议），或等 Stream 契约落地后再接。给时间线定义：传输形状（**首版 poll**，MCP `workflow_timeline(runId)` 可查询）、增量/`seq`、保留/清理/上限、失败与 `unavailable` 的表示。**不要**再写“照 Source 形状做”。

#### C4 · 旗舰需求不可表达：没有输入参数，“用户选定位置”无处安放，`confirmed` 没有判据

- **位置**：`docs/24:31-35`（用户原话）、`:238-292`（§3.4 格式，顶层无 `inputs/params`）、`:376`（“不做变量”）、`:426`（`run_workflow(…,{source:"local"})`）、`:229-231`（placement 语义）、`:279`（`load` 硬编码路径）、`:222`（`await` 只认 tag）、`:318-319`、`:341`。

  1. **参数化缺失使“一件事”退化成“一个硬编码实例”**：真实样板 `buildrun.py` 的核心就是参数化（`br:258-288`：项目路径 + `--make/--run/--no-run/--ko-dir/--bin-dir/--transport/--board`）。按现 schema，每个项目/每个安装位置 = 一份新流程包，§5.2/§5.3 的“可复用/可交易”直接落空。

- **怎么改**：
  1. 加顶层 `inputs:`（封闭类型：integer/number/string+`maxLength`/boolean/enum，与 `spec/02` §4.3 同表），步骤里允许 `{input}` 占位——这是**声明式替换**不是表达式；替换后的最终命令必须过地板/编码。

  3. 成功判据统一成 **M6 回读的同五个形式**（tag/`file_equals`/`command_ok`/`verify`/`none`，`spec/02` §4.4），每步显式声明；`await` 只是其中“tag + 期望状态”的用法。这样“编译成功=command_ok+产物存在”可表达，`confirmed` 也有了定义来源。
  4. 若“模块已加载”确实要 tag：要么用 `custom.*`（各板自绑），要么走契约升版新增核心 tag——**不能像 `system.load` 那样在样例里私造**。
- **怎么验证**：把 `buildrun.py` 的用法机械翻译成流程包（含项目参数、`--ko-dir` 覆盖、`--transport net|adb` 切换）——按现 schema **翻不出来**；改完后应能 `dry-run` 输出编码后的最终命令。🟢

### 三·二 Important

**I1 · “四个缺概念”被夸大：Role 是薄别名，跨目标直传是优化，Job/流/卡片 API 才是真缺。**
（`docs/24:150-157`）①Job 真缺（无取消 API——全仓无 `AbortController`；无进度/流）；②Role 只是“带用途名的 profile 引用”，可直接写 `profile id`（`docs/24:298-311` 本身就是 profile 引用）；③跨目标直传**能力已有**：`buildrun.py` 的“客机直达板子”就是在客机上跑 `scp`（`br:339-383`），等价于 `exec` 一条命令——缺的是一等步骤和进度条，不是能力；④非标量通道真缺，但载体不是 Source（C3）。真正该撑起“必须重构”的只有 Job+流+卡片文件/目标 API。

**I2 · “策略只能住在卡片里”不准确。**
（`docs/24:54-58`）板型包的动作已经承载策略：命令模板、参数编码、`guard`、`readback`、`danger`、地板（`spec/02:410-452,739-782`）；宿主侧 poll group 调度、终端、文件 API 也都是策略；卡片 JS 能顺序/条件/循环调多个已声明动作（`spec/03:548`；实现属 M6）。准确说法是：“**没有一个声明的、可复用的、可审计的编排实体**”——这仍成立，但论证要换。

**I3 · reader kind 的类比只复制了“形式”，没复制“契约机制”，且语义不可迁移。**
（`docs/24:209-211,565-569`）reader kind 是**纯读函数**：文本→sample、sample 显式绑 tag（`spec/00:126` SPEC-D6），失败=`unavailable`，无副作用、无授权（`spec/02:243-301`）；step 是**副作用**：可能改板/改宿主、可能部分失败、需要 danger/guard/readback/审批。正确的既有范式是 **Action**（`spec/02` §4）。而且文档只复制了“封闭清单”的口号：reader kind 有参数 schema、注册表、校验器（`spec/02:283-301`），step kind 表只有 4 列（`docs/24:215-225`），没有参数 schema/产出类型/版本/规则号——**形式也没复制全**。“reader kind 成功 ⇒ step kind 也会成功”（`docs/24:566`）是非因果。

**I4 · step kind 集：冗余 4 个、缺口 5 个。**
（`docs/24:215-225`）冗余：`file.fetch`≈`artifact.transfer`≈`artifact.deploy`（都是跨角色复制，区别只在 path/placement，deploy 还混入安装语义——安装本身是 `depmod/modprobe` 的 exec）；`exec`≈`launch`（都“退出码+输出流”，exec 的 1800s 已是长任务，`stream` 应是一个参数）；`await`≈`assert`（同一 tag 判据）；`note` 是时间线元数据不是步骤；`exec_script` 文档自己说首版不要（`:621`）。缺口：**`action`**（调用已声明板型动作——最该有的一个）、**`discover`**（产物发现，`br:312-328`）、**`inputs`**（C4）、**凭据/准备**（客机→板免密，`br:213-236`；`chmod +x` `规:146`）、**`cleanup/rollback`**（`docs/24:357` 自己说首版不做，但状态机没有位置）。`produces: [hello.ko]`（`:266`）声明了却没有任何消费语法。

**I5 · 状态机混了“定义态/运行态”，缺关键状态，且自造与契约同名的状态词。**
（`docs/24:313-343`）①`idle/armed` 是定义态与运行态混在一起（`armed` 没有独立转移语义）；②缺 `queued`（并发 run）、`awaiting_confirmation`（流程中途遇到 destructive 步骤要人确认——`docs/21:586-588` 的确认通道；中段 `denied` 也无处落）、`partial/aborted`（中途失败但已有副作用，`:357` 说回滚首版不做，那就必须有“脏”状态）；③`unconfirmed` 与 `spec/04:269-290` 的 `verified:false`/“已执行，未验证”**同义异名**；步骤态 `ok`（`:335-339`）与 tag 五态同名异义（`spec/01:123-131`、`shared/tag-reading.ts:11`）——违反 `AGENTS.md`“不得另立命名/状态语义”；④`stages` 概念在 YAML schema 里**不存在**（只有平铺 `steps`，`:253-285`），而 `observability.timeline`/`produces` 语义未定义。

**I6 · placement 的落点与解析机制都错了。**
（`docs/24:229-231,279,511,602,622`）①`placement` 词表（`kernel-module` 等）没有单一源头——应像 reader kind 一样进 `spec/02` 做**封闭清单**（带版本），板型包只放“语义名→路径/解析方式”的映射（与 SPEC-D6 的 sample→tag 同构）；②`docs/24:230` 的板型包路径含 `$(uname -r)`——这是**模板/命令替换**，与 `:376` 禁变量、`spec/02` §4.6 的编码精神冲突；正确做法是显式 resolver（例如用现成的 `board.kernel` tag，`tag-vocabulary.yaml:135-140` 已留 reserved）或声明式 `resolve` 命令；③`:279` 的 `load` 把解析后的路径又硬编码进命令，**自己破坏“换板不改流程”红线**；④放置规范里的 `depmod` 顺序、`chmod`、勿并发推模块（`规:141-148`）是**流程/动作规矩**，不是“板子的规矩”，塞进板型包会撞 `docs/24:203-205` 自己划的界。

**I7 · 角色绑定不够，而且绑出了“第三套连接定义面”。**
（`docs/24:248-251,298-311`）①角色 1:1，没有基数/多板形态，但 §十-2 又设想“双板对比”（`:618`）；②绑定文件路径三处不一致：`:299` `# profiles/workflows/`、`:509` `profiles/workflows/*.yaml`、`:617` 顶层 `workflows/`；③`:310` 在绑定里覆写 `host`——连接的定义面变成三处（`profiles/targets/*`、板型包 `board_pack`、流程绑定），与 `docs/09` 的统一扩展点原则冲突；④`expects: [exec, files]` 把能力词当**门禁**，撞 `docs/05:1101` O10 与 `spec/02:1052-1059`“`requires.capabilities` 是信息不是门禁”，且两轴词表（板级/连接级）也没引用；⑤没有任何绑定校验规则（profile 存在吗？已连接吗？角色能力对得上吗？绑定缺失→`denied` 的判定点在哪？）。**“用户选定位置”不是 role 能解决的问题**（那是 inputs，C4）。

**I8 · 时间线与审计的关系没定义：要么两份记录，要么审计留洞。**
（`docs/24:346-348,350-357,514`）若步骤走 M6，每个动作按 `spec/02:730-737`/`spec/04:303-315` 写**一行审计**；时间线又是一条 run 记录——同一次执行两份真源，`audit_id` 怎么关联没写。若“从每次 action 一行扩到一次闭环一条”（`:514`）是**替换**，又与 M6“每个 `execute_action` 写一行”冲突。更严重：非动作步骤（宿主/客机 `exec`、transfers）**没有 M6 审计**——对宿主机的写完全无审计。改：时间线是运行记录，审计行带 `runId/stepId` 外键；非动作步骤也要产审计行；定义查询/保留。

**I9 · “流程执行器 = M6 执行器”未证明，且 M6 的范围装不下流程。**
（`docs/24:174,367,623`；`docs/21:549-558`）M6 执行链是“权限→授权→参数→地板→执行（RoundTripQueue）→回读→审计”，对象是**单个板型包 action id**；流程没有 `action` kind（I4），跨连接、长任务、取消、流式输出、阶段推进都不在 M6 设计里。`docs/21:580-584` 甚至说“执行器现在拿不到连接与队列”。`docs/17:457-459` 明确 M6 要**单独写计划 5**。所以正确关系是“流程执行器**调用** M6 的动作原语”，不是“同一个执行器”；`docs/24:623` 的“流程是一串动作”需要一个映射（`action` kind + 非动作步骤）才成立。

**I10 · 时机论证不成立：“M6 未开工=现在最好”恰恰说明现在没有可扩的执行器。**

## 附 · 任务问题 A–E 的逐条回答

**A1 “当前架构 hold 不住”成立吗？** 结论：**对“卡片形态的闭环”成立，对“四条都缺能力”不成立**。逐环节：选代码源（卡片无文件/目标 API 🔴 成立）；编译（无 Job/取消/流 🔴 成立，但 `exec` 可设长超时 🟡）；传输（一等步骤缺，但 `exec`+scp 已能实现直传 🟡）；落位（知识不在仓库、无载体 🟢 成立）；加载运行（`Session` 能收输出，缺任务语义 🟡）；观察中间结果（非标量通道缺 🟢 成立，但载体不是 D20）；审计（零实现 🔴 成立）。**“策略只能住在卡片里”不成立**（I2）。

**A2 四个概念真缺吗？** Job：真缺（无取消/进度/阶段）。Role：薄别名，不是原语（真新东西是绑定解析与多连接事务）。跨目标直传：实现可绕过（`exec`+scp，`br:339-383`），缺的是一等步骤+进度。非标量通道：“流不进 tag”的边界已有（D4），缺的是**时间线/Stream 自己的契约**（C3）。所以是 **2 个真缺 + 2 个被夸大**。

**A3 “策略只能住在卡片里”准确吗？** 不准确（I2）。准确说法：“**没有声明的、可复用的、可审计的编排实体**；卡片没有编排原语，宿主没有编排载体。”

**B1 五层有无错配？** ①/② 不是两个“层”，是同一份契约的“词表（kind）+ 实例（pack）”（reader kind 先例就是这样，`spec/02:275-301`）；③④⑤ 才是运行时层。真正错配：④宣称与 M6 同路径，但 M6 不存在（C5/I9）；③与既有两套绑定（`profile→board_pack`、布局 `(cardId,connectionId)`）的关系没写（I7）；“每层不知道下一层”不成立——④执行①，需要③；①的 `exec` 语义受传输能力影响（串口无 `exitCode`，`docs/02:173`）。建议压成 4 层：**语言层（kind+pack）/ 绑定层 / 执行层 / 呈现层**。

**B2 9 种 step kind 够吗？** 不够：多 4 个（`file.fetch`/`artifact.transfer`/`artifact.deploy` 三者可并；`exec`/`launch` 可并；`await`/`assert` 可并；`note` 是元数据；`exec_script` 首版不要），缺最关键的 **`action`**（调用已声明板型动作），还缺 `discover`（产物发现）、`inputs`、凭据准备/`chmod`、`cleanup`（见 I4）。

**B3 “封闭清单+逃生门”从 reader kind 复制成立吗？** **形式成立、语义不成立**。可迁移的是“封闭 kind + 参数 schema + 注册表 + 校验器 + 逃生门”；不可迁移的是“纯函数读、失败=unavailable、无授权”这一套——step 是副作用，必须走 Action 那套（danger/guard/readback/审批）。而且文档连“参数 schema/注册表/校验器”都没复制（I3）。“reader kind 成功 ⇒ step kind 成功”是非因果。

**B4 placement 与“用户选定路径”怎么共存？** 能共存，但现设计没有入口：语义 placement 是默认，`transfer` 的 `to` 允许 `{placement}` **或** `{path}`；`path` 由 board pack `allowed_paths` 校验；用户输入走 `inputs`（C4）。placement 词表必须进契约（封闭清单），板型包只放“语义名→路径/解析器”的映射（I6）。`buildrun.py` 的 `--ko-dir/--bin-dir`（`br:276-279`）正是这个自由度。

**B5 `await` 用 tag 做完成判据够吗？** 不够。编译成功=**退出码 + 产物存在**，不是板上的量（C4/I1）；词表里没有 `system.load`；`stale` 的语义（值可能不准，`spec/01:273-286`）与“算不算达标”必须写死；还要区分**电平触发 vs 边沿触发**（值在 run 开始前已满足怎么办）；超时映射到 `failed` 还是 `unconfirmed` 要定。正解是统一成 M6 回读五形式（tag/`file_equals`/`command_ok`/`verify`/`none`）。

**B6 状态机够不够/有没有多余？** 不够且混：缺 `queued`、`awaiting_confirmation`、`partial/aborted`；`armed` 多余（可并入 idle 的校验结果）；`unconfirmed` 与 `verified:false` 同义异名；步骤态 `ok` 与 tag 五态同名异义；`stages` 概念无 schema。建议：运行态 `queued/running/awaiting_confirmation/succeeded/unconfirmed/failed/cancelled/denied`；步骤态 `pending/running/ok/failed/skipped/cancelled`（不复用 tag 五态的词，除非语义完全相同）。

**B7 时间线与“每次 action 一行审计”什么关系？** **并存，不是替换**：时间线是运行记录，审计行是逐次追责单位（破坏性步骤的确认记录不能被阶段摘要吸收）；时间线的 stage 引用 `audit_id`；非动作步骤（宿主/客机 exec、transfer）也必须产审计行。若哪天流程执行器不是 M6 执行器，才谈“替换”。现稿没写死这条（I8）。

**C1 与冻结契约冲突吗？要不要升 `apiVersion`？** 有硬冲突：裸命令撞 `spec/04:38-47`（C1）；写权限词撞 `SPEC-D11`/`spec/03`（M4）；状态命名撞 `spec/04:269-290`（I5）；新增 kind/字段撞封闭 schema（C2）；MCP 状态边界撞 `spec/04:533-540`（M6）。`apiVersion` 不能“待定”：按 `spec/02:830`，新格式=格式变了；要么升 v2，要么给 workflow pack 独立版本号——**二选一必须 W0 拍板**；同时 O11 多板要一并解决。不能沿用“v1 未发布所以不升版”的旧口径而不承认这是契约层变更。

**C2 是否在重复发明已有机制？** 三处要区分：step kind vs reader kind——形式同构、语义不同（B3，可接受但要改称 Action）；板型包 vs 流程包——**不是重复**（一个描述板、一个描述事），但 `placement` 知识与流程性规矩（depmod/chmod/顺序）的归属要切开（I6）；M6 executor vs 流程执行器——**宣称同一个、实际类型不接**（I9，这是最危险的一处）；`await` vs M6 `verify` 是机制重复（B5）。风险提示：文档实际引入了 **5 套新词表**（step kind、placement、role、permissions、状态），却都没有单源——这是“第三套真源”的真正风险。

**C3 破坏“词表只有一个源头”“契约与实测差异不私自改”吗？** 是，两处：①`system.load` 在样例里私造（词表无此 tag；`tag-vocabulary.yaml` 头注规则 3）；②placement 事实目前是 🟡（只在学习工作区），没进 `docs/02` 就要写进板型包契约（I6）。另有程序问题：`docs/24` 没有把外部样板的“实测 vs 转述”标出来（C6），把转述当 🟢。建议：所有新词表（step kind/placement/role/permissions/timeline schema）都要么进契约封闭清单、要么明确“宿主内部词表”并给单源（参照 `tag-vocabulary.yaml` + `gen:` 校验的做法）。

**C4 “M6 未开工 = 最好的时机”成立吗？** 半成立，且结论相反：对“服务路径一起设计”成立；对“现在冻结流程包契约”不成立——M6 没有实现可扩，流程 W2 会同时造 M6+流程引擎（I9/I10）；Stream、O11 两个前置未决；作者自己的低成本的实验（§8·八）没做。正确时机是：**现在定 M6 的服务边界（Job/审计/回读事务粒度），流程声明层等 M6 + 第二条真实流程之后**。

**D1 四问判据好吗？** 不够准：④“被审计”几乎对所有副作用闭环恒真（作者 `:497` 自己也承认单卡固定流程不必抽，自相矛盾）；①与②相关；漏了“长时且需取消”——30 分钟编译即使不复用/不换目标/不给 agent，也仍然需要 Job。建议改成三条硬判据：**（a）跨目标或跨传输；（b）长时且必须可取消/可观察；（c）必须由 agent 无卡触发且要可审计的部分失败**——任一成立才进流程层，且再加一条“第二条真实流程出现前不抽”。

**D2 §5.2 矩阵虚高吗？** 两行虚高：“换传输”在串口上改变退出码/文件能力（`docs/02:173,175`；`docs/21:576`），依赖它们的步骤要改或被拒；“换板子”在新板型包没声明 placement 名时解析失败。建议改成验证计划，每行一次真实对拍（I11）。

**D3 最没价值的三条？** `exec_script`（作者自己也说首版不要，`:621`）；`artifact.deploy`（= `transfer` + placement，安装本身是 `exec`）；`note`（时间线元数据，不是步骤）。备选可合并：`launch`→`exec`、`assert`→`await`。

**D4 §八 哪几条站不住？** 一（“同一个套路第二次应用”）：tag/board-pack 是“语义 vs 实现”，reader kind/step kind 是“读 vs 写”，不是同一种分离——错位；三（“reader kind 成功所以 step kind 也会成功”）：安全域不同，非因果；六（“中间结果不是 tag 所以观察窗不能靠现有通道”）：结论对，但与 §2.3“D20 push 源就是通道”自相矛盾；七（“agent 能力边界=宿主已声明”）：如果 agent 能写流程，边界就被改写，而审批模型没设计——与 §5.3 的卖点冲突。二/四/五/八站得住；八最好但应最先执行。

**E1 W0–W4 合理吗？** 不合理在顺序：W1 契约先行违背 `spec/02:243-273` 的教训；W2 的假设备多角色/传输判据现在无法执行（I12）；W0–W4 没有 M6 的位置。砍 W1，重排为 §五·四（W0 事实+实验 → W1 宿主内建单流程真板 → W2 M6 边界 → W3 契约 → W4 第二条流程 → W5 卡片/MCP）。

**E2 用 `buildrun.py` 当第一份流程包样板够代表性吗？** 不够：它是**参数化 CLI**（8 个参数）、**条件分支**（net/adb、`.ko`/可执行）、**产物启发式发现**、**文本判据**（modinfo）、**免密准备**、`chmod`、**无回读的 run**；缺多板、授权/确认、取消/清理、重试/回滚、进度、交互输入。用它可以，但必须**先把它的真实复杂度当需求矩阵**；现稿的映射把 8 个参数、2 条支路、2 类产物都抹平了，还编了两个不存在的步骤（`dmesg`、`insmod`）——按这个样板做 W3 会在真板上直接对不上（C6）。

**E3 最小可用一版长什么样？** **不先做流程包格式**：在宿主实现一条**内建 procedure**（TypeScript、人审、走 M6 服务路径），把 `buildrun.py` 的 net 支路跑通——参数化项目、长时 Job（开始/状态/流/取消）、时间线落盘、卡片启动/观察、宿主/客机命令也产审计行。假设备上做单角色单测（替身按行为建模），真板跑通一次（`modprobe` 路线、`depmod`+`chmod`、参数化、超时齐全）。跑通后，第二份真实流程（如“抓日志并归档”）用同一引擎走一遍——**两条真实流程都命中同一组步骤时，再把它们抽成 workflow pack 并写契约**。这就是“能被真板跑通”的最小版本，也是最便宜的“要不要流程包”的判据。
