# 04 · 想法三：组装画布与「一键造卡」

> **作者**：Codex　**日期**：2026-11-17　**性质**：**探索**（不约束任何人 ✓）
> **想法原文**：「是否有可能或者是否支持做出一个画板区域，可以自由的将不同元操作，流程组装到一起，
> 然后一键生成卡片？通知某个agent让其工作？」

---

## 〇 · 结论先行

1. **造卡的管道 90% 已经存在** ✓ —— `validate_card` ✓ · `install_card` ✓ · `get_card_sdk_docs` ✓
   → **缺的只有两件**：一个画布 ✓ + 一份「从画布到规格」的转换 ✓
2. **决定性约束**：**卡片没有构建步骤** ✓（沙箱 + CSP + 免构建 ✓）→
   → **画布不能生成代码** ✗ → **它只能生成「规格」** ✓
3. **所以「一键生成卡片」的正确形态是**：
   **画布 → 一份规格 → 人或 agent 照着实现 → 校验 → 安装** ✓
   → **「一键」的那一下，是「把规格交出去」** ✓，不是「代码从天上掉下来」✓
4. **这正好和想法④ 解耦** ✓ —— 规格既能给人，也能给 agent ✓ → **③ 不必等 ④** ✓
5. **画布上的积木有三类** ✓：**板级动作** ✓ · **流程** ✓ · **流程片段** ✓（后者要等想法② 的 fragment ✓）
6. **画布不是「可视化编程」** ✓ —— 它是**脚手架 + 任务书** ✓

---

## 一 · 现状：造卡的管道已经通了 🟢

### 1.1 现成的四件套 🟢

| 件 | 是什么 | 出处 |
|---|---|---|
| **校验** | `validate_card` —— 13 条校验规则 ✓（manifest 形状 ✓ · 权限 ⊆ requires ✓ · 词表 ✓ …） | `src/main/mcp/card-tools.ts` ✓ |
| **安装** | `install_card` —— 写进用户卡根 ✓ · **装完即生效** ✓ | 同上 ✓ |
| **说明书** | `get_card_sdk_docs` —— **给 agent 的卡 API 文档** ✓（manifest 字段 ✓ · `cockpit.*` ✓ · 例子 ✓） | `src/main/mcp/sdk-docs.ts` ✓ |
| **热更新** | **改文件即热更新** ✓ —— 卡片是文件 ✓ | 契约 §二 ✓ |

> → **「让 agent 造一张卡」这件事，今天就能做** ✓ —— 前提是**有人告诉 agent 造什么** ✓
> → **画布要提供的，正是那份「告诉」** ✓

### 1.2 但**没有「新建卡片」的入口** 🟢

卡片库页（`src/renderer/shell/pages/LibraryPage.tsx` ✓）只能**浏览 / 放置 / 打开详情** ✓
→ **没有「从零建一张卡」的按钮** ✓ → **想法③ 的根** ✓

### 1.3 卡片的形状（**画布要产出的东西**）🟢

```jsonc
// manifest.json —— 契约 spec/03 定的封闭形状 ✓
{
  "apiVersion": "devboard/v1",
  "kind": "Card",
  "id": "my-card",           // 稳定标识，全局唯一 ✓
  "name": "人类可读名",       // ✓
  "version": "1.0.0",        // ✓
  "entry": "index.html",     // 相对卡片目录 ✓
  "layout": { "w": 4, "h": 3, "minW": 3, "minH": 2 },  // ✓
  "requires":   { "capabilities": [...], "workflows": [...] },   // ✓
  "permissions":{ "read": [...], "write": [...], "workflows": [...] }  // ✓
}
```

> → **画布上摆的东西，最终要落成这个 manifest** ✓
> → 而 `permissions` 是**封闭**的 ✓ → **画布摆什么，权限就写什么** ✓ → **一一对应** ✓

## 二 · 决定性约束：**卡片没有构建步骤** 🟢

```
CSP: default-src 'none'; script-src 'self'; connect-src 'none'
卡片 = 免构建 ES Module（ADR-D4 / ADR-D14）
```

### 2.1 这条约束**排除掉一整类方案** ⚠️

| 方案 | 成立吗 | 为什么 |
|---|---|---|
| 「画布 → 生成 React 代码 → 编译 → 打包 → 装」 | ❌ | **卡片没有构建步骤** ✓ → 装进去也是坏的 ✓ |
| 「画布 → 生成 HTML/CSS/JS → 直接装」 | 🟡 **理论可行** ✓ | 但**生成的代码质量不可控** ⚠️ → 谁维护？改一行怎么改？✓ |
| 「画布 → 生成**规格** → 人/agent 写代码 → 校验 → 装」 | ✅ | **代码由能写好它的人写** ✓（人 or agent ✓） |

### 2.2 为什么「生成代码」这条路**即使技术上可行也不该走** 🔵

| 理由 | 说明 |
|---|---|
| **产物没人维护** | 自动生成的代码，改一行要去改画布？✓ 那画布就成了「第二个 IDE」✓ |
| **沙箱里没有调试手段** | 卡片里没有 console、没有 devtools 的舒服环境 ✓ → 生成错了**很难发现** ✓ |
| **质量不可控** | 「自动生成的卡」和「人写的卡」会**长得不一样** ✓ → **两套视觉语言** ⚠️（ADR-D27 的老问题 ✓） |
| **违背产品主线** | 「**AI 可造卡**」= **AI 写卡** ✓，不是「UI 生成器写卡」✓ |

> → **画布的产物是「意图的结构化表示」** ✓ —— 与 Claude Code 的 plan、Cursor 的 rules **同一个模式** ✓

## 三 · 画布的正确形态：**产出规格** 🔵

### 3.1 规格 = 三块拼起来 ✓

```
┌─────────────────────────────────────────────────────────────┐
│  ① 流程部分  →  **流程包 YAML**（已经能跑 ✓）               │
│     steps: [exec / action / file.transfer / assert …]        │
├─────────────────────────────────────────────────────────────┤
│  ② 卡片部分  →  **manifest 骨架**（契约已定 ✓）             │
│     requires / permissions / layout                         │
├─────────────────────────────────────────────────────────────┤
│  ③ 人话部分  →  **一段自然语言** ★                           │
│     「这张卡显示板子的 CPU 占用，并允许切换调频策略」        │
└─────────────────────────────────────────────────────────────┘
```

> **③ 是最关键的一块** ✓ —— 因为**人话正是 agent 真正需要的** ✓
> → 「给我一个 YAML」agent 很难写对 ✓；「给我一段话 + 一份 YAML 骨架」✓ → agent 写得好得多 ✓

### 3.2 为什么**不新造一种规格格式** 🟢

| 理由 | 说明 |
|---|---|
| **流程部分已经是能跑的格式** ✓ | 新格式 = **要再实现一个解析器** ✗ |
| **manifest 已经是契约** ✓ | 新格式 = **要再实现一套校验** ✗ |
| **规格必须能被人读** ✓ | YAML + 一段话 ✓ |
| **规格必须能被工具校验** ✓ | `validate_card` 现成 ✓ |

> → **规格 = 「已有的两份」+「一段人话」** ✓ → **零新格式** ✓

### 3.3 一个**中间产物**的建议：**画布的快照** 🔵

```yaml
# 画布保存的东西 —— 它不是流程包，是**画布本身**
kind: Canvas
id: cpu-console
name: CPU 控制台
board: rk3588-atk          # ← 面向哪块板 ✓
workflow: workflows/cpu-console.yaml     # ← ① 流程部分（引用）
manifest:                              # ← ② 卡片部分
  layout: { w: 4, h: 3, minW: 3, minH: 2 }
  permissions: { read: [cpu.usage, cpu.governor], write: [cpu.governor.set_all] }
intent: |                                # ← ③ 人话
  这张卡显示当前连接的 CPU 总占用与调频策略，
  并允许在「性能 / 节能 / 平衡」之间切换。
  切换后必须显示**回读到的**策略，而不是用户点的那个。
```

> → **画布 = 一份「组装结果」的声明** ✓
> → **它可以被拆开看** ✓ · **可以被 agent 读** ✓ · **可以被版本化** ✓
> → **它不是运行时就绪的东西** ✓ → **还要一步「编译成卡」** ✓（§六 ✓）

## 四 · 画布上能摆什么：三类积木

| 类 | 是什么 | 来自哪 | 在规格里落成 |
|---|---|---|---|
| **板级动作** | `led.set` / `backlight.set` / `cpu.governor.set_all` ✓（15 条 ✓） | **板型包** ✓（换板就变 ✓） | 流程的 `action` 步 ✓ + manifest 的 `permissions.write` ✓ |
| **流程** | `hello-kernel.build-run` ✓ 等（8 条 ✓） | **流程包** ✓ | 流程的嵌套（**要等想法②的 call** ⚠️）或 **manifest 的 `permissions.workflows` ✓**（**今天就能声明** ✓） |
| **流程片段** | 「传文件 + 落位 + 验证」✓ | **要等想法② 的 fragment** ⚠️ | 流程的片段引用 ✓ |

> → **今天就能做的画布**：板级动作 ✓ + 完整流程 ✓
> → **要等 ② 的**：片段 ✓

### 4.1 一个**重要的一致性**：画布上的权限 = manifest 的权限 ✓

> 画布上摆了一个 `cpu.governor.set_all` ✓ → manifest 的 `permissions.write` 里**必须**有它 ✓
> → **不然校验器会拦** ✓（规则：`permissions ⊆ requires` ✓ · `requires ⊆ 契约允许的` ✓）
> → **所以画布天然自洽** ✓ —— **摆了什么就写什么** ✓

### 4.2 换一块板，画布会**自动变形** ✓ 🔵

> 画布引用的动作来自**板型包** ✓ → 换板（不同的 `board_pack` ✓）→
> → **那块板上没有的动作，画布上要标成「不可用」** ✓
> → **这正是「同一张工作台服务多块板」的形态** ✓

---

### 4.4 ⭐ **第一个交付物可能不是画布** ✓ —— 对方探索指出的一条既有线索 ⚠️

> **代码里已经有一个 `disabled` 的「AI 造卡 · M7」按钮** ✓
> （`src/renderer/shell/pages/LibraryPage.tsx:86-94` ✓ · 标题写着「**AI 造卡依赖 M7 的 MCP 工具集**」✓）
> → **这个需求的名字早就在代码里了** ✓ —— **它不是新的** ✓
>
> 而 **`cards/workflows/` 已经是「选流程 + 起流程 + 看阶段」的活页** ✓
> → **它就是画布的雏形** ✓
>
> → **所以第一个交付物大概是「把 `cards/workflows` generalize」** ✓
> （让它能摆**任意**流程 ✓ + 任意**输入** ✓ + 任意**动作** ✓ —— 而不只是编译那两条 ✓）
> → **交付物更近** ✓ · **而且画布的 UI 骨架已经有了** ✓
> → 详见 [`11` §二.5](11-两份探索的对账.md) ✓

## 五 · 「一键造卡」的管道（**「一键」的那一下在哪**）🔵

```
  画布（拼装）
     │  ① 导出流程部分 → 流程包 YAML
     │  ② 导出卡片部分 → manifest 骨架
     │  ③ 带上人话
     ▼
  ┌─────────────────────────────────────────┐
  │           一份「造卡规格」                │
  │   （三个文件 + 一段话 + 落位目录名）        │
  └─────────────────────────────────────────┘
     │
     ├──► 交给**人**：照着写 → validate_card ✓ → install_card ✓
     │
     └──► 交给**agent**：（想法④）→ 写文件 → validate_card ✓ → install_card ✓
```

> **「一键」的那一下 = 「把规格交出去」** ✓ —— 不是「代码生成出来」✓
> → **所以这个 feature 的一半是「规格」，一半是「交接」** ✓

### 5.1 「一键生成卡片」的**字面版本**其实也存在 ⚠️

如果不要求「代码由 agent 写」，画布**可以直接生成一张能跑的卡** ✓：
- 生成 `index.html` + `card.js` + `style.css` 的**模板** ✓
- → **但那生成的是「一个只会显示几个数的卡」** ✓ —— **没有交互** ✓
> → **它立刻撞上《11-卡片内部设计规范》那条「一张卡 = 一个主张」** ✓
> → **所以「一键生成的卡」必然平庸** ✓ → **这正是要交给 agent 的理由** ✓

## 六 · 代价

| 项 | 量级 | 说明 |
|---|---|---|
| **画布的数据模型** | 中 | 一份 Canvas 声明 ✓（§三.3 ✓）· **不是新运行时** ✓ |
| **画布的交互** | **大** | 拖放 ✓ · 连线 ✓ · 参数编辑 ✓ · **这才是主要工作量** ✓ |
| **画布 → 规格的导出** | 小 | 三段拼接 ✓ |
| **「造卡」管道** | **零** ✓ | `validate_card` ✓ · `install_card` ✓ **已有** ✓ |
| **人话部分的生成** | 中 | 画布上的元素 → 一句话 ✓ · **可以给模板 + 让 agent 补** ✓ |
| **「新建卡片」入口** | 小 | 卡片库页加一个按钮 ✓ |

**契约影响**：**零** ✓ —— 画布是**宿主侧的东西** ✓ · 产出的卡还是契约里的卡 ✓

## 八 · 一句话

> **画布不是可视化编程，是「把意图结构化」。**
>
> 因为卡片活在**没有构建步骤的沙箱**里 ✓ → 自动生成的代码必然平庸且没人维护 ✓
> → 所以画布的产物是**一份规格** ✓，而**「一键」的那一下是「把规格交出去」** ✓
> —— 交给人也好，交给 agent 也好 ✓（**这就让它与想法④ 解耦了** ✓）。
