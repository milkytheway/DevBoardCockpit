## 二 · 五处分歧

### 2.1 ⚠️ **想法② 的 `include` —— 我错了一半** ⚠️

| | 我的说法 | 对方的说法 |
|---|---|---|
| 主张 | include **不建议** ✓ ——「在封闭的 YAML 格式里做文本包含 = 自造预处理器」✗ | **Codex 的顾虑要拆开看** ✓ —— 那说的是「**纯 YAML、靠锚点跨文件**」✗，**不是「宿主侧预处理」** ✓ |
| 对不对 | **对了一半** ⚠️ —— 我把两种 include 混成了一种 ⚠️ | **对** ✓ |

**拆开之后是这样**：

| include 的两种 | 可行吗 | 判断 |
|---|---|---|
| **纯 YAML 锚点跨文件**（`$ref` 式 ✓） | ❌ | **要改包格式** ✓ → **包格式是封闭的** ✓ → **不值** ✓（我的原意 ✓） |
| **宿主侧预处理**（解析时展开 ✓） | ✅ **可行** ✓ | 已经有 **js-yaml** ✓ + **一个注册表** ✓ + **一个解析入口** ✓ → **技术上不新建机制** ✓ |

> **但代价不在技术，在时机** ⚠️ → **对方给了一条我漏掉的关键实现细节** ✓：
> > **展开必须发生在占位符静态检查之前** ✓ ——
> > 否则被包含进来的步骤引用 `{output:artifacts}` 会被误判成「没有产出这个槽」✗
> > （位置 = `format.ts` 的 `parseWorkflow` 之内 ✓ · `checkPlaceholders` 之前 ✓）
>
> → **这条是硬的** ✓ —— 顺序错了，展开进来的步骤**全部误判** ✗

**修正后的判断** ✓：
> include **不是「不可行」** ✓，而是「**可行但没必要**」✓ ——
> 因为 **fragment 能吃到同样的复用收益 ✓，却不引入预处理顺序这个坑** ✓
> → **我的结论（先做 fragment）不变** ✓，但**理由要换** ✓：
> ~~「格式撑不住」✗~~ → 「**fragment 的收益一样，成本低一个数量级**」✓

### 2.2 ⚠️ **想法② 的 `call` —— 我漏了一条硬要求** ⚠️

我列了五条（角色映射 ✓ · 槽隔离 ✓ · 取消穿透 ✓ · 审计归属 ✓ · 递归限深 ✓），
**对方补了第六条，而且它比我的五条都硬** ⚠️：

> **今天没有环检测** ✓ —— `runner.ts:190` 是个**普通 for 循环** ✓，**没有 visited 集合** ✓
> → **唯一的屏障是「step kind 是封闭的」** ✓
> → **call 一开，那个屏障就没了** ⚠️ → **必须同时有 visited** ✓

> → **这条我认** ⚠️ —— 它不是「多一条语义」，它是「**不做这件事，call 就不能开**」⚠️

**还补了一条更简单的约定** ✓：
> 审计归属现在只有一个**扁平的 actor 串** ✓（`workflow:<pack.id>` ✓）→
> 嵌套时**父流程是谁** ✓ → **要么加字段** ✓，**要么约定「嵌套里的审计行归子流程」** ✓（**更简单** ✓）→ **我倾向后者** ✓

### 2.3 ⚠️ **想法① 的「枚举 COM」—— 我说得太轻** ⚠️

我的第一版设计里有「自动枚举 COM」✓，第二轮已按用户意见**删掉** ✓。
但**对方指出**：**就算以后要做，也不是一行代码** ⚠️ →

| 路 | 怎么列 | 能列出 **CH343** 吗 |
|---|---|---|
| node-serialport 的 `SerialPort.list()` ✓ | 走 serialport 自己的枚举 ✓ | ⚠️ **列不出** ✓（`docs/02:211` ✓ —— 旧工程为此专门用了 pyserial ✓） |
| **Windows 设备查询** ✓ | `Get-CimInstance Win32_PnPEntity` / `Win32_SerialPort` ✓ 按「USB-SERIAL CH343」匹配 ✓ | ✅ **能** ✓（这类 USB 转串口**以设备而非 COM 口枚举** ✓） |

→ **向导第一步要做的是「把这两个来源合起来去重」** ✓ —— **不是只加一行** ✓

> → **这条对我们当前的结论没有影响** ✓（用户已定：**手动选** ✓）→
> 但它**修正了「以后做自动枚举」的成本估计** ✓ → 已补进 [`02`](02-想法一-接板向导.md) 的「未来项」✓

### 2.4 ⚠️ **想法④ —— 我漏掉了最安全的第一形态** ⚠️ ⚠️

> **这是本次对账最重要的修正** ✓

我给的形态全是**出站方向**的（推送 ✓ · 投递 ✓ · 拉起 ✓），
而**对方指出还有第 0 形态** ✓ —— **而且它最安全** ✓：

| 序 | 形态 | 怎么做 | 出站？ | 要探测 agent 吗 |
|:--:|---|---|:--:|:--:|
| **0** | ⭐ **让 agent 自己来看** | 宿主在 **MCP 上开一条 `list_tasks`** ✓ → **agent 轮询** ✓ | **零出站** ✓ | **不需要** ✓ |
| 1 | 投递到文件 | 写进 `tasks_dir` ✓（**与 `cards_dir` 同款** ✓） | 零出站 ✓ | 不需要 ✓ |
| 2 | 推送 | 写一个「有活了」的标记 ✓ → **人自己看** ✓ | 零出站 ✓ | 不需要 ✓ |
| 3 | 拉起 | 起一个进程 ✓ | **有出站** ✓ | **要探测** ✓ |

> **形态 0 为什么最安全** ✓：
> → **方向没变** ✓ —— 仍然是 **agent → 宿主** ✓（**入站** ✓）
> → **权限模型一个字不用动** ✓ → 「宿主给 agent 授权」这件事**根本不存在** ✓
> → **而且它复用了现成的通道** ✓（**MCP 就是给 agent 用的** ✓ —— 发现文件 ✓ · token 认证 ✓ · loopback ✓）

**还有一条关键的澄清** ✓：
> **「活」是什么** → **活 = 一个流程包 id + 一组输入** ✓ —— **不是新东西** ✓
> → **④ 不需要新的产物类型** ✓ → **不需要新的契约** ✓
> → **而且它让 ② 与 ④ 咬合** ✓：**② 的可复用粒度 = ④ 能派什么活** ✓

> **这条我完全认同** ✓ —— 它比我写的「推送 / 投递 / 拉起」**更省** ✓，
> 而且它把「探测主机上有什么 agent」**整个推到最后** ✓（**探测是形态 3 的前置** ✓ → **形态 3 最晚做** ✓ → **探测也最晚做** ✓）

### 2.5 ✅ **想法③ 的第一个交付物 —— 互补（他们更准）** ✓

我的结论：**画布** ✓。对方的结论：**第一个交付物不是画布，是「把 `cards/workflows` generalize」** ✓

**证据在代码里** ✓ —— 卡片库里那个 **`disabled` 的「AI 造卡 · M7」按钮** ✓（`LibraryPage.tsx:86-94` ✓）
