# 03 · 想法二：流程包可组装 —— 流程由动作组装，那流程能不能由流程组装？

> **作者**：Codex　**日期**：2026-11-17　**性质**：**探索**（不约束任何人 ✓）
> **想法原文**：「如何优化流程包的架构，使其可组装？一个流程是由各个元操作组装起来的，
> 流程与流程之间使其也可以进行组装？例如流程中的一个节点可插入另一个流程。
> 这只是一个想法，似乎具有更大的潜力但是目前想不到应用。因为一个卡片似乎也可以包含多个不同的流程」

---

## 〇 · 结论先行

0. **⭐ 想法② 已经在代码里发生了** ✓ —— DSH v0.11 把编译流程拆成三段，
   **同一段步骤被复制了三份** ✓，**参数已经开始漂** ✓ → **这不是设想，是压力** ✓（§1.4 ✓）
1. **想法的一半已经实现了** ✓ —— 流程**已经是**动作的组装 ✓（`action` 步 ✓），
   而「**一张卡包含多个流程**」**今天就能做** ✓（卡片 manifest 的 `workflows` ✓ · DSH 的 `workflows` 卡就是这么干的 ✓）
2. **剩下的那一半，难点不在语法，在语义** ⚠️ —— 子流程的**角色映射 / 槽隔离 / 取消穿透 / 审计归属 / 递归限深** —— 这五件事
3. **三种形态的代价差一个数量级** ✓：
   **include（文本包含）≈ 没有预处理器的包格式撑不住** ✗ ·
   **fragment（参数化片段）= 复用，语义最轻** ✓ ·
   **call（嵌套运行）= 编排，语义最重** ⚠️
4. **建议从 fragment 开始** ✓ —— 它能吃到「复用」这个**最大的实际收益** ✓，
   而**完全不引入嵌套运行语义** ✓（取消 / 审计 / 超时 / 权限都不用穿一层 ✓）
5. **组合会放大权限面** ⚠️ —— 契约 §7.4 已经要求「**必须展示这个流程会在哪些目标上跑哪些命令**」✓
   → 组合后这个展示必须**递归展开** ⚠️ → **这是组合带来的新治理负担** ✓
6. **call 形态要动契约** ✓（加第 7 种 step kind ✓）→ **先证明真的需要它** ✓ → 再评审 ✓

## 一 · 现状：组装已经存在，只是不能往上再组装一层 🟢

### 1.1 现在的两级组装 🟢

```
第 1 级：动作 → 流程          ✅ 已实现
         板型包的 actions（15 条 ✓）→ 流程的 action 步 ✓

第 2 级：流程 → 流程          ❌ 不存在
         step kind 是 6 种**封闭**的（spec/05 §4.1 ✓ / format.ts:64 ✓）
```

> **六个 kind** 🟢：`exec` · `discover` · `file.transfer` · `action` · `await` · `assert` ✓
> → **没有「调另一个流程」这一种** ✓ → 这就是想法② 的**确切缺口** ✓

### 1.2 「一张卡包含多个流程」—— **已经存在** 🟢

卡片 manifest 里的 `permissions.workflows` 是一张**清单** ✓ → **一张卡可以声明多条流程** ✓

> **实证**：DSH 的 `workflows` 卡（`cards/workflows/` ✓）声明了 **6 条流程** ✓
> （板子体检 / 厂商自检 / 相机抓帧 / 网络测速 / authorized_keys / 存储测速 ✓）
> → **想法③ 里的「一张卡包含多个不同的流程」✓ 今天就是那样** ✓

### 1.3 所以想法② 真正剩下的是什么？ 🟢

| 想法里的说法 | 今天的状态 |
|---|---|
| 「一个流程是由各个元操作组装起来的」 | ✅ **已经如此** ✓ |
| 「流程与流程之间也可以组装」 | ❌ **缺的就是这一句** ✓ |
| 「一个卡片似乎也可以包含多个不同的流程」 | ✅ **已经如此** ✓ |

> → **想法② 收敛成一句话**：**能不能让一个流程的某一步 = 另一个流程** ✓

### 1.4 ⭐ **想法② 已经在代码里发生了** —— 只是没有机制，所以用了「复制粘贴」 🟢

> **这一节是本篇最重要的一节** ✓ —— 它把想法从「设想」变成「**已经在冒头的压力**」✓

**2026-11-17（DSH v0.11）** 把「编译上板」**拆成了三段** ✓：

| 流程包 | 步骤 | 🟢 出处 |
|---|---|---|
| `hello-kernel.build-run` | compile · artifacts · deliver · load · assert-loaded（**5 步** ✓） | `profiles/workflows/` ✓ |
| `hello-kernel.compile` | compile · artifacts（**2 步** ✓） | ✓ |
| `hello-kernel.upload` | artifacts · deliver（**2 步** ✓） | ✓ |
| `hello-kernel.load` | load · assert-loaded（**2 步** ✓） | ✓ |

> → **同一段步骤被复制了三份** ✓ —— **这正是「复用」诉求在真实压力下浮现的样子** ✓
> → **想法② 不是空想** ✓ —— **它已经在仓库里了** ✓

#### 而复制的代价**已经开始收了** 🟢

| 代价 | 证据 |
|---|---|
| **① 同一个参数有四种说法** | `build_dir` 在 `build-run` 里 **required: true**（无默认值）✓；在 `compile` / `upload` 里是 **`required: false` + `default: /home/alientek/kernel-build`** ✓ → **已经漂了** ✓ |
| **② 产物名的语义对不上** | `load` 的参数叫 **`module`**（默认 `hello` ✓）✓；而 `build-run` 里的产物名是**自动发现的**（`{output:artifacts.name}` ✓）→ **一个用发现、一个用手填** ✓ → **两边会对不上** ⚠️ |
| **③ 子流程之间传不了产物** | `upload` **又做了一次 `discover`** ✓（与 `compile` / `build-run` **完全重复** ✓）→ **因为独立的流程之间没有共享槽** ✓ → **只能自己再发现一次** ✓ → **多一次往返** ✓，而且**产物被清掉时会失败而不是用上一步的结果** ✓ |
| **④ 四份 YAML 描述同一件事** | `build-run` 与三个子流程**并存** ✓ → **改一处要改四处** ⚠️ |

> #### → **这就是「组装机制」要解的四件事** ✓
>
> | 现象 | 要的机制 | 对应形态 |
> |---|---|---|
> | 参数四种说法 | **单一来源** ✓ | **fragment**（片段的参数在一处声明 ✓） |
> | 产物名对不上 | **槽能跨片段传** ✓ | **fragment**（片段的 `out` 进调用方的槽 ✓） |
> | 子流程传不了产物 | **同上** ✓ | **fragment** |
> | 改一处要改四处 | **片段被引用，而不是被复制** ✓ | **fragment** |
>
> → **四件事里，三件是 fragment 能解的** ✓ → **call 一次也解不了** ✓
> → **这给「先做 fragment」提供了来自真实代码的证据** ✓（而不是我的偏好 ✓）

## 二 · 先把「组装」拆成**三种不同的需求** 🔵

用户的描述里混着三件事，**它们的代价差很多**：

| # | 需求 | 例子 | 需要什么 |
|---|---|---|---|
| **N1 复用** | 「这段步骤我在三个流程里都要用」 | 「传文件 + 落位 + 验证」在两个编译流程里重复 ✓ | **片段能引用** ✓ |
| **N2 参数化** | 「同一段步骤，每次参数不同」 | 「传文件」的源/目的/路径每次不同 ✓ | **片段能带参数** ✓ |
| **N3 编排** | 「这一步本身就是一个完整的事」 | 「编译上板」这一整件事嵌进「上电 → 编译 → 验证」的流程里 ✓ | **子流程能作为一步运行** ✓ |

> → **N1 + N2 是「fragment」能解决的** ✓ · **N3 才是「call」** ✓
> → **它们不是一回事** ✓ → **分清楚才能选对** ✓

## 三 · 三种形态：语义与代价

### 形态 A · include（文本包含）❌

```yaml
# 想这样写 —— 但 YAML 没有预处理器
steps:
  - include: common/transfer.yaml
    with: { source: build }
```

| 维度 | 评估 |
|---|---|
| 复用 | ✅ 能 |
| 参数化 | ⚠️ 要自己写预处理器（**包格式是封闭的** ✓ → **没有预处理器的位置** ✗） |
| 运行语义 | ✅ 展开后就是普通步骤 ✓ |
| 取消 / 审计 / 超时 | ✅ **不用穿层** ✓ |
| 校验 | ⚠️ 展开要在**校验时**做 → 「静态检查占位指向的东西都存在」（契约 §九 规则 10 ✓）得在展开后跑 |
| **结论** | ❌ **在封闭的 YAML 格式里做文本包含 = 自造预处理器** ✓ → **不值** ✓ |

> → **对方探索提醒了一个我漏掉的分层** ✓ —— 「include」有**两种** ✓，别混：
>
> | include 的两种 | 可行吗 | 判断 |
> |---|---|---|
> | **纯 YAML 锚点跨文件**（`$ref` 式 ✓） | ❌ | 要改**包格式** ✓ → 包格式封闭 ✓ → **不值** ✓ |
> | **宿主侧预处理**（解析时展开 ✓） | ✅ **可行** ✓ | 已有 **js-yaml** ✓ + 注册表 ✓ + 解析入口 ✓ → **技术上不新建机制** ✓ |
>
> ⚠️ **但代价不在技术，在时机** ✓ —— **展开必须发生在占位符静态检查之前** ✓
> （位置 = `format.ts` 的 `parseWorkflow` 之内 ✓ · `checkPlaceholders` 之前 ✓）→
> 否则展开进来的步骤引用 `{output:artifacts}` 会被**误判成「没有产出这个槽」** ✗
>
> → **结论不变**（先做 fragment ✓），但**理由要换** ✓：
> ~~「格式撑不住」✗~~ → 「**fragment 收益一样、成本低一个数量级**」✓
> → 详见 [`11` §二.1](11-两份探索的对账.md) ✓

### 形态 B · fragment（参数化片段）✅ **推荐先做**

> **片段不是一个能运行的流程**，**它是一段可被引用的步骤模板** ✓

```yaml
# profiles/workflows/_fragments/transfer-and-verify.yaml
kind: Fragment            # ← 新的一类，但不是「新的一种 step」
id: transfer-and-verify
inputs:
  source: { type: path, required: true }
  dest:   { type: path, required: true }
steps:
  - id: deliver
    kind: file.transfer
    from: { role: "{input:from_role}", path: "{input:source}" }
    to:   { role: "{input:to_role}",   path: "{input:dest}" }
    readback: { kind: verify, role: "{input:to_role}", command: "test -f {to.path}" }
```

```yaml
# 引用它的流程
steps:
  - id: deliver
    kind: fragment          # ← 第 7 种 step kind
    fragment: transfer-and-verify
    params:
      from_role: build
      to_role: target
      source: "{output:artifacts}"
      dest: "{input:dest_path}"
```

| 维度 | 评估 |
|---|---|
| 复用 + 参数化 | ✅ **都解决** ✓ |
| 运行语义 | ✅ **展开成普通步骤** ✓ → **取消 / 审计 / 超时 / 权限都不用穿层** ✓ |
| 校验 | ✅ 展开后跑现有的静态检查 ✓ |
| 角色 | ⚠️ **片段里的 role 必须由调用方给** ✓（否则片段自己绑 profile → **机器专属的值进包** ✗ → **违反契约 §三 的规矩** ✓） |
| 递归 | ✅ **片段不能含片段** ✓（一层 ✓ → 无限套娃的风险直接没有 ✓） |
| 契约影响 | ⚠️ **加一种 step kind** ✓ → **要评审** ✓（ADR-D15 ✓） |

> → **fragment 的代价 = 展开期的工作** ✓，**收益 = 复用与参数化** ✓
> → **它是「组合」里最便宜的那一半** ✓

### 形态 C · call（嵌套运行）⚠️

```yaml
steps:
  - id: deploy
    kind: workflow          # ← 第 7 种 step kind（另一个语义）
    workflow: hello-kernel.build-run
    params: { project: "{input:project}" }
    roles: { build: build, target: target }   # ← 角色映射 ★
```

| 维度 | 评估 | 难点 |
|---|---|---|
| 编排 | ✅ **能** ✓ | |
| **角色映射** | ⚠️ | 子流程有自己的 `roles`（绑 profile ✓）→ **父的角色要映射给子的角色** ✓ → **新的语义** ✓ |
| **槽隔离** | ⚠️ | 父的 `{output:x}` 与子的 `{output:y}` **同名怎么办** ✓ → 要命名空间 ✓ |
| **取消穿透** | ⚠️ | 父取消 → 子必须停 ✓ → `AbortSignal` 透传 ✓（契约 §八·A 已有 ✓ → **可复用** ✓） |
| **审计归属** | ⚠️ | 子流程的每一步**单独记一行** ✓（契约「两个事实、两行账」的既有原则 ✓）→ 但**父这一步记什么** ✓ → **约定「嵌套里的审计行归子流程」** ✓ 比加字段简单 ✓ |
| **超时** | ⚠️ | 父这一步的超时**管不管子** ✓ → 两个超时谁先到 ✓ |
| **递归限深** | ⚠️ | 子流程里再调 → **必须限深** ✓（防环 ✓） |
| **环检测** | ⚠️⚠️ | **今天没有** ✓ —— `runner.ts` 是个**普通 for 循环** ✓，**没有 visited 集合** ✓ → **唯一的屏障是「kind 封闭」** ✓ → **call 一开，那个屏障就没了** ⚠️ → **必须同时上 visited** ✓ |
| **权限面** | ⚠️ | 父 + 3 子 = 4 份命令 → 权限区要**递归展开展示** ✓（契约 §7.4 ✓） |
| 契约影响 | ⚠️ **大** | 加 step kind + 角色映射 + 槽命名空间 + 取消语义 **四条契约一起动** ✓ |

> → **call 是四项语义一起上** ✓ → **不该在没有证据前就上** ✓

## 四 · 推荐路径：**先 B，再看要不要 C**

### 4.1 为什么先 B 🔵

| 理由 | 说明 |
|---|---|
| **收益先到** | 「这段步骤重复了」是**当下就存在**的问题 ✓（两个编译流程的「传 → 落位 → 验证」高度相似 ✓） |
| **成本最低** | 展开期的工作 ✓ → **取消 / 审计 / 超时 / 权限全都不穿层** ✓ |
| **风险最低** | 片段**不能嵌套** ✓ → **递归 / 环 / 深度**这些坑**直接不存在** ✓ |
| **它是 C 的前置** | 若将来真要 C，**fragment 可以直接升格成 call 的输入** ✓（片段是「无运行时的流程」✓ → call 的子流程是「有运行时的流程」✓ → **同一个概念的两面** ✓） |

### 4.2 一条**中间路线**：把「可复用的流程」先做成**更完整的东西** 🔵

> 用户说「似乎具有更大的潜力但是目前想不到应用」——**这句话是对的**，
> 而且**潜力恰恰在于它不只是一种复用机制** ✓。
>
> **fragment 一旦存在，就同时是三样东西** ✓：
>
> | 身份 | 用在哪 |
> |---|---|
> | **复用单元** | 流程引用它 ✓ |
> | **画布的元件**（想法③） | 画布上摆的「积木」✓ —— **fragment 是天然的积木** ✓ |
> | **agent 的词汇**（想法④） | agent 看到的「可用的动作」清单里既有**板级动作**也有**流程片段** ✓ |
>
> → **fragment 是①②③④ 四条线的公共地基** ✓ → **它比「子流程」更值得先做** ✓

## 五 · 组合带来的**新治理负担** ⚠️

### 5.1 契约已经有一条要求 🟢

> `spec/05` §7.4：**权限区里必须展示「这个流程会在哪些目标上跑哪些命令」** ✓

### 5.2 组合之后，这条要求**变重了** ⚠️

| 形态 | 「这个流程会跑什么」的答案 |
|---|---|
| 今天 | **这个包的步骤** ✓ —— 一层 ✓ |
| fragment | **这个包的步骤 + 每个 fragment 展开后的步骤** ✓ —— 两层 ✓ |
| call | **递归展开** ⚠️ —— **深度不定** ✓ → **必须限深** ✓ |

> → **组合越深，权限区的「展开」越重要** ✓
> → **而权限区是「一行一个操作」** ✓（ADR-D47 ✓）→ **一行怎么装得下一个递归展开的清单** ⚠️？

> → **这是想法② 最该先想清楚的一件事** ✓：
> **权限区一行 = 一个操作** ✓，那**一个流程**（内含多个子流程）**算几个操作** ✓？
> → 我倾向于：**流程算一个操作** ✓（它的内部是**它自己的**事 ✓），
> 但**展开清单必须能展开看** ✓（点进去看到全部命令 ✓）✓

### 5.3 一条**不能忘**的纪律 🟢

> ADR-D48：**危险等级只是信息，闸在权限区的开关上** ✓
> → 组合之后**仍然如此** ✓：一个组合流程**整体是一个开关** ✓，
> 它的内部命令**不再逐条问** ✓ —— 否则组合一次问一遍，**没人愿意用组合** ✓

## 六 · 代价

| 形态 | 契约 | 实现量 | 新语义 | 风险 |
|---|---|---|---|:--:|
| A include | 加 kind | 中 | 预处理器 | **建议排除** ✓ |
| **B fragment** | **加 1 种 kind + 片段格式** ✓ | **中** ✓ | **角色由调用方给 + 槽同名空间** ✓ | **低** ✓ |
| C call | 加 kind + **四条语义** ✓ | **大** ✓ | 角色映射 / 槽隔离 / 取消穿透 / 审计归属 ✓ | **高** ⚠️ |

**共同的前置**：**片段目录的约定** ✓（`_fragments/`？✓ · 还是单独一个根 ✓）→ 要拍板 ✓

## 八 · 一句话

> **「流程组装」不是一个特性，是三个** —— 复用、参数化、编排 ✓
> → **前两个用 fragment 一次拿下** ✓（而且它顺带成了画布的积木 ✓ 与 agent 的词汇 ✓）
> → **编排（call）要动四条契约语义** ✓ → **等真实需求出现再上** ✓
>
> 而且**想法里「已经想到」的那一半** ——「一张卡包含多个流程」✓ —— **今天就能做** ✓。
