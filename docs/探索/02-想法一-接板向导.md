# 02 · 想法一：接板向导 —— 从「选一个 COM 口」到「这块板被完整接进来」

> **作者**：Codex　**日期**：2026-11-17　**性质**：**探索**（不约束任何人 ✓）
> **想法原文**：「如果要添加一个引导界面帮助添加一块板，标准以串口开始，选择 com 和波特率后。
> 尽最大可能的探索出连接板子的方式，该怎么设计和怎么做？才能使其具备能力尽可能广泛的支持接入一张新板？」

---

## 〇 · 结论先行

1. **「串口优先」是对的，而且比想象的更对** —— 串口**不是一种传输，是一条万能探测通道** ✓
   （它给你一个 **root shell** ✓ → 板子自己的 IP、型号、SSH 状态**都能问出来** ✓）
2. **向导的形状不是「填表」，是「一条发现链」** ✓：
   **枚举 COM → 试波特率 → 问板子 → 推荐其他连接 → 匹配板型包 → 探针 → 生成三条连接** ✓
3. **「广泛支持新板」的真问题不是「多接几种传输」，是「没见过的板也能接进来」** ✓
   → 关键是**发现式建板型包** ✓（§五 ✓）
4. **契约零改动** ✓ —— profile schema 已封闭且够用 ✓（`src/main/profiles/schema.ts` ✓）
5. **代价**：新增 `connections:*` 的写 IPC ✓ + 一个向导页 ✓ + **COM 枚举与试波特率** ✓ +
   **发现式建包**（最重的一块 ✓）✓
6. **最该先做的不是向导，是「能不能枚举 COM 口」** ✓ —— 那是一行 `SerialPort.list()` ✓，
   **但它今天不存在** ✓（`src/main/hal/serial.ts` ✓）

## 一 · 现状：今天加一块板要做什么 🟢

### 1.1 实际步骤（**手写 JSON** ✓）

```jsonc
// profiles/targets/board-serial.json
{
  "id": "board-serial",
  "label": "板子 · 串口",
  "transport": "serial",
  "board_pack": "rk3588-atk",
  "device_key": "atk-01",          // ← 板实物与连接是两层（契约增量 v6 ✓）
  "options": {
    "port": "COM3",                  // ← **用户得自己知道是哪个 COM** ✓
    "baudrate": 1500000,             // ← **用户得自己知道波特率** ✓
    "pty": true,
    "prompt": "root@ATK-DLRK3588",
    "commands": "serial",
    "ssh": { "host": "192.168.5.100", "port": 22, "username": "root" }
  }
}
```

### 1.2 三个**真实的洞** 🟢

| # | 洞 | 出处 |
|---|---|---|
| **A** | **没有「新建连接」的入口** —— 连接相关的 IPC **只有 `connections:list` 一个** ✓ | `src/shared/ipc-contract.ts:23` ✓ |
| **B** | **串口不能枚举 COM 口** —— profile 必须**已经知道** `port` 与 `baudrate` ✓ | `src/main/hal/serial.ts`（**全文无 `SerialPort.list()`** ✓） |
| **C** | **波特率写死在人脑里** —— 代码默认 115200 ✓，而这块板是 **1500000** ✓ | `src/main/hal/serial.ts`（`?? 115200` ✓）· `docs/02:44` ✓ |

> → **用户第一次接板，要先知道「串口是 COM3、波特率 1500000」** ✓
> → 而这个知识**只有读过那份手册的人才有** ✓
> → **向导要消除的正是这个门槛** ✓

### 1.3 但工程**已经有三块地基** ✓

| 地基 | 是什么 | 出处 |
|---|---|---|
| **探针** | `probePack` 逐个 reader 试 → 报告哪些绿、哪些红、**并给出「这板不提供」还是「读错了」** ✓ | `src/main/tags/probe.ts` ✓ |
| **自动识别** | 板型包 `match.models` ↔ 板子 `/proc/device-tree/model` ✓ | `spec/02` ✓ · `board.yaml` ✓ |
| **三条连接共享一块板** | `device_key` ✓（契约增量 v6 ✓）· `options.ssh` 让 ADB 连接也带 SSH 端点 ✓ | `spec/02` §10.2/§10.3 ✓ |

> → **向导不需要发明什么** ✓ —— 它需要**把已有的三块地基串起来** ✓，
> 再补上**「枚举」与「试波特率」**两块 ✓。

## 二 · 为什么「串口优先」不只是「习惯」——**它是一条万能通道** 🟢

### 2.1 串口的特殊性 🟢

| 事实 | 出处 |
|---|---|
| 串口是**唯一的「零配置」传输** —— 不需要 IP、不需要配对、不需要驱动栈 ✓ | 通用事实 ✓ |
| **这块板的调试串口是 root shell** —— 「root 用户自动登录」✓ | 《快速体验手册》§1.4 ✓ |
| 波特率 **1500000**（1.5M）✓ | `docs/02:44` ✓ · 手册 §1.2 ✓ |

> → **串口一通，你就有了板子自己的 root** ✓
> → **板子关于它自己的所有事实，都能问出来** ✓
> → **所以串口不是「第一条路」，是「问路的那条路」** ✓

### 2.2 串口能问出的事实（**全部实测过** ✓）

| 问什么 | 命令 | 得到的 | 能推出什么 |
|---|---|---|---|
| **型号** | `cat /proc/device-tree/model` | `ATK-DLRK3588 Board`（**带尾随 NUL** ✓） | **匹配板型包** ✓（`match.models` ✓） |
| **本机 IP** | `ip -br addr show` | `eth0 UP 192.168.5.100/24` ✓ | **直接建 SSH 连接** ✓ |
| **网口状态** | 同上 | `eth1 DOWN` ✓ `wlan0 DOWN` ✓ | 「还有哪个口能用」✓ |
| **SSH 在不在** | `netstat -ltn \| grep :22` | 有/无 ✓ | **要不要建议 SSH** ✓ |
| **USB gadget 在不在** | `ls /sys/class/udc` | 有/无 ✓ | **要不要建议 ADB** ✓ |
| **主机名** | `cat /etc/hostname` | `ATK-DLRK3588` ✓ | **一个可读的设备名** ✓（比 `device_key` 好看 ✓） |
| **内核** | `uname -r` | `6.1.141` ✓ | **板型包的适用性** ✓ |

> → **一次串口会话 = 一份「板子自述」** ✓
> → **向导的推荐就基于这份自述** ✓ —— 不是猜 ✓

### 2.3 三条连接的关系（**这是设计上最漂亮的一点** ✓）

```
                    ┌──────────────────────────────┐
   串口（永远可用） ──▶│        一块板（device_key）   │
   COM3 / 1500000    │   型号 · IP · 内核 · 能力      │
                    └──────────────────────────────┘
                        ▲            ▲
                        │            │
              ADB（USB 直连）    SSH（串口问出来的 IP）
              自动发现            凭据要问人
```

→ **一块板三条连接** ✓ —— 这正是 `device_key` 存在的理由 ✓（契约增量 v6 ✓）
→ **向导要做的是：把三条连接一次性建出来，并绑到同一个 `device_key`** ✓
→ **而不是让用户建三次** ✓

## 三 · 发现的六步链

```
① 选串口
   ├─ 枚举 COM 口（Windows PnP / WMI / serialport 的 list）
   ├─ 显示：COM3 (CH343 USB-UART) · 厂商 ID/描述
   └─ 选一个 → 进 ②
        ↓
② 试波特率
   ├─ 候选表：1500000 / 115200 / 921600 / 57600 / 38400
   ├─ 判据 = **板子的 banner**（不是「有没有回显」！）
   │   → 认 root@ATK-DLRK3588 / Buildroot / u-boot 关键字
   ├─ 试到就停，并**记住这个组合**（存进 profile ✓）
   └─ 全试不通 → 给出「换一个 COM 口 / 换波特率 / 用 ADB 直连试试」
        ↓
③ 问板子（一次串口会话，跑一组只读命令）
   └─ 型号 / IP / 网口 / SSH / USB gadget / 主机名 / 内核
        ↓
④ 推荐并生成连接（**建议，不是自动落盘** ✓）
   ├─ 串口 profile（**永远建** ✓ —— 它是保底通道 ✓）
   ├─ ADB profile（USB 插上了才建议 ✓）
   └─ SSH profile（串口问到了 IP 才建议 ✓ · 凭据要问人 ✓）
        ↓
⑤ 匹配板型包
   ├─ 用型号匹配 `profiles/boards/*/board.yaml` 的 match.models
   ├─ 命中 → 绑定 ✓
   └─ 没命中 → 进 §五 的「发现式建包」✓
        ↓
⑥ 探针
   └─ probePack 跑一遍 → 哪些 reader 绿 / 哪些红 / 为什么红
```

### 3.1 第②步的判据：**不是「有回显」，是「认得出板子」** 🟢

> **为什么重要** 🟢：串口上**任何波特率都可能「有回显」**（乱码也是回显 ✓）。
> → 用「有没有回显」当判据 = **假阳性** ⚠️
> → 正确判据 = **认得出板子的特征串** ✓（`root@ATK-DLRK3588` ✓ / `Buildroot` ✓ / u-boot 的 `U-Boot` ✓）
>
> → 这正是 `docs/02` 事实 A3 记的那套「认 banner 而不是认提示符」的做法 ✓
> → **向导要复用它** ✓ —— 不要发明第二套识别逻辑 ✓

## 四 · 方案：三层

### 层① · **枚举与试波特率**（纯 host 能力）🟢

| 要做的 | 说明 |
|---|---|
| `listSerialPorts()` | Windows：PnP 设备枚举（`Get-CimInstance Win32_PnPEntity` 或 serialport 自带 ✓）→ 返回 `{path, manufacturer, description}` ✓ |
| `probeSerialBaudRate(path, candidates)` | 逐个试 ✓ → 认 banner ✓ → 返回 `{baudrate, banner, model?}` ✓ |

> **落点**：`src/main/hal/serial.ts` 旁边新增一个 `serial-discovery.ts` ✓
> **测试**：`SerialPortFactory` **已经是可注入的** ✓（`src/main/hal/serial.ts:58` ✓）→
> 枚举与试波特率都能**用假实现测** ✓ —— 好 ✓

### 层② · **问板子**（一次串口会话）🟢

> ⚠️ **关键约束**：串口**一次只能跑一条命令** ✓（事实 A5/A6 ✓）→ **问一次 = 一条命令** ✓
> → **一条命令问出全部事实** ✓（用 `;` 或换行串起来 ✓ —— **但要过危险地板的检查** ✓）

```sh
# 一条命令，七个事实（⚠️ 每一条都是只读 ✓）
echo MODEL=$(cat /proc/device-tree/model | tr -d '\0');
     IP=$(ip -br addr show);
     HOST=$(cat /etc/hostname);
     KERNEL=$(uname -r);
     SSH=$(netstat -ltn 2>/dev/null | grep -c ':22 ');
     UDC=$(ls /sys/class/udc 2>/dev/null | wc -l)
```

> → **一次往返** ✓（契约 §3.2 的精神 ✓）→ **符合事实 A5/A6** ✓

### 层③ · **建议 + 生成**（**不自动落盘** ✓）

向导的最后一屏 = **一张「建议清单」** ✓：

```
将为「ATK-DLRK3588」建立 3 条连接：

  ✓ 板子 · 串口   COM3 @ 1500000     ← 已验证通 ✓
  ○ 板子 · ADB    自动发现          ← 请插上 USB 数据线后重试
  ✓ 板子 · SSH    192.168.5.100    ← 已验证通 ✓ · 凭据：⸺ 待填

  板型包：rk3588-atk（按型号自动匹配 ✓）
  探针：7 个 reader · 6 绿 1 红（背光1 不存在 —— 这板只有一个背光 ✓）

  [ 全部建立 ]   [ 只建串口 ]   [ 取消 ]
```

→ **人点一下才落盘** ✓（Q1 ✓）
→ **理由不是「谨慎」，是「自动写一个会执行命令的东西」** ⚠️ → 必须人审 ✓

## 五 · 「广泛支持新板」的**真问题**：发现式建板型包 🟢

### 5.1 为什么这是关键 🔵

用户问的是「**能力尽可能广泛地支持接入一张新板**」。

| 理解 | 覆盖范围 | 评价 |
|---|---|---|
| ❌ 「支持更多种传输」 | 4 种传输已封闭 ✓（约束④ ✓） | **天花板已经在了** ✓ |
| ✅ 「**没见过的板也能接进来**」 | **无限的板** ✓ | **这才是真问题** ✓ |

> → **传输层没有扩展空间** ✓（`TransportKind` 封闭 ✓）→
> → **扩展空间在「板型包」这一层** ✓ → **发现式建包**才是「广泛」的关键 ✓

### 5.2 一条**从串口出发的自动发现链** 🔵

```
cat /proc/device-tree/model          → 型号         → match.models 匹配
cat /proc/cpuinfo | grep 'model name' → CPU 型号     → cpu.* 标签
ls /sys/class/devfreq/               → 有哪些 devfreq → gpu.freq_hz / npu.freq_hz
  + cat */load                       → 值长什么样    → 判断是 duty 还是 utilization ★
ls /sys/class/thermal/thermal_zone*/ → 几个温区      → temp.soc / temp.gpu / temp.npu
cat /proc/meminfo                    → 有内存        → mem.* 标签
ls /sys/class/backlight/             → 几个背光      → backlight / backlight1 ★
cat /sys/class/leds/                 → 有没有 LED     → led.set 的前提
```

★ = **语义要人来定** ✓（这正是 `docs/06` C1/C7 那一类坑的来源 ✓ —— **NPU 的 load 文件是占空比不是利用率** ✓ → **自动猜会猜错** ✓）

### 5.3 产出物：**一份草稿包 + 一份「我猜了什么」的清单** 🔵

```yaml
# 草稿（**必须人审** ✓ —— 猜错就是错的读数 ✓）
id: my-new-board
name: （人填）
match: { mode: exact, models: [从 /proc/device-tree/model 读到的] }
readers:
  - id: npu
    kind: rknpu_load
    args: { path: /sys/kernel/debug/rknpu/load }
    provides: [{ tag: npu.usage, sample: usage }]
    # ⚠️ **猜的** ⚠️ → 必须标出来 ✓
    _provenance: guessed
```

> → **每条猜的都要标出来** ✓ → **人只需审「猜的那几条」** ✓ → 审的成本从「读懂整个板型包」降到「看几行」✓
> → **这是本节最重要的一条** ✓

### 5.4 与既有机制的关系 🟢

| 机制 | 关系 |
|---|---|
| `validate:profiles` ✓ | **草稿先过校验器** ✓ → 语法错当场发现 ✓ |
| `probe:board` ✓ | **草稿先过探针** ✓ → 猜错的 reader **当场变红** ✓ |
| `docs/06` 的 C* 条目 ✓ | 猜错的地方**记进核对表** ✓ —— **自动发现不能取代契约评审** ✓ |

> → **发现式建包不是「绕过契约」，是「用契约的工具造一份待评审的草稿」** ✓

## 六 · 代价

| 项 | 量级 | 说明 |
|---|---|---|
| `connections:add` / `connections:probe` IPC | 小 | 现有 `connections:list` 的兄弟 ✓ |
| 串口枚举 | 小 | Windows PnP 枚举 ✓ |
| 试波特率 | 中 | 要限流（试错太快会漏字 ✓）· 要超时 ✓ |
| 「问板子」那条命令 | 小 | 一条只读命令 ✓ |
| 向导页（renderer） | 中 | 4~5 屏 ✓ —— 按《11-卡片内部设计规范》的克制原则 ✓ |
| **发现式建包** | **大** | 猜的逻辑 + 溯源标注 + 人审界面 ✓ |
| SSH 凭据 | 中 | 私钥在客机上 → **走已有的 `prepare-credentials.authorize-key` 流程** ✓（ADR-D49 ✓） |

**契约影响**：**零** ✓ —— profile schema 封闭且够用 ✓ · 板型包格式不变 ✓（草稿只是普通包 ✓）

## 八 · 一句话

> **串口不是「第一条路」，是「问路的那条路」。**
>
> 接进一块板的真正难点，**不是连上它，是认出它** —— 而认出它**只需要一个 root shell** ✓。
> → 向导的顺序因此是：**先问出板子自述 → 再由自述推出其他连接 → 再由型号推出板型包** ✓。
>
> 而「广泛支持」的真正含义，是**给没见过的板也能生成一份待审的草稿** ✓ —— 不是多接几种传输 ✓。
