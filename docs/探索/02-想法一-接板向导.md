# 02 · 想法一：接板向导 —— **第一个真相 → 通用元操作 → 默认包 → 卡片启用**

> **作者**：Codex　**日期**：2026-11-17　**性质**：**探索**（不约束任何人 ✓）
> **想法原文**（用户 2026-11-17 第二轮）：「一开始接串口**不一定需要自动枚举和试波特率**，
> 而是向其他串口工具一样，**手动选择 com 和波特率**。先把**第一个真相**建立起来。
> 然后是**自带一些通用的元操作**，可以广泛一些，**嵌入式 Linux 通用**的，
> 然后**利用串口一个个地试**，这样就通过一个**默认包**建立了这个板的包。
> 然后根据试出来的**真相**在**默认卡片库**中启用卡片。
> 至于**建议清单就不需要了** —— 这个向导开发的目的就是让使用者**尽可能少参与**就能用上板子。
> 至于之后**板子描述包的完善**，就需要使用这通过手册等**自己操作 agent**了，
> 这**也是开发 MCP 的意义**不是吗。」

---

## 〇 · 结论先行

1. **串口：手动选 COM + 波特率** ✓ —— **不自动枚举、不试波特率** ✓
   → 像串口工具那样 ✓ → **用户已经会的动作** ✓ → **零学习成本** ✓
2. **「第一个真相」= 有一条能真的跑命令的连接** ✓ —— **后面一切的地基** ✓
3. **自带一组「嵌入式 Linux 通用」的元操作** ✓ —— 在串口上**一个个试** ✓ →
   试出来的**绿/红** = **真相表** ✓
4. **真相表 → 实例化出这块板的包** ✓ —— **打破了「先有包才能连板」的鸡生蛋** ✓✓
   （这是这一版最重要的改进 ✓ —— 我上一版没意识到 ✓）
5. **真相 → 启用默认卡片库里的卡** ✓ —— 用不了的卡**不出现** ✓
6. **人只参与第一步** ✓ —— 选 COM + 波特率 ✓（+ 给个名字 ✓）**就这些** ✓
7. **包的完善 = agent 通过 MCP 做** ✓ —— **这正是 MCP 的意义** ✓（读手册 + 探测 + 细化 ✓）
8. **⭐ 已实测**：一份「通用包」草稿在真板 ATK-DLRK3588 上探出 **4/4 全绿** ✓
   （读到了 `ATK-DLRK3588 Board` ✓ 与 `Buildroot 2024.02` ✓）
   → **「通用包 → 试出真相」这条路是真的** ✓，不是设想 ✓（§3.3 ✓）

## 二 · 「第一个真相」

### 2.1 它是什么 🟢

> **一条真的能跑命令的连接** ✓ —— 不是「连上了」，是「**命令真的返回了东西**」✓

### 2.2 怎么建立 🟢

```
人：选 COM 口 + 波特率          ← 【整个向导里，人唯一必须做的事】
        ↓
向导：用这条连接跑一条命令        ← 「第一个真相」
        ↓
     板子回了 → 真相成立 ✓
     板子没回 → 报告「连上了但没回话」+ 常见原因 ✓
```

> → **用户参与 = 一次选择** ✓
> → **其余全自动** ✓

### 2.3 「没回话」的诚实报告 🔵

| 现象 | 可能原因（按概率） |
|---|---|
| 端口打不开 | **COM 口不对 / 被别的程序占着** ✓（`docs/02` 事实：曾被 `serial-server.py` 独占 ✓） |
| 打开但无输出 | **波特率不对** ✓ · **不是调试口** ✓ |
| 有乱码 | 波特率不对（**认 banner 而不是认提示符** ✓） |

> → **报告要说「板子没说话」，而不是「连接失败」** ✓ —— **这两个是不同的故障** ✓
> → 并且**把用户选的 COM + 波特率原样记住** ✓（下一次不用再选 ✓）

## 三 · 通用元操作 —— **这一版的核心**

### 3.1 什么叫「通用」🟢

> **不假设任何一块板特有的路径** ✓ —— 只用**嵌入式 Linux 共通的东西** ✓

| 类别 | 例子 | 为什么通用 |
|---|---|---|
| **读文件** | `/proc/meminfo` · `/proc/loadavg` · `/proc/version` · `/etc/os-release` · `/etc/hostname` | 所有 Linux 都有 ✓ |
| **列目录** | `/sys/class/thermal/` · `/sys/class/devfreq/` · `/sys/class/backlight/` · `/sys/class/leds/` · `/sys/class/net/` | Sysfs 的**约定** ✓（不是某块板的私有路径 ✓） |
| **读一个 glob** | `/sys/class/thermal/thermal_zone*/temp` | Sysfs 的**约定** ✓ |
| **跑一条只读命令** | `uname -a` · `ip -br addr` · `cat /proc/uptime` | 所有 Linux 都有 ✓ |
| **写** | 重启 · 网口 up/down · 写一个文件 | 通用动作 ✓ |

### 3.2 形态：**它们是 reader 与 action，不是新东西** 🟢

| 元操作 | 是 | 落成 |
|---|---|---|
| **探测一个路径/目录/glob** | **reader** ✓ | 通用包里的 `file_read` / `exec_regex` reader ✓ → 产出通用 tag ✓ |
| **重启 / 网口 / 写文件** | **action** ✓ | 通用包里的 action ✓ → 要过地板 ✓ → 危险的在权限区默认关 ✓ |

> → **零新机制** ✓ —— **现有的 reader kind 与 action 就够** ✓

### 3.3 ⭐ **「默认包」= 一个内置的、嵌入式 Linux 通用的板型包** 🟢

> **它是关键** —— 因为它让**「连板子」不再需要「先有板型包」** ✓✓

```
profiles/boards/generic-linux/board.yaml
  这板子 → 通用的读法与动作
  ├─ readers
  │   ├─ cpu.usage      → /proc/stat
  │   ├─ mem.info       → /proc/meminfo
  │   ├─ load.avg       → /proc/loadavg
  │   ├─ temp.zones     → /sys/class/thermal/thermal_zone*/temp   ★ 通用但**粗**
  │   ├─ devfreq.*      → /sys/class/devfreq/*/load                ★ 通用但**粗**
  │   ├─ backlight.*    → /sys/class/backlight/*/brightness
  │   ├─ led.*          → /sys/class/leds/*/brightness
  │   ├─ net.iface      → /sys/class/net/*
  │   └─ board.model    → /proc/device-tree/model
  └─ actions
      ├─ sys.reboot
      ├─ net.iface.set
      └─ file.write
```

| 关键性质 | 说明 |
|---|---|
| **它是普通包** ✓ | 用**现有的包格式** ✓ → **校验器能校验它** ✓ → **探针能直接探它** ✓ |

> ### 🟢 **实测通过**（2026-11-17）
>
> 我写了一份 `generic-linux` 草稿（4 个 reader + 1 个动作 ✓），**用真校验器与真探针跑过** ✓：
>
> ```
> $ npm run validate:profiles -- <草稿目录>
> ✅ 1 个包，0 个错误，0 个警告
>
> $ npm run probe:board -- --pack <草稿目录> --profile board-adb
>   ✓ cpu     proc_stat    cpu.usage=0.227…  cpu.core.0.cluster=A55 …
>   ✓ mem     meminfo      mem.total_bytes=8302329856byte …
>   ✓ model   file_read    custom.generic-linux.board.model=ATK-DLRK3588 Board
>   ✓ osrel   file_read    custom.generic-linux.sys.osrelease=NAME=Buildroot …
> ✅ generic-linux：4 个 reader 全绿
> ```
>
> → **它就是一份普通包** ✓（`match` 可以不写 ✓ · `custom.<id>.*` 命名空间可用 ✓）→
> → **「通用包 → 逐条试 → 真相表」这条路是真的** ✓
>
> #### ⚠️ 但有一条边界，必须说清楚（**别把「零新机制」说得太满**）⚠️
>
> | 通用包**能**表达的 ✓ | 通用包**表达不了**的 ⚠️ |
> |---|---|
> | **路径是约定的那几个** ✓ —— `/proc/stat` ✓ · `/proc/meminfo` ✓ · `/etc/os-release` ✓ · `/proc/device-tree/model` ✓ · `/proc/loadavg` ✓ · `/sys/class/net/*` ✓ · `/sys/class/backlight/backlight/brightness` ✓ | **数量不定的多实例硬件** ⚠️ —— **温区** ✓ · **devfreq 节点** ✓ · **背光的第 2 块** ✓ |
> | 理由：这些路径是 **Linux / Sysfs 的约定** ✓ | 理由：`thermal_zone` 的 **`type_map` 是必填** ✓（**板子特有的名字** ✓）→ 通用包**给不出**「7 个温区，各是多少」✓ |
>
> → **要覆盖「数量不定的那几个」，需要 1~2 个新的 reader kind** ⚠️
> （例如 `thermal_zones_raw` —— **把 `thermal_zone` 的「不归并」版本** ✓）
> → **reader kind 是封闭词表** ✓ → **加它要走契约评审** ✓（ADR-D15 ✓）
> → **这是想法① 里唯一真正的新东西** ⚠️ → **其余全是复用** ✓
| **它的语义是「诚实但粗」** ✓ | `temp.zones` 给出「**7 个温区**」✓ —— 但**不说哪个是 SoC** ✓ → **那要 agent 读手册才知道** ✓ |
| **它服务所有板** ✓ | 一份包 → **任何嵌入式 Linux 都能先跑起来** ✓ |

> ### ★ 这就是「打破鸡生蛋」的那一步 ✓
>
> **旧路**：要有板型包 → 才能连板 → 才能探针 → 才知道这板能干什么 ✗
> **新路**：**用通用包连上板** → **试通用包** → **试出来的就是这块板的包** ✓

### 3.4 试出来的**真相表** 🟢

> **它几乎就是现成的** ✓ —— `probePack` 已经产出这个形状了 ✓（`ProbeReport` ✓ · `judgeReader` ✓ · `probeHint` ✓）

```json
{
  "connection": { "transport": "serial", "port": "COM3", "baudrate": 1500000 },
  "results": [
    { "reader": "cpu.usage",   "status": "ok",   "detail": "8 个 cpu 行" },
    { "reader": "mem.info",    "status": "ok",   "detail": "MemTotal 8107744 kB" },
    { "reader": "temp.zones",  "status": "ok",   "detail": "7 个 zone" },
    { "reader": "devfreq.*",   "status": "ok",   "detail": "fb000000.gpu/load = 37@300000000Hz" },

  ]
}
```

> → **「绿」= 这板有** ✓ · **「红」= 这板没有 / 读法不对** ✓（`probeHint` 已经会区分 ✓）

## 四 · 从真相到包：**实例化**

### 4.1 一条规则 🟢

> **通用包里绿的 reader → 留下；红的 → 删掉** ✓
> **通用包里红的、但板子上确实有别的 → 留给 agent 发现** ✓

### 4.2 产物

```
用户数据目录/
  boards/
    atk-01/
      board.yaml        ← 由通用包实例化而来 ✓
      provenance.json   ← **它是怎么来的** ✓
```

```yaml
# provenance.json —— **「这份包是猜的」这件事必须留痕** ✓
{
  "source": "generic-linux",          ← 从哪个通用包实例化 ✓
  "probedAt": "2026-11-17T…",
  "connection": { "transport": "serial", "port": "COM3", "baudrate": 1500000 },
  "guessed": [
    { "tag": "temp.zone0", "why": "通用规则：第 0 个温区", "needsHuman": true },
    { "tag": "gpu.devfreq.duty", "why": "load 文件的值形如 37@300MHz —— **利用率还是占空比未定** ⚠️",
      "needsHuman": true, "knownTrap": "docs/06 C1 / C7" }
  ]
}
```

> → **猜的必须标出来** ✓ → 人/agent **只审这几条** ✓ → 而不是审一整份包 ✓
> → 这与《11-卡片内部设计规范》的「一张卡 = 一个主张」**同一个思路** ✓：**把注意力收到最小** ✓

### 4.3 它是**初版**，不是终版 ⚠️

> → **必须明确告诉用户**：「这是**自动探出来的初版包** ✓，
> 它说得准的地方是**事实**（有没有、几个、什么形状）✓，
> 说得**不准**的地方是**命名与语义**（哪个温区是 SoC ✓ · 那个 duty 是不是利用率 ✓）」✓
> → **下一步 = 让 agent 去补** ✓（§六 ✓）

## 五 · 卡片启用：**按真相** 🔵

### 5.1 默认卡片库 🔵

> 一组**通用的卡** ✓ —— 不依赖具体板 ✓ —— 装上就有 ✓

| 现有 | 依赖的 tag | 在别的板上的命运 |
|---|---|---|

| `build-deploy` ✓ | 无（要流程 ✓） | 永远开 ✓ |
| `workflows` ✓ | 无 ✓ | 永远开 ✓ |
| `board-actions` ✓ | `led.*` · `backlight.*` | 有才开 ✓ |

### 5.2 「能不能用」的数据**已经有了** 🟢

| 机制 | 出处 |
|---|---|
| 卡片的 `missing_tags`（**声明了但这块板没有**） ✓ | `src/main/cards/state.ts` ✓ · ADR-D46 ✓ |
| 卡的 `unreadable_tags`（**有但读不到**） ✓ | 同上 ✓ |

> → **判定已经存在** ✓ → 缺的只有两件 ✓：
> **① 一组足够大的默认卡片库** ✓ · **② 界面上「这张卡在这块板上用不了」的表现** ✓

### 5.3 不用的卡**不出现**，而不是**出现后报错** 🔵

> → 与《11-卡片内部设计规范》同一条原则 ✓：**能用的才摆出来** ✓

## 六 · 人 vs agent 的分工（**这一版的核心分工**）🔵

| 环节 | 谁 | 为什么 |
|---|---|---|
| **选 COM + 波特率** | **人** ✓ | 只有人知道板子插哪 ✓ |
| **建立第一个真相** | **向导** ✓ | 自动 ✓ |
| **逐个试通用元操作** | **向导** ✓ | 自动 ✓ |
| **实例化出初版包** | **向导** ✓ | 自动 ✓ |
| **按真相启用卡片** | **向导** ✓ | 自动 ✓ |
| **读手册 → 命名与语义**（哪个温区是 SoC ✓ · duty 是不是利用率 ✓） | **agent** ✓ | **要知识 + 要探测** ✓ → **这是 agent 擅长的** ✓ |
| **加动作 / 加流程 / 加卡** | **agent** ✓ | 同上 ✓ |
| **审 agent 改过的包** | **人** ✓ | 最后一道 ✓ |

> ### → **这正是 MCP 的意义** ✓
>
> **MCP 让 agent 能：**
> - **探测** ✓（`sample_tag` ✓ · `list_tags` ✓ · `describe_tag` ✓）
> - **读板子的真实状态** ✓（`list_data_sources` ✓ · `list_connections` ✓）
> - **验证自己写的东西** ✓（`validate_card` ✓ —— **但没有 `validate_board_pack`** ⚠️）
> - **装上去** ✓（`install_card` ✓ · `run_workflow` ✓ · `execute_action` ✓）
>
> → **agent 完善板型包，需要 MCP 补三个洞** ⚠️（§七 ✓）

## 七 · MCP 要补的三个洞 ⚠️

> **这轮探索挖出来的具体缺口** ✓ —— 不是「以后再说」✓

| # | 缺口 | 为什么 agent 需要它 |
|---|---|---|
| **①** | **`validate_board_pack`**（验证板型包） | 现在只有 `validate_card` ✓ → agent 写完包**没有门** ⚠️ |
| **②** | **装/更新板型包** | 现在板型包只能**手写文件到仓库目录** ✓ → 用户数据目录里的包**没有安装路径** ⚠️ |
| **③** | **通用探测**（对任意路径试一下） | agent 要细化包，就得试**还没声明的路径** ✓ → 现在只能跑**已声明**的动作 ✓ → **缺一个受限的通用探测** ⚠️ |

### 7.1 ③ 的形状（**必须受限**）⚠️

> **通用探测 = 一个动作** ✓ → 走**危险地板** ✓ → 参数是字符串 ✓ → **必须声明 `maxLength`** ✓
> → **它比 agent 自己乱跑安全** ✓ —— 因为它**落在地板与权限区里** ✓
> → 而且**它只在 agent 需要时开** ✓（默认关 ✓ · ADR-D47 ✓）

| **Q5** | 通用包要覆盖多少条 reader？ | **先 10~15 条** ✓ —— **够用就行** ✓（覆盖：cpu / mem / load / temp / devfreq / backlight / led / net / model / uptime ✓） |
| **Q8** | ⭐ **要不要加「不归并」的新 reader kind**（`thermal_zones_raw` 之类）？ | **要** ✓ —— 否则通用包**说不出「有 N 个温区」** ✓ → 「粗粒度」这一层就残了 ⚠️ · **但它要走契约评审** ✓（reader kind 是封闭词表 ✓） |
| **Q6** | **USB / ADB 作为「第二个真相」**要不要做？ | **要** ✓ —— **插上 USB 就有** ✓ · **零凭据** ✓ → 比 SSH 省事得多 ✓（SSH 要私钥 ⚠️ → 后做 ✓） |
| **Q7** | agent 完善包时，**手册怎么给它**？ | **用户给一个文件路径** ✓ —— 宿主不做文档解析 ✓ → **agent 自己读** ✓ |

## 十 · 一句话

> **先有一条能跑命令的连接**，再让**一整套通用元操作**在板上**一个个试**，
> 试出来的**真相表**就是这块板的**初版包** —— **「先有包才能连板」这个死结被解开了** ✓
>
> 而**把粗粒度的事实变成准确的语义**（哪个温区是 SoC ✓ · 那个 duty 是不是利用率 ✓）
> **需要知识与探测** → **那是 agent 的活** ✓ → **而让 agent 能干这活，正是 MCP 存在的意义** ✓
