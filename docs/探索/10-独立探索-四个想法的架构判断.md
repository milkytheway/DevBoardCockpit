## 三 · 一条贯穿四个想法的架构判断

### 3.1 工程里**已经有三条通道**，形状完全一样

| 通道 | 声明 | 机器验证 | 人/agent 确认 | 落盘 | 热插拔 |
|---|---|---|---|---|---|
| **板型包** | `board.yaml` ✓ | `npm run validate:profiles` ✓（31 条 ✓） | —— | `profiles/boards/` ✓ | 运行时 `resolvePack` ✓ |
| **卡片** | `manifest.json` ✓ | `validate_card` ✓（14 条 ✓） | —— | 用户卡片根 ✓ | **watcher 200ms 去抖** ✓ |
| **流程包** | `*.yaml` ✓ | 注册表 `scan()` ✓（12 条 ✓） | **权限区那一行开关** ✓ | `profiles/workflows/` ✓ | 注册表重扫 ✓ |

> **三行一模一样** ✓ —— **声明 → 验证 → 落盘 → 热插拔** ✓。
> **第四步（人/agent 确认）在前两条通道上还是空的** ✓（板型包没人确认 ✓ · 卡片没人确认 ✓）。

### 3.2 所以四个想法是**同一条流水线的四个入口**，不是四套新机制

```
                        ┌──────────── 声明 ────────────┐
   ① 接板向导 ────────▶ │ 板型包草稿 + 三条连接 profile │
   ② 流程可组装 ─────▶ │ 流程包（片段拼装 / 嵌套）      │──▶ 机器验证 ──▶ 落盘 ──▶ 热插拔
   ③ 组装画布 ───────▶ │ 卡片 manifest + 入口文件      │
                        └──────────────────────────────┘
                                              │
   ④ 唤起 agent ────────────────────────────┘
      （活 = 一个流程包 + 一组输入 ✓）
```

> **为什么这个视角有用** ✓：
> → **①②③ 做的其实是同一件事** ✓ —— **各自去配「入口」** ✓（而不是各自造机制 ✓）✓
> → **④ 是出口** ✓ —— **活就是流程包** ✓ → **④ 复用了 ② 的成果** ✓
> → **「AI 造卡」不是新系统** ✓ —— **是给卡片通道配一个入口** ✓

## 四 · 想法① · 接板向导

### 4.1 我同意 Codex 的核心判断 ✓

**「串口优先」是对的，而且比想象的更对** ✓ —— 串口**不是一种传输，是一条万能探测通道** ✓：
它给你一个 **root shell** ✓ → **板子自己的 IP、型号、SSH 状态都能问出来** ✓
→ **向导的形状不是「填表」，是「一条发现链」** ✓：

```
枚举 COM → 试波特率 → 问板子 → 推荐其它连接 → 匹配板型包 → 探针 → 生成三条连接
```

### 4.2 我要改的一处：**「枚举 COM」不是一行代码，是两条路**

| 路 | 怎么列 | 能列出 CH343 吗 |
|---|---|---|
| **node-serialport 的 `SerialPort.list()`** | 走 serialport 自己的枚举 | ⚠️ **列不出** ✓（`docs/02:211` ✓ —— 旧工程为此专门用了 pyserial ✓） |
| **Windows 设备查询** | `Get-CimInstance Win32_PnPEntity` / `Win32_SerialPort` 按「USB-SERIAL CH343」匹配 | ✅ **能** ✓（这类 USB 转串口是以设备而非 COM 口枚举的 ✓） |

→ **向导第一步要做的是「把这两个来源合起来去重」** ✓ —— **不是只加一行** ✓。

### 4.3 试波特率：**判据要机械** ✓

候选：`115200`（代码默认 ✓）· **`1500000`（这台板子真实的 ✓）** · `921600` · `57600`。
判据：**认出启动横幅里的特征串** ✓（`U-Boot` ✓ · `Linux version` ✓ · `buildroot` ✓）——
**认不出就换下一档** ✓（**不猜** ✓ —— 这是这个工程一贯的判据风格 ✓）。

### 4.4 发现式建板型包：**先做「只读探针」版**（我的建议 ✓）

Codex 的 Q2 问「要不要做发现式建包」✓ —— **要做** ✓，但**第一版可以很薄** ✓：

| 包里有什么 | 第一版 | 以后 |
|---|---|---|
| **readers** | **猜出来** ✓（`file_read` 探 `/proc`、`/sys` 的几个固定路径 ✓） | 加更多 kind ✓ |
| **match.models** | 从 `/proc/device-tree/model` 读出来 ✓ | —— |
| **actions** | **留空** ✓ | 逐个动作探命令与回读 ✓ |

→ **这样「没见过的板也能接进来」当天就能兑现** ✓（**哪怕只有读数** ✓）✓
→ **动作是第二阶段** ✓（**它要一条条试命令与回读** ✓ —— 那是最费时的部分 ✓）✓

### 4.5 探完之后：**产物是数据，不是副作用** ✓

Codex 的 Q1 问「要不要自动写盘」✓ —— 我同意**不自动写** ✓，
但**建议探完落一份建议文件** ✓（`board-<serial>.suggested.json` ✓）→
人点一下导入 ✓ → **探针的产物可审、可改、可丢** ✓。

## 五 · 想法② · 流程包可组装

### 5.1 已经在发生的事（**不是设想，是压力** ✓）

DSH v0.11 把编译流程拆成三段（`compile` / `upload` / `load` ✓），
**同一段步骤被复制了三份** ✓：

| 重复的东西 | 出现在 |
|---|---|
| `compile` 步（逐字相同 ✓） | `build-run:45-57` ✓ = `compile:34-41` ✓ |
| `artifacts` discover（pattern + 7 项 exclude ✓） | `build-run` / `compile` / `upload` **三份** ✓ |
| `deliver` 步（scp + placement + 跨目标判据 ✓） | `build-run` / `upload` **两份** ✓ |
| `load` + `assert-loaded` | `build-run` / `load` **两份** ✓ |

**参数已经开始漂** ✓：

| 参数 | `build-run` | `compile` / `upload` |
|---|---|---|
| `build_dir` | **必填** ✓ | **默认值** ✓（`/home/alientek/kernel-build` ✓） |
| 产物名 | 自动发现 ✓ | **手填 `module`** ✓（默认 `hello` ✓） |
| 角色 | build + target ✓ | 只有 build ✓ / 只有 target ✓ |

> **为什么 `upload` 又 discover 了一次** ✓ —— **因为 `outputs` 是 runner 的局部变量** ✓

### 5.2 我的形状建议：**三步，每步都不动契约**

| 步 | 形态 | 契约 | 解决什么 |

| **2** | **`include`（宿主侧预处理）** | **小改** ✓（step 表加一个键 ✓） | **步骤级去重** ✓ —— 直接治上面那三份重复 ✓ |
| **3** | **`call`（流程里调流程）** | **要评审** ✓（第 7 种 kind ✓） | **真正的编排** ✓ |

### 5.3 关于 `include`：**Codex 的顾虑要拆开看** ✓

Codex 说「include（YAML 文本包含）**没有预处理器的包格式撑不住**」✓ ——
**那说的是「纯 YAML、靠锚点跨文件」** ✓，**不是「宿主侧预处理」** ✓。

宿主侧预处理**完全可行** ✓ —— 它已经有：
**js-yaml** ✓（注册表解析 ✓）· **一个注册表** ✓（按 id 取流程包 ✓）· **一个解析入口** ✓。

> 否则被包含进来的步骤引用 `{output:artifacts}` 会被误判成「没有产出这个槽」✗。

### 5.4 `call` 形态：**除了 Codex 列的五条，还要加一条**

Codex 列的五条 ✓（角色映射 / 槽隔离 / 取消穿透 / 审计归属 / 递归限深 ✓）——

## 七 · 想法④ · 唤起 agent

### 7.1 我同意 Codex 的核心判断 ✓：**出站绕过了整个权限模型** ✓

```
入站：agent ──HTTP 回环──▶ 宿主    （能力由宿主授予 ✓ · 权限区说了算 ✓）
出站：宿主 ──────────▶ agent        （不在这套模型里 ✗）
```

### 7.2 但我认为**形态的排序可以再改** —— 而且**「探测 agent」应该整个推迟**

Codex 的四种形态：推送 ✓ / 投递 ✓ / 拉起 ✓（+ 探测 ✓）。

**我的排法**：

| 序 | 形态 | 怎么做 | 出站？ | 要不要探测 agent |
|---|---|---|---|---|
| **1** | **让 agent 自己来看** | 宿主在 **MCP 上开一条 `list_tasks`** ✓ → **agent 轮询** ✓ | **零出站** ✓ | **不需要** ✓ |
| **2** | **投递到文件** | 写进 `tasks_dir`（**与 `cards_dir` 同款** ✓ · 发现文件里多一个字段 ✓） | 零出站 ✓ | 不需要 ✓ |
| **3** | **推送** | 写一个「有活了」的标记 ✓ → **人自己看** ✓ | 零出站 ✓ | 不需要 ✓ |
| **4** | **拉起** | 起一个进程 ✓ | **有出站** ✓ | **要探测** ✓ |

> **形态 1 为什么最安全** ✓：
> → **方向没变** ✓ —— 仍然是 **agent → 宿主** ✓（**入站** ✓）
> → **权限模型一个字不用动** ✓ → **「宿主给 agent 授权」这件事根本不存在** ✓
> → **而且它复用了现成的通道** ✓（**MCP 就是给 agent 用的** ✓ —— 发现文件 ✓ · token 认证 ✓ · loopback ✓）

> **「探测主机上有什么 agent」是形态 4 的前置** ✓ —— **而形态 4 最晚做** ✓
> → **所以探测也最晚做** ✓ —— **今天完全不用写那行 grep** ✓。

### 7.3 一个关键澄清：**「活」是什么**

> **活 = 一个流程包 id + 一组输入** ✓ —— **不是新东西** ✓。
> → **④ 不需要新的产物类型** ✓ → **不需要新的契约** ✓
> → **而且它让 ② 与 ④ 咬合** ✓：**② 的可复用粒度 = ④ 能派什么活** ✓
> （**能派活的前提是那活是个流程包** ✓ → **流程能组装，活的粒度就更细** ✓）✓

### 7.4 一个具体的落点：**Claude Desktop 已经在链路上了** ✓

宿主是 MCP **服务端** ✓ → **Claude Desktop / Claude Code 是客户端** ✓ → **发现文件里写着端口与 token** ✓。
→ **「通知 agent」= 让它自己来看** ✓ —— **不是宿主去敲门** ✓。
→ **这正好与这个工程已有的那句原则一致** ✓：「**MCP 是 AI 的眼睛和手，不是 AI 的硬盘**」✓。
