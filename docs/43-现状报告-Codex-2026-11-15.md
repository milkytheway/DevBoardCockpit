## 四 · 待优化（结构性，六条）

### O1 · 采样队列与流程队列是**两条**，却覆盖同一块板 ⚙️ 🟢

```
卡片动作 → index.ts:372   → runtime.runTransaction → TagRuntime 的队列
流程的步 → runner.ts:990  → targets.runOn(profileId) → TargetRegistry 的队列   ← 另一条
```

→ 流程的 exec 步与标签采样**可以并发**。
**对 ADB 无害**（adb server 允许同设备多 shell，各是独立管道）；
**对串口**靠 OS 的 `EBUSY` 兜底 → 表现是 `PORT_BUSY`（抢不到），**不是串台** ✅ 可接受，但**靠 OS 兜底不是自己的账**。
→ **建议**：把队列的键从"对象"提到"物理资源 / profileId"，让采样与流程共用一条。

### O2 · 同一个 profile 会被开出多条连接 ⚙️ 🟢

`TagRuntime` 一条 + `TargetRegistry` 一条（✅ 已按 profileId 复用）+ **每个终端会话一条**（`terminal/manager.ts:108`）。
→ ADB 下是 N 条 shell 管道；串口下第二条就 `PORT_BUSY`（已有 `isPortBusy` 专门识别 ✓）。
→ **建议**：把 TargetRegistry 已做对的「按 profileId 复用同一条连接」推广到终端会话 → 串口上从"直接失败"变成"排队"。

### O3 · 多卡片并发**没有机械判据** ⚙️ 🟢

机制是齐的：一份 `TagStore`（一份状态一份副本）、每 profile 一条队列、动作独占事务、
`conn_busy` 背压（deadline 3 s + 上限 32）、同流程不并发（守卫 M117）。
**但没有任何一条测试守着"两张卡共用一个 profile"这个场景。**
→ **建议判据**（本报告提议，成本很低）：

> 构造"两张卡 + 一个 profile"：一张卡持续采样、另一张卡持续发动作 10 分钟 →
> 断言 ① 读数不出现交叉 ② 动作回读不错配 ③ 队列不无限增长（`conn_busy` 是允许的结果）。

### O4 · 卡片侧的"写"有两种交互模型 ⚙️ 🟢

`actions.invoke` = **同步**（一次 await 拿 `{ok, readback}`）；
`workflows.run` = **异步**（拿 `runId` → 轮询 `status` / 订阅时间线）。
→ **AI 写卡时必须先判断同步还是异步**，混合卡要写两套渲染。
→ **建议**：卡片视角收敛成一个写入口（`{status:'done'|'running', value?, runId?}`），
或至少在 `get_card_sdk_docs` 里把这条写死。**计划 7 已过，现在补要再动一次契约** → 建议记 ADR 而不是现在改。

### O5 · `spec/05` 开头没写「动作 = 原语、流程 = 编排」 ⚙️ 🟢

实现层面二者共用同一批原语（`runner.ts` 直接 `import { invokeAction } from '../actions/executor'`），
且流程的 kind 里有 `action`（可以把动作当一步）。
**但契约文本没把这层关系讲出来** → 读者容易把"动作"和"流程"当成并列的两套抽象。
→ **建议**：在 `spec/05` §〇 加三行说明（**表述澄清，不改语义**）：
动作是**原语**（板型包声明的能力）· 流程是**一串原语**（流程包声明的一件事）·
「只发送指令-获取结果」在机制上就是流程的一步，两者的区别在**信任锚**（板子 vs 用户批准过的一件事）。

### O6 · `verified` 的两种强度没在契约里写明 ⚙️ 🟢

动作的 `verified` = 执行与回读**同一事务**（SPEC-D22，不可拆）；
流程阶段的 `verified` = 判据可能**跨目标**（两个事实、两行账，ADR-D34 D34-7）。
→ 卡片侧统一用 `verified`（`spec/05` B5 的缩减投影 ✓）避免了词混 ✅，
**但强度差异没写** → 卡片没法判断"这个 verified 是强是弱"。
→ **建议**：契约里给流程阶段的 `verified` 加一个限定（如 `verified: 'same-target' | 'cross-target'`）。
