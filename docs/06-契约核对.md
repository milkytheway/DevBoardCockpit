## 一、确认无误的部分

| 契约/包里的说法 | 实测 | 结论 | 标记 |
|---|---|---|---|

| `cpu.core.*.cluster` ← `/proc/cpuinfo` 的 `CPU part` | 0xd05 ×4、0xd0b ×4 | A55×4 + A76×4 | 🟢 |
| `npu.usage` ← `/sys/kernel/debug/rknpu/load` | `NPU load:  Core0: 0%, Core1: 0%, Core2: 0%` | 3 个计算核，`npu.core.*.usage` 对得上 | 🟢 |
| `gpu.usage` ← `/sys/class/devfreq/fb000000.gpu/load` | `0@300000000Hz`（空闲） | 包里声明 `measure: utilization` 是对的 | 🟡 见下 |

## 二、发现的缺陷与差异

### C1 · 板型包里有一个**指向不存在路径**的 reader 🟢 确认为缺陷 ✅ 已拍板回滚

| 项 | 内容 |
|---|---|
| 位置 | `profiles/boards/rk3588-atk/board.yaml` → `custom` → `npu_devfreq` |
| 迁入时写的 | `/sys/kernel/debug/rknpu/devfreq/cur_freq` |
| 实测 | `/sys/kernel/debug/rknpu/` 下**只有** `delayms  freq  load  power  reset  version  volt`，**没有 `devfreq/` 目录** |

**候选改法**：

1. 改用 `/sys/kernel/debug/rknpu/freq`（实测内容 `1000000000`，就是当前频率 Hz），
   或 `/sys/class/devfreq/fdab0000.npu/cur_freq`（同样 `1000000000`）。
2. 保留原路径但在包里注明「该路径在本板不存在」，让 tag 稳定报 `unavailable`。

> 无论选哪个，这个 tag **只能绑到 `.freq_hz`，不能绑任何 `*.usage`**——
> 它是频率，不是利用率。校验规则 3 正是拦这个。

**状态**：用户 2026-11-12 拍板**回滚到候选 1**（不走「改成读占空比」那条路）。
处置细节见 §3.1。

### C2 · 背光有**两个**实例，核心词表只定义了一个 🟢

| 路径 | 实测值 | 说明 |
|---|---|---|
| `/sys/class/backlight/backlight/brightness` | `200`（max 255） | 第一块屏（软链到 `platform/backlight/backlight/backlight`） |
| `/sys/class/backlight/backlight1/brightness` | `255`（max 255） | 第二块屏（`platform/backlight1`） |

> ⚠️ 注意目录名是 **`backlight`**，不是 `backlight0`——写路径时别想当然。

**候选改法**：核心词表把 `backlight.brightness` 扩展为 `backlight.*.brightness`
（模式匹配已支持 `*`），两个实例分别叫 `backlight.backlight.brightness` /
`backlight.backlight1.brightness`——**命名有点丑**。

另一个选项：保留单数 `backlight.brightness` 表示主屏，第二块屏走
`custom.rk3588-atk.backlight1.brightness`。**这更符合词表准入门槛**
（「至少两块板才会产生」才进核心词表）——背光双实例是这块板的特点，不是通例。

### C3 · 核心词表缺「调频策略」这类量 🟢 实测可得

| 路径 | 实测值 | 可选值 |
|---|---|---|
| `/sys/devices/system/cpu/cpu0/cpufreq/scaling_governor` | `schedutil` | interactive conservative ondemand userspace powersave performance schedutil |
| `/sys/class/devfreq/fdab0000.npu/governor` | `rknpu_ondemand` | rknpu_ondemand dmc_ondemand vop2_ondemand venc_ondemand userspace powersave performance simple_ondemand |

**候选改法**：核心词表加 `cpu.governor`（enum）与 `npu.governor`（enum）。
理由：cpufreq 的 governor 是 **Linux 通用量**（任何跑 cpufreq 的板子都有），
满足词表准入门槛的「Linux 通用量」一条。

> NPU 那个节点的 `available_governors` 是 **rkdevfreq 的全局列表**
> （含 dmc/vop2/venc 的），不是 NPU 专属——枚举要按实际值收敛，别照抄列表。

### C4 · 板型包缺三个动作（尤其缺 destructive 的例子）🟢 ✅ 已拍板（2026-11-13）

包里只有 `backlight.set` 与 `cpu.governor.set`（两个 reversible）。当时缺：

| 候选动作 | tier | 命令 | 回读 | **拍板结果** |
|---|---|---|---|---|
| `npu.governor.set` | reversible | `echo {governor} > /sys/class/devfreq/fdab0000.npu/governor` | `npu.governor` | ❌ **不补**——实测会**锁死板子**（E4，见下） |
| `debugfs.mount` | reversible | `mount -t debugfs debugfs /sys/kernel/debug` | `npu.usage`（挂上后才可读） | ❌ **不补**——这块板**已经挂着**（E7） |
| `system.reboot` | **destructive** | `reboot` | —（无回读，需 `verify` 兜底） | ✅ **已补**（destructive + `verify` 回读） |

**为什么重要**：`destructive` 档位此前**没有任何实例**，
两档分级与「二次确认 + dry-run」这条链就没有可验证的样本。
`system.reboot` 是最真实的 destructive 例子。

#### C4.1 · `npu.governor.set` 不补的理由（2026-11-13 实测推翻原理由）

**原理由（错的）**：那个节点是 rkdevfreq **全局**的，写它会影响 dmc/vop2/venc。

**实测 E3 证伪**：写 NPU 节点期间 `dmc/governor` **始终是 `dmc_ondemand`**。
**当前值是每节点独立的**——全局的只是**可选值列表**（E1），不是当前值。

**真理由（实测 E4）**：写 `powersave` → **写调用挂死在内核里**，
进程进 **D 状态**，`kill -9` 无效，
此后该节点的**所有** governor 读写与 `trans_stat` 读取全部阻塞。
**只有重启能恢复**（竞态，非必现，但一次就够锁死）。

> **对 agent 可触发的动作，这是不可接受的**：
> 写错一个值 → 板子失去 devfreq 控制 → 只能靠物理重启。
> 详见 `docs/02` §3.4 与 `docs/05` ADR-D26。

#### C4.2 · `debugfs.mount` 不补的理由 + **事后草图**

1. **这块板默认已经挂着**（E7：`/proc/mounts` 有 debugfs 行，`rknpu/load` 读得出 0%）
   → 动作在这块板上是**空转**。
2. **引导路径本来就通**：契约 §2.1 已把「debugfs 没挂」建模成 `unavailable`，
   并在 `detail` 里给了修复提示。**契约早就假设它可能没挂。**
3. **挂载是系统级改动**，不是「这块板的能力」；真要做也该是**人类在板子上做**。
4. 真要加就得动**危险地板表** = 改契约 = 升 `apiVersion`——为一块不需要的板子不值。

> **事后草图（账要留，事不做）**：若将来真要加 `debugfs.mount`，
> 回读走 **`/proc/mounts` 的 debugfs 行**（挂载成功后该行必在），
> **不是**「挂上之后才有值」的 `npu.usage`——后者是**自指**。
> **这条路线是通的**，只是今天不值得做。


### C5 · debugfs 前置条件在契约里没有位置 🟢

`npu.usage` 依赖 `/sys/kernel/debug` 已挂载。实测**当前已挂载**：

```
debugfs /sys/kernel/debug debugfs rw,relatime 0 0
```

但它**不是持久的**（重启后可能丢，取决于板子的 `/etc/fstab` 与 init 脚本）。
契约里的 `unavailable` 状态没地方写「为什么不可用」。

**候选改法**：

1. `unavailable` 允许带一个 `reason` 码（如 `debugfs_not_mounted`），
   让卡片能显示「需要挂载 debugfs」并直接给出 `debugfs.mount` 动作按钮。
2. 或在板型包里声明 `requires: [debugfs]`，由运行时在采 `npu.usage` 前自动检查。

> 这条是 **C4 的 `debugfs.mount` 动作**能派上用场的前提。

### C6 · 单位的换算责任要写死 🟢 ✅ 已写入契约

核心词表用 `mem.total_bytes`（**byte**），而 `/proc/meminfo` 给的是 **kB**
（实测 `8107744 kB`）。契约应明确：**reader 负责换算，契约只认 byte**。
包里的 `meminfo` kind 必须做 ×1024，否则卡片显示的内存会小 1024 倍。

**状态**：已写入契约（`docs/spec/02` §4.3 的 kind 参数表 + `docs/spec/01` 词表的单位列）。
**其他单位的换算**（thermal 的毫摄氏度、`@Hz` 的抽取、disk 的块大小、net 的计数器回绕）
仍需在每个 reader kind 的参数说明里写死——这一条留在实现阶段逐 kind 补。

### C7 · 板型包缺 `npu` 的占空比对照量 🟢 ✅ 随 C1 一并处理

实测 `/sys/class/devfreq/fdab0000.npu/load` = `100@1000000000Hz`——
**板子空闲时它就是 100**。这正是 spec/01 §七 那个坑。

包里已经正确地**没有**把它绑到任何 `*.usage`（✅ 做对了），
但可以补一个板型私有量 `custom.rk3588-atk.npu.duty`，
让卡片能同时展示「利用率 0%」和「占空比 100%」——**对照着看才不至于误判**。

**状态**：对照量保留，但它**只提供 `duty`**（不提供 `freq_hz`）——
频率从 C1 回滚后的路径单独取。这样「利用率 / 占空比 / 频率」三者语义各自干净，
不再互相冒名（`load` 里的 `@freq` 是「duty 在哪个频率上测的」，不是当前频率）。

### C8 · 契约里 debugfs 的示例与本板实际不符 🟢（2026-11-13）

| 项 | 内容 |
|---|---|
| 位置 | `docs/spec/01-tag-contract.md` §2.1.1 的读数示例；以及板型包里 `npu` reader 的注释 |
| 契约/包里的说法 | 「`/sys/kernel/debug` **默认没挂载**」——`unavailable` 的示例就用「debugfs 未挂载」当理由 |
| 实测（E7） | **这块板默认已经挂着**：`/proc/mounts` 有 `debugfs /sys/kernel/debug debugfs rw,relatime`，`rknpu/load` 直接读得到 |

**这不是契约错误**——契约讲的是「环境状态」这个**模型**
（「资源此刻不在」→ `unavailable` + `reason: device_absent` + `detail` 里的修复提示），
模型对不对与某一块板的当前状态无关。

**但示例与本板实际不符** → 板型包里的注释已经改成
「**本板默认已挂载；重启后可能丢**（不是持久的），读不到时如实报 `unavailable`」，
免得后来的人以为「读不到 = 包写错了」。

**处置**：**契约不动**（示例保留，它演示的是 `unavailable` 的形状）；
板型包注释已改。见 `docs/02` §3.3。

### C10 · 契约 §2.4 的 kind 表**漏了** `available_bytes` 🟢（2026-11-13 实施时发现）

### C11 · 危险地板的 `mkfs` 按 **`mkfs*`** 实现 🟡（2026-11-13 实施时发现）

| 项 | 内容 |
|---|---|
| 位置 | `docs/spec/02-board-pack.md` §5.2 的地板表与 §5.2.1 的匹配规范 |
| 契约写的 | 地板表里写 `mkfs`（精确匹配）；同表里还有 `erase`、`burn` |
| 实现做的 | `mkfs*`、`erase*`、`burn*`（前缀匹配）——所以 `mkfs.ext4 /dev/mmcblk0`、`erase_cache`、`burn_count` **都会被拦下** |
| 理由 | §5.2.1 的前缀规则（「如 `flash*` 命中 `flash_uboot`」）说明带后缀的**同义**命令也算命中。`mkfs.ext4` 与 `mkfs` 是**同一个操作**。而且「**地板是下限，不是上限**」——地板表里漏掉的同义写法会让**同一个破坏性操作**从地板底下钻过去 |

**已做的处置**：实现按 `mkfs*`、`erase*`、`burn*` 处理
  （`src/main/tags/floor.ts` 的注释里写明了理由）。

> **`erase*` / `burn*` 的依据比 `mkfs*` 弱**：契约 §5.2.1 只给了 `flash*` 的例句，
> 没提 `erase*` / `burn*`。但那两个动词的带后缀写法（`erase_cache`、`burn_count`）
> **不是破坏性操作**——前缀匹配会**误伤**。这是**假阳性**：一个无害动作被迫声明 destructive。
> 候选：① 三条都用前缀（现状，假阳性风险）；② 只有 `mkfs*` 用前缀，
> `erase` / `burn` 回到精确匹配（少两个假阳性，但 `erase_all` 这类写法会漏）。
> **待拍板。**

**候选**：
1. 回写契约 §5.2 的表，把 `mkfs` 写成 `mkfs*`（**建议**：与 `flash*` 的写法对齐）；
2. 或严守字面 `mkfs`（**不建议**：`mkfs.ext4` 是真机上最常见的写法，
   按字面实现等于地板有个洞）。

### C13 · 危险地板：**词元的 basename 也算** + `rm -rf /*` 🟡（2026-11-13 实施时发现）

| 项 | 内容 |
|---|---|
| 契约写的 | §5.2.1「词元相等」；§5.2 的表里写 `rm -rf /` **及其等价形式** |
| 实现做的 | ① 词元的 **basename 也算**（`/sbin/reboot` → `reboot` 命中）；② `rm -rf /*` 与 `rm -rf /` 等价 |
| 为什么 | 真实的调用几乎都带绝对路径（`/sbin/reboot`、`/usr/sbin/shutdown`）——**只按字面实现，地板在真实写法上是空的**；而 `/*` 展开后就是根目录下的全部条目 |

### 3.1 C1 已拍板：回滚到「读真实频率」

**原状态**：这条曾经被**单方面改掉**——`docs/06` 记为「已按实测改」，
板型包也被直接改了。这违反了本文件卷首与 `docs/05` ADR-D12 的规矩
（「差异不私自改包，一律记进清单由用户拍板」）。

**改成了什么、为什么不对**：

```yaml
# 改后的（现已回滚）
kind: devfreq_load
args: {path: /sys/class/devfreq/fdab0000.npu/load, measure: duty_cycle}
provides:
  - {tag: custom.rk3588-atk.npu.duty,    sample: duty}
  - {tag: custom.rk3588-atk.npu.freq_hz, sample: freq_hz}
```

三处问题：

1. **语义**：`load` 文件里的 `@<freq>Hz` 是「这条 duty 是在哪个频率上测的」，
   不是「此刻的频率」。C1 原本要的是**当前频率**。
2. **时延**：这个 reader 挂在 `rare` 组（30 秒一次），
   而 `npu.freq_hz` 的名字暗示它是「当前」——每 30 秒才更新一次的「当前频率」很容易被误读。
3. **流程**：绕过了「由用户拍板」这一步。

**已回滚为**：读 `/sys/kernel/debug/rknpu/freq`（实测内容 `1000000000`，就是当前频率），
或 `/sys/class/devfreq/fdab0000.npu/cur_freq`（同为 `1000000000`）。

**回滚后的取舍**：`/sys/kernel/debug/rknpu/freq` 依赖 debugfs，
没挂载时读不到（报 `unavailable`）；`cur_freq` 在 sysfs 下 always available。
两条路径都实测存在，具体选哪条由用户定（🔵 建议真机各读一次确认在变频时是否一致）。

**C7 怎么办**：占空比对照量仍然有用，但**不能**再从同一条 `load` 读「频率」。
做法是让对照量只提供 `duty`（不提供 `freq_hz`），频率单独从上面两条路径之一取。
这样「利用率 / 占空比 / 频率」三者的语义各自干净，不再互相冒名。

| GPU 的 devfreq `load` 空闲时读 **0** | `/sys/class/devfreq/fb000000.gpu/load` = `0@300000000Hz` | 与 NPU **行为相反**——所以 GPU 的那条**可能**就是忙碌占比，但**缺一次带负载的采样**（见 5.3） |
| NPU 真正的利用率在 rknpu | `NPU load:  Core0:  0%, Core1:  0%, Core2:  0%,` | `npu.usage` = **三个核的最大值**（契约 §一 词表） |
| **rknpu 那一行末尾带逗号** | `Core2:  0%,` | 解析器要认这个尾巴，否则会把 `,` 当成数值的一部分 |
| **thermal zone 的 type 带 `-thermal` 后缀** | `soc-thermal=34230`、`gpu-thermal=33307`、`npu-thermal=34230` | 归并到 `temp.soc` / `temp.gpu` / `temp.npu` 时**要剥这个后缀**，不能整串当名字 |
| thermal 的值是毫度 | `34230` = 34.23 °C | 契约 C6「单位换算责任写死」——reader 负责 ×1/1000 |
| debugfs **在这块板上挂着** | `debugfs on /sys/kernel/debug type debugfs (rw,relatime)` | rknpu 读得到 → `npu.usage` 是 `ok` 而不是 `unavailable` |
| CPU 簇 = A55×4 + A76×4 | `CPU part` = `0xd05`×4（core 0–3）+ `0xd0b`×4（core 4–7） | `cpu.core.*.cluster` 的取值表 |
| 内存 | `MemTotal: 8107744 kB` / `MemAvailable: 7655500 kB` | `mem.total_bytes` / `mem.available_bytes` |

### 5.6 还没核的 🔵

| 项 | 还差什么 |
|---|---|
| **`gpu.usage` 真的是「利用率」吗** | 采到了两次**空闲**读数（都是 `0@300000000Hz`），但**缺一次带负载的采样**——没法证明它随负载上升。这是 `spec/01` §六 准入门槛第 2 条（「必须先在多个板上核对语义一致」）要求的，**仍是最该补的一条** |
| `/sys/class/devfreq/fdab0000.npu/load` 的 `@freq` 含义 | 它是「duty 在哪个频率上测的」还是「当前频率」？与 `rknpu/freq`、`cur_freq` 在变频时是否一致？需要一次**变频过程**中的连续读数 |
| `rknpu/freq` 与 `cur_freq` 的取舍 | 两条路径的取舍要用户定（C1 回滚后选哪条） |
| `board.kernel` / `disk.*` / `net.*` | 词表里有（v1 标 `reserved`），板型包里没有对应 reader |
| **pipe 模式的真实交互** | ✅ **已验**（2026-11-13）：应用真跑起来（Xvfb + CDP 驱动）对着**真板子**敲 `uname -a`，命令真的执行了——见验收清单步骤 3 |
