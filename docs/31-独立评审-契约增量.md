## 二 · Critical

### **C1 · 信任模型缺一块：没有「启用流程包要人点头」**

**结论**：一份能执行任意命令的格式被提升进契约层，而**它生效需要人点头**这条在提案里一个字都没有。

**证据**

- 🟢 `docs/05:1095`（ADR-D31 R2）逐字写着四条，第二条是：
  「**启用流程包要人点头**（确认界面展示『会在哪些目标上跑哪些命令』）」。
- 🟢 `docs/28:192`（R2 裁决行）同一句话；它的理由栏第一条就是
  「不做 → 流程包给 agent 开了一条**在用户机器上执行任意命令**的通道，比 `spec/04:38-47` 禁止的还宽」。
- 🟢 `spec/02:784-800`（§5.6「谁能写板型包」）是现成的先例：
  reader 能执行任意命令 → **包 = 设备权限，不是卡片** → 「启用前要由人确认」。
  流程包的 `exec` 步是**同一种东西**，甚至更宽（它能指定在哪台机器上跑）。
- 🟢 提案全文检索「点头」只出现在 §3.1 的一句注释里（`docs/30:127`「装卡时点头 ✓」），
  说的是**卡片装卡**的点头，不是**流程包启用**的点头；§五「不做的事」表里也没有这一条。
- 🟢 实现侧完全没有这个机制：`src/main/workflows/runner.ts:102-107` 声明了
  `opts.approved?: boolean`，但**全文件没有任何一处读它**（`grep -n "approved" runner.ts` 只有那一行）；
  `runner.ts:767-773` 的 `granted()` 把动作**无条件**标成已授权；
  `scripts/run-workflow.ts:123` 传的 `approved: true` 是个**没有读者的参数**。

**为什么是问题**

契约层是**权威文档**。「宿主已声明的流程」这句话在没有审批语义的情况下 =
「任何 YAML 文件 = 一条在用户客机上执行任意命令的通道」。
`spec/02` §5.6 花了整整一节堵 reader 那条旁路，流程包这条**更宽**的旁路却一个字不堵。
本工程的产品底线是「**没有人能绕过人的确认**」（`spec/03:172`）；
没有这条，契约层自己就破了这条底线。

**建议怎么改**

在 `docs/spec/05-workflow-pack.md` 里加一节「**流程包的信任模型**」，逐字对齐 `spec/02` §5.6：

| # | 规定 |
|---|---|
| 1 | 谁能写流程包 → **人**；agent 可以起草，**启用要人点头** |
| 2 | 确认界面必须展示：**会在哪些目标（role → profile）上跑哪些命令**（`cmd` 原文 + 角色绑定）、每个写步骤的 `danger`、判据读在哪个角色上 |
| 3 | 「已启用的流程包」= 一份**宿主侧的授权记录**（谁、什么时候、哪些 role、包的哈希）——参照 `spec/04:198-205` 的 `consent_id` 绑哈希的做法 |
| 4 | **升级不静默扩权**：流程包内容变了（命令/角色/`danger`）→ 重新确认 |
| 5 | 未启用的流程包：可以被 `list_workflows()` **看见**（像 `list_data_sources` 一样），但**不可运行** |

### **C2 · `requires.workflows` 与 `spec/03` 正面冲突：封闭 schema 与「requires ⊆ permissions」都破了**

**结论**：提案把流程写权限的**唯一来源**放在 `requires` 里，而 `requires` 在 `spec/03` 里是「愿望」不是「授权」；
并且新增这个字段会**直接被 manifest 校验器判为未知字段**。

**证据**

- 🟢 提案 `docs/30:119-124`：
  ```yaml
  requires:
    workflows: [hello-kernel.build-run]
  permissions:
    write: []          # ← 流程的动作不在这里声明 ✓
  ```
  `docs/30:134` 的权限表：`| `cockpit.workflows.run(id, inputs)` | 写 | `requires.workflows` 里有这个 id ✓ |`
- 🟢 `spec/03:64-80`（§2.2）：「`requires` 里的**每一项**，必须被 `permissions` 里的**某一项**覆盖」；
  🟢 `spec/03:631`（§九 规则 3）：「`requires` ⊆ `permissions`（愿望不得超出授权，按模式覆盖判定）」。
  → 按现有条款，`requires.workflows` 的每一项都**没有**被 `permissions` 覆盖 → **规则 3 不过**。
- 🟢 `spec/03:106-127`（§2.5）：manifest 的 schema **每一层封闭**，未知字段报错；
  🟢 实现 `src/main/cards/manifest.ts:68`：`REQUIRES_ALLOWED = ['tags', 'actions', 'min_board_pack']`
  → `requires.workflows` 是**未知字段** → 规则 10（`spec/03:638`）直接报错。**现成的校验器会拒它。**
- 🟢 `spec/03:93-104`（§2.4）：「**有效写权限 = `permissions.write` ∩ 已授权的动作**」，
  「`permissions.write` 是 manifest 说的，**已授权**是用户点过头的。**只有两个都有的动作才能执行。**」
  🟢 实现 `src/main/cards/permissions.ts:60-63`：`effectiveWrite(perms, granted)` —— 两个集合的交。
- 🟢 `spec/03:162-181`（§3.2）：授权流程是「安装卡片时**扫描 `permissions.write` 里每个动作**」，
  授权记录绑 `(卡片 id, 动作 id, 板型包 id)`；🟢 `spec/03:197-203`（§3.3）：改 manifest 要重新征求授权。

**为什么是问题**

提案把 `requires.workflows` 当成写权限的**唯一**来源，等于宣布：
**「卡片自己声明要跑哪些流程」= 「卡片有权跑这些流程」**。
这与 `spec/03` 的整个权限模型相反——`requires` 是**愿望**（可以超出），
`permissions` 是**申请**，用户点过头才是**授权**。
按提案的写法，一张 AI 写的卡只要在 `requires.workflows` 里写上流程 id，
**装卡时不需要任何人点头**，就能触发一条含 `depmod -a` / `modprobe` /
（乃至 `danger: destructive` 的 `authorized_keys` 写入）的流程。
`spec/03:172` 的「**没有人能绕过人的确认**」当场失效。

而且这不是「要不要加个字段」的问题——**是这一层能不能这么放的问题**：
现有契约把「申请」和「授权」分成两处，是刻意的（`spec/03:99-104`「这条规则让『用户只批准了其中一部分动作』有意义」）。
提案把它压成一处，是**绕过现有条款**。

**建议怎么改**

二选一，但**必须选一条**，并且在 `spec/03` 里写清楚：

| 方案 | 形状 | 代价 |
|---|---|---|
| **甲（推荐）** | 加 `permissions.workflows: []`（与 `write` 并列，**精确 id、不支持通配**，理由同 `spec/03:82-91` 的不对称风险）；`requires.workflows` 仍然保留为**愿望**；运行前的有效集合 = `permissions.workflows ∩ 已启用的流程包 ∩ 该卡已获授权的流程` | 卡片 manifest 多一个键；`spec/03` §2.2/§2.3/§2.4/§三/§九 都要动 |
| **乙** | 不进 manifest：卡片**不能**触发流程，只有 agent（MCP）能 | 用户的「点一下就编译上板」还是没位置——用户等的就是这个（`docs/05:1208`） |

**无论选哪条，都要同步**：`spec/03` §2.5 的封闭层表加 `permissions.workflows`、
§九 规则 3 加一条「`requires.workflows` ⊆ `permissions.workflows`」、
规则 10 明确新键名、§3.2 的授权流程加「装卡时对流程逐个点头（展示该流程会在哪些 role 上跑哪些命令）」。

### **C3 · 长任务的运行语义整段缺失：同步返回整条时间线，与实测耗时对不上**

**结论**：提案让一次调用**同步返回完整时间线**，而实测编译步是 58.9s / 98.5s；
没有 `run_id`、没有 poll、没有续跑、没有幂等、没有取消语义——这段在契约里必须是有的。

**证据**

- 🟢 提案 `docs/30:136-139`：
  ```js
  const r = await cockpit.workflows.run('hello-kernel.build-run', { project: '01-hello' });
  // r = { ok: true, runId: 'wf-…', stages: [ { stepId, ok, verified, audit_id, … } ] }
  ```
  —— **一次调用返回全部阶段**。卡片 API 与 MCP 工具都是同步调用。
- 🟢 实测耗时：🟢 `docs/superpowers/spikes/2026-11-16-流程直传.md:56`「`compile` **58.9s**」、
  `:92`「`compile` **98.5s**」；且 🟢 同报告 `:111` 记着两跳传输的耗时波动是
  **3.8s / 75.6s / >110s**（20 倍）。
- 🟢 `docs/05:1102`（ADR-D31 R9）：「时间线是一条**新通道**……首版形状 **poll**」。
  提案 `docs/30:170` 也自己写了「流程的卡片 API 的推送（订阅进度）→ 首版 **poll**」。
  → **但 poll 与「一次调用返回全部阶段」是两种形状**，提案只否了 push，没给 poll 的形状。
- 🟢 `spec/04:533-539`（§六「MCP 自身的边界」）：「**不存 agent 的状态** | 每次调用自带上下文」。
  一个「运行中的流程 + 它的阶段」就是状态。🟢 `docs/28:91` 已经把这条列为待处置项
  （`27·M6`：「`run_workflow` 要求宿主长期保存任务状态，与 `spec/04:533-540` 冲突」）。
- 🟢 取消与清理也没测：🟢 spike `:160`「**取消**（Ctrl-C 中途停）—— 执行原语**不可中断**（ADR-D32 D32-4）」、
  `:161`「**失败/取消后的清理**……半截产物的清理还没做」；🟢 `docs/05:1280`（O25）把 abort 归流程层。

**为什么是问题**

契约必须能回答三个问题，提案一个都没答：

1. **调用返回时流程还没跑完怎么办？** 现在的形状是「卡住两分钟」。
2. **流程跑到第 3 步要人确认，前 2 步已经写了板子，重试会不会再来一遍？**
   🟢 实现里的行为是：`runner.ts:165-177` 一遇到 `needs_confirmation` 就 `break`，
   整个运行**停在半路**；重试只有一条路——**从头再跑一遍**（`runner.ts:151` 的 `for` 循环没有断点续跑）。
   → 编译两遍、传输两遍、`depmod -a` 两遍。**契约必须说清这是不是允许的。**
3. **同一个流程被点两次会怎样？** 没有幂等键、没有运行锁、没有并发约束。
   🟢 `docs/28:73`（I7）早就提过：「流程在板上跑 30 秒命令 → 这 30 秒该板采样全停摆（`SPEC-D22` 一次往返独占）；状态机缺 `awaiting_confirmation`、缺并发约束」。

**建议怎么改**

契约里把「运行」定成一个**有身份的对象**，而不是一次同步调用：

```
run_workflow(id, inputs) → { ok: true, runId: "wf-…", state: "running" | "awaiting_confirmation" | "done" | "failed" }
workflow_status(runId)   → { runId, state, stages: [...] }        ← poll
workflow_confirm(runId, stepId, confirm_id)                        ← 确认凭据的落点
```

并补齐四条硬规定：

| # | 规定 |
|---|---|
| 1 | **运行有 `runId`**，阶段不可变地追加；`runId` 绑定 `(流程包 id, 输入摘要, 启用人)` |
| 2 | **重试从断点续跑**，不从头重跑：已完成的步骤不重复执行（**这是幂等性**，必须在契约里写死，否则 `depmod -a` + `modprobe` 会跑两遍） |

### **C4 · 确认凭据在流程层没有落点：`confirm_id` 缺失，`action` 步永远无法被确认**

**结论**：提案说 `run_workflow` 与 `execute_action`「同样要确认 ✓」，但**没有 `confirm_id` 参数、没有确认工具、没有绑定规则**；
而且实现里 `action` 步根本传不进确认凭据——它会永远卡在 `needs_confirmation`。

**证据**

- 🟢 提案 `docs/30:151-160`（§四）的 `run_workflow(id, inputs, dry_run)` —— **没有 `confirm_id`**；
  全文检索「`confirm_id`」= **0 命中**。
- 🟢 `docs/05:1095`（ADR-D31 R2③）逐字要求：
  「`run_workflow` 与 `execute_action` 同构（`dry_run` → 人确认 → **带 `confirm_id` 重试**）」。
- 🟢 `spec/04:292-300`（`execute_action` 的参数表）里 `confirm_id` 是四个参数之一；
  🟢 `spec/04:416-428`（§2.4.1「`confirm_id` 的生命周期」）把绑定定死为
  `(动作 id, 参数的规范化摘要, **板型包 id**, 契约版本)`，并规定「参数一变，凭据立即失效」「消费即失效」。
- 🟢 流程侧没有任何对应的绑定规则；实现里的凭据绑的是
  `src/main/actions/authorization.ts:150-190`：`(actionId, paramsDigest, packId, contractVersion)`，
  而流程里 `actionId` 是**合成的**（`runner.ts:277` `exec:${step.id}`、`runner.ts:519` `transfer:${step.id}`），
  `packId` 是**流程包 id**（`runner.ts:760` `packId: ctx.pack.id`）——
  **既不是「板型包 id」也不是「动作 id」**，与 `spec/04` 的绑定规则不是同一条。
- 🟢 🟢 **实现 bug**：`runner.ts:409-413`（`runAction`）调 `invokeAction(def, values, deps)` 时
  **没有传 `opts`** → `executor.ts:198-224` 走「没凭据 → 签发一张新的」分支 → **永远返回 `needs_confirmation`**。
  对比 `runner.ts:289-298`（`runExec`）与 `runner.ts:529-538`（`runTransfer`）——**那两个传了 `confirmIds`**。
  → **流程里的 `action` 步无法被确认**。

**为什么是问题**

`danger: destructive` 的步骤是这条产品底线的最后一道闸（`spec/03:172`）。
提案在流程层保留了这道闸的**名字**（§2.4 规则 2「每次运行都要人确认」），
却没给**凭据**、没给**确认工具**、没给**绑定规则**——
契约读者（以及实现者）会照着「同构」两个字自己编一套，
而 `spec/04` 的绑定规则**只覆盖动作**，不覆盖流程。

**建议怎么改**

1. `run_workflow(id, inputs, dry_run, confirm_id?)` —— 参数表照 `spec/04:292-300`；
2. 新增一个 `confirm_workflow(runId, stepId)`（对照 `spec/04:401-414` 的 `confirm_action`）：
   **不返回可用凭据**，只把请求递到 GUI 的确认队列，返回 `confirm_id`；
3. 在 `spec/04` §2.4.1 的绑定表里**加一行流程侧的变体**：
   `(流程包 id, **步骤 id**, 输入的规范化摘要, 契约版本)`——并说清「**输入**变了凭据也失效」
   （输入变了 = 命令变了 = 人看到的东西变了）；
4. 修 `runner.ts:409-413`（`runAction` 也要传 `confirmIds`）——**这一条是实现 bug，不是契约问题，
   但它让「`action` 步要人确认」在实现里变成死路**，契约照现在这样写下去会把 bug 固化。

### **I1 · `inputs` 的类型表不是「照 `spec/02` §4.3」——多一个 `path`、少一个 `default`、多两个字段**

**结论**：提案 `docs/30:66` 标注 `inputs: { … } # 封闭类型表（照 spec/02 §4.3 ✓）`，
但实现里的类型表**与 `spec/02` §4.3 不是同一张**——这是**第二套类型方言**。

**证据**

- 🟢 `spec/02:482-489`（§4.3 的封闭表）只有五个 type：
  `integer` / `number` / `string`（必填 `maxLength`）/ `boolean` / `enum`（必填 `values`）；
  可选字段是 `min` / `max` / **`default`** / `pattern`。
- 🟢 `src/main/workflows/format.ts:29`：
  `export const INPUT_TYPES = ['string', 'integer', 'number', 'boolean', 'enum', 'path'] as const;`
  → **多一个 `path`**。
- 🟢 `src/main/workflows/format.ts:156`：`INPUT_KEYS = ['type','required','maxLength','min','max','values','description']`
  → **没有 `default`**，多了 `required` 与 `description`。
- 🟢 `docs/29:43-56`（宿主层格式）自己写的是「类型表**照 `spec/02` §4.3，不另造一套**」，

**为什么是问题**

一旦流程包的 `inputs` 进了契约层，AI 面前就有两张参数类型表：
板型包动作用五类型，流程包输入用六类型 + 另一组可选字段。
**「照 §4.3 ✓」这个标注是错的**——它是本提案里最容易被下游当成「已经统一了」的一句话。

**建议怎么改**

三选一，**并在契约里写死是哪一种**：

| 方案 | 内容 |
|---|---|
| **甲（推荐）** | 流程包的 `inputs` **直接引用** `spec/02` §4.3 的那张表（五个 type + `min`/`max`/`default`/`pattern`），`path` **删掉**（它是 `string` 的一个用法，不是新类型）；`required` 保留（它表达的是「必填」，与 `default` 互补，不冲突），`description` 保留（文档字段） |
| 乙 | 保留 `path`，但契约里明写「流程包的输入类型表 = `spec/02` §4.3 **加一个 `path`**」，并给出 `path` 与 `string` 的**唯一差别**（`path` 只许出现在路径位置的参数上，运行时做路径规范化） |
| 丙 | 不给流程包单独的输入类型表，流程包的输入**就是**板型包的动作参数（`spec/02` §4.3） |

**不管选哪个，`spec/02` §4.3 那张表都要加一句「本表被流程包引用」（避免下游又长出第三张）。**

### **I3 · `readback.role` 对形式 1（`tag`）会被静默丢弃**

**结论**：提案 §2.3 说判据「只多一个 `role`」，没说它只对形式 2–5 有效；
而实现里 `tag` 分支**提前 return**，`role` 根本没被解析——写进去会被**静默忽略**。

**证据**

- 🟢 `docs/30:82-89`：示例用 `kind: verify` + `role: target`，但正文没限定形式。
- 🟢 `src/main/workflows/format.ts:516-527`：
  ```ts
  if (raw['tag'] !== undefined) {
    out.tag = nonEmptyString(raw['tag'], 'readback.tag', ctx);
    if (raw['expect'] !== undefined) { … }
    return out;            // ← 在这里就返回了
  }
  ```
  `role` 的解析在 `format.ts:553-559`（在 `return` **之后**）→ **`readback: {tag: 'x', role: 'target'}` 的 `role` 被丢掉，不报错**。
- 🟢 而且**语义上也不成立**：形式 1 读的是**宿主当前连接**的 tag
  （🟢 `src/main/index.ts:271` `readTag: (tag) => runtime.sampleTag(tag)`），
  **不是 role 那条连接**的 tag —— role 可以是客机，客机上没有 tag。
- 🟢 🟢 宿主层 CLI 入口**根本没接 `readTag`**：`scripts/run-workflow.ts:114-124` 的 deps 里
  只有 `targets` / `profileFor` / `audit` → `runner.ts:601` 退回 `async () => undefined`
  → **形式 1 在唯一的宿主入口里永远返回 `not_found`**。

**为什么是问题**

「只多一个 `role`」这句话会被读成「五种形式都能指名角色」。
实际上：**形式 1 根本不能指名角色**（tag 是宿主连接级的概念），

**建议怎么改**

> 与 role 无关。**形式 2–5 可以在 `readback.role` 里指名在哪个角色上读**；不写 = 本步自己的角色。
>
> **校验规则**：`readback` 带 `tag` 时又带 `role` → **报错**（不是忽略）。

（顺带：宿主层也要把这条加上，否则契约与实现继续错位。）

### **I4 · 跨目标判据把 `destructive` 步骤的回读降级成 `kind: none`——绕过了 `spec/02` §4.4.1**

**结论**：`spec/02` 明写「`destructive` **仍禁止** `none`」；
流程层为了做跨目标判据，给合成的动作塞了 `kind: none`——**当这个步骤是 `destructive` 时，这条禁令被绕过**。

**证据**

- 🟢 `spec/02:548`（§4.4.1 规矩 3）：「**只允许 `danger: reversible`** | `destructive` **仍禁止** `none` |
  不可逆动作不许『不验证』」；
  🟢 `spec/02:862`（校验规则 15）：「`danger: destructive` 的动作必须有 `readback`（形式 1/2）或 `verify`（形式 4），
  **不得**用 `command_ok`，**也不得**用 `none`」。
- 🟢 实现：`src/main/workflows/runner.ts:284-287`（`runExec`）与 `runner.ts:525-527`（`runTransfer`）：
  ```ts
  readback: step.readback?.role !== undefined && step.readback.role !== role
    ? { kind: 'none', consequence: '判据在另一个角色上读（由流程层执行）' }
    : toReadbackDef(step.readback, substitution),
  ```
  而同一个合成动作的 `danger` 来自 `step.danger ?? 'reversible'`（`runner.ts:280` / `:521`）。
  → **一个 `danger: destructive` + 跨角色判据的步骤 = 合成出「destructive + `kind: none`」的动作。**
- 🟢 流程校验器**不查这条**：`src/main/workflows/format.ts:434-440` 只解析 `danger` 的取值，
  不看 `readback.kind` 与 `readback.role` 的组合。
- 🟢 提案 `docs/30:96-103`（§2.4）只承诺了「编码 + 危险地板」两条，**没有提回读闭环**。

**为什么是问题**

`spec/02` §4.4.1 那条禁令的**理由**是：「不可逆动作不许『不验证』」。
跨目标判据本身是**另一个事务**（`docs/05:1224` D33-2），
所以「合成动作读不到」是事实；但**事实成立 ≠ 禁令可以绕过**——
现在的情况是：一个 destructive 的凭据准备步骤，审计里会写
`verified=false detail="判据在另一个角色上读（由流程层执行）"`，
而**流程层的跨目标那一行**又是**另一个 `audit_id`**——追责时看不出
「这个 destructive 步骤到底验没验过」。

**建议怎么改**

契约里补一条**流程层的等价规定**，并让校验器执行：

> **写步骤 + 跨角色判据** → 该步骤在**执行侧**的回读是「不可观测的」（记 `verified=false` 并注明原因），
> **但它必须在跨目标那一行里被验证过**，否则该步骤**不算完成**。
> **判定口径**：`destructive` 的步骤若其判据在别的角色上 → 校验器**要求**该判据存在且非 `kind: none`；
> **执行侧**的 `kind: none` 是执行器内部的合成产物，**不计入** `spec/02` §4.4.1 的禁令
> （理由写死：那条禁令约束的是**声明**，不是**运行时合成**）。

并在 `docs/30` §2.4 规则 1 里把「编码 + 危险地板」扩成「编码 + 危险地板 + 回读闭环（跨目标版）」。

2. **在提案里给这两条标出「谁来执行」**，别让它们以「校验规则」的身份混在 §2.4 的表里。

**附**：🟢 真机实测里，**凭据准备那一步从没跑过**——
`docs/superpowers/spikes/2026-11-16-流程直传.md:164`：
「**凭据准备这一步**……本轮没跑『装凭据』那一步」。所以这条规则目前**零实测**。

### **I6 · `readback.tag` 不查核心词表——ADR-D31 R3 想杀的那个洞原样留着**

**结论**：流程包可以声明任何一个 `readback.tag`，校验器不查它是不是核心词表里的 tag。

**证据**

- 🟢 `docs/05:1096`（ADR-D31 R3）的理由栏：「「编译成功」不是板上的量测；词表 21 条**无 `system.*`** →
  样例里的 `system.load` 是**私造词表**」。
- 🟢 `docs/28:58`（C3）：「旗舰 YAML 私造词表：时间线里 `"tag": "system.load"`，而词表 21 条**无任何 `system.*`** →
  违反『词表只有一个源头』，且 `await` 它永远是 `unavailable`」。
- 🟢 `spec/02:848`（校验规则 1）：「每个 `provides[].tag` 匹配核心词表，或落在 `custom.<本包 id>.` 下」——
  **板型包有这条**，流程包没有。
- 🟢 `src/main/workflows/format.ts:516-517`：`out.tag = nonEmptyString(raw['tag'], 'readback.tag', ctx);`
  → **只查非空**。
- 🟢 `spec/00:129`（SPEC-D9）：「核心词表只有一份，就是 `data/tag-vocabulary.yaml`」。

### **I8 · `file.transfer` 的命令跑在**源**角色上——提案没写这条，而它是直传的全部语义**

**结论**：提案的 kind 表只列了必填字段，没说 `cmd` 在哪台机器上跑；
而「传输命令在**源目标**上跑」正是 ADR-D31 R7 的核心。

**证据**

- 🟢 提案 `docs/30:77`：`| `file.transfer` | 搬运（源 → 目的地） | `from` `to` `cmd` |` —— **没说 `cmd` 在哪跑**。
- 🟢 `src/main/workflows/runner.ts:513-515`：
  ```ts
  const fromRole = step.from?.role as string;
  const profileId = ctx.pack.roles[fromRole]?.profile;
  ```
  → **命令在 `from` 那台机器上跑**（不是宿主、不是 `to`）。
- 🟢 `docs/05:1100`（ADR-D31 R7）：「形态 = **「在源目标上跑一条传输命令」**」；
  🟢 `fixtures/workflows/hello-kernel.build-run.yaml` 的 `deliver` 步注释：
  「**直传**：传输命令在**源目标（客机）**上跑」。
- 🟢 🟢 直传是这次的核心价值：🟢 spike `:107-114`「**直传 vs 两跳：909KB 的差别是 750 倍**」。

**为什么是问题**

「cmd 在哪跑」决定了三件事：**谁的网络、谁的凭据、谁的目标机**。
契约不说，AI 就会写出 `scp` 在宿主上跑（回到两跳，慢 750 倍），

**建议怎么改**

在 kind 表里加一句（或加一列「在哪跑」）：

> `file.transfer` 的 `cmd` **在 `from` 那个角色上执行**（源目标）。
> → 这就是「**直传**」：产物**不经宿主取回**。
> 目的地 `to` 只提供**路径**（`path` 或 `placement`），**不由宿主连接**。

### **I9 · 流程里 `action` 步的授权被桩掉；`params` 只许字符串 → integer/boolean 动作参数结构上不可达**

**结论**：ADR-D31 R2① 说 action 步「走 M6 全链」，但流程把 M6 的第③步授权换成了「无条件已授权」的桩；
同时 `action` 步的 `params` 只能是字符串，导致**整数/布尔型动作参数根本传不进去**。

**证据**

| 项 | 证据 |
|---|---|
| 授权被桩掉 | 🟢 `src/main/workflows/runner.ts:767-773`：`granted: () => ({ actions: { [actionId]: undefined } })` —— **无条件已授权**；而 `src/main/actions/executor.ts:182-194` 的第③步授权就是查这个集合 |
| ADR 的要求 | 🟢 `docs/05:1095`（R2①）：「写步骤要么引用**已声明的动作**（**走 M6 全链**），要么是自由命令（**必须过同一张危险地板**）」 |
| `params` 只许字符串 | 🟢 `src/main/workflows/format.ts:416-419`：`params[k] = nonEmptyString(v, ...)` → **值必须是字符串**；🟢 `runner.ts:406-408` 再经 `substituteValue` 仍是字符串（`substitute.ts:81-84` `String(value)`） |
| 编码器只吃真类型 | 🟢 `src/main/actions/encoder.ts:61-66`：`case 'integer': if (typeof raw !== 'number' \|\| !Number.isInteger(raw)) throw invalid(param, '要 integer（整数）')` → **字符串 `'30'` 会被拒** |

**为什么是问题**

1. **授权**：M6 全链的第③步在流程里是空转。那么「流程引用了一个 destructive 的板型动作」时，
   **谁授权它**？按提案 §2.4 规则 2，destructive 步骤每次要人确认——那是**执行期**的确认；
   但**这个动作本身有没有被授权过**（装包/装卡时点过头没有）被跳过了。
2. **`params`**：`spec/02` §4.3 的 `integer` / `number` / `boolean` 三种类型，
   在流程的 `action` 步里**结构上不可达**。契约若不定义 `params` 的类型，就等于默认它只有字符串。

**建议怎么改**

- 契约里为流程的 `action.params` **指定类型**（照 `spec/02` §4.3 的那张表），
  并明确**由被引用动作自己的 `params` schema 校验**（运行时二次校验，`spec/02:609-610` 已经要求）。
- 明确流程里的 action 步**走哪条授权**：
  - 甲：流程包被启用时，**它引用的每个动作被一次性授权**（绑定 `(流程包 id, 动作 id, 板型包 id)`，
    与 `spec/03:176` 的授权记录同构）——**这最省事，也最像现有模型**；
  - 乙：流程的 action 步每次执行都按 `spec/03:162-181` 单独确认（**贵，但最严**）。
  **必须选一个并写进契约**，不能像现在这样「全链」两个字糊过去。

### **M2 · `roles` 的 profile 存在性不是校验器职责——契约要说清哪一层查**

- 🟢 `src/main/workflows/format.ts:362-376`：`parseRoles` **不查 profile 存不存在**；
  🟢 `scripts/run-workflow.ts:82-87`：在**入口脚本**里查，缺了就 `exit(2)`。
- **建议**：契约里写明「**`roles.*.profile` 的存在性与 `transport` 检查在装载期做**（校验器拿不到宿主配置）」——
  别让实现方以为纯 YAML 校验能查（这条与 I5 的 `local` 检查是同一层的事）。

### **M3 · `placement` 封闭词表与「路径三形态」在提案里完全没有**

- 🟢 `docs/29:100-116`（§4.2）：目的地三形态 `path` / `placement` / `ask`；
  `placement` 封闭词表 = `kernel-module` / `user-program`；🟢 `src/main/workflows/placement.ts:22-33` 是实现；
  🟢 `docs/05:1274`（O19）已拍板「三形态都支持」。
- 🟢 提案 `docs/30:52-113`（§二）**一个字都没提 `placement`**——但 §2.2 的 kind 表里 `file.transfer` 的 `to` 就是它。
- **建议**：§二 必须补 `placement` 词表（封闭，两个 id）+ 三形态 + 「拼错 → 报错」（`docs/29:116` 的理由：
  不能默默回落到「随便放」→ 流程报成功而东西不在该在的地方）。

### **M4 · 提案的 §二 没有字段表——`step.id` / `timeout_ms` / `on_mismatch` / `out` / `params` / `exclude` / `dir` 全都不在**

- 🟢 `src/main/workflows/format.ts:159-176`：`STEP_KEYS` 有 **16 个**字段；提案的 §2.2 表只有「kind / 干什么 / 必填」三列。
- **建议**：契约层必须给**完整的字段表**（字段 / 类型 / 必填 / 语义），
  否则「封闭 schema」只是一句口号——下游不知道有哪些字段。

### **M5 · §2.5 只说「每个写步骤一行审计」，漏了读步骤也有一行**

- 🟢 提案 `docs/30:109`：「**每个写步骤一行审计**」
- 🟢 实现里**读步骤也写行**：`runner.ts:456-464`（discover 没找到）、`runner.ts:479-488`（discover 找到）、
  `runner.ts:629-638`（await/assert）。
- 🟢 `docs/05:1101`（ADR-D31 R8）的要求更宽：「**非动作步骤也必须产审计行**」。
- **建议**：改成「**每个步骤一行审计**（写步骤与读步骤都写）」。

### **M6 · §五「不做的事」漏了两条该写进去的**

- 🟢 「流程可中断」——🟢 `docs/05:1166`（D32-4）/ `:1280`（O25）：abort 归流程层，**首版做不到**；
  🟢 spike `:160` 实测确认「取消杀不掉在飞的传输」。
- 🟢 「失败/取消后的清理」——🟢 `docs/05:1142`（尖兵 S4）：中断的传输会在板子上留垃圾。
- 🟢 还应有一条：「**流程包首版没有分支/循环**」（🟢 `docs/29:188`）——它是一条**语法限制**，
  不写下来的后果是 agent 会写分支然后发现跑不了。
- **建议**：§五 补这三条。

### **M7 · 提案 §3.2 的 stage 形状没说 `verified` 什么时候是 `false`**

- 🟢 提案 `docs/30:138`：`stages: [ { stepId, ok, verified, audit_id, … } ]`
- 🟢 实现里 `verified: false` 有**两种**来源：
  （a）判据是 `kind: none`（`src/main/actions/readback.ts:264-272`）；
  （b）**跨目标判据**：执行侧永远是 `kind: none` → `verified: false`，
  真实结论在 `readback_audit_id` 那一行（🟢 `runner.ts:284-287`、`:308-309`）。
- 🟢 `spec/04:287-289`（UI 口径写死）：「`verified: false` → 卡片**必须**显示『**已执行，未验证**』」
  ——**按现在的形状，一张卡上「直传成功」的那一步会显示「未验证」**，
  而它其实验过了（在另一个角色的那一行里）。
- **建议**：契约里定死 `verified` 的口径，并给跨目标情形一个**不同的字段**
  （例如 `verified: false` + `verifiedBy: 'workflow:<pack>:<step>:readback'`），
  否则 UI 口径（`spec/03:287-289`）与流程的返回形状打架。

### **M8 · 没有给 `docs/06-契约核对.md` 留台账条目**

- 🟢 `docs/06` 是本工程核对契约与实现的固定去处（现有 C1–C16）。
- **建议**：改动清单里加一条「在 `docs/06` 留一条 C17（流程包晋升契约的核对台账）」。
