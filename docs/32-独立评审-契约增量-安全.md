## 〇 · 总判定

### **需重做（信任模型这一层）。**

这份提案把一条**能在用户机器上执行任意命令**的格式提升进契约层，
却在提案文本里**丢掉了它原本有的那条底线**（ADR-D31 R2：「启用流程包要人点头」）。
同时它把「卡片声明了 `requires.workflows`」当成授权，
把「每个写步骤都过危险地板」当成已经成立的保证——
这两句在实现里**都不成立**，而且都是**静默不成立**（不报错、不警告、照跑）。

契约层是权威文档。把「宿主已声明的流程」写进契约却不写「谁批准了它」，
等于把 `spec/02` §5.6 花了整整一节堵掉的那条旁路（reader 能执行任意命令）
**换了个入口重新打开**，而且比原来更宽（它还能指定在哪台机器上跑）。

## 一 · Critical

### **C1 · 流程包「谁批准了它」在提案里一个字都没有 —— agent 可以自己写一个流程包然后跑它**
**（与 31 号文档 C1 同源；本文补的是安全后果与「注册表怎么来」这个具体漏洞）**

**结论**：提案把 `exec`（在某个角色上跑一条命令）、`file.transfer`（在源机器上跑一条搬运命令）
写进契约，而**流程包本身是一份宿主侧的文件** —— 契约却**没有规定这份文件由谁批准才能生效**。

**证据**

- 🟢 提案全文检索「点头 / 批准 / 启用 / 审批 / consent」——**只有一处命中**：
  `docs/30:127`「卡片只声明『我要用哪些流程』✓（**装卡时点头** ✓）」——说的是**装卡**，不是**启用流程包**。
  `docs/30:96-103`（§2.4 危险等级与确认）四条规则里**没有**「谁批准了这份包」；
  `docs/30:164-172`（§五「不做的事」）也没有这一条。
- 🟢 被丢掉的原文在这里：`docs/05:1095`（ADR-D31 **R2**）逐字写着
  「……**启用流程包要人点头**；`run_workflow` 与 `execute_action` 同构……；**角色不许绑到 `local` 当执行目标**」，
  它的**理由栏**第一条就是「不做 → 流程包给 agent 开了一条**在用户机器上执行任意命令**的通道，
  比 `spec/04:38-47` 禁止的还宽」；`docs/28:192`（R2 裁决行）同一句话，还多一句
  「确认界面展示『**会在哪些目标上跑哪些命令**』」。
- 🟢 先例就在契约里：`spec/02:784-822`（§5.6「谁能写板型包」）——「**板型包 = 设备权限，不是卡片**」，
  「agent 起草可以，**启用前要由人确认**」，「确认界面必须展示：这个包会**执行哪些命令**……
  每个动作的 `danger` 等级、涉及哪些 tag 与设备路径」。
- 🟢 **具体漏洞在「注册表」上**：提案 §四给了 MCP 工具 `run_workflow(id, inputs, dry_run)`（`docs/30:156`）——
  它按 **id** 调用，宿主就必须有一份「id → 流程包」的**注册表**。
  提案**从头到尾没说这份注册表怎么来、谁能往里加**。
  若注册表 = 「扫描某个目录里的 YAML」，那么 **agent 往那个目录写一个 YAML = 注册了一条流程**。
  `spec/04:40`（§1.3）明写「agent 只能触发**已声明的动作**，不能发任意命令」——
  `run_workflow` 一旦能被 agent 自造的包喂到，这条禁令从侧门被绕开。
- 🟢 流程包比板型包**更宽**：板型包只能作用在它绑定的连接上；流程包的 `roles` → `profile`
  让它**指定在哪台机器上跑**（`docs/30:67`），且 `exec` / `file.transfer` 都是**自由命令**。

**为什么是问题**

契约层说「宿主已声明的流程」却不说「声明」这个动作由谁做、要不要人点头，
契约读者（以及实现者）会照字面理解成「**任何一份 YAML 文件 = 一条在用户客机上执行任意命令的通道**」。
本工程的底线是「**没有人能绕过人的确认**」（`spec/03:172`）——
这条底线现在写在契约里，但提案正好在它旁边开了个门。

**建议怎么改**

在 `docs/spec/05-workflow-pack.md` 写一节「**流程包的信任模型**」，逐条对齐 `spec/02` §5.6，
外加本文这两条：

| # | 规定 |
|---|---|
| 1 | 谁能写流程包 → **人**；agent 可以起草，**启用要人点头** |
| 2 | 确认界面必须展示：**会在哪些目标（role → profile）上跑哪些命令**（`cmd` 原文 + 角色绑定 + 每个写步骤的 `danger` + 判据读在哪个角色上） |
| 3 | 「已启用的流程包」= 一份**宿主侧的授权记录**（谁、何时、哪些 role、包的**内容摘要**）；**注册表只收已启用的包** |
| 4 | **升级不静默扩权**：包内容变了（命令 / 角色 / `danger` / 判据）→ 重新确认 |
| 5 | 未启用的包：`list_workflows()` **看得见**（像 `list_data_sources`），**跑不了**；`run_workflow` 对它返回 `denied` |
| 6 | **流程包不许出现在卡片能读的目录里**：它的路径与内容不进任何返回给卡片的数据 |

### **C2 · 跨目标判据是一条「不过地板、不过确认」的命令通道，而且能指名任意角色**
**（31 号文档没有这一条；31 的 I4 说的是「destructive + `kind: none` 绕过了 §4.4.1 禁令」，与此相邻但不同）**

**结论**：提案 §2.3 把 `role` 加进判据（「在哪个角色上读」），
但**判据的命令不在任何一道闸门后面**——不过危险地板、不过授权、不过确认——
而且可以指名**流程里任意一个角色**，包括**本流程本不该碰的那台机器**。

**证据**

- 🟢 判据命令的执行路径（`src/main/workflows/runner.ts:586-613`）：
  ```ts
  exec: (command) => ctx.deps.targets.runOn(profileId, (conn) => conn.exec(command)),
  ```
  → **直接落到连接上执行**。整条路径里**没有** `checkFloor`（`src/main/actions/floor-check.ts:226-228`
  只在 `invokeAction` 里被调，`src/main/actions/executor.ts:180`）、
  **没有** `authorize`（`executor.ts:183`）、**没有**确认通道（`executor.ts:197-225`）。
- 🟢 同一个洞对**同角色**的判据也成立：`runner.ts:284-287` 把判据塞进合成动作，
  执行器里的 `verify` 形式走的是 `deps.exec`（`src/main/actions/readback.ts:219-237`）——
  **那条命令同样不过地板**（地板只查动作自己的那条 `command`）。
- 🟢 `verify` 形式会**反复执行**直到成功或超时（`readback.ts:223-237`，每 100ms 一次）→
  一条有副作用的判据命令会被**重复执行 N 次**。
- 🟢 提案 §2.4 规则 1 只承诺「**每个写步骤**都过 §4.6 的编码 + §5.2.1 的危险地板」（`docs/30:100`）——
  判据按提案自己的分类**不是写步骤**，所以地板**静默不适用**。
- 🟢 形式 1（`tag`）的跨角色读**读的是运行时的连接，不是指名的角色**：
  `runner.ts:601` `readTag: ctx.deps.readTag ?? …`（运行时的 tag store）→
  「在板子上问板子」实际问的是**运行时那条连接** → 跨目标的「事实」可能是**另一台机器的事实**。

**为什么是问题**

- **地板被绕开**：`rm -rf /` 在判据位置**不需要人确认**（地板表 `spec/02:649-656` 里那六条模式只在动作路径上生效）。
- **授权被绕开**：判据能指名**任意 role**，而 role → profile 是宿主侧文件（`docs/30:67`）
  → 一个流程可以读**宿主 profile 表里任何一台机器**上的任何文件。
  `kind: file_equals` 会把文件内容读出来（`readback.ts:139-171`，成功时 `value` = 文件内容）
  → 内容进 `stage.value`（`runner.ts:650`）→ **进卡片**。
- **「跨目标的事实」这条新能力本身没有安全前提**：判据说「板子上真的有那个文件」，
  但它跑在一条**不校验主机身份**的连接上（见 I4）→ 这个「事实」可以是一个假事实。

**建议怎么改**

| # | 规定 |
|---|---|
| 1 | **判据的命令 = 命令**：凡是在流程里执行的命令（写步骤的 `cmd`、判据的 `command`）**走同一套闸门**——编码 → 地板复查 → 确认 → 审计 |
| 2 | 判据命令**不得有副作用**：契约规定它只能是**只读**的；不能验证的办法是 `kind: none` + 非空 `consequence`（`spec/02:546-548`） |
| 3 | `verify` 的轮询必须**只跑一次**（现在的循环会重复执行有副作用的命令） |
| 4 | 判据的 `role` **只能在本流程已声明的 role 里选**（`format.ts:553-559` 已经查了「role 声明过」✓，但没查「这个 role 与本步有授权关系」） |
| 5 | 形式 1（`tag`）**跨角色时必须报错**（读的是运行时的连接，不是指名的机器）——不能静默降级 |

### **C3 · 流程层的确认凭据不绑「实际要跑的那条命令」——一次确认可以复用到同一流程同一步骤的另一组输入**
**（与 31 号文档 C4 同源：31 指出流程层没有 `confirm_id` 规格；本文指出的是「绑什么」——即使按 31 的建议补上参数，照现在的绑定方式**照样可重放**）**

**结论**：`spec/04:416-428` 把 `confirm_id` 的绑定定死为
`(动作 id, 参数的规范化摘要, 板型包 id, 契约版本)`，理由逐字写着
「人批准的那一次和实际执行的那一次不是同一件事」。
流程层照抄了「绑参数摘要」这四个字，**但流程的 `exec` / `file.transfer` 步传的参数恒为 `{}`**
→ 摘要恒等于 `digest({})` → **人批准的是 `make -C /A`，实际跑的是 `make -C /B`，凭据照样有效**。

**证据**

- 🟢 摘要怎么算：`src/main/actions/authorization.ts:122-128`（`paramsDigest`）、
  `:150-190`（`issue` / `consume`）。
- 🟢 流程的 `exec` 步传的是**空参数**：`src/main/workflows/runner.ts:289-291`
  `invokeAction(action, {}, executorDeps(...), …)`；`file.transfer` 步同理（`runner.ts:529-532`）。
- 🟢 而**命令**是在调用之前就已经替换好的（`runner.ts:271` `substituteCommand(step.cmd, substitution)`）
  → **命令随 inputs 变，摘要不变**。
- 🟢 合成动作 id 与包 id 都在摘要里（`runner.ts:277` `exec:${step.id}`、`runner.ts:519` `transfer:${step.id}`、
  `runner.ts:760` `packId: ctx.pack.id`）→ **换步骤 / 换流程不能复用 ✓**（这一半是对的）。
- 🟢 有效期 5 分钟（`authorization.ts:119` `CONFIRM_TTL_MS`）→ 复用窗口明确存在。
- 🟢 顺带：**确认界面上没有参数可显示**（params = `{}`）→ 人确认的是一个他**看不见的命令**
  ——违反 `spec/04:357-360`「确认界面必须显示最终命令与参数域」。
- 🟢 顺带：**`action` 步根本没传凭据**（`runner.ts:409-413` `invokeAction(def, values, deps)` 少了第三个参数）
  → `danger: destructive` 的板型动作在流程里**永远卡在 `needs_confirmation`**（与 31-C4 同源）。
- 🟢 顺带：**流程层现在根本没有确认通道的接线**——`scripts/run-workflow.ts:114-121` 不传 `confirmations`
  → `runner.ts:774-779` 落到 `issue: () => ''` / `consume: () => false` 的桩
  → 流程只能「问」，不能「被确认」。单测里也没有 `confirmations`（`tests/unit/workflows/runner.test.ts:104-113`）。

**为什么是问题**

「destructive 的步骤每次运行都要人确认」（`docs/30:101`）是这条产品底线在流程层的最后一道闸。
但**闸门认的是哪一次执行**这件事没定死 → 闸门形同虚设：
用户点了「确认」之后，同一个包里换一个输入重跑，**命令已经变了，人没看过，凭据还是那张**。
这正是 `spec/04:430-433` 明写要防的那件事。

**建议怎么改**

契约里给流程层写死一条绑定（**不要**照抄「参数摘要」四个字）：

| 项 | 流程层的值 |
|---|---|
| 绑定 | `(流程包 id, **步骤 id**, **inputs 的规范化摘要**, **该步骤最终命令的摘要**, 契约版本)` |
| 输入变化 | 输入一变 → 凭据立即失效（输入变了 = 命令变了 = 人看到的东西变了） |
| 一次性 | 消费即失效（沿用 `authorization.ts:187-188`） |
| 有效期 | 5 分钟（沿用 `authorization.ts:119`） |
| 确认界面 | 显示**最终命令**（替换后的，不是模板）+ 输入 + 目标 role + `danger` |

### **C4 · 「装卡时的授权」与「这张卡能不能跑这个流程」被压成了同一件事 —— 而实现层**根本没有**这道检查**
**（与 31 号文档 C2 同源：31 指出 `requires.workflows` 破了「requires ⊆ permissions」；
本文补的是实现层证据——授权检查在流程路径上被**结构性旁路**，不是「补一个字段」能解决的）**

**结论**：卡片声明了 `requires.workflows` **不等于**被授权；
**这两件事在契约里必须是两件事**（申请 ∩ 人授过），
而且**实现层连「人授过」的那一半都没有落点**——流程路径上的授权检查是**无条件放行**。

**证据**

- 🟢 契约现状：卡片授权是**两层**（`spec/03:93-104`「有效写权限 = `permissions.write` ∩ 已授权」）；
  `requires` 是**愿望**不是授权（`spec/03:64-80`、§九 规则 3 `spec/03:631`）；
  授权记录绑 `(卡片 id, 动作 id, 板型包 id)`（`spec/03:174-177`）。
- 🟢 提案把写权限的**唯一来源**放在 `requires.workflows`（`docs/30:121`），
  并在权限表里写死「`cockpit.workflows.run(id, inputs)` | 写 | **`requires.workflows` 里有这个 id** ✓」（`docs/30:134`）
  → 运行时的判据 =「**卡片自己声明过**」。
- 🟢 **实现层：流程路径无条件放行**——`src/main/workflows/runner.ts:767-773`：
  ```ts
  granted: () => ({ actions: { [actionId]: undefined } }),
  ```
  → 被执行的动作**无条件算「已授权」**；`authorize()` 的第一道检查
  （`src/main/actions/authorization.ts:69-71`「授权集合里有没有这个动作」）永远过。
  对比**卡片路径**：`src/main/index.ts:272` `granted: () => grantedFor(cardId)`（那张卡的人授账）。
- 🟢 **卡片的授权账里没有「流程」这一类**：`src/main/cards/grants.ts:26-31`
  `CardGrant { actionId, domains?, at }`；`:46-52` `GrantStore` 按 `cardId` 存**动作**。
  → 没有「这张卡被批准跑哪些流程」的记录位。
- 🟢 提案 §3.1 的注释「（装卡时点头 ✓）」（`docs/30:127`）**没有对应物**：
  没有规格说装卡时给用户看什么、点的是哪一条、记在哪。
  对比 `spec/02:800-804`（包审批要展示什么）与 `spec/03:179-183`（授权界面必须显示参数范围）。
- 🟢 后果（可算）：一张 AI 写的卡，只要 `requires.workflows` 里写上流程 id，
  就能触发一条含 `depmod -a` / `modprobe`（乃至 `danger: destructive` 的 `authorized_keys` 写入，
  `fixtures/workflows/prepare-credentials.authorize-key.yaml:50-55`）的流程
  ——**而 `permissions.write` 按提案写的是 `[]`**（`docs/30:123`），
  于是 `spec/03:93-104` 的「交集」规则**在这一路上变成空集**，任何交集检查都无从谈起。

**为什么是问题**

这是**两件被合并的事**：
① 装卡时，用户批准「这张卡**可以**用流程 X」；
② 运行时，「这张卡**此刻**对流程 X 的这次调用有效」（输入是什么、目标是哪台、这一步危不危险）。
提案只做了 ①（连 ① 的界面规格都没有），② 完全空白。
更麻烦的是：**实现上 ② 是「无条件真」**——
所以哪怕契约把 ① 写对了，光靠加一个 `permissions.workflows` 字段也堵不住
（执行器那道 `authorize` 在流程路径上根本不查这张卡）。

**建议怎么改**

| # | 规定 |
|---|---|
| 1 | 加 `permissions.workflows: []`（与 `write` 并列、**精确 id、不支持通配**，理由同 `spec/03:82-91` 的不对称风险）；`requires.workflows` 保留为**愿望** |
| 2 | 运行时的有效集合 = `permissions.workflows` ∩ **人授过的流程** ∩ **已启用的流程包** ∩ **本卡可见的目标集合** |
| 3 | 授权账新增一类 `(卡片 id, 流程 id, **流程包内容摘要**)`；流程包内容变了 → 重新征求授权 |

### **I2 · 提案的「每个写步骤都过编码 + 危险地板」与实现不符：角色事实**原样插入**，且流程包校验器**没有地板规则**
**（31 号文档没有这一条；31 的 I2 说的是「占位符词汇表整段缺失」）**

**结论**：`docs/30:100` 承诺「每个写步骤都过 `spec/02` §4.6 的编码 + §5.2.1 的危险地板」。
这两样**各有各的漏**：
① **角色事实不经编码器**（原样插入）；
② **流程包在装包期没有地板检查**（板型包有规则 16，流程包没有）。

**证据**

- 🟢 ①`src/main/workflows/substitute.ts:68-74`：
  ```ts
  // ── 角色事实：原样（它是宿主自己的连接信息）──
  return value === undefined ? `{role:${role}.${fact}}` : String(value);
  ```
  → `{role:target.host}` / `.user` / `.port` / `.key` **原样进命令**。
  `spec/02:595-617`（§4.6）管的是「**参数值**」；流程层**新增了一个不受管的插值面**。
  它的安全性建立在「这些值来自宿主自己的 profile 文件」上（`substitute.ts:18-20` 的注释也这么说）——
  而 **profile 文件里的 `host` 是自由文本**（`src/main/profiles/schema.ts:64-65` 只要求是字符串），
  一个 `host: "10.0.0.1; reboot"` 就是**第二条命令**。
  提案 §2.4 规则 1 那句「过 §4.6 的编码」**对角色事实不成立**。
- 🟢 ②板型包**有**装包期地板检查：`src/main/tags/validator.ts:356-359`（规则 16）

  `src/main/workflows/format.ts` 里 `danger` 只在 `:434-440` 解析取值合法性。
  → 流程包落地时**没有任何地板预警**；地板只在运行时对 `exec` / `file.transfer` / `action` 三种步生效
  （`executor.ts:180`），**判据命令不生效**（见 C2）。
- 🟢 顺带：流程包也**没有**板型包的规则 21（`spec/02:868`「命令模板里的 `{param}` 占位**不得自带引号**」）——

**为什么是问题**

`spec/02:706-710` 有一条方法论级的教训：「**匹配不上不等于安全**……如果规则是『匹配不上就放行』，
那漏写一条 = 开一个后门」。流程层现在正是「漏写」：

**建议怎么改**

| # | 规定 |
|---|---|
| 1 | 契约明写：`{role:*.*}` 的事实**也要过编码**（或明写「事实表里的值必须是 `[A-Za-z0-9._:-]` 的白名单字符集」，并在校验器里查） |
| 2 | 流程包校验器加**规则 16 的对应条**：命中地板的 `cmd` 必须声明 `danger: destructive`（**装包期**报，不是运行期才报） |

| 4 | 判据命令也走地板（并入 C2 的第 1 条） |

### **I3 · 「跨机器写」的粒度 = 「源机器上的一条任意命令」——地板不命中 `ssh` / `scp`，一次确认都不需要**
**（31 号文档没有这一条；31 的 I8 说的是「传输命令跑在源角色上」这个语义事实）**

**结论**：`file.transfer` 步的 `cmd` **在源角色上跑**（客机），
命令里带 `{role:target.user}@{role:target.host}:{to.path}` →
**客机上的一条命令就能往板子上写任何东西**，而这条命令**不命中危险地板** → **不需要任何确认**。

**证据**

- 🟢 `src/main/workflows/runner.ts:503-538`（`runTransfer`）：
  `:513-517` 取的是 **`fromRole`** 的 profile；`:529-538` 在**源**目标上执行这条 `cmd`；
  `:541` 目的地路径进槽。
- 🟢 危险地板表 `spec/02:649-656` 六条模式：`reboot/shutdown/…`、`flash*/upgrade/erase/burn`、
  `mkfs*`、`dd` 到块设备、`rm -rf /`、`iptables -F`。
  **没有 `ssh` / `scp` / `rsync`** → 传输命令**永远命中不了地板** → 永远按 `reversible` 处理
  （`runner.ts:521` `danger: step.danger ?? 'reversible'`）。
- 🟢 黄金样本就是这个形状：`fixtures/workflows/hello-kernel.build-run.yaml:72`
  `scp -o StrictHostKeyChecking=no {from.path} {role:target.user}@{role:target.host}:{to.path}`。
  → 同一份 YAML 里，命令**可以是** `ssh target 'rm -rf /usr/lib/modules'`，**一样不命中地板**。
- 🟢 对比：`spec/02:640-643` 明写「如果没有任何别的约束，一个把 `reboot` 写成 `reversible` 的包就能跳过人的确认，
  **分档就成了摆设**」——流程层把这个洞**原样留着**，只是把命令换成了 `scp` / `ssh`。

**为什么是问题**

「一件事」的写权限因此**不是**「往板子上放一个文件」，
而是「**在客机上执行一条能往任意目标机写的命令**」。
而这条命令**由包给出**（`docs/30:77`）、**由 agent 或人触发**、**一次确认都不需要**（只要不写 `rm -rf /`）。
契约层如果只写「每个写步骤过地板」，这条通道就**合规地存在**。

**建议怎么改**

| # | 规定 |
|---|---|
| 1 | 传输步的写权限**按「目标 + 源 + 路径」建模**，不按「一条命令」建模：契约规定 `file.transfer` **只能**做「把 `from.path` 这个文件放到 `to.path` 这个路径」这一件事 |
| 2 | 传输命令**由宿主生成**（host/port/user 从 role 事实来，源与目的路径从 `from`/`to` 来）——**包不提供传输命令的模板**，或包提供的模板必须**逐词**匹配一个封闭的允许集 |
| 3 | 若保留「包给传输命令」：则**跨目标的写必须走目标侧的确认通道**（不是源侧的），且确认界面显示「将从 A 机把 X 传到 B 机的 Y 路径」 |

### **I4 · 跨目标的「事实」建立在一条**不校验主机身份**的连接上 —— 判据验的是一台可能冒充板子的机器**
**（31 号文档没有这一条）**

**结论**：提案把「跨目标的判据」写成契约能力（`docs/30:82-94`），
但**黄金样本里那条唯一的跨机通道关掉了主机密钥校验** →
「板子上真的有那个文件了吗」这个判据，验的是**一台冒充板子的机器**。

**证据**

- 🟢 `fixtures/workflows/hello-kernel.build-run.yaml:72` 与
  `fixtures/workflows/meminfo-user.build-run.yaml:68`：
  `scp -o StrictHostKeyChecking=no …`。
- 🟢 判据那一步是 `readback: {kind: verify, role: target, command: "test -f {to.path}"}`
  （同文件 `:77-81`）→ 它跑在**同一条不校验身份的连接**上
  （`runner.ts:586-613` → `targets.runOn(profileId, conn => conn.exec(...))`）。
- 🟢 真机实测用的是「客机 → 板子 `scp`」直连（`docs/superpowers/spikes/2026-11-16-流程直传.md:29`
  目标 `192.168.5.100`、`:58` 直传 0.10s）——即**跨机写已经真的发生过**，
  而那条通道当时**不校验主机身份**。
- 🟢 凭据准备那一步更狠：`fixtures/workflows/prepare-credentials.authorize-key.yaml:55`
  往**目标机**的 `~/.ssh/authorized_keys` 追加公钥。
  → 一次不校验身份的传输 + 一次往 `authorized_keys` 的写 =
  **可以把自己的公钥装到攻击者的机器上**（或反过来）。

**为什么是问题**

契约里「跨目标的判据」是一条**新能力**——它回答的是「**另一台机器**上有没有这个东西」。
这条能力的前提是**那台机器的身份可信**。
现在的前提不成立：判据证明的是「**某台**机器的某个路径上有那个文件」。
配合 C1（谁能写流程包）与 I3（跨机写的粒度），这就是一条**完整的、无人值守的跨机写通道**。

**建议怎么改**

| # | 规定 |
|---|---|
| 1 | 跨目标连接**必须校验主机身份**（SSH known_hosts / 指纹固定）；`StrictHostKeyChecking=no` **不许出现在流程包的能力面里** |
| 2 | 「跨目标判据成立」的定义里要写明：**判据跑在那台机器上，且那台机器的身份已校验** |
| 3 | 身份校验失败 → 判据**不成立**（不是「warning」） |

### **I5 · `dry_run` 的回显面：未授权方能拿到跨机的拓扑与凭据路径**
**（31 号文档没有这一条；31 的 I11 说的是「同构不成立：dry_run 的内容没说」）**

**结论**：提案 §四说 `run_workflow(id, inputs, dry_run)`「`dry_run` = **只回显将要执行什么**」，
但**没说这个回显在授权之前能不能拿**。按 `spec/04:317-319` 的先例（「动作的 `command` **只在通过授权后才返回**」），
流程层必须写死「未授权 → 不回显」；不写死，它就成了一条**侦察通道**。

**证据**

- 🟢 先例：`spec/04:317-319`「先查存在性，再查授权。这样一个未授权的调用方能知道『这个动作存在』，
  但**不能知道它会做什么**——动作的 `command` 只在通过授权后才返回。」
  `spec/04:321-322`：`dry_run` 返回的是**编码后**的最终命令。
- 🟢 提案：`docs/30:156`「`run_workflow(id, inputs, dry_run)` | 跑一个流程（`dry_run` = **只回显将要执行什么** ✓）」。
  → 一个流程的回显**比一个动作大得多**：它含**每一步**的命令、**每个 role** 的绑定、
  以及 `{role:x.host}` / `.port` / `.user` / **`.key`** 展开后的值。
- 🟢 `.key` 在封闭事实表里：`src/main/workflows/format.ts:193`
  `ROLE_FACTS = ['host','port','user','key','profile_id']` → **私钥文件路径**可进命令、可进回显。
- 🟢 对比：`list_workflows()` 提案写的是「id / name / 输入声明」（`docs/30:155`）→ **不含命令** ✓ 这一半是对的；
  但 `run_workflow(..., dry_run=true)` 这一半没有前置条件。

**为什么是问题**

未授权的 agent / 未授权的卡片，一次 `dry_run` 就能拿到：
**板子的 IP、端口、用户名、私钥文件路径、落位目录、每一步要执行的命令**。
`spec/04:641` 明写 agent 的可信边界是「agent **不能**读用户的文件系统、不能改授权、不能连别的板子」——
`dry_run` 的回显会把这三条里的前两条的信息**送出去**。

**建议怎么改**

| # | 规定 |
|---|---|
| 1 | `dry_run` **只对已授权的流程回显命令**；未授权 → 返回 `denied`，**不回显任何命令**（照 `spec/04:317-319`） |
| 2 | `list_workflows()` **只给** id / name / 输入声明 / 状态（**不给** role 绑定、命令、路径）——提案 `docs/30:155` 已是这样，**写进契约** |
| 3 | 确认界面与 `dry_run` 的回显里，**`.key` 这类事实要脱敏**（显示「已配置密钥」而不是路径） |

### **I6 · 沙箱面：卡片能看到**别的机器**的路径、内容与目标身份，而 `permissions.read` 管不到它**
**（31 号文档没有这一条；31 的 M7 说的是「stage 的 `verified` 什么时候是 false」）**

**结论**：提案 §3.2 给的返回形状只列了 `stepId / ok / verified / audit_id` +「…」（`docs/30:138`），
**没规定其余字段**。实现的 stage 还有 `role / kind / reason / detail / value`（`runner.ts:40-56`），
其中 **`detail` 与 `value` 会把另一台机器的绝对路径与文件内容带给卡片**。

**证据**

- 🟢 `src/main/workflows/runner.ts:40-56`（`WorkflowStage`）：`role`（`:44`）、`reason`（`:46`）、
  `detail`（`:47`）、`value`（`:55`）。
- 🟢 `detail` 带别的机器的路径：`runner.ts:455`「在 `${dir}` 里没找到 `${pattern}`」——
  `dir` 是**客机上的目录**（`runner.ts:443` 值模式替换）。
- 🟢 `value` 带别的机器的路径：`runner.ts:498` `value: found[0]`（**客机上的绝对路径**）、
  `runner.ts:650`（assert 的回读值）。
- 🟢 `outputs` 槽（`runner.ts:64`）若进返回值 → `{artifacts: '/home/…/hello.ko',
  dest: '/usr/lib/modules/6.1.141/extra/hello.ko'}` → **客机与板子的路径都出去**。
- 🟢 **文件内容**：`readback` 形式 2 成功时 `value` = **文件内容**（`readback.ts:170`）
  → `runner.ts:650` → `stage.value` → 卡片。
- 🟢 `role` **打破「卡片不知道目标」**：提案 `docs/30:40` 说「卡片**只看到流程**（id + 输入声明）✓ → **卡片不知道目标** ✓」，
  而 stage 里带 `role`（`runner.ts:44`）→ role 名 + 上面那条 `detail` 就能反推出「哪个 role 是板子」。
- 🟢 沙箱**管不了这些**：`spec/03:135`（§3.1）「**沙箱只保证卡片搞不垮工作台，不保证卡片不会乱动板子**」；
  `spec/03:540-552`（§7.7）里 `permissions.read` 只管 **tag**；
  对照 `spec/03:579`——`capabilities()` 的 `tags` 是「**已按 `permissions.read` 过滤**」的。
  → **流程的返回是唯一一条不经 `permissions.read` 过滤的数据通道**，而提案没写它要过滤。

**为什么是问题**

卡片是 AI 写的，`permissions.read` 是它唯一的读权限边界。
现在多了一条**不受这条边界约束**的读通道：
「我这张卡看不到板子的 tag，但我能跑一条流程，然后从返回里读出客机的目录结构、
板子的内核版本号、以及判据读到的文件内容」。
`spec/03:341-342` 那句话（一张 AI 写的卡如果能随便把数据发出去……）的前提就是
**宿主不能主动把别的机器的信息递给它**。

**建议怎么改**

| # | 规定 |
|---|---|
| 1 | 契约**逐字段**规定 `stages[]` 的形状与**可见性**：`stepId / kind / ok / verified / reason / audit_id / at / durationMs` 给卡片；**`role` / `detail` / `value` / `outputs` 默认不给卡片** |
| 2 | 若要给，必须**按「本卡可见的目标集合」过滤**（与 `spec/03:579` 的 tag 过滤同一口径） |
| 3 | `detail` 里的路径必须**脱敏**（只给 basename 或相对路径）——跨机路径属于拓扑信息 |
| 4 | 流程返回**不包含** `outputs` 槽（除非显式声明哪些槽是公开的） |

### **M1 · 「值模式原样」+ 回读自己还会再做一次 `{name}` 替换 → 输入值里可以夹带另一个输入**
**（31 号文档没有这一条）**

**结论**：`{input:x}` 在**值模式**下**原样**插进去（`substitute.ts:79-101`），
而回读模块**还会**对已经替换过的文本再做一次 `{name}` 替换（`readback.ts:124`（`expect`，用 raw）、
`:144`（`path`，raw）、`:150`（`expect`，raw）、`:219`（`command`，**encoded**））。
→ 一个输入值里带 `{artifact}`，会被**二次替换成另一个输入的值**。

**证据**：`src/main/workflows/substitute.ts:81-84`（值模式原样）·
`src/main/workflows/runner.ts:599`（`{ raw: ctx.inputs, encoded: ctx.encodedInputs }`）·
`src/main/actions/readback.ts:124` / `:144` / `:150` / `:219`（`substitute(text, params.raw|encoded)`）。

**为什么是问题**：不是命令注入（值模式不进命令，`readback.path` 还会被 `quotePath` 包住
——`runner.ts:602-607`），是**值混淆**：人看到的输入与实际参与比较的值不是同一个。
`spec/02:608-610` 的原话是「**不信任包的自述**，校验不过就拒绝执行」——这条精神要延伸到替换层。

**建议怎么改**：替换**只做一遍**。流程层的判据不要再走 M6 那套 `{param}` 替换；
或值模式的替换结果打一个「已替换」标记，二次替换时跳过。

### **M2 · `run_id` / `audit_id` 是时间戳派生 → 可预测、可碰撞**
**（31 号文档没有这一条）**

**结论**：`runId = wf-${at.toString(36)}`（`runner.ts:118`）、
`audit id = audit-${at.toString(36)}-${seq}`（`audit.ts:314-319`）。
同一毫秒内的两次运行会拿到**同一个 `run_id`**；不同进程各有一个 `seq` → **审计行 id 也会撞**。

**为什么是问题**：这两个 id 是「追责单位」（`spec/04:246-254`、`ADR-D31 R8`）——
**追责单位撞号 = 追责链不可靠**。时间戳还让 id **可预测**（可枚举、可伪造引用）。

**建议怎么改**：两个 id 都用随机量（`randomUUID()`，`authorization.ts:157` 已经是这么做的）。

### **M3 · 封闭事实表里有 `key`（私钥路径）——它会进命令、进 `dry_run` 回显**
**（31 号文档没有这一条）**

**结论**：`ROLE_FACTS` 含 `key`（`format.ts:193`），值是**私钥文件路径**
（`runner.ts:682-684` 取的是 profile 的 `key_filename`）。
它**原样**进命令（`substitute.ts:68-74`），并会出现在 `dry_run` 的回显里（见 I5）。

**为什么是问题**：私钥路径本身不是私钥，但它告诉对手「**这台机器上哪个文件是私钥**」，
而它进了**远端机器的 shell 命令行**（会出现在远端的进程表 / shell 历史里）。
`spec/04:623-625` 把 token 放发现文件里是**因为**「发现文件本身受权限保护」——
同一个标准在这里没人守。

**建议怎么改**：**流程命令里不需要私钥路径**（SSH 认的是 profile 里的配置）→
把 `key` 从 `ROLE_FACTS` 里**删掉**；若确有需要，则在 `dry_run` / 确认界面 / 审计里**脱敏**。

## 四 · 上面六个问题的逐条回答

### Q1 · **谁能触发一个流程？卡片声明了 `requires.workflows` 就等于被授权了吗？**

**结论：等于被「申请」，不等于被「授权」——而提案把这两件事压成了一件；
实现层则**连申请都没兑现**（流程路径上的授权检查无条件放行）。**

装卡时的授权与「这张卡能不能跑这个流程」**必须是两件事**：
① 装卡时用户批准「这张卡**可以**用流程 X」（一次性、绑卡片 id + 流程 id + 流程包摘要）；
② 运行时判「这张卡**此刻**对流程 X 的这次调用有效」（输入、目标、这一步的危险等级）。

- 契约现状：卡片授权两层（`spec/03:93-104`），`requires` 是愿望（`spec/03:64-80`），
  授权记录绑 `(卡片 id, 动作 id, 板型包 id)`（`spec/03:174-177`）。
- 提案把唯一来源放在 `requires.workflows`（`docs/30:121`、`:134`）→ **声明即授权**。
- 实现：`runner.ts:767-773` `granted()` 无条件放行；`grants.ts:26-31` 的授权账里**没有流程这一类**。
- 谁能触发：**人**（`scripts/run-workflow.ts:114-124`，唯一有人点头的一条）、
  **卡片**（提案新增）、**agent**（提案新增）——后两条在契约里都没有授权落点（C1 + C4）。

### Q2 · **流程包里的写步骤凭什么被信任？谁批准了它？agent 能不能自己写一个流程包然后跑它？**

**结论：提案里「谁批准了它」**不存在**。按提案现在的字面，**能**——
agent 写一个流程包（写文件是 agent 的本职工作，`spec/04:535`）→ 放进注册表目录 → `run_workflow(id)` → 跑。

- 丢掉的原文：`docs/05:1095`（ADR-D31 **R2**）逐字「**启用流程包要人点头**」，
  理由栏「不做 → 流程包给 agent 开了一条**在用户机器上执行任意命令**的通道，比 `spec/04:38-47` 禁止的还宽」；
  `docs/28:192` 同句，还要求「确认界面展示『**会在哪些目标上跑哪些命令**』」。
- 提案全文只有 `docs/30:127` 一处「点头」，说的是装卡。
- 先例：`spec/02:784-822`（§5.6）对板型包的完整处置（包 = 设备权限；agent 起草可以，**启用要人点头**）。
- 具体漏洞：MCP 的 `run_workflow(id, …)`（`docs/30:156`）需要一份「id → 包」的注册表，
  **提案没说它怎么来、谁能加**（C1 的建议第 3、5 条）。
- 附带：**流程包比板型包宽**——它能指定在哪台机器上跑（`docs/30:67`），
  而 `local` 这个 transport 在本机是真的会执行命令的（`src/main/hal/local.ts:58-64`：Windows 上 `cmd.exe`、其他 `/bin/sh`）；
  ADR-D31 R2 明写「**角色不许绑到 `local` 当执行目标**」，而**流程包校验器不查**
  （`format.ts:362-376` 只看 `purpose`/`profile` 非空）→ 流程包可以在**用户的 PC 上**跑命令。
  补一句 31 号文档没说清的严重性：**危险地板是 POSIX 命令表**（`spec/02:649-656`），
  而 `local` 在 Windows 上跑的是 `cmd.exe` → `del /f /s /q C:\`、`format c:`、`powershell -enc …`
  **一条都不命中地板** → 在 Windows 上，`local` 角色的地板**等于没有**。
  （与 31-I5 同源，本文补严重性。）

### Q3 · **注入面：流程的 `exec` 命令是宿主拼的还是包给的？包给的命令 + 外部输入，经过编码器之后还剩什么面？**

**结论：命令是**包给的**（`docs/30:75`、`docs/29` §四）。宿主只做「替换 → 编码 → 地板」。
**输入值那一路是关着的**（有单测：`tests/unit/workflows/runner.test.ts:144-161`，
`{input:note}` = `x; reboot` → `echo 'x; reboot'` ✓）。
**但还剩三个面**：**

| 面 | 证据 | 状态 |
|---|---|---|
| **角色事实原样插入**（`{role:x.host}` 等不经编码器） | `substitute.ts:68-74`；事实表 `format.ts:193` | ✗ 提案 §2.4「过 §4.6 的编码」对它**不成立**（I2） |
| **判据的命令不过地板、不过确认** | `runner.ts:586-613`、`readback.ts:219-237` | ✗ 一条**无闸门的命令通道**（C2） |
| **值模式原样 + 回读二次替换** | `substitute.ts:79-101` + `readback.ts:124/144/150/219` | △ 不注入命令，但**值会混淆**（M1） |

**两套替换会不会有一条漏网**：会——**命令模式与值模式的分界不在「谁来填」，而在「填进去的东西会不会进 shell」**。
现在的实现里：
- `{input:x}` → 命令模式按类型编码（`runner.ts:126` `encodeParams`）✓；值模式原样。
- `{output:槽}` / `{from.path}` / `{to.path}` → 命令模式**单引号包住**（`substitute.ts:59-67`）✓；值模式原样。
- `{role:*.*}` → **两种模式都原样**（`substitute.ts:69-74` 与 `:94-99`）✗ ← **这就是漏的那一条**。
- `{output:槽}` 在**值模式**下原样 → 而 `readback.path` 会进 `cat -- '<path>'`（`runner.ts:602-607`，`quotePath`）✓；
  `readback.pattern` / `dir` / `exclude` → 进 `conn.list()`（不是 shell）✓。
→ 所以漏网的是**角色事实**，以及**判据命令这条通道本身**。

### Q4 · **跨目标的信任边界：「目标 A 的流程去读目标 B 的文件」权限怎么算？会不会变成跨机器读写的通道？**

**结论：会。而且现在算不出来——提案没有写「流程的作用域 = 哪个 profile 集合」。**

- **读**：判据能指名**任意 role**（`runner.ts:363-384` `crossRoleReadback`），
  `kind: file_equals` 会把文件**内容**读出来（`readback.ts:139-171`）→ 进 `stage.value` → 进卡片。
  判据命令**不过地板、不过确认**（C2）。
- **写**：`file.transfer` 的命令**在源机上跑**（`runner.ts:513-517`），目标由命令自己指定
  → 客机上的一条任意命令就能写板子，**不命中地板 → 不需要确认**（I3）。
- **作用域**：`roles` → `profile` 是宿主侧文件（`docs/30:67`）→ 流程的作用域 = **宿主 profile 表的全集**；
  而卡片**看不见**目标（`docs/30:40`）→ **用户在装卡时也看不见**（除非宿主解析包）→ 同意界面无从展示（I6 / C4）。
- **身份**：跨机通道**不校验主机身份**（`StrictHostKeyChecking=no`，两个黄金样本）→ 判据验的可能是一台假板子（I4）。
- 契约必须写死的四条：① 流程的 role 只能引用**本次运行被授权的连接集合**；
  ② 跨目标的**写**必须走**目标侧**的确认；③ 跨目标的判据**必须校验主机身份**；
  ④ 判据的**读**结果按「本卡可见的目标集合」过滤。

### Q5 · **确认与凭据：流程层的 `confirm_id` 绑什么？一次确认能不能被复用到另一个步骤 / 另一个流程？**

**结论：流程层**没有** `confirm_id` 的规格（提案全文 0 命中「confirm_id」，与 31-C4 同源）。
按现有实现推下去会变成：**

| 复用场景 | 能不能复用 | 证据 |
|---|---|---|
| 复用到**另一个步骤** | **不能** ✓ | 摘要含合成动作 id `exec:<step.id>` / `transfer:<step.id>`（`runner.ts:277`、`:519`；`authorization.ts:159`） |
| 复用到**另一个流程** | **不能** ✓ | 摘要含 `packId`（`runner.ts:760`；`authorization.ts:159`） |
| 复用到**同流程同步骤的另一组 inputs** | **能** ✗ | 摘要绑的是 `paramsDigest({})`——流程的 `exec`/`file.transfer` 步传的是**空参数**（`runner.ts:289-291`、`:529-532`），而**命令已经按 inputs 替换好了**（`runner.ts:271`）→ 摘要恒定，命令已变 |
| 重放同一张凭据 | **不能** ✓ | 一次性（`authorization.ts:187-188`） |

**这条正是 `spec/04:430-433` 明写要防的**：「人批准的是『把背光调到 30』，不是『把背光调到任意值』」。
流程层要绑的是 **inputs 的摘要 + 最终命令的摘要**，不是「参数摘要」这四个字（C3）。

**另外三条**（同源/相关，见对照表）：
- `action` 步**根本没传凭据**（`runner.ts:409-413`）→ destructive 的板型动作永远卡住（31-C4）；
- 流程层**没有确认通道的接线**（`scripts/run-workflow.ts:114-121` 不传 `confirmations` → `runner.ts:774-779` 落到桩）→ 只能问、不能被确认；
- 确认界面**没有参数可显示**（params = `{}`）→ 人确认的是一个他看不见的命令（违反 `spec/04:357-360`）。

### Q6 · **沙箱：卡片调 `cockpit.workflows.run` 之后，它能看到什么？时间线里有没有别的目标的信息？输出会不会把凭据/路径泄给卡片？**

**结论：有。提案没规定 stage 的字段可见性，实现的形状会把**别的机器**的路径、内容与目标身份泄给卡片；
而这条通道**不受 `permissions.read` 约束**。**

| 泄什么 | 从哪来 | 证据 |
|---|---|---|
| **目标身份**（role 名 → 推断出哪台是板子） | `stage.role` | `runner.ts:44`；提案自己说「卡片不知道目标」（`docs/30:40`） |
| **别的机器的绝对路径** | `stage.detail`（「在 X 里没找到 Y」）、`stage.value`（发现的绝对路径） | `runner.ts:455`、`:498` |
| **文件内容** | `readback` 形式 2 成功时 `value` = 内容 | `readback.ts:170` → `runner.ts:650` |
| **客机与板子的路径** | `outputs` 槽 | `runner.ts:64`（提案未提这个字段） |
| **凭据材料** | 公钥进 `outputs` 槽；**私钥路径**进 `detail` / 命令 / `dry_run` 回显 | `fixtures/workflows/prepare-credentials.authorize-key.yaml:45`、`:55`；`runner.ts:301-303`；`format.ts:193`（M3） |

**沙箱管不了这些**：`spec/03:135`「沙箱只保证卡片**搞不垮工作台**，不保证卡片**不会乱动板子**」——
这里更严重：不是乱动，是**读**。而 `permissions.read` 只过滤 tag（`spec/03:579` 是唯一一处显式过滤的先例），
流程返回**没有任何过滤**。契约必须逐字段规定（I6 的建议 1–4）。

| 2 | **判据里的命令 = 命令**：与写步骤受同一套闸门（编码 → 地板 → 确认 → 审计）；判据命令必须只读；判据的 role 只能在已授权的 role 里选 | C2 |
| 3 | **流程层的确认绑定**：`(流程包 id, 步骤 id, inputs 摘要, 最终命令摘要, 契约版本)`，一次性、5 分钟、界面显示最终命令 | C3 |
| 4 | **卡片对流程的授权是独立的一类**：申请 ∩ 人授过 ∩ 已启用 ∩ 本卡可见目标；装卡同意界面必须显示「哪些目标上跑哪些命令」 | C4 |
| 5 | **审计行必须有触发者 + 最终命令 + 输入值**；`actor` 与 `workflow/step` 分开记 | I1 |
| 6 | **角色事实也受约束**（白名单或编码）；**流程包校验器加地板规则**（对应板型包规则 16）与「占位不得自带引号」（规则 21） | I2 |
| 7 | **跨机写按「目标 + 源 + 路径」建模，不按「一条命令」建模**；跨机通道**必须校验主机身份**；**角色不许绑 `local`**（并在 Windows 上说明地板表不适用） | I3 / I4 / C1 |
| 8 | **流程返回逐字段规定可见性**：`role`/`detail`/`value`/`outputs` 默认不给卡片，给的话按「本卡可见目标集合」过滤 + 路径脱敏；`dry_run` 只对已授权流程回显命令 | I5 / I6 / M3 |
