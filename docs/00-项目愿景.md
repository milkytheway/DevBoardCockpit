## 〇、一句话定位

面向嵌入式 Linux 开发者和玩家的 Windows 桌面工作台：把板子的能力标准化成**语义位号**，
把可视化与操控标准化成**卡片**，把扩展标准化成 **MCP**——然后让一个不知疲倦的 AI 照着手册，
替你批量制造仪表和开关。

> 板子即数据源，GUI 即座舱——既是仪表盘（看状态），更是驾驶舱（改行为）。

## 一、产品的两重身份

1. **统一工作台**：终端、文件互传、状态监控、显示输出，一个 GUI 全搞定，
   替代 PuTTY + scp + htop + 采集软件的多窗口切换。
2. **AI 可扩展的能力宿主**：功能不写死。宿主机上的 AI 编程 agent（Claude Code / Codex）
   通过 MCP 读取 GUI 内部状态、直接编写卡片，改完热插拔即生效。

## 二、总体架构

```
┌──────────────────────────────────────────────────────────────┐
│ 应用层：终端卡 │ 监控卡 │ 控制卡 │ HDMI采集卡 │ 布局编辑器      │
├──────────────────────────────────────────────────────────────┤
│ 卡片系统：manifest 声明 · 即文件 · 热重载 · 沙箱 · promote     │
├──────────────────────────────────────────────────────────────┤
│ 能力层（两族）                                                │
│   观测源（板→GUI）：Metric / Video / File / Shell              │
│   控制面（GUI→板）：Action / Command（参数·分级·回读）         │
├──────────────────────────────────────────────────────────────┤
│ 语义 tag 契约（卡片 ↔ 板子之间的总线，稳定词汇表）             │
├──────────────────────────────────────────────────────────────┤
│ 连接层 HAL：统一 Connection 接口 + capabilities 能力协商       │
├─────────┬──────────┬──────────┬──────────────────────────────┤
│  串口    │   SSH    │   ADB    │        未来任意               │
└─────────┴──────────┴──────────┴──────────────────────────────┘
▲
├─ 板型 profile（YAML 数据包，每板一份：声明各 tag 怎么产生）
│  MCP 协议（读状态/写卡片）＋ 文件监听（热重载）
▼
┌──────────────────────────────────────────────────────────────┐
│ 宿主机 AI Agent：感知 → 写卡 → 热插拔 → 自测 → 迭代            │
└──────────────────────────────────────────────────────────────┘
```

两条对称的总线：**MCP 是「AI ↔ GUI」的契约，tag 契约是「卡片 ↔ 板子」的契约。各有一份手册，缺一不可。**

## 三、三层功能

### 第一层：统一连接与终端（基础盘）

- **连接管理**：串口 / ADB 接板子；SSH 接后台的 Ubuntu 虚拟机（SSH 也可直连板子）。
- **终端整合**：所有会话在一个 GUI 里多标签呈现。
- **数据互传**：Windows ↔ 板子（ADB）、Windows ↔ Ubuntu（SSH/SFTP）。
- 终端是红海，只做基础盘不恋战；但终端有特权——支持 **promote 全屏提升**
  （htop/vim/tmux 在小卡里没法用；契约上一切皆卡片，交互上允许独占）。

### 第二层：可插拔卡片系统（核心差异）

卡片 = 板子某块能力的「面板」，读写双向：

| 族 | 方向 | 例子 |
|---|---|---|
| 观测 | 板子 → GUI | CPU/温度曲线、摄像头流、日志、推理结果 |
| 控制 | GUI → 板子 | 采样率滑条、NPU 接入开关、管线启停、背光、GPIO |

- **卡片即文件**：一个目录 = `manifest.json`（含双向绑定 + 动作声明）+ 视图代码；
  放进去就生效，agent 最擅长编辑的就是文件。
- **热重载 + 拖拽布局**：react-grid-layout，布局可保存可分享。
- **控制闭环（技术命门）**：点击 → 写命令 → 回读状态 → UI 以回读为准。
  按钮显示板子的真实状态，不是你上次点的意图——这是「驾驶舱」和「遥控器」的区别。
- 典型场景：板子接摄像头和显示屏，视频在两者间流转；插一张「管线卡」，
  滑条改帧率、开关挂 NPU 进链路——原本几条终端命令的事，变成一键操作。

### 第三层：宿主机 AI Agent 协作（前卫所在）

GUI 实现 MCP server，agent 可用工具：

| 工具 | 用途 |
|---|---|
| `list_connections` / `list_data_sources` / `list_capabilities` | 感知现状（能力动态出现，不能靠静态文档） |
| `describe_source(id)` / `sample_source(id, n)` | 运行时自省 schema + 拿真实样本，不盲写 |
| `list_cards` / `get_card_sdk_docs` | 查已有卡片、查可查询的活文档 |
| `validate_card(path)` / `get_card_runtime_log` | 写完静态校验 + 运行时看报错——agent 自测的眼睛 |
| `execute_action(cardId, actionId, params, dry_run)` | 取代裸 `send_command`：只准触发已声明动作，带权限检查和 dry-run |
| `promote_card(id)` | 提卡到全屏 |

**协作回路**：你自然语言提需求 → agent 查数据源、读 SDK、写卡片文件 → GUI 监听目录热插拔 →
你看效果反馈 → agent 迭代。做一张卡从半天变一轮对话。

**闭环之美**：agent 写卡依赖的数据，正是 GUI 从板子取的——agent 借 GUI 之力感知板子，
再反过来增强 GUI。

## 四、横切设计原则

| 原则 | 内容 | 类比 |
|---|---|---|
| 连接层 HAL | 统一接口 + 能力协商，UI 自动降级 | HAL / 设备探测 |
| 板型 profile | 板型差异不下沉为核心代码，而是每板一份 YAML 数据包（几十行：tag 从哪读、命令怎么发）。支持新板 = 提交一个包，不是等发版；AI 读 YAML 即知这块板的一切 | 设备树 overlay |
| 语义 tag | 卡片订阅标准化位号（`cpu.usage`、`gpu.temp`），不关心具体板型。N 张卡 × M 种板 = N+M 个文件，不是 N×M | SCADA 位号 / sysfs |
| 板端三档 | Tier 0 零安装 / Tier 1 脚本 / Tier 2 守护进程推流 | — |
| 双层安全 | ① 代码沙箱：卡片跑 iframe + 白名单 API，坏卡搞不垮工作台；② 动作权限：只读/可逆写/破坏性写三档分级 + 安装时授权 + dry-run + 破坏性二次确认 + 审计日志 | — |

产品本质的另一重定位由此而来：**给嵌入式板子做的组态软件（SCADA/HMI）**，
只不过组态工程师是 AI——位号 = 数据源，画面元件 = 卡片，组态 = 布局。

## 五、技术栈

**Electron + React + TypeScript**：electron-vite、xterm.js + node-pty、serialport、ssh2、
react-grid-layout。

> 决定性理由：终端方案成熟（VS Code 同款）、三种连接全有金牌库、卡片即网页，
> 且是 AI 结对编程效果最好的栈——本项目的开发模式（AI 结对）和产品形态（AI 造卡片）
> 是同一个假设，栈必须选它。

> **2026-11-13 修订（O1 拍板，见 `docs/05` ADR-D27）**：
> **主体 UI 不引 Ant Design**，改用**自有的 design token 层**
> （`src/renderer/theme/tokens.css`）。理由三条：
>
> 1. **卡片即网页，而卡片不受控**——卡片是 agent 写的任意 HTML。
>    套一层 antd 的 chrome 只会让**两套视觉语言**并存（壳一套、卡片一套）。
> 2. 主体 UI 是**壳**（工具栏 / 标签页 / 终端 / 读数面板 / 文件树 / 卡片容器），
>    antd 的组件里真正用得上的是**文件树**与**动作确认弹窗**两个——
>    代价是一整套 CSS-in-JS 与**第二套主题机制**。
> 3. **token 层本来就是换皮的接口**：将来想换视觉，改 token 就行，
>    不必先拆掉 antd。
>
> `react-grid-layout`（拖拽布局）**仍要引**——那是 M5 的硬需求，
> 自己手写拖拽布局不划算。**ECharts 是给卡片用的**：卡片的网络被 CSP 禁了，
> 所以图表库要**由宿主提供给卡片**（`cockpit://` 协议）——属于 M5 的范围。

已知坑：node-pty 是原生模块，需针对 Electron ABI 重编译。对策：锁定 Electron 版本 +
electron-rebuild 固化进构建脚本；Go 侧车留作 B 计划，不现在做。

## 六、现状与重构方向

- **现状**：已有终端（ADB/串口接板子、SSH 接 Ubuntu），但为硬编码功能集合，
  无卡片系统、无 agent 协作。（→ 详见 `docs/01-旧工程现状.md`）
- **重构本质**：从「带终端的工具」变成「能力宿主」——一切能力（本地的、板端的、
  AI 生成的）走同一套注册 / 发现 / 渲染管线。

## 七、演进路线（双轨并行，防规格空转）

```
规格线 ──→ 定 tag 契约 + 一块真板的 profile（一板十几个 tag 起步，留版本号和自定义逃生门）
工程线 ──→ 第1步 串口终端跑通
          第2步 SSH 连 Ubuntu VM + 多标签
          第3步 SFTP 文件互传          ← 以上与契约零依赖，绝不返工
             ↓ 两线汇合
          第4步 卡片框架 + 第一张监控卡（按已定契约实现）
          第5步 第一张控制卡（读-改-写闭环 + 动作分级）
          第6步 MCP server + SDK 活文档
          第7步 HDMI 采集卡、多板管理、布局分享、录制回放
```

## 八、护城河

终端聚合是红海（MobaXterm / Termius / WindTerm）；
护城河 = **卡片系统 + 语义 tag 总线 + AI agent 协作**。
把「扩展这个软件的人」从人类插件开发者变成任何 AI agent——市面上没有这个定位的产品。
