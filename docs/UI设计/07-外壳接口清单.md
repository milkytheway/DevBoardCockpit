# 外壳接口清单 · 新外壳（DSH）必须遵守的接口

> **日期**：2026-11-14
> **起因**：用户拍板 —— **当前这版 UI 设计作废，外壳交给 DSH 重写**。
> **这份是什么**：把「**换了外壳之后不能坏的东西**」摊开——
> 不是审美约束，是**功能约束**：下面每一条接错，**卡片就跑不起来**，
> 而症状是「卡片区一片空白」，**不报任何错**。

---

## 一、机制与外观的分界

| 层 | 归谁 | 说明 |
|---|---|---|
| `src/main/cards/*`（manifest / validate / permissions / registry / protocol / session / tags-service / storage / runtime-log / layout / watcher） | **不动** | 卡片宿主（main 侧）：发现、校验、权限、沙箱、存储、日志、布局 |
| `src/main/cards/bridge-script.ts` 生成的 **bridge 脚本**（卡片里的 `window.cockpit`） | **不动** | 契约 `spec/03` §7.7 的 API 全集 |
| `src/shared/ipc-contract.ts` + preload 的 **`window.cockpit.*`** | **不动** | 跨进程接口（main ↔ 页面） |
| **token 三层**（种子 → 映射 → 别名） | **机制不动；种子（调色板）可换** | 换皮的正确姿势：**只改 `src/shared/theme/seed.ts` 的值** → `npm run gen:theme` → 卡片与外壳一起变 |
| 契约里的 **15 个 `--cockpit-*` 别名**（`spec/03` §6.3） | **不动** | **卡片靠它们活着**（卡片自己的 CSS 只能用这些变量） |
| `src/renderer/**` 的 React 组件与 CSS | **DSH 重写** | 外观层 |

> **一句话**：**main 侧与 bridge 是机制，renderer 是外观。**
> 新外壳换掉的是外观；只要按下面的接口接上，机制原封不动。

## 二、新外壳必须做的九件事

> 每一条后面都写了「不这么做会怎样」——**那都是真会发生的**。

### ① 取装着的卡片

```js
const cards = await window.cockpit.cardsList();
// CardInstanceInfo { instanceId, cardId, url, connectionId, degraded }
```
不取 → 卡片区永远空。

### ② 每张卡渲染一个 iframe，**属性不能改**

```jsx
<iframe
  src={info.url}                       // cockpit://card/<实例 id>/<entry>
  sandbox="allow-scripts"              // ← 只这一个！不加 allow-same-origin
/>
```

| 改错的后果 | 症状 |
|---|---|
| 加了 `allow-same-origin` | **所有卡共享 `cockpit://card` 一个源** → **A 卡能读 B 卡的存储**（实测，ADR-D28） |
| 改了 `src` 的形状 | bridge 注入的脚本取不到实例 id → **404** → `window.cockpit` 恒 undefined |

### ③ 握手（**认人要认两次**）

```
卡片 → parent.postMessage({ type:'cockpit-hello', instanceId }, '*')
外壳 → ① event.source 必须是**登记过的那个 iframe**
     ② instanceId 要与那个 iframe 对得上
     → 建 MessageChannel
     → frame.contentWindow.postMessage({ type:'cockpit-port' }, '*', [port2])
     → window.cockpit.cardsHello(instanceId)
```

**只比 source 不够**：卡片 A 把自己导航到卡片 B 的 URL，就能借到 A 的权限（RF-1）。
**不比 instanceId 也不够**：那是 bridge 认人的凭据。

### ④ 卡片的请求走那条**私有端口**

拿到 `{type:'cockpit-port'}` 之后，卡片的所有请求都在那条 **MessagePort** 上往返
（`{ id, method, args }` → `{ id, ok, value }`）。

**不要用 `parent.postMessage` 走请求**——共用父窗口的话，**每张卡的请求都经过同一个窗口**，
卡与卡之间就有了公共面。

### ⑤ main 的推送也走那条端口

```js
const off = window.cockpit.onCardEvent((instanceId, payload) => { /* 推给那张卡的端口 */ });
```

### ⑥ 热插拔：卡片变了要重新取清单

```js
const off = window.cockpit.onCardsChanged(() => refresh());
```
不订 → **新放进卡片目录的卡永远不出现**（「卡片即文件」的核心动作）。

### ⑦ 布局：拖完存回去

```js
const layout = await window.cockpit.layoutGet();   // 宿主算好的格子（含 manifest 的默认尺寸）
await window.cockpit.layoutSet({ units, updatedAt: Date.now() });
```

### ⑧ CSP 违规：卡片自己报上来

卡片里的 `__host/csp.js`（宿主注入的）会 `parent.postMessage({ type:'cockpit-csp', instanceId, detail })`。
外壳**认人两次**后转给 main：

```js
window.cockpit.cardsCsp(instanceId, detail);
```

不转 → 契约 §6.1 承诺的「agent 能看到这张卡试图联网」**兑现不了**。

### ⑨ 样式只用 `--cockpit-*`

- 契约的 **15 个别名**（`spec/03` §6.3）：`--cockpit-bg` `--cockpit-text` `--cockpit-border`
  `--cockpit-radius` `--cockpit-font-mono` `--cockpit-font-ui` …（完整清单见契约）
- 状态类：`cockpit-value` / `cockpit-unavailable` / `cockpit-pending` / `cockpit-degraded` / `cockpit-broken`

**不硬编码颜色** → 换肤就是换种子（`src/shared/theme/seed.ts`），
卡片与外壳**一起**变；硬编码了就换不动。

## 三、新外壳**不能**做的事

| 不能 | 为什么 |
|---|---|
| 给卡片 iframe 加 `allow-same-origin` | 卡之间会共享源 → A 卡能读 B 卡的存储 |
| 用 `parent.postMessage` 走卡片请求 | 卡之间会有公共面 |
| 在 renderer 判权限 | 过滤**只在 main**（`tags-service.ts`）；renderer 判就等于把安全边界放在不可信侧 |
| 改卡片实例 URL 的形状（`cockpit://card/<实例 id>/…`） | 实例 id 是 bridge 认人的凭据 |
| 给卡片 iframe 加同源脚本（`allow-scripts` 之外的能力） | 沙箱就是隔离的边界 |

## 四、e2e 的**稳定钩子**（换皮也不会断）

10 条 e2e 是 M5 的验收主体。新外壳写完，**跑一遍就知道有没有接错**。

| 钩子 | 用在哪 | 说明 |
|---|---|---|
| `[data-cockpit-drag-handle="true"]` + `data-card-id="<cardId>"` | 布局那条（拖拽） | **不靠 class 名**——外壳换皮、class 改名，判据都不该断 |
| 卡片帧的 **URL 前缀 `cockpit://card/`** | 隔离那几条 | e2e 用 `cardsList()` 拿 instanceId → 按 URL 精确匹配帧（**不靠 DOM 结构**） |
| `window.cockpit.cardsList()` | 所有 | 唯一的「卡片在不在」判据 |

> 换句话说：**e2e 不认识任何 class 名**——新外壳的 DOM 可以完全不同，
> 只要①–⑨ 接上了，10 条就该全绿。

## 五、10 条 e2e 是什么

| # | 判据 |
|---|---|
| 1 | 应用起得来，preload 装上了宿主能力 |
| 2 | 卡片碰不到宿主 DOM（`SecurityError`） |
| 3 | 卡片连不上网（fetch 被 CSP 挡） |
| 4 | 卡片读不到没权限的 tag（**且看不出存不存在**） |
| 5 | 卡片抛异常不影响宿主 |
| 6 | 卡片用不了浏览器的存储（不透明源 → `SecurityError`） |
| 7 | **内置的第一张卡自动出现**（不用手动复制） |
| 8 | **卡片碰不到别的卡**（A 卡读不到 B 卡的存储） |
| 9 | **改文件即热更新**（改 `card.js` → 卡片重载 → 新行为生效） |
| 10 | **拖动一张卡 → 关掉应用 → 再开 → 位置还在** |

```powershell
npm run test:cards        # 10 条（内部会先 build）
```

## 六、换肤的正确姿势（不是重写）

**视觉要换，但别去改机制**：

1. 改 `src/shared/theme/seed.ts` 的**值**（调色板、圆角、字体）
2. `npm run gen:theme` → 生成 `src/renderer/theme/tokens.generated.css`
3. `npm run gen:theme:check` → 守着它与种子一致
4. 外壳的组件**只消费** `--cockpit-*`（不要硬编码）

> **为什么值得这么做**：token 三层（种子 → 映射 → 别名）就是为「换皮不返工」造的——
> 种子是**唯一**要改的地方，映射与别名是机制。改种子 = 换肤；
> 改别名 = **动契约**（`spec/03` §6.3 的 15 个别名是**契约的一部分**）。
