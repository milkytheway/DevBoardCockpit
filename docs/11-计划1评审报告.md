## 二、P0 —— 核心功能不通（5 条）

### R-01 · ADB 交互终端按回车不执行命令 🟢 **真机实测**

**位置**：`src/main/hal/adb.ts:203-207`、`src/main/terminal/manager.ts:91-99`

```ts
// src/main/hal/adb.ts:203
  write(data: string): void {
    // pipe 模式：板子不回显，宿主负责回显
    this.child.stdin.write(data);
    this.record(data);
  }
```

**根因**：ADB 是 **pipe 模式**（事实 A1：`adb shell -t -t` 在 Windows 上会晚一条，所以不用 PTY）。
管道**没有行规程**，板端 busybox 只认 `'\n'`。而 xterm 的 `onData` 在回车键上发的是 **`'\r'`**。
`TerminalView.tsx` 的 `convertEol: false` 意味着宿主不做任何转换，
于是 `'\r'` 被原样塞进管道——**shell 永远等不到行尾**。

**🟢 真机实测（板子 `f34dca7784396ab2`，Buildroot/busybox）**：

```
sent: "sleep 2; echo DONE_MARKER\r"   （只发 CR，从不发 LF）
3.5 秒后输出 = ""                      ← 命令没被执行
补发 LF 后输出 = "DONE_MARKER\r\n"      ← 命令这才跑
```

另一组（两条命令都被 CR 结尾）：
```
sent: "echo AAA\recho BBB\r\n"
output: "AAA\r\necho BBB\r\n"   ← 「echo BBB」被当成 echo 的参数，没当第二条命令
```

**失败场景**：用户点「板子 · ADB」→ 打字，字符被宿主回显出来（**终端看着像在工作**）→
按回车，什么也不发生 → 输入越积越长。退格同样无效（`'\x7f'` 被当作普通字符送进远端）。

**这违反两处已写明的设计**：
- `docs/07-评审报告.md` P1-10 明写「管道模式下远端没有 readline，**行编辑必须由本地做**」；
- `docs/superpowers/plans/2026-11-12-plan1-真机验收清单.md` 步骤 2 明写「输入 `ls` → 列出的文件名应该是多列」
  ——**按现状这条验收必挂**。

前身工程为此专门写了 `ui/line_editor.py` + `keymap.py`，`docs/03-迁移对照表.md:32`
判为「xterm.js 自带」而丢弃——**那个判断是错的**，xterm.js 只带 PTY 流。

**注意别误改**：`src/main/hal/adb.ts:198` 的会话环境脚本写法**是对的**
（`this.child.stdin.write(\`${terminalEnvScript()}\r\n\`)`），实测 `export TERM=xterm-256color`
与 `ls()` 函数定义确实生效。末尾那个只有 CR 的空行被板端当空行忽略，不报错。

**修法方向**：管道模式下由宿主做行编辑（把 `'\r'` 译成 `'\n'`，补退格与行内编辑），
或者接受 `adb shell -t` 的「晚一条」代价——**但事实 A1 已否掉后者**。

**测试覆盖**：**无**。`tests/unit/adb.test.ts` 只测 `adbCapabilities`/`adbArgs`/`open()` 的状态过滤，
**完全没有 `AdbSession` 的写入路径测试**；`tests/unit/terminal-manager.test.ts` 的假连接
把 `write` 记进数组就断言通过，从不检查「回车必须变成换行」。

### R-02 · 串口 transcript 被截断后 marker 下标失效 → exec 永久超时且输出全丢 🟢 **代码复刻实测**

**位置**：`src/main/hal/serial.ts:158-162`、`206`、`254`、`274-278`

```ts
// serial.ts:158
    this.port.onData((chunk) => {
      this.transcript += chunk;
      this.trimTranscript();          // ← 截断会让绝对下标失效
      this.dataCb?.(chunk);
    });
// serial.ts:206
    const before = this.transcript.length;   // ← 绝对下标
// serial.ts:254
    const chunk = this.transcript.slice(from);   // ← 截断后 from 指向错的位置
// serial.ts:274
  private trimTranscript(): void {
    const MAX = 64 * 1024;
    if (this.transcript.length > MAX) { this.transcript = this.transcript.slice(this.transcript.length - MAX); }
  }
```

**根因**：`before` 是 transcript 的**绝对下标**，但 `trimTranscript()` 会把前面的内容切掉。
切掉之后 `slice(from)` 要么切错位置，要么切出空串。

**🟢 实测（在 `$env:TEMP` 用 JS 复刻 `serial.ts` 的认领逻辑）**：

```
场景 A：单条命令输出 100KB（大文件 / 大目录 ls）
  → { markerCount: 1, sliceLen: 65536, wouldTimeout: true }
     （需要 2 个 marker：板子回显一次 + echo 一次。第一个被截掉了）

场景 B：交互终端先产生 70KB 流量（transcript 已贴在 64KB 上限）
  → { markerCount: 0, sliceLen: 0, wouldTimeout: true }
     （before = 65536，数据一到就再次截断，slice(65536) 恒为 ''）
```

**失败场景（两条）**：
1. 单条命令输出 > 64 KB（`cat` 大文件、`ls -la` 大目录）→ 板子**正确回包了**，
   但 30 秒后返回 `exitCode: 124 / timedOut: true / stdout: ""`。
2. 交互终端跑一段时间后 transcript 贴在上限 → **该连接上的 exec 通道永久死亡**，
   每条命令都挂满 30 秒、返回空输出。

**修法方向**：不要用绝对下标认领 marker。改成「记住 marker 字符串、在 transcript 里找最后一次出现」，
或截断时同步修正 `before`，或把 transcript 改成环形缓冲并保留「上次 marker 位置」。

**测试覆盖**：**无**。`tests/unit/serial.test.ts` 的假板子只回几十字节，
`tests/unit/serial-real-factory.test.ts` 只测端口是否真开。**没有任何用例跨越 64 KB 窗口**。

### R-03 · 错误对象跨 IPC 边界退化 → 用户看到 `[object Object]` 🟢 **源码比对实测**

**位置**：`src/shared/errors.ts:28-39`、`src/main/index.ts:64`、`79-85`、`src/renderer/App.tsx:76`

```ts
// src/shared/errors.ts:33
  return {
    code,
    message,
    retryable: extra?.retryable ?? false,
    ...(extra?.detail !== undefined ? { detail: extra.detail } : {}),
  };
```

**根因**：`makeError` 返回**普通对象**，不是 `Error` 实例。而 Electron v34.5.8 的
`lib/renderer/api/ipc-renderer.ts` 里：

```ts
  async invoke (channel: string, ...args: any[]) {
    const { error, result } = await ipc.invoke(internal, channel, args);
    if (error) {
      throw new Error(`Error invoking remote method '${channel}': ${error}`);
    }
    return result;
  }
```

**🟢 实测**：

```
instanceof Error : false
String(err)      : [object Object]
Electron 包出来的字符串： Error invoking remote method 'terminal:open': [object Object]
```

**失败场景**：
- **用户**：串口被占用时，界面上显示的是
  `Error invoking remote method 'terminal:open': [object Object]`
  ——「串口 COM3 被占用」这句话**永远到不了用户眼前**。
- **主进程日志**：`guard()` 里 `err instanceof Error ? err.message : String(err)`
  → 日志里只剩 `[terminalWrite] [object Object]`，
  `PORT_BUSY` / `TERM_NOT_FOUND` / `CONN_CLOSED` **全都变成同一串**。
- **错误码到不了 UI**：`AppError.code` 在 IPC 边界全丢，renderer 侧没有任何按 `code` 分支的代码路径。

**这违反三处已写明的设计**：
- `docs/04-架构设计.md` §11.1「统一错误对象」（`code` + `message` + `retryable`）；
- §11.2 降级矩阵「串口被占用 → 报错并**指出是哪个端口**」；
- 计划 RF-5：「报『端口被占用』并**指出是哪个端口**」。

**修法方向**：`makeError` 返回 `Error` 实例（把 `code`/`retryable`/`detail` 挂在实例上），
这样 `guard()` 与 renderer 两处都能拿到 `message` 与 `code`。

**测试覆盖**：**无，且现有测试恰好掩盖了它**。`tests/web/app-error.test.tsx` 里宿主抛的是
`new Error('串口 COM3 被占用')`（**真 Error**），所以测试绿——**而真实代码路径抛的不是 Error**。
这正是 `docs/09` §六 说的「测试替身建模了结论而不是行为」。

### R-04 · 上传传的是 basename 而不是路径 → 传错文件或直接失败 🟢 **实测**

**位置**：`src/renderer/App.tsx:143-145`

```tsx
onPush={(file, remoteDir) => {
  // 上传：本地文件 → 远端目录。真实传输由宿主的 files:push 做。
  void apiRef.current?.filesPush(current.profileId, file.name, remoteDir);
}},
```

**根因**：`filesPush(connectionId, localPath, remotePath)`（`src/shared/ipc-contract.ts:35`）
要的是**本地路径**，但 renderer 传的是 `file.name`——一个不带目录的 basename。
宿主于是跑 `adb push build.log /`（`src/main/hal/adb.ts:129`），
`build.log` 相对 **adb 进程的 CWD** 解析，不是用户选的目录。

**🟢 实测（板子在线）**：

```
真实文件在: C:\Users\ADMINI~1\AppData\Local\Temp\build.log
renderer 传的 localPath = 'build.log'（无目录）
→ adb push build.log /tmp/  →  "build.log: 1 file pushed"
```

也就是说：**它传成功了，但传的是另一个文件**（恰好在 CWD 里的那个）。
在真实场景里，用户选 `D:\logs\build.log`，宿主传 `build.log` →
要么 `adb push` 报「找不到文件」，要么**静默传走 CWD 里同名的一个**——
后者是数据安全问题。

**叠加因素**：`File.path` 在 **Electron 32 已被移除**（本仓库用 34.5.8），
受支持的 API 是 `webUtils.getPathForFile(file)`，需要经 preload 暴露——
`src/preload/index.ts` 没有暴露任何此类方法。

**测试覆盖**：**无**。`tests/web/file-browser.test.tsx` 只断言 `onPush` 收到了 `File` 对象，
**从不断言跨 IPC 边界实际传了什么**，所以生产坏了测试照样绿。

## 三、P1 —— 正常用法下会出错的路径（14 条）

### R-06 · 切标签销毁 xterm 实例：历史丢失 + 后台标签输出被丢弃 🟡 推断

**位置**：`src/renderer/terminal/TerminalView.tsx:106`、`src/renderer/App.tsx:132-140`

`TerminalView` 主 effect 的依赖是 `[sessionId]`，清理函数调 `term.dispose()`（`:102`）。
而 `App.tsx:132` 渲染 `<TerminalView>` **没有 `key`** → React 按位置复用组件实例 →
切标签时 `sessionId` 变 → effect 重跑 → 旧 `Terminal` 被 dispose，新建一个。
`scrollback: 2000`（`:65`）随旧实例一起消失。

**两重损失**：
1. **回滚历史没了**——切走再切回来，终端是空白的。
2. **后台标签期间产生的输出没了**——只有活动标签的 `TerminalView` 挂着，
   只有它订阅 `IPC.terminalData`；后台会话的 chunk 被广播给一个**没有监听者**的 renderer → 丢弃。

**用户可见**：多标签终端是这产品的招牌功能，它**静默丢历史、丢输出**。
会话日志里还在（`manager.ts:80` 记了），事后能捞，但界面上捞不回来。

**修法方向**：给 `<TerminalView key={current.sessionId}>`，
并把 xterm 实例按 sessionId 缓存，让后台输出进缓冲区而不是进虚空。

**测试覆盖**：**无**。`tests/web/terminal-view.test.tsx` 只挂载单个 `TerminalView`，从不切 `sessionId`。

### R-07 · 串口的 `busy` 只挡 exec↔exec，交互会话与 exec 共用一根线且互不知情 🟡 推断

**位置**：`src/main/hal/serial.ts:123`、`186-191`、`242-247`

```ts
// serial.ts:123
  private busy = false;
// serial.ts:186
    if (this.busy) {
      throw makeError('CONN_TIMEOUT', '这条连接上还有命令在跑', { detail: { id: this.id, command } });
    }
// serial.ts:242
  async openSession(_opts?): Promise<Session> {
    return new SerialSession(this.port, this.log);   // ← 与 exec 共用同一个 port、同一条 transcript
  }
```

**失败场景**：用户开着串口终端，正输入到一半（`ls -l /tm`，没回车）；
此时任何动作发起一次 `exec`（`execLocked` 会 `this.port.write(\`${command}; echo ${marker}\r\n\`)`）
→ **这条命令被追加在用户未完成的输入后面**，板端 shell 拿到的是
`ls -l /tmpuptime; echo __DBC...__`。反向污染同样成立：
交互会话的输出进的是同一份 transcript，会插进 exec 认领 marker 的区间里。

**违反**：`docs/spec/02-board-pack.md` §1.2.1 明写「**同一个连接上，同时只能有一次往返**……
poll group 的采样与动作都进同一个队列」；事实 S1 明写「命令通道和交互终端**共用一根线**」。

**修法方向**：把互斥从 `busy` 布尔升级成**每连接一条往返队列**；
至少要禁止「会话开着时 exec」。

### R-08 · SSH `exec` 超时调 `client.end()`，把整条连接拆掉，而连接仍被当成「已打开」 🟡 推断

**位置**：`src/main/hal/ssh.ts:127-130`、`110-113`

```ts

        timedOut = true;
        this.client?.end();          // ← 结束的是 client，不是那一条 exec 通道
      }, timeoutMs);
```

**失败场景**：
- 用户开着「Ubuntu · SSH」终端，同时某次 `exec` 超时 → `client.end()` →
  ssh2 把该 client 上**所有通道**一起关掉 → **用户正在用的交互终端当场断掉**。
- 超时路径**不置空** `this.client` → 连接已死，`this.client` 仍非空 →
  后续 `exec`/`openSession` 继续往死连接上打；UI 侧 `connectionsList` 仍把它列为可用。
- 超时**没有独立的结算路径**：timer 只做了 `end()`，Promise 只能靠 `stream.on('close')` 结算；
  若远端不主动关通道（`end()` 只是半关闭），这个 Promise 永不 settle → 调用方永久挂起。

**修法方向**：超时只关**那一条 channel**（`stream.close()`），不要 `client.end()`；
并给 Promise 一条独立的超时结算路径。

**测试覆盖**：**无**。`tests/unit/ssh.test.ts` 只测 `sshCapabilities`/`sshArgs`/`openSession`，
**根本没测 `exec`**，更没有超时路径。

## 十、给下一轮计划的三条硬约束

> 这三条是从上面 57 条里**提炼**出来的，不是新规矩。

1. **假设备必须按真实行为建模，不能按契约编答案。**
   `docs/09` §六 已经写过一次教训（假串口盖住了 C2），
   但 R-01/R-04/R-05/R-12 **同型复发**——假板子不回显行规程、假文件只断言「收到了 File 对象」、
   假样本里没有符号链接。**建真行为 fixture 的活要当成产品活干，不是测试的附属品。**

2. **「验收判据」要写成人能复核的断言，不能写「✅ 全满足」。**
   M2 的判据原文是「双树浏览 + 双向传输」——**一句话，两个可测的能力**；
   而复核给的是「✅」。判据与复核**必须一一对应**，否则复核就是背书。

3. **每加一条契约，都要同时想清楚「它怎么坏」。
   `docs/04 §12.1`（8 类攻击面）与 §12.2（16 种失败注入）写得很好，
   但**一行都没进过测试**。这不是「以后补」——**危险地板现在有零道防线**（R-49），
   而地板是这产品唯一的「不许对板子做坏事」的机制。
