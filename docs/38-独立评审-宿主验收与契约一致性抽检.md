## 三 · 契约↔实现一致性抽检

### 3.0 为什么做这件事

这一轮的评审史是：**提案 v1 → 评（需重做）→ v2 → 评（有条件通过）→ v3 → 评（有条件通过）→ 晋升契约**。
**三轮评的都是提案文本**，没有一轮问过「实现照着冻结后的契约做对了吗」。

而契约晋升恰恰是**方言切换**的那一刻：
流程包从「宿主层数据格式」（`docs/29`）变成「契约格式」（`spec/05`），
**版本词汇、字段表、类型表都换了说法**——最容易漏的就是这里。

### 3.1 抽样一致的 6 处 ✅（带证据）

| # | 契约怎么说 | 实现怎么做 | 判定 |
|---|---|---|---|
| 1 | 判据**形式 1（tag）首版报错**（D34-6） | `format.ts:536` 直接 fail | ✅ |
| 2 | 占位符**封闭五种**（§六「它就是注入防线」） | `substitute.ts` 只认 `input:` / `output:` / `role:` 三类前缀，替换后过编码 | ✅ |
| 3 | 长任务 = `run_id` + 轮询；`run_id` 不可预测（D34-8） | `service.ts:160-164` `randomUUID` | ✅ |
| 4 | 信任模型**三层**（manifest 声明 ∩ 卡级授权 ∩ 包被批准） | `service.ts:108` + `registry.requireApproved` + 守卫 M114/M116 | ✅ |
| 5 | 六种 kind（§4.1） | `format.ts:50-58` 六个 | ✅ |
| 6 | `roles` = `purpose` + `profile`（§三） | `format.ts:169` `ROLE_KEYS` 两个 | ✅ |

### 3.2 C1 · 版本词汇：契约写 `apiVersion`，实现与三份黄金样本仍是 `formatVersion` 🟢

**位置**：契约 `docs/spec/05-workflow-pack.md` §一（顶层字段）；
实现 `src/main/workflows/format.ts:130`、`:143-155`、`:298`；
样本 `fixtures/workflows/{hello-kernel,meminfo-user}.build-run.yaml`、`prepare-credentials.authorize-key.yaml`。

**契约说**（§一）：

```yaml
apiVersion: devboard/v1
kind: Workflow
```

**实现说**（`format.ts:130`）：

```ts
/** 宿主层格式版本（**不是契约的 `apiVersion`**——免得混淆） */
formatVersion: 1;
```

`TOP_KEYS` 的封闭字段表里**只有 `formatVersion`**，没有 `apiVersion`；
而 `checkKeys`（`:217-221`）对**未知字段一律报错**。

**为什么这是 Critical**：

1. 🟢 **一份完全符合契约的包，会被实现拒掉**，报错是「未知字段 `'apiVersion'`」——
   契约自己的示例（§一那段 YAML）就是非法输入。
2. 🟢 **三份黄金样本全部用旧字段** → 样本与契约不一致，而样本是流程层的「合法输入基准」。
   按 ADR-D31 R1 与 D34-1 的口径，**黄金样本是晋升契约的依据**；现在依据本身不合契约。
3. 🟢 **这个决定早就写下了**：`docs/05` ADR-D34-1「版本词汇**统一成 `apiVersion: devboard/v1`**」；
   `docs/33` A9 也点名过「`formatVersion` 与 `apiVersion` 两套版本词汇」。
   → **决策落了，实现与样本没跟上。** 这不是设计分歧，是**执行漏项**。
4. 🟡 影响面：若将来 agent 按 `spec/05` 写流程包（它读的是契约，不是实现），
   写出来的东西**宿主跑不了**——这正是「AI 造卡/造流程」这条主线的第一次实战失败。

**怎么改**（建议，两选一，但要**选一个**并同步四处）：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 实现与三份样本改用 `apiVersion: devboard/v1`；`formatVersion` 若是历史包袱就删掉 | 实现与样本各改 4 行；`formatVersion` 的旧样本（若有）需迁移 |
| B | 契约改回 `formatVersion`（并改 ADR-D34-1） | 契约与板型包/卡片 manifest 不一致（那两个用 `apiVersion`）→ **我不建议** |

**机械判据**：把 `spec/05` §一 那段 YAML 原样喂给 `format.ts` 的校验器，**必须不报错**。
现在它一定红。

### 3.3 I1 · `inputs` 的 `default` / `pattern`：契约允许，实现的封闭表里没有 🟢

**位置**：契约 `spec/05` §二；实现 `src/main/workflows/format.ts:170`（`INPUT_KEYS`）；
依据 `docs/spec/02-board-pack.md` §4.3（契约说「照它」）。

| | `default` | `pattern` |
|---|---|---|
| `spec/02` §4.3（参数的封闭类型表） | ✅ 有（integer / number / string 可选） | ✅ 有（string 可选，正则） |
| `spec/05` §二（「类型表照 02 §4.3」） | ✅ 有（「其余字段：required · default · pattern · description」） | ✅ 有 |
| **实现 `INPUT_KEYS`** | ❌ **没有** | ❌ **没有**（实现里的 `pattern` 只在 **step** 层，用于 `discover`） |

**为什么这是 Important**：

1. 🟢 **按契约写的包会被拒**（封闭表 → 未知字段报错）。契约说「照 02 §4.3」，
   而 02 §4.3 明确有这两个字段 → **契约转述准确，是实现少了两项**。
2. 🟡 `default` 的实际价值不小：流程包可以被宿主**预填**常用输入（例如默认工程目录），
   卡片点一下就能跑；没有 `default`，每个调用方都得自己填全。
3. 🟡 `pattern` 是**注入防线的第二道**（`maxLength` 挡长度、`pattern` 挡形状）。
   契约许诺了，实现没给 → 契约与实现的**安全能力**不一致，这比字段缺失更值得记一笔。

**怎么改**：把 `default` / `pattern` 加进 `INPUT_KEYS`，并按 `spec/02` §4.3 的规则实现校验
（`pattern` 是正则 → 非法正则要报错；`default` 必须过该类型的取值检查）。
**机械判据**：一个带 `default:` 的 input 喂进校验器，必须不报错且能取到默认值。

## 四 · 下一步方向建议（排序 + 验收判据）

- **2 在 3 之前**：否则「点一下编译」按了停不下来、中断把板子搞脏。
- **4 可并行**：与 1–3 无依赖。

## 五 · D7 的拍板建议（一页，可直接评审）

### 5.1 问题

用户原话（2026-11-14）：「**用户可以选择本机或者客机上的代码**，选择后可点击编译，然后上传编译产物到板子上的选定位置，并可以点击加载运行。」

ADR-D34-2 已定：「**『目标』不是契约的概念**」→「本机编译」与「客机编译」是**两个流程包** →
「用户可以选择本机还是客机」在契约层**没有位置** → **用户还要再等一期**（代价已知 ✓）。

### 5.2 我的建议：**两个流程包 + 宿主路径选择器（契约零改动）**

| 环节 | 做法 | 为什么不选另一种 |
|---|---|---|
| **选本机 / 客机** | 两个流程包（`build-local` / `build-ubuntu-ssh`），卡片给**两个入口** | 不做「一个包两个目标」：**net 与 adb 是结构不同的两条支路**——步骤数、依赖、失败点都不同（第三份评审 C6-7 ✓）。硬塞进一个包就要分支语法 → 会长出表达式语言（`spec/02` §2.2 的前车之鉴） |
| **选代码位置** | **宿主提供路径选择器**（复用现成的文件浏览 UI），选完把路径填进 `inputs` | 不给卡片加文件 API：契约零改动 ✓、卡片沙箱**零开口** ✓、路径由宿主注入（与 `spec/03` §7.8「目标由宿主注入」一致，只是注入时机由卡片经 input 指定） |
| **看中间结果** | 订阅流程时间线（`run_id` + 轮询已定） | 无需新通道 |

### 5.3 顺带解决的一件事

> 🟢 **卡片侧现在没有文件/目标浏览能力**（`spec/03`、`spec/05` 里 `cockpit.files` / `cockpit.targets` **零命中**）——
> 我在 `docs/24` §六 的缺口清单第 10 项就写过它，至今未做。
> **路径选择器这条路把它绕开了**：卡片不需要看目录，只需要**把选择结果交给宿主**。
> 🔵 需确认：现成的文件浏览（`src/renderer/files/FileBrowser.tsx`）能否**选目录**（而不只是选文件）——
> 这一条我没验。

### 5.4 代价（诚实说）

- 卡片侧要多一个「本机 / 客机」的选择控件 + 一个「选路径」按钮（宿主弹窗）。
- 「同一件事在两台机器上」= 两个包，**改一处要改两处**（但它们共用同一套 kind 与样本结构）。
- **D7 仍然不进契约**（目标不是契约概念这条不变）。

## 六 · 我的建议与不建议

**建议**：
1. 第 0 步（修 C1/I1）**今天就做**——它是"契约说了、代码没做"的欠账。
2. D7 按 §五 拍板：**两个流程包 + 宿主路径选择器**，契约零改动。
3. 计划 7 之前补可中断原语（否则"点一下编译"停不下来）。

**不建议**：
