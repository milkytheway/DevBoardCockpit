> **作者**：Claude，2026-11-15。

> 客机 VMware Ubuntu `alientek@192.168.136.131`（aarch64 交叉工具链 + 内核源码树）。
> **脚本**：一次性脚本，**写 `$TEMP` 不进仓库**（计划 5 的 A14）。仓库只留**这份发现**。

## 〇 · 一句话结论

> **流程跑通了**（两个项目都通了，`modprobe` 按名字加载成功，`lsmod` 里能看到模块）。
>
> **但它同时暴露了三件设计必须回答的事**：
> ① **传输耗时波动 20 倍**（同一份文件、同一路径：3.8s / 75.6s / >110s）→ 传输步骤**必须有进度、必须可中断**；
> ② **取消只能「下一步边界生效」** → 对一个一两分钟的传输来说**那不叫取消** → M6 要**可中断的执行原语**；
> ③ **中断的传输会在板子上留下垃圾**（`.b64` 文件）→ 流程层要管**清理**。
>
> 另外两条**事实修正**（`docs/02` 的旧记载已过时）：**板子现在有 IP `192.168.5.100`，
> 客机能直连它**（ping 通、22 端口可达）→ 「客机↔板子两边不通」那条**不再成立**。

## 一 · 跑通的两条流程

### 1.1 `01-hello`（内核模块 → `extra/` → `modprobe`）

```
sync（宿主 → 客机，源码）           221ms  rc=0
compile（客机 make，超时 1800s）     727ms  rc=0   ← aarch64 交叉编译
discover（产物发现）                13ms  rc=0   {"kos": ["hello.ko"], "bins": []}
fetch（客机 → 宿主）                15ms  rc=0   hello.ko(30832 字节)
deliver（宿主 → 板子）              162ms  rc=0   → /usr/lib/modules/6.1.141/extra/hello.ko
load（depmod -a）                   34ms  rc=0
run（modprobe hello）               15ms  rc=0   ← **不是 insmod**
observe（8 秒）                    8029ms  rc=0
```

**板上复核**（`lsmod` / `ls`）：

```
Module                  Size  Used by
hello                  16384  0          ← 模块已加载 ✓
-rw-rw-rw- 1 root root 30832 /usr/lib/modules/6.1.141/extra/hello.ko
```

### 1.2 `01-meminfo`（用户态程序 → `/usr/local/bin` → 运行）

```
sync                                213ms  rc=0
compile                             661ms  rc=0   （静态 + 动态两个产物）
discover                             12ms  rc=0   {"kos": [], "bins": ["meminfo_static", "meminfo_dynamic"]}
fetch                                78ms  rc=0   meminfo_static(909560) meminfo_dynamic(9240)
deliver（宿主 → 板子）            **3819ms**  rc=0   → /usr/local/bin/…（+ chmod +x）
load（depmod -a）                    21ms  rc=0
run（meminfo_static）                  7ms  rc=0   MemTotal = 8107744 KB (7917.7 MB)
```

**多产物分流是对的**：`.ko` → `extra/` + `depmod` + `modprobe`；
可执行 → `/usr/local/bin` + `chmod +x` + 直接运行（**硬规矩 6** ✓）。
→ **placement 不能只有一个语义名**——它要按产物种类分流（ADR-D31 R5 的三形态是对的，
但「按种类」这一维还没进设计）。

## 二 · 计划 5 问的五个问题，逐条回答

### Q1 · 每一步的真实耗时是多少？

| 步 | 01-hello | 01-meminfo | 备注 |
|---|---|---|---|
| sync（源码上客机） | 221ms | 213ms | 三个小文件 |
| **compile** | **727ms** | **661ms** | ⚠️ **增量编译**（内核树已构建过，只重编模块）。**冷编译是分钟级**——原设计的 1800s 超时就是给冷编译准备的 |
| discover | 13ms | 12ms | |
| fetch（客机→宿主） | 15ms | 78ms | sftp |
| **deliver（宿主→板子）** | **162ms**（30KB） | **3819ms / 75559ms / >110s**（909KB，同一份文件！） | ⚠️ **见 §三·F1** |
| depmod -a | 34ms | 21ms | 很快 |
| modprobe / 运行 | 15ms | 7ms | |

**「编译要几分钟」只在冷编译时成立**（实测的是增量）——**判据要按冷编译写**。

### Q2 · 取消能不能真停？

**不能（在飞的那一步不会被中断）。**

实测形态：SIGINT 置一个标志 → **当前步做完才停**。
在一个 75 秒的传输步上，这**不叫取消**。

> → **M6 的执行器必须有「可中断的执行原语」**（abort / 能杀掉在飞的子进程与传输），
> 不能只是「跑完这步再看标志」。
> 这条要写进计划 5 的 Task 4（执行器）——**它现在只写了「经队列执行」，没写「能中断」**。

### Q3 · 中途失败时板子处于什么状态？能不能重跑？

- **实测**：源码不存在 → **立刻停，板子一点没被碰** ✓（失败即停）。
- **由构造保证**（未单独实测）：步序是 `sync → compile → discover → fetch → deliver → load → run`，
  所以**编译失败时板子未被碰**；**deliver 成功但 load 失败**时，板子处于
  「**文件在、没生效**」——这正是 `spec/02` §5.6 说的「文件存在」与「文件生效」的区别。
  → 流程层的失败报告**必须说清「文件已到位但没生效」**，不能只说「失败」。
- **重跑**：由构造可重跑（步是无状态的），但**中断的传输会留垃圾**（见 F2）→ 重跑前要清理。

### Q4 · 产物发现的实际规则是什么？

- `.ko`（含 `.ko.xz`）：按扩展名 ✓。
- 可执行文件：**按 `-u+x` 权限位**，并**排除**工具链的副产物
  （`*.c` `*.h` `Makefile` `*.o` `*.mod*` `*.order` `*.symvers` `*.cmd`）。
- 真实样本：`01-hello` → 1 个 `.ko`；`01-meminfo` → 2 个可执行（静态 909KB + 动态 9KB）。
- → **「产物」不是「一个文件」**（`docs/24` 的 `produces: [hello.ko]` 是错的形态）；
  发现规则必须**按产物种类**给，且**要能表达「多个」**。

### Q5 · 落位：`modprobe` 按名字能找到吗？`depmod -a` 要多久？

- **`modprobe hello` 成功** ✓——`depmod -a` 之后，`lsmod` 里能看到 `hello  16384  0` ✓
  （**按名字加载确实比 `insmod /path/x.ko` 好**：路径变了不用改命令）。
- **`depmod -a` 只花 21–34ms** ✓（比想象快得多）。
- 可执行文件：**push 过去是 `-rw-rw-rw-`** → **必须 `chmod +x`**（硬规矩 6）✓
  ——实测 `chmod +x` 之后 `/usr/local/bin/meminfo_dynamic` 是 `-rwxrwxrwx` ✓ 且能运行 ✓。

## 三 · 三条设计必须回答的发现

### F1 · 传输耗时**波动 20 倍**（同一份文件、同一路径）

| 次 | 文件 | deliver 耗时 |
|---|---|---|
| 1 | `meminfo_static`（909560 字节） | **75559ms** |
| 2 | 同一份 | **3819ms** |
| 3 | 同一份 | **>110s**（我把它停了） |

原因（已定位到实现层）：手工 adb 客户端的推送是
**base64 分块 → 每块一条独立的 adb shell 命令 → 每块一条新连接**
（593 块 / 909KB）→ **每块的连接开销乘以块数**。
慢的那些次里，宿主上的 adb-over-TCP 通道状态不好（`netsh portproxy` 那条链路）。

> → **流程层的三条要求**：
> ① **传输步骤必须有进度**（字节数 / 总数 / 速率）——它可能是一两分钟；
> ② **传输耗时不归流程层决定**（归传输实现与通道状态）→ 流程层**不许假设它快**；
> ③ 顺带：**大产物（几 MB）走这条路是分钟级的** → 传输方式本身值得单独选型
> （真 `adb push` 的协议比 base64-over-shell 快得多）。

### F2 · 中断的传输会**在板子上留垃圾**

第三次（被我打断的）跑完，板子上留下：

```
-rw-rw-rw- 1 root root 1114112 /usr/local/bin/meminfo_static.b64
```

→ 推送是「base64 写文件 → 板子上 `base64 -d` 解码」，**中途断了，`.b64` 就留在那儿**。
（已手工清掉。）

> → 流程层**失败/取消时必须清理**（临时文件 + 半截产物）。
> 这与「文件存在 ≠ 文件生效」是同一族问题：**板子上不能留「看起来像结果」的残留**。

### F3 · 取消机制要的是「可中断」，不是「设标志」

见 Q2。→ 计划 5 的 Task 4（执行器）要补一条：**执行原语必须可中断**。

## 四 · 两条**事实修正**（`docs/02` 的旧记载已过时）

| 旧记载 | 实测（2026-11-15） | 证据 |
|---|---|---|
| 「板子 eth0 的 DHCP 失败（169.254.214.1），**无 IP 所以 SSH 不通**」 | **板子有 IP `192.168.5.100/24`** | `ip -4 addr show`（板子上） |
| H2：「客机是 VMware NAT，板子在宿主物理网段，**两边不通**；板子↔客机互传需要桥接」 | **客机能直连板子**：ping 通（2ms）、22 端口可达 | 客机上 `ping 192.168.5.100` ✓ |

> → **ADR-D31 的 R7（首版不做跨目标直传）结论不变，但理由要改**：
> 不是「网络不通」，是「**凭据模型缺**」——
> 直传要客机拿什么去连板子（客机的公钥进板子的 `/root/.ssh/authorized_keys`），
> 那是 **destructive 级的写**（R2③ 的确认流程要覆盖它）。
> → **「换传输只改绑定」在板子上依然不成立**（换的是「谁去搬」，不是 profile）——这条不变。

## 六 · 这轮没验的（诚实说）

| # | 没验 | 为什么 |
|---|---|---|
| 1 | **冷编译**（内核树没构建过） | 客机上的内核树已构建 → 实测到的是增量（727ms）。冷编译的耗时**没测** |
| 2 | **取消真的停**（在飞的那一步被打断） | 沙箱的 pid 命名空间让信号投递不可靠（`kill -INT` 打到了 pid 1）；且实现本身是「下一步边界生效」→ 结论由实现得出 |
| 3 | **客机→板子直传**（`scp`） | 网络已验证可达 ✓，但**没装凭据**（那是 destructive 级的写，见 F4/ADR-D31 R2③） |
| 4 | **串口上的同一流程** | 串口传不了文件（事实 S7）→ 这条流程在串口上**不存在**；串口只有 `modprobe`/`depmod` 那几步 |
