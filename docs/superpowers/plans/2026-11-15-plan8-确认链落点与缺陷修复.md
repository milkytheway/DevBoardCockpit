## 一 · Task 1 · CLI 的确认链能走通（C-1 ✓）

**问题**：`destructive` 的流程步今天**跑不完** ✓ —— `workflow:confirm` 脚本不存在 ✓ ·
`approveAndResume` 零调用者 ✓ · `ConfirmationStore` 纯内存 ✓。

**修法（选了最省且最合契约的一条）**：**CLI 在停住时原地问人** ✓
（按 Enter = 人点头 ✓ → **同进程**批准 ✓ → 续跑 ✓）。

**为什么这样就对**（对照契约 `spec/05` §7.6 ✓）：

| 契约要求 | 同进程交互怎么满足 |
|---|---|
| 同一个 `run_id` ✓ | 同进程 ✓ |
| 同一份时间线 ✓ | 同进程 ✓ |
| **从停住的那一步继续**（前面的步**不重跑** ✓） | 同进程直接续跑 ✓ |
| 凭据一次性 + 5 分钟 TTL ✓ | 内存 Map 天然满足 ✓ |

**反过来，「另一个进程批准」那条路需要什么**：`workflow:confirm` 跨进程 ✓ →
凭据要落盘 ✓ **且运行状态也要落盘** ✓（否则「同一份时间线」做不到 ✓）→ 大工程 ✓，
**而用户的需求并不需要它** ✓ → **不做** ✓，**并把这个理由写进台账** ✓。

| 步 | 做什么 | 判据（先看见它红 ✓） |
|---|---|---|
| 1.1 | CLI 停住时**交互式**点头 → 同进程批准 → **续跑**（前面的步**不重跑** ✓） | 集成测试：起一条带 `destructive` 步的流程 ✓ → 喂一个「按 Enter」✓ → 跑完 ✓ → 时间线里 destructive 步 `ok:true` ✓ 且**前面的步只跑了一次** ✓ |
| 1.2 | **订正措辞**：`docs/05` ADR-D34 的「`npm run workflow:confirm -- <runId> <confirmId>`」✓ → 改成「同进程交互 ✓」✓；`scripts/run-workflow.ts:194` 的提示 ✓ 同改 | 脚本实跑 ✓（提示里不再出现不存在的命令 ✓） |
