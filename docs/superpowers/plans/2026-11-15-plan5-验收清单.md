## 三、真机侧（**要板子**）

> 这一节是**本清单最实的部分**：写侧的第一条真实闭环。
> 沙箱的 adb → 板子通路可用（`192.168.136.1:5037`）。

### ① 真板上跑通一次动作，**回读值与板子真实状态一致**

```powershell
npm run dev
```

在一张卡上触发一个**带回读**的动作（`spec/02` §4.4 的形式 1 或 2），
然后**用另一条通路核对同一个量**（例如 `adb shell cat <file>`）。

**判据**：
- 卡上显示的值 == 板子上的真值（**不是「命令发出去了」**）；
- `actions.log` 里**恰好一行**审计（时间 / 动作 id / 参数 / 结果 / 回读值）；
- **回读不符时**，界面显示的是「未确认生效」而**不是**「已生效」。

### ② `destructive` 动作**必须**有人点确认

**判据**：
- 第一次调用 → 返回 `needs_confirmation`（**命令没执行**）；
- 拿 `confirm_id` 重试 → 执行；
- **同一个 `confirm_id` 再用一次** → **被拒**（一次性）；
- 换一个动作 id / 换一个参数 / 超过 5 分钟 → **被拒**（RF-3 的四个变体）。

### ③ 串口上 `command_ok` / `verify` **被拒**

**判据**：用**串口** profile 起运行时，调用一个依赖退出码的动作 →
返回 `unsupported_transport`，**不是**「永远不符」。

> **这条为什么要真机**：串口**没有退出码**（事实 S5）——
> 若不拒，界面会说「动作失败」，而实际**动作成功了**。
> 单测能验逻辑，**验不了「串口真的没有退出码」这件事**。

### ④（可选）真机上的**危险地板**

**判据**：一个模板无害、但**参数致命**的动作（例如参数里塞 `; reboot`）
→ 编码后命中地板 → **按 `destructive` 处理**（要人确认），**不是直接执行，也不是直接拒绝**。

## 四、判不了的（**诚实记下，不假装过了**）

| 事 | 为什么判不了 | 归谁 |
|---|---|---|
| **跨目标的验证**（「客机连得上板子吗」「产物真到板上了吗」） | **板型包的回读只验「目标自己」**——不是实现没做，是这一层**做不到** | 流程层（ADR-D32 D32-1/D32-2 / O24） |
| **执行原语可中断**（取消能杀掉在飞的传输） | 尖兵实测：取消只在**步骤边界**生效；HAL 的 abort 语义没做 | 流程层（ADR-D32 D32-4 / O25） |
| **中断的传输不留垃圾** | 同上（`.b64` 残留） | 流程层 |
| **「用户选本机/客机的代码 → 点编译 → 上板 → 跑 → 看中间结果」** | 契约里**没有「目标」这一维**（`spec/03` §7.8：目标由宿主注入） | **待裁决 D7**（`docs/17` §2.4.3） |
| **越权读的审计** | 「没权限」与「不存在」**刻意长得一样** → 审计会泄露存在性 | 另设机制（`docs/17` L12） |
