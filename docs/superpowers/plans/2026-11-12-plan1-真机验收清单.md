# Task 10 · 真机验收清单与验收记录

> **为什么这份清单单独存在**：实现跑在 Linux 沙箱里，而验收要连**真板子**——
> 沙箱里没有 adb、没有串口设备、没有你的 VMware 客机。
> 自动化测试（218 个用例）覆盖了纯逻辑与接线，但**证明不了线是通的**。
>
> **本文件既是清单，也是记录**：2026-11-13 的验收已经做过了，
> 每一步下面写着**实际结果**与**怎么验的**。

---

## 一、验收环境（2026-11-13）

| 项 | 用的是什么 | 说明 |
|---|---|---|
| 板子 | **真的 RK3588 ATK-DLRK3588**（serial `f34dca7784396ab2`） | 经宿主 adb server 过 USB 到达；`adb devices` 确认在 `device` 状态 |
| 客机 | **真的 Ubuntu 20.04.2 客机**（`alientek@192.168.136.131`） | 密码认证 |
| 串口 | **虚拟串口设备**（pty 对）＋ 真 `node-serialport` 驱动 | 真板子的物理 COM3 **尚未验**（见 §四） |
| 应用 | **真的 Electron 34.5.8**，在 Xvfb 下跑 | Linux 构建；Windows 构建见 §四 |
| 驱动方式 | CDP 驱动真实渲染进程（`scripts/acceptance/`） | 读 DOM、点按钮、敲键盘 |

> **为什么能在沙箱里跑 Electron**：Linux 版 Electron 二进制不在 npm 包里，

> GTK 等运行库用 `apt-get download` + `dpkg-deb -x` 手动解包，不装 root。

## 四、**还没**验的（需要 Windows 宿主机）

| 项 | 为什么沙箱验不了 | 用户要做什么 |
|---|---|---|
| **Windows 版 Electron** | 沙箱是 Linux；`node-pty`/`serialport` 的 Windows ABI 要 `electron-rebuild` 重编译 | 在宿主上 `npm install`（触发 postinstall 的 electron-rebuild）→ `npm run dev` |
| **物理 COM3（真串口控制台）** | 宿主 COM3 是 CH343，驱动在 Windows 上 | 宿主上 `python 90-工具\serial-server.py --port 2323`，我就能从沙箱驱动 COM3 |
| **串口控制台的回显与提示符** | 上面那条的副产品 | 同上 |
| **真机 SSH 的免密** | 沙箱重启丢了 `/tmp/id_ed25519` | 宿主上跑一次 `sshvm.py bootstrap`（幂等追加公钥） |

> **这不是「没做」，是「换个人做」**：前三项要在 Windows 上跑，
> 第四项是客机侧的一次性准备。

## 五、这次验收的收获

1. **评审读不出来的 bug，只有真机跑才看得见。**
   会话环境脚本里多一个 CR —— 四轮评审（117 + 57 条）都没看出来，
   真机第一次跑就报在屏幕上。
2. **「验证器自己跑不起来」比「没有验证器」更隐蔽。**
   本轮在沙箱里把应用真跑起来，靠的是三个自己写的辅助脚本
   （Xvfb + CDP 驱动 + 虚拟串口）——它们不在仓库里的时候，
   验收就只能靠人肉点。
3. **驱动方式决定验收的强度。**
   「点了没报错」不算过；**读到真实状态**才算过
   （这次就是靠读终端内容才看见那句 `command not found`）。
