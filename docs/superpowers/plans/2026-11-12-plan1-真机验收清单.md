### 4.1 验收过程中抓到的三个 bug

| # | 抓在哪 | 是什么 |
|---|---|---|
| 1 | **真机（沙箱）** | 会话环境脚本多带一个 CR → 板子的 bash 报 `line 3: $'\r': command not found`。**四轮评审都没看出来** |
| 2 | **真机（沙箱）** | 远端树进目录不重新列；「↑ 上级」对根下的目录无效（`parentPath('/.cache')` 返回了它自己） |
| 3 | **真机（本地 Windows）** | `node_modules` 是 Linux 装的 → 两个原生模块是 ELF，Windows 上测试**加载即失败**（178 → 222 条：加载失败的文件里还有一批用例没跑到） |

### 4.2 共享 node_modules 的原生模块规矩（**两边都要知道**）

`node_modules` 是**沙箱与 Windows 宿主共享的同一个目录**，而原生模块按平台编译：

| 包 | Linux | Windows | 冲突吗 |
|---|---|---|---|
| `@serialport/bindings-cpp` | `prebuilds/linux-x64` ✓ | `prebuilds/win32-x64` ✓ | **不冲突**（NAPI，ABI 稳定）——把 `build/` 删掉，两边各走各的 prebuild |
| `node-pty` | **没有 linux prebuild**，只能自己编 | `prebuilds/win32-x64` ✓ | **冲突** |

- **沙箱侧**：`bash scripts/acceptance/linux-natives.sh` → 恢复 Linux 产物。
- **Windows 侧**：`npm install` / `electron-rebuild` 之后，
  **删掉 `node_modules/node-pty/build/`** → 回落到 `prebuilds/win32-x64`
  （NAPI，ABI 稳定，**其实不需要重编译**）。

> 更好的做法是**两边各有一份 node_modules**——共享一份跨两个平台，
> 原生模块这件事就永远要来回倒腾。
>
> **→ 怎么做的**：见
> `docs/superpowers/plans/2026-11-13-plan1-本地部分-执行档案.md`
> ——那是给**在 Windows 上跑的 agent** 的执行档案：要装什么、装到哪、
> 命令、判据、坑、以及填完交回来的回执模板。

## 五、这次验收的收获

1. **评审读不出来的 bug，只有真机跑才看得见。**
   会话环境脚本里多一个 CR —— 四轮评审（117 + 57 条）都没看出来，
   真机第一次跑就报在屏幕上。
2. **「验证器自己跑不起来」比「没有验证器」更隐蔽。**
   本轮在沙箱里把应用真跑起来，靠的是三个自己写的辅助脚本
   （Xvfb + CDP 驱动 + 虚拟串口）——它们不在仓库里的时候，
   验收就只能靠人肉点。
3. **驱动方式决定验收的强度。**
   「点了没报错」不算过；**读到真实状态**才算过
   （这次就是靠读终端内容才看见那句 `command not found`）。
