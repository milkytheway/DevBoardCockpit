## Review Focus

评审者**专门**盯这五类输入——本计划的测试**故意不覆盖**它们：

| # | 输入类 | 为什么危险 |
|---|---|---|
| **RF-1** | **采样与动作并发**：一个动作正好在一次采样往返**飞行中**被排进来 | 契约点名的「点了按钮，监控卡数值乱跳」——两个 marker 的回包在同一份 transcript 里交错 |
| **RF-2** | **往返超时之后的下一次往返**：上一次超时、marker 没收齐，下一次就开始 | 串口上「上一条命令的残留回包」认领了下一条命令的 marker → **数据被算到别的 reader 名下** |
| **RF-3** | **采样周期短于一次往返耗时**（`interval_ms` < 往返耗时） | 调度器会永远追不上 → 要么疯狂堆积，要么静默丢样本；两者都得是**可解释的**行为 |
| **RF-4** | **renderer 订阅晚于 / 早于第一次采样**，以及**中途断开重连** | 漏掉一次推送，面板就永远停在旧值——而面板上那个数**看起来是真的** |
| **RF-5** | **板型包认不出来**（型号不匹配、没有包、多个包都匹配） | 契约 §10 明写「**不猜**」。猜错的后果是「把 `gpu.usage` 绑到一块没有 GPU 的板上」——一个恒为 0 的仪表 |

## Task 1: 往返队列（契约 §1.2.1）

**Files:**
- Create: `src/main/hal/round-trip-queue.ts`
- Test: `tests/unit/round-trip-queue.test.ts`

**Interfaces:**
- Consumes: 无（纯逻辑，**不 import 任何传输实现**）
- Produces:
  ```ts
  export type RoundTripKind = 'action' | 'sample';
  export class RoundTripQueue {
    constructor();
    /**
     * 排队执行一次往返。'action' 插队到 'sample' 之前。
     *
     * **硬约束：同一时刻只有一次往返在飞。**
     * 这是契约 §1.2.1 的第一句（「同一个连接上，同时只能有一次往返」）——
     * 串口上只有一根线、一个读线程、一份 transcript，两次往返并发会让
     * 两个 marker 的回包在同一份 transcript 里交错
     * （契约点名的症状：「点了按钮，监控卡数值乱跳」）。
     *
     * 所以：**无论从哪个队列进来，都由同一条推进链驱动**。
     * 「动作优先」= 动作排在采样**前面**，
     * **不是**「动作可以插到正在飞的那次往返中间」——
     * 已经在飞的那次往返**必须等它回来**（串口上没法半途换人）。
     */
    run<T>(kind: RoundTripKind, fn: () => Promise<T>): Promise<T>;
    /** 队列里还没开始执行的个数 */
    get pending(): number;
    /** 当前有没有一次往返在飞 */
    get busy(): boolean;
  }
  ```

- [x] **Step 1: 先写失败的测试**（`tests/unit/round-trip-queue.test.ts`）

  断言（每条一个 `it`）：

  1. `run('sample', fnA)` 与 `run('sample', fnB)` **串行**：`fnA` 的 promise 未 resolve 前，`fnB` 的闭包**没有被调用**（用一个数组记录调用顺序与时刻断言）。
  2. `run('action', fnAction)` 在**两个 sample 已经在排队**时**先执行**——断言调用顺序是 `sample1 → action → sample2`。
  3. `run` 的返回值是闭包的返回值（`await` 透传）。
  4. 闭包**抛错**时，`run` **reject** 同样的错误，且**队列继续可用**（下一个 `run` 正常完成）——「一把锁坏了，通道就废了」是更糟的失败。
  5. 同一个 `run` 里闭包**被调用恰好一次**。
  6. **任何时刻只有一次往返在飞**（契约 §1.2.1 的第一句）：
     第一个 `run` 的闭包还没 resolve 时，第二个 `run` 的闭包**没有被调用**——
     **哪怕第二个是 `action`**。动作优先 ≠ 动作插队插到飞行中的那次往返中间。
  7. `busy` 在有往返在飞时为 true，队列空且没有在飞时为 false。

- [x] **Step 2: 跑，确认红**

  Run: `npx vitest run tests/unit/round-trip-queue.test.ts`
  Expected: FAIL —— `Cannot find module '../src/main/hal/round-trip-queue'`

- [x] **Step 3: 写实现**（`src/main/hal/round-trip-queue.ts`）

  一个 `Promise` 链 + 两个待执行队列（action 一个、sample 一个）。
  - `run('action')` → 推进 action 队列；action 队列**优先于** sample 队列。
  - `run('sample')` → 推进 sample 队列。
  - **一条推进链**：不管 `run` 从哪个队列进来，都由**同一条**链推进
    （action 队列优先，action 空了才取 sample）——
    **这是「同一时刻只有一次往返在飞」的实现方式**。
    两个独立 Promise 链会各自开跑 → 两次往返并发 → 串口上串台。
  - 推进逻辑：`while (本次队列非空) { 取一个出来 await 它 }`，**每次 await 之后重新检查 action 队列**——「动作插队」就是靠这个。
  - 闭包抛错：**catch 住、reject 调用方、但继续推进队列**（不要让链断掉）。
  - **队列不做自己的超时**（接口里**没有** `timeoutMs`）：超时是**传输层**的事
    （事实 G1：统一返回 124，串口是「等 marker 收齐或**明确放弃**」）。
    队列若自己判超时，就会在**传输层还在等 marker**的时候放行下一次往返——
    **下一次会认领上一次残留的回包**（RF-2）。
    那比「队列堵住」糟得多：**堵住是看得见的，串台是看不见的**。
    （传输层真的放弃时，它自己会返回 124 —— 队列看到的是「这次闭包结束了」。）

- [x] **Step 4: 跑，确认绿**

  Run: `npx vitest run tests/unit/round-trip-queue.test.ts`
  Expected: PASS

  ```ts
    now?: () => number;
    /** 可注入的定时器，便于测试里用假时钟 */
    setTimer?: (fn: () => void, ms: number) => unknown;
    clearTimer?: (handle: unknown) => void;
  }
  export class PollScheduler {
    constructor(pack: BoardPack, sampler: TagSampler, queue: RoundTripQueue, opts?: SchedulerOptions);
    start(): void;
    stop(): void;
    /** 本次运行中因让路而**跳过**的采样周期数（判据用） */
    get skipped(): number;
    /** 每个组实际跑过的次数（判据用） */
    get ran(): Map<string, number>;
  }
  ```

- [x] **Step 1: 先写失败的测试**（`tests/unit/tags-scheduler.test.ts`）

  用**假时钟**（注入 `now` 与 `setTimer`）断言：

  1. `start()` 之后，推进假时钟到 `interval_ms`，该组被 `sampleGroup` 调了**一次**。
  2. **跳过不补发**：让某次采样在队列里**等了超过一个周期**（用假队列把 `run` 的闭包推迟），断言**这一轮被跳过**、`scheduler.skipped` 递增、且**没有补发**（`sampleGroup` 的调用次数**不**因为补发而多一次）。
  3. `stop()` 之后推进假时钟，**不再**有 `sampleGroup` 调用。
  4. **一次往返超过 `interval_ms` 时不堆积**：断言待执行的采样周期数**不超过 1**（`scheduler.ran` 的计数不暴涨）。

- [x] **Step 2: 跑，确认红**

  Run: `npx vitest run tests/unit/tags-scheduler.test.ts`
  Expected: FAIL —— 模块不存在

- [x] **Step 3: 写实现**（`src/main/tags/scheduler.ts`）

  - 每个 poll group 一个定时器，`ms = group.interval_ms`。
  - 定时器触发时：`const enqueuedAt = now()` → `queue.run('sample', () => sampler.sampleGroup(group.id))`。
  - **跳过不补发**：拿到执行权时若 `now() - lastRanAt > interval_ms + slack`（`slack` 取 `interval_ms` 的一半），**跳过本周期**（`skipped++`、更新 `lastRanAt`），**不调用** `sampleGroup`。
  - **绝不直接调 `sampler.sampleGroup`**——一律经 `queue.run('sample', ...)`（P3）。
  - **不堆积**：每个组一个「**已入队**」标志——
    定时器再响也不重复入队（否则一次慢往返会让队列越积越多，
    而契约要的是「**跳过本周期**，不补发」）。
    标志在**拿到执行权时**清掉。
  - `stop()` 清掉所有定时器。

  Run: `npx vitest run tests/unit/tags-scheduler.test.ts`
