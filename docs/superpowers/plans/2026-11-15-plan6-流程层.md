# 计划 6 · 流程层（workflow pack · 宿主层格式）

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 让宿主能**跑一件事**（多目标、多步骤、有判据、可追责），而不只是「发一条命令」：把「编译 → 产物 → 送到板子 → 装 → 跑 → 看输出」做成**宿主侧的一份声明**，由宿主执行、逐步审计、如实回报。

**Architecture:** 新增一层 **流程层**（`src/main/workflows/`）：**格式与校验器**（宿主层 YAML，封闭 schema）→ **目标登记处**（role → 连接，按 profile id 指名）→ **步骤执行器**（每一步**复用 M6 的七步链**：编码 → 地板 → 授权 → 确认 → 执行 → 回读 → 审计）→ **时间线**（每阶段引用 `audit_id`）。**不新造第二条执行路径**。

**Tech Stack:** TypeScript `strict`、Electron 34、vitest、`js-yaml`（已在依赖里）

**Spec:** `docs/28-流程包评审处置.md`（ADR-D31 的 R1–R13）、`docs/05` 的 **ADR-D31 / ADR-D32**、`docs/spec/02-board-pack.md` §4/§5（动作与回读五形式）、`docs/spec/03-card-manifest.md` §5（写侧闭环）、`docs/04-环境/板子放置规范.md` §4（落位硬规矩）

> **本计划不动契约**：`docs/spec/` 五份**一个字不改**。
> 流程包首版是**宿主层格式**（`docs/29` + `fixtures/`），**不进 `docs/spec/`**（ADR-D31 R1）。
> 卡片 API 与 MCP 工具首版**也不动**（同 R1）——所以本计划的产物**由宿主命令触发**。

## Global Constraints

| # | 约束 | 出处 |
|---|---|---|
| **A1** | **契约一个字不改**。流程包是**宿主层的数据格式**，不是契约 | ADR-D31 R1 |
| **A2** | **不新造第二条执行路径**：每个写步骤**一律过 M6 的七步链**（编码 → 地板 → 授权 → 确认 → 执行 → 回读 → 审计） | ADR-D31 R2；`docs/24` §一 |
| **A3** | **成功判据复用 M6 的回读五形式**（tag / file_equals / command_ok / verify / none）。**不新增第六种形式**——只是**多了一个「在哪个 role 上读」** | ADR-D31 R3；ADR-D32 D32-2 |
| **A4** | **自由命令（`exec`）必须过同一张危险地板**，且**编码后再匹配**（`spec/02` §5.2.1） | ADR-D31 R2 |
| **A5** | **step kind 只有 6 个**：`exec` / `file.transfer` / `action` / `await` / `assert` / `discover`。**`exec_script` 连「留位置」都不留** | ADR-D31 R11 |
| **A6** | **流程包必须有 `inputs`**（封闭类型表，照 `spec/02` §4.3）；步骤里 `{input}` 占位，**替换后的最终命令过地板与编码** | ADR-D31 R4 |
| **A7** | **目的地三形态**：`path`（用户指定）\| `placement`（语义默认）\| `ask`（现场问）；placement 词表**封闭** | ADR-D31 R5 |
| **A8** | **产物发现不写死文件名**（按扩展名/glob 找），发现规则来自**包里的声明**，不是脚本里的 if | ADR-D31 R4；尖兵 §二·Q4 |
| **A9** | **落位按板子的硬规矩**：`.ko` → `/usr/lib/modules/<ver>/extra/` → `depmod -a` → **`modprobe <名字>`**（**绝不 `insmod`**） | `docs/02` §3.5；放置规范 §4 |
| **A10** | **凭据准备是独立的 `destructive` 一步**（写 `authorized_keys`），**必须显式**、**必须走确认通道**——**不许藏在某个步骤的命令里** | ADR-D31 R7；ADR-D32 D32-1 |
| **A11** | **审计与时间线并存**：审计是追责单位（每步一行）；时间线是一次运行的记录，每阶段引用 `audit_id` | ADR-D31 R8 |
| **A12** | **时间线首版是 poll**（不订阅）——`spec/00` §七 的连续流契约**还没定死** | ADR-D31 R9 |
| **A13** | **每个新模块都要有变异守卫**。「测试通过」≠「测试能抓住 bug」 | 计划 4 P11；计划 5 A13 |
| **A14** | **长步骤必须能看见进度**。传输耗时实测波动 **20 倍**（同一份 909KB：3.8s / 75.6s / >110s）→ 不许假设它快 | 尖兵 §三·F1；计划 5 A16 |
| **A15** | **真机判据要由真跑兜底**。本工程吃过一次教训：假设备的 `MemAvailable` 写成 MiB，**单测全绿，真机跑起来才发现** | `docs/17` §1.6 |
| **A16** | **机器专属值只进 `profiles/settings.json`**；一次性探针脚本不进仓库 | 计划 4 P10 |
| **A17** | **判断用机械判据**：真机与真 Electron 的判据用脚本，不靠手工探针 | 计划 4 P12 |

## Review Focus

评审者**专门**盯这六类输入——本计划的测试**故意不覆盖**它们：

| # | 输入类 | 为什么危险 |
|---|---|---|
| **RF-1** | **参数里塞分隔符**：`; reboot`、`$(rm -rf /)`、反引号、`%USERPROFILE%\.ssh\id_rsa` | 流程层开了第二条命令通道 → 注入防线漏一条 = 客机上跑任意命令 |
| **RF-2** | **`{input}` 占位自带引号**（`cmd: "make '{project}'"`） | 编码器按类型注入引号；模板自带引号 = 双层引号 = 参数逃逸 |
| **RF-3** | **role 绑到 `local`**（本机） | ADR-D31 R2 明写「**角色不许绑到 `local` 当执行目标**」——`local` 是宿主自己的 shell |
| **RF-4** | **placement 词表外的词**（拼错 `kernel-module` → `kernel_modle`） | 封闭词表 = 拼错要**报错**，不能默默回落到别的语义 |
| **RF-5** | **凭据准备被藏在别的步骤的命令里** | A10：它是 destructive 级 → 必须独立一步 + 必须走确认 |
| **RF-6** | **判据在错的 role 上读**（该读板子却读了客机） | 跨目标判据的**归属**写错 = 「板子上没有产物」被判成「有」→ 假阳性 |

## Task 2: 目标登记处（按 profile id 指名执行）

> **为什么必须先有它**：M6 的执行器**只能用运行时那一条连接**——
> 而「在客机上跑一条 scp」（直传）**要的是另一条连接**。
> 计划 5 的 A17 写了「执行器要能对指定的连接执行」，**实现里还没有**（接线给的是 `runtime.runTransaction`）。

### 2.1 步骤

- [x] **2.1.1 `src/main/workflows/targets.ts`**：
  - `TargetRegistry`：按 **profile id** 取得一条连接（**第一次用时开，之后复用**，流程结束可关）；
  - **一条 role ↔ 一条连接**；同一条连接上**所有往返都经它自己的队列**（串口是一根线）；
  - `runOn(profileId, fn)`：**独占事务**（与运行时那条队列**不是同一个**——两台机器各一根线）；
  - **profile 不存在 → 报错**（不许悄悄连到别的）。
- [x] **2.1.2 执行器能指名目标**：把 `invokeAction` 的 `runTransaction` 依赖改成**由调用方给**（现在就是这样 ✓）→ 流程层传自己的目标事务 ✓；**不**改 M6 的行为。
- [x] **2.1.3 单测**：目标登记处的开/复用/关、profile 不存在报错、**同一次运行里两条目标各跑各的**（不串台）。
  - ✅ **15 条**（`tests/unit/workflows/targets.test.ts`）：复用、两条线各跑各的、
    **同一个目标上的两次往返不并发**（顺序断言）、profile 不存在报错、closeAll 后再取会重开 ✓。

### 2.2 判据

| # | 判据 |
|---|---|
| 1 | 两条目标（客机 + 板子）**各跑各的**，输出不串台 ✅ |
| 2 | profile id 不存在 → **报错**（不是连到别的） ✅ |
| 3 | 同一 role 的连接**复用**（不每次重开） ✅ |
| 4 | **同一个目标上的两次往返不并发**（一条线一次只能有一个） ✅ |

## Task 3: 步骤执行器（七步链复用）+ 时间线

- [x] **3.1.1 `src/main/workflows/runner.ts`**：
  - 跑一个流程包：解析 `inputs` → 按 `steps` 顺序执行 → 产出**时间线**；
  - 每个写步骤**过 M6 的七步链**（A2）：编码 → 地板 → 授权 → 确认 → 执行 → 回读 → 审计；
  - **判据可以指名 role**（A3）——「客机上跑完 scp，板子上真的有那个文件了吗」；
  - `assert` = `await` + `on_mismatch`（`fail` / `continue`）；`await` 的判据就是五形式之一。
- [x] **3.1.2 时间线**：`{ runId, stage: [{stepId, kind, ok, verified, reason?, audit_id, at, durationMs}] }`（A11）；**每阶段引用那一行的 `audit_id`** ✓。
- [x] **3.1.3 审计**：每步一行，复用 `ActionAudit`（**追加写、每行 flush**）；`actor` = `workflow:<packId>` ✓。
  - **跨目标的判据单独记一行**（`workflow:<pack>:<step>:readback`）——
    「客机那条命令跑了」与「板子上真的有那个文件」是**两个事实** → **两行账** ✓
    （时间线的阶段带 `audit_id` 与 `readback_audit_id` 两个 ✓）。
- [x] **3.1.4 单测**（假的连接，`tests/unit/workflows/runner.test.ts`，**10 条**）：
  命令**发到指名的目标上**（客机那条命令不许跑到板子上 ✓）· 输入**按类型编码**
  （`; reboot` 被当字面量 ✓）· **命中危险地板 → 要人确认**（命令**没执行** ✓）·
  **每步一行审计**且时间线的 `audit_id` 指得到 · 产物发现**落进槽** ·
  没找到 → **失败**（不报成功 ✓）· 传输命令在**源目标**上跑、目的地按 placement 解析 ✓ ·
  **判据在指名的角色上读**（在板子上问板子 ✓）· `assert` 不符 → 失败 ·
  `on_mismatch: continue` → 继续往下跑（但整体仍不算成功 ✓）。
- [x] **3.1.5 宿主侧的入口**：`scripts/run-workflow.ts` + `npm run workflow:run`
  （**流程包首版的唯一入口**——ADR-D31 R1：卡片 API 与 MCP 工具首版不动契约）。
  支持 `--package` / `--input 名字=值` / `--dry-run`。

### 3.2 判据

| # | 判据 |
|---|---|
| 1 | 每个写步骤**都有一行审计** |
| 2 | 时间线的每个阶段**都有 `audit_id`**，且**能在审计文件里找到那一行** |
| 3 | 判据指名 role → **在那个 role 上读**（RF-6） |
| 4 | `exec` 的命令**过了地板**（A4；守卫：把地板查掉 → 测试必须红） |
