### 🟡 I-1 · 取消过的运行，走**异常路径**时仍会被翻成 `failed`

**位置**：`src/main/workflows/service.ts:401-405`（`catch` 块）

```ts
} catch (err) {
  status.state = 'failed';        // ← 没有 cancelled 守卫 ✓
```

**证据**：成功路径有守卫（`:382` 的 `if (status.state !== 'cancelled')` ✓），**catch 路径没有** ✓。

### 🟡 I-3 · `inputs.default` 只到了**命令模式**，值模式拿到的是字面量 `{input:x}`

**位置**：`src/main/workflows/encoder.ts:121`（`spec.default` ✓ 只在编码路 ✓）· `substitute.ts:86-89`（值模式读 `ctx.inputs` ✓）

**证据**（审计的探针，我复核了代码路径 ✓）：
- 声明 `count: {type: integer, default: 5}` 而调用方不给 ✓ → `exec` 步的命令是 `echo 5` ✓（**命令模式拿到了默认值** ✓）

### 🟡 I-5 · 确认凭据**没绑「这一步的最终命令」**

**位置**：`src/main/actions/authorization.ts:177`（签发）与 `:275`（消费）

```ts
digest:  `${actionId}|${paramsDigest(params)}|${packId}|${contractVersion}`   ← 绑了四样
```

**契约要求五样**（`spec/05` §7.5-3 ✓）：动作 id（含步骤 id ✓）· 参数摘要+输入摘要 ✓ ·
**这一步最终命令的摘要** ✗ · 包 id ✓ · 契约版本 ✓。

**为什么重要**：最终命令是**消费时**现算的 ✓，而命令里的 `{output:槽}` / `{from.path}` / `{to.path}`
**不在摘要里** ✓ → 同一张凭据认得两条不同的最终命令 ✓。
实际可利用路径窄 ✓（同一 run 内槽不变 ✓），但这是凭据作用域上**与契约明文写死的缺口** ✓。

**修法**：签发时把最终命令的 sha256 一起存进凭据条目 ✓，消费时比对 ✓。
