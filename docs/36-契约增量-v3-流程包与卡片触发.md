## 一 · D7 的处置：**目标不进契约，进数据**

> **待裁决的 D7**（「目标」这一维要不要进契约）—— **本文给出一个不需要它也能满足用户需求的答案**。

**用户原话**：「用户可以选择**本机**或者**客机**上的代码」。

**本文的形状**：

```
目标（哪台机器）  ← 由**流程包**声明（role → profile id，宿主侧的文件 ✓）
用户的选择        ← 由**用户选哪个流程**表达 ✓
```

→ **「本机编译」与「客机编译」是两个流程包** ✓ → 卡片**只看到流程**（id + 输入声明 ✓）→
**卡片不知道目标** ✓ → **契约层不需要「目标」这个概念** ✓。

> **措辞订准**（评审 35 的 A10 ✓，v2 没改准）：
> 不是「契约层一个字都不用改『目标』这一维」，而是 ——
> **「目标」从来就不是契约的概念** ✓；
> `roles` 是**流程包这个数据格式的字段** ✓（数据格式 ≠ 契约 ✓）。
> 契约要改的是**卡片与 agent 怎么触发流程** ✓（§四、§五 ✓）。

**代价（诚实说）**：卡片**不能自己拼**「先在客机编译、再传到板子」这种多步组合
——它只能选一个**已经声明好的流程** ✓。
→ 用户要的新组合 = **写一个新的流程包**（宿主侧的文件 ✓，不是卡片代码 ✓）。

## 二 · 信任模型（**本次增量的核心**）

### 2.1 三本账

| 账 | 记什么 | 在哪 | 谁能改 |
|---|---|---|---|
| **注册表** | 目录里有哪些包（id → 包 + **内容摘要**） | `profiles/workflows/`（内置）+ `~/.local/share/DevBoardCockpit/workflows/`（用户） | 放文件进目录 |
| **批准账** | 哪些包**被用户批准过**（id → 摘要 + 时刻） | `workflows-approved.json`（用户数据目录 ✓） | **只有人能改** ✓ |
| **审计** | 每次运行每一步做了什么 | `logs/actions.log`（行式 ✓） | 宿主 |

### 2.2 五条规矩

| # | 规矩 | 为什么 |
|---|---|---|
| **T1** | **放一个文件进目录 ≠ 批准它** | 否则「能写文件」=「能执行命令」✗ |
| **T2** | **批准绑内容摘要** | 改了内容 → **要重新批准** ✓（不然「批准 A 版、跑 B 版」✗） |
| **T3** | **卡片与 agent 只能按 id 取注册表里的包**，**给不了路径** | agent 不能自写一个包就跑 ✗ |
| **T4** | **每个写步骤都过 `spec/02` §4.6 的编码 + §5.2.1 的危险地板**；命中地板 → **按 destructive 处理** | 自由命令是**第二条命令通道** ✗ —— 它必须与动作**同一条防线** ✓ |
| **T5** | **角色不许绑到 `local` 传输** | `local` 是**宿主自己的 shell** ✓ —— 流程在它上面跑命令 = 在宿主上跑命令 ✗ |

### 2.3 「点头」发生在哪（**两条路，落到同一本账** ✓）

| 路 | 谁点头 | 什么时候 |
|---|---|---|
| **装卡** | 装卡的界面（**卡片声明 `requires.workflows`** → 装它时逐条过目 ✓） | 装卡时 ✓ |
| **命令行** | 人自己敲 `npm run workflow:approve -- <id>` ✓ | 随时 ✓ |

→ **批准前必须展示「会在哪些目标上跑哪些命令」** ✓（**否则批准只是「批准一个文件名」✓ → 等于没看 ✗**）：
角色 → profile id、每个写步骤的命令**模板**、这一步危不危险、判据读在哪个角色上 ✓
（实现：`workflow:approve` 逐条打印 ✓）。

### 2.4 危险命令的**运行期**确认（与动作同构 ✓）

| # | 规矩 | 实现 |
|---|---|---|
| 1 | 步骤声明 `danger: destructive` → **每次运行都要人确认** ✓ | ✅ `format.ts` + `runner.ts` ✓ |
| 2 | **命中危险地板 → 也按 destructive 处理**（取更严的 ✓） | ✅ `floor-check.ts` ✓ |
| 3 | **确认凭据绑**：`(动作 id（含步骤 id）, 参数摘要 + **这一步的输入摘要**, **这一步最终命令的摘要**, 包 id, 契约版本)` | ✅ `runner.ts` 的 `confirmationsFor` ✓ |
| 4 | **凭据一次性**（用掉即废）+ **TTL 5 分钟** | ✅ `ConfirmationStore` ✓ |
| 5 | **「签发 ≠ 有效」**：没人点，`confirm_id` 永远无效 ✓（契约 `spec/04` §2.4.1 的原话 ✓） | ✅ `approve()` 两段式 ✓ |

### 2.5 确认链的**落点**（**V2-C1 / V3-C1 的正面回答** ✓）

```
某个写步骤要确认
   → 执行器签发 confirm_id（**待确认**，还不能用 ✓）
      绑的是：(动作 id（含步骤 id）, 参数摘要 + 这一步的输入摘要,
              这一步最终命令的摘要, 包 id, 契约版本) ✓
   → 流程**停在那一步**（状态 = awaiting_confirmation ✓，**不是 failed** ✓）
   → **人点头**（GUI 的确认界面 / 宿主命令行 `workflow:confirm` ✓）
      → 凭据**变成可用** ✓（这一步**不是 MCP 工具** ✓ —— 见下 ✓）
   → 流程**从停住的那一步继续**（**前面的步不重跑** ✓ —— 重跑 = 编译两遍 ✗）
   → 同一个 run_id、同一份时间线 ✓
```

> **⚠️「批准」不是一个 MCP 工具**（评审 37 的 **V3-C1** ✓）：
>
> → **agent 唯一能做的是「递一次确认请求」**（`confirm_workflow(run_id)` ✓），
>   那只是**把请求递进 GUI 的确认队列** ✓ —— **凭据仍然无效** ✓。
> → **「批准」这个动作在 GUI 那一侧** ✓（与 `spec/04` §2.4.1 的 `confirm_action` 同形 ✓：
>   **它不返回可直接使用的凭据** ✓）。
> → **暴露 `approve` 给 agent = 两段式白做** ✗（评审 37 的原话 ✓）——
>   拿到 `needs_confirmation` 的那一方**自己就能重试成功** ✓ → 确认通道形同虚设 ✗。

> **续跑会产生**一行新审计**（不是重写原来那行）** ✓：
> → 时间线上同一阶段可能有两个 `audit_id`（前一行是「**被拦下的那一次**」✓）✓
> → 审计是**追加写**的 ✓（`spec/02` §5.4 ✓），**不改写历史** ✓。

> **「前面的步不重跑」是硬要求** ✓：编译要一分钟、传输要几十秒 ✓
> → 重跑一遍 = 白等一倍时间 ✗，而且**有副作用的步重跑 = 做两遍事** ✗。

> **判据命令不进确认通道**（首版取舍 ✓）：
> 判据命令是**只读的验证**（`test -f` / `lsmod | grep` ✓），
> 它**必须过地板** ✓（§三·3.5 ✓），
> 但**不进 `authorize` 的确认通道** ✓。
> **代价**：一个判据命令理论上能写（`verify` 的命令是包给的 ✓）→ **首版的防线是「装包时人看过」** ✓（§二·2.3 ✓）+ 地板 ✓。
> **下一期**若要更严：判据命令也走确认通道 ✓（代价：每次验证多一次人点 ✓）。

| `boolean` | — | |
| `enum` | `values`（封闭取值表 ✓） | 不在 `values` 里 → **报错** ✓ |
| `path` | `maxLength` | **等价于 `string`** ✓（不另造类型 ✓） |

### 3.3 `roles`：角色 → 连接 profile（**只许引用** ✓）

| # | 规矩 |
|---|---|

### 3.4 六种 step kind（**封闭** ✓）

| kind | 干什么 | 必填 | **在哪跑** |
|---|---|---|---|
| `exec` | 在某个角色上跑一条命令 | `role` `cmd` | `role` 指的那个目标 ✓ |
| `discover` | 产物发现（**规则 + 排除表** ✓） | `role` `pattern` `out` | `role` 的目标上**列目录** ✓ |
| `file.transfer` | 搬运（源 → 目的地） | `from` `to` `cmd` | **源目标**（`from.role` ✓）——**传输命令在源上跑** ✓（直传的全部语义 ✓） |
| `action` | 引用**板型包里已声明的动作** | `role` `action` | `role` 的目标 ✓ |
| `await` | 等一个判据成立 | `readback`（+ **在哪个角色上读** ✓） | **判据指定的角色** ✓ |
| `assert` | 判据 + 不符时怎么办 | `readback`（+ 同上 ✓） | 同上 ✓ |

> **`file.transfer` 的命令跑在**源**角色上** —— 这一句是**直传的全部语义** ✓
> （v2 漏了它 ✓ —— 评审 35 的 V2-M1 ✓）：
> 客机编译的产物**由客机自己 scp 给板子** ✓，**不经宿主取回** ✓（用户 2026-11-15 的原话 ✓）。

> **`exec_script` 连「留位置」都不留**（ADR-D31 R11 ✓）。

### 3.5 判据：**复用 `spec/02` §4.4 的五形式**

```yaml
readback:
  kind: verify
  role: target          # ← **在哪个角色上读**（不写 = 本步自己的角色 ✓）
  command: "test -f {to.path}"
```

| # | 规矩 |
|---|---|
| 1 | **判据的词汇就是 M6 那五种**（`spec/02` §4.4 ✓）——**不新增第六种形式** ✓；**首版支持形式 2–5**，**形式 1（tag）保留位置但首版报错** ✓（理由：tag 属于**板型包的核心词表** ✓，流程层没有板型包 → **查不了** ✗） |
| 2 | **多一个 `role`**：「在哪个角色上读」 ✓ —— 跨目标的验证靠它 ✓ |
| 3 | **`role` 指到没声明过的角色 → 报错** ✓ |
| 4 | **`await`/`assert` 必须说得出在哪个角色上读**（自己的 `role` 或判据的 `role` ✓） |
| 5 | **形式 1（tag）在流程层首版报错** ✓（见上 ✓） |
| 6 | **`none` 只在 `danger: reversible` 的步上用** ✓（照 `spec/02` §4.4.1 ✓） |
| 7 | **判据的命令也要过危险地板** ✓（它是**包给的命令** ✓ → 不查就能借「验证」之名跑危险命令 ✗） |
| 8 | **判据的 `role` 只能选本流程已声明的角色** ✓（不能借判据去读**没授权的机器** ✗） |

### 3.8 跨机写（**V2-I4 的正面回答** ✓）

跨机写是「**源目标上的一条任意命令**」✗ —— `scp` / `ssh` **不命中危险地板表** ✓
→ 所以它**需要自己的规矩** ✓：

| # | 规矩 |
|---|---|
| 1 | **`file.transfer` 的传输命令按「跨机写」建模**：源目标、目标角色、源路径、目的地路径 —— **四项都要进确认摘要** ✓ |
| 2 | **跨机写**在**装包批准**时就必须显示出来 ✓（§二·2.3 ✓）—— 人看到「客机 → 板子 传 x」✓ |
| 3 | **不许关掉主机身份校验**（`StrictHostKeyChecking=no` **禁止** ✓）—— 判据建立在一条**不校验身份**的连接上 = 事实可能是假板子 ✗ |
| 4 | **主机身份校验失败 → 判据**不成立** ✓（不是「判据失败」也不是「忽略」✓） |
| 5 | **危险地板对 `ssh` / `scp` 是空的** ✓（事实：地板表里没有它们 ✓）→ 所以跨机写**不能靠地板兜住** ✗ → 它靠**上面四条**兜住 ✓（人在批准时看见了 ✓ + 传输命令本身在包里 ✓ + 判据在**目标**上读 ✓ + 主机身份校验 ✓） |
| 6 | **传输命令要进确认摘要** ✓（源目标 / 目标角色 / 源路径 / 目的地路径 ✓ —— 「人批的是这一条传输」，不是「传输这类东西」✓） |

## 四 · `docs/spec/03-card-manifest.md` 的增量

### 4.1 manifest 的两处改动（**V2-C2 的正面回答** ✓）

```yaml
requires:
  workflows: [hello-kernel.build-run]          # ← 新增 ✓
permissions:
  read: []
  write: []
  workflows: [hello-kernel.build-run]          # ← **也新增** ✓
```

| # | 规矩 | 为什么 |
|---|---|---|
| 1 | **`requires.workflows` 进 manifest 的封闭字段表** ✓ | 不加就过不了解析器 ✓ |
| 2 | **`permissions.workflows` 进 manifest 的封闭字段表** ✓ | **规则 3 说「requires ⊆ permissions」** ✓ —— 声明了 `requires.workflows` 就**必须**有 permissions 字段覆盖它 ✓，否则规则 3 无从判定 ✓（**V2-C2** ✓） |
| 3 | **声明 ≠ 授权**：装卡时**逐条过目** ✓ → 写进批准账 ✓ | 与 `permissions.write` 同理 ✓ |
| 4 | **流程的动作不重复声明**（流程包自己声明它的步骤 ✓） | 单一源头 ✓ |
| 5 | **`permissions.workflows` 为什么不是 `permissions.write`** | `write` 装的是**板型包里的动作 id** ✓，而规则 5/6 会对它做「在板型包里存在吗」「不许通配符」的检查 ✓ —— **流程 id 不是动作 id** ✓ → 混进去会让那两条规则误判 ✓ |
| 6 | **流程的授权有**两层** ✓（**第三件事** ✓ —— 评审 37 的 V3-I9 ✓）：① **流程包已批准**（宿主侧 ✓）② **这张卡被授过这个流程**（卡级 ✓）→ **两层都要过** ✓ |

### 4.2 §7.7 的 API 全集：加两行

| 方法 | 读/写 | 权限 | 返回 |
|---|---|---|---|
| `cockpit.workflows.list()` | 读 | 无（**只列用户批过的** ✓ —— 没批过的卡片看不见 ✓） | `[{ id, name, inputs }]` ✓ |
| `cockpit.workflows.run(id, inputs)` | 写 | `permissions.workflows` 里有这个 id ✓ **且**它已批准 ✓ | `{ runId }`（**长任务** ✓） |
| `cockpit.workflows.status(runId)` | 读 | 同上 | `{ state, stages }`（**时间线** ✓） |

> **卡片侧看时间线时**：`stages` 只给 `stepId` / `kind` / `ok` / `verified` / `reason` ✓ ——
> **明细（路径、输出值）留在宿主与 agent 那边** ✓（§三·3.7·6 ✓）。

### 4.3 §5 的写侧闭环：加一段「一件事」

> §5 现在写的是「**一个动作**」的闭环 ✓。
> §5.5 加：「**一件事**」= **流程**（卡片 → 流程 → 多个步骤 → **时间线** ✓）。

### 4.4 §7.8 连接上下文：**流程不改变它**

→ 流程里的每个角色**各自绑定一个连接 profile** ✓（包自己声明 ✓）；
→ 卡片侧**不感知**这些连接 ✓（§7.8 的隐式作用域**只管读写侧那条线** ✓）。

## 六 · 长任务的运行语义

| # | 规定 |
|---|---|
| 1 | **`run` 立刻返回 `run_id`** ✓（编译实测 58.9s / 98.5s ✓ → 同步返回不成立 ✓） |
| 2 | **`status(run_id)` 轮询取时间线** ✓ |
| 3 | **状态机**：`running` / `awaiting_confirmation` / `done` / `failed` ✓（**`awaiting_confirmation` 是一档** ✓ —— 「等人点头」**不是失败** ✓） |
| 4 | **幂等**：同一个 `run_id` 重复查 → **同一份时间线** ✓（不是重跑 ✓） |
| 5 | **续跑**：人点头后**从停住的那一步继续** ✓（**前面的步不重跑** ✓） |
| 6 | **两条互斥的路**：**重新触发**（`run_workflow` / `workflows.run` 再调一次）= **从头再跑** ✓（**前面已完成的写步骤会重复执行** ✓ → 因此 `destructive` 的步**不要放在有副作用的写步之后** ✓）；**续跑**（人点头后）= `confirm(run_id, confirm_id)` ✓ → **从停住的那一步继续** ✓（§二·2.5 ✓） |
| 7 | **并发**：**同一个流程包同时只允许一次运行** ✓（首版 ✓）——两个流程同时抢一条串口会串台 ✓（事实 S1 ✓）→ **执行者**：服务层按 `workflowId` 查有没有在跑的 ✓ |
| 8 | **超时**：**单步超时**由步的 `timeout_ms` 定 ✓；**整次运行无总超时**（编译可能很久 ✓） |
| 9 | **取消**：**首版不支持** ✓（执行原语不可中断，ADR-D32 D32-4 ✓）→ 契约里**明写不支持** ✓ |

## 七 · 这条增量**不做**的事

| 不做 | 为什么 |
|---|---|
| **「目标」进契约** | §一 的形状已经满足用户需求 ✓ |
| **卡片自己拼多步** | 组合属于**流程包** ✓ |
| **流程的卡片 API 的推送** | ADR-D31 R9：首版 **poll** ✓ |
| **流程包自己携带凭据** | 只许引用 profile id ✓（凭据是宿主的账 ✓） |
| **`exec_script`** | ADR-D31 R11：连位置都不留 ✓ |
| **续跑的任意步跳转** | 只能从**停住的那一步**继续 ✓（跳着跑 = 状态不自洽 ✗） |
| **失败后的产物清理** | 首版不做 ✓（**已知欠账** ✓ → 尖兵 §三·F4 的 `.b64` 垃圾 ✓） |
| **分支与循环** | 首版是**一条直线** ✓；分支属于流程层的后一期 ✓ |
| **判据命令走确认通道** | 首版：判据是只读验证 ✓ + 过地板 ✓（§二·2.5 ✓） |
