## 二 · Critical

### C-1 · 「取消后状态 = `cancelled`」与「取消已结束的运行 = 幂等」——**今天两条都是假的**

**证据**

- `src/main/workflows/service.ts:195-205`：
  ```ts
  cancel(runId: string): { runId: string } {
    const status = this.runs.get(runId);
    if (status === undefined) throw ...;
    this.aborts.get(runId)?.abort();
    status.state = 'cancelled';      // ← 同步置上
    status.reason = 'cancelled';
    status.finishedAt = this.now();
    return { runId };
  }
  ```
- `src/main/workflows/service.ts:313-316`（**同一个 `execute()` 的续段**，在 `abort()` 之后几毫秒就会跑到）：
  ```ts
  status.stages = [...status.stages, ...result.stages];
  status.outputs = result.outputs;
  status.ok = result.ok;
  status.state = result.ok ? 'done' : 'failed';   // ← 无条件覆盖
  ```
  → 被取消的那一步跑完 unwind 后，`state` **从 `cancelled` 翻回 `failed`**，
  `reason` 也从 `'cancelled'` 变成那一步的回读原因（`service.ts:325`）。
- `service.ts:201` 那一行**对已结束的运行也照写** → 取消一个 `done` 的运行，
  它的状态**从 `done` 变成 `cancelled`** → **违反 C5 的「幂等（状态不变）」**。

**为什么现有的测试与守卫抓不到**（这一条最要紧）

- `tests/unit/workflows/service.test.ts:290-300`：断言 `expect(status.state).toBe('cancelled')`
  是**紧跟 `cancel()` 同步读**的，**没有 await 那次 unwind** → 抓不到覆盖。
  更糟的是它的**标题**写着「**且在飞的那一步真停**」，但**它一个字都没断言**在飞的那一步——
  **测试名承诺了一个它不检查的性质**。
- `scripts/mutation-check.mjs:1500-1509`（M123）：只把 `status.state = 'cancelled';` 改成 `'failed'`
  → 它守的是**那一行赋值**，**不守「赋值之后不被覆盖」**。

**后果**：按提案原文把 C2/C5 写进契约 → **契约又跑在实现前面**。
这正是提案 §〇 要治的 C1 同型病。→ **§五 row 2 与 row 6 必须改成 ❌待做**，
并且 ADR 里要**记下这条欠账**（`docs/06-契约核对.md` 加一条 C*）。

### C-2 · C1 写死的机制（SIGTERM → 200ms → SIGKILL）**只在一种传输上成立**，串口上明说做不到

**证据**

| 传输 | 取消时到底做了什么 | 位置 |
|---|---|---|
| `local` | `child.kill('SIGTERM')` → 200ms → `SIGKILL` ✓ | `util/spawn.ts:88-103` |
| `adb` | 杀的是**本地的 `adb.exe` 客户端**；板子上那条命令**不是**被 SIGTERM/SIGKILL 杀的 | `hal/adb.ts:191-194` → `spawn.ts` |
| `ssh` | **关掉那条 SSH 通道**（`stream?.close()`）；**没有 SIGTERM、没有 SIGKILL**；远端进程的命运取决于服务端 | `hal/ssh.ts:259-269` |
| `serial` | **什么都杀不了** —— 代码自己写着：「串口上**没法杀远端的进程** ✓（那不是一条 shell 连接 ✗）→ 至少**宿主不等了** ✓」 | `hal/serial.ts:332-334` |

**两条附带事实**

- `spec/05` §三**只禁 `local`**，**串口角色是允许的** → 契约不能假装「五种传输一样」。
- `spawn.ts` 的三级升级在 **Windows 上也不是原样**：`child.kill('SIGTERM')` 在 Windows 上
  Node 直接调 `TerminateProcess`（**立刻硬杀**，不等 200ms），`SIGKILL` 那一步是空转
  → 宿主是 win32，这条「给它 200ms 自己退」在**主战场上是假的**。

**为什么这是契约问题不是实现问题**：C1 现在的措辞是
「执行原语可中断：先 `SIGTERM`，给它 200ms 自己退，不退再 `SIGKILL`」
——这是**实现层机制**被写进了契约，**而且对 4 种传输中的 3 种是假的**。

**必须改成可判的语义**（我的建议措辞）：

> C1：取消 = 宿主**请求**中止在飞的那一步。
> **能不能真的停，取决于传输与远端** —— 契约**不承诺**「进程一定死」。
> 串口上**做不到**（宿主只能不再等）；ssh/adb 上**取决于远端**（通道断了不等于进程死了）。
> **契约承诺的是「宿主不再等」+「时间线如实说」**，不是「进程一定没了」。

（这与 `docs/05` ADR-D32 D32-4（`docs/05:1166`）「HAL 的 abort 语义留给流程层」的分工一致，
但 D32-4 只说了「推迟到流程层」，**没说四种传输能给出同一个语义** —— 这一条 v4 要补上。）

5. 这条删除**同时绕过**：危险地板（R6 明确不过）、确认链（没人点）、批准时展示

**结论：会变成后门**（严重度取决于 R3 的强度，见 I-3 —— R3 弱 + R6 强 = 真的后门）。

- **R6-b**：清理只许作用于**一个普通文件**（不许 `-r`、不许目录、不许通配符），

**顺带**：R6 的**理由本身是假的**（M-4）—— 地板表里只有 `rm -rf /`

### I-1 · 「取消」今天**没有任何用户可达的入口**；而提案给的唯一入口**在当前架构下做不到**

- `service.cancel()`（`service.ts:195`）是全仓唯一的 cancel 实现。
  `grep -rn "cancel" src/` 只命中 `service.ts`、HAL 的 `cancelled` 标志、
  以及 `renderer/shell/cards/CardShell.tsx:100` 的 `onPointerCancel`（无关）
  → **没有 IPC 通道、没有 MCP 工具、没有 CLI 脚本**（`package.json:20-23` 只有
  `workflow:run/list/approve/revoke`）。
- 更要紧：`scripts/run-workflow.ts:160-179` **直接调 `runWorkflow`**，
  **根本不用 `WorkflowService`** → CLI 连 `run_id` 都没有
  （`runner.ts:142` 现生成一个）。
- 而 `WorkflowService.runs` 是**进程内存里的 Map**（`service.ts:92`）
  → **另一个进程里的 `npm run workflow:cancel -- <run_id>` 找不到任何东西。**

→ 提案 §一·1.3 与 §六 说的「用户得去宿主命令行 `workflow:cancel -- <run_id>`」
**在当前架构下不成立**。要么运行登记处落盘（但 O26 已把「运行记录临时」拍成宿主内存
→ 又一条冲突），要么给 CLI 一个「**后台跑 + 轮询 + 从同一个进程发取消**」的形态。
**§五 必须把「取消有可达入口」列为待做**（现在是 6 条里没有的第 7 条）。

### I-2 · §五 的台账只覆盖 18 条规则里的 6 条 —— 「一次成文」留了空洞

- 提案新增 **18 条**规则（C1–C7 = 7，P1–P5 = 5，R1–R6 = 6），§五 只列了 **6 条**实现性质。
- **C5**（幂等）、**C7**（时间线理由写 `cancelled`）、**R2 / R4 / R5 / R6** 在 §五 里**一个字都没有**。
- 实测：
  - **C7 没有实现** —— 被取消那一步的 `reason` 来自 `outcome.reason` / `cross.reason`
    （`runner.ts:342-356`），会是「回读不匹配」之类，**不是 `cancelled`**；
    `cancel()` 只改**运行级**的 `status.reason`（`service.ts:202`），**不改 step 级**。
  - **R4 没有落点** —— `AuditRow` 里没有「清理」这个 action 的命名约定，
    `runner.ts` 里的 action id 形如 `workflow:<pack id>:<step id>`（`runner.ts:270/403/500/686`）
    → 清理行该叫什么，没写。
- → **每一条规则都要在 §五 有一行**（已实现 / 待做 / 不做）。
  这正是 `docs/37` V3-I8 说的「§〇 的『已实现』清单与代码对不上」的**同型复发**
  —— 提案 §〇 的表格已经写得很克制了，但 §五 没有守住。

### I-3 · R3 的「变了没有」判据**不够**，而且在**最常见的**取消场景里取不到「传输后」那次快照

三个漏：

1. **同秒同大小**：ext4 的 mtime 常见精度是**秒**；同一秒内被换成同尺寸的文件
   → 「没变」→ **不清理** → **半截文件留着**（这恰是 R1 要治的）。
2. **TOCTOU + 认不出主人**：传输期间**用户**把 `/opt/x` 换成了自己的好文件
   → 「变了」→ **宿主把它删了**。快照证明的是「文件变了」，**不是「这一步改的」**。
3. **取不到「传输后」快照时怎么办，提案没写** —— 而「板子正忙 / 连接断了」
   正是**最常见的**取消原因（提案 §三·3.5 自己的场景）→ 契约必须说清「取不到 → 删还是留」。

**更简单、而且同样安全的判据（我的建议，替换 R3）**

> **「目的地在传输前不存在」就是最强的判据** —— 那它**一定是**这次传出来的。
> → 契约写三档：
> - 目的地**原本不存在** → 这次要么成功、要么是半截 → **归宿主管**（成功则留着，失败/取消则清或改名留档）。
> - 目的地**原本存在** → **默认不动**（宁可留一个被截断的旧文件，也不删用户的东西），
>   只有「**能确定是这一步写的**」才清。
>
> 这个判据**不需要「传输后」快照** → 不受「取不到快照」的影响 → **比「大小+mtime」更简单也更安全**。

### I-4 · `current` 的语义有洞：**停下等确认的那一步**恰恰是界面最需要显示的那一步

- P1 说 `current` = 「**在飞的那一步**」，并说「在飞的那一步**不在** `stages` 里 ✓」。
- 但 `awaiting_confirmation` 时**没有任何东西在跑**（`runner.ts:196-203` 停了），
  那一步的 `ok` 也「还没定」→ 按 P1 的字面定义，`current` 应该是 **`null`**
  → 界面在「**等人点头**」这个最需要知道「是哪一步在等我」的时刻，**看不到是哪一步**。
- 处置：
  - `current` 的定义改成「**当前这一步**（正在跑 **或** 停下等人点头）」；
  - `null` ⟺ 运行**已结束**（`done`/`failed`/`cancelled`）；
  - 并且说清 **`current` 是活快照、会变**；`stages` 是**只增不改**、幂等（`spec/05:333` §八·4）
    → **两者的幂等性不同**，P5 只说了后者，契约要分开写。

### I-5 · `current.at` 的口径会与 `spec/04` §四 的通用约定打架

- `docs/spec/04-mcp-tools.md:552`：「时间：毫秒时间戳，UTC。**`at` = 本次采样完成的时刻**，不是广播时刻」。
- P2 说 `current.at` = 「这一步**开始的**时刻」→ **同一个字段名，两种口径**。

## 五 · 逐条回答提案的七个问题

### Q1 · 取消该不该给 agent / 卡片？—— **不给**（同意提案），但**理由要换**

- 提案的理由（「取消看着无害，但会留下半截文件 → 判断归人」）**不成立**：
  「留下半截文件」正是**提案三要治**的东西 → 如果 R1 成立，取消就不再有「不无害」的后果。
- **真正的理由是权限边界**：「批准」与「取消」是**同一族**判断 ——
  「行不行」与「停不停」都是**关于这次执行要不要发生**的判断。
  既然「行不行」**不给 agent**（ADR-D34-4 / `spec/04` §2.4.1），
  「停不停」也不该给 → 否则 agent 就有了「**自己决定不干**」的通道
  → 「人点头」这条链出现一个**绕过它的旁路**（agent 取消 → 人根本不用点头 → 运行结束）。
  而且**取消是「少做事」，看着最无害** —— 恰恰是这种无害的旁路最容易被顺手加上。
- **卡片也不给**（同意），但**理由不同**：卡片是**用户在看的界面**；
  给卡片一个「停」按钮 = 把宿主的状态控制搬进沙箱，而卡片权限是**逐方法**授权的
  （`spec/03` §7.7）→ 「停一次别人的运行」**不在任何权限项里** → 要给就得新增一条权限，
  而**新增权限不该由这条增量顺手加**。
- **但必须补一句**：既然 agent 与卡片都不能取消，**人怎么知道该去取消**？
  → **P1/P2 的 `current` + `at` 就是那盏灯**。
  → 所以：**不给**，但**必须先把 `current` 做好**，否则「不可取消」就变成「**不可观测**」。

### Q2 · `current` 用附加字段 vs 改 `stages[].ok` 的类型 —— 有第三个更好的形状吗？会跟 `spec/04` 现有消费者打架吗？

- **同意「附加」**，但**理由要换**：不是「不破已有消费者」（没有消费者，M-2），
  而是「**改类型会让 `ok` 变成三态**（`true`/`false`/`null`）——
  而 `ok` 在契约里是**判定**（`spec/05` §七「两个事实、两行账」；`spec/04` §2.4 的 `verified` 语义）。
  **「还没定论」不是 `ok` 的第三种取值**，是**另一个维度**」。
- **第三个更好的形状？有，但不是换字段名，是换承载物**：
  ① **首版仍用 `current`**（简单、够用），但形状定成
     **`current: { stepId, kind, at }`（去掉 `role`）**（C-4）。
  ② **另一个真正不同的第三个**：`stages` 保持只增不改，**另开一条 `events`**
     （追加式事件流：`{ at, type: 'step_started' | 'step_done' | 'cancelled' | 'cleaned', stepId }`）。
     它天生只增不改（满足 §八·4 幂等），能表达「开始了/完成了/取消了/清理了」**四件事**
     （`current` 只能表达「现在在哪」），而且**取消 + 清理 + 进度**三件事都能进同一条流。
     代价：`events` 与 `stages` 是**两份重叠的账**（谁定论了？）→ 首版复杂度高。
  ③ **我的建议**：首版按 ① 走；**取消与清理事件记进审计**
     （审计是永久的、逐行的 —— `spec/05` §七·2 第三本账），
     等真的有「进度百分比」的需求再上 ②。
- **会不会跟 `spec/04` 现有消费者打架**：**不会**（**没有消费者**，M-2）；
  但会跟 **v3 的卡片侧投影决定**打架 —— **那才是真冲突**（C-4）。

### Q3 · §三·3.5：传输成功但回读失败 → 清理还是不清？（**给准话**）

**准话：不是 A/B 二选一，是三档；而且「退出码不可信」这句话在契约里应该被彻底赶出去。**

**① 回读失败 → 不清理**（同意提案的 B）。理由：回读失败只说明「**没验成**」，
不说明「**没传成**」；删掉一个可能是好的文件，比留一个半截文件更坏。
**并且要在时间线上说清楚**：这一行是「**传了，未验成**」——不是一个 `ok:false` 的「失败」
（M-5·e 就是这个状态，它现在**没有名字**）。

**② 「传输命令的退出码不可信」在契约里怎么表达 —— 这是提案要我给准话的地方：**

> **不要在契约里写「退出码不可信」。** 契约不该描述传输工具的退出码语义
> （`scp` / `rsync` / `dd` / base64-over-shell 各不一样，那是实现层）。
> 契约该写的是**结果的三档**，而不是**原因**：
>
> | 传输步的结果 | 判据（**不是退出码**） |
> |---|---|
> | `transferred`（传成了） | 目的地有这次传的完整产物 |
> | `partial`（传了一半/传坏了） | 目的地**原本不存在**、现在存在一个**不完整**的东西 |
> | `not_transferred`（一个字节都没到） | 目的地**与传输前完全一样** |
>
> → **判据是「目的地状态」，不是退出码。传输工具爱用什么退出码都行 —— 契约不认它。**
> 「退出码」在契约里只保留**一个**作用：**它是「传输命令失败」的一个信号，不是判据**。

**③ 但我要给 B 加一条尾巴**：B 有个洞 —— **回读失败与「传输只写了一半」是同一种观测**
（板子正忙 → `test -f` 跑不成；但板子上那个文件**也可能是半截的**）。
→ **B 必须配一条「拿不准时的默认动作」**。
**我的裁定：拿不准 → 不删**（宁可留半截，不删用户的文件），
**并在时间线上明说「目的地有一个未确认的文件」**（让人能自己判断）。
**唯一的例外**：目的地**原本不存在**（传输前没有）而现在存在
→ 那它**一定是**这次传出来的 → 无论回读成不成功，**都归宿主管**（删掉 or 改名留档）。

**④ 一句话给用户**：**清理只在「能确定那是这一步的半截产物」时做；其余一律不删，只记账。**
这比提案的 A/B 准，也把「退出码不可信」从契约里彻底赶出去。

**⑤ 与 R3 的关系**：§三·3.5 的判据正好可以**替换** R3 的「大小+mtime 快照」
（见 I-3 的「更简单的判据」）：**「目的地原本不存在」** 就是那个最强的判据。

### Q4 · R3 的「变了没有」判据够不够？有没有被绕过或误判的可能？—— **不够**，三个漏（I-3）

- **绕过**：传输期间**别人**改了那个文件 → 「变了」→ 被删 → **删掉的是别人的东西**。
- **误判**：同秒同大小 → 「没变」→ **半截文件留着**（R1 失守）。
- **取不到**：最常见的取消场景（板子正忙/连接断了）里**取不到「传输后」快照** → 提案没写怎么办。
- **更简的同安全性写法**：见 I-3 与 Q3·⑤ → **「目的地原本不存在」→ 归宿主管；「原本存在」→ 默认不动。**

### Q5 · 清理命令不过危险地板（R6）—— 会不会变成「宿主替包删文件」的后门？—— **会**（C-3 / I-9 / M-4）

三点：

1. **后门是真的**：`to.path` 是**包给的**、值模式**不编码**、批准时人只看到**模板**
   → 人**看不到真实路径** → 包可以把 `to.path` 写成 `/etc/xxx` → R2 让宿主去删它
   → R6 又不让它过地板、不过确认 → **一条「人没看过的路径」上的删除，由宿主执行，无确认**。
2. **但它不是「任意删除」**：只在「这一步动过它」时才删 → 而传输命令本来就要写那个路径
   → 权限上**没有新增写权限，新增的是「删」** → **后门的严重度 = R3 的强度**
   → **R3 弱 + R6 强 = 真的后门**（→ I-3 的新判据把 R3 变强，后门随之变小）。
3. **R6 的理由是假的**（M-4）：地板表里只有 `rm -rf /` → `rm -f /opt/x` **根本不命中**
   → 「走地板会拦下来」不成立。
   **结论可以保留，但必须补 R6-a（编码）与 R6-b（只许一个普通文件 + 路径逐字符相等）**，
   并且在 `spec/05` §七 里把「宿主自己的写」与「包给的写」分开（I-9 / T4）。

### Q6 · 取消后要不要回滚？—— **不回滚**（同意提案），但理由要更硬，且**要补一条**

- 理由（比提案多一条）：回滚需要**每个写步声明自己的逆操作** →
  **逆操作是另一条命令** → 它自己也要过地板、也要人确认 → **回滚的代价大于收益**，
  而且**回滚本身可能失败** → 回滚失败 = 状态更乱。
  → 「不回滚」不是「暂时没空做」，而是「**契约层没有回滚这个概念，且不宜有**」✓。
- **但「不回滚」≠「不说明白」**：契约要规定「取消/失败后，**必须能看出机器现在处于什么状态**」。
  尖兵 Q3 已经给了原型：「deliver 成功但 load 失败 → 板子处于『**文件在、没生效**』」
  —— 这正是 `spec/02` §5.6 的「文件存在 ≠ 文件生效」。
  → **「清理」（删半截文件）与「报告」（说清留了什么）是两件事**：
  R1/R4 覆盖前者，**后者没人写** → **缺一条**（Important 级，我列在 §八 的清单里）。

### Q7 · 这条增量要不要并进计划 7？—— **不并**（同意提案），但理由要更硬，且**有一条依赖**

- **不并的理由（比提案硬）**：计划 7 实现的是**入口**（`cockpit.workflows.*` + `run_workflow` /
  `workflow_status` / `confirm_workflow`）；这条增量改的是**契约语义**。
  并在一起 = 一次改动同时动契约与入口 → **评审的边界就没了**（契约错还是实现错分不清）
  —— 这正是 `docs/21` §三·C-2「一次成文、一次评审、留痕」要防的。
- **不并的代价与依赖**：计划 7 一旦开工，**卡片侧的形状就被实现了** →
  **V3-M7 必须先关掉**（否则计划 7 会把「全泄」实现出来）→ 而 P4 恰好要「统一形状」
  → **顺序必须是：先关 V3-M7 → 再定 P1/P4 → 才能开工计划 7**。
- **实现分三批**（与 §五 的 6 条对得上）：
  ① 取消真停（HAL 语义 + **服务层状态机修正**（C-1））
  ② 在飞步（时间线边跑边填 + `current`）
  ③ 残留清理（快照/判据 + 清理 + 审计）
  → **③ 依赖 ②**（没有 `current` 就不知道「在飞的是哪一步」，清理无从挂起）。
