## 一、为什么有这份文档

计划 3 之后，「读数会自己动」这件事已经成了。剩下的路只有一条：**把读数装进卡片**（M5），
再让卡片能**写板子**（M6）。

这两件事的技术难点不在「画界面」和「发命令」，而在**卡片与宿主之间的那条边界**——
一张卡片是 agent 写的任意网页，它跑在用户的工作台里，读得到板子上的数据，还可能写板子。
这条边界一旦设计错了，后面全是补丁。

契约 §六 明写「卡片跑在 iframe 里……**本轮规格不锁这一点**」——
所以这是 M5 必须自己做的技术决策。Codex 用一次 **Electron 34 尖兵**把它从推测变成了事实
（`docs/superpowers/spikes/`），本文是**把那份实测固化成设计**，并补上它没覆盖的部分。

## 二、目标 / 非目标 / 反目标

### 2.1 目标

1. **一张卡能安全地跑起来**：读它要读的 tag，不碰别的，不联网，不搞垮工作台。
2. **卡片即文件**：agent 改文件 → 热插拔 → 立刻看到效果（AI 迭代回路不断线）。
3. **卡片与宿主之间有一条可验证的边界**：每一条隔离承诺都有**机械可判**的判据。
4. **控制面有注入防线**：`--model 'x; reboot'` 只能是参数值，不是命令。
5. **为 M7（MCP）与 M8（多板）留好接口**：卡片能力是 main 里的**一个服务**，不是 renderer 里的逻辑。

### 2.2 非目标（本部分不做）

| 不做 | 归谁 |
|---|---|
| `cockpit.actions.invoke` 的**写侧**实现 | M6（本文含 M6 的设计，执行另开计划） |
| **布局**（`react-grid-layout` + Slot + 内置卡迁移 + 「第一张卡能拖拽」） | **M5b**（2026-11-14 拍板：M5 只做卡片宿主与沙箱，**布局单独一期**） |
| MCP server | M7 |
| 多板并行、多张卡同时看不同板 | M8（v1 一条连接上下文） |
| 卡片引入 npm 依赖 | 永远不做（`script-src 'self'` 决定，ADR-D14） |
| `script` 逃生舱的推脚本机制 | M6 |

### 2.3 反目标（**做成了也算失败**）

| 反目标 | 为什么它是失败 |
|---|---|
| **卡片能联网，但「我们尽量不写会联网的卡」** | 一张 AI 写的卡如果能随便联网，它就能把用户板子上的数据发到任何地方。**承诺必须是机制，不是善意** |
| **卡片用 `window.parent.cockpit` 直接调宿主能力** | 那就把卡片权限模型（`permissions.read` / `permissions.write`）整个绕过了 |
| **CSP 违规只是「记录一下」** | 记录不阻断 = 没有边界。**违规要挡住，而且要能看见** |
| **控制面「先能跑通再说」** | `spec/02` §4.6 的参数编码是**注入防线**。它不是「顺手写的工具函数」，它的单测必须**先于**动作执行代码存在 |
| **卡片状态显示「状态不对就不显示数值」** | 契约 §2.1 特意让 `stale` / `error` **保留旧值**。藏掉旧值 = 面板上那个数看起来是真的 |
| **安全过滤放在 renderer** | 「renderer 只画」是铁律；而且**一张卡的 bug 就能泄漏另一张卡的数据** |

## 四、事实与发现

### 4.1 【更正】沙箱与 CSP —— 实测结论（🟢 实测）

**我初稿的推演（错的）**：不给 `allow-same-origin` → 文档处于不透明源 → CSP 的 `'self'`
匹配的是文档所在源 → 不透明源与任何源都不同源 → `'self'` 什么都不匹配 →
按契约 §六 + §6.1 实现，**卡片自己的 `card.js` 与 `style.css` 全被挡住，一行脚本都跑不起来**。

**尖兵实测（🟢 对的）**：

| 实测项 | 结果 |
|---|---|
| `script-src 'self'` 在 `sandbox="allow-scripts"`（不透明源）下 | **照样匹配**——卡片的 `<script type="module" src>` 与**相对 import** 都能跑 ✅ |
| 协议 handler 的 MIME | **必须按扩展名给对**（`.js` → `text/javascript`），否则 module script 直接被拒（"Strict MIME type checking is enforced"） |
| `fetch` / `WebSocket` / `<img>` 外传 | **全被 CSP 拦掉** ✅（`new WebSocket()` / `new Image()` **构造时不抛错**，CSP 在连接/加载时才拦 → 卡片不能靠 `try/catch` 判断「有没有网」） |
| 卡片读 `parent.document` / `window.top` | **SecurityError** ✅ |
| `localStorage.setItem` | 不透明源下**抛 SecurityError** ✅（与契约 §6.2 的前提一致） |
| Electron 的 preload | **不进子 iframe**（主帧有 `window.cockpit`，卡里 `undefined`） |
| `MessagePort` 转进不透明源 iframe | ✅ **可用** |
| `event.source` 认人 | ✅ **准确**（不透明源下 `event.origin` 是 `null`，**不能靠 origin**） |

**结论**：**契约 §六 + §6.1 照字面就是对的，不用改。**
「不透明源让 `'self'` 失效」是一个看起来很合理的推论——**幸好做了实测**。
（同一个坑的另一个旁证：`file://` 页面上的 `'self'` 确实是废的——但那是因为 `file:` 的
URL 本身就是**本地 scheme**，origin 是 opaque 的；`cockpit://` 注册成 `standard` 之后
**URL 的 origin 是真的**，CSP 的 self-origin 取的是**响应的 URL origin**，不是文档被沙箱后的源。）

**尖兵没证明、必须重验的一条**：契约 §6.1 承诺「CSP 违规进卡片运行时日志」。
尖兵的宿主处理器是 `(_e, _lvl, msg) => out('[console] ' + msg)`，
而 **Electron 25 起 `console-message` 的签名已改成 `(event, details)`**——
仓库的 Electron 34.5.8 里 `msg` 会是 `undefined`；尖兵贴出的那三行违规文本**没有 `[console]` 前缀**，
说明它们不是宿主捕获到的。

> ### ✅ 这一条已实测（2026-11-14 · ADR-D29 §七）——而且**结论与尖兵相反**
>
> 真机（Linux Electron 34.5.8）量出来的**不是**「签名读错了」，是**根本没有归属信息**：
>
> | 违规类型 | `console-message` 的 `sourceId` | 能归属到卡吗 |
> |---|---|---|
> | `img-src`（外链图片） | 卡片的 URL | 能 |
> | `connect-src`（`fetch` 外网） | **空串** | **不能** |
> | `script-src`（内联脚本） | **空串** | **不能** |
>
> 而契约承诺的「agent 能看到**这张卡试图联网**」正是 `connect-src`
> → **恰恰是 `console-message` 抓不到的那一类**。
>
> → 改用**卡片文档里的 DOM 事件 `securitypolicyviolation`**（宿主注入
> `__host/csp.js` 监听）→ **实测三类违规全中**（`captured=e2e-card`）。
> → `console-message` 那条路**整个删掉**（半通不通比不通更糟）。

### 4.2 卡片之间必须互不可见 → 沙箱**不给** `allow-same-origin`（🟢 实测）

尖兵跑了两个变体：

| 变体 | `localStorage` | 卡片之间 |
|---|---|---|
| A `sandbox="allow-scripts"` | **SecurityError** | **每个 iframe 一个独立的不透明源 → 互不可见** ✅ |
| B `sandbox="allow-scripts allow-same-origin"` | 可用 | **所有卡共享 `cockpit://card` 一个源 → A 卡能读 B 卡的 localStorage** ✗ |

契约 §6.2 承诺「每卡一个命名空间、**互不可见**」——**只有变体 A 能兑现**。
所以：**沙箱不给 `allow-same-origin`**，契约 §六 照原样。

> **初稿在这里提过「给每实例一个真源」（变体 B 的加强版）。撤回**：变体 A 已经在隔离上
> **严格更强**（不透明源连 `location.origin` 都是 `null`），而且**不需要动契约、
> 不需要屏蔽 localStorage**。

### 4.3 preload 进不了 iframe → bridge 是必须的（🟢 实测）

主帧有 `window.cockpit`，两张卡里都是 `undefined` → **`contextBridge` 这条路不存在**。
所以 API 必须由**宿主注入**：协议 handler 在响应入口 HTML 时插一个
`<script type="module" src="cockpit://card/…/__host/bridge.js">`（同源，`script-src 'self'` 允许，
且**卡片改不了**——它是宿主写的响应）。

### 4.4 权限过滤点没定 —— 定在 **main**（设计判断）

契约 §7.1 说「运行时保证：只返回 `permissions.read` 里列出的 tag」，但没说「运行时」是 main 还是 renderer。

| 放哪 | 后果 |
|---|---|
| renderer | 违反「renderer 只画」；**安全过滤落在 renderer**——一张卡的 bug 就能泄漏另一张卡的数据；MCP 在 main 也拿不到同一套过滤 |
| **main ✅** | 过滤与授权**一处做**；MCP 与卡片共用同一条服务路径 |

→ **每张卡一个会话（权限 + tag 服务 + 动作执行 + 审计）由 main 持有**；
renderer 只负责「建 iframe、转发握手、转发请求与响应」，**不做任何权限判断**。

### 4.5 卡片 API 没有能力发现 → 加 `cockpit.capabilities()`（设计判断）

MCP 侧有 `list_capabilities()`（`spec/04` §2.1），**卡片侧没有**：
`spec/03` §7.7 的方法是**封闭全集**，卡片**无法问**「宿主支持哪些方法 / 当前连的是谁 / 哪些 tag 可读」。

**为什么这是扩展性的瓶颈**：「AI 可造卡」是这个产品的核心主张。agent 写卡片时**必须知道宿主现在支持什么**——
现在它只能硬编码假设「`cockpit.tags.get` 一定在」，宿主版本一换，
卡片只能靠 try/catch 猜，而**卡片跑在沙箱里，猜错了没有任何提示**。

→ 给卡片 API 加 **`cockpit.capabilities()`**（§6.3 定义了载荷）。
它是**对称**的（与 MCP 侧同形），也是**让卡片 API 能演进的前提**。

### 4.6 布局要认「槽位」不认「实现」（设计判断）

`docs/04` §8 说内置卡（终端、文件浏览器、日志、目标切换器）**与用户卡片同一套布局**。
但内置卡是**宿主的 React 组件**，用户卡是 **sandbox iframe**——
焦点 / 键盘 / 滚动 / 缩放 / 右键菜单**行为不一致**，热插拔、崩溃隔离、CSP **只对 iframe 卡有意义**。

→ **布局只认「槽位」**：

```
Slot { id, kind: 'builtin' | 'user', cardId?, connectionId?, layout }
```

`kind: 'builtin'` → 宿主 React 组件；`kind: 'user'` → sandbox iframe。
布局引擎只管 `Slot` 的位置与尺寸。**这样 M8 的 promote / 全屏 / 布局分享不必再动布局系统。**

> **本节属 M5b（布局期）**：2026-11-14 拍板「**M5 不做布局**」——
> 布局（`react-grid-layout` + Slot + 内置卡迁移）单独一期。
> 本节保留设计，**实现排在 M5b**。
> 「哪些 builtin 卡迁进网格」也随之延到 M5b 一起定。

### 4.7 宿主外壳自己没有 CSP（🟢 实测）

尖兵跑起来 Electron 直接报 Security Warning——`index.html` **一个 CSP 都没有**。
但**不能照抄卡片的 CSP**：生产环境外壳走 `win.loadFile()`（`file://`，origin 是 opaque）
→ **`'self'` 匹配不到任何东西 → 外壳自己的 JS/CSS 被自己的 CSP 挡掉 → 白屏**；
开发环境走 Vite dev server → `script-src 'self'` 挡掉 Vite 注入的 inline module preamble，
`connect-src 'none'` 挡掉 HMR 的 WebSocket。

→ **做法（我的判断）**：

| 环境 | 外壳怎么加载 | 外壳的 CSP |
|---|---|---|
| **生产** | 改走 **`cockpit://app/`**（同一个协议 handler，`cockpit://app/index.html`） | `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self' data:; connect-src 'self'; object-src 'none'; base-uri 'none'; frame-src cockpit:` |
| **开发** | 仍是 `http://localhost:5173` | 同一份，但 `script-src 'self' 'unsafe-inline'`、`connect-src 'self' ws://localhost:*`（给 HMR） |

**顺带的好处**：生产的外壳有了一个**真源** `cockpit://app`，
而卡片在 `cockpit://card/...` → **不同源**（比现在的 `file://` 不透明源更好推理）。

> ### ⚠️ `frame-src` 必须是 `cockpit:`（2026-11-14 修正 · ADR-D29）
>
> 原表里写的是 `frame-src 'none'`——**照抄了卡片的 CSP**，而这张表是设计基线，
> 计划和实现都照着它做 → **生产环境一张卡片都装不上**，
> 症状只是「卡片区一片空白」，**不报任何错**。
>
> | | scheme | host | origin |
> |---|---|---|---|
> | 外壳 | `cockpit:` | `app` | `cockpit://app` |
> | 卡片 | `cockpit:` | `card` | `cockpit://card` |
>
> **两个不同的源**（host 不同）→ 外壳的 `'self'` **盖不住卡片**；
> 而 CSP 的 host-source 语法只认 http/https/ws/wss/ftp → 只能用 **scheme 源** `cockpit:`。
>
> 实现：`src/main/shell-csp.ts`（单独一个文件，因为 `main/index.ts` 引入 Electron，**单测进不去**）；
> 判据：`tests/unit/shell-csp.test.ts`。

### 4.10 校验器要分「不合法」与「未验证」（契约 §九 规则 5）

规则 5：`permissions.write` 里每个动作 id 在**当前连接的板型包**里存在
（**连不上板时跳过此检查，标注「未验证」**）。

→ 校验器有**两种模式**：连上板（full）与连不上（degraded）。
返回形状**照契约 `spec/04` §2.3**：`{ ok, errors, warnings, resolved }`——
**「未验证」进 `warnings`**（不是 `errors`），并在 `resolved` 里照常给清单。
**不许自造 `issues[]` / `unverified[]` 字段名**（那会变成第二套方言）。

## 五、方案比较（已选）

### 5.1 卡片的 iframe 沙箱与源

| 方案 | 做法 | 实测 | 结论 |
|---|---|---|---|
| **A ✅ 选定** | `sandbox="allow-scripts"`（不透明源），契约 §六/§6.1 **一字不改** | 🟢 隔离成立、CSP 生效、ES module 与相对 import 能跑、卡片之间互不可见、localStorage 抛 SecurityError | **不动契约** |
| B | 每实例一个真源 + `allow-same-origin` | 🟢 也能隔离，但**所有卡共享一个源 → A 卡能读 B 卡的 localStorage** | 要动契约三处，且**不比 A 强** |
| C | 保持不透明源 + CSP 改 nonce | — | module import 挂不上 nonce → ADR-D14 报废 |

**选 A 的理由**：**契约不用改**是最大的收益——断网这条承诺（§6.1 逐条原文）一个字不动，
ADR-D14 的「免构建 ES Module」保住，卡片之间隔离**更硬**（连 `location.origin` 都是 `null`）。

**URL 形状**：`cockpit://card/<instanceId>/<相对路径>`
——**沿用 ADR-D4 与契约 §6.1 的字面**（host 是 `card`，实例 id 在路径里），**契约一个字不用改**。
协议处理器只放行**自己登记过的实例**（实例 id 是 UUID，不可猜）→ 猜到别人的路径也拿不到。

### 5.2 串口独占的产品口径

| 方案 | 行为 | 代价 |
|---|---|---|
| **A ✅ 选定** | 串口候选因端口被占而失败 → **跳过它，继续试下一个**；面板显示「串口 COM3 被终端占用」；运行时按退避重试 | 面板的连接上下文可能在 adb/串口之间切换（§6.3 说明怎么处理） |
| B | 终端优先：终端标签开着时运行时完全不碰串口 | 只有串口、没有 adb 的板子会一直没有数 |
| C | 维持现状，只把错误显示清楚 | 同上；且一次失败的串口尝试可能占着端口不放，把能用的 adb 挤掉 |

**选 A 的理由**：这个产品的主线是「看板子的读数」。**一根被占用的串口不该让面板死掉**。
「看得见的失败」是底线，不是目标。
**注意真实顺序**（§4.9）：adb 先试，所以这条主要救**只有串口**的板子。

### 5.3 M5 / M6 的切分

| 方案 | 内容 | 代价 |
|---|---|---|
| **A ✅ 选定** | M5 = 卡片框架 + 只读卡；M6 = 动作执行器 + 控制卡 | 两期 |
| B | 一次做完 | `spec/02` §4.6 参数编码会被赶工——它是**注入防线**，最不该赶的就是它 |
| C | 先 M6 | 卡片框架是控制卡的地基，顺序反了 |

**切分随之再分一次**（2026-11-14 拍板 Q1「M5 不做布局」）：
**计划 4 = M5（卡片宿主与沙箱）+ M5b（布局）**；**计划 5 = M6（控制面）**（§九）。

### 5.4 卡片通道由谁建（**这一条初稿是错的**）

初稿写「main 创建 `MessageChannel` → 经 IPC 转交 renderer → renderer 再转进 iframe」。
**过不了**：Electron 的 `contextBridge` 传递的类型是**白名单**，`MessagePort` **不在表内**
→ preload 里 `ipcRenderer.on(...)` 收到的 `event.ports[0]` **无法交给页面 JS**。
（现有 `src/preload/index.ts` 正是走 contextBridge。）

| 方案 | 谁建端口 | 后果 |
|---|---|---|
| **A ✅ 选定** | **页面（renderer）建 `MessageChannel`**，端口在页面与卡片之间；**main 只持有会话与权限** | 尖兵**已验**这条路可行。页面的角色是「卡片帧的经纪人」（转发），**但不做任何权限判断**——权限在 main 判 |
| B | preload 当经纪人（preload 有 DOM 访问权，能自己 `postMessage` 端口） | preload 从「白名单代理」变成「卡片帧经纪人」；且 isolated world 里 `event.source` 与页面侧的 `iframe.contentWindow` **不是同一个包装对象**，`===` 比对不可靠 |
| C | main 建端口、跨 IPC 转移 | **不可实现**（见上） |

**选 A 的理由**：唯一被**实测**跑通的形状；代价是页面能看到卡片请求的载荷——
但页面是**可信**的，而**权限判据在 main**，所以这条不产生安全洞。

## 六、定下来的设计

### 6.1 卡片的装载（协议与 iframe）

**协议**：`cockpit://`，注册为 privileged scheme
（`standard` + `secure` + `supportFetchAPI` + `cspEnabled`）——`docs/04` §6.1 已定，尖兵已验。

**URL**：`cockpit://card/<instanceId>/<卡片目录内的相对路径>`

| 项 | 规则 |
|---|---|
| `instanceId` | UUID v4，**每个卡片实例一个**，由 main 生成并登记（`instanceId → {cardId, connectionId, dir, manifest, permissions}`）。**不可猜** |
| 路径 | 拼到卡片目录后 **normalize + 校验前缀**；越界 → **403**。防护要挡：`..`、绝对路径、符号链接、`%2e%2e`（尖兵**没测**这一条，**M5 必须测**） |
| 未登记的实例 | **404**（页面自己编一个 URL 也拿不到东西） |

**协议处理器**（main，`src/main/cards/protocol.ts`）：

1. scheme 必须是 `cockpit`；host 必须是 `card`；路径第一段必须是**已登记的 instanceId**；否则 404
2. 解析相对路径 → 定位卡片目录内的文件；越界 → 403
3. **MIME 按扩展名给对**（`.js` → `text/javascript`；`.css` → `text/css`；`.html` → `text/html`；
   `.json` → `application/json`；图片按型）——**给错 module script 直接被拒**
4. **入口 HTML**：注入 **CSP 响应头**（契约 §6.1 原文，**一字不改**）+ 注入 **bridge `<script>` 标签**
5. `__host/bridge.js`：**由 API 注册表动态生成**（§6.3）
6. 其它文件按 MIME 返回，不注入 CSP 头（CSP 只对 document 有意义）

**bridge 注入点**：优先插在 `<head>` 之后；没有 `<head>` 就插在 `<html>` 之后；
再没有就**前置到文档开头**。**失败时前置**（fail-closed）。
**必须排在卡片自己的脚本之前**——卡片脚本一跑就该看到 `window.cockpit`。

**iframe**：

```html
<iframe sandbox="allow-scripts" src="cockpit://card/<instanceId>/index.html">
```

`sandbox` **只给 `allow-scripts`**（不给 `allow-same-origin`，见 §4.2；也不给
`allow-top-navigation` / `allow-popups` / `allow-forms` / `allow-modals` / `allow-downloads`）。

**宿主侧再堵两道**：

| 措施 | 挡什么 |
|---|---|
| `will-frame-navigate`：卡片 iframe 不得导航到自己的 URL 之外 | 卡片把自己导航到别的实例（别的实例 id 不可猜，且协议处理器只放行自己登记的实例 → 双保险） |
| 页面的全局 `message` 监听：**只认已登记实例的 `event.source`** | 别的页面冒名发消息 |

### 6.2 桥接协议（握手 → 端口转移 → 私有通道）

**实测结论**：preload 进不了 iframe（🟢）、`MessagePort` 能转进不透明源（🟢）、
`event.source` 认人准确（🟢）、不透明源下 `event.origin` 是 `null`（🟢，所以**不能靠 origin**）。

```
① 卡片里的 bridge 脚本（同源，由 cockpit:// 提供）发
   parent.postMessage({type:'cockpit-hello', instanceId}, '*')
② 页面收到：按 event.source 认出是哪个 iframe → 取出它绑定的 instanceId
   → 与 hello 里带的 instanceId 比对（★ 见下）
③ 页面创建 MessageChannel → e.source.postMessage({type:'cockpit-port'}, '*', [port2])
   → port1 留在页面里（端口不跨 IPC，绕开 contextBridge 的限制）
④ 页面把 instanceId 告诉 main（「实例 X 就绪」）→ main 建会话（权限 + tag 服务）
⑤ 卡片侧 bridge 收到端口 → window.__cockpitReady = true
⑥ 此后：卡片在私有端口上发请求 → 页面转给 main（普通数据，走 IPC）
   → main 按权限判 → 回答案 → 页面转发到端口 → 卡片
```

**★ 第 ② 步为什么必须比对 `instanceId`**：只靠 `event.source` 认人的话，
**卡片 A 把自己导航到卡片 B 的 URL**（若它猜得到 B 的实例 id），
加载的就是 B 的代码，但 `event.source` 还是同一个 iframe → 宿主会把它当成 A →
**B 的代码借 A 的权限发消息**。
协议处理器只放行自己登记过的实例 + bridge 里带着实例 id + 宿主比对 → **三道**。

**为什么不需要 nonce**：卡片拿不到别的卡的 window 引用 → **冒充不了**（🟢 实测）。
认人靠 `event.source`（**谁发的窗口**）+ 上面那个实例 id 比对（**是哪一个实例**）。

### 6.3 卡片 API（读侧，M5）

**一个注册表，两处使用**：`src/main/cards/api-registry.ts`

```
每条 API 声明：{ name, permission: 'read' | 'write' | 'none', handler }
```

- **宿主侧**：注册表 → handler 表（main 进程里执行，权限过滤在这一层）
- **卡片侧**：注册表 → **生成 bridge 脚本**（协议处理器动态产出）→ 卡片拿到 `window.cockpit`

**收益**：卡片看到的 API 与宿主实现的 API **不可能对不上**。
契约 §7.7 说它是唯一定义处——那就让它真的只有一处。加一个新 API 只改注册表一处。
（尖兵的 bridge 是手写字符串——那是尖兵，不是产品。）

**M5 实现的 API**：

| 方法 | 权限来源 | 返回 | 备注 |
|---|---|---|---|
| `capabilities()` | 无（只读） | `{ apiVersion, methods, connection, tags }` | **新增**（§4.5） |
| `tags.get(name)` | `permissions.read` | **状态化的值** | 契约 §7.7 的例外：**不返回 `{ok:false}`**，读不到是 `{value:null, status:'unavailable', reason:…}` |
| `tags.subscribe(name, cb)` | `permissions.read` | **退订函数** `() => void` | 契约没规定返回值 → 用退订函数最自然（与 `TagStore.subscribe` 一致） |
| `tags.subscribePattern(pattern, cb)` | `permissions.read` | 退订函数 | 实例出现时逐个推 |
| `tags.list()` | `permissions.read` | `TagReading[]` | 只列**被权限覆盖**的 tag |
| `degradation()` | 无（只返回本卡的） | 缺失/降级的 tag + 原因 | |
| `storage.get/set/remove/keys/clear` | 无（限本卡命名空间） | | §6.5 |
| `log(level, message)` | 无 | | agent 的「自测眼睛」 |
| `notify(title, body)` | 无 | | **不能代替动作确认** |

**M6 补**：`actions.invoke(id, params)`。
**M5 的 bridge 里没有 `actions.invoke`** → 卡片调它得到
`{ok:false, reason:'unknown_method'}`（reason 词表见 §七 的契约改动 1）。
**`capabilities().methods` 列的是「本 build 实际有的」**——否则这个扩展性地基是空的。

**`capabilities()` 的载荷**（我的判断）：

| 字段 | 内容 |
|---|---|
| `apiVersion` | 契约版本（`devboard/v1`） |
| `methods` | **本 build 实际实现的方法名数组**（M5 的九个；M6 后加 `actions.invoke`） |
| `connection` | `{ label, transport }`——**不含 `connectionId`**（契约 §7.8：「卡片代码里没有 `connectionId` 这个词」） |
| `tags` | **本卡可读**的 tag 清单（按 `permissions.read` 过滤后的） |

**权限过滤规则**（在 main）：

| 操作 | 规则 |
|---|---|
| `tags.get(name)` | `name` 必须被该卡 `permissions.read` 的**某一项覆盖**（模式覆盖判定，契约 §2.2）→ 否则 **`{value:null, status:'unavailable', reason:'not_found'}`**（契约 §7.7 的形状；`not_found` 也是**信息隐藏**——不告诉卡片「那个 tag 存在但你没权限」） |
| `tags.subscribe*` | 订阅前检查**模式**被覆盖；**每次推送再检查一次**（通配符不许越权）；**退订时释放** |
| `tags.list()` | 只列被覆盖的 tag |
| `degradation()` | 本卡 `requires.tags` 里当前板型包**不提供**的 tag（缺失）+ 当前**降级**（`unavailable` / `error`）的 tag 与原因 |

**连接上下文**：契约 §7.8 明写「卡片**实例**的 connectionId，**由宿主在 iframe 创建时注入**」→
**照契约做**：实例创建时绑定当时的运行时连接；**运行时换连接时，宿主重建实例**（新的 instanceId、iframe 重载）。
「还没连上」时 connectionId 为 `null`，读 tag 得到 `unavailable`。

**值的来源**：TagStore（ADR-D22）。
> ⚠️ **别假设 TagStore 按连接分区**——实现的 `TagStore` 是 `Map<string, TagReading>`，**只按 tag 分区**
> （`docs/04` §9.4 的说法不成立，§4.8 第 5 条）。v1 单连接下无碍，但**多板（M8）之前必须改**。

### 6.4 卡片运行时日志

| 项 | 规则 |
|---|---|
| 按谁取 | `get_card_runtime_log(cardId)`（**按卡片 id**，契约 `spec/04` §2.3） |
| 条目的 `source` | `card`（卡片自己 `cockpit.log` 写的）/ `host`（宿主产生的，如卡片加载失败）/ `csp`（CSP 违规） |
| `level` | `error` / `warn` / `info`（与 `cockpit.log` 同一套；CSP 违规按 `error`） |
| CSP 违规怎么抓 | **卡片文档里的 DOM 事件 `securitypolicyviolation`**——宿主注入**经典脚本** `cockpit://card/<实例 id>/__host/csp.js`（**不是** module：要赶在卡片自己的脚本之前装上监听）→ 卡片 `parent.postMessage` → 页面侧经纪人**认人两次**（`event.source` + `instanceId`）→ main → 那张卡的运行时日志。**🟢 实测**（ADR-D29 §七：三类违规全中） |
| 为什么不用 `console-message` | Electron 34.5.8 的 `sourceId` 对 `connect-src` / `script-src` 违规是**空串** → **归属不到卡** → 而「试图联网」正是 `connect-src`（同上） |
| 卡内也报不报 | **不依赖卡内上报**——监听脚本是**宿主注入的**（卡片自己的脚本之前就在），卡片改不了它 |

### 6.5 权限与授权

> **M5 只做只读卡，不做授权流程**（`permissions.write` 恒为空 → 没有东西可授权）。
> 校验器对**非空**的 `permissions.write` 记一条 warning「本宿主还不支持写权限」——
> **不拒绝卡片**（契约 §3.3：卡片不能提权，所以**不授权**就够了）。
> 授权本身（`consent_id`、装卡授权、动作授权、`guard` 域）属 **M6**。

| 项 | 规则 | 出处 |
|---|---|---|
| 权限集 | 装卡时算：`permissions.read`（模式）+ `permissions.write`（**精确 id，不许通配**） | 契约 §2.3 |
| 授权粒度 | **按动作**：`reversible` 问一次；`destructive` 问一次**且每次执行再问** | 契约 §3.2 |
| 授权记录 | `(卡片 id, 动作 id, 板型包 id)`；**换板（pack id 变）要重新授权** | 契约 §3.2 |
| 参数域 | 批准界面显示 `guard` 范围（「可以把背光调到 16–255」），不是动作名 | 契约 §3.2 / `spec/02` §5.5 |
| 热重载 | `permissions.write` 变了（增/删）→ **重新征求授权** | 契约 §3.3 |
| `consent_id` | 绑 **manifest 内容哈希**；一次性；5 分钟有效 | `spec/04` §2.3 |

### 6.6 存储

| 项 | 规则 |
|---|---|
| 落盘 | `<userData>/cards/<cardId>/storage.json`（**按卡片 id**，不是实例） |
| 命名空间 | 卡片之间互不可见（不透明源 → 卡片自己都摸不到 localStorage，🟢 实测） |
| 值类型 | 必须 JSON 可序列化 |
| 配额 | 单键 64 KB；总量 1 MB → `quota_exceeded` |
| 键名 | 不得以 `__` 开头 |
| 卸载 | **保留**数据 |
| 浏览器原生存储 | **不可用**（不透明源 → SecurityError，🟢 实测）——所以 `cockpit.storage.*` 是**唯一**通道，契约 §6.2 的前提成立 |

### 6.7 布局（Slot）与主题

> ⚠️ **本节分两半**：**主题 token 注入属 M5**（第一张卡马上要用）；
> **布局本体属 M5b**（2026-11-14 拍板，M5 不做布局）。

| 项 | 规则 | 出处 |
|---|---|---|
| 归属 | **main**（GUI 状态都在 main，ADR-D2） | Q7（我的判断，见 §九） |
| 模型 | **Slot**：`{ id, kind: 'builtin' | 'user', cardId?, connectionId?, layout }` | §4.6 |
| 组件 | `react-grid-layout`（**要引这个依赖**，当前未安装） | ADR-D3 / O1 |
| 落盘 | 用户数据目录下的布局文件；`get_layout` / `set_layout` 两个接口 | `spec/04` §2.5 |

**主题 token 怎么进不透明源的卡片**（`docs/04` §6.5 要求「卡片不得硬编码颜色，只用宿主注入的 CSS 变量」）：
**协议 handler 在响应入口 HTML 时注入一段 `<style>`**，里面是当前主题的 `--cockpit-*` 变量
（CSP 有 `style-src 'self' 'unsafe-inline'` → 允许内联样式 ✅）。
**换主题时**：**不走重载 iframe**——卡片在**不透明源**里，宿主碰不到它的 DOM（跨源）。
改走**卡片已有的私有端口**：main 把新的别名值推过去，卡片的 bridge 执行
`document.documentElement.style.setProperty(...)` → **实时换肤，不闪、状态不丢**
（`docs/24` §八 给出了完整链路与理由）。

**卡片根目录**：**双根**（用户目录 + 内置目录），**同 id 用户优先**（Q6，我的判断，见 §九）。

### 6.8 卡片实例的生命周期（热插拔状态机）

```
扫描卡片根目录（双根，用户优先）
  → 读 manifest → 用 §九 的 13 条规则校验
      ├─ 不合法 → **保留上一版实例**，卡片位显示「无效」+ 错误摘要（docs/04 §11.2）
      └─ 合法   → 算权限集
                   ├─ permissions.write 变了 → **重新征求授权**（契约 §3.3）
                   └─ 无变化 → 直接生效
  → 重建 iframe（新 instanceId）→ 发新的 cockpit-hello
```

| 事 | 规则 |
|---|---|
| 谁扫描 | main（文件系统监听用 `fs.watch`，非递归：卡片根目录 + 每个卡片目录） |
| 同一 cardId 两个实例 | 都更新（实例是 `(cardId, connectionId)` 的投影） |
| 重载时布局 | **位置不丢**（布局在 main，与实例生命周期分开） |
| 重载时卡片运行时状态 | **全丢**（订阅要重订阅）。宿主代管的存储保得住（契约 §6.2 承诺卸载保留）。**这条要写进卡片开发规范** |
| 卡片崩了 | 只影响它自己（iframe 崩了不影响工作台） |

### 6.9 控制面（M6）

**执行链**（每一步都不可省）：

```
卡片调 actions.invoke(id, params)
  → ① 权限：这个动作在 permissions.write 里吗？
  → ② 授权：用户批准过吗？（destructive 与超出 guard 的要单次确认）
  → ③ 参数：按类型校验（不信任包的自述）+ spec/02 §4.6 编码
  → ④ 地板：地板匹配**编码后的 argv**（spec/02 §5.2.1 的匹配规范，运行时复查）
  → ⑤ 执行：经 RoundTripQueue（动作优先，ADR-D23）
  → ⑥ 回读：按板型包的 readback 取值 → 返回给卡片
  → ⑦ 审计：追加写一行
```

**§4.6 参数编码**（`src/main/actions/encoder.ts`）：纯函数，**先写单测再写实现**。
（这里的「§4.6」指 **`spec/02` §4.6**，不是本文档的 §4.6。）

| type | 编码 |
|---|---|
| `integer` / `number` | 十进制数字字面量，不带引号，不带任何其他字符 |
| `boolean` | `true` / `false` |
| `enum` | 必须是 `values` 里的某一项，原样注入 |
| `string` | **单引号包裹**，内部 `'` 转义为 `'\''`，长度不超过 `maxLength` |

**回读的五种形式**（`spec/02` §4.4）：

| 形式 | M6 的实现 |
|---|---|
| 1 `tag` | 定向读一次那个 tag（**新鲜**，不是等下一个周期） |
| 2 `file_equals` | 读文件比值，`expect` 可以是 `{param}` |
| 3 `command_ok` | 看退出码 —— **串口上没有退出码（事实 S5），在串口上必须拒绝这个形式** |
| 4 `verify` | 执行后跑二次命令，轮询到成功或超时 |
| 5 `none` | 返回 `ok:true` + **`verified:false`**；必须 `danger: reversible`；校验器记 warning；审计行标「未验证」 |

**执行器怎么拿到那条连接与那个队列**（现在的实现拿不到）：
`src/main/tags/runtime.ts` 里的 `new RoundTripQueue()` 是**函数内的局部变量**，`this.connection` 是 private。
→ **M6 在 `TagRuntime` 上开一条「跑一次独占事务」的口子**（执行完再取回读），
并把队列升级到 ADR-D23 的**四级优先级**（`action-verify` > `manual-refresh` > `card-sampling` > `diagnostics`）。
**否则串口上采样与动作会并发串台**——契约 §1.2.1 说的正是这件事。

**确认通道**：main 维护待确认队列 → 页面弹模态（显示**最终命令与参数域**）→
人点了 → agent 带 `confirm_id` 重试。`confirm_id` 绑 `(动作 id, 参数规范化摘要, 板型包 id, 契约版本)`，
**一次性**，5 分钟有效。

**审计**：追加写、每行 flush（沿用旧工程 `core/session_log.py` 的形态）。

## 十、验收判据（**机械可判**，不是「看着像对」）

### 10.1 M5 的隔离判据（Playwright 自动化）

| # | 判据 | 怎么判 |
|---|---|---|
| 1 | 卡片**碰不到宿主 DOM** | 卡片里 `parent.document` 抛 SecurityError |
| 2 | 卡片**碰不到别的卡** | A 卡读不到 B 卡的存储（不透明源 → SecurityError） |
| 3 | 卡片**连不上网** | `fetch` 抛错，**且** CSP 违规出现在**卡片运行时日志**里（agent 可见） |
| 4 | 卡片**拿不到未授权的 tag** | 卡片请求 `permissions.read` 之外的 tag → 被拒（`{value:null, status:'unavailable', reason:'not_found'}`），**且**主进程有审计记录 |
| 5 | 卡片**崩了不影响别人** | 一张卡抛异常，其他卡照常 |
| 6 | **改文件即热更新** | 改 `card.js` → iframe 重载 → 新行为生效 |
| 7 | **MIME 给错必须失败** | 故意把 `.js` 发成 `text/html` → module script 被拒 |
| 8 | **路径穿越必须挡住** | `entry: ../../secret.txt`、`%2e%2e`、符号链接 → 全部 403/404 |
| 9 | **CSP 头在宿主外壳上也生效** | 外壳的 `index.html` 带 CSP；Electron 不再报 Security Warning |

**第 3 条依赖 §6.4 的机制，而那条 🟡 未证明**（§4.1）→ **M5 的第一个 Playwright 用例就要把它验掉**：
`console-message` 在 Electron 34 的新签名下能不能拿到 CSP 违规、按 `sourceUrl` 能不能归属到具体的卡。

### 10.2 M6 的判据

| # | 判据 |
|---|---|
| 1 | `spec/02` §4.6 参数编码的**正负例**都有单测（`--model 'x; reboot'` → 无害值） |
| 2 | 动作经 **RoundTripQueue**，与采样**不并发**（串口上不串台） |
| 3 | 回读值**以回读为准**渲染，不乐观更新 |
| 4 | `readback: {kind: none}` → `ok:true` + `verified:false`，**不显示成已生效** |
| 5 | 串口上 `command_ok` / `verify` **被拒绝**（串口没有退出码，事实 S5） |
| 6 | 审计日志每行可追责；`kind: none` 的动作**标出「未验证」** |
