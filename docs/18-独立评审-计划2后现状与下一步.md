## 一、一句话结论

**计划 2 交付的是「一个质量不错的库 + 一个 CLI」，不是「一个活着的系统」。**
M3/M4 的代码经得起读（校验器带规则号、store 照抄契约的五态迁移表、地板按 §5.2.1 的词法匹配），
**但这套东西目前只有一个消费者：`scripts/probe.ts`。**

**下一步不该直接写卡片框架（M5）。** 理由见 §二 F1：卡要显示活的值，
而**值现在不会自己来**——没有调度器，IPC 里也没有一条 tag 通道。

## 二、五个发现（按严重度）

### F1 ·【阻塞 M5】tag 运行时**完全没接进应用**

| 事实 | 证据 |
|---|---|
| `src/main/index.ts` **不 import** `src/main/tags/` 任何东西 | 逐文件搜过 |
| `src/shared/ipc-contract.ts` 里**一条 tag 通道都没有**（11 条通道全是 terminal/files/connections） | 同上 |
| renderer **看不到任何读数** | 同上 |
| `src/main/tags/` 的消费者**只有** `scripts/probe.ts` 与 `scripts/validate-profiles.ts` | 逐文件搜过 |
| **没有调度器**——`poll_groups[].interval_ms` 只被 validator 检查「≥200」，**没有任何代码按它定时** | 搜 `setInterval` / `schedule`：零命中 |
| 契约 §10 的**自动识别**（读 `board.model` → 选包）也没实现 | `probe.ts` 只能 `--profile` / `--pack` 手工指定 |

**后果**：M5 的判据是「**第一张监控卡**可拖拽、热更新」——
监控卡要显示活的值，而值**永远不会自己来**。现在能显示值的只有一条命令：`probe:board`。

> **这不是谁的疏忽，是里程碑切分的必然结果**：
> M3 叫「契约移植」（库），M4 叫「板型包真机验证」（探针）——
> **两者都不包含「让它在应用里活着」**。这个里程碑**从来没被排过**。
> 而 M5 直接要卡片。中间**缺一环**。

### F2 ·【阻塞 M5/M6】契约 §1.2.1 的「一次往返互斥」**没有实现层**

契约 §1.2.1 明写了一张表：

| 契约要求 | 实现现状 |
|---|---|
| 一个连接上有一个**往返队列**，采样与动作都进同一个队列 | ❌ 没有队列 |
| **动作优先于采样**，采样让路 | ❌ 没有优先级 |
| 采样因让路错过本周期 → **跳过本周期，不补发** | ❌ 没有这个语义 |
| 往返超时后必须**等 marker 收齐或明确放弃**才能开始下一次 | ❌ 没有清理语义 |
| 串口上**一次往返只能是一行命令**（事实 S6） | ⚠️ 合成命令确实是一行（`fetch.ts` 用 `;` 拼），但**从未在串口上验过**（见 F4） |

**现状只有一个传输级的布尔锁**：`src/main/hal/serial.ts` 的 `private busy = false`，
它挡的是「exec↔exec」和「exec↔交互会话」（计划 1 的成果）。
而 `TagSampler.sampleGroup()` 是**直接** `await this.connection.exec(...)`——**零排队**。

**后果（契约自己点名了）**：调度器一接上，三个 poll group + 交互终端 + 将来的动作会同时打同一条线。
串口上的表现就是契约 §1.2.1 写的那句：**「点了按钮，监控卡数值乱跳」**。

> **这一块应该第一个做**：它是**纯逻辑**、不依赖任何 UI、可以彻底单测，
> 而且**做错了要到 M6 才有症状**（那时候再回头改，代价大得多）。

### F3 ·【质量缺口】变异守卫**只覆盖计划 1**

`npm run mutation:check` 的 26 项**全部是计划 1 的**（C4–C6、M7–M26、M12）。

**M3 新增的全部代码——27 条校验规则、危险地板、TagStore、采样器、8 个 reader kind——零变异守卫。**

AGENTS.md 明写「跑 `npm run mutation:check` 看**当前这批修复**是否都还守着」。
现在守的是**上一批**。新写的 27 条规则（尤其规则 4「必须等于 `utilization`」、
规则 25/26「能力词表」）**正是最该有守卫的地方**——
规则 4 被窄化过一次（只判非空不判等于 `utilization`，于是 `measure: utilzation` 一路放行
= **占空比被发布成利用率**），这说明**这批规则确实容易退化**。

### F4 ·【真机缺口】串口路径**未验**，而且**当前验不了**

`probe:board --profile board-serial` → **11/11 全部超时（124）**。

我进一步做了排除实验（用项目自己的 `Connection` 接口）：

| 命令 | 长度 | 结果 |
|---|---|---|
| `echo hello` | 10 字符 | ❌ 超时 8s，输出为空 |
| `echo a; echo b; echo c` | 22 | ❌ 超时 |
| 314 字符 | 314 | ❌ 超时 |
| 814 字符 | 814 | ❌ 超时 12s |

→ **不是命令太长**（事实 S6 那一类问题），**是连最基本的往返都不通**。

**根因锁定**：宿主上的 `serial-server.py --port 2323`（pid 17904，15:18 启动，计划 1 验收的遗留物）
**独占打开了 COM3**。经它发 `echo MARKER_TEST_12345` → 板子回了
`MARKER_TEST_12345` + `root@ATK-DLRK3588:/#` —— **板子是活的，串口是通的**。
但**回包被那个进程吃掉了**，所以应用自己的 `exec` 永远等不到。

**这里有两个独立的问题**：

1. **流程问题**：串口验收需要一个「**谁独占 COM3**」的约定。
   现在 `serial-server.py` 留着不停，串口路径就永远验不了。
2. **产品问题**：`probe:board` 在串口上**失败形态极差**——
   它**不报「端口被占」**，而是逐个 reader 报「超时」，**总共挂了近 4 分钟**。
   → **串口 exec 超时的第一嫌疑应该是「回包被别的程序吃了」**，
   而不一定是「板子慢」。这条提示应该写进超时错误里。

> 顺带：**SSH 路径也从未验过**（包声明 `requires.transports: [adb, serial, ssh]`）。
> 本机（`local`）也不承载板型包（`board_pack: null`），所以不涉及。

### 第 1 步 · 计划 3 = **M4.5「运行时接进应用」**

**这是我认为下一步唯一该做的事。** 它把 M3/M4 从「库」变成「活的东西」，
而且**不碰卡片**——卡片框架留给 M5。

| Task | 做什么 | 为什么是这个顺序 |
|---|---|---|
| **Task 1** | **往返队列**（契约 §1.2.1 全表）：排队 / 动作优先 / 跳过不补发 / 超时清理 | **纯逻辑、可单测、不依赖 UI**。做错了要到 M6 才有症状 |
| **Task 2** | **轮询调度器**：按 `interval_ms` 驱动 `sampleGroup`，走 Task 1 的队列 | U2 |
| **Task 3** | **板型包绑定 + 自动识别**（连接指名 → 读 `board.model` → 匹配 `match`） | U4；也是 Task 4 的前置 |
| **Task 4** | **TagStore → IPC → renderer**：加 `tags:readings` / `tags:subscribe` 通道 + 一个**最小读数面板** | U3。**判据就是「面板上的数自己在动」** |
| **Task 5** | **串口往返**：独占诊断 + 超时错误里点明「端口可能被占」；若 0.2 证明长命令不行，再做**单行变体** | T1 + F4 的产品问题 |
| **Task 6** | **变异守卫扩到 M3**：27 条规则 / floor / store / sampler 各挑 1–2 个高价值变异 | F3 |

> **Task 4 的判据要写死**：「面板上的数自己在动」——**不是**「有一条 IPC 通道」。
> 前者能抓到「调度器没跑」「store 没更新」「renderer 没订阅」三种失败；
> 后者只能抓到第一种。
