## 二 · 读侧的语义补全（**S1–S11** ✓）

### 2.1 `list_connections`（**S1 · S2 · S3** ✓）

```
→ [{ id, label, transport, board_pack, connected, capabilities }]
```

**逐字段定死** ✓：

| 字段 | 语义 | 宿主侧来源 |
|---|---|---|
| `id` / `label` / `transport` | 连接 **profile** 的身份 ✓（**不是**某条活连接 ✓） | `ConnectionProfile` ✓ |
| `board_pack` | **绑定的板型包 id** ✓；**没绑就是 `null`** ✓。**只给 id** ✓ —— **不给版本** ✓（见下） | `profile.board_pack` ✓ |
| `connected` | **这条 profile 现在有活着的连接吗** ✓（布尔 ✓） | 见 §2.1.1 ✓ |
| `capabilities` | **连接级**能力位 ✓（`exec` / `pty` / `files` / `exitCode` ✓）—— **不是板级能力词表** ✓ | `capabilitiesFor(profile)` ✓ |

> **`board_pack` 为什么不给版本** ✓（**S3** ✓）：
> 契约原文说「包 id 与版本」✓，但**版本是包自己的属性** ✓ —— 一个 profile 绑了包，
> 那个包**在哪台机器上**、**哪个版本** ≠ 这条连接的属性 ✓
> （同 id 的包可以有好几个版本 ✓）。
> → **`list_connections` 给 id** ✓；**版本在 `list_data_sources` 里给** ✓（那里本来就在讲包 ✓）。
> → 这样 agent 仍然能拿到版本 ✓，但**不把包的属性挂到连接上** ✓。

> **`connected` 怎么算** ✓（**S1** ✓）：
> 「这条 profile **有活着的连接**」✓ —— 即：
> - 它是**当前 tag 运行时**那条连接 ✓（`runtime.status.profileId` ✓），**或**
> - 它**开着终端会话** ✓（TerminalManager 里活着的会话 ✓）。
>
> **为什么不是「连上了吗」**：profile 是**配置** ✓，连接是**实例** ✓ ——
> 一个 profile 可以开两个终端 ✓ → 「它连着」对配置说**没有意义** ✓。
> → 所以 `connected` 的口径是「**这条配置背后现在有活连接**」✓。

### 2.2 `list_data_sources`（**S1 · S3** ✓）

```
→ [{ id, board, poll_group, reader, kind, interval_ms, provides: [...], status }]
```

| 字段 | 语义 |
|---|---|
| `id` | **reader 的 id** ✓（数据源的粒度就是 reader ✓ —— 契约自己写的 ✓） |
| `board` | **板型包 id** ✓（**不是**连接 id ✓ —— 见 §2.2.1 ✓） |
| `poll_group` | 这个 reader 所在的**轮询组 id** ✓ |
| `kind` | reader 的 kind ✓（`proc_stat` / `file_read` / … ✓） |
| `interval_ms` | 它所在**轮询组的周期** ✓（不是 reader 自己的 ✓ —— reader 没有周期 ✓） |
| `provides` | 这个 reader 提供的 **tag 名** ✓ —— **展开成具体名** ✓（见 §2.2.2 ✓） |
| `status` | **reader 自身**的状态 ✓ —— 取值**与 tag 状态同一套** ✓（契约已写 ✓）：`ok` / `stale` / `unavailable` / `error` / `pending` |

> **`board` 与 `board_pack` 有什么区别** ✓（**S2** ✓）：
> | 字段 | 在哪 | 指什么 |
> |---|---|---|
> | `board_pack` | `list_connections` ✓ | **这条连接绑的包 id** ✓（可能是 `null` ✓） |
> | `board` | `list_data_sources` / `list_tags` / `describe_tag` ✓ | **当前生效的那块板的包 id** ✓ |
>
> → **`list_data_sources` 的 `board` 恒为当前板型包 id** ✓（v1 只有一块板 ✓ —— 多板是 M8 ✓）。
> → **`list_tags` / `describe_tag` 的 `board` 同理** ✓（恒为当前包 id ✓）。
> → **不给 `null`** ✓ —— 没有包就没有数据源 ✓（返回空数组 ✓）。

> **`provides` 为什么要展开** ✓：
> 包里写的是 `cpu.core.*.usage` ✓（**模式** ✓），而 agent 要写卡片 → 卡片要填**具体 tag 名** ✓
> （`permissions.read` 里可以写模式 ✓ 但**具体名更好用** ✓）。
> → **给具体名** ✓（当前实际可读的那些 ✓），**模式另由 `describe_tag` 的语义承担** ✓。

> **reader 的 `status` 怎么算** ✓（**宿主侧新增** ✓）：
> 一个 reader 的状态 = **它提供的那些 tag 的状态之「最差」** ✓：
> | 情形 | reader 状态 |
> |---|---|
> | 一个都没读出来 | `pending` ✓ |
> | 有读数、全部 `ok` | `ok` ✓ |
> | 有读数、有 `stale` | `stale` ✓ |
> | 有读数、有 `error` | `error` ✓ |
> | 有读数、全部 `unavailable` | `unavailable` ✓ |
>
> → **「最差」的次序**：`error` > `unavailable` > `stale` > `pending` > `ok` ✓
> （`error` 最差 ✓ —— 它意味着「读它失败了」✓；`unavailable` 次之 ✓）。

### 2.3 `list_tags`（**S4 · S5 · S2** ✓）

```
→ [{ name, type, unit, range, status, value, board, source_reader }]
```

| 字段 | 语义 |
|---|---|
| `name` | tag 名 ✓（宿主侧叫 `tag` ✓ → **对外改名** ✓） |
| `type` | **核心词表**里的类型 ✓（`number` / `string` / `boolean` / `enum` ✓） |
| `unit` | 单位 ✓（**核心词表**的 ✓ —— 契约 §二 说「与 tag 状态同一套」的同类封闭性 ✓） |
| `range` | **核心词表**里的取值域 ✓（`[min,max]` 或一句自然语言 ✓） |
| `status` / `value` | 当前读数 ✓（**原样** ✓ —— 五态 ✓） |
| `board` | 当前板型包 id ✓ |
| `source_reader` | **这个 tag 是哪个 reader 提供的** ✓（见 §2.3.1 ✓） |

> **`type` / `unit` / `range` 从核心词表来** ✓（**S4** ✓）：
> 宿主侧的 `CORE_VOCABULARY` ✓ 就是**契约 §1.1 的「核心词表」** ✓（`spec/01` ✓）→
> **有词表的给词表的值** ✓；**没有的（`custom.*` 私有量）给 `null`** ✓
> → **不猜** ✓（契约 §四 的「未知用 `unavailable` 不返回 null」的同类原则 ✓ —— 但这里是**类型**不是状态 ✓，
> 给 `null` 是「**这一项没有值**」✓ 不是「**值是 null**」✓）。

> **`source_reader` 怎么算** ✓（**S5** ✓）：
> 包里 reader 的 `provides[].tag` 是**模式** ✓（`cpu.core.*.usage` ✓）→
> **反推**：一个 tag 名**匹配上**某个 reader 的某个 provides 模式 → 那个 reader 就是它的来源 ✓。
> → **匹配不上就是 `null`** ✓（**不猜** ✓）—— 典型是**词表里有但这个包没提供**的 tag ✓。

### 2.4 `describe_tag`（**S4 · S5 · S6 · S7** ✓）

```
→ { name, type, unit, range, semantics, status, value, board,
    source: { reader, kind, args_summary }, history: [...] }
```

| 字段 | 语义 |
|---|---|
| `semantics` | **核心词表里那条语义描述的原文** ✓（契约 §2.1 明说「这是防误用的关键」✓）→ **没有就是 `null`** ✓ |
| `source.reader` | 同 §2.3 的 `source_reader` ✓ |
| `source.kind` | 那个 reader 的 kind ✓ |
| `source.args_summary` | **这个量是怎么来的** ✓ —— **不含命令原文** ✓（见 §2.4.1 ✓） |
| `history` | **最近的样本** ✓ → `[{ value, unit, status, at }]` ✓（形状与 `sample_tag` 一致 ✓） |

> **`args_summary` 的脱敏边界** ✓（**S6** ✓ —— **这一条是安全底线** ✓）：
> 宿主侧的 reader kind 里，`exec_regex` 的 args 有 **`command`** ✓、
> `script` 的 args 有 **`path`（宿主上的路径）**与 **`interpreter`** ✓。
>
> | 参数 | 给不给 agent | 为什么 |
> |---|---|---|
> | `path`（`file_read` 的**板上**路径 ✓） | **给** ✓ | 「哪个文件」正是契约要它说的 ✓ |
> | `glob` | **给** ✓ | 同上 ✓ |
> | `pattern`（正则 ✓） | **给** ✓ | 说的是「取哪一段」✓ 不是命令 ✓ |
> | `format` / `measure` / `strip_trailing_null` 等 | **给** ✓ | 形状参数 ✓ 无害 ✓ |
> | **`command`**（`exec_regex` 的 ✓） | **不给** ✓ | **它就是一条裸命令** ✓ → 给出去 agent 就会去发它 ✓ → **正是契约 §1.3 禁止的那件事** ✓ |
> | **`path`（`script` 的——宿主上的路径 ✓）** | **不给** ✓ | 它是**宿主文件系统**的位置 ✓ → 泄漏本机目录结构 ✓ |
> | **`interpreter`**（`script` 的 ✓） | **不给** ✓ | 与 `script` 是一套 ✓（`interpreter + path` 就是一条命令 ✓） |
>
> → **`args_summary` 是「按参数名逐个筛」的白名单** ✓ —— **不是**「按 kind 整块放行或整块拒绝」✓
> → 白名单：`path` / `glob` / `pattern` / `format` / `measure` / `strip_trailing_null` / `type` ✓
> → **其余一律不给** ✓（`command` / `interpreter` / `path`（script 的）✓ 全挡在外面 ✓）。
>
> → **给 agent 的是「哪个文件、什么 kind」** ✓ —— 契约 §2.1 原话 ✓。

> **`history` 的容量与形状** ✓（**S7** ✓）：
> | 项 | 定死 |
> |---|---|
> | 形状 | `[{ value, unit, status, at }]` ✓ —— **与 `sample_tag` 完全一致** ✓ |
> | `at` | **本次采样完成的时刻** ✓（毫秒 UTC ✓）—— 契约 §四 ✓ |
> | 容量 | **每个 tag 保留 64 个样本** ✓（环形 ✓ —— 满了丢最旧的 ✓） |
> | `value` 在 `unavailable` 时 | **`null`** ✓（契约 §1 的五态表 ✓ —— 与当前读数一致 ✓） |
>
> → **为什么是 64**：契约 §2.1 说 `n` 是「最近 n 个样本」✓ —— 判「抖动」要看几个点 ✓，
> 而**「刷新周期实际是多少」**要看**跨越两个周期**的样本 ✓ → 64 够跨越很多个快组周期 ✓
> （快组 1s ✓ / 慢组 30s ✓ → 64 个慢组样本 = 32 分钟 ✓）。**不锁死** —— 这是实现细节 ✓，
> 但**容量要写进契约** ✓ —— 否则 agent 会以为「要 200 个就一定给 200 个」✗。

### 2.5 `sample_tag`（**S7** ✓）

```
→ [{ value, unit, status, at }, ...]
```

| 项 | 语义 |
|---|---|
| `n` | **最近 n 个样本** ✓（契约 §四 已明说「不是最近 n 秒」✓） |
| **n 大于已有的样本数** | **有多少给多少** ✓（**不 pad** ✓ —— 造不出没采过的样本 ✓） |
| **n ≤ 0** | **`invalid_params`** ✓（见 §四·失败理由 ✓） |
| **这个 tag 从来没被读过** | **空数组** ✓（**不是 `null`** ✓ —— 契约 §四：「未知用 `unavailable` 不返回 null」✓） |
| **`at`** | **本次采样完成的时刻** ✓（毫秒 UTC ✓） |

> **`sample_tag` 不触发采样** ✓ —— 它读的是**环形缓冲里已有的样本** ✓。
> → 想看**新鲜**的值有别的路 ✓（`execute_action` 的回读 ✓）。
> → 契约 §2.1 说「取最近 n 个样本」✓ —— **「最近」就是已经采过的那些** ✓。

### 2.6 `list_cards`（**S4 · S8 · S9 · S10** ✓）

```
→ [{ id, name, version, path, installed_at, status, degraded, missing_tags }]
```

| 字段 | 语义 |
|---|---|
| `id` | **manifest 的 id** ✓（**不是目录名** ✓ —— 两者可以不同 ✓；契约 §2.3「装卡按 id」✓） |
| `name` / `version` | manifest 的 ✓ |
| `path` | **卡片目录的绝对路径** ✓（契约 §四：「路径用绝对路径」✓） |
| `installed_at` | 见 §2.6.1 ✓ |
| `status` | 见 §2.6.2 ✓ |
| `degraded` | **这张卡在当前板上是不是残的** ✓（布尔 ✓）—— 与 `missing_tags` **一致** ✓（见 §2.6.3 ✓） |
| `missing_tags` | 见 §2.6.3 ✓ |

> **`installed_at` 用什么时刻** ✓（**S8** ✓）：
> 宿主侧**从没记过安装时间** ✓ → 加一个字段要改所有卡的落盘流程 ✓（**代价大** ✓）。
> → **用卡片目录的 mtime** ✓（**「这个目录最后一次被改动」** ✓）。
> → **并把这件事写进契约** ✓ —— agent 拿到的是 mtime ✓，
> **它就知道这是「文件最后改动时刻」而不是「人点装上的时刻」** ✓ → **不撒谎** ✓。
>
> → **为什么不新增一个 `installed.json`** ✓：那要让**装卡流程**多写一个文件 ✓，
> 而**契约明写「MCP 不做文件 IO（除了 install_card 的复制）」** ✓ → 与它的精神相悖 ✓。

> **`status` 的取值域** ✓（**S9** ✓ —— **封闭** ✓）：
> | 值 | 含义 |
> |---|---|

> **`missing_tags` 的判定口径** ✓（**S10** ✓）：
> **「这张卡要的、当前板上读不到的 tag」** ✓ —— 具体地：
> | 来源 | 取什么 |
> |---|---|
> | `permissions.read` | 每一个读权限里的 **tag 名** ✓（**按模式展开** ✓ —— `cpu.core.*.usage` 匹配当前所有读不到的 `cpu.core.N.usage` ✓） |

> **或**它在那儿但**状态不是 `ok`** ✓（`unavailable` / `error` / `stale` / `pending` ✓ 都算读不到 ✓

> → **`degraded` = `missing_tags` 非空** ✓（**或** `status` 是 `degraded` ✓ —— 同一件事的两个说法 ✓
