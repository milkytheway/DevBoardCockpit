### **有条件通过**

**先说好的**：v2 把 v1 最要命的那块补上了 —— **信任模型第一次成形，而且不是纸上的**。
「三本账 + 五条规矩」（`docs/34:66-83`）在实现里有对应物

v1 的「信任模型缺一块」从「一个字都没有」变成了「有骨架、有执行者、有真机复验」。
**这是这一轮最大的进步，且是真的进步，不是话术。**

**再说要命的**：v2 仍**开着两个洞**，且这两个洞都会**直接落到契约文本里**：

1. **确认链没有落点**（V2-C1）—— 契约写了「destructive 每次都要人确认」，
   也写了凭据**绑什么**，却没写**谁签发 → 人怎么点头 → 点完之后怎么继续**；
   实现里 `WorkflowService` **根本没有 confirm / resume 方法**，
   `scripts/run-workflow.ts` 不传 `confirmations` → destructive 步**永远卡住**。
2. **`requires.workflows` 与 `spec/03` §九 规则 3 正面冲突**（V2-C2）——
   v2 加了这个字段、却没加 `permissions.workflows`，
   也没把 `spec/03` 的 §2.2/§2.3/§2.4/§三/§九 列入改动清单 →
   **按 v2 改完契约，装一张声明 `requires.workflows` 的卡仍然过不了 `validate_card`**。

这两条**不是补几行字就完**的架构问题，是**必须先在提案里定死**的规格问题。
所以判定是「有条件通过」：**这两条在写 `docs/spec/05` 之前必须先在提案里解决**；
其余 Important/Minor 可与契约同批改。

## 二 · v2 新引入 / 仍然开着的洞

> **说明**：下面每一条都给了 `文件:行号`。凡是「实现已做但提案没写」的，

### 2.1 · Critical

---

#### **V2-C1 · 确认链在契约与实现里都没有落点：签发 → 人点头 → 继续跑，这一整条链是断的**

**结论**：v2 §二·2.4 把「确认」写成了**一条规矩**（`danger: destructive` → 每次都要人确认），
又把凭据的**绑定**写清楚了（`docs/34:99`），但**从头到尾没有一个字说**：
**谁签发这张凭据？人在哪个界面上点？点完之后，那次运行怎么继续？**
实现层对应的三条路**全是断头路**。

**证据**

| 环节 | 契约 | 实现 |
|---|---|---|
| 工具清单 | §五 列了 `list_workflows` / `run_workflow` / `workflow_status`（`docs/34:271-275`）—— **没有 `confirm_workflow`**；但 §五·2 又写着「都要确认（**`confirm_workflow` ✓**）」（`docs/34:280`）→ **引用了一个不存在的工具** | `service.ts` 整个文件只有 `list` / `start` / `status` / `recent`（`service.ts:75,102,155,164`）——**没有 confirm，没有 resume** |
| 人怎么点头 | 没说 | `scripts/run-workflow.ts:150-163` 的 `runWorkflow` 调用**不传 `confirmations`** → `runner.ts:788-791` 落到桩 `{ issue: () => '', consume: () => false }` → destructive 步**永远返回 `needs_confirmation`**，命令不执行（`tests/unit/workflows/runner.test.ts:245` 验证了「命令没执行」✓） |
| 点完之后怎么继续 | 没说 | `runner.ts:152` 的 `for (const step of pack.steps)` **从头开始**；`:166-173` 遇到 `needs_confirmation` 就 `break`；`service.ts:136-138` 把这次运行置成 `needsConfirmation` + `reason: 'needs_confirmation'`，而 `service.ts:135` 把它记成 `state: 'failed'`。**没有任何续跑路径** —— 唯一可行的办法是**重新 `start()` 一次并把 `confirmIds` 传进去**（`service.ts:105`），于是 **前面的写步骤全部重跑** |

**为什么是问题**

1. **契约引用了一个不存在的工具**（`confirm_workflow`）—— 契约层是权威文档，
   引用不存在的工具 = 下游实现者会自己编一个出来。
2. **「destructive 每次都要人确认」这条产品底线的最后一道闸，在流程层没有门框。**
   注意它**是 fail-safe 的**（命令确实没执行 ✓，这一点要给 v2 记功），
   但 fail-safe 不等于可用 —— **这条流程永远跑不完**。
3. **「重试 = 从头再跑」这个语义一字未写**，而它正是 31-C3 点名的要害：
   > 「流程跑到第 3 步要人确认，前 2 步已经写了板子，重试会不会再来一遍？
   > ……编译两遍、传输两遍、`depmod -a` 两遍。**契约必须说清这是不是允许的。**」
   （`docs/31:223-226`）

   v2 §六·5 只写了「**续跑**：失败后从失败的步继续 —— **首版不做**」（`docs/34:293`），
   这句话**回答的是「能不能从失败步继续」，没有回答「那重试到底会怎样」**。
   实现给的答案是「**从头再跑，前面的写步骤重复执行**」——
   对 `depmod -a && modprobe`（`profiles/workflows/hello-kernel.build-run.yaml:98`），
   重跑一次 = **板子上再装一遍模块**。契约必须明写这是不是允许的。

**建议**

1. 契约补一条完整的**确认生命周期**（照 `spec/04:401-414` 的 `confirm_action` 形状）：
   `run_workflow` 返回 `needs_confirmation` + `confirm_id` →
   人**在 GUI 里**看到「这一步会在哪个角色的哪台机器上跑哪条命令」→ 点 →
   agent/卡片**重试**（带 `confirm_id`）。
2. **明写重试语义**：「首版重试 = **从第一步重新跑**；前面已完成的步骤**会重复执行**；
   因此 `danger: destructive` 的步骤**不得**放在有副作用的写步骤之后，或者
   **首版要求流程最多一次确认**。」
   —— 两条路都行，但**必须选一条并写进契约**。
3. 把 `awaiting_confirmation` 写进状态机（见 **V2-I1**）。
4. **实现的对应缺口**（不阻塞契约评审，但要进计划 7 的头一条）：
   `WorkflowService` 加 `confirm(runId, stepId, confirmId)` 或
   `start(id, inputs, { confirmIds })` 的**续跑语义**；`scripts/run-workflow.ts` 把
   真的 `ConfirmationStore` 接进去（现在接的是桩）。

#### **V2-C2 · `requires.workflows` 与 `spec/03` §九 规则 3 正面冲突；改动清单漏了要改的那几节**

**结论**：v2 §4.1 正确地识别出「加这个字段要同步改封闭字段表」（`docs/34:240`），
**但只改了封闭字段表，漏了「requires ⊆ permissions」那条更硬的规则**。
按 v2 改完契约，**装一张声明了 `requires.workflows` 的卡仍然会被 `validate_card` 拒掉**。

**证据**

- `spec/03:69`（§2.2）：「`requires` 里的**每一项**，必须被 `permissions` 里的**某一项**覆盖。」
- `spec/03:631`（§九 规则 3）：「`requires` ⊆ `permissions`（愿望不得超出授权，按模式覆盖判定，§2.2）」
- v2 §4.1 的例子（`docs/34:231-236`）：
  ```yaml
  requires:
    workflows: [hello-kernel.build-run]
  permissions:
    write: []          # ← 流程的动作不在这里声明 ✓
  ```
  → **`requires.workflows` 的每一项都没有被 `permissions` 里的任何一项覆盖** → **规则 3 不过**。
- v2 §八 item 2（`docs/34:317`）的 spec/03 改动清单：
  「§2.5 封闭字段表加 `requires.workflows` · §5.5 加「一件事」 · §7.7 加两行 API · §7.8 说明不变」
  → **§2.2 / §2.3 / §2.4 / §三 / §九 一节都没列**。
- 顺带：v2 说「§2.5 封闭字段表加 `requires.workflows`」（`docs/34:240`）——
  但 `spec/03:121-127` 的 §2.5 表列的是**层**（顶层 / `requires` / `permissions` / `layout` / `actions[]`），
  **不是键名**；真正列键名的是 `spec/03:49-62` 的 §二 逐字段表。
  → **改的是哪一节，v2 指错了**。
- 现成的校验器会拒：`src/main/cards/manifest.ts:68` `REQUIRES_ALLOWED = ['tags','actions','min_board_pack']`
  → `requires.workflows` 是未知字段 → 规则 10 报错。
  **这是 v1 就点到的**（`docs/31:155-156`），v2 加了字段却没让它过规则 3。

**为什么是问题**

v2 §4.1 规则 1 的理由是「不加就过不了校验 ✓」——**加了也过不了**，只是从规则 10 挪到规则 3。
更要命的是**语义**：v2 保留了 `permissions.write: []`，
按 `spec/03:98` 的「**有效写权限 = `permissions.write` ∩ 已授权的动作**」，
流程的权限**根本不在这个交集模型里** → 「用户只批准了其中一部分」这条语义对流程**不成立**。
32-C4 建议的方案甲（**加 `permissions.workflows`，与 `write` 并列，精确 id 不支持通配**）
**没被采纳，也没有给出替代方案**。

**建议**（二选一，写进 `docs/05` 的 ADR-D34）

| 方案 | 内容 | 代价 |
|---|---|---|
| **甲（推荐，与 31-C2 / 32-C4 一致）** | 加 `permissions.workflows: []`（精确 id、不支持通配，理由同 `spec/03:84-91` 的不对称风险）；`requires.workflows` 保留为**愿望**；运行时有效集合 = `permissions.workflows` ∩ **这张卡被授过的流程** ∩ **已批准的包** ∩ **本卡可见的目标集合** | 要动 `spec/03` 的 §2.2 / §2.3 / §2.4 / §三 / §九 五节 + 加一个授权类别（`src/main/cards/grants.ts:26-38`）+ 改 `runner.ts:817-823` 的 `granted()` |
| **乙** | 不进 manifest：卡片**不能**触发流程，只有 agent（MCP）能 | 用户的「点一下就编译上板」还是没位置 —— 而这正是这一期要解决的事之一（`docs/34:27`） |

**无论选哪条**，§八 item 2 的 spec/03 改动清单**必须补上那五节**。

#### **V2-I1 · §六 的状态机自相矛盾：写了 `cancelled`，又明写「取消不支持」；漏了实现真会产生的 `awaiting_confirmation`**

- **证据**：`docs/34:291` 状态机 = `running` / `done` / `failed` / `cancelled`；
  `docs/34:294`「**取消**：`cancel(run_id)` → **首版不支持**……契约里**明写不支持** ✓」
  → **同一个状态既在枚举里、又被声明为不可达**。
  实现里 `service.ts:36` 的类型也有 `cancelled`，但**没有任何代码路径能置上它**
  （`service.ts:135` 只写 done/failed，`:146` 只写 failed）——
  **一个永远不可达的状态写进契约 = 下游会写 `case 'cancelled':` 的死分支**。
- **反方向**：实现**会**产生「要人确认」这个中间态（`service.ts:136-138`），

  → 卡片按 `state` 渲染会把「在等你点头」显示成「失败了」。
- **建议**：状态机写成 `running` / `awaiting_confirmation` / `done` / `failed`；
  **删掉 `cancelled`**（不支持就不该出现在枚举里）；
  实现把 `needsConfirmation` 的那次运行置成 `awaiting_confirmation` 而不是 `failed`；
  并在 §六 补一句「`awaiting_confirmation` 的运行**不算失败**」。

#### **V2-I2 · §三·3.7 内部打架：`actor` 被钉死成 `workflow:<pack id>`，却又要求「触发者 / 最终命令 / 输入值」**

#### **V2-I4 · §二·T4 没堵「跨机写 = 源机上的一条任意命令」这个地板洞**

- **证据**：v2 §二·T4（`docs/34:81`）承诺「每个写步骤都过 §4.6 的编码 + §5.2.1 的危险地板；
  命中地板 → 按 destructive 处理」。**但 `spec/02:651-656` 的地板表六条里没有 `ssh` / `scp` / `rsync`**
  → `file.transfer` 的传输命令**永远不命中** → 永远按 `reversible` → **零确认**。
  黄金样本就是这个形状（`profiles/workflows/hello-kernel.build-run.yaml:85`
  `scp {from.path} {role:target.user}@{role:target.host}:{to.path}`）。
- **为什么是问题**：「一件事」的写权限因此不是「往板子上放一个文件」，
  而是「**在客机上执行一条能往任意目标机写的命令**」——
  同一份 YAML 里，命令**可以是** `ssh target 'rm -rf /usr/lib/modules'`，**一样不命中地板**。
  v2 §二·T4 说「自由命令是第二条命令通道 ✗ —— 它必须与动作**同一条防线** ✓」，
  **但这条防线对传输命令恰好是空的** → 那句话在自己的例子里就失效了。
- **32-I3 的收口**（`docs/32:713`）要求三件事：跨机写按「目标 + 源 + 路径」建模、
  传输命令**由宿主生成**、跨机通道**必须校验主机身份** —— **v2 一条都没进**。
- **建议**：契约里写死：
  ① `file.transfer` 的写权限按 `(目标 role, 源 role, to.path)` **建模**，不按「一条命令」建模；
  ② 传输命令要么**由宿主生成**（host/port/user 从 role 事实来、路径从 from/to 来），
     要么包提供的模板必须**逐词匹配一个封闭允许集**；
  ③ 跨目标的写走**目标侧**的确认通道（不是源侧）；
  ④ 契约里补「跨目标连接必须校验主机身份」（**32-I4**，目前全仓 0 命中）。

#### **V2-I5 · §六 没有并发与超时语义**

- **证据**：v2 §六 的 6 条（`docs/34:289-294`）里**没有并发、没有超时**（全文「并发」/「超时」= 0 命中）。
- **为什么是问题**：
  ① **并发**：板子上一次往返独占（`spec/02:213-231` / SPEC-D22 `spec/00:142`）→
     同一块板被两个流程同时跑会**互相排队**（`src/main/hal/round-trip-queue.ts`），
     而传输步的耗时波动是 **20 倍**（尖兵 `:111`：3.8s / 75.6s / >110s）→ 排队会叠加成**分钟级**等待。
     31-C3 建议第 3 条明写这条（`docs/31:246`）。
  ② **超时**：步骤级 `timeout_ms` 是**必填的实践**（黄金样本每一步都给了：
     `hello-kernel.build-run.yaml:61` 1800000 / `:85` 1800000 / `:99` 120000 / `:79` 30000），
     但**契约里 `timeout_ms` 全文 0 命中** → **默认值、超时后的 reason、超时后该步算不算完成，全都没说**。
     而 `spec/02:580` 只给了 `verify` 的默认 5000，**没有步骤级命令执行的默认超时**。
- **建议**：§六 补两条：并发（同一个 `run_id` 同时只允许一个在跑；
  同一个 `(流程 id, role 集合)` 同时只允许一个运行，超出的**排队还是拒绝**要写死）；
  超时（步骤级 `timeout_ms` 的默认值 + 超时的 reason 码 + 超时后该步算不算完成 + 是否清理半截产物）。

#### **V2-I6 · §一 / §4.4 的「卡片不知道目标」与返回形状里的 `role` / `detail` / `value` 自相矛盾；返回不过 `permissions.read`**

- **证据**：v2 §一「**卡片不知道目标** ✓」（`docs/34:50`）、§4.4「卡片侧**不感知**这些连接 ✓」（`docs/34:265`）。
  实现里 stage 带 `role`（`runner.ts:44`）、`detail` 带客机上的目录（`runner.ts:465`
  「在 `${dir}` 里没找到 `${pattern}`」）、`value` 带客机上的绝对路径（`runner.ts:508`）与
  **文件内容**（`readback.ts:170` → `runner.ts:672`）。
  → **role 名 + 一条路径就足以反推出「哪个 role 是板子」**——§一 那句话在自己的返回形状上就失效。
- **而且这条通道不受任何读权限约束**：`spec/03:60` 的 `permissions.read` 是卡片唯一的读权限边界，
  `spec/03:579` 是全契约**唯一一处显式过滤**的先例（「已按 `permissions.read` 过滤」）。
  流程返回是**唯一一条不过这条边界的读通道**，而 v2 §3.7·5 只有一句「要过滤」（`docs/34:223`）。
- **32-I6 建议的是「逐字段规定」**（`role`/`detail`/`value`/`outputs` 默认不给卡片 + 脱敏 + 口径），
  v2 **一个字段都没列**。
- **建议**：契约逐字段规定 `stages[]`：
  `stepId / kind / ok / verified / reason / audit_id / at / durationMs` 给卡片；
  **`role` / `detail` / `value` / `outputs` 默认不给**；
  要给则按「本卡可见的目标集合」过滤 + 路径脱敏（只给 basename 或相对路径）。

#### **V2-I7 · §三·3.5·5 与 §三·3.5·1 打架：「五形式不变」 vs 「形式 1 直接报错」；ADR-D32 要求的「判据词汇分两类」没做**

- **证据**：§3.5·1「**五形式不变**（tag / file_equals / command_ok / verify / none ✓）——**不新增第六种** ✓
  （ADR-D31 R3 ✓）」（`docs/34:185`）↔ §3.5·5「**形式 1（tag）暂不支持**……→ **直接报错**」（`docs/34:189`）。

- **为什么是问题**：ADR-D31 R3 的原文是「**成功判据统一复用 M6 回读五形式**（tag / file_equals /
  command_ok / verify / none）」（`docs/05:1096`）——v2 把「复用五形式」**缩成「支持四种」**。

  而实现的报错信息（`format.ts:526`）与契约的字面**冲突**。
  这不是文字游戏：31-I3 的原话是「**形式 1 根本不能指名角色**……而且**写上去不报错**——
  本工程治的就是这个（`spec/03:110`「被静默忽略的字段，就是拼错的字段」）」——
  **报错是对的方向，但契约的措辞要跟上**。
- **另外**：ADR-D32 §二（`docs/05:1183-1184`）明确留了一条待办：
  「**流程层晋升契约时，回读词汇要分「目标内」与「跨目标」两类**（进 `docs/06-契约核对.md` 的视野）」——

- **建议**：① 契约写「首版支持形式 2–5；**形式 1（tag）保留位置但首版报错**，
  理由：流程层没有板型包，查不了核心词表（`spec/00:129` SPEC-D9）」；
  ② 按 ADR-D32 §二 把判据词汇分成「目标内」与「跨目标」两张表，各列允许的形式。

## 四 · 逐条答复提案 §九「请评审重点看的这六条」

> **1. §二 的信任模型（五本账 / 五条规矩）——「谁批准」这条线够不够？**

**不够，但已经过了及格线。**

- **够的部分**：三本账的划分是对的，**而且有执行者**：
  注册表（`registry.ts:86-131`）、批准账（`registry.ts:148-189`，摘要绑定 ✓）、审计（`runner.ts:237-244`）。
  T1「放文件 ≠ 批准」✓、`T2`「批准绑摘要」✓（`registry.ts:126`）、
  T3「只按 id 取」✓（`service.ts:107` + `registry.ts:139-159`）、
  T4「过地板」✓（`executor.ts:181` + `runner.ts:622`）、
  T5「不许绑 local」✓（`targets.ts:131-135`）——
  **五条规矩全部有条款、有实现、有单测**。这是 v1 → v2 最大的增量，**记功**。
- **不够的部分**：① **卡级授权这一维仍然空着**（32-C4 / V2-C2）——
  「谁批准了这个**包**」答了，「谁批准了**这张卡用这个包**」没答；
  ② **确认链没有落点**（V2-C1）——「destructive 每次都要人确认」在契约与实现里都是**空的**；
  ③ **确认界面展示什么**没有规格（§三·缺口 16）；
  ④ **跨机写与跨机身份**两条没有（V2-I4 / 32-I4）；
  ⑤ §二·2.3 说「两条路都写进**同一本**批准账 → 卡片与 agent 看到的是**同一份授权**」——
  **这在实现里不成立**：包批准在 `workflows-approved.json`，
  卡片授权在 `grants.json`（`src/main/cards/grants.ts`），**是两本**。
  v2 把它们说成一本文，恰恰是 32-C4 反对的那种合并。

> **2. §一 的形状（卡片选流程 = 选目标）——产品判断**

**本评审不答（越权），但有两句必须说。**

- ① 「本机编译」与「客机编译」是**两个流程包** —— 这个形状**可行**，成本可接受，
  `docs/24` 提的组合需求（先客机编译再传板子）由**流程包**表达（`file.transfer` 就是那个语义）✓。
- ② **「目标不进契约」这句话现在是不准确的**（V2-C2 附带的 A10）：
  `roles` → `profile id` 的绑定被**写进了新增的契约文件**（`docs/34:120`），
  而 ADR-D33 D33-1（`docs/05:1223`）说的是「绑定**写在宿主侧**」。
  → **要么**把 §一 的措辞改成「卡片侧看不见目标；流程包这个**数据格式**里有 `roles` 这个字段
  （它不是卡片 manifest 的词汇 —— `spec/03:585-601` 里没有 target/role/connection 任何一个词）」，
  **要么**承认这就是 D7 的一部分、**交回用户拍板**。**现在这样两头不靠**。
- ③ 这一条的**代价**（「卡片不能自己拼多步组合」）v2 写得很诚实 ✓（`docs/34:52-54`）——
  这条要**进 ADR-D34**，别只写在提案里（31 §六·1 的原话）。

> **3. §三·3.6 的占位符与两种替换模式——注入防线写全了没有？**

**大体写全了，但有一处与实现对不上、一处缺一条。**

- **五种占位符 ✓**、**两种替换模式 ✓**、**命令模式=注入防线 ✓**（`docs/34:192-214`），
  且**与实现一致**：命令模式里输入按类型编码（`runner.ts:127` → `encoder.ts:59-104`）、
  槽里的路径包引号（`substitute.ts:59-63`）、**角色事实也包引号**（`substitute.ts:68-79`）✓。
  **这是 v1 的 I2 + 32-I2·1 一起解决掉的，做得好。**
- **对不上的一处**：`docs/29:163` 的两种替换模式表里，角色事实仍写「**原样**（它是宿主自己的连接信息 ✓）」——
