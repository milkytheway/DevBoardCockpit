## 〇 · 一句话结论

> **当前架构 hold 不住这个需求——不是"不够优雅"，是缺四个概念：**
> **任务（Job）· 目标角色（Role）· 跨目标直传 · 非标量结果通道。**
>
> **要重构的不是「信息怎么显示」，而是「一件事怎么做」**：
> 把这个闭环从卡片的 JS 里提到宿主，做成**流程包（workflow pack）**——
> 与「板型包」并列的第二个数据包，回答「这件事怎么做」，而不是「这块板有什么」。

## 一 · 前因后果

### 1.1 触发点：一个具体的卡片需求

用户提出这样一个卡片（2026-11-14）：

> 做一张卡，里面有控件和观察窗口。用户可以选择**本机**或者**客机**上的代码，
> 选完点**编译**，然后把编译产物**上传到板子上的选定位置**，再点**加载运行**，
> 并且能**观察过程中的中间结果**（在卡上看，或者在右侧信息面板上看都行）。

这不是一个假想的卡片——它是这个产品**最典型的使用场景**：开发板驾驶舱的核心用途，
就是「改代码 → 编译 → 刷上去 → 跑起来 → 看结果」。

### 1.2 为什么这个需求会逼出架构问题

因为它同时踩了四条当前架构**没有覆盖**的路：

| 维度 | 这个卡片要做的事 | 当前架构有没有 |
|---|---|---|
| **多目标** | 源在**本机**或**客机**，产物要落到**板子** | 只有「板子」是动作的宿主（板型包是每类板一份） |
| **长时** | 编译可能几分钟到几十分钟 | `exec()` 同步 + 超时；没有任务、没有取消 |
| **跨目标搬运** | 客机编好的产物 → 板子 | `pull`/`push` 的语义是「**宿主** ↔ 一个目标」 |
| **非标量结果** | 编译日志、传输进度、运行输出 | tag 只表达**标量量测**（`SPEC-D4`） |

**关键判断**：这四条里，前三条是"缺能力"，第四条是"缺通道"。
但它们背后是**同一个结构性问题**——

> **当前架构里，"策略"只能住在卡片里。**
>
> 卡片能读 tag、能调已声明的动作，但**没有任何"编排"原语**：
> 没有条件、没有阶段、没有任务、没有跨目标编排。
> 于是「多目标 + 多条指令 + 一个闭环」这件事，只能由卡片自己用 JS 拼出来。

### 1.3 一路推演（三步）

**第一步：这个卡片做不出来。**
不是因为卡片沙箱不够用（它能订阅 tag、能 invoke 声明过的动作），
而是因为卡片**没有文件 API、没有目标枚举 API、没有任务 API**。

**第二步：那把这个闭环放进宿主？**
放进宿主后发现：宿主需要能表达
「在哪台机器上跑」「跑多久」「产物是什么」「怎么搬到另一台」「什么时候算成功」。
**这些词在现有契约里一个都没有。**

**第三步：所以要一个新概念——流程包。**
它不是"再加一个 UI 抽象层"，而是**补上"编排"这一维**：

```
位号（tag）        = 这个板子上的一个量          「有什么」
板型包（board pack）= 这块板怎么产生这些量、能接受什么写  「这块板能做什么」
流程包（workflow pack）= 这件事怎么做（多目标、多阶段、有条件）  「这件事怎么做」
```

### 1.4 为什么现在写这份文档（时机）

| 事实 | 出处 | 对时机的影响 |
|---|---|---|
| **M6 控制面还没开工** | `src/main/` 下**没有** `actions/` 目录；`docs/17` §六 列 M6 为"下一个主线"（动作执行器 + 参数编码 + 授权 + 回读 + 审计 + 确认 sheet） | 流程包是 **M6 的延伸**，现在做是"扩 M6"；M6 写完再抽 = **二次重构** |
| 契约层已冻结且**语言中立** | `docs/spec/` 五份 + `apiVersion: devboard/v1` | ⚠️ **此栏已被评审推翻**（`docs/28` R1）：流程包若进 `docs/spec/` **就是契约层**（`AGENTS.md:21`），而它的下游（执行器/授权/审计/回读）**全都没实现** → **首版不进 `docs/spec/`**，格式先落 `docs/` + `fixtures/`，真板跑通两条后再晋升 |
| 已有机制全在 | 卡片宿主 / 沙箱 / 权限 / 布局 / tag 五态 / 假设备 | 流程包是**加法**，不是重写 |
| e2e 不认 class 名 | `data-cockpit-drag-handle` / `cardsList()` | 卡片可以自由重画，流程包的呈现层不受牵连 |

> **一句话时机**：**M6 是这套架构里最后一个"控制面"的入口。**
> 流程包要用的执行器、授权、审计、回读，全都是 M6 要造的东西。
> **一起设计，比事后抽便宜得多。**

## 二 · 现状：当前架构 hold 不住什么（逐条带证据）

### 2.1 连接层的真实形状

`src/main/hal/connection.ts` 的 `Connection` 接口（🟢 实测）：

| 方法 | 语义 | 对这个卡片够不够 |
|---|---|---|
| `exec(cmd, {timeoutMs})` | 同步执行一条命令 | ❌ 编译要几分钟；**没有任务、没有取消、没有进度** |
| `pull(remote, local)` / `push(local, remote)` | **宿主 ↔ 一个目标** | ❌ 客机 → 板子**直传**做不到，只能绕宿主中转两跳 |
| `list(path)` | 列远端目录 | ✅ 但**卡片调不到**（卡片 API 里没有文件操作） |
| `openSession()` | 开一个交互式会话（终端用） | ⚠️ 不是"跑一个进程并收集它的输出" |
| `capabilities()` | 能力协商 | ✅ |

> **关键读法**：`pull`/`push` 的两端是「**宿主**」和「**一个目标**」。
> 这就是为什么"客机 scp 直达板子、宿主全程不碰产物"（学习工作区 2026-11-14 实测跑通的路）
> **在驾驶舱里表达不了**——那条路没有对应的接口形状。

### 2.2 卡片 API 的真实形状

契约 `docs/spec/03` §7.7 给卡片的**全集**是 13 个方法（`tags.*` 5 个、`storage.*` 5 个、
`degradation`、`capabilities`、`log`、`notify`），加上 §五 的 `actions.invoke`。

> ⚠️ **本 build 实有的只有 12 个**（`src/main/cards/api-registry.ts`），
> **没有 `actions.invoke`**（写侧属 M6，尚未开工）——
> 卡片调它会得到 `unknown_method`。卡片能知道自己支不支持什么：`capabilities().methods`。

- ✅ 能读标量位号、能存自己的数据、能写自己的运行时日志。
- ❌ **不能列文件**、**不能枚举目标**、**不能起任务**、**不能拿流**。
- ⚠️ 「不能列文件」**只对卡片成立**：外壳层已经有 `filesList` / `filesPush` / `filesPull` / `connectionsList`。

### 2.3 契约早就划了两条边界（本文沿用，不推翻）

| 编号 | 原文 | 出处 |
|---|---|---|
| `SPEC-D4` | **标签只描述标量量测，连续流不是标签**。视频流、日志流、文件内容塞进 tag 词汇表会污染它。流走另一条 API | `spec/00` §六 |
| `SPEC-D20` | 取数侧接口统一为 **Source**，`kind ∈ {poll, push}`，v1 只实现 poll。**接口层已预留** | `spec/00` §六 |

**这两条正好是流程包的接口基础**：
- `SPEC-D4` 决定了**流程的中间结果不能做成 tag**（编译日志不是位号）；
- `SPEC-D20` 说的是**取数侧**（Source → TagStore 供标量），**不是流程时间线**；
  `spec/00` §七 明写「连续流的契约…**没定死**」。
  → **时间线是一条新通道**（`docs/28` R9）：首版形状 **poll**（卡片轮询），不订阅。

### 2.4 逐环节对账

| 卡片里的步骤 | 需要的能力 | 现状 | 结论 |
|---|---|---|---|
| 选代码源（本机 / 客机） | 卡片能列文件、选路径、枚举目标 | 卡片 API 无文件 / 无目标枚举 | ❌ 做不了 |
| 编译（客机 `make`，几分钟） | **任务**：启动、流式输出、取消、阶段状态 | 只有同步 `exec` + 超时 | ❌ 做不了 |
| 传输产物（客机 → 板子） | **跨目标直传** + 进度 | `pull`/`push` 只连宿主 | ❌ 做不了（只能两跳中转） |
| 落到板子规范位置 | 板子的落位知识（`.ko` → `extra/`、可执行 → `/usr/local/bin/`） | 知识在**学习工作区**的 `板子放置规范.md`，驾驶舱里没有 | ⚠️ 缺载体 |
| 加载运行 | 长时任务 + **持续输出** | 只有交互式 `openSession()` | ⚠️ 语义不匹配 |
| 观察中间结果 | **非标量通道**：阶段、进度、日志、产物 | tag 只表达标量（`SPEC-D4`） | ❌ 无处安放 |
| 闭环被审计 | 一次闭环的完整时间线 | 审计只有**单次动作级** | ❌ 拼不出"这次卡在哪一步" |

### 2.5 结论：缺的是四个概念

| # | 缺的概念 | 是什么 | 为什么不能靠现有东西凑 |
|---|---|---|---|
| **1** | **任务（Job）** | 长时、可取消、流式、阶段化的一等公民 | `exec` 是同步调用，超时就是失败——编译不是失败，是还在跑 |
| **2** | **目标角色（Role）** | `source` / `build` / `target` 这类**角色**，而不是"板子" | 板型包是每类板一份；"在客机上编译"不属于任何板型 |
| **3** | **跨目标直传** | 产物从 A 目标直接到 B 目标 | 现有传输两端固定是"宿主 ↔ 目标" |
| **4** | **非标量结果通道** | 阶段状态 / 输出流 / 进度 / 产物清单 | `SPEC-D4` 已经把流排除在 tag 之外了（这是对的） |

> 这四个概念**互相咬合**：没有角色就没有跨目标；没有任务就没有阶段；
> 没有阶段就没有可审计的时间线；没有非标量通道，阶段就只能显示成几个数字，
> 又回到"读数之外什么都没有"。

## 三 · 设计

### 3.1 五层分层（改动落点固定）

```
┌─ ⑤ 呈现层 ─────────────────────────────────────────────┐
│  卡片 / 右侧检查器 / 日志页 / MCP 视图                    │
│  只消费「流程状态流」，不自己拼策略                        │
├─ ④ 执行层（宿主）────────────────────────────────────────┤
│  Job 调度 · 阶段推进 · 输出流 · 取消 · 审计时间线           │
│  ← 与 M6 的 executor / 授权 / 审计是同一条服务路径          │
├─ ③ 绑定层 ─────────────────────────────────────────────┤
│  role → connection（哪个板 · 哪条通道 · 哪种传输）         │
│  换板子 / 换传输 = 只改这里                               │
├─ ② 定义层（流程包）──────────────────────────────────────┤
│  一串步骤 + 参数 + 阶段 + 权限诉求 + 产物声明              │
│  ← 与板子无关、与传输无关                                 │
├─ ① 语义层（step kind）──────────────────────────────────┤
│  封闭清单 · 参数化 · 版本化 · 逃生门                        │
│  ← 与板子无关、与传输无关、与 UI 无关                      │
└──────────────────────────────────────────────────────────┘
        ↑ 引用
   板型包（board pack）：落位知识 / 动作 / 可写路径
   tag 契约：完成判据（五态）
```

**读法**：要改的东西永远落在**一层**里，
每层的输入是上一层的输出，**没有哪一层需要知道下一层的存在**——
和「卡片不知道板子是谁，只认识 tag 名字」是同一条依赖规则。

### 3.2 流程包是什么

| | 板型包（board pack） | **流程包（workflow pack）** |
|---|---|---|
| 回答 | 这块板**有什么**、能接受什么写 | 这件事**怎么做** |
| 归属 | 每类板一份 | 每个流程一份，**可跨板** |
| 里面 | readers→tags、actions、落位知识 | 步骤、参数、阶段、权限诉求、产物声明 |
| 谁执行 | 宿主（位号运行时 / 动作执行器） | 宿主（流程执行器） |

**并列为两个数据包**，不是把流程塞进板型包：
"这块板装 `.ko` 要去 `extra/`" 是**板子的规矩**（板型包）；
"我这个流程要装 `.ko`" 是**这件事的要求**（流程包）。

### 3.3 step kind：封闭清单 · 参数化 · 版本化 · 逃生门

**这套套路是本项目已经验证过的**——板型包的 reader kind 就是同一招
（`spec/02` §2.2：`纯声明式` 表达不了"两次采样做差""跨文件 join"，
硬做会长出一套微型表达式语言，**比代码更糟**）。

> **所以流程包也不做通用表达式语言。** 只给一个**封闭的、有版本的**步骤清单。

| kind | 做什么 | 关键参数 | 产出 |
|---|---|---|---|
| `file.fetch` | 从某角色取文件/目录到某角色 | from(role,path) → to(role,path) | 文件 |
| `exec` | 在某角色跑一条命令 | role, cmd, cwd, timeout, env | 退出码 + 输出流 |
| `artifact.transfer` | 把产物从 A 角色搬到 B 角色 | from(role,path) → to(role, placement) | 文件（**直连，不经宿主**） |
| `artifact.deploy` | 落到板子的规范位置 | placement(语义) → 由**板型包**解析成路径 | 文件 + 落位说明 |
| `launch` | = `exec` + `stream: true`（**不是另一个 kind**——三路评审一致指出的冗余） | role, cmd, stream | 退出码 + 输出流 |
| `await` | 等某个 **tag** 达到期望 | tag, op, value, timeout | tag 值 + 状态 |
| `assert` | 断言某个前置条件 | tag/param, op, value | — |
| `note` | 在时间线上记一笔（给人看） | text | — |

**两条设计红线**：

1. **`placement` 是语义，不是路径。** 流程说 `kernel-module`，
   板型包说"这类板子上 kernel-module 放 `/usr/lib/modules/$(uname -r)/extra/`"。
   → **换板子不改流程**。
2. **`await` 的判据是 tag，不是字符串。** "板子说起来了"的标准就是一个位号
   （五态齐全：ok/stale/unavailable/error/pending），
   → **闭环与 tag 契约缝在一起，不另造成功判定**。

### 3.4 流程包格式（草案）

```yaml
# workflows/hello-kernel/build-run.yaml
apiVersion: devboard/v1
kind: Workflow

id: hello-kernel.build-run
name: 编译内核模块 → 装板 → 运行
version: 1.0.0
description: 在构建机编译 01-hello 内核模块，装到板子规范位置，跑起来看输出

inputs:
  project:
    type: string
    required: true
    maxLength: 200
    description: 项目目录名（相对 source 角色的工作根）

roles:
  source:  { purpose: 代码所在 }
  build:   { purpose: 编译所在, expects: [exec, files] }
  target:  { purpose: 板子,     expects: [exec, files] }

steps:
  - id: sync
    kind: file.fetch
    params:
      from: { role: source, path: "{project}" }
      to:   { role: build,  path: "build/{project}" }

  - id: compile
    kind: exec
    params:
      role: build
      cmd: "make -C build/{project} modules"
      timeout: 1800s          # 编译是分钟级的，不是命令级
    produces: ["*.ko"]        # 产物**发现**（不写死文件名）

  - id: deliver
    kind: artifact.transfer
    params:
      from: { role: build, path: "build/{project}/{product}" }
      # 目的地三形态：**path（用户指定）** | **placement（语义默认）** | **ask（现场问）**
      to:   { role: target, placement: kernel-module }
    # 路径由板型包解析 → 换板子不改这一行

  - id: load
    kind: exec
    params:
      role: target
      # ⚠️ **不用 `insmod /path/x.ko`** —— 板子放置规范 §4 硬规矩 2：
      #    装进 extra/ + depmod -a + **modprobe <名字>**（按名字加载，不需要写路径）
      cmd: "depmod -a && modprobe {module_name}"
    readback: { kind: command_ok }     # 真判据：不是 tag（编译/加载不是板上的量测）

  - id: run
    kind: launch
    params:
      role: target
      cmd: "modprobe {module_name}"
      stream: true
    readback: { kind: verify, timeout_ms: 30000 }

permissions:
  write: [exec, files]        # 写权限诉求 → 宿主授权时按动作粒度问

observability:
  timeline: true               # 每次运行产出一条时间线
```

### 3.5 角色绑定（role → connection）

流程包**不指名任何具体设备**。绑定是运行时的另一份数据：

```yaml
# profiles/workflows/hello-kernel.yaml
workflow: hello-kernel.build-run
bindings:
  source: { profile: local }                        # 本机
  build:  { profile: ubuntu-ssh }                   # 客机（VMware 里的 Ubuntu）
  target: { profile: board-adb }                    # 板子（走 ADB）
```

**换传输 / 换板子，改的是这份绑定，不是流程**：

```yaml
  target: { profile: board-ssh, host: 192.168.5.100 }   # 换成网线 + SSH
```

### 3.6 状态机与阶段时间线

**运行态**：

```
idle ──▶ armed ──▶ running ──┬─▶ confirmed     回读符合预期
                 │            ├─▶ unconfirmed   命令成功但回读不符（状态存疑）
   （绑定缺失/权限不足）        ├─▶ failed        某阶段失败（带阶段 id 与错误）
                 │            └─▶ cancelled     用户中止
                 └─▶ denied       授权/策略拒绝
```

**每一步产出一条时间线记录**（这是"统一管理和分析"的载体）：

```jsonc
{
  "runId": "wr-2026-11-15-0007",
  "workflow": "hello-kernel.build-run",
  "state": "confirmed",
  "startedAt": 1763155200000,
  "endedAt":   1763155620000,
  "stages": [
    { "step": "sync",    "state": "ok",      "ms": 8200,  "bytes": 1048576 },
    { "step": "compile", "state": "ok",      "ms": 318000, "exitCode": 0, "tail": "…CC [M]  Building modules" },
    { "step": "deliver", "state": "ok",      "ms": 2400,  "bytes": 15360 },
    { "step": "load",    "state": "ok",      "ms": 610,   "exitCode": 0 },
    { "step": "run",     "state": "ok",      "ms": 30000, "exitCode": 0 }
  ],
  "readback": { "kind": "command_ok", "step": "load" },
  "audit": { "by": "user|agent|mcp", "at": 1763155200000 }
}
```

> 对比现状：现在的审计日志是「**每次 action 一行**」。
> 流程包产出的是「**一次闭环一条时间线**」——
> 能回答"这次编译花了 5 分 18 秒、在哪一步失败、失败时板子什么状态"。

### 3.7 权限与审计

| 规则 | 说明 |
|---|---|
| **授权粒度不变** | 流程里的写动作仍走 M6 的动作授权（按动作 id，`reversible` 问一次、`destructive` 每次问） |
| **流程不自带权限** | 流程包只声明**权限诉求**（`permissions.write`），实际授权在宿主、用户手上 |
| **dry-run 要能走通全链** | 列出"将要执行什么"而不执行（含目标、命令、产物路径） |
| **失败要能回滚/重跑** | 时间线带 stage id → 可以从某阶段重跑（首版不做，但要留位置） |

### 3.8 与既有资产的关系（几乎全是复用）

| 既有资产 | 在流程包里怎么用 |
|---|---|
| **tag 契约（五态）** | `await` / `assert` 的判据；回读结果的状态 |
| **板型包** | `placement` 的解析（落位知识）、可写路径、动作定义 |
| **reader kind 的封闭清单套路** | step kind 的封闭清单套路 |
| **`spec/02` 的"纯声明式走不通"教训** | 直接作为"不做表达式语言"的依据 |
| **M6 的 executor / 授权 / 回读 / 审计** | 流程执行器**调用**它们，不另造一套 |
| **`docs/21` §4.4「过滤与授权一处做、MCP 与卡片共用同一条服务路径」** | 流程执行器就在那条路上 |
| **e2e 稳定钩子** | 呈现层随便改，判据不变 |
| **假设备** | 流程可以在假设备上演练（不出真板） |

### 3.9 反目标（做成这些也算失败）

- ❌ **不引入通用声明式渲染管线**——卡片类型学（半圈表盘、寄存器位组）是这个产品的卖点。
  **渲染归卡片，策略归宿主。**
- ❌ **不做通用工作流引擎**（DAG、循环、条件分支、变量、模板引擎）——那是另一个产品。
  首版只有**直线流程 + `await` + `assert`**。
- ❌ **不把流程塞进板型包**——板型包是"这块板"，流程包是"这件事"。
- ❌ **不让卡片自己执行流程**——卡片只订阅状态流、发起启动/取消请求。
- ❌ **不改已冻结的契约语义**——新增 API 是兼容的，但契约文档要改，要走评审（§九）。

## 四 · 示例用法

### 4.1 例一：编译 → 装板 → 运行（真实存在过的流程）

**这不是编的**——学习工作区的 `90-工具/buildrun.py`（2026-11-14 实测跑通）做的是同一件事：

| buildrun.py 做的事 | 流程包里的对应步骤 |
|---|---|
| 把项目目录传到 Ubuntu 客机（SDK 与两套工具链在那儿） | `sync`（`file.fetch`，source → build） |
| 在客机里 `make`（`ssh_run` 超时 **1800 秒**） | `compile`（`exec`，timeout 1800s，产出 `hello.ko`） |
| 取回产物 → `adb push`；或**客机自己 scp 直达板子** | `deliver`（`artifact.transfer`，build → target，直连不经宿主） |
| 装到规范位置（`.ko` → `/usr/lib/modules/$(uname -r)/extra/`，可执行 → `/usr/local/bin/`） | `placement: kernel-module` → **板型包**解析成路径 |
| `adb shell` 跑起来，输出原样打出 | `run`（`launch`，stream） |

**注意 `ssh_run` 的超时是 1800 秒**：这就是"命令"和"任务"必须分家的实证——
现有 `exec(cmd, {timeoutMs})` 的形状，天然表达不了"跑 30 分钟，中途要看、要能停"。

### 4.2 例二：换传输 / 换板子——只改绑定

今天（2026-11-14）学习工作区刚做过一次这样的切换：
**「宿主 adb push」→「客机 scp 直达板子 192.168.5.100，宿主全程不碰产物」，adb 降级为兜底。**

| | buildrun.py（脚本） | 流程包 |
|---|---|---|
| 换传输 | 改命令行参数 `--transport net\|adb` | 改绑定里 `target` 的 profile / 传输策略 |
| 换板子地址 | 改 `--board 192.168.5.100` | 改绑定里 `target` 的 host |
| 换板型（落位规矩变了） | 改脚本里的路径常量 | 改**板型包**的 `placement` |
| **流程/卡片要不要改** | 脚本本身要改 | **都不改** ✅ |

**这一格就是整个重构的收益所在**——而且它是**活的**：本机本周就在经历这种切换。

### 4.3 例三：agent 经 MCP 触发

今天 agent 在驾驶舱里能做的，只有"MCP 工具列出的那些"（`spec/04`）。
"帮我把这个模块编了推到板子上跑起来"——**做不到**，因为：

- "编译"不是板型动作（它在客机上）；
- 跨目标搬运没有接口形状；
- 没有任务，agent 无法知道进行到哪一步。

有了流程包：

```
agent → run_workflow("hello-kernel.build-run", {source: "local"}, {dry_run: false})
      → 拿到 runId
      → workflow_timeline(runId)   ← 订阅/轮询时间线
      → 看到 compile 用了 5 分 18 秒、deliver 2.4 秒、run 正常退出
      → 卡片那边同步显示同一条时间线
```

**注意这里的关键差别**：agent 触发的**不是一串裸命令**，而是**宿主已声明的一个流程**——
和今天 agent 只能触发"宿主已声明的动作"是同一个安全模型，只是粒度从"一步"变成"一件事"。

### 4.4 例四：一张只读卡 vs 一张带闭环的卡

| | 只读卡（今天 80% 的卡） | 带闭环的卡（今天做不出来的那种） |
|---|---|---|
| 卡片职责 | 订阅 tag，画 | **订阅流程状态流**，画 |
| 谁做策略 | 无 | 宿主（流程包） |
| 谁做长时任务 | 无 | 宿主（Job） |
| 换板子 | 不用换（tag 稳定） | 改绑定 |
| agent 能不能触发 | ❌（只读） | ✅ |
| 能不能审计 | 一次读数一行 | **一次闭环一条时间线** |

**这张表就是判据**：左边那一列流程层帮不上忙，右边那一列全都靠它。

## 五 · 优势与潜力

### 5.1 判据：什么时候值得抽出来（四问）

> **这个闭环是否要被 ①复用 ②换目标/换传输 ③给 agent 触发 ④被审计？**
> **有一问是"是"，才值得抽出来。**

编译→部署→运行：**四问全中** ✅
纯只读监控卡：**四问全否** ❌（流程层零收益）

### 5.2 优势（改动的隔离度）

| 你要改的 | 只改哪层 | 卡片要动吗 | 流程包要动吗 |
|---|---|---|---|
| 换板子 / 板子地址 | ③ 绑定 | ❌ | ❌ |
| 换通信方式（adb ↔ scp ↔ 网线） | ③ 绑定 | ❌ | ❌ |
| 换落位规范 | 板型包 | ❌ | ❌ |
| 换编译器 / 工具链 / make 目标 | ① ② | ❌ | ✅ |
| 换"成功"怎么判定 | ①（判据用 tag） | ❌ | ✅ |
| 换呈现（表格 / 仪表 / 进度条） | ⑤ | ✅ | ❌ |
| 换流程的步骤顺序 | ② | ❌ | ✅ |

> **用户原话「最大化的设计复用以至于同样的需求修改其中任何细节都不会导致整个重做」——
> 上表就是它的可执行版本。**

### 5.3 潜力（三条）

**潜力一 · 护城河从"能看"扩到"能干活"。**
今天这个产品的独特性是"AI 能造卡"。加了流程包之后，**AI 还能造"流程"**——
而流程是比卡片更值钱的东西：卡片是展示，流程是**能力**。
一个会写流程的 agent，比一个会写卡的 agent，跨出的步子大得多。

**潜力二 · 时间线是一份新的数据资产。**
每次闭环产出一条结构化时间线（阶段 · 耗时 · 退出码 · 回读 · 输出）。
攒下来之后可以回答今天答不出的问题：
「我的编译→部署→运行闭环，**中位数**花多久？哪一步最容易卡？换网线之后省了多少？」
——这是**只有驾驶舱这种"每次干活都经过"的工具才攒得出来的数据**。

**潜力三 · 「一件事」成为可交易单元。**
流程包 + 绑定 = 一件**可命名、可授权、可审计、可分享**的事。
「装模块并跑起来」「抓一次日志并归档」「跑一遍回归」——
今天这些是散落在人脑里的操作序列；之后它们是仓库里的文件。

### 5.4 不划算的情况（诚实说）

- **80% 的只读卡**（CPU 曲线、温度表）——流程层对它们零收益。
- **只有一张卡、一个固定流程、永远不换目标、也不给 agent** → 写在卡片里更省事。
- **流程只有一个步骤**（就是跑一条命令）→ 那就是一次 action，不需要流程包。
- **首版不做 DAG/循环/分支**——真出现这类需求再谈（`spec/02` §2.2 的教训）。

## 八 · Insight（几条判断）

**一 · 「位号 vs 板型包」是同一个套路的第一次应用，流程包是第二次。**
同一个套路用第二次，说明**它不是偶然**——它就是这个产品扩展性的骨架：
**语义与实现分离**。tag 是语义、板型包是这块板的实现；
流程包是"这件事"的语义、板型包+绑定是它的实现。

**二 · 用户感受到的"耦合"其实是策略耦合，不是渲染耦合。**
「同一个信息换一张简单卡片」**本来就不需要新抽象**——
两张卡订阅同一个 tag 即可（tag 是稳定词汇表，这正是契约的价值）。
把"渲染"和"策略"分开看，是这次讨论最关键的一步；
**如果不分，就会去做一个通用渲染 DSL，把卡片类型学掐死。**

**三 · 契约的"封闭清单"是本项目已经验证过的扩展机制——但它也会失败。**
reader kind 成功了（**加板型不用改代码**），所以 step kind 也会成功。
但同一个套路在另一种形态下会失败：如果 step kind 变成通用表达式语言，
就重蹈 `spec/02` §2.2 的覆辙。**封闭清单 + 参数化 + 逃生门**是它的正确形态——
逃生门留，但不在首版。

**四 · 解耦不是为了少写代码，是为了"改细节时不用重写"。**
这正是用户说的「最大化的设计复用」。衡量它的指标不是代码行数，
而是**改动落点的层数**（§5.2 那张表）。

**五 · 把闭环搬进宿主，卡片变简单了，但产品变复杂了。**
多了一个数据包、多了一层绑定、多了一种要理解的概念。
值不值，取决于 §5.1 那四问。**不是所有卡都该走流程层**——
诚实地说，这条路会让"只想画个曲线"的人也要理解流程包。

**六 · 中间结果不是 tag（`SPEC-D4`），所以"观察窗"不能靠现有通道。**
这条早就写在契约里了，只是没人碰到"编译日志"这种需求。
**契约写对的价值，是在新需求来的时候少一次返工。**

**七 · agent 的能力边界 = 宿主已声明的东西的边界。**
今天 agent 只能做"MCP 工具列出的那些"。流程包会把这条边界
从"单个动作"扩到"一整个流程"——**这才是护城河真正变深的地方**。

**八 · 一个可以立刻验证的小实验。**
不必先设计完整流程包：**拿 `buildrun.py` 的能力，用现有契约先表达一遍**
（角色 = local / ubuntu-ssh / board-adb，步骤 = fetch → exec → transfer → exec），
看它能不能在当前架构里被完整描述。
**如果描述不出来，就证明确实需要新概念；如果能，说明缺口比想象的小。**
这个实验的代价是一张 YAML，收益是**避免为不存在的问题设计一整套机制**。
