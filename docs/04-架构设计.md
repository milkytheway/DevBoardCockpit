## 1. 目标与非目标

### 1.1 目标

1. **统一工作台**：串口 / ADB / SSH 三通道接入板子与 Ubuntu 客机，终端、文件互传、
   状态监控、显示输出在同一 GUI 内完成。
2. **语义 tag 契约**：板子能力 = 稳定位号；卡片只订阅位号，不关心板型。
3. **卡片系统**：卡片即文件；AI 写完即生效；热插拔；沙箱隔离。
4. **控制闭环**：写动作后回读位号，UI 以回读为准。
5. **MCP 协作**：宿主机 AI agent 通过 MCP 感知现状、写卡片、触发动作、自测迭代。

### 1.2 非目标（本期不做）

| 不做 | 理由 |
|---|---|
| 板端长期服务 / systemd | 板子是 Buildroot + eudev；Tier 2 推流留到有视频需求时 |
| 多用户 / 权限体系 | 单人桌面工具 |
| 跨平台 | 宿主是 Windows；跨平台留接口不留实现 |
| 卡片市场 / 远程分发 | 先做本地目录热插拔 |
| 与旧 Python 工程并存运行 | 明确切干净，避免两套真相 |
| **改动契约语义** | 契约是权威；要改先改 `docs/spec/` 并升 `apiVersion` |

## 2. 总体架构

### 2.1 进程模型

```
┌─ Electron main（设备、契约执行、MCP）────────────────────────┐
│  hal/       连接层 HAL：serial │ ssh │ adb │ local + 能力协商      │
│  tags/      位号层：reader kind 注册表 │ poll group 调度 │ 绑定    │
│  actions/   控制面：分级判定 → 执行 → 回读 → 审计                 │
│  cards/     卡片注册表：manifest 校验 │ 协议托管 │ 热重载          │
│  mcp/       MCP server（HTTP 回环 + token）——与卡片注册表同进程  │
│  profiles/  连接 profile + 板型包加载与校验                       │
└───────────┬─────────────────────────────────────────────────────┘
            │ IPC（invoke/handle + 事件推送）
┌───────────▼─────────────────────────────────────────────────────┐
│ Electron renderer（只画，不碰设备）                              │
│  layout/   网格布局引擎（react-grid-layout）                     │
│  cards/    卡片宿主：sandbox iframe + `cockpit.*` 白名单桥        │
│  terminal/ xterm.js                                             │
│  panes/    文件浏览器 │ 日志工作区 │ 目标切换器 │ 资源条          │
└───────────┬─────────────────────────────────────────────────────┘
            │ postMessage（白名单，无同源）
┌───────────▼─────────────────────────────────────────────────────┐
│ 卡片 iframe：sandbox="allow-scripts"（无 same-origin）           │
│ 入口 index.html；API 见 spec/03（cockpit.tags.get / subscribe …） │
└─────────────────────────────────────────────────────────────────┘

┌─ 磁盘 ─────────────────────────────────────────────────────────┐
│ %LOCALAPPDATA%/DevBoardCockpit/      ← 用户数据目录（可写）        │
│   profiles/boards/<pack>/board.yaml  用户自己的板型包              │
│   profiles/targets/*.json            用户自己的连接 profile        │
│   cards/<card-id>/                   用户自己的卡片                │
│                                     （+ 宿主内置目录，同 id 用户优先）│
│ ── 只读（随应用分发）────────────────────────────────────────── │
│ <app>/profiles/boards/<pack>/        内置板型包（契约 spec/02）     │
│ <app>/profiles/targets/*.json        内置连接 profile（怎么连上）  │
│ <app>/cards/<card-id>/               内置卡片                      │
└─────────────────────────────────────────────────────────────────┘
```

**两个扩展点待遇必须一致。** 卡片根目录已经是「用户目录 + 内置目录合并，同 id 用户优先」，
**板型包与连接 profile 也要走同一套**：

| 扩展点 | 用户目录 | 内置目录 | 同名时 |
|---|---|---|---|
| 卡片 | `%LOCALAPPDATA%/DevBoardCockpit/cards/` | `<app>/cards/` | **用户优先** |
| 板型包 | `%LOCALAPPDATA%/DevBoardCockpit/profiles/boards/` | `<app>/profiles/boards/` | **用户优先** |
| 连接 profile | `%LOCALAPPDATA%/DevBoardCockpit/profiles/targets/` | `<app>/profiles/targets/` | **用户优先** |

**为什么这条重要**：前身工程最顺手的加板路径是「把 JSON 丢进
`%LOCALAPPDATA%/DevBoardConsole/profiles/`，**重启，板子出现**」——
零代码、零 git、零发版。新工程如果只读仓库里的 `profiles/`，
这条路径就断了，而卡片那条路（用户目录 + 内置目录）却保留着——
**同一个工程里两个扩展点待遇不一致**，是最容易让人失望的地方。

**用户目录是唯一可写扩展点**；仓库里的 `profiles/` 与 `cards/` 是只读的内置目录。
运行时扫描两处并合并，冲突时用户优先。

**铁律**：

- renderer **永远不**直接碰设备，一律经 `tags/` 与 `actions/`。
- MCP server 与卡片注册表**同进程**（ADR-D2），
  因此 agent 读到的 GUI 状态与用户看到的完全一致。
- 卡片**永远不**能触碰宿主 DOM / 存储 / 任意消息（spec/03 §六）。

### 2.2 三条数据通路

| 通路 | 方向 | 载体 |
|---|---|---|
| 采样 | 板子 → reader → tag → 订阅者 | `tag:update` 推送 |
| 控制 | GUI / MCP → actions → 板子 → 回读 | `action:execute` → `ActionResult` |
| 感知 | agent → MCP → GUI 内部 | spec/04 的工具集 |

## 5. 采样通路的实现

### 5.1 调度模型

**链路仲裁（LinkArbiter）**：一次往返在链路上是**独占**的，
所以同一时刻只能有一个事务在飞。四级优先级，从高到低：

| 级 | 事务 | 说明 |
|---|---|---|
| 1 | `action-verify` | 动作的**执行 + 回读**是一个不可拆分的独占事务 |
| 2 | `manual-refresh` | 用户手动刷新 / MCP 显式 refresh |
| 3 | `card-sampling` | poll group 的常规采样 |
| 4 | `diagnostics` | 连通性探测等 |

**动作 + 回读不可拆分**是最要紧的一条：回读若被采样插队，读到的可能是
别的命令的输出，「回读不符」就成了假阴性——驾驶舱会显示错的真实状态。

**终端独占**：用户正在终端里敲命令时（事实 S1：串口只有一根线、一个读线程），
托管采样**暂停**，该连接下受影响的 tag 转 `stale` 并带 reason `link_busy_terminal`；
终端空闲 N 秒后恢复采样。**停采必须如实反映成质量，不能静默**——
否则卡片会一直显示一个已经过时的数字，而它看起来是新的。

**每个事务都带 deadline**（连接级默认 3 秒，板型包可覆盖）：
排队超时报 `conn_busy`，队列有上限，满时拒绝新采样并降级。
**无界排队等于把「卡」变成「数据旧」**——那是最难排查的一类故障。

契约已定：板型包用 `poll_groups` 把 reader 分组，每组一次往返、每组一个周期。

```
poll group (fast, 1000ms)  → readers [cpu, gpu, npu]  → 合成一条命令 → 一次往返
poll group (slow, 2000ms)  → readers [mem, temp]
poll group (rare, 30000ms) → readers [board, npu_devfreq]
```

- 每组内部把各 reader kind 的取数 shell 片段合并成**一条**命令，
  段间用标记分隔（等价于旧工程 `SNAPSHOT_SCRIPT` 的 `###` 分段思路）。
- **串口单行压平**：目标不支持多行脚本时（spec/02 要求 kind 片段能压成一行），
  合并结果用 `;` 连接不换行。

**一次往返的互斥**（契约 `spec/02` §1.2.1，ADR-D18）：
同一连接上的采样往返与动作往返进**同一个队列**，一次只有一条在飞。

| 项 | 规则 |
|---|---|
| 优先级 | **动作优先于采样**。动作在队列里等采样时，采样让路 |
| 采样让路 | 错过本周期就**跳过**，不补发（补发的差值窗口已无意义） |
| 超时清理 | 必须等 marker 收齐或明确放弃，才能开始下一次往返 |

这在串口上是硬约束（事实 S1/S2：单通道、单读线程、marker 会出现两次）。
实现落点：`src/main/tags/poll.ts` 的调度器与 `src/main/actions/executor.ts`
共用一个**每连接往返队列**，不是各自轮询。

### 5.2 值与状态

契约定义五态（`ok / stale / unavailable / error / pending`），TS 侧一一对应：

```ts
type TagStatus = 'ok' | 'stale' | 'unavailable' | 'error' | 'pending';
interface TagValue {
  tag: string;
  value: number | string | boolean | null;
  unit: string;
  status: TagStatus;
  at: number;            // 毫秒时间戳（采样完成时刻）
  reason?: string;       // unavailable/error 的原因码（见 06 核对 C5 / 待决 O6）
}
```

**`value` 的类型要覆盖 `enum`**：词表里有 `cpu.governor` 是 `enum` 类型，
TS 侧不能只有 number/string/boolean。落点：`src/shared/tag-types.ts`。

- `pending`：**两次采样做差**的 tag（CPU 占用率）第一次读必然是 pending，
  卡片要显示「等待第一次采样」而不是转圈或 0（spec/01 §三）。
- `unavailable` ≠ `0`：**硬约束**（spec/01 §二）。

### 5.3 广播

- 采样在 main，**运行时是唯一的轮询者**（spec/03 §四）。
  卡片只订阅，不自轮询——否则每张卡各自 fork 一个 `adb shell`，
  板子会看起来 100% 忙，且 N 张卡负载翻 N 倍。
- 订阅关系按 `(connectionId, tag)` 维护；连接断开时订阅保留、值转 `unavailable`。

#### TagStore：数据的唯一汇点

**所有读数都写进 TagStore，再从 TagStore 分发。** 不管数据是轮询来的、
还是将来推送来的（§5.4），进 TagStore 之后再出去。

| 是 | 不是 |
|---|---|
| TagStore 是板子状态的**唯一一份** | UI 自己缓存一份、卡片自己缓存一份 |
| 卡片订阅 TagStore | 卡片订阅「某个连接」 |
| 质量由 tag 引擎产生 | 卡片/UI/MCP 改写质量 |

**为什么这条要写死**：「单一真源在能力层」——UI、卡片、AI 看到的都是同一份状态的投影。
一旦某层开始自建「我记得是……」，就会出现两块卡片显示不同数字，
而用户无法判断哪个是真的——这在「驾驶舱」产品里是不可接受的。

**每个读数带 `seq`**（同一 tag 内单调递增）。异步推送必然乱序，
渲染层按 `seq` 丢弃过期的——否则一个慢到达的旧值会盖掉新值。
这条对将来接推送源尤其重要（那时的乱序是常态，不是例外）。

### 5.4 取数侧：poll 与 push 的接口预留

**问题**：契约里 Stream 是占位（`spec/00` §七自己承认）。但 Stream
（HDMI 采集、摄像头→NPU、日志尾随）天然是 **push**：高频、不由宿主发起往返、
不服从「采样给动作让路」的互斥模型。

**如果 M1/M2 把「取数 → 分发」的路径按纯 poll 焊死**，将来补 Stream
等于破坏所有卡片 API——每张卡都要改。

**决策**：v1 **不实现** Stream，但取数侧统一为 **Source 接口**，
`kind` 有两个取值：

| | poll source（v1 实现） | push source（v1 只留形状） |
|---|---|---|
| 驱动者 | poll group 调度器 | 连接层事件 / 板端推送 |
| 互斥 | 进往返队列，给动作让路 | **不进队列**，独立通道 |
| 新鲜度 | 3 × group 周期 → `stale` | 到达间隔超阈 → `stale`（同一倍数语义） |
| 汇点 | TagStore | **同一个 TagStore** |

**这条不违反 `SPEC-D4`**（「连续流不是标签」）：
push source 只是把 `stale` 的判据从「轮询间隔」泛化为「数据到达间隔」，tag 层不变。

**v1 的实现要求只有一条**：poll 路径走 Source 接口，
push 分支留空壳 + 一条注释指向本节。**不写任何 Stream 业务代码。**

> **为什么现在做这件事**：接口多态是一行签名的决定，
> 拖到 M3 的代价是返工所有卡片订阅路径。

## 6. 卡片运行时

### 6.1 发现与托管

```
cards/<card-id>/            # 卡片根目录（用户目录 + 内置目录合并，同 id 用户优先）
  manifest.json              # 格式见 spec/03
  index.html                 # entry
  *.js / *.css / assets/     # 原生 ESM，无构建
```

- 卡片资源由 main 用自定义协议 `cockpit://card/<id>/…` 托管，
  **只允许访问卡片自己的目录**（路径穿越防护）。
- 每次加载带 `?v=<内容哈希>`，文件变了 URL 就变，缓存自然失效。
- `cockpit://` 必须注册为 **privileged scheme**
  （`standard` + `secure` + `supportFetchAPI` + `cspEnabled`），
  否则原生 ES Module 的相对 `import` 与 `fetch` 在自定义协议下不工作。🔵 待 Electron 里实测。

### 6.2 沙箱

```html
<iframe sandbox="allow-scripts" src="cockpit://card/<id>/index.html"></iframe>
```

- **不给 `allow-same-origin`** → 卡片在独立不透明源里，碰不到宿主 DOM / 存储。
- 宿主只认白名单方法（**以契约 `spec/03` §7.7 的全集为准**，本文不另列一套），
  每条消息校验三件事：**来源 frame** → **方法在白名单** → **该卡片的权限**。

**断网由宿主注入的 CSP 执行**（ADR-D16，契约 `spec/03` §6.1）。
`sandbox` 属性**不限制网络**——不给 same-origin 只是拿不到宿主的源，
卡片在自己的不透明源里照样能 `fetch` / `WebSocket` / `sendBeacon` / `<img src>`。
所以 main 在响应 `cockpit://card/...` 时**注入 CSP 响应头**：

```
Content-Security-Policy:
  default-src 'none'; script-src 'self'; style-src 'self' 'unsafe-inline';
  img-src 'self' data:; font-src 'self' data:;
  connect-src 'none'; form-action 'none'; frame-src 'none'; base-uri 'none';
```

| 指令 | 作用 |
|---|---|
| `connect-src 'none'` | 断掉 `fetch` / `XHR` / `WebSocket` / `EventSource` |
| `img-src 'self' data:` | 断掉 `<img>` 外传通道 |
| `form-action 'none'` / `frame-src 'none'` / `base-uri 'none'` | 断掉表单外传、嵌套 frame、`<base>` 改写 |

CSP 由**宿主**注入，不是卡片目录里的 `meta` 标签——`meta` 里的 CSP 限制不了自己，
而且卡片可以删掉它。卡片无法放宽它。

**存储由宿主代管**（ADR-D16，契约 `spec/03` §6.2）。
不透明源里 `localStorage` / `sessionStorage` / `IndexedDB` **全部抛 `SecurityError`**，
所以契约承诺的「写卡片自己的命名空间」必须经白名单 API：

| 方法 | 落点 |
|---|---|
| `cockpit.storage.get/set/remove/keys/clear` | 宿主落盘到 `%LOCALAPPDATA%/DevBoardCockpit/cards/<card-id>/storage.json` |

每卡一个命名空间、互不可见；值必须 JSON 可序列化；
单键 64 KB、总量 1 MB，超出报 `quota_exceeded`；卡片卸载时**保留**数据。

**CSP 违规要进运行时日志**：浏览器的 CSP 违规事件被宿主捕获后写进卡片运行时日志，
这样 agent 用 `get_card_runtime_log` 能看到「这张卡试图联网」。

### 6.3 权限与降级

- 权限在**安装/加载时**确定，绑定 `(卡片 id, 动作 id, 板型包 id)`（spec/03 §3.2）。
- **卡片不能运行时提权**（spec/03 §3.3）。
- **缺 tag 照常加载**（spec/01 §五）：缺失项显式可见——
  卡片内显示「不可用 · 缺 cpu.usage」，MCP 的 `validate_card` 返回缺失清单。
  这条是 AI 迭代回路不断线的前提。

### 6.4 热插拔

```
监听 cards/**  →  读 manifest → schema 校验
   ├─ 不通过 → 保留上一版可用实例，标记「无效」，记错误日志（不炸宿主）
   └─ 通过   → 换 ?v=hash 重载该卡片的 iframe
```

卡片运行时错误由 `window.onerror` 捕获 → 写入卡片运行时日志 →
MCP `get_card_runtime_log` 可读 → **agent 的自测眼睛**（spec/04）。

### 6.5 主题 token（保证「重新设计」不破卡）

卡片**不得硬编码颜色**，只用宿主注入的 CSS 变量：

```css
--cockpit-bg / --cockpit-bg-elevated / --cockpit-border
--cockpit-text / --cockpit-text-dim / --cockpit-text-faint
--cockpit-accent / --cockpit-accent-2
--cockpit-ok / --cockpit-warn / --cockpit-danger / --cockpit-unavailable
--cockpit-radius / --cockpit-font-mono / --cockpit-font-ui
```

换主题 = 换一套变量值 = 所有卡片跟着变，**不用重写任何卡片**。
这条要写进卡片开发规范（`get_card_sdk_docs` 里也会给 agent）。

## 7. 控制面（实现 spec/03 §4、§5）

```
GUI 按钮 ─┐
          ├─→ actions/executor → hal.run() → 板子 → 回读(readback) → UI
MCP 工具 ─┘        （唯一写入口）
```

执行流程：

```
1. 查动作在当前板型包里存在吗          → 没有 = not_found
2. 查调用方（卡片 / agent）对它的授权    → 没有 = denied
3. 校验参数（类型 / 范围 / 枚举）        → 不过 = invalid_params
4. 参数超出该动作的 guard 域             → needs_confirmation（guard_exceeded）
5. danger=destructive 且未确认           → needs_confirmation（附一次性 token）
6. dry_run                            → 只回显「将要执行什么」
7. 执行（超时 = 124；串口上无退出码的动作 = unsupported_transport）
8. 回读（readback 四种形式：tag / file_equals / command_ok / verify）
9. 写审计日志
```

**UI 的显示依据是第 8 步的回读值**，不是第 7 步的退出码。
回读不符 → 显示「命令已发出，未确认生效」，**不乐观显示成已开启**（spec/03 §5.3）。

**参数在第 7 步之前必须编码**（ADR-D17，契约 `spec/02` §4.6）：

| 类型 | 编码方式 |
|---|---|
| `integer` / `number` | 十进制数字字面量，不带引号 |
| `boolean` | `true` / `false` |
| `enum` | 必须是 `values` 里的某一项，原样注入 |
| `string` | **单引号包裹**，内部 `'` 转义为 `'\''`，长度受 `maxLength` 限制 |

模板里的 `{param}` **不得自带引号**（引号由运行时统一加）。
运行时在执行前**再校验一次**类型，不信任包的自述。

**危险地板匹配的是编码后的 argv 序列**，不是模板（契约 `spec/02` §5.2.1）。
落点：`src/main/actions/policy.ts`——先按 §4.6 拼出最终命令，
再按 shell 词法切分，对切出的词元匹配地板表；表外命令记一条 warning。

**参数域 `guard`**（契约 `spec/02` §5.5）：动作可声明「温和参数域」，
超出域内的参数走第 4 步的确认。落点：`src/main/actions/policy.ts` + `src/main/cards/consent.ts`。

## 8. 布局与主题

- **网格**：12 列；卡片在 manifest 里声明 `layout`（spec/03 §一），布局可覆盖。
- **拖拽**：react-grid-layout（ADR-D3）；布局存 `LayoutDoc`，可导出/导入 → 可分享。

## 9. MCP server 的落地（实现 spec/04）

**传输：HTTP 回环（127.0.0.1）**，listener 仍在 **Electron main 进程内**——
所以 ADR-D2「MCP 与 GUI 同进程」不变，但 agent 能**连到已经在跑的 GUI**。

> **2026-11-12 评审修订**：本节原写「传输：stdio」，并给出两种启动方式
> （随 GUI 启动 / 独立进程 `devboard-cockpit --mcp-stdio`）。
> 独立进程那条同时违反 ADR-D2（同进程）与契约（没有发现机制），
> stdio 本身也与契约 §7.1「agent 连到已经在跑的 GUI」冲突。
> 按 ADR-D19 改为 HTTP 回环 + 发现文件 + bearer token。

### 9.0 进程与安全基线

```
┌─ Electron main ────────────────────────────────────────────┐
│  mcp/                                                       │
│    server.ts    HTTP listener（只绑 127.0.0.1）             │
│    security.ts  Origin / Host 校验 + bearer token 中间件    │
│    discovery.ts 写/删发现文件                               │
│    tools.ts     工具实现（薄封装）                          │
│    docs.ts      SDK 活文档                                  │
└──────────────────────────────────────────────────────────────┘
```

**listener 在 main 进程内，但对外是一个本机 HTTP 服务**：

| 项 | 实现 |
|---|---|
| 监听地址 | `127.0.0.1:0`（让 OS 分配端口，避免多开撞端口） |
| `Origin` 校验 | 请求带 `Origin` 且不属本机 → **403**。MCP 规范要求（MUST validate） |
| `Host` 校验 | 只接受 `127.0.0.1:<port>` 与 `localhost:<port>` |
| 认证 | `Authorization: Bearer <token>`；token 每次启动随机生成 ≥32 字节 |
| 发现文件 | `%LOCALAPPDATA%/DevBoardCockpit/mcp.json`，含 `port` / `token` / `pid` |
| 写入方式 | 先写 `.tmp` 再原子改名，避免 agent 读到半个文件 |
| 权限 | 仅当前用户可读（Windows: 显式 ACL；POSIX: 0600） |
| 清理 | GUI 退出时删除；监听失败时也要删（不留指向死进程的发现文件） |
| CORS | 不发 `Access-Control-Allow-Origin` |

**为什么这些是硬要求**：不校验 `Origin`/`Host` 的本地 MCP server，
任何用户访问过的恶意网页都能通过 DNS rebinding 向 `127.0.0.1` 发请求，
直接驱动 `execute_action` 改用户的板子。已有多起同类漏洞公告
（见 `docs/08` §10 的来源）。

**token 不写进日志**：审计日志与运行时日志都要过滤 `Authorization` 头与
发现文件里的 `token` 字段。

### 9.1 实现原则

- 工具清单**以 spec/04 为准**，本文不重复列举（避免两份定义漂移）。
- 每个工具都是**薄封装**：读 GUI 内部状态，或触发 GUI 已声明的动作。
- MCP **不做文件 IO**：agent 直接写卡片目录（spec/04 §三）——
  「MCP 是 AI 的眼睛和手，不是 AI 的硬盘」。
- 返回值遵守 spec/04 §四的共同约定：`ok: false + reason` 不抛异常、
  未知用 `status: "unavailable"` 不返回 null/0、时间用毫秒 UTC 时间戳、
  路径用绝对路径、每个响应带 `apiVersion`。

### 9.2 工具 → main 内部实现的映射

| 工具类别 | 落到 main 的什么 | 备注 |
|---|---|---|
| 感知现状（连接/数据源/能力） | `hal/registry` + `tags/` 的**当前位号表** | 能力动态出现，不能靠静态文档 |
| ↳ 其中 `list_data_sources` | `tags/poll` 的 **reader 粒度**表 | 契约要求它返回 **reader 粒度**（含 `interval_ms`），不是 tag 粒度——「哪些 tag 可读」天然按 reader 组织（一个 reader 挂了，它提供的 tag 全挂） |
| ↳ 其中 `list_tags` | `tags/` 的 **tag 粒度**表 | 与上面配套：agent 写卡时先看这个，知道有哪些 tag 名可用 |
| 自省（描述/采样） | `tags/describe` + `tags/readers` | agent 不盲写的前提 |
| 卡片管理（列/校验/装/卸/日志） | `cards/` | 校验规则 = spec/03 §九 |
| 动作执行 | `actions/executor` | **与 GUI 同一个入口**（spec/03 §五） |
| 布局 | `layout/` | |
| 活文档 | `mcp/docs.ts` | 随宿主版本走的那份 markdown |

### 9.3 为什么必须在 main 进程

ADR-D2：卡片清单、卡片运行时日志、布局、位号表**都住在 main 进程**，
MCP server 与它们同进程 → 直接读，零延迟、零一致性风险。
这也是否掉「Python 后端 + Electron 界面」双层混合的直接原因。

**HTTP 传输不改变这一点**：HTTP 只是**对外的接口形态**，
listener 仍然跑在 main 进程内，直接读同一份内存状态。
不是「另起一个 MCP 进程再让它回头连 GUI」。

### 9.4 卡片实例与连接上下文（GLM-D2）

**问题**：契约规定卡片只见 tag 名（`spec/03` §7.7 的 `tags.get("cpu.usage")`），
但本工程是多连接的。`cpu.usage` 在 TagStore 里的键是 `(connectionId, cpu.usage)`——
这个上下文由谁携带、在哪一层定死，决定卡片 API 的形状。契约没写。

**决策**：

1. **manifest 不携带连接。** 卡片声明的是**能力**（tag 名、动作 id），不是去向。
   ——写死连接会让卡绑死某块板，「N+M」退化回「N×M」。
2. **连接发生在布局层。** 布局单元记录 `(cardId, connectionId)`——
   用户把一张卡放到某个连接的画布上，绑定即发生。
   一张卡可以在两个连接上各有一个实例（实例 = `(cardId, connectionId)`，
   共享同一份代码目录与授权）。
3. **卡片 API 的隐式上下文 = 实例的 connectionId。**
   iframe 创建时宿主把 connectionId 注入 shim；
   卡片调 `tags.get("cpu.usage")`，宿主在 `(实例的 connectionId, "cpu.usage")` 上取值。
   **卡片代码里没有 `connectionId` 这个词。**
4. **订阅键 = `(connectionId, tag)`**，TagStore 的分区键天然就是它。

**对 agent 的含义**：agent 写卡不需要知道连了谁；
MCP 的 `list_tags(board?)` 返回带 `board` 字段，供 agent 校验「这张卡在目标连接上是否降级」。

**需要契约跟上的一步**：`spec/03` §七 补一段——
「卡片以**宿主注入的连接上下文**为隐式作用域；tag 名在卡片 API 内始终是不带连接前缀的全局名」。
写死这一句，多板前缀问题（`docs/05` O11）才能安全延后：
**前缀问题被隔离在宿主的解析层，永远不进卡片与 manifest。**

> **被否掉的选项**：manifest 写死 `connection`（卡绑死板）；
> 卡片 API 显式传 connectionId（把宿主的路由问题泄漏给卡片作者，
> 每张卡多写一个没意义的参数，且写错不易察觉）。

### 9.5 给 agent 的三条硬规则

spec/04 §五 已经写好了，**随 SDK 活文档一起给 agent**：

1. 不要发裸命令——要新能力就写板型包扩展或卡片 action。
2. 不要乐观更新 UI——动作之后一律用回读值渲染。
3. 写完卡一定要 `validate_card` + `get_card_runtime_log`。

**第 4 条（本轮补）**：动作的参数不要超出该动作声明的 `guard` 域——
超出会走一次人工确认，把你的回路打断。

## 10. IPC 契约

`src/shared/ipc-contract.ts` 定义全部通道，main 与 renderer 共用类型。

| 通道 | 方向 | 载荷 |
|---|---|---|
| `connections:list` / `terminal:open` / `terminal:close` | R→M | 连接实例 + 能力协商结果 |
| `tag:snapshot` | R→M | `{ tagIds }` → `{ [tag]: TagValue }` |
| `tag:update` | M→R（推送） | `TagValue`（五态之一） |
| `tag:subscribe` / `:unsubscribe` | R→M | 订阅句柄 |
| `action:execute` | R→M | `{ cardId?, actionId, params, dryRun, confirmToken? }` → `ActionResult` |
| `card:list` / `:validate` / `:reload` | R→M | |
| `card:event` | M→R（推送） | 卡片请求宿主能力（经白名单校验） |
| `card:storage` | R→M | `cockpit.storage.*` 的读写（宿主代管并落盘） |
| `card:consent` | M→R（推送） | 需要人工确认时弹窗（动作确认 / 装卡授权 / 参数超域） |
| `layout:get` / `:set` / `:export` / `:import` | R→M | `LayoutDoc` |
| `log:list` / `:read` | R→M | 会话日志 |
| `settings:get` / `:set` | R→M | 宿主设置（含 adb 路径等机器专属路径） |

**约束**：

- preload 用 `contextBridge` 只暴露上述白名单方法，**不暴露 `ipcRenderer` 本身**。
- 跨进程载荷全是**可序列化纯数据**（无类实例、无函数），
  main ↔ renderer 不共享内存状态。
- `tag:update` 的载荷必须**带 status**，禁止只推数值——五态是契约的一部分。

## 11. 错误处理与降级

### 11.1 统一错误对象

```ts
interface AppError {
  code: string;      // 'CONN_OPEN_FAILED' | 'TAG_UNAVAILABLE' | 'ACTION_DENIED' | ...
  message: string;   // 人话，可直接展示
  retryable: boolean;
  detail?: unknown;
}
```

### 11.2 降级矩阵

| 故障 | 表现 | 降级行为 |
|---|---|---|
| 板子不在 `device` 状态 | ADB 连不上 | 连接标 offline；位号转 `unavailable`；UI 显示 `--` + 「设备未连接」 |
| 串口被占用 | 打开失败 | 报错并指出端口；不做重试风暴 |
| 位号读不到 | 单个 tag 失败 | 该 tag `unavailable` + reason；**其它 tag 照常**；不影响整组采样 |
| debugfs 没挂载 | `npu.usage` 不可用 | `unavailable` + reason `debugfs_not_mounted`；界面给出 `debugfs.mount` 动作按钮（见 06 核对 C5） |
| 板子掉线 | 连续采样失败 | 保留最后值并转 `stale`；持续失败后转 `unavailable` |
| 卡片 manifest 不合法 | 加载失败 | 保留上一版实例；卡片位显示「无效」+ 错误摘要；宿主不受影响 |
| 卡片运行时抛错 | iframe 崩 | 捕获写运行时日志；占位显示；不影响其它卡片 |
| 卡片调用未授权动作 | 被拒 | 返回 `denied` 原因；写审计；卡片自行展示 |
| 动作超时 | 执行超时 | 退出码 124；UI 保留旧值 + 标注超时 |
| 动作成功但回读不一致 | 写成功状态不符 | `ok: false` + 差异；**不假装成功**（spec/03 §5.2） |
| MCP 误用 | 参数错 | 结构化错误 + 提示该用哪个工具 |

### 11.3 三条不许

1. **不许把 `unavailable` 显示成 0**（spec/01 §二）。
2. **不许把「命令返回 0」当成「状态正确」**——真相是回读值。
3. **不许让单个卡片 / 单个位号的失败波及宿主**。

| 单元 | vitest | 提取器、绑定、manifest 校验、动作分级、poll 合并、串口单行压平 |
| 黄金向量 | vitest + `fixtures/` | 真机样本；样本只增不改 |
| 契约 | vitest | 校验器对**故意写错**的 pack / manifest 必须报错（负例） |
| **安全** | vitest | **参数编码**：注入用例（`'x; reboot'`）必须被编码成惰性参数；**地板**：注入后的 argv 必须命中地板；**guard**：超域参数必须报 `needs_approval` |
| **安全（运行时）** | vitest | **CSP**：卡片 `fetch` 外部被挡住；**storage**：跨卡不可见、超配额报错；**往返互斥**：同一连接同时发起采样与动作，marker 不串台 |
| 集成 | vitest + 真板 | `npm run probe:board`：对真板跑每个 reader，核对输出 |
| 端到端 | Playwright（M8） | 加载卡片 → 改文件 → 断言热插拔生效 |
| **安全** | vitest + 攻击性用例 | 见 §12.1：沙箱逃逸、断网、路径穿越、伪造审批凭据、命令注入 |
| **负例** | vitest | 故意非法的板型包/manifest 必须被拒（`fixtures/validator/`） |

**验收判据看输出，不看感觉**：

```powershell
npm run gen:vocabulary:check       # 词表 YAML / 文档表格 / 代码三份一致
npm run mutation:check             # 变异测试：证明回归测试真的在守着
npm run build                      # 三段构建 + 构建产物自检

# 下面两条属于**计划 2（M3/M4）**，现在还不存在：
npm run validate:profiles          # 板型包 + 卡片 manifest 全合法（计划 2）

```

词表既然以 YAML 为唯一权威，就必须有一道自动检查保证
「YAML / `spec/01` 的表格 / 代码里的词表」三份不会漂移（§4.3）。

### 12.1 安全测试清单（发布门禁）

安全承诺必须有对应的**攻击性测试**，否则只是文档里的一句话。
每条对应一处契约承诺：

| 攻击面 | 用例 | 期望 |
|---|---|---|
| **沙箱逃逸** | 卡片访问 `window.parent` / `window.top` / `window.open` / 任意 `postMessage` / `localStorage` / `indexedDB` | 全部拿不到（不透明源） |
| **断网** | 卡片 `fetch('https://example.com')`、`fetch('http://192.168.1.1')`、WebSocket、`sendBeacon`、`<img src="https://...">` | 全部被 CSP 挡住，**且违规进运行时日志** |
| **路径穿越** | 卡片请求 `../../etc/passwd`、绝对路径、Windows UNC 路径 | 协议 handler 拒绝，只放行自己目录 |
| **审批凭据伪造** | agent 自己构造 `confirm_id`、重放已消费的 `confirm_id`、改了参数再带旧 `confirm_id` | 全部拒绝（一次性 + 绑参数摘要） |
| **命令注入** | `string` 参数传 `x; reboot`、`$(reboot)`、换行、反引号、超长串 | 全部被编码成惰性参数；超长被 `maxLength` 拒 |
| **地板绕过** | 包把 `reboot` 声明成 `reversible`；包用 `exec_regex` 跑 `reboot` | 校验器拒包；运行时仍判 destructive |
| **越权写路径** | agent 写卡片目录之外的文件；agent 装未经确认的板型包 | 拒绝 |
| **审计完整性** | 审计日志被截断 / 写入失败 | 写入失败时 **destructive 动作拒绝执行**（账本不能缺） |

> **最后一条是取舍**：审计写失败时，是「仍然执行但提示」还是「拒绝 destructive」？
> 本设计选**拒绝 destructive**——审计是账本，账本缺页的动作不该发生。
> reversible 动作仍然执行（记一条「审计异常」）。

### 12.2 失败注入矩阵

每种失败都要有明确期望，不能「跑起来看看」。至少覆盖：

断连 / 超时 / 非零退出 / 半包乱码 / 值越界 / 推送乱序重复 /
串口被占 / 动作未生效 / **超时但实际已生效** / 卡片 manifest 损坏 /
卡片运行时崩溃 / 卡片试图联网 / MCP 无 token / MCP 越权写路径 /
agent 直触 destructive / verify 的 tag 不可观测 / 卡片 id 冲突。

其中「**超时但实际已生效**」最容易被漏：动作超时后**仍要回读**并展示实际状态，
不能因为超时就报失败——那会让用户以为没生效，然后重复点一次。

## 14. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| `node-pty` 与 Electron ABI 不匹配 | 终端起不来 | 锁 Electron 版本；`electron-rebuild` 固化进 `postinstall`；CI 验一次 |
| 串口 marker 协议重写踩坑 | 命令输出串台 | 照搬旧工程事实 S1–S4；真板回归 |
| iframe 沙箱与相对路径模块冲突 | 卡片加载失败 | 自定义协议托管 + `?v=` 版本参数；先写最小卡片验证 |
| **契约漂移**（实现层词表 ≠ `docs/spec/01` 的表） | agent 写出互相矛盾的卡片 | §4.3：实现层的词表必须**从契约生成**，不是手写；改词表先改契约 |
| MCP SDK 演进 | API 变动 | 只依赖 `tools/list` + `tools/call`；SDK 封装在 `src/main/mcp/` 一层 |
| 采样与渲染争抢 | 界面卡顿 | 采样在 main；UI 只收增量；单次采样节流 ≥ 200 ms（与 `spec/02` 规则 18 的下限一致） |
| **MCP HTTP 端口被 DNS rebinding 攻击** | 恶意网页驱动 `execute_action` 改用户的板子 | 契约强制：`Origin`/`Host` 校验 + bearer token + 仅绑回环 + 不发 CORS（§9.0） |
| **卡片 CSP 被绕过** | 板子数据外泄 | CSP 由宿主注入而非卡片 `meta`；`connect-src 'none'`；CSP 违规进运行时日志（§6.2） |
| **参数注入绕过地板** | agent 用字符串参数执行未声明的命令 | 参数按类型编码（§4.6）；地板匹配编码后的 argv（§5.2.1）；两者都有负例单测 |
| 板型包写了板上没有的路径 | 位号永远 unavailable | `probe:board` 把 unavailable 当失败；`06-契约核对.md` 记账 |
