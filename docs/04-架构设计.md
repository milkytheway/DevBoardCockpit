## 1. 目标与非目标

### 1.1 目标

1. **统一工作台**：串口 / ADB / SSH 三通道接入板子与 Ubuntu 客机，终端、文件互传、
   状态监控、显示输出在同一 GUI 内完成。
2. **语义 tag 契约**：把板子的能力抽象成稳定位号（`cpu.usage`、`gpu.temperature`），
   卡片只订阅位号，不关心板型。
3. **卡片系统**：卡片即文件；AI 写完即生效；热插拔；沙箱隔离。
4. **控制闭环**：写动作后**回读**位号，UI 以回读为准。
5. **MCP 协作**：宿主机 AI agent 通过 MCP 感知现状、写卡片、触发动作、自测迭代。

### 1.2 非目标（本期明确不做）

| 不做 | 理由 |
|---|---|
| systemd / 板端长期服务 | 板子是 Buildroot + eudev，无 systemd；Tier 2 守护进程推流留到有视频/高频流需求时 |
| 多用户 / 权限体系 | 单人桌面工具 |
| 跨平台（Linux/macOS） | 宿主是 Windows 宿主；跨平台留接口不留实现 |
| 卡片市场 / 远程分发 | 先做本地目录热插拔 |
| 与旧 Python 工程共存运行 | 明确切干净，避免两套真相 |

## 2. 总体架构

### 2.1 进程模型

```
┌─ Electron main（设备与契约的大本营）──────────────────────────┐
│                                                                 │
│  hal/        连接层：serial │ ssh │ adb │ local（统一接口 + 能力协商）│
│  tags/       位号层：板型 profile → 批量采样 → 缓存 → 广播          │
│  actions/    控制面：分级判定 → 执行 → 回读 → 审计                 │
│  cards/      卡片注册表：manifest 校验 │ 协议托管 │ 热重载          │
│  mcp/        MCP server（stdio）——与卡片注册表同进程              │
│  profiles/   profile 加载 + schema 校验                          │
│                                                                 │
└───────────┬─────────────────────────────────────────────────────┘
            │ IPC（invoke/handle 拉取 + 事件推送）
┌───────────▼─────────────────────────────────────────────────────┐
│ Electron renderer（只画，不碰设备）                              │
│  layout/   网格布局引擎（react-grid-layout）                     │
│  cards/    卡片宿主：sandbox iframe + 白名单 API 桥              │
│  terminal/ xterm.js 终端                                        │
│  panes/    文件浏览器 │ 日志工作区 │ 目标切换器 │ 资源条          │
└───────────┬─────────────────────────────────────────────────────┘
            │ postMessage（白名单，无同源）
┌───────────▼─────────────────────────────────────────────────────┐
│ 卡片 iframe：sandbox="allow-scripts"（无 same-origin）           │
│  card-sdk.js 提供 getTag / subscribeTag / setAction / log …      │
└─────────────────────────────────────────────────────────────────┘

┌─ 磁盘 ─────────────────────────────────────────────────────────┐
│ profiles/boards/*.yaml   板型数据包（tag 怎么产生）              │
│ profiles/targets/*.json  连接实例（怎么连上）                    │
│ cards/<card-id>/         卡片目录（manifest.json + view.js）     │
└─────────────────────────────────────────────────────────────────┘
```

**铁律**（对应 AGENTS.md）：

- renderer **永远不**直接碰设备，一切经 `tags/` 与 `actions/`。
- MCP server 与卡片注册表**同进程**（决策 D2），因此 agent 读到的 GUI 状态与用户看到的完全一致。
- 卡片**永远不**能触碰宿主 DOM / 存储 / 任意消息（决策 D6）。

### 2.2 三条数据通路

| 通路 | 方向 | 典型消息 |
|---|---|---|
| 采样通路 | 板子 → tags → 订阅者 | `tag:update`（tagId, value, quality, ts） |
| 控制通路 | GUI / MCP → actions → 板子 → 回读 | `action:execute` → `action:result`（含回读值） |
| 感知通路 | agent → MCP → GUI 内部 | `list_cards` / `describe_source` / `validate_card` |

## 4. 核心数据模型

### 4.1 连接 profile（TargetProfile）— 怎么连

```jsonc
{
  "id": "board-adb",
  "label": "板子 · ADB",
  "transport": "adb",          // serial | ssh | adb | local | 运行时注册的任意传输
  "board": "atklrk3588",       // ← 指向板型 profile；null = 不是板（如本机、Ubuntu 客机）
  "options": { /* 传输相关参数 */ }
}
```

- 存放：`profiles/targets/*.json`（用户目录可覆盖同 id）。
- 一个板型可被多个连接实例引用（同一块板的 ADB 与串口）。
- 加载时做 **JSON Schema 校验**，坏文件**报错并跳过**（旧工程只跳过不校验，改进点）。

### 4.2 板型 profile（BoardProfile）— 这块板是什么

```jsonc
{
  "id": "atklrk3588",
  "label": "ATK-DLRK3588",
  "version": 1,
  "status": "draft",           // draft | verified
  "identity": { /* compatible、内核、CPU 分簇、内存 */ },
  "recipes": {                 // 读取配方：怎么把板子上的东西读出来
    "stat":  { "run": "cat /proc/stat" },
    "gpu":   { "run": "cat /sys/class/devfreq/fb000000.gpu/load 2>/dev/null" }
  },
  "tags": {                    // 语义位号：每条指向一个 recipe + 一个提取器
    "cpu.usage": { "recipe": "stat", "extract": "proc_stat_total", "unit": "percent" }
  },
  "actions": [ /* 可写动作，带 tier */ ],
  "custom_tags": {}
}
```

**recipe（读取配方）是本设计的关键抽象**：

> 板型 profile **不写脚本**，只声明「读什么」；**怎么读**由通用的提取器（extractor）负责。
> 于是「板型差异」= 一份数据（路径 + 配方 + 提取器名），而不是一段代码。

这样做的收益：N 种板 × M 个位号 = N+M 个文件（愿景的核心承诺）成立；
新增板型不需要新增代码，新增位号类型才需要新增提取器（少得多）。

### 4.3 位号取值（TagValue）— 三个状态，不是两个

```ts
type TagQuality = 'ok' | 'stale' | 'unknown';
interface TagValue {
  tagId: string;
  value: number | string | boolean | null;
  unit: Unit;
  quality: TagQuality;   // unknown ≠ 0，这是硬约束（事实 G2）
  ts: number;            // 采样时刻
  error?: string;        // quality != ok 时的原因
}
```

| quality | 含义 | UI 表现 |
|---|---|---|
| `ok` | 读到了 | 显示数值 |
| `stale` | 上次读到了，现在读不到 | 显示数值 + 灰色「已过期」标记 |
| `unknown` | 从未读到 / 读失败 | 显示 `--`，**不显示 0** |

### 4.4 卡片 manifest（CardManifest）

```jsonc
{
  "id": "pipe-line",
  "title": "推理管线",
  "version": 1,
  "view": { "entry": "view.js" },        // 免构建 ESM（决策 D4）
  "grid": { "w": 6, "h": 4, "minW": 3, "minH": 2 },
  "subscribe": [
    { "tag": "npu.utilization" },
    { "tag": "gpu.utilization" }
  ],
  "actions": [
    {
      "id": "npu.perf",                                   // 卡片内本地 id
      "action": "npu.governor.set",                       // ← 板型 profile 里声明的动作
      "params": { "governor": "performance" },
      "label": "挂 NPU 进管线",
      "tier": "reversible"
    }
  ],
  "permissions": ["tag:npu.utilization", "action:npu.governor.set"]
}
```

**关键约束**：卡片只能调用**板型 profile 已声明**的动作，不能自己发明命令；
卡片声明的 `permissions` 在**首次加载时**由用户授权，未授权的动作调用一律被拒。

### 4.5 动作与结果（ActionSpec / ActionResult）

```ts
type ActionTier = 'read' | 'reversible' | 'destructive';

interface ActionSpec {
  id: string;
  tier: ActionTier;
  params: ParamSpec[];
  command: string;          // 模板：{param} 占位
  verify?: { tag: string }; // 写完回读哪个位号
}

interface ActionResult {
  actionId: string;
  ok: boolean;
  exitCode: number;         // 超时统一 124（事实 G1）
  stdout: string;
  stderr: string;
  verified?: TagValue;      // 回读结果 —— UI 的显示依据
  denied?: string;          // 被策略拒绝的原因
}
```

### 4.6 布局文档（LayoutDoc）

```jsonc
{
  "version": 1,
  "grid": { "cols": 12, "rowHeight": 80 },
  "items": [
    { "cardId": "pipe-line", "x": 0, "y": 0, "w": 6, "h": 4 },
    { "cardId": "terminal",  "x": 6, "y": 0, "w": 6, "h": 6 }
  ]
}
```

可导出/导入成文件 → **布局可分享**（愿景第三层功能之一）。

## 5. 语义 tag 契约（第一份手册的骨架）

### 5.1 命名规则

```
<domain>.<measure>
```

- `domain`：设备域 —— `cpu` `gpu` `npu` `memory` `soc` `storage` `network` `system`
  `camera` `display` `backlight` `dmc` `vop` `custom`
- `measure`：量的名字 —— `usage` `utilization` `load` `duty` `temperature` `frequency`
  `total` `used` `available` `count` `state` `governor` `brightness` `rate` `latency`

规则：

1. **小写、点分、驼峰不用**；`cpu.core.usage` 这类多段允许。
2. **不复用旧名**：含义变了就是新名 + `version` 递增，不做静默语义变更。
3. **自定义位号一律 `custom.` 前缀**，避免撞标准词汇表。
4. 位号**只描述量本身**，不带单位后缀（`gpu.temperature` 而不是 `gpu.temperature.c`）；
   单位由 profile 的 `unit` 声明。

### 5.2 单位词表

`percent` `celsius` `hertz` `byte` `kibibyte` `mibibyte` `level` `count`
`text` `boolean` `bitrate` `millisecond` `microsecond` `volt` `watt` `ampere`

### 5.3 采样策略

| 策略 | 用在哪 | 说明 |
|---|---|---|
| `interval` | 指标类（cpu/gpu/npu/内存/温度） | 默认 1000 ms，可按位号覆盖 |
| `onDemand` | 文件类（governor、背光） | 变化不频繁，按需读 + 事件触发 |
| `push` | 流类（Tier 2 守护进程推流） | 本期不实现，词表先占位 |

### 5.4 批量采样：一次往返（**硬约束**）

事实清单 A5/A6 写得很清楚：每个文件一次 `adb shell` ≈ 30 ms，
而且 **fork 出来的 shell 自身 CPU 时间会算进 `/proc/stat`，让板子看起来 100% 忙**。

因此 tag 层必须做**采样规划器（planner）**：

```
要采样的位号集合
   ↓ 按 recipe 分组
   ↓ 合并成一条命令（每段带 ###recipe:<name> 标记）
   ↓ 一次往返执行
   ↓ 按标记切段 → 各提取器解析 → 各 recipe 多次复用的结果
```

示例（合并后的实际命令）：

```sh
echo '###recipe:stat'; cat /proc/stat; echo '###recipe:gpu'; cat /sys/class/devfreq/fb000000.gpu/load 2>/dev/null; echo '###recipe:mem'; grep -E 'MemTotal|MemAvailable' /proc/meminfo; echo '###recipe:done'
```

> **串口例外**：UART 一次只能跑一行（事实 S6）。planner 检测到
> `capabilities().supportsMultiline === false` 时，自动把各 recipe 压成
> 单行（用 `;` 连接，不换行）。因此 **recipe 里的命令必须本身能写成一行**——
> 这是写板型 profile 时的硬性要求，schema 校验要检查。

### 5.5 「一份手册」的形态

第一份手册 = **本文第 5 节 + `profiles/boards/README.md` + 标准词汇表文件**。
建议词汇表落成机器可读：`src/shared/tag-vocabulary.ts`（标准位号、单位、提取器名的注册表），
这样「AI 读 YAML 即知这块板的一切」有确定的依据，也能被 `validate` 工具检查。

## 6. 板型 profile 格式（第一份手册的另一半）

### 6.1 顶层字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` / `label` | ✅ | 标识与显示名 |
| `version` | ✅ | 语义变更时递增 |
| `status` | ✅ | `draft` / `verified` |
| `identity` | ⬜ | 板子自我描述（compatible、内核、CPU、内存） |
| `recipes` | ✅ | 读取配方表 |
| `tags` | ✅ | 位号表 |
| `actions` | ⬜ | 可写动作 |
| `custom_tags` | ⬜ | 逃生门 |

### 6.2 提取器词表（第一版）

| extractor | 输入 | 输出 | 备注 |
|---|---|---|---|
| `proc_stat_total` | `/proc/stat` | 百分比 | busy = total − idle |
| `proc_stat_cores` | `/proc/stat` | 每核百分比 | 核编号取 `cpuN` 的 N |
| `cpuinfo_part` | `/proc/cpuinfo` | 分簇名 | `0xd05`→A55，`0xd0b`→A76 |
| `devfreq_percent` | `<p>@<f>Hz` | 百分比 | |
| `devfreq_hertz` | 同上 | 频率 | |
| `rknpu_load` | `NPU load: Core0: 12%, …` | 百分比（取 max） | |
| `meminfo_value` | `Key: 8107744 kB` | KiB | |
| `thermal_zone` | `type=temp` 行 | 摄氏度（× scale） | 按 type 过滤 |
| `file_text` | 文件全文 | 文本 | 需 trim |
| `file_number` | 文件全文 | 数字 | 需 trim |
| `derive` | 其它位号 | 派生 | 如 `used = total − available` |

> 提取器是**通用代码**，数量应远少于位号数量。板型 profile 只引用它的名字。

### 6.3 动作的权限与回读

```yaml
actions:
  - id: backlight.set
    tier: reversible
    params:
      - { name: path, type: enum, values: [...] }
      - { name: value, type: integer, min: 0, max: 255 }
    command: "echo {value} > {path}"
    verify: { tag: backlight.0.brightness }
```

执行流程（`actions/executor.ts`）：

```
1. 查板型 profile 里有没有这个 action          → 没有 = 拒绝
2. 判 tier：destructive 需要二次确认 + 已授权     → 否则 = 拒绝
3. dry_run？→ 只回显将要执行的命令，不执行
4. 执行（超时 → 124）
5. verify？→ 重新采这个位号 → 结果作为 ActionResult.verified
6. 写审计日志（谁、何时、什么参数、结果、回读值）
```

**UI 的显示依据是第 5 步的回读值**，不是第 4 步的退出码——
这是「驾驶舱」与「遥控器」的分界（决策 D7）。

### 6.4 新增一块板的步骤

1. 抄一份 `profiles/boards/atklrk3588.yaml` → 改 `id` / `identity`。
2. 改 `recipes` 里的路径（这是**唯一**需要按板改的地方）。
3. 改 `tags` 里的位号映射与 `actions`。
4. `npm run validate:profiles` → schema + 命名规则 + 提取器存在性全过。
5. 对着真板跑一次 `npm run smoke:board -- --profile <id>` → 把 `status` 改成 `verified`。

## 7. 卡片系统

### 7.1 卡片即文件

```
cards/
├─ pipe-line/
│  ├─ manifest.json
│  └─ view.js
├─ cpu-gauges/
│  ├─ manifest.json
│  └─ view.js
└─ _templates/
   └─ blank/            ← 给 agent 的起手模板
```

发现规则：扫描 `cards/*/manifest.json`（可多级目录，深度上限 3）。
用户目录 `%LOCALAPPDATA%/DevBoardCockpit/cards/` 与内置目录合并，**同 id 用户优先**。

### 7.2 协议托管：`cockpit://`

卡片视图通过自定义协议加载：

```
cockpit://card/pipe-line/view.js
cockpit://card/pipe-line/assets/logo.png
```

- 由 main 进程用 `protocol.handle()` 托管，**只允许访问卡片自己的目录**（路径穿越防护）。
- 好处：卡片内可以用相对路径 `import './util.js'`、可以带 CSS/图片，**且完全不需要构建步骤**（决策 D4）。
- 每次加载附带版本号 `?v=<hash>`，文件变了就是新 URL，浏览器缓存自然失效。

### 7.3 沙箱与白名单 API

```html
<iframe sandbox="allow-scripts" src="cockpit://card/pipe-line/view.js"></iframe>
```

- **不给 `allow-same-origin`** → 卡片处在独立的不透明源里，碰不到宿主 DOM / localStorage / cookie。
- 卡片与宿主只通过 `postMessage` 通信，且宿主**只认白名单方法名**：

| 白名单方法 | 作用 | 权限来源 |
|---|---|---|
| `getTag(tagId)` | 读一个位号的当前值 | manifest.subscribe 声明的位号 |
| `subscribeTag(tagId, cb)` | 订阅位号变化 | 同上 |
| `setAction(actionId, params)` | 触发一个动作 | manifest.actions 声明 + 用户授权 |
| `listTags()` | 列出可读位号 | 自动授予 |
| `log(level, msg)` | 写卡片运行时日志 | 自动授予 |
| `notify(title, body)` | 弹一条宿主通知 | 自动授予 |

宿主侧对每条消息做三件事：**校验来源 frame** → **校验方法在白名单** → **校验该卡片的权限**。
任何一条不通过 → 丢弃并记日志。

> `card-sdk.js` 是随宿主分发的客户端胶水（几十行），卡片 `import` 它即可。
> 它**不是**框架，只是一层薄封装——保持卡片「原生 JS」这一决策不被稀释。

### 7.4 热插拔流程

```
文件系统监听（chokidar，监听 cards/**）
   ↓ 变更（新增 / 修改 / 删除）
   ├─ 新增或修改 → 读 manifest → JSON Schema 校验
   │     ├─ 不通过 → 卡片标记为「无效」，保留上一版可用实例，记错误日志
   │     └─ 通过   → 换 ?v=hash 重新加载该卡片的 iframe
   └─ 删除 → 卸载 iframe，布局里移除该项
```

- 校验不过**不炸宿主**：坏卡只坏自己（这是「双层安全」第一层的兑现）。
- 卡片运行时错误由 `window.onerror` 捕获 → 写入 `cards/<id>/runtime.log` → MCP 的
  `get_card_runtime_log` 可读 → **agent 的自测眼睛**。

### 7.5 主题 token 契约（保证「重新设计」不破卡）

卡片**不得硬编码颜色**，只能使用宿主注入的 CSS 变量：

```css
--cockpit-bg / --cockpit-bg-elevated / --cockpit-border
--cockpit-text / --cockpit-text-dim / --cockpit-text-faint
--cockpit-accent / --cockpit-accent-2
--cockpit-ok / --cockpit-warn / --cockpit-danger / --cockpit-unknown
--cockpit-radius / --cockpit-font-mono / --cockpit-font-ui
```

换主题 = 换一套变量值 = 所有卡片跟着变，**不需要重写任何卡片**。
这条是「重新设计」这个需求能成立的技术前提，写进卡片开发规范。

### 7.6 promote（提卡到全屏）

契约上一切皆卡片，交互上允许独占：`promote_card(id)` 把卡片的 iframe 提升为
全屏窗口（独立 BrowserWindow 或 renderer 内的全屏态），共享同一套主题与白名单 API。
终端卡也支持 promote（htop/vim/tmux 在小卡里没法用——愿景原话）。

### 7.7 卡片权限与授权

| 时机 | 行为 |
|---|---|
| 卡片首次加载 | 弹出「这张卡要读 X、写 Y」的授权清单；用户勾选 |
| 卡片升级（manifest 权限变大） | 重新授权 |
| 动作被拒 | 宿主返回 `denied` 原因，卡片负责展示 |
| 全部动作 | 走 `actions/executor`，**与 GUI 按钮同一个入口**（决策 D7） |

授权记录落在 `%LOCALAPPDATA%/DevBoardCockpit/grants.json`，可随时在设置里撤销。

## 8. 控制面

```
GUI 按钮 ─┐
          ├─→ actions/executor ─→ hal.run() ─→ 板子 ─→ 回读 verify.tag ─→ UI
MCP 工具 ─┘        （唯一的写入口）
```

- **唯一写入口**：GUI 与 MCP 都不直接调 `hal.run()`，一律走 executor。
- **分级**：`read`（只读，直接放行）/ `reversible`（可逆写，需已授权）/ `destructive`（需二次确认 + 审计）。
- **dry-run**：只回显将要执行的命令与影响面，不落地。
- **审计日志**：每次执行落一行（时间、来源 gui|mcp、卡片 id、动作 id、参数、退出码、回读值），
  追加写，不覆盖。

## 9. 布局与主题

- **网格**：12 列，行高 80 px；卡片声明 `grid: {w,h,minW,minH}`，布局里可覆盖。
- **拖拽**：react-grid-layout；拖动时显示占位框；松手写回 `LayoutDoc`。
- **持久化**：布局按「工作区」保存（`%LOCALAPPDATA%/DevBoardCockpit/layouts/<name>.json`），
  支持导出/导入 → **可分享**。
- **内置卡**（宿主自带，非文件卡片）：终端卡、文件浏览器卡、日志工作区、目标切换器。
  它们与用户卡片**同一套布局**，只是不可删除。
- **主题**：见 §7.5；Ant Design 的主题变量与 `--cockpit-*` 一一映射。

## 10. MCP server

**传输**：stdio（宿主 AI agent 拉起 GUI 时注入一个环境变量指向配置即可；
也支持独立进程模式 `devboard-cockpit --mcp-stdio`）。

### 10.1 工具集（愿景那张表 + 补齐项）

| 工具 | 用途 | 备注 |
|---|---|---|
| `list_connections` | 列出连接实例 | 含 transport、capabilities、连接状态 |
| `list_data_sources` | 列出所有可订阅位号 | **能力动态出现**，不能靠静态文档 |
| `list_capabilities` | 列出各连接的能力协商结果 | shell / exec / stream / files / multiline |
| `describe_source(id)` | 运行时自省：单位、采样策略、质量、提取器、最近值 | agent 不盲写的前提 |
| `sample_source(id, n)` | 取 n 个真实样本 | 给 agent 看真实数据形态 |
| `list_cards` | 列出已加载卡片（id、订阅的位号、动作、授权状态） | |
| `get_card_sdk_docs` | 取卡片 SDK 的活文档 | 随宿主版本走，不写过时文档 |
| `validate_card(path)` | 静态校验：manifest schema、位号是否存在、动作是否存在、权限是否声明 | 写完立刻自查 |
| `get_card_runtime_log(cardId)` | 运行时错误日志 | agent 的自测眼睛 |
| `execute_action(cardId, actionId, params, dry_run)` | 触发已声明动作 | 带权限检查与 dry-run |
| `promote_card(id)` | 提卡到全屏 | |
| `get_layout` / `set_layout` | 读写布局 | 让 agent 能摆卡片 |

> `list_data_sources` 返回的是**当前连接 + 板型**合成后的位号表，
> 因此「板子上没有的东西」不会出现在列表里——这正是 agent 自省需要的。

### 10.2 为什么必须在 main 进程

见决策 D2：卡片清单、运行时日志、布局、位号表**都住在 main 进程**，
MCP server 与它们同进程 → 直接读，零延迟、零一致性风险。

### 10.3 活文档

`get_card_sdk_docs` 返回的是**宿主当前版本**的卡片 SDK 文档（随代码一起维护的一份 markdown），
而不是一份静态 PDF。这是「活文档」的含义。

## 11. IPC 契约

`src/shared/ipc-contract.ts` 定义全部通道，main 与 renderer 共用类型。

| 通道 | 方向 | 载荷 |
|---|---|---|
| `connection:list` | R→M | `TargetProfile[]` + 状态 |
| `connection:open` / `:close` | R→M | id |
| `tag:snapshot` | R→M | `{ tagIds }` → `{ [tagId]: TagValue }` |
| `tag:update` | M→R（推送） | `TagValue` |
| `tag:subscribe` / `:unsubscribe` | R→M | tagId / 订阅句柄 |
| `action:execute` | R→M | `{ cardId?, actionId, params, dryRun }` → `ActionResult` |
| `action:list` | R→M | 当前连接可用的动作 |
| `card:list` / `:validate` / `:reload` | R→M | |
| `card:event` | M→R（推送） | 卡片请求宿主能力（经白名单校验） |
| `layout:get` / `:set` / `:export` / `:import` | R→M | `LayoutDoc` |
| `log:list` / `:read` | R→M | 会话日志 |
| `settings:get` / `:set` | R→M | 宿主设置（含 adb 路径等机器专属路径） |

**约束**：

- renderer 的 `preload` 用 `contextBridge` 只暴露上述白名单方法，**不暴露 `ipcRenderer` 本身**。
- 所有跨进程载荷都是**可序列化纯数据**（无类实例、无函数），保证 main↔renderer 不共享内存状态。

## 12. 错误处理与降级

### 12.1 统一错误对象

```ts
interface AppError {
  code: string;        // 'CONN_OPEN_FAILED' | 'TAG_UNAVAILABLE' | 'ACTION_DENIED' | ...
  message: string;     // 人话，直接可展示
  retryable: boolean;
  detail?: unknown;    // 原始错误，仅日志用
}
```

### 12.2 分层降级矩阵

| 故障 | 表现 | 降级行为 |
|---|---|---|
| 板子不在 `device` 状态 | ADB 连不上 | 连接标 `offline`；位号全部 `unknown`；UI 显示 `--` 与「设备未连接」 |
| 串口被占用 | 打开失败 | 报错并指出端口；不重试风暴 |
| 位号读不到（路径不存在） | 单个位号失败 | 该位号 `unknown` + 原因；**其它位号照常**；不影响整次采样 |
| debugfs 没挂载 | `npu.utilization` 读不到 | `unknown` + 提示「需要挂载 debugfs」+ 给出可一键执行的 `debugfs.mount` 动作 |
| 板子掉线（采样中途失败） | 连续失败 | 保留最后值并标 `stale`；连续 N 次后置 `unknown` |
| 卡片 manifest 不合法 | 加载失败 | 保留上一版实例；卡片位显示「无效」+ 错误摘要；宿主不受影响 |
| 卡片运行时抛错 | iframe 崩 | 捕获写入 runtime.log；占位显示；不影响其它卡片 |
| 卡片调用未授权动作 | 被拒 | 返回 `denied` 原因；写审计；卡片自行展示 |
| 动作超时 | 执行超时 | 退出码 124；UI 保留旧值 + 标注超时 |
| 动作执行成功但回读不一致 | 写成功、状态不符 | 结果标 `ok: false` + 差异；**不假装成功** |
| MCP 客户端误用 | 参数错 | 返回结构化错误 + 提示该用哪个工具 |

### 12.3 三条不许

1. **不许把 unknown 显示成 0**（事实 G2）。
2. **不许把「命令返回 0」当成「状态正确」**——控制面的真相是回读值。
3. **不许让单个卡片/单个位号的失败波及宿主**。

## 14. 里程碑与验收判据

> 顺序原则：**先终端（最可能做不出来），后契约，最后卡片与 AI。**
> 规格线与工程线并行，规格线零返工。

| # | 里程碑 | 验收判据 |
|---|---|---|
| M0 | 工程骨架 | `npm run dev` 起得来；`lint`/`typecheck`/`test` 全绿；目录结构如 §3 |

| M4 | 卡片框架 | 第一张监控卡（CPU/温度曲线）可拖拽、可保存布局、改文件即热更新 |
| M5 | 控制卡 | 第一个 `reversible` 动作（背光/调频）走 executor，回读验证，UI 显示回读值 |
| M6 | MCP server | 上表 13 个工具可用；agent 能完成「查位号 → 写卡 → 热插拔 → 自测」全链路 |

**M1 是全项目的风险集中点**（xterm.js + node-pty + serialport 三件套同时上），

## 15. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| `node-pty` 与 Electron ABI 不匹配 | 终端起不来 | 锁 Electron 版本；`electron-rebuild` 固化进 `postinstall`；CI 里验一次 |
| 串口 marker 协议在 TS 里重写踩坑 | 命令输出串台 | 照搬旧工程 S1–S4；用真板做回归 |
| iframe 沙箱与 ESM 相对路径冲突 | 卡片加载失败 | 自定义协议托管 + `?v=` 版本参数；先写一个最小卡片验证 |
| MCP SDK 仍在演进 | API 变动 | 只依赖 `tools/list` + `tools/call` 两个稳定面；SDK 封装在 `src/main/mcp/` 一层 |
| 采样频率与 UI 渲染争抢 | 界面卡顿 | 采样在 main，UI 只收增量；单次采样节流 ≥ 250 ms |
| 板型 profile 写得不对 | 位号一直 unknown | `status: draft → verified` 强制人工核；`smoke:board` 把 unknown 当失败 |
| 卡片越写越多把宿主拖慢 | 卡顿 | 卡片 iframe 独立进程（Chromium 站点隔离）；宿主只做转发 |
