## 1. 目标与非目标

### 1.1 目标

1. **统一工作台**：串口 / ADB / SSH 三通道接入板子与 Ubuntu 客机，终端、文件互传、
   状态监控、显示输出在同一 GUI 内完成。
2. **语义 tag 契约**：板子能力 = 稳定位号；卡片只订阅位号，不关心板型。
3. **卡片系统**：卡片即文件；AI 写完即生效；热插拔；沙箱隔离。
4. **控制闭环**：写动作后回读位号，UI 以回读为准。
5. **MCP 协作**：宿主机 AI agent 通过 MCP 感知现状、写卡片、触发动作、自测迭代。

### 1.2 非目标（本期不做）

| 不做 | 理由 |
|---|---|
| 板端长期服务 / systemd | 板子是 Buildroot + eudev；Tier 2 推流留到有视频需求时 |
| 多用户 / 权限体系 | 单人桌面工具 |
| 跨平台 | 宿主是 Windows；跨平台留接口不留实现 |
| 卡片市场 / 远程分发 | 先做本地目录热插拔 |
| 与旧 Python 工程并存运行 | 明确切干净，避免两套真相 |
| **改动契约语义** | 契约是权威；要改先改 `docs/spec/` 并升 `apiVersion` |

## 2. 总体架构

### 2.1 进程模型

```
┌─ Electron main（设备、契约执行、MCP）────────────────────────┐
│  hal/       连接层 HAL：serial │ ssh │ adb │ local + 能力协商      │
│  tags/      位号层：reader kind 注册表 │ poll group 调度 │ 绑定    │
│  actions/   控制面：分级判定 → 执行 → 回读 → 审计                 │
│  cards/     卡片注册表：manifest 校验 │ 协议托管 │ 热重载          │
│  mcp/       MCP server（stdio）——与卡片注册表同进程              │
│  profiles/  连接 profile + 板型包加载与校验                       │
└───────────┬─────────────────────────────────────────────────────┘
            │ IPC（invoke/handle + 事件推送）
┌───────────▼─────────────────────────────────────────────────────┐
│ Electron renderer（只画，不碰设备）                              │
│  layout/   网格布局引擎（react-grid-layout）                     │
│  cards/    卡片宿主：sandbox iframe + `cockpit.*` 白名单桥        │
│  terminal/ xterm.js                                             │
│  panes/    文件浏览器 │ 日志工作区 │ 目标切换器 │ 资源条          │
└───────────┬─────────────────────────────────────────────────────┘
            │ postMessage（白名单，无同源）
┌───────────▼─────────────────────────────────────────────────────┐
│ 卡片 iframe：sandbox="allow-scripts"（无 same-origin）           │
│ 入口 index.html；API 见 spec/03（cockpit.tags.get / subscribe …） │
└─────────────────────────────────────────────────────────────────┘

┌─ 磁盘 ─────────────────────────────────────────────────────────┐
│ profiles/boards/<pack>/board.yaml   板型包（契约 spec/02）         │
│ profiles/targets/*.json             连接 profile（怎么连上）        │
│ cards/<card-id>/                    卡片目录（spec/03）            │
└─────────────────────────────────────────────────────────────────┘
```

**铁律**：

- renderer **永远不**直接碰设备，一律经 `tags/` 与 `actions/`。
- MCP server 与卡片注册表**同进程**（ADR D2），
  因此 agent 读到的 GUI 状态与用户看到的完全一致。
- 卡片**永远不**能触碰宿主 DOM / 存储 / 任意消息（spec/03 §三）。

### 2.2 三条数据通路

| 通路 | 方向 | 载体 |
|---|---|---|
| 采样 | 板子 → reader → tag → 订阅者 | `tag:update` 推送 |
| 控制 | GUI / MCP → actions → 板子 → 回读 | `action:execute` → `ActionResult` |
| 感知 | agent → MCP → GUI 内部 | spec/04 的工具集 |

### 4.2 移植顺序（先把纯函数搬走，再碰有 I/O 的）

```
第 1 步  vocabulary.ts   纯数据，零依赖，先搬
第 2 步  binding.ts      纯函数，模式匹配
第 3 步  readers.ts      纯函数，输入是文本
第 4 步  kinds.ts        有 shell 片段拼接，但无 I/O
第 5 步  validate.ts     纯函数 + YAML 解析
第 6 步  poll.ts / 调度   真正的 I/O，最后接 HAL
第 7 步  probe.ts        只用于人工验证
```

前 5 步可以**离线**完成并对拍（第 1~5 步的断言全在 `test_boardkit.py` 里，
样本在 `fixtures/` 与该文件内嵌的字符串里）。

### 4.3 「语义不漂移」的唯一硬判据

> TypeScript 实现必须能跑通 `reference/boardkit-python/test_boardkit.py` 里的**同一批断言**
> （同一样本、同一结果）。任何一条不一致，就是移植出错，不是「实现差异」。

为此，新工程的 vitest 里会有一组**对拍用例**：
从 `fixtures/` 读样本 → 喂给 TS 解析器 → 断言与 Python 参考实现的输出**逐字节相等**。

### 4.4 与 ADR 的关系

- ADR D5（profile 双轴）= 契约 `spec/00` 的 D5，**一致**，无需改。
- ADR D6（sandbox iframe）= 契约 `spec/03` §三的代码沙箱，**一致**。
- ADR D7（动作三档 + 回读）= 契约 `spec/03` §4.2 + §5，**一致**（契约的档位叫
  `readonly / reversible / destructive`，本文沿用契约叫法）。
- ADR D4（免构建 ESM）= 契约 `spec/03` 的 `entry: index.html` 的**实现方式**：
  入口是 HTML，其中的脚本是原生 ES Module，**不引入任何构建步骤**。两者不冲突。

## 5. 采样通路的实现

### 5.1 调度模型

契约已定：板型包用 `poll_groups` 把 reader 分组，每组一次往返、每组一个周期。

```
poll group (fast, 1000ms)  → readers [cpu, gpu, npu]  → 合成一条命令 → 一次往返
poll group (slow, 2000ms)  → readers [mem, temp]
poll group (rare, 30000ms) → readers [board, npu_devfreq]
```

- 每组内部把各 reader kind 的取数 shell 片段合并成**一条**命令，
  段间用标记分隔（等价于旧工程 `SNAPSHOT_SCRIPT` 的 `###` 分段思路）。
- **串口单行压平**：目标不支持多行脚本时（spec/02 要求 kind 片段能压成一行），
  合并结果用 `;` 连接不换行。

### 5.2 值与状态

契约定义五态（`ok / stale / unavailable / error / pending`），TS 侧一一对应：

```ts
type TagStatus = 'ok' | 'stale' | 'unavailable' | 'error' | 'pending';
interface TagValue {
  tag: string;
  value: number | string | boolean | null;
  unit: string;
  status: TagStatus;
  at: number;            // 毫秒时间戳
  reason?: string;       // unavailable/error 的原因（见 06 核对 C5）
}
```

- `pending`：**两次采样做差**的 tag（CPU 占用率）第一次读必然是 pending，
  卡片要显示「等待第一次采样」而不是转圈或 0（spec/01 §三）。
- `unavailable` ≠ `0`：**硬约束**（spec/01 §二）。

### 5.3 广播

- 采样在 main，**运行时是唯一的轮询者**（spec/03 §四）。
  卡片只订阅，不自轮询——否则每张卡各自 fork 一个 `adb shell`，
  板子会看起来 100% 忙，且 N 张卡负载翻 N 倍。
- 订阅关系按 `(connectionId, tag)` 维护；连接断开时订阅保留、值转 `unavailable`。

## 6. 卡片运行时

### 6.1 发现与托管

```
cards/<card-id>/            # 卡片根目录（用户目录 + 内置目录合并，同 id 用户优先）
  manifest.json              # 格式见 spec/03
  index.html                 # entry
  *.js / *.css / assets/     # 原生 ESM，无构建
```

- 卡片资源由 main 用自定义协议 `cockpit://card/<id>/…` 托管，
  **只允许访问卡片自己的目录**（路径穿越防护）。
- 每次加载带 `?v=<内容哈希>`，文件变了 URL 就变，缓存自然失效。

### 6.2 沙箱

```html
<iframe sandbox="allow-scripts" src="cockpit://card/<id>/index.html"></iframe>
```

- **不给 `allow-same-origin`** → 卡片在独立不透明源里，碰不到宿主 DOM / 存储。
- 宿主只认白名单方法（spec/03 §四的 `cockpit.tags.get / subscribe` 等），
  每条消息校验三件事：**来源 frame** → **方法在白名单** → **该卡片的权限**。

### 6.3 权限与降级

- 权限在**安装/加载时**确定，绑定 `(卡片 id, 动作 id, 板型包 id)`（spec/03 §3.2）。
- **卡片不能运行时提权**（spec/03 §3.3）。
- **缺 tag 照常加载**（spec/01 §五）：缺失项显式可见——
  卡片内显示「不可用 · 缺 cpu.usage」，MCP 的 `validate_card` 返回缺失清单。
  这条是 AI 迭代回路不断线的前提。

### 6.4 热插拔

```
监听 cards/**  →  读 manifest → schema 校验
   ├─ 不通过 → 保留上一版可用实例，标记「无效」，记错误日志（不炸宿主）
   └─ 通过   → 换 ?v=hash 重载该卡片的 iframe
```

卡片运行时错误由 `window.onerror` 捕获 → 写入卡片运行时日志 →
MCP `get_card_runtime_log` 可读 → **agent 的自测眼睛**（spec/04）。

### 6.5 主题 token（保证「重新设计」不破卡）

卡片**不得硬编码颜色**，只用宿主注入的 CSS 变量：

```css
--cockpit-bg / --cockpit-bg-elevated / --cockpit-border
--cockpit-text / --cockpit-text-dim / --cockpit-text-faint
--cockpit-accent / --cockpit-accent-2
--cockpit-ok / --cockpit-warn / --cockpit-danger / --cockpit-unavailable
--cockpit-radius / --cockpit-font-mono / --cockpit-font-ui
```

换主题 = 换一套变量值 = 所有卡片跟着变，**不用重写任何卡片**。
这条要写进卡片开发规范（`get_card_sdk_docs` 里也会给 agent）。

## 7. 控制面（实现 spec/03 §4、§5）

```
GUI 按钮 ─┐
          ├─→ actions/executor → hal.run() → 板子 → 回读(readback) → UI
MCP 工具 ─┘        （唯一写入口）
```

执行流程：

```
1. 查动作在当前板型包里存在吗        → 没有 = not_found
2. 查调用方（卡片 / agent）对它的授权 → 没有 = denied
3. danger=destructive 且未确认        → needs_confirmation（附一次性 token）
4. dry_run                          → 只回显「将会执行什么」
5. 执行（超时 = 124）
6. 回读（readback 三种形式：tag / file_equals / command_ok）
7. 写审计日志
```

**UI 的显示依据是第 6 步的回读值**，不是第 5 步的退出码。
回读不符 → 显示「命令已发出，未确认生效」，**不乐观显示成已开启**（spec/03 §5.2）。

## 8. 布局与主题

- **网格**：12 列；卡片在 manifest 里声明 `layout`（spec/03 §一），布局可覆盖。
- **拖拽**：react-grid-layout（ADR D3）；布局存 `LayoutDoc`，可导出/导入 → 可分享。
- **内置卡**：终端卡、文件浏览器卡、日志工作区、目标切换器——与用户卡片同一套布局，不可删除。
- **主题**：§6.5 的 token 契约；Ant Design 的主题变量与 `--cockpit-*` 一一映射。

## 9. MCP server 的落地（实现 spec/04）

**传输**：stdio。两种启动方式——
随 GUI 启动（宿主 AI agent 拉起 GUI 时注入配置），或独立进程
`devboard-cockpit --mcp-stdio`。

### 9.1 实现原则

- 工具清单**以 spec/04 为准**，本文不重复列举（避免两份定义漂移）。
- 每个工具都是**薄封装**：读 GUI 内部状态，或触发 GUI 已声明的动作。
- MCP **不做文件 IO**：agent 直接写卡片目录（spec/04 §三）——
  「MCP 是 AI 的眼睛和手，不是 AI 的硬盘」。
- 返回值遵守 spec/04 §四的共同约定：`ok: false + reason` 不抛异常、
  未知用 `status: "unavailable"` 不返回 null/0、时间用毫秒 UTC 时间戳、
  路径用绝对路径、每个响应带 `api_version`。

### 9.2 工具 → main 内部实现的映射

| 工具类别 | 落到 main 的什么 | 备注 |
|---|---|---|
| 感知现状（连接/数据源/能力） | `hal/registry` + `tags/` 的当前位号表 | 能力动态出现，不能靠静态文档 |
| 自省（描述/采样） | `tags/describe` + `tags/readers` | agent 不盲写的前提 |
| 卡片管理（列/校验/装/卸/日志） | `cards/` | 校验规则 = spec/03 §八 |
| 动作执行 | `actions/executor` | **与 GUI 同一个入口**（spec/03 §五） |
| 布局 | `layout/` | |
| 活文档 | `mcp/docs.ts` | 随宿主版本走的那份 markdown |

### 9.3 为什么必须在 main 进程

ADR D2：卡片清单、卡片运行时日志、布局、位号表**都住在 main 进程**，
MCP server 与它们同进程 → 直接读，零延迟、零一致性风险。
这也是否掉「Python 后端 + Electron 界面」双层混合的直接原因。

### 9.4 给 agent 的三条硬规则

spec/04 §五 已经写好了，**随 SDK 活文档一起给 agent**：

1. 不要发裸命令——要新能力就写板型包扩展或卡片 action。
2. 不要乐观更新 UI——动作之后一律用回读值渲染。
3. 写完卡一定要 `validate_card` + `get_card_runtime_log`。

## 10. IPC 契约

`src/shared/ipc-contract.ts` 定义全部通道，main 与 renderer 共用类型。

| 通道 | 方向 | 载荷 |
|---|---|---|
| `connection:list` / `:open` / `:close` | R→M | 连接实例 + 能力协商结果 |
| `tag:snapshot` | R→M | `{ tagIds }` → `{ [tag]: TagValue }` |
| `tag:update` | M→R（推送） | `TagValue`（五态之一） |
| `tag:subscribe` / `:unsubscribe` | R→M | 订阅句柄 |
| `action:execute` | R→M | `{ cardId?, actionId, params, dryRun, confirmToken? }` → `ActionResult` |
| `card:list` / `:validate` / `:reload` | R→M | |
| `card:event` | M→R（推送） | 卡片请求宿主能力（经白名单校验） |
| `layout:get` / `:set` / `:export` / `:import` | R→M | `LayoutDoc` |
| `log:list` / `:read` | R→M | 会话日志 |
| `settings:get` / `:set` | R→M | 宿主设置（含 adb 路径等机器专属路径） |

**约束**：

- preload 用 `contextBridge` 只暴露上述白名单方法，**不暴露 `ipcRenderer` 本身**。
- 跨进程载荷全是**可序列化纯数据**（无类实例、无函数），
  main ↔ renderer 不共享内存状态。
- `tag:update` 的载荷必须**带 status**，禁止只推数值——五态是契约的一部分。

## 11. 错误处理与降级

### 11.1 统一错误对象

```ts
interface AppError {
  code: string;      // 'CONN_OPEN_FAILED' | 'TAG_UNAVAILABLE' | 'ACTION_DENIED' | ...
  message: string;   // 人话，可直接展示
  retryable: boolean;
  detail?: unknown;
}
```

### 11.2 降级矩阵

| 故障 | 表现 | 降级行为 |
|---|---|---|
| 板子不在 `device` 状态 | ADB 连不上 | 连接标 offline；位号转 `unavailable`；UI 显示 `--` + 「设备未连接」 |
| 串口被占用 | 打开失败 | 报错并指出端口；不做重试风暴 |
| 位号读不到 | 单个 tag 失败 | 该 tag `unavailable` + reason；**其它 tag 照常**；不影响整组采样 |
| debugfs 没挂载 | `npu.usage` 不可用 | `unavailable` + reason `debugfs_not_mounted`；界面给出 `debugfs.mount` 动作按钮（见 06 核对 C5） |
| 板子掉线 | 连续采样失败 | 保留最后值并转 `stale`；持续失败后转 `unavailable` |
| 卡片 manifest 不合法 | 加载失败 | 保留上一版实例；卡片位显示「无效」+ 错误摘要；宿主不受影响 |
| 卡片运行时抛错 | iframe 崩 | 捕获写运行时日志；占位显示；不影响其它卡片 |
| 卡片调用未授权动作 | 被拒 | 返回 `denied` 原因；写审计；卡片自行展示 |
| 动作超时 | 执行超时 | 退出码 124；UI 保留旧值 + 标注超时 |
| 动作成功但回读不一致 | 写成功状态不符 | `ok: false` + 差异；**不假装成功**（spec/03 §5.2） |
| MCP 误用 | 参数错 | 结构化错误 + 提示该用哪个工具 |

### 11.3 三条不许

1. **不许把 `unavailable` 显示成 0**（spec/01 §二）。
2. **不许把「命令返回 0」当成「状态正确」**——真相是回读值。
3. **不许让单个卡片 / 单个位号的失败波及宿主**。

## 14. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| `node-pty` 与 Electron ABI 不匹配 | 终端起不来 | 锁 Electron 版本；`electron-rebuild` 固化进 `postinstall`；CI 验一次 |
| 串口 marker 协议重写踩坑 | 命令输出串台 | 照搬旧工程事实 S1–S4；真板回归 |
| iframe 沙箱与相对路径模块冲突 | 卡片加载失败 | 自定义协议托管 + `?v=` 版本参数；先写最小卡片验证 |
| **契约漂移**（TS 词表 ≠ Python 词表 ≠ spec 文档） | agent 写出互相矛盾的卡片 | §4.3 的对拍是硬判据；改词表必须三处同改 |
| MCP SDK 演进 | API 变动 | 只依赖 `tools/list` + `tools/call`；SDK 封装在 `src/main/mcp/` 一层 |
| 采样与渲染争抢 | 界面卡顿 | 采样在 main；UI 只收增量；单次采样节流 ≥ 250 ms |
| 板型包写了板上没有的路径 | 位号永远 unavailable | `probe:board` 把 unavailable 当失败；`06-契约核对.md` 记账 |
