## 一 · 提案一 · 取消（cancel）

### 1.1 契约原文

| 位置 | 原文 |
|---|---|
| `spec/05` §八·3 | **状态机**：`running` / `awaiting_confirmation` / `done` / `failed` |
| `spec/05` §八·8 | **取消**：**首版不支持**（执行原语不可中断 ✓）→ **契约里明写不支持** ✓ |
| `spec/05` §十 | **取消** —— 归在「契约里**不做**的事」里 |

### 1.2 改成什么

**§八·3 的状态机**：`running` / `awaiting_confirmation` / `done` / `failed` / **`cancelled`** ✓。

**§八·8 换成取消的七条规定**：

| # | 规定 | 为什么 |
|---|---|---|
| **C1** | `cancel(run_id)` → **在飞的那一步真的停**（执行原语可中断：先 `SIGTERM`，给它 200ms 自己退，不退再 `SIGKILL` ✓） | 「不等了」**不够** ✓ —— 尖兵实测：一个 75 秒的传输步收到取消后**照跑完** ✗（进程还在后台跑 ✓） |
| **C2** | 运行状态 = **`cancelled`** ✓（**不是 `failed`** ✓ —— 取消不是失败 ✓） | 混在一起 → 界面会把「人叫停」说成「出错了」✗；重试逻辑也会误判 ✗ |
| **C3** | **已经跑完的步不回滚** ✓ | 契约里**没有回滚**这回事 ✓ —— 回滚是另一件事（要另立契约 ✓），现在写「取消」**不带这个承诺** ✓ |
| **C4** | **只有宿主能取消** ✓（GUI 的「停一下」/ 宿主命令行 ✓）→ **卡片与 agent 没有取消接口** ✓ | 「批准」是人的事 → 不给 agent 工具 ✓（`spec/04` §2.4.1 ✓）；**取消的代价落在机器的状态上**（板子上可能留了半截东西 ✓）→ **要不要认这个账，是人的决定** ✓ |
| **C5** | 取消一个**不存在**的 `run_id` → **报错** ✓；取消一个**已经结束**的运行 → **幂等** ✓（状态不变 ✓） | 打错 id 要说清楚 ✓；重复点「停」不该炸 ✓ |
| **C6** | 取消**只影响那一次运行** ✓ | 别的运行不该跟着停 ✓ |
| **C7** | 被取消的那一步，在时间线里**理由写 `cancelled`** ✓（**不是 `failed`** ✓） | 同 C2 ✓ —— 追责时要能看出「人叫停」✗≠「机器坏了」✓ |

**§十 的「取消」从「不做」清单里去掉** ✓。

### 1.3 「取消只有宿主能做」的代价（诚实说）

- **卡片里的流程停不下来** ✗ → 用户得去**宿主界面或宿主命令行**停 ✓。
  → 宿主命令行那一族（`workflow:list` / `workflow:approve` / `workflow:revoke` ✓）加一条 `workflow:cancel -- <run_id>` ✓。
- **agent 唯一的出路**是「告诉用户我等不动了」✓ —— `workflow_status` 已经能说 ✓（状态是 `running` ✓）。

> **不选「也给 agent 一个取消」的理由**（评审可能会问这一条 ✓）：
> 取消**看着无害**（只是不跑了吧 ✓），但它有一个**不无害**的后果 ——
> **被取消的传输会留下半截文件** ✓（提案三就是在治这个 ✓）。
> → 「要不要在半截状态上继续」**是个判断** ✓ → 判断归人 ✓。
> → 而且 agent **本来就有更好的出路**：`workflow_status` 能看出「卡住了」✓，
> 由**人**决定要不要停 ✓。

## 二 · 提案二 · 在飞的那一步（**界面不能一片死寂**）

### 2.1 问题

| 事实 | 出处 |
|---|---|
| 编译实测 **58.9s / 98.5s** | 独立评审 31-C3 ✓ |
| 传输耗时**波动 20 倍**（同一份产物 0.10s ↔ 75.6s） | 尖兵 S2 ✓ / 直传尖兵 ✓ |
| 现在 `status(run_id)` 在**整个流程跑完之前只给空时间线** ✗ | 实现现状 ✓（`runner` 只在**最后**返回 `stages` ✓） |

→ 用户点完「编译上板」，界面**几十秒没有动静** ✗ → **他不知道是在跑、在等、还是死了** ✗。

### 2.2 契约原文

| 位置 | 原文 |
|---|---|
| `spec/05` §八·2 | **`status(run_id)` 轮询取时间线** ✓（首版 poll ✓） |
| `spec/04` `workflow_status` | `→ { state: "running" \| "awaiting_confirmation" \| "done" \| "failed", stages: [ { stepId, kind, ok, verified, reason?, audit_id } ] }` |

### 2.3 改成什么（**附加**一个字段 ✓）

```
→ { state: "running" | "awaiting_confirmation" | "done" | "failed" | "cancelled",
    current: { stepId, kind, role?, at } | null,     ← 新增 ✓
    stages: [ { stepId, kind, ok, verified, reason?, audit_id } ] }
```

| # | 规定 | 为什么 |
|---|---|---|
| **P1** | `current` = **在飞的那一步**：`{ stepId, kind, role?, at }`；**没有在飞的** → `null` ✓ | 「现在到哪了」是**界面最需要的一件事** ✓ |
| **P2** | `at` = 这一步**开始的时刻** ✓ → 界面能自己算「**已经用了多久**」✓ | **不给百分比** ✓ —— 传输的百分比是猜的 ✗；「已经 42 秒」是事实 ✓ |
| **P3** | **附加**字段 ✓ —— `stages` 的形状**一个字不改** ✓（`ok` 仍是布尔 ✓） | 已有的消费者（卡片侧的渲染 ✓）**不破** ✓ |
| **P4** | 卡片 API（`cockpit.workflows.status` ✓）与 MCP 工具（`workflow_status` ✓）**同一个形状** ✓ | 两处形状不一样 → 卡片与 agent 看到的东西不一样 ✗ |
| **P5** | 时间线**只增不改** ✓（§八·4「同一份时间线」**不变** ✓） | 幂等 ✓ —— 同一个 `run_id` 反复查，看到的是同一件事 ✓ |

> **`current` 与 `stages` 的分工**：`stages` 是**已经定论**的步 ✓；`current` 是**还没定论**的那一步 ✓。
> 两处**不重叠** ✓（在飞的那一步**不在** `stages` 里 ✓ —— 它的 `ok` 还没定 ✓）。

## 三 · 提案三 · 传输步**不留半截文件**

### 3.1 问题

- 尖兵 S4：**中断在板上留了 `.b64` 垃圾** ✓（尖兵 §三·F4 ✓）。
- 直传改成 `scp` 之后**不留 `.b64`** ✓，但**半截产物**照样留 ✗ ——
  `scp` 是**边传边写**的 ✓，传到一半被打断 → 目的地是个**半截文件** ✗。
- 现在：**没有取消** → 没这个问题 ✓；**一旦有了取消** → 立刻有了这个问题 ✗。

> → **提案一与提案三是同一件事的两半** ✓：**能停**，就**必须停得干净** ✓。

### 3.2 契约原文

`spec/05` §4.4 写了 `file.transfer` 的两端与 `placement` ✓；
**§八（运行语义）里没有任何关于失败后清理的规定** ✓。

### 3.3 改成什么（加到 §八 ✓）

| # | 规定 | 为什么 |
|---|---|---|
| **R1** | **传输步失败或被取消之后，目的地不得留下半截文件** ✓ | 「停得干净」是取消的一部分 ✓ —— 否则用户不敢停 ✗ |
| **R2** | **流程层负责清理它知道的那一个目的地** ✓ | 流程层知道 `to.path` / `placement` 算出来的路径 ✓；包若把文件写到**别处**，流程层**看不见也管不着** ✓（那是包自己的事 ✓） |
| **R3** | 清理**只许删「这一步动过的那个文件」** ✓ → 清理前先看目的地**变了没有** ✓（**没变就不删** ✓） | 见 §3.4 的反例 ✓ |
| **R4** | 清理**单独记一行审计** ✓（谁删的、删的哪个路径 ✓） | 删了东西**必须留账** ✓ —— 否则用户发现文件没了都不知道是谁删的 ✗ |
| **R5** | 清理**不弹确认** ✓ | 它是**这次运行自己的**收尾 ✓ —— 取消时再弹一个框 → 用户以为没停干净 ✓ |
| **R6** | 清理命令是**宿主写的** ✓（不是包给的 ✓）→ **不走**「包命令的危险地板」✓（T4 管的是**包给的命令** ✓）；但**路径只许取自这一步的目的地** ✓（包不许另给清理路径 ✓） | 地板的用途是「不让包借执行器之名跑危险命令」✓；清理命令是**宿主自己**写的、路径是**宿主自己**算的 ✓ → 走地板会把它当成包命令拦下来 ✗（而它确实不是 ✓） |

### 3.4 R3 的反例（**这一条必须有，否则会删掉用户的好文件** ✗✗）

```
to.path: /opt/x          ← 上一版的产物，本來就在那儿 ✓
这一次的传输：连都连不上（握手失败）✓ → 一个字节都没写 ✓
若无脑清理：rm -f /opt/x   ✗✗ → 把用户上一版的好产物删了 ✗✗
```

→ 所以：**传输前取一次快照（大小 + mtime）✓，传输后再取一次 ✓** →
**变了才清** ✓ → 没变就**什么都不做** ✓。

> 顺带一提：**传输前的那次快照**还有第二个用处 ✓ ——
> 它让「这一步动过它」这件事**有据可查** ✓（不是靠猜 ✓）。

### 3.5 **我自己没把握的一处**（**请评审裁定** ✓）

**场景**：传输命令**成功了** ✓，但**回读**失败了 ✗（比如 `test -f {to.path}` 那条命令在板子上没跑成 —— 板子正忙 ✓）。

| 两种读法 | 后果 |
|---|---|
| **A：清理的触发条件 = 「这一步的结果是失败」** | 回读失败 → 清理 → **把一个好好的文件删了** ✗✗（它其实是传对了的 ✓） |
| **B：清理的触发条件 = 「传输命令自己失败或被取消」** | 回读失败 → **不清理** ✓（文件可能是好的 ✓）→ 但时间线要说清楚「传了，但没验成」✓ |

**我倾向 B** ✓ —— 理由与「跨目标的判据是另一个事实」同源 ✓：
**传输成了**与**验成了**是**两个事实** ✓（`ADR-D32` D32-2 ✓）→
**其中一个不成立，不该由另一个来收拾** ✓。

> **但 B 有一个尾巴** ✓：如果传输命令**部分成功**（写了一半才断 ✓），
> 它的退出码**未必非零** ✗（`scp` 断了会非零 ✓，但别的传输工具未必 ✓）→
> → B 的触发条件可能要写成「**传输命令失败/被取消，或传输命令的退出码不可信**」✓。
> → **这一条请评审给个准话** ✓（我拿不准的是「退出码不可信」怎么在契约里表达 ✓）。
